# 費用・利用上限と provider 障害の後続計画

[実装ガイド](../README.md) / [Stage 6](../stages/stage-6.md) / [Stage 7](../stages/stage-7.md)

現行の費用予約を使う上限契約は [Usage / Cost / Cap](../../design/concrete/usage-cost-cap.md) と関連設計が定める。以下の実績ベースの停止ラインと価格の自動取得・新しい障害表示は変更提案であり、先に [要件](../../requirements/requirements.md) と設計の関連箇所を整合させる。設計の競合を実装で独断解決しない。

## U1: 上限の意味を確定する（U2・U3 の前提）

- 送信前の token 見積もりと upper-bound reservation を必須とする現行方式と、報告済み実績が設定額に達した後の次の送信を止める方式を比較し、要件・サブシステム・具象設計・interface / 永続化契約を一緒に更新する。後者を採る場合は、単発・並行中の呼び出しで設定額を超え得ること、Ene 外の請求額を制御しないことを設定と画面に明示する。
- 確定済み費用、処理中、費用不明を分け、同じ期間・対象の admission と集計を owner の不可分な境界で行う。利用量欠落・応答喪失・価格不明をゼロ円とみなさず、追加送信の保留、状況確認、明示的な再開を定義する。未知の外部作用を自動で再実行しない。不要になった予約状態・表示・API は設計変更後に整理する。
- 単発、並行、期間境界、restart、未知費用での停止を検証する。送信前見積もりを使わない場合に「厳密な請求上限」と表示しない。

## U2: 価格情報の更新と記録（U1 と並行して設計可能）

- 手書きの `FIRST_PARTY_OPENAI_RATES` を外すため、Host が取得・検証・保存する外部価格データを設計する。LiteLLM の公開モデル価格表を第一候補として、形式、利用条件、更新頻度、失敗時と不正データの扱いを確認する。LiteLLM を推論経路に追加することは前提にしない。要件と Usage / Cost / Cap 設計を更新してから実装する。
- 単価は接続先サービス・エンドポイントとモデルの組で選び、同名モデルを別 provider に流用しない。未収録なら提供元情報または明示的なユーザー単価を設計上検討し、特定できなければ料金不明とする。API の `usage` を実績の根拠にし、cached input、cache write、長文・tier 別料金など既存の三単価で計算できない条件を洗い出して必要な利用量と価格形式を決める。
- 呼び出し時点の価格とデータ版を保存し、更新後に過去の費用を再計算しない。画面では Ene 算出額と provider 請求額を区別する。更新失敗・不正・未収録・利用量欠落、同名モデルの異サービス、過去スナップショットを検証する。

## U3: 利用量・上限画面（U1 の意味確定後、U2 と並行可能）

- 今日・今月などの対象期間と基準時刻、記録済み費用合計・不明件数・明細を区別する。期間集計は owner の bounded query で行い、先頭ページの合計を全期間と表示しない。
- 明細に入力・cached input・出力 token、料金内訳、状態、時刻、用途を出す。利用量未取得と価格未設定を区別できる範囲で説明し、推定と確定を混ぜない。
- system / provider の日次・月次 cap について、現在値、記録済み、処理中・不明、停止、次の UTC 境界を示す。選んだ cap の現在値を読み込んで編集し、未設定・設定済み・編集中を区別する。保存・stale を即反映し、正数制約を Host と GUI で一致させる。解除が必要なら要件・設計・command を先に定め、0 を暗黙の解除にしない。
- U1 で確定した上限の意味と、Ene と provider 側の請求・上限の範囲の違いを利用者へ表示する。日本語・英語、未設定、未知費用、ページング、stale、restart を GUI で確認する。

## U4: チャットへ provider 障害を伝える（U1～U3 と独立）

- provider 応答の許可されたエラー分類を inference → dialogue → Desktop まで保つ。OpenAI の spend / approved usage limit、プリペイド残高不足、一時的 rate limit と、認証・通信失敗、Ene 内の cap を混同しない。互換 provider の未知コードを上限と断定しない。外部 API のコード体系を実装時に公式資料で照合する。
- 利用者へ原因と次の行動を短く示し、生の HTTP body、API key、prompt、個人情報は UI・ログに出さない。送信前の確実な拒否と送信後の成否不明を分け、通信失敗時に自動再送しない。
- 少なくとも provider 429 の上限系と短時間 rate limit、認証・接続失敗、結果不明、Ene cap で異なる案内をテストし、チャット画面の失敗表示へ接続する。
