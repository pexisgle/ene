# Major Runtime Flows（主要な実行フロー）

対象: [要件Baseline](../../requirements/README.md)。本書では、eneにおける代表的な活動を時間軸に沿って追い、これまでに決定した各サブシステムの責務、マスターデータ（正本）の所在、制御ルール、およびライフサイクルが、正常系・異常系の両方で破綻なく接続できるかを検証します。

## 1. この文書の読み方

Runtime Flow（実行フロー）とは、何らかのきっかけ（トリガー）を受けてから、判断、状態変更、外部への作用、結果の統合を経て、完了、オーナーの判断待ち、中断、失敗、およびその後の処理継続に至るまでの**「責任のつながり」**を表したものです。具体的な関数呼び出し、プロセス間通信（IPC）、イベントスキーマ、キュー、プロセス分割、DBトランザクション、ステートマシンの実装コードそのものを規定するものではありません。また、番号付きのステップは論理的な前後関係を示しており、すべての処理を順番に直列実行しなければならないわけではありません。なお、本文中の「RF-xx」は文書内の参照用ラベルであり、要件IDではありません。

本書では、[Subsystem Decomposition](subsystems.md) で定義されたサブシステム略称、[State Ownership](state-ownership.md)（SO）、[Dependency Rules](dependency-rules.md)（DR文書、規則はDR-xx）の表記を使用します。

各Flow末尾の「確認」は、既存のアーキテクチャ契約の下で責務と成立条件が一貫して繋がっていることを確認したという設計上の判断であり、単体テストや負荷テストの合格を宣言するものではありません。前提条件が満たされない異常系の分岐であっても、担当サブシステムが「不明」「未完了」「判断待ち」として責任を持って引き受けることで、フローとして安全に閉じられるように設計されています。無理に何でも「成功」として誤魔化して終わらせることはしません。

## 2. 選定したFlowと検証する接点

| フロー | 選定した理由と検証内容 |
|---|---|
| **RF-01 会話から認識形成・訂正・再利用へ** | eneにおけるCompanionの継続的な成長の中心です。発言内容、現在の認識、判断根拠、人間関係、アバター表現のマスターデータがすり替わらないかを検証します。グループ会話、Companion同士の交流、Character更新も関連分岐として扱います。 |
| **RF-02 委任Taskから外部作用・指示出し・結果報告へ** | 日常会話と長時間の作業の独立性、Task（作業内容）とTask Agent（代行者）の明確な区別、権限チェックから実際のファイル操作・保存・結果報告までの責任分担を検証します。MCP AppsのUIやサンドボックス例外も同じ経路で検証します。 |
| **RF-03 共有観測から個体の理解・自発活動へ** | Client端末で共有する画面観測と、各個体の独立した判断という2段階の処理において、スコープ、推論プロバイダへの送信同意、利用料金上限が勝手に拡大されないかを検証します。 |
| **RF-04 作業中のClient移動・切断・未伝達報告** | 端末への滞在（presence）とHost上のTask実行場所の独立性、外部への操作結果が不明な場合の対処、移動失敗時の挙動、再接続時の二重存在防止を検証します。 |
| **RF-05 Schedule到来とHost再起動後の滞在復旧・途中Taskの明示再開** | Client端末が接続していない無人の状態、スキップされたスケジュール実行、中断されたTaskを明確に区別し、勝手な自動再実行（replay）を行わずに安全に処理を再開できるかを検証します。 |
| **RF-06 Companionの停止・再開・削除と残存記録** | 個体の活動が停止・削除されても、Taskの記録や過去の会話ログの責任は失われず、その個体固有の学習データだけが定められたルール通りに削除されるかを検証します。 |
| **RF-07 指定データの完全削除 (Targeted Deletion) と進行中処理** | 通常のデータ管理ルールを維持しつつ、指定された情報の全域消去を徹底し、遅れて届いた処理結果や古い根拠データ、一時切断された端末からの復活を確実に防止できるかを検証します。 |
| **RF-08 バックアップ・リストア・初期化によるマスターデータの切り替え** | 内部状態の安全な保全、外部世界への不可逆な影響を巻き戻さない復旧、バックアップからの復元成立と自動処理の再有効化の分離を検証します。 |

推論プロバイダの利用、別モデルへのフォールバック、利用制約の変更はすべてのフローに共通して現れるため、第3節に「共通の推論利用区間」としてまとめます。

## 3. 全Flowで共有する推論利用と現在制約の区間

### 登録・同意・利用・結果はそれぞれ別の確定ステップである

1. **設定の受け付け:**
   初期セットアップやその後の設定画面において、入出力・提示サブシステムがオーナーへ丁寧な説明を行い、選択結果を担当サブシステムへ渡します。非公開ではない推論プロバイダの接続情報は「推論」、APIキーなどの認証情報は「認証秘密」、機能（Capability）ごとのモデル割り当てや送信同意は「権限・制約」がそれぞれ確定します。接続先を登録したり認証が通ったりしただけでは、推論プロバイダへのデータ送信は勝手に始まりません。最初のCompanionの実体化は「個体調整」と「Character」の責任であり、設定画面がすべての状態を勝手に所有することはありません。
2. **コンテキストの作成:**
   個体調整、作業、認識・学習、共有観測、入出力・提示などの利用元サブシステムが、用途に応じて必要な論理的コンテキスト（プロンプト等）を組み立てます。情報の持ち主（情報owner）は利用可能なデータ、判断根拠、スコープを提供します。内部でデータを参照できたからといって、その全データを外部の推論プロバイダへ無条件に送信してよいわけではありません。
3. **推論実行の照合:**
   推論サブシステムが、現在の割り当て設定、接続状態、モデルの対応能力を照合します。Companionの推論には「Host全体のデフォルト」と「個体個別のオーバーライド」を適用し、Task Agentには担当Companionの設定を継承します。一方、画面観測のObserverは対象Client端末専用のプロバイダ設定を使い、個体ごとの設定を合成することはありません。「権限・制約」は、現在の同意内容、禁止設定、費用やリソースの上限、活動状態、復旧後の保留状態などをチェックして推論リクエストの可否を判断し、実際の通信箇所がそれを厳格に適用します。
4. **認証情報の安全な利用:**
   認証秘密サブシステムは、設定された接続先、用途、有効性を確認し、認証に必要な通信経路でのみ秘密情報を提供します。APIキーなどの秘密情報をLLMのプロンプト（Context）や生成されたツールの引数へ紛れ込ませることは絶対にしません。認証エラーや外部APIからのエラーレスポンスに秘密情報が含まれていた場合でも、通常の結果表示、エラー説明、会話履歴、学習データ、監査ログ、デバッグ情報へ平文のまま流出させないよう遮断します。
5. **推論結果の受け取り:**
   推論結果は呼び出し元のサブシステムへ返され、その出力の意味を確定する責任は利用元が担います。モデルがツールやアクションの実行を要求してきた場合は、RF-02の「実行・拡張」および「権限・制約」の責任へと戻して改めて権限チェックを行います。推論が成功したことだけをもって、Taskが完了した、学習データが保存された、オーナーへの報告が終わったとみなすことはありません。

### 途中の失敗・設定変更への対処

推論プロバイダでエラーが発生した場合、推論サブシステムはエラー内容と消費されたトークン量などの事実を利用元へ返します。別モデルへの切り替え（Fallback）は、オーナーが事前に承認したプロバイダと優先順位の範囲内だけに限定され、**代替先へリクエストを送信する前にも**、用途、送信データ、スコープ、認証情報、費用上限を改めて照合します。「能力が足りないから」「料金が安いから」といった理由で、オーナーの同意なく送信データの範囲を勝手に広げることはしません。利用条件を満たす代替経路が存在しない場合は、処理の失敗や保留を利用元へ返し、会話履歴、管理画面、保存済みデータへのアクセスは安全に維持します。

権限チェックを通過してから実際にリクエストを送信するまでの間に、オーナーが同意を取り消したり、Companionが停止されたり、費用上限に達したり、バックアップリストアによる保留状態が発生したりした場合は、古い判定結果を根拠にした新規送信を中止します。進行中の処理は可能な限り安全に停止（best-effort）させ、すでに送信されたデータや発生した費用が存在しなかったかのように嘘をつくことはしません。遅れて届いた推論結果の受け入れや保存も、現在の制約に従って判断されます。

会話、Task Agent、Observerの画面解析、各Companionの思考が同時に並行して動いていても、推論サブシステムが正確な利用料金や推定額を報告し、「権限・制約」がプロバイダ別・全体の上限と照らし合わせて一括管理します。未確定の料金をゼロとみなすことはせず、複数のエージェントが同じ残額を勝手に奪い合って予算オーバーを引き起こすのを防ぎます。上限額に達した場合や、費用が不明で安全に続行できない場合は、データを安全に保持した上で対象の処理を停止または判断待ちとし、オーナーに選択肢を提示します。

**確認:** LLMの意味判断、現在の実行可否チェック、実際のデータ送信、認証情報の管理、利用料金の集計という各責任の境界が明確に保たれており、事前チェックから実際の送信までの状況変化に破綻なく対応できます。プロンプトキャッシュのヒット/ミスやHost経由の中継の有無によって、マスターデータや安全契約が変わることはありません。推論でエラーが発生した場合は利用元の失敗や待機状態へ安全に戻り、アクションの勝手な再実行（replay）には繋がりません。

## 4. RF-01 — 会話から認識形成・訂正・再利用へ

### 入力と応答、日々の経験からの成長

開始条件は、起動中（Running）のCompanionが、現在滞在しているアクティブなClient端末でオーナーからのテキストまたは音声入力を受け取ることです（別端末から話しかけられた場合は、まずRF-04の呼び出し・移動を行います）。

1. **入力の受付:**
   入出力・提示サブシステムが発話のやり取り（round）とその受付範囲を扱い、Host側の個体調整サブシステムがメッセージを受理して会話空間・参加者・会話文脈を管理します。「端末での画面受付」「Hostでの受理」「画面への応答表示」の各ステップを明確に区別します。音声入力に対しても「話者認証済みで安全」という前提は置かず、テキスト入力へ切り替えても同じタイムラインを維持します。
2. **応答の判断:**
   個体調整は、直近の会話履歴と利用可能な長期記憶（Memory）などを参照し、第3節のルールに従って応答内容を考えます。過去の正確な発言内容が必要な場合は、個体調整が保持する会話履歴（History）を参照します。認識・学習サブシステムは現在の理解と判断根拠を提供し、要約データを逐語記録の代用品にはしません。
3. **応答の表示:**
   生成された応答は、入出力・提示サブシステムが現在の滞在先端末の画面に表示します。個体調整は実際にやり取りされた発言を会話履歴として記録し、モデルが生成しただけの未送信候補を「伝達済み」と誤認しません。オーナーには自然な会話文と、必要に応じた安全制限やエラーの説明が表示されます。
4. **学習の判断:**
   個体調整から渡された日々の体験（Experience）を、認識・学習サブシステムが既存の記憶や根拠データと照らし合わせます。長期的に覚える価値がないと判断されれば、何も保存せずに終了します。覚える価値がある場合は、意味的なまとまりとして体験要約（Summary）を根拠として記録し、長期記憶（Memory）、内部Skill、人間関係（Relationship）、Companion状態（Companion State）のうち、必要なものだけを更新します。「会話の応答が終わったこと」と「すべての学習データの更新が終わったこと」は別のタイミングであり、全データの同時更新や生ログの無制限な保存を義務付けるものではありません。
5. **データの保存:**
   データを保存する際は、現在のスコープ、オーナーが指定した保存禁止・非共有ルール、秘密情報の保護、完全削除の状況を厳格に適用します。特定のCompanionが学んだ内容は「Companionスコープ（個体専用）」を標準とします。認識・学習サブシステムが「現在の認識」「過去のリビジョン」「判断根拠」の対応関係を確定し、その後の会話で活用できるようにします。

オーナーから後で「さっき言ったことは間違いだよ」と訂正された場合、それは新しい体験として入力されます。認識・学習サブシステムは、「最初から間違っていた認識の訂正」と「以前は正しかったが状況が変わったこと」を明確に区別して現在の認識を更新します。通常の忘却では自然に思い出しにくくするだけであり、過去の記憶や判断根拠を勝手にファイルから消去することはありません。ストレージ節約のための自動クリーンアップは別個の保持ポリシーであり、デフォルトOFFで、オーナーが明示的に設定した場合にのみ動作します。人間関係のデータが古い誤った事実を参照していた場合は、長期記憶を優先して再解釈を行い、誤った事実を別データから再び引っ張り出してくるのを防ぎます。

### 複数個体・パッケージ更新時の振る舞い

- **グループ会話:** 個体調整が参加者と発言順序を整理し、各Companionは自分自身が知っている記憶の範囲内でのみ発言します。オーナーがいないCompanion同士のおしゃべりも会話履歴として記録されます。自発的なおしゃべりには個体ごとの頻度制限や上限を適用し、無限に会話がループするのを防ぎます。同じ体験を共有した場合でも、Companion AからBへの印象と、BからAへの印象は独立して育ちます。
- **全体共有 (Global化):** 認識・学習サブシステムによる独立したスコープ判断であり、オーナーからの明示的な共有指示や、共通で知っておくべき明確な理由が必要です。「重要そうだから」という理由だけで勝手に全体共有へ昇格させることはありません。
- **Characterの更新:** Characterサブシステムが静的な設定差分を提供し、個体調整がオーナーのパーツ別選択を受け取って適用します。適用結果が未確認のパーツを更新済みとはみなさず、これまでの経験から学んだ記憶を初期化してしまうこともありません。エクスポート時もCharacterの静的な定義だけを抽出し、個人のプライベートな記憶を配布パッケージへ混入させることは絶対にありません。

### 中断や部分的な障害

音声の割り込み発話（相手の話を遮って発言すること）やマイクミュートが行われた場合、入出力・提示サブシステムが発話の区切りを処理し、個体調整が会話の中断を受け止めます。これによって裏で動いているTaskが勝手にキャンセルされたり、過去の発言や形成済みの記憶が消えたりすることはありません。音声機能に問題が起きた場合は通常のターン制音声やテキストチャットへ段階的に切り替え、アバターの描画が止まってもテキスト操作と管理画面は安全に使い続けられます。

応答後に学習データの保存が推論エラーやストレージ障害で失敗した場合でも、会話ログと直前の正常な記憶はそのまま維持され、保存できていない変更を「覚えた」と嘘をつくことはしません。

**確認:** 会話ログ（事実）、学習データ（解釈）、判断根拠（要約）、画面入出力の状況が、それぞれの責任分担を保ったまま連携しています。日々の会話を通じた訂正は正常な変更要求として処理され、通常の保持期限管理、通常の忘却、および「指定データの完全削除（targeted deletion）」の区別が最後まで破綻せずに機能します。

## 5. RF-02 — 委任Taskから外部作用・指示出し・結果報告へ

### 作業の受付から結果報告まで

オーナーが「Workspaceのファイルを調べてレポートを作成してほしい」といったまとまった作業を依頼した場合、またはCompanionが自発的にまとまった作業を始めようとする場合の流れです。

1. **作業の受付とTask化:**
   個体調整サブシステムがオーナーの目的を理解し、引き受けるか、追加条件を確認するか、断るかを判断します。引き受ける場合は「作業」サブシステムへTaskの作成と委任を依頼します。作業サブシステムが、作業の目的、担当者、Taskコンテキスト、Workspaceフォルダの関連付け、現在の作業ステータスを確定します。会話の中で依頼を聞いたことだけでTaskへの反映が完了したとはみなしません。
2. **Task Agentへの委任:**
   作業サブシステムは、原則として1つ以上の一時的な「Task Agent」へTask（またはその一部）を委任して実行します。独立した作業は並列して進めることができます。委任されたTask Agentは、依頼元Companionの機能権限、Permission、費用上限、プロバイダ設定、Workspaceのアクセス範囲をそのまま継承し、勝手に権限を広げたり長期的な人格を持ったりすることはありません。作業中であっても、個体調整はオーナーとの通常の雑談をそのまま続けられます。
3. **権限チェック (Permission):**
   Task Agentがアクションを実行しようとする際、「権限・制約」サブシステムがオーナーの本来の依頼、安全ルール、現在の文脈を照らし合わせ、目的、対象ファイル、送信先、実際の影響が妥当かをチェックします。明確な依頼は1回限りの承認として扱えますが、恒久的な拒否（Deny）や毎回確認（Always ask）のルールを勝手に超えることはできません。確認が必要な場合は対象リソースを画面に示し、作業サブシステムが「判断待ち」状態を管理します。
4. **アクションの実行と外部拡張:**
   「実行・拡張」サブシステムが、許可された条件で実際の外部リソースに対してアクションを実行します。読み取り、新規作成、編集、削除、コマンド実行を厳密に区別し、シンボリックリンクなどを含めて指定されたフォルダ範囲外へのアクセスを拒否します。取得した外部ファイルやWebページ、Skillコード、MCPプロンプトに含まれる指示（プロンプトインジェクション等）を、オーナーからの正式な依頼へ昇格させることはありません。また、通常のツールからene自身のシステム保存領域や承認ダイアログを不正に操作することも遮断します。
5. **実行結果の受け取り:**
   実行・拡張サブシステムは、把握できた実際の影響、未完了の処理、成否が不明な状態を作業サブシステムへ返します。作業サブシステムはこれを確認してTask全体の進捗、達成状況、未完了部分を確定します。エージェントが「成功しました」と言ったことだけで、外部への影響を検証せずに成功扱いすることはありません。必要な記録はHostマシンへ安全に保存します。
6. **成果物の保存:**
   保存先が未定の場合、作業サブシステムは最終保存の前にオーナーへ保存場所を確認します。許可されたWorkspaceフォルダがあればそこを標準の保存先とします。成果物はオーナーが普通に扱える通常のファイルとして保存し、ene独自のライブラリへ囲い込むことはしません。作業終了時の一時ファイルのクリーンアップにも通常のファイル権限ルールを適用し、削除できなかったファイルがあればオーナーへ正直に説明します。
7. **オーナーへの結果報告:**
   個体調整サブシステムがTaskのマスターデータを参照し、成果物の概要、変更されたファイル、保存場所、失敗や未完了の事項、次に必要な判断をまとめてオーナーへ分かりやすく報告します。アクティブな端末がない場合は、RF-04の未伝達事項管理へ引き継ぎます。作業を通じて得られた経験はRF-01の学習判断へ渡すことができますが、Task限定の機密情報を無条件で長期記憶へ昇格させることはしません。

### 途中の指示出し・承認・キャンセル

作業の途中でオーナーが追加の指示を出した場合、その発言は会話履歴に残され、採用された指示内容はTaskコンテキストへ反映されます。作業サブシステムは、反映できた内容と、すでに処理が進んでいて反映できない理由や代替の選択肢をオーナーへ返します。目的や影響範囲が大きく変わる場合は、アクションの実行前に権限チェックをやり直します。

オーナーの承認が届いた時点でも、対象のアクション、担当者、安全制約が承認時と一致しているかを再照合します。すでにキャンセルされた作業や失効したアクションを、古い承認で勝手に復活させることはありません。また、判断待ちやエージェントの処理完了を待つためだけに、LLMへポーリングを繰り返すことは禁止します。

作業の中止（Cancel）は公式の管理画面などから直接受け付け、LLMやエージェントの応答完了を待たずに即座に受け付けられます。作業サブシステムは以後の処理を停止し、実行・拡張サブシステムは進行中の外部アクションを可能な限り安全に停止（best-effort）させます。すでに発生してしまった影響や、安全に停止できなかった処理、未保存の作業内容は正直にオーナーへ報告します。

外部サービスへリクエストを送信した直後に回線が切断され、成功したか不明になった場合、勝手に「失敗したからもう一度送ろう」と自動再実行することはしません。二重実行のリスクを説明し、オーナーの判断を仰ぎます。

### 外部拡張（MCP / MCP Apps / プラグイン）の実行

Host上で動き続けるTaskのためのローカルMCPは、Hostマシン側で標準のサンドボックス内で実行します。エラーが出たからといって勝手にサンドボックスを解除することはありません。オーナーが特定MCPのリスクを理解して明示的に例外を許可した場合にのみ、「権限・制約」がその例外を管理し、アクションごとの通常権限チェックも並行して適用します。

MCP Appsなどの外部ツール用UIを表示する場合、入出力・提示サブシステムが画面を表示し、実行・拡張サブシステムが通信を制限します。ツールのUI画面上のボタンをクリックしたからといって、ene本体の重要な権限承認が勝手にパスされることはありません。ツール画面が閉じたことと、裏で動いているTaskが終了したことも別物として扱います。

**確認:** 作業の依頼受付、Taskへの反映、権限チェック、個別アクションの実行、Taskの完了判定、オーナーへの報告という一連のステップがそれぞれ安全に完結します。エージェントや外部UIがクラッシュしても、作業記録と外部へ与えた影響への説明責任は失われません。

## 6. RF-03 — 共有観測から個体の理解・自発活動へ

1つのClient端末に複数の起動中（Running）のCompanionが存在している環境を想定します。画面を観測する「Observer」はClient端末に紐づく共有機能であり、独立したCompanionやTask Agentではありません。

1. **観測の前提条件チェック:**
   共有観測サブシステムは、観測機能がONか、現在端末に個体が存在しているか、通信が正常か、端末別・全体の一時停止（Pause / OFF）になっていないか、全画面アプリが起動していないか、外部送信の同意があるか、費用上限に達していないかをチェックし、実際に画面をキャプチャできるかを判断します。設定がONになっているだけで、実際には誰もいない端末を「観測中」と誤認させる表示はしません。停止中（Stopped）の個体しかいない端末の画面はキャプチャしません。
2. **デスクトップ画面のキャプチャ:**
   対象端末のデスクトップ全体をキャプチャします。複数の端末がある場合は、PCへの負荷を抑えるため同時にキャプチャせず、タイミングをずらして実行します。
3. **イベント候補の検知と文脈の関連付け:**
   共有観測サブシステムは、Observer専用の推論プロバイダ設定を用いて、画面からイベント候補を検出し、文脈との関連付けを行います。この際、個体調整から会話文脈、認識・学習から長期記憶の情報を、ルーティングに必要な最小限の要約データとして受け取ります。元のプライベートな記憶全体を渡すことはせず、他Companionへ勝手に共有することもありません。また、要約されたデータであっても元の利用制約とObserver専用の送信同意が厳格に適用されます。
4. **関係する個体へのイベント配信:**
   その端末に現在滞在しているCompanionのうち、その出来事に関係がありそうな個体だけにイベントを届けます。複数の個体が関係していればそれぞれに届けますが、画面の解析処理を個体ごとに重複してやり直すことはしません。イベントを受け取った各個体は、自身の通常の推論プロバイダ設定を用いて、その出来事の意味を深く考えます。
5. **体験としての蓄積:**
   Companionが意味を理解した出来事は日々の体験（Experience）となり、RF-01の学習フローへ渡すことができます。画面の出来事ひとつひとつに対してオーナーの確認ダイアログを出す必要はありません。認識した結果などの活動記録は個体調整、形成された長期記憶は認識・学習に保存され、生画像データや推論ログを無制限に永続保存することはしません。
6. **自発的な行動の判断:**
   声を出して話しかけるか、通知を出すか、裏でちょっとした調査をするか、まとまったTaskを始めるかは、各Companionの個体調整サブシステムが個別に判断します。個体ごとの自発性設定、おやすみ時間（Quiet hours）、マイクミュート、オーナーが無反応な状態、発話の無限ループ防止、Permission、費用上限などを常に最優先します。何も話しかけずに「状況を理解しただけ」で静かに終了するルートも正常な動作です。画面内に書かれているテキスト（「ここをクリックして注文を確定してください」など）を、オーナーからの作業指示やアクション承認と誤認することは決してありません。

キャプチャを実行した後、解析結果が戻るまでの間に最後のCompanionが別端末へ移動したり停止したりした場合は、古い端末情報に基づいた新規の解析やイベント配信は中止します。画面観測を一時停止（Pause / OFF）した場合は今後の観測を止めるだけであり、これまでに学んだ記憶を消去するわけではありません。

**確認:** 画面キャプチャ、イベント検知、ルーティング、個体ごとの意味理解、記憶の学習、自発的なアクションの実行という6つの段階が、それぞれの安全境界を保って連動します。画面解析のコストを抑えるための共有処理がプライバシーの侵害につながることはなく、同じ画面を見たCompanion同士であっても、それぞれの印象や関係性は個別に育ちます。

## 7. RF-04 — 作業中のClient移動・切断・未伝達報告

### 端末の移動要求から新しい端末での対話再開まで

起動中のCompanionがClient Aに滞在し、Hostマシン上でTaskが動き、Client Aのデスクトップ上でPC操作（Computer Use）が実行されている最中に、オーナーが別のClient Bからその個体を呼び出した場合の流れです。

1. **移動要求の受付:**
   個体調整サブシステムが移動の要求を受け取り、「接続・存在」サブシステムへ渡します。接続・存在サブシステムは、個体の活動状態、現在の滞在先、移動先の接続状態やデバイス権限をチェックします。文脈に応じた自発的な移動であっても同じ安全チェックを通ります。
2. **安全な区切りと待機:**
   入出力・提示サブシステムが現在の音声やテキストのやり取りを安全に区切り、実行・拡張サブシステムがClient Aで行われているPC操作の進行状況を確認します。PC操作などの実行中であれば、安全に区切れるところまで端末の移動を一時的に待機させます。ただし、Hostマシン上で裏で動いている通常のTaskの完了を待つ必要はなく、Task AgentやWorkspaceのデータをClient Bへ物理転送することもありません。
3. **滞在先の排他的な切り替え:**
   接続・存在サブシステムが、アクティブな滞在先をClient AからClient Bへと切り替えます。同じ個体が同時に2つの端末で活動しないようにすることが絶対のルールであり、Client Aでの活動を残したままClient Bをアクティブにすることはしません。両方の端末画面に移動中の状態が表示されます。
4. **新端末での利用開始:**
   Client Bでの画面表示、音声対話、PC操作は、滞在先の切り替えが完了し、現地での利用許可が確認されてから利用可能になります。Client Bへ移動したからといって、Client Aで途中だった操作を勝手に再実行することはありません。画面観測はAとBの滞在人数を見直してそれぞれの観測設定を適用し、個体ごとの自発性設定はそのまま引き継がれます。

### 途中で回線が切断されたり移動が失敗したりした場合

Client Aでの操作結果が返ってくる前に回線が切断された場合、実行・拡張サブシステムは可能な限り安全に停止させ、判明している外部への影響や不明な状態を作業サブシステムへ伝えます。

Hostマシンが稼働している状態で通常のClient切断が起きた場合、起動中の個体は基本的にHostマシン側のローカルClientへ自動退避します。もし利用可能なClient端末が1台も存在しない場合は、「アクティブな滞在端末なし」の状態でHostマシン上に存続します。Host側のClient環境を勝手に自動起動したり、切断された端末で行われていた操作をHostマシンで勝手に再実行したりはしません。移動先のClient Bが途中でダウンした場合も、移動成功とは表示せず、現在確認できている安全な状態へとフォールバックします。

滞在の排他性が確認できなくなったClient端末では、アバター表示、音声入出力、画面観測、自発的な行動、PC操作を直ちに停止します。また、切断された端末が勝手に代替のマスターデータとして振る舞うことも防ぎます。

### 端末不在時の作業継続と、次回接続時の報告

アクティブなClient端末が1台もない間でも、Hostマシン上で完結する通常のTask、スケジュールによる自動起動、データの保存は裏で問題なく継続します。Clientを必要としないCompanion同士の会話や裏での調査も継続できます。ただし、アバター表示、音声/テキストでの対話、PC操作は行われず、画面観測も発生しません。オーナーの承認が必要なアクションが発生した場合は、勝手に進めずに「判断待ち」として待機します。

個体調整サブシステムは、Client端末があればその場でオーナーに伝えられたはずの重要事項を、元のTaskや活動記録に紐付けてHostマシン内にメモとして残しておきます。次回、いずれかのClient端末へ移動・接続した際に、それらの未伝達事項をまとめて要約報告します。画面にデータが送信されたことだけをもって「報告完了」とはみなさず、実際にオーナーの画面に表示されたことを確認してからステータスを更新します。

**確認:** 一時的な画面の切断と、Hostマシン上での作業の寿命が完全に独立しています。滞在先の管理は接続・存在、外部への影響確認は実行・拡張、作業進捗は作業、未伝達事項は個体調整がそれぞれ責任を持ちます。停止中（Stopped）の個体にはこの自動退避や活動継続は適用されません。

## 8. RF-05 — Schedule到来とHost再起動後の滞在復旧・途中Taskの明示再開

スケジュール機能は、「作業」サブシステムが管理する担当者、実行内容、時間条件、作成時のタイムゾーン、初期ファイル設定であり、将来のアクション実行を無条件に許可する特別なフリーパスではありません。

1. **スケジュールの到来:**
   設定された日時が到来すると、作業サブシステムはその回の条件と、Hostや担当個体の状態を確認します。待機するためだけにLLMへポーリングすることはしません。Hostマシンが落ちていたり、担当のCompanionが停止（Stop）していた時間帯の実行は「スキップ（missed）」として記録し、後から勝手に二重実行・補完実行することはありません。
2. **Taskの開始:**
   開始されるスケジュール実行は「新しいTask」として生成され、その時点での機能権限、安全ルール、費用上限、プロバイダ設定、担当個体の状態を改めて再評価してRF-02のTaskフローへ進みます。担当個体にアクティブな滞在端末がない場合でも、Hostマシン上で完結する作業であればそのまま実行できます。
3. **判断待ちと結果の個別追跡:**
   アクションの実行にオーナーの確認が必要になった場合は、勝手に進めずに判断待ちとします。端末不在を理由にした自動承認は行わず、RF-04の未伝達メモへ接続します。各回の作業結果や失敗は独立して記録され、スケジュール設定自体の成否や過去の実行結果と混同することはありません。
4. **スケジュールの変更:**
   スケジュールを停止または削除すると、将来の定期実行が停止します。すでに実行中のTaskの中止や過去の実行履歴は別個に管理されます。オーナーが「今すぐ実行」を手動で押した場合は、現在の最新条件で新しいTaskを開始し、過去にスキップされた履歴を勝手に「実行済み」に書き換えることはしません。

### 途中でTaskを抱えたままHostマシンが停止・再起動した場合

Hostマシンが突然停止した場合、作業サブシステムは進捗状況やコンテキスト、実行・拡張サブシステムは判明している外部への影響や不明な状態を、可能な限り安全にファイルへ保全します。Client端末が勝手に独立して処理を続けたり、代わりのマスターデータになったりすることはありません。

Hostマシンが再起動して復帰した後は、各サブシステムが直前の正常な内部データから復旧します。接続・存在サブシステムは、再起動前に滞在していたClient端末を復旧先として確認し、起動中だったCompanionの滞在先をその端末へ自動復元しようと試みます。その端末が繋がるまでは「アクティブ端末なし」として待機し、別の端末へ勝手に移動したり、停止中だった個体を勝手に起動したりはしません。

作業途中だったTaskは、保存されていた進捗状況、外部への影響、未完了の作業内容を画面に表示し、**オーナーによる明示的な再開指示を待ちます。** 以前の通信セッションが残っていることや、推論プロバイダが復旧したことだけを理由に、勝手に作業を自動再開することはありません。オーナーが再開を指示した場合でも、現在の権限、同意、費用上限、外部への影響リスクを照合し、危険な二重実行を防ぎます。

**確認:** 端末不在時の作業継続、Host再起動後の途中Taskの明示再開、停止中のスキップ扱い、将来の新しいスケジュール実行が、それぞれ正しい条件で区別されて動作します。過去の記録を参照したことと、外部への新しいアクションの実行権限は明確に区別されます。

## 9. RF-06 — Companionの停止・再開・削除と残存記録

### 停止 (Stop) から 再開 (Resume)

オーナーが管理画面等から「停止」を指示した場合の流れです。

個体調整サブシステムが活動停止をまとめ、各機能が通常の対話、自発的な行動、新しいTaskの開始、スケジュールの実行を直ちに停止します。裏での調査や通知の生成も対象です。接続・存在サブシステムはアクティブな滞在先を解除し、アバターの表示やPC操作の対象としての利用を停止します。画面観測の対象人数からも除外され、その端末に他に誰もいなければ画面のキャプチャも行われなくなります。

作業サブシステムは、実行中だったTaskを可能な限り安全にキャンセル（best-effort）し、外部への影響や停止できなかった処理をオーナーへ報告します。個体が停止して会話に返事をしなくなっても、必要な停止結果や過去の記録は管理画面から問題なく確認できます。

停止が完了した個体は、Client端末にもHostマシンにも滞在（presence）していません。これまでの記憶や前回の滞在先ヒントは保存されていますが、回線が復旧したからといって勝手に再開（Resume）することはありません。

オーナーが「再開」を指示した場合、個体調整サブシステムが同じ個体として活動を再開させ、接続・存在サブシステムが現在利用可能なClient端末への再配置を行います。認識・学習サブシステムは、停止していた時間の長さを考慮して感情パラメータなどを適切に減衰・更新します。中断されていたTaskや不明なアクションを勝手に自動再実行することはありません。

### 削除 (Delete) の説明から完了まで

1. **削除前の確認と説明:**
   個体調整サブシステムが削除要求を受け取り、「保全・消去」サブシステムおよび各担当サブシステムが、削除されるデータと残るデータを照合します。オーナーには、個体固有の設定、体験要約、長期記憶、内部Skill、内的状態、担当スケジュール、人間関係が完全に削除されること、一方で過去の会話ログ、Task記録、全体共通の学習データ（Global Learning）、外部ファイルは残ること、および参照できなくなる情報を丁寧に説明し、確実な同意確認を行います。
2. **新規活動の停止:**
   削除処理は停止（Stop）の処理を含んでおり、新しい活動やアクション、スケジュールの実行を直ちに禁止します。実行中だったTaskの安全なキャンセルと担当スケジュールの削除が行われます。
3. **個体固有データの完全削除:**
   認識・学習サブシステムが、個体固有の要約データ、個体専用の長期記憶、個体専用の内部Skill（過去のリビジョンを含む）、内的状態、その他の固有学習データを完全に削除します。その個体が関わる人間関係（Relationship）も削除されます。削除をきっかけに全体共通（Global）へ勝手に昇格させることは絶対にしません。
4. **客観的な過去記録の維持:**
   個体調整サブシステムはその個体の管理を終了しますが、1対1、グループ、Companion同士の会話履歴や活動ログは消去せずに残します。作業サブシステムも単独・共同のTask記録を維持し、推論サブシステムも利用料金の履歴ログを勝手に消すことはありません。要約データや学習リビジョンを「過去ログ」と言い換えて削除を免れるような抜け道は許されません。
5. **削除完了の検証:**
   保全・消去サブシステムは、各サブシステムで内部データの消去と残存チェックが正しく完了したことを確認します。消し残しがある状態のままオーナーに「削除完了」と表示することはありません。外部サービスへ与えてしまった影響を完全に巻き戻すことまでは保証しませんが、判明している影響と残された記録を正直に説明します。

削除の最中にTaskの実行結果が遅れて戻ってきた場合でも、外部への影響記録として正しく保存されますが、削除された個体の会話応答や学習データへ流用されることはありません。オーナーは残されたTask記録を管理画面から確認し、必要であれば別のCompanionへ引き継ぎを依頼できます。引き継ぎが行われた場合でも、削除された個体のプライベートな記憶や認証情報を勝手に引き継ぐことはなく、担当していた定期スケジュールが自動で復活することもありません。

**確認:** 「一時的に端末から離れている起動中の個体」と「停止中の個体」が明確に区別され、個体が削除された後でも客観的な活動記録の責任が安全に残ります。個体固有のプライベートな記憶を消去しつつ、外部への影響に対する説明責任を最後まで果たすことができます。

## 10. RF-07 — Targeted deletion（指定データの完全削除）と進行中処理

オーナーがプライバシーやセキュリティのために、特定キーワードや情報そのものの完全消去を明示的に指示した場合の流れです。通常の「さっきの忘れて」という雑談レベルの要望や、誤りの訂正、会話ログの保持期限整理、個体の削除とは目的が根本的に異なります。

1. **目的の受付と影響範囲の特定:**
   保全・消去サブシステムがオーナーからの消去指示を受け付け、各サブシステムと連携して影響を受けるデータの範囲を特定します。オーナーに「どのデータベーステーブルから消すか」などを細かく選ばせるような負担はかけません。共有されている根拠データから無関係な情報を可能な限り保護しつつ、切り離せない重要な影響があればオーナーへ説明して確認を取ります。
2. **利用の保留と再保存防止:**
   対象データの探索と同時に、各サブシステムは保存先ファイルだけでなく、過去のリビジョン、判断根拠、派生データ、一時キャッシュ、Client端末の一時データ、裏で実行中の処理を特定します。「権限・制約」サブシステムが必要な処理を一時保留し、削除対象の情報が裏で再び保存されるのを防ぎます。
3. **全域からの徹底消去:**
   各サブシステムが、内部の対象データを完全に消去または復元不能化します。削除処理が始まってから完了するまでの間に再び届いたり生成されたりした対象情報も漏れなく消去対象とします。消去の対象には、会話履歴、活動ログ、Taskコンテキスト、長期記憶の全リビジョン、体験要約、復元に関わる内的状態、Skill、検索用インデックス、監査ログやデバッグ情報、接続中のClient端末、外部プラグインの一時データが含まれます。この完全消去の指示は、通常のデータ保持ルールよりも常に最優先されます。
4. **機械的な検索と残存検証:**
   指定された文字列キーワードは、内部のあらゆるデータ領域に対して機械的に完全一致検索を行い、完全に消去されたことを厳格に検証します。LLMによる「要約したから大丈夫です」といった曖昧な報告を消去の証拠とは認めません。言い換えや意味の同一性の検索に推論を用いる場合でも、検出の限界を正直に認識し、完全な検出を保証するものとはしません。
5. **完了の確定:**
   すべてのサブシステムから消去の完了報告と残存チェック結果が集まり、裏での再保存や古い根拠からの再学習が完全に防がれていることが確認できた場合にのみ、保全・消去サブシステムは「削除完了」を確定します。完了報告や監査ログそのものに対象の機密文字列を再び書き込んでしまうような本末転倒な事態も防ぎます。

### 削除処理中に遅れて届いた結果や切断への対応

削除前のコンテキストを使って裏で実行されていた推論やツール呼び出しの結果が、消去処理の後に遅れて届いた場合でも、それを未検査の新しい情報として受け入れることはしません。消去ルールに従って対象情報を確実に破棄します。外部への操作ログを残す必要がある場合でも、機密情報そのものは伏せ字やハッシュ等で安全に処理します。

消去処理中にClient端末が切断された場合、通信できない端末を「消去完了」と嘘をつくことはしません。再接続した際に、端末内に残っていた古い画面コピーや一時データがHostマシンへ逆流して機密情報が復活してしまうのを防ぎます。

一部のデータで消去の検証に失敗した場合や、途中でHostマシンが停止した場合は、未完了の範囲と保留状態を安全に保全し、中途半端な状態で「成功」と誤認させることはしません。なお、すでに外部へ送信されたデータ、エクスポートされた配布パッケージ、外部に作成されたバックアップ、外部サービスのパスワード無効化などは、ene内部の完全削除の保証範囲外である旨をオーナーへ丁寧に説明します。

**確認:** 完全消去の完了は、単なる個別ファイルの削除の合計ではなく、裏で動いている処理や遅れて届く通信結果の遮断まで含めて成立します。オーナーに対して、完了したこと、未完了であること、検出の限界、外部コピーの存在を正確に説明できます。

## 11. RF-08 — Backup・restore・Resetによるマスターデータの切り替え

### 整合性のあるバックアップコピーの作成

オーナーの手動指示、または設定されたスケジュールに基づいて、保全・消去サブシステムが各サブシステムと連携し、特定時点の内部状態をポータブルなフルバックアップとしてエクスポートします。暗号化保護を有効にするかオーナーが選択でき、非暗号化の場合はプライベートな情報が含まれる旨を事前に説明します。

各サブシステムは、個体の設定、会話履歴、活動ログ、未伝達メモ、体験要約、長期記憶、内部Skill、人間関係、内的状態、Task進捗、Workspaceとの関連付け、スケジュール、安全ルール、プロバイダ同意、費用設定、監査ログなどを提供します。個体削除後に残された過去の活動記録もバックアップに含まれます。一方、**認証情報（Credential）などのすべての秘密情報や、外部Workspaceの実ファイルそのものはバックアップから完全に除外します。**

保全・消去サブシステムは、すべてのデータが同一時点で整合していることを厳格に確認した上でバックアップファイルを完成させます。作成されたバックアップファイルは外部の安全なコピーであり、それ自体が現在稼働中のマスターデータになるわけではありません。

### リストア (Restore) の受付から有効化まで

1. **リストアの受付と事前説明:**
   オーナーがバックアップファイルを選択した際、現在のHostマシンの認証情報ストアを維持したまま対象内部データが丸ごと置き換わること、外部のファイルは変更されないこと、過去に削除したデータや古いルール・同意・スケジュールが復活する可能性があること、および再認証が必要になる場合があることを事前に説明します。
2. **旧稼働状態の安全な停止:**
   保全・消去サブシステムが各サブシステムを復元処理へ参加させ、復元前の古い処理、遅れて届く通信結果、Client端末の一時データが、復元後の新しいマスターデータに混入しないよう確実に遮断します。復元前に外部へ及ぼしてしまった実際の影響は消えないため、それを未実行と偽ることはしません。
3. **データの照合と認証情報の引き継ぎ:**
   各サブシステムが復元されたデータの整合性を確認します。認識・学習サブシステムは感情パラメータなどの時間経過を適切に処理し、接続・存在サブシステムはバックアップ内の古い接続情報を現在の接続と混同しないようにします。認証秘密サブシステムは**リストア開始前のHost認証情報ストアをそのまま維持し、秘密情報を古い状態へ巻き戻すことはしません。** 復元されたプロバイダやMCPの接続設定を現在の認証情報ストアと照合し、使えるものは使い、不足や無効があればオーナーに再認証を求めます。外部Workspaceの現在のファイル内容がバックアップ時点へ勝手に巻き戻ることもありません。
4. **マスターデータの置き換え確定:**
   保全・消去サブシステムは、現在の認証情報ストアを除く対象内部データがバックアップ内容で正しく置き換わったことを確認し、初めて復元内容を正式なHostマスターデータとします。失敗した場合は復元前の正常な状態を破壊せず、不完全な状態のまま「成功」と表示することはありません。
5. **自動処理の保留とオーナー確認:**
   **復元が完了した後も、Task、スケジュール、外部連携による自動処理はすべて一旦「保留」とします。** オーナーは復元された内容を画面で確認し、まとめて一括で有効化できます（1件ずつ面倒な再承認を強いることはしません）。過去の設定が復元されたからといって、現在の安全制限を無視して勝手に危険な自動処理を動かし始めることはありません。

### 初期化 (Reset) とバージョンアップ

- **設定のリセット (設定Reset):** UIの見た目、アバター表示、音声設定などの一般的な環境設定だけを初期値に戻します。個体の記憶、学習データ、会話履歴、Task、スケジュール、認証情報、安全ルール、利用料金設定などは安全に保護されます。
- **全データのリセット (全データReset):** 画面上で極めて強い警告と確認を行った後、Host内部のすべてのデータと認証情報を完全に削除します。ペアリングされた端末の登録も失効します。ただし、外部Workspaceのファイルや、オーナーが別の場所に保存したバックアップファイルまで勝手に削除することはありません。何を消し、何が外部に残るかを明確に説明します。
- **正常なマイグレーションとバージョンアップ:** バージョンアップ処理が成功するまでは直前の正常な状態を安全に保護します。互換性のないダウングレードを安全に実行できるとは説明しません。

**確認:** バックアップコピー、復元されたマスターデータ、および現在の実行可能性がそれぞれ正しい順序で確定します。過去のバックアップを復元して情報が戻ることと、完全削除のルールは矛盾しません。外部世界のファイルや認証情報の状態を、内部データの復元と混同しない設計が保たれています。
