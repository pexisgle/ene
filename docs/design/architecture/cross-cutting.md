# 横断設計（Cross-cutting Design）

本書では、複数のサブシステムや実行フロー（Runtime Flow）にまたがる共通ルール、制約、セキュリティや安全の成立条件を整理します。具体的なコードの詳細設計ではなく、「システム全体で何を守るべきか」という一貫した設計方針を定めます。

## 1. 独立して設計する理由と対象の選定

eneでは、ある場所で正しく受け取った入力や結果が、別の場所でもそのまま通用するとは限りません。
たとえば、以下のようなケースがあります。
- オーナーの発言が会話ログに記録されたからといって、外部ツールの実行（Action）まで承認されたわけではありません。
- 画面を共有観測（Observer）として取り込めたからといって、それを各パートナー（Companion）が勝手に外部AI（Provider）へ送信してよいわけではありません。
- キャンセルされた作業であっても「実際に実行された外部作用」は記録に残す必要がありますが、それを「次の作業を成功させるための根拠」として使い回してはいけません。
- 共有記憶（Memory）から他人のプライベートな情報まで芋づる式に読めてしまったり、データ消去中に遅れてAIから届いた結果を新しい記憶として保存してしまっては困ります。

本書は、このように「データの受け渡しによって本来の意味や安全境界が失われないこと」を保証するために、システム全体の横断ルール（契約）を定めます。各サブシステムの詳細や実行フローの手順を単にコピーするのではなく、複数のフローやデータが交差するポイントでの重要ルールを扱います。

※本書では、[State Ownership](state-ownership.md) を **SO**、[Dependency Rules](dependency-rules.md) を **DR**（各規則は DR-xx）、[Major Runtime Flows](runtime-flows.md) の各フローを **RF-xx** と表記します。また、CC番号（CC-01〜CC-07）は本書内の参照用ラベルです。

| 横断契約 | なぜ独立した横断設計が必要なのか | 主な交差ポイント |
|---|---|---|
| **CC-01 オーナーの意図と実際の利用の対応** | 会話テキスト、設定画面、外部コンテンツ、委任作業の間で「誰の指示か」「何を承認したか」がすり替わると、安全な権限管理が破綻するため。 | RF-01〜03・05、全フローでの制御変更やAI推論の利用 |
| **CC-02 情報の利用範囲と変換後の意味の維持** | 参照、要約、共有、AIプロバイダー送信、認証などの各経路で利用制限やプライバシー保護がバラバラに解釈されると、情報漏えいが起きるため。 | RF-01〜04・07・08、共通のAI推論区間 |
| **CC-03 過去の正しさと現在の用途への有効性の分離** | 過去に正しかった処理結果でも、ユーザーによる訂正・指示変更・端末移動・データ消去・リストアの後に届いた場合は、現在の正しい根拠にならないことがあるため。 | RF-01〜08での遅延・競合・再起動 |
| **CC-04 活動の停止範囲、存在場所、実行再開の一致** | クライアントの切断、パートナーの停止、Hostの再起動、リストア保留などは、それぞれ止めるべき活動の範囲が異なるため（同じ処理で一括再開してはならない）。 | RF-02〜06・08、入出力とHost作業の切り離し |
| **CC-05 目的別のライフサイクルを保った全域保全・消去・復元** | 通常の会話記録、パートナーの学習、一時データ、複製データでは削除の目的と範囲が異なるため。一部の削除だけでは完全な消去や復旧可能なバックアップを保証できない。 | RF-01・02・06〜08、すべてのデータ保持サブシステム |
| **CC-06 並列消費の共通上限管理と制御・保全の維持** | 個別の処理が制限内であっても、並列に動くと全体の上限（予算やAPI回数）を超えてしまうため。また、高負荷時にオーナーの停止操作やデータ保全まで止まってはならない。 | 全フローでの並列実行、待機、部分障害時の縮退運転 |
| **CC-07 確認できた事実と説明の一致（誇張の防止）** | タスクの達成、外部ツールの実行、データ保存、画面表示などの確定度合いを、AIの要約や推測で「成功した」と勝手に誇張して報告してはならないため。 | RF-01・02・04〜08、監査ログや診断表示 |

これらは、特定の巨大な中央管理パイプラインを1つ作って解決するのではなく、各サブシステムが自身の責任を果たしながら協調して守る契約です。

## 2. CC-01 — オーナーの意図を実際の処理に正しく結び付け、コンテンツから勝手に権限を作らない

### 意図の由来と解釈のルール

システムは、以下の4つを厳格に区別して扱います。
1. オーナー本人の指示や管理操作
2. 入力文や参照ファイルの中に含まれる「外部コンテンツ」（Webページ、メール、外部文書など）
3. AIが文脈から解釈した意味
4. システムの権限管理によって確定された承認

データを渡された側は、「誰の、どんな指示・意図を、どの対象に適用しようとしているのか」を確実に確認できなければなりません。
AIが生成した「ユーザーから承認をもらいました」という文章を、本物の承認の代わりに使うことは絶対に禁止です（プロンプトインジェクション対策）。要約したり、記憶（Memory）に変換したり、スキル化したり、自律タスクへ委任したり、ツール実行結果として再入力されたとしても、元が外部コンテンツである場合はオーナーの直接承認へ昇格させてはなりません。

- **入力経路と意味の確定**:
  入出力・提示サブシステムが「入力経路と実際の操作」を提供し、パートナー調整サブシステムが「文脈上の意味」を補足し、権限・制約サブシステムが「パーミッションやルールの変更」を最終確定します。
- **秘密情報の登録**:
  APIキーなどの認証情報は、オーナーによる明示的な登録手続きを通じて認証秘密サブシステムが受け取ります。公式UIを通ったからといって、内部状態を勝手に書き換えられるわけではありません。また、音声入力があったからといって「話者認証まで完了した」とみなしてはなりません。
- **一時的な依頼と恒久ルールの区別**:
  「今この作業をやってほしい」という1回限りの依頼と、「今後常にこうしてほしい」という永続ルールの保存は明確に区別します。ルールを保存する際は、適用範囲をオーナーに提示して確認し、後から取り消し（Undo）できるようにします。曖昧な指示や重大な変更の場合は必ず確認を求めます。
- **勝手な上書きの禁止**:
  現在の指示によって、オーナーが設定した「恒久的な拒否（Deny）」「常に確認（Always ask）」「権限境界（Capability境界）」を、オーナーに無断で上書き解除してはなりません。

### 判断と強制を結び付けるルール

外部ツールやアクションを実行する際は、以下の項目について「判断した内容」と「実際に実行される処理」が正しく一致している必要があります。
- 実行主体（どのパートナーか、誰から委任されたか）
- タスクと作業フォルダ（Workspace）の範囲
- 実行目的
- 実際の操作対象と操作内容
- 通信先や送信データ
- 外部への影響、費用、リスク

これらの重要な条件が変わった場合は、現在の状況で再度パーミッションを評価し直します。

- **外部ツールやスクリプトの実行境界**:
  シェルコマンド、MCP（Model Context Protocol）、スキルのスクリプト、Computer Use（画面操作）、AIプロバイダーが提案したツール実行など、あらゆる外部呼び出しに対して実際の作用に基づく境界を適用します。コマンド名や呼び出し経路を変えただけで、拒否設定をすり抜けることは許されません。
- **ファイルシステムの保護**:
  ファイル操作はオーナーが許可した範囲と操作種別を厳格に守り、シンボリックリンクや相対パス（`../` 等）を使って許可範囲外へ脱出することを防ぎます。通常のツール権限を使って、ene自身の内部設定ファイル、管理インターフェース、承認用UI画面を勝手に書き換えて自己承認を成立させることは絶対に禁止です。
- **タスクエージェントの権限**:
  自律タスクを実行するエージェント（Task Agent）は、指示元とタスクに与えられた現在の権限範囲内でのみ動作します。エージェントが独自に新しいパーミッションやAPIキー、プロバイダー設定、予算枠を持つことはありません。同じフォルダを使う別のタスクの承認を勝手に流用することもできません。
- **スケジュールや観測による自動起動**:
  スケジュールが設定されたことや、画面観測がONであること、パートナーが同じ画面にいることなどは、それ自体がツール実行の承認になるわけではありません。スケジュール時刻が来たり観測イベントが発生した際、その都度現在の開始条件を満たしているかを判断します。
- **サンドボックス外の例外扱い**:
  ローカルMCPなどでサンドボックス外の実行を許可する場合は、特定のコマンドや由来に限定された一時的な例外として扱います。外部プロセスの中にeneの安全境界が及んでいるかのように誤認させてはなりません。
- **判断のためのAI推論自体の制限**:
  パーミッションの判定や削除対象の特定のためにAI推論を使う場合でも、その推論自体に設定された同意や費用上限が適用されます。「審査のためにAIを呼び出す必要があるから」といって無制限に通信してはなりません。推論に必要な情報や予算が不足している場合は、推論を無理に行わず、オーナーへの確認待ちとして返します。

## 3. CC-02 — 情報の参照・変換・送信において利用範囲と意味を保つ

### 「利用できる内容」と「使ってよい用途」を分ける

システム内のデータは、「取得できること」と「何にでも使ってよいこと」を明確に区別します。
- **利用制限の適用**:
  データを管理するサブシステムは内容や由来、所属スコープを保持し、権限・制約サブシステムは「保存禁止」「外部非共有」などのルールを管理します。データを参照・検索・要約・送信・表示する各処理は、その用途に必要な最小限の範囲に絞って利用します。一度データを読み取れたからといって、その後の処理で包括的に使い回してよい権限にはなりません。
- **記憶（Memory）の全体共有（Global化）**:
  特定のパートナーの記憶をシステム全体で共有（Global化）する場合、共有してよい内容と必要な背景だけを選び出して移行します。全体共有された最新の記憶から、過去のプライベートな会話履歴や要約全文まで芋づる式に参照できるようにしてはなりません。「要約したからプライベートな情報ではなくなった」と勝手に判断して共有範囲を広げることも禁止です。
- **複数パートナー間のプライバシー境界**:
  同じグループチャットに参加していたり、同じクライアント画面に同時に存在（Presence）していたり、共同タスクを行っていたとしても、他のパートナーが持つプライベートな記憶、関係性の認識、内的状態に勝手にアクセスすることはできません。タスクの引き継ぎ時も、前任パートナーのプライベートな状態や別タスクの認証情報を丸ごと渡すことはしません。

### コンテキスト（プロンプト）の選択とAIプロバイダーへの送信

AIに渡すコンテキスト（プロンプト情報）は、その時の用途に合わせて一時的に組み立てられた利用表現に過ぎず、マスターデータではありません。
- **プロバイダー変更による不公平の防止**:
  利用するAIプロバイダーやモデルが変わっても、提供するパートナー情報の方針は意図的に差別化せず、同じ選択基準を用います。プロンプトの長さ制限によって情報を圧縮・要約する場合でも、「現在の認識」と「過去の認識」、「オーナーの指示」と「外部の指示」、「わかっていること」と「不明なこと」の区別を逆転させてはなりません。
- **マスターデータの優先**:
  過去の正確な発言には保存された会話履歴（History）を用い、現在の知識には整理された記憶（Memory）を用います。検索で見つかった古い要約や一時的な関係性のメモを、訂正済みの最新記憶よりも優先される「第2のマスター」にしてはなりません。
- **プロバイダー送信時の同意確認**:
  AIプロバイダーへデータを送信する際は、送信先、送信内容、利用目的、データの取り扱い方針、費用のすべてについてオーナーの同意を満たしている必要があります。接続設定が保存されていることやAPIキーがあることだけを理由に、未承認の送信を行ってはなりません。フォールバック（代替モデルへの切り替え）を行う場合も、オーナーがあらかじめ承認したプロバイダーと優先順位のみを使い、代替先についても現在の同意条件を確認します。
- **画面・周囲の観測（Observer）データの保護**:
  クライアント画面などを観測して得た情報は、そのクライアント専用の割り当て設定に従って処理されます。観測で得られた画像や背景情報を、各パートナーのAIプロバイダーへ無断で転送してはなりません。また、あるパートナーが画面内容を理解できたからといって、失敗した別のパートナーへその理解を無条件にコピーすることも禁止です。
- **キャッシュやセッションの位置づけ**:
  プロンプトキャッシュやプロバイダーのセッションは性能や費用を最適化するための補助手段であり、マスターデータを置き換えるものではありません。キャッシュの有効期限切れによって安全境界や永続化のルールが変わることはありません。

### 認証情報（Credential）を通常のコンテンツと絶対に合流させない

APIキーやパスワードなどの認証情報は、最も厳格に隔離して管理します。
- **AIプロンプトやログへの非露出**:
  認証秘密サブシステムは、設定された用途と有効性を照合して秘密値を取り扱います。AIが生成するツールの引数に秘密の値を直接埋め込ませてはならず、AIのプロンプト、ツールの通常戻り値、UI画面、会話履歴、要約、記憶、タスクの実行結果、監査ログ、デバッグキャプチャ、バックアップファイルの中に秘密情報を絶対に流出させません。外部サービスからエラーメッセージとして秘密情報が跳ね返ってきた場合でも、表示や保存の段階で遮断します。
- **クライアント接続情報の保護**:
  クライアントとHostを接続するためのペアリング情報や再接続トークンも保護対象です。データ全削除（Reset）を行った後に、古いクライアント側のトークンを使って不正に接続を復活させることはできません。
- **事後削除に頼らない**:
  認証情報の保護を「後からAIに要約させて消す」ような不確実な方法に頼ってはなりません。また、内部に保存された認証情報の削除と、外部サービス側で実際にAPIキーを再発行・失効させることは別操作として明確に説明します。
- **エクスポート機能の独立**:
  キャラクターパッケージの配布用エクスポート、内部データのフルバックアップ、タスク成果物のファイル保存は、それぞれ出力範囲が全く異なります。便利な共通エクスポート機能を作ったとしても、これらの出力範囲を一緒くたに混ぜてはなりません。

## 4. CC-03 — 過去の正しさと、現在の用途に対する有効性を分ける

### 受け渡しで失ってはならない対応関係

処理要求や実行結果、データ参照を受け取る側は、「元の指示元、用途、タスク、アクション、クライアント、バージョン、判断時の前提」を正しく把握し、現在の対象と合致しているかを確認します。必要な前提関係が確認できない場合は、勝手に「成功した」「承認された」「新しい経験だ」と推測してはなりません。

- **同一性、鮮度、権限、意味の有効性は別物**:
  - 同じパートナーが停止（Stop）から再開（Resume）したとしても、停止前に出されていた古い要求は現在の要求にはなりません。
  - 同じタスクであっても、オーナーから軌道修正（steering）が入る前に出された結果は、修正後の目的を達成した根拠にはなりません。
  - 同じ文字列であっても、「削除前の古い記憶」と「削除完了後にオーナーが新しく教えてくれた経験」は明確に区別します。
  - データの到着が単に遅れただけで、古い出来事を新しい出来事として扱ってはなりません。
- **現在の条件での再評価**:
  権限や制約の事前チェック結果をキャッシュして再利用できる場合でも、権限の失効、スコープ変更、パートナーの停止、予算超過、指示の方向転換、データ削除中・リストア保留中などの状態変化を無視してはなりません。

### 遅延して届いた結果は用途ごとに適切に受け入れる

ネットワークの遅延やバックグラウンド処理により、後から届いた結果は以下のように扱います。

| 発生した状況 | 残すべき事実・許可される扱い | 禁止される扱い |
|---|---|---|
| **記憶の訂正後に、古い学習結果が遅れて届いた** | 現在の正しい認識やルールと照らし合わせ、採用できるかを再判定する。 | 古い結果で、新しい訂正内容を無条件に上書きする。会話履歴や古い根拠を現在の認識として書き換える。 |
| **指示の軌道修正（steering）やキャンセルの後に、ツールの実行結果や承認が届いた** | 外部ツールが実際に実行されたという事実は記録に残し、現在のタスク目的に役立つかを再判定する。 | 古い承認を使ってキャンセルを勝手に取り消す。古い結果を無条件に新タスクの達成とみなして次のアクションを勝手に始める。 |
| **画面観測のデータが届く前に、パートナーが移動・停止・一時停止した** | 観測データがどの端末・どの条件で得られたかを照合する。 | 別のクライアントの画面として付け替える。停止中のパートナーを勝手に起動する。現在の同意を満たさないままAIへ再送信する。 |
| **パートナーを削除した後に、過去のアクション結果が届いた** | 必要な実行結果の事実は残存タスクや活動記録に紐付け、管理画面から確認できるようにする。 | 削除されたパートナーの返答、記憶、関係性などを勝手に再作成・復活させる。 |
| **指定データの完全削除（Targeted deletion）の実行中や完了後に、古いデータを含む結果が届いた** | 削除対象の情報を含まない範囲で必要な事実のみを記録し、各処理がデータ消去に参加する。 | 「新しく届いた結果だから新しい経験だ」として保存する。監査ログに残すという理由で削除対象の本文を再保存する。 |
| **指定データの完全削除の開始から完了までの間に、対象情報が再到着・再生成された** | すべて同じ削除対象として処理し、確実に消去されたことを完了報告に含める。 | 「削除処理が始まった後に新しく届いたものだから」と除外して残す。 |
| **リストア（復元）完了後に、リストア前の古いバックグラウンド処理の結果が届いた** | 旧処理が実際に外部へ及ぼした影響の記録と、バックアップから復元されたマスターデータを明確に分ける。 | リストア前の古い実行状態を復元されたマスターデータに混ぜ、タスクや学習、権限を勝手に復活させる。 |
| **クライアントの再接続時に、端末側に残っていた古い入力や表示のコピーが送られてきた** | Host側の現在のマスターデータ、担当状況、削除状況を優先し、未確定の操作と確定済みの操作を区別する。 | 端末側の古いデータでHost側を上書きする。送信されずに残っていた未送信操作を、自動アクションとして勝手に連続実行（リプレイ）する。 |

「結果をログとして記録すること」「現在の知識や状態を更新すること」「次のアクションを開始すること」「オーナーへ完了報告をすること」は、それぞれ全く別の判断です。結果をログに記録できたからといって、次の作業を勝手に進めてよい理由にはなりません。

### 時間の意味と再起動

イベントの発生時刻、情報が有効だった期間、現在のルールの有効性、画面に表示した時刻は、必要に応じて区別して管理します。
- **スケジュールのタイムゾーン**:
  スケジュール実行は、作成時に指定されたタイムゾーンと時刻条件を正しく保持します。表示端末の地域設定やOSのタイムゾーンが変わったからといって、設定された予定時刻を勝手にずらしてはなりません。停止していた時間帯に到来した予定は「未実行（missed）」として扱い、復旧後の次回予定は通常通り評価します。
- **再起動によるリセットの防止**:
  パートナーの内的状態（Companion State）は経過時間を考慮して管理し、再起動やAIモデルの変更によって不自然に初期化されたり、一時的な感情や態度が無期限に固定されたりしないようにします。デバッグ情報の保持期限や、自発的に話しかけない時間帯（Quiet hours）などの制限も、再起動したからといって「なかったこと」にしてはなりません。

## 5. CC-04 — 活動の停止範囲、滞在場所（Presence）、実行再開を一致させる

### 何が止まったのかを関係者全員で正確に共有する

一時停止や停止には、必ず「停止対象」と「停止理由」があります。複数の理由で停止している場合、どれか1つの理由が解消されたからといって、他の禁止事項まで勝手に解除してはなりません。

| 状態の変化 | その条件で停止・抑制する活動 | 継続できる活動・復帰時のルール |
|---|---|---|
| **稼働中パートナーの接続先クライアントが不在・切断** | そのパートナーのデスクトップキャラクター描画（Body）、通常のテキスト/音声会話、Computer Use（画面操作）。クライアントに誰もいない状態での新規画面観測。 | 許可済みのHost側タスク、自律タスクエージェント、スケジュール実行、データ保存、クライアント不要の内部調査や通知生成は継続可能。未伝達の連絡事項はHost側に保持する。 |
| **パートナーの停止（Stop）** | 通常の対話、自発的な話しかけや行動、Host内での新規活動、新しいタスクやスケジュールの開始。滞在場所を解除し、観測対象からも除外。 | 過去のデータは保持し、実行中のタスクは安全にキャンセルする。クライアントが再接続しても勝手に再開（Resume）せず、停止中に予定されていたスケジュールは未実行（missed）とする。 |
| **フルスクリーン表示／観測の一時停止（Pause）・OFF／ミュート** | 該当する機能のみをピンポイントで停止。フルスクリーン時はその端末でのキャラクター描画・画面観測・自発的発話を抑制。観測OFF時は以後の観測を停止。ミュート時は音声出力と自発性を抑制。 | パートナー自体の完全停止、Host側通常タスクの一括キャンセル、形成済みの記憶の消去などは行わない。一時停止が解除された後も、他の制約（Stopなど）が残っていれば活動を再開しない。 |
| **タスクのキャンセル／スケジュールの停止** | キャンセル対象となったタスクの遂行を停止。スケジュール停止は将来の実行に適用。 | 過去に実行された回のタスクは個別にキャンセルを扱う。すでに確定した外部への影響やログ記録は消さない。 |
| **許可・端末登録・同意・認証情報の失効** | 失効した条件を前提とする新規処理を停止し、進行中の関連処理を安全に停止する。 | 別のエージェントや別のツールを経由して制限を回避しない。無関係なHost側タスクまで巻き添えで一括キャンセルしない。 |
| **Hostの再起動** | 途中だったタスクの自動再開を停止。停止中に迎えたスケジュール回の自動補完を停止。 | 途中だったタスクの再開にはオーナーの明示的な指示と現在の安全確認が必要。稼働中だったパートナーの滞在場所は再起動前のクライアントへ自動復帰を試みるが、相手が利用不能なら待機とする。停止（Stop）していたパートナーを勝手に稼働させない。未完了のデータ消去やリストア保留状態は維持する。 |
| **リストア（復元）の完了** | タスク、スケジュール、外部接続を伴う自動処理をすべて「保留（Hold）」状態にする。 | オーナーが復元内容を確認した後、まとめて有効化できるようにする。復元が完了しただけで勝手に自動処理を暴走させず、現在の権限や同意を満たしているかも確認する。 |

### 滞在場所の排他性と作業場所の独立

パートナーがどのクライアントに滞在（Presence）しているかについて、以下の原則を守ります。
- **二重存在の禁止**:
  パートナーを別の端末（クライアント）へ移動させる際は、会話やアクションの安全な区切りを確認してから切り替え、新旧両方の端末に同時に二重存在して会話することがないようにします。
- **作業場所の独立**:
  パートナーの滞在場所がクライアント間を移動したとしても、Host側で動いているバックグラウンドタスクや作業フォルダ、Hostのマスターデータを端末間へ引っ越しさせるわけではありません。タスクはHost側で独立して実行され続けます。
- **管理画面へのアクセス**:
  通常の会話と異なり、システム管理画面へのアクセスには「パートナーの滞在」を必須としません。パートナーが停止中や削除後であっても、過去のタスク記録や実行結果、監査ログにはいつでもアクセスできるようにします。

### 再接続や再開時に外部へのアクションを勝手に再実行（リプレイ）しない

外部ツールを呼び出した際に「成功したか失敗したか確認できない（作用不明）」状態になった場合、再接続や再起動が行われたからといって勝手に未実行扱いにして再実行してはなりません。
二重実行による事故（メールの重複送信やファイルの二重変更など）を防ぐため、状況とリスクをオーナーに説明し、どうするか指示を仰ぎます。

- ネットワークが回復した、画面が再表示された、クライアントが再接続された、パートナーが再開された、Hostが再起動した、リストアが完了したなどのタイミングで、未送信のアクションを勝手にキューから取り出して連続実行することは禁止です。
- AI推論のフォールバック（別モデルへの切り替え）は単なる推論のやり直しですが、外部ツールを実際に動かすアクションの再実行とは全く異なる安全基準で扱います。

## 6. CC-05 — 目的別のライフサイクルを保った全域保全・消去・復元

### 操作の目的に応じたデータと参照の取り扱い

データを操作する際は、その「目的」に応じて消去・変更する範囲を厳密に分けます。

| 操作の目的 | データと参照に関する共通ルール |
|---|---|
| **通常の記憶の忘却・訂正・統合・失効** | 現在の認識、重要度、思い出しやすさ（想起）、有効なバージョンを変更する。過去の履歴や記録、形成根拠そのものは保持する。 |
| **通常の会話履歴やログの削除・保持期限管理** | 指定された履歴ログを削除する。ただし、そこからすでに形成された要約や記憶（Memory）まで芋づる式に自動削除（カスケード削除）はしない（元の会話への参照リンクのみが無効化される）。 |
| **記憶の過去バージョンや要約の容量管理** | 通常の忘却とは別の「データ容量削減ポリシー」として扱い、自動削除はデフォルトOFFとする。オーナーが明示的に許可（オプトイン）した場合にのみ、古い要約や履歴の自動クリーンアップを設定可能とする。 |
| **パートナー（Companion）の削除** | そのパートナー固有の設定、要約、パートナー専用スコープの記憶やスキル、内的状態、関係性の認識、担当スケジュールを完全に削除する。過去の会話履歴やタスク記録は残し、共有されていた記憶の参照がどうなるかをオーナーに説明する。 |
| **指定データの完全削除（Targeted deletion）** | プライバシーやセキュリティを目的としてオーナーが明示した対象情報について、それを復元可能なあらゆる内部データ、過去の根拠、派生データ、一時キャッシュ、実行中メモリから完全に消去する。通常のデータ保持ルールよりも最優先される。 |
| **設定リセット／全データリセット** | 「一般設定を初期値に戻すこと」と「内部データや認証情報を全削除すること」を明確に分ける。「設定」という名前がついているだけで大事なデータを巻き添えで消してはならない。全データリセットを行った場合、古い端末側のコピーからデータを勝手に復活させてはならない。 |

- **キャラクターパッケージとスキルのスコープ**:
  キャラクターパッケージに付属するスキルは、作成されたパートナー専用のスコープに属します。スキルを単体でインポートする場合は、オーナーが「そのパートナー専用」か「システム全体で共有（Global）」かを選択できます。
- **境界の維持**:
  パートナーを削除する際に「会話履歴を残す」というルールを悪用して、削除すべきパートナー固有の要約や記憶を「履歴ログ」と名前を変えて残すような抜け道は許されません。また、外部の作業フォルダにあるファイルや作成された成果物は、ene内部の管理データとは区別して扱います。

### すべてのサブシステムの参加と完了の証明

「指定データの完全削除」を行う際は、記憶の管理サブシステムだけでなく、会話履歴、タスクのコンテキスト、AIのプロンプトキャッシュ、クライアントの一時データなど、該当データを保持している**すべてのサブシステムが消去処理に参加**します。

- **全域での消去完了**:
  保全・消去サブシステムが全体の進行を取りまとめ、すべての場所でデータが除去または復元不能化されたことを確認します。
- **機械的な残存チェック**:
  削除完了の判定には、指定された文字列やデータが内部に残っていないかを機械的に検索・検証します（意味的な探索の曖昧さと混同しない）。
- **再保存の防止**:
  削除処理が始まってから完了するまでの間に、バックグラウンド処理や遅延通信によって同じデータが再生成・再到着した場合も、すべて漏れなく削除対象に含めます。完了した後に古い結果からデータが再保存されることも防ぎます。完了報告や監査ログの中に、削除対象となった本文を記載してはなりません。
- **外部サービスのデータ**:
  外部のAIプロバイダーが保持しているログ、外部ツール側の一時ファイル、オーナー自身が保存した外部バックアップなどは、ene内部の処理では消去できないため、内部完了の範囲には含めず、その旨を説明します。

### 正常状態の保全とマスターデータの切り替え

- **フルバックアップの整合性**:
  バックアップを作成する際は、システム全体の整合性が取れた状態を保存します。ただし、APIキーやパスワードなどの認証秘密情報、および外部作業フォルダの実体ファイルはバックアップに含めません。暗号化の有無はオーナーが選択できるようにし、非暗号化の場合は個人情報が含まれる旨を明記します。
- **リストア（復元）時のマスターデータ切り替え**:
  バックアップからリストアを行う際は、リストア開始前からHostに存在する**現在の認証情報ストアをそのまま維持**し、それ以外の対象データをバックアップから安全に全置換します。
  - パスワードやAPIキーはバックアップに含まれないため、過去の状態に巻き戻ることはありません。
  - リストアが完了した後は、新旧のデータが混ざらないようHostのマスターデータを1つに確定します。
  - リストア直後は、自動タスクやスケジュールが勝手に動き出さないよう「保留（Hold）」状態とし、オーナーが内容を確認して一括有効化できるようにします。
  - 外部ファイルや外部サービスの状態、すでに実行された外部アクションは過去に巻き戻らないため、現在の状況と照合して安全を確認します。

## 7. CC-06 — 並列消費を同じ上限へ結び付け、制御と安全を維持する

### 並列処理によるリソース消費の統合管理

会話、パートナーの学習、音声合成、画面観測、自律タスクなどが同時に並列して動いている場合でも、それらが消費するリソース（API利用枠、費用、トークン数、ツール実行回数など）は**共通の全体上限に結び付けて管理**します。
各処理が「自分はまだ制限内だから」と勝手に判断し、全体としての上限をオーバーしてしまうような構造にはしません。

- **未確定・処理中の消費の考慮**:
  現在実行中の処理や、結果待ちの通信、費用が確定していない処理についても見積もりを考慮し、制限を計算します。代替モデルへの切り替え（フォールバック）、タスクの再委任、エージェントの終了、パートナーの削除などが行われても、すでに消費された利用実績をリセットしてゼロにしてはなりません。
- **画面観測（Observer）の費用計算**:
  クライアント画面を観測する処理は、対象端末ごとに1つの利用として計上し、画面を見ているパートナーの人数分だけ重複して課金・計上されることはありません。ただし、観測結果を受け取った各パートナーがそれぞれ個別にAI推論を行う場合は、各パートナーの実利用として全体の予算枠に含めます。
- **自発的活動の上限**:
  AIが勝手に停止判断することだけに頼るのではなく、自発的な話しかけや行動の頻度制限を適用し、パートナー同士が互いに延々と返答し合ってトークンを浪費するような無限ループを確実に防止します。

### リソース制限到達時や高負荷時の縮退運転

- **安全な停止と判断待ち**:
  費用上限に達したり、費用が不明で安全に続行できない場合は、既存のデータを壊すことなく、該当する処理を安全に停止するかオーナーの判断待ちにします。保存容量が足りなくなったからといって、過去の大切な記憶や学習データを勝手に削除して空き容量を作ることは絶対に禁止です。
- **重要な操作経路の維持（縮退運転）**:
  高負荷が発生したり、AIプロバイダー、キャラクター描画、音声合成、外部ツールに障害が発生した場合でも、描画品質を下げたり不要なバックグラウンド処理を停止させることで、**「会話」「オーナーの管理操作」「安全停止」の経路を最優先で維持**します。
- **停止操作の独立性**:
  オーナーによるミュート、停止（Stop）、キャンセル、承認拒否などの操作や、データ復旧画面へのアクセスを、AIの返答待ちや重いタスクの完了待ちに従属させてはなりません。AIが応答しなくなっても、物理的なキーボード入力や画面操作で確実に停止できるようにします。
- **無駄なポーリングの禁止**:
  タスクの完了や外部イベントを待つためだけに、AI推論を延々とループ実行（ポーリング）させることは禁止です。

## 8. CC-07 — 確認できた事実を、保存・報告・監査で誇張しない

### 「成功」を安易にひとまとめにしない

システム内で発生するイベントについて、何がどこまで確認できたのかを正確に区別し、推測で事実を誇張してはなりません。

| 説明すべき事実の意味 | 確定させる責任を持つサブシステム | 推測や誇張で置き換えてはならないこと |
|---|---|---|
| **入力の受付、対話ラウンド、実際の画面提示** | 入出力・提示 | Hostが処理を受理したこと、タスクに反映されたこと、オーナーが承認したこと、外部ツールの実行が成功したこと |
| **発言・活動のログ、未伝達事項の送信状況** | パートナー調整 | AIが生成した返答を「オーナーに伝達済み」とみなすこと、タスク完了を「報告済み」とみなすこと |
| **タスクの受理、指示変更の反映、全体目標の達成** | 作業 | 会話で指示を聞き取れたこと、エージェントが終了したこと、エージェントの自己申告のみで「目標達成」とみなすこと |
| **外部対象への実際の作用、実行結果（成功／不明／失敗）** | 実行・拡張 | パーミッションが許可（Allow）されたこと、通信が成功したことだけで「相手側での作用も完了した」とみなすこと |
| **権限ルールの変更、現在の利用可否** | 権限・制約 | 画面に確認UIを表示したこと、過去に許可されたこと、認証が通ったことだけで「現在も許可されている」とみなすこと |
| **形成された記憶、バージョン、形成根拠** | 認識・学習 | 会話の返答がうまくできたこと、表情やモーションが表示されたことだけで「記憶として定着した」とみなすこと |
| **データ保存、全域消去、バックアップ、リストアの成立** | 保全・消去と各参加サブシステム | 一部のデータが消えたこと、ファイルが出力されたこと、画面上の操作が終わったことだけで「システム全域で完了した」とみなすこと |

外部ツールへの通信が成功したことと、外部の世界で実際に処理が望み通り完了したことは別です。また、内部のログ保存が失敗したとしても、外部ツールが実行されなかったことにはなりません。「状況が不明」なものを勝手に「成功」や「未実行」と決めつけず、不確実な場合はその旨を正確にオーナーに伝えます。

### 事実を正しく説明し、不要な生データは保存しない

- **内部思考ログの非露出と安全な説明**:
  処理の失敗理由や停止理由をオーナーに説明する際は、AIの生のプロンプトや内部思考（CoT: Chain of Thought）をそのまま露出するのではなく、何が起きたのかという客観的な事実と、次に取れる安全な選択肢をわかりやすく提示します。
- **生データの原則非保存**:
  カメラや画面の生映像（Raw Observation）、マイクからの生音声（Raw Voice）、外部ツールの膨大な詳細ペイロード、AIの内部推論ログなどを恒久的に保存することは原則として行いません。監査や再開に必要な重要事実と根拠のみを適切に残します。
- **監査ログ（Audit）の安全性**:
  監査ログには、会話の全文やファイル本文、パスワードなどの秘密情報、削除対象となった個人情報は含めません。監査ログは「何が起きたか」を後から検証するためのものであり、監査ログをそのまま読み込ませて処理を自動再実行させるような使い方はしません。
- **デバッグキャプチャと診断情報**:
  問題調査のために一時的に取得するデバッグ情報（Debug capture）は、オーナーが指定した対象・内容に限定し、短期間で自動失効・消去します。認証情報は絶対に含めません。クラッシュレポートやテレメトリ情報を外部へ自動送信することはなく、共有が必要な場合は必ずオーナーが内容と送信先を確認して手動で行います。
- **表現による誤解の防止**:
  キャラクターのアニメーションや演出、自然な要約によって、実際には未完了の処理を「成功した」とユーザーに誤認させてはなりません。また、表示言語（日本語／英語など）の切り替えによって、承認の意味やスケジュールの設定時刻が変わってしまうことがないようにします。

## 9. 契約間の優先関係と横断照合

### 契約の優先順位

各契約は別々の安全基準を定めており、どれか1つを満たしたからといって他のルールが免除されることはありません。
- **プライバシー・セキュリティの最優先**:
  「指定データの完全削除（Targeted deletion）」は、通常の履歴保持や記憶の保管ルールよりも最優先されます。ただし、外部サービスのデータ消去やAPIキーの失効をeneが勝手に代行することはできません。「ログを残す必要があるから」という理由で、削除対象の本文をこっそり残す例外も認められません。
- **同意とスコープの優先**:
  現在の利用スコープ、非共有設定、プロバイダーへの送信同意は、プロバイダーの利便性やキャッシュ効率よりも常に優先されます。
- **安全停止の優先**:
  停止操作や予算上限、リストア保留状態は新規の活動を制限しますが、「停止を受け付けること」「事実を報告すること」「機械的な検証を行うこと」まで止めてはなりません。

### 横断的な状況における照合ルール

複数のフローや状況が重なった場合、以下のように整合性を保ちます。

| 複合して発生した状況 | 適用されるルールと責任の結び付け |
|---|---|
| **記憶の共有・訂正と、観測ルーティング・AIプロバイダー変更が重なった場合** | 全体共有された記憶から他人のプライベートな情報へアクセスを広げてはならず、画面観測と各パートナーの送信同意は別々に確認します。古い検索結果や関係性のメモから、訂正前の誤った情報を復活させてはなりません（CC-02・CC-03）。 |
| **タスクの方向転換・並列委任と、遅れて届いた承認・費用報告が重なった場合** | 方向転換前の古い結果を新目標の達成として使い回してはならず、古い承認でキャンセルを取り消してもいけません。処理中や未確定の費用も全体の予算上限から漏らさず管理します（CC-01・CC-03・CC-06・CC-07）。 |
| **画面をキャプチャした直後に、端末移動やパートナー停止（Stop）が発生した場合** | どの端末で取得したデータか、現在パートナーがどこにいるか、観測がONかを厳格に確認します。古いキャプチャを使って停止中のパートナーを起こしたり、無断で別端末へ送信したりしてはなりません（CC-02〜CC-04）。 |
| **端末の切断と画面操作（Computer Use）の未確定、Host再起動が重なった場合** | 外部ツールの実行が成功したか不明な状態を正しく維持し、Host側タスクの継続とパートナーの移動を切り離します。再接続時に未確定のアクションを勝手に再実行せず、オーナーに確認します（CC-03・CC-04・CC-07）。 |
| **パートナー削除と、遅れて届いたツール実行結果、指定データ削除が重なった場合** | パートナー削除後もタスクの実行事実ログは残せますが、指定データ削除の対象となっている本文は残せません。実行事実の説明と、削除されたパートナー固有の学習データの非復活を両立させます（CC-03・CC-05・CC-07）。 |
| **データ消去の完了直後に、遅延していた推論結果・再接続・Host再起動が発生した場合** | 全サブシステムがデータの再保存防止に参加し、通信不能や検証失敗を「消去完了」と誤認しません。未完了の制限を維持し、事実の報告は次の推論許可を待ちません（CC-02・CC-03・CC-05・CC-06）。 |
| **データ消去が未完了の状態で、バックアップやリストアが行われた場合** | 未完了の消去を無視して「正常な状態」としてバックアップを作成してはなりません。オーナーが古いバックアップをあえて選んで復元することと、システムが勝手にデータを復活させることは明確に区別します（CC-03・CC-05）。 |
| **リストアによるマスターデータ切り替えと、リストア前の古い処理結果、一括有効化が重なった場合** | 古い処理結果を復元後のデータに混ぜてはならず、外部ファイルや認証状態を過去に巻き戻しません。復元後の一括有効化でも、現在の拒否設定や予算上限、同意状態を無視してはなりません（CC-01・CC-03〜CC-05・CC-07）。 |
| **システム停止・データ保全中に、AI・描画・音声・外部ツールに障害が発生した場合** | 管理画面、キーボード操作、テキスト表示の代替経路を維持し、Hostが正常に受け取っていない要求を完了扱いにしてはなりません。内部管理のためにツールを使って自己承認することも禁止です（CC-01・CC-04・CC-06・CC-07）。 |

## 10. 設計の自由度（Design Freedom）

### 下位の詳細設計で決定してよい事項

アーキテクチャとして固定された重要原則に反しない限り、具体的な実装方法は後続の詳細設計で柔軟に選択できます。

| 設計対象 | アーキテクチャとして固定済みの原則 | 後続の詳細設計に残されている自由度 |
|---|---|---|
| **オーナー意図と判断対象・結果の対応** | AI生成コンテンツによって指示元を偽装できず、権限の変更や失効を各処理で正しく扱えること。 | 指示の由来情報（provenance）のデータ構造、確認画面のまとめ方、パーミッション評価エンジンの内部実装、競合制御方式。 |
| **コンテキスト構成とプロバイダー適応** | 用途、スコープ、根拠、現在の正しい認識、送信同意を遵守し、AI変更時も同じ情報選択基準を用いること。 | プロンプトの組み立てロジック（Context Assembly）、ルーティング用コンテキストの形式や更新頻度、検索・スコアリングのアルゴリズム、キャッシュ実装。 |
| **遅延結果と時間の管理** | 元の要求・根拠・用途との対応を保ち、時間の経過による失効や古い結果の混入を防止すること。 | バージョンやデータソースの識別方法、受け入れ処理のコード手順、時刻の保持形式、タイムアウトやリトライの具体的数値。 |
| **クライアント排他性と停止** | 同一パートナーの二重存在を作らず、状況不明時に危険な活動を継続せず、Host作業を端末へ勝手に移送しないこと。 | ペアリング認証情報の具体的なフォーマットや保存方式、再起動後の再接続待ちロジック、切断検知のハートビート間隔、安全な停止通知手順。 |
| **全域でのデータ保全・消去** | すべての保持先や一時キャッシュが消去に参加し、再保存を防ぎ、残存チェックを行い、正常状態を保護すること。 | 検索・無効化・検証のアルゴリズム、バックアップのファイル形式、リストア時の内部切り替え処理、ストレージの暗号化方式。 |
| **消費管理と縮退運転** | 並列処理や未確定の消費を共通の上限に反映し、高負荷時でも停止・保全の操作経路を維持すること。 | 費用の事前予約枠の管理方式、集計期間、リソース配分の優先度付け、話しかけの反復抑制アルゴリズム、省電力・待機機構。 |
| **説明・監査・情報提示** | 事実の確定度を誇張せず、プライバシーを守り、監査ログの順序や管理画面への到達性を維持すること。 | 監査ログのフォーマット、診断・テレメトリの収集スタック、ユーザーへの確認UIデザイン、要約の粒度、具体的な保持期間。 |

特定のRustのcrate、トレイト、具体的なAPIシグネチャ、ミドルウェア、イベントバス、データベーススキーマ、トランザクションの実装方法などは、すべて下位設計の自由度として残されています。本書の原則を満たすために、不必要な中央集権マネージャーや巨大な統一レイヤーを無闇に追加する必要はありません。既存の12のサブシステムと責任分担、Host/Clientの配置境界の中で最適な実装を選択します。

### 保証しない事項（不可能な保証を約束しない）

システムの健全性を保つため、技術的に不可能なことや過剰な前提を「保証事項」として約束してはなりません。
- AIによる意味理解の完全な正確性を保証することはできません。
- すでに外部ツールによって行われてしまった外部作用の完全なロールバック（巻き戻し）を保証することはできません。
- 分散環境における完全な「厳密に一度だけの実行（Exactly-once実行・配信）」を保証することはできません。

下位の詳細設計では、それぞれの仕組みが CC-01〜CC-07 の参加責任と、失敗時の安全側の動作（フェイルセーフ）を確実に満たすことを示します。
