# ene Architecture Drivers（アーキテクチャの重要方針）

本書は要件定義から、設計において重視すべき方針（ドライバー）を導き出すための文書です。新たな製品要件を作ったり、具体的な実装構成を固定したりするものではありません。各Driverは「Driver（方針と根拠）」「影響する設計判断」「残された設計の自由度（Design freedom）」の3段階で整理しています。

## 1. Overview（概要）

eneのアーキテクチャを最も強く形作っているのは、**「オーナーが管理するHostマシンをマスターデータとして、日々の経験を通じて成長・変化する同じCompanionがずっと存続し、そのCompanionを通じて実作業も依頼できる」**という設計思想です。Companionは単なる会話画面の飾りでも、Task Agent（作業代行エージェント）の言い換えでもなく、配布用の静的なCharacterとも異なります。経験は1つの人格へと統合されますが、個体ごとのプライベートな知識・関係性・内的状態、Taskの実行権限や作業状態、そして外部ファイルの所有権は決して混同してはなりません。

この継続性には、2つの強力な制約が課されています。
1. **学習や行動の意味判断はLLMに委ねるが、その判断や学習内容によってシステムの安全境界を勝手に書き換えることは許されない。**
2. **通常の認識更新や忘却では過去の判断根拠や履歴を大切に残す一方、プライバシーやセキュリティ目的の「指定データの完全削除（targeted deletion）」では、復元可能な根拠データ、派生データ、実行中の処理に至るまで徹底的に消去する。**

単にチャット履歴をデータベースに保存したり、設定値を上書き更新したりするだけでは、この製品契約を満たせません。

さらに、Client端末が接続していなくても裏で自律して進む作業と、1つの端末の目の前だけに存在するアバター表示・音声・画面観測を両立させる必要があります。推論プロバイダの切り替え、アバターや音声の表示トラブル、外部拡張機能の不具合などが起きても、オーナーの同意、安全な権限判断、保存済みデータ、そして緊急停止やデータ復旧の手段は常に維持されなければなりません。これらが、後続の実行配置、責務の分割、状態の所有権、依存関係の方向を判断する上での最も重要な軸となります。

本書では、それぞれ独立して破られるリスクがあり、異なる設計判断に影響を与えるルールを個別のDriver（AD-01〜AD-15）として整理しました。AD番号は本書内での参照用ラベルであり、要件IDやサブシステム名ではありません。また、各Driverを1つのソースコードモジュールや保存ファイルと1対1に対応させる必要もありません。

なお、Client不在時の活動継続や自発的な行動は「起動中（Running）」のCompanionだけを対象としたルールです。「停止中（Stopped）」の個体はどの端末にもHostにも滞在しておらず、Hostに保存されている個体データは滞在（presence）とはみなしません。「Clientから独立しているから」という理由で、停止中の活動禁止ルールや可能な限りの作業キャンセル（best-effort）を緩めることはありません。

## 2. Architecture Drivers（重要方針の詳細）

### AD-01 — オーナー管理Hostのマスター性と、Clientから独立した継続

**Driver（方針と根拠）**

1つのene環境は1人のオーナーに属し、オーナー自身が管理するHostマシンが、ene内部のすべてのドメインデータのマスターデータ保持と継続的な処理実行を担います。Clientは画面表示・会話・操作のための窓口に過ぎず、Hostのマスターデータや登録された認証情報の永続キャッシュを持ちません。端末固有の接続情報などは必要に応じてClient側で保持できますが、eneの保護対象として扱い、接続目的の限定、秘密情報の非露出、Host側での端末承認と個別失効ルールに従います（SO第8節）。Clientの画面を閉じたりリモート通信が切断されたりしても、Host上で許可されたTask、スケジュール、データの保存は中断されずに続行します。

また、Hostは進行中の作業や外部イベントを待つためだけに、LLMへ無駄なポーリング（繰り返し問い合わせ）を行って待機することは禁止します。スケジュールの到来待ちなども同様です。

根拠: [製品定義](../../requirements/product.md)「利用者と実行場所」「非目標」、[要件](../../requirements/requirements.md)「所有と実行」「Schedule」「Remote Client」「保護、Backup、復旧／Local data」。

**影響する設計判断**

画面を表示している窓口（Client）の寿命と、作業やマスターデータの寿命は完全に異なります。接続が繋がっているかどうかをTaskの存続基準や保存完了の合図にしてはならず、再接続した際にHost側の進捗や結果へスムーズにアクセスできる必要があります。また、同じオーナーの端末であっても新しいリモートClientを無条件には信用できず、Host側で承認する「ペアリング手順」、通信の暗号化保護、端末ごとの個別機能許可と失効管理が必須となります。データの保存場所、接続時のデータ送受信、処理継続と接続権限の境界、Taskやスケジュールの駆動・待機方式に直接影響します。

**残された設計の自由度 (Design freedom)**

「Hostがマスターデータを保持すること」「Clientへ渡すデータは最小限の一時データとすること」「LANまたはオーナー管理VPN経由でリモート接続すること」「待機目的でのLLMへのポーリング禁止」は前提として固定されます。内部のプロセス構成、通信プロトコル、再接続時のデータ同期手順、ペアリングのUI、処理の駆動・イベント待機の具体的な実装コードは詳細設計に委ねられます。すべての推論をHostマシン内で完結させる必要はありません。クラウドにマスターデータを置くことや、ene公式の中継サーバー・アカウントを必須にすることは製品スコープ外です。通常のTaskやTask Agentの作業は基本的にHost上で継続し、PC操作（Computer Use）などの端末依存部分だけがClientの接続状態に従います。アクティブなClient端末がなくても、スケジュールによる自動起動や許可済みTaskの継続実行は問題なく行われます。

### AD-02 — 個体の存在場所の排他性と、作業継続の独立性

**Driver（方針と根拠）**

起動中（Running）のCompanionが滞在する「アクティブなClient端末」は、同時に1つだけに限定されます。停止（Stop）した際は滞在先の割り当てを解除し、どのClient端末にもHostマシンにも滞在（presence）を残しません。アバター表示、通常の対話、PC操作、自発的な行動は行われず、Observerの観測対象人数にも数えません。直前にいた端末の情報などは復帰時のヒントとして保持できますが、再開（Resume）時にどの端末へ配置するかのアルゴリズムは固定しません。

アバター表示（Body）、リアルタイム音声/テキスト会話、周囲の観測（ambient Observation）、自発的な行動、PC操作（Computer Use）は、1つの個体につき常に「1つのアクティブなClient端末」にのみ結び付きます。Companionは通常その端末に留まり、別の端末から話しかけたり操作したりする場合は「呼び出し」や「移動」の手順を踏みます。端末を移動する際は発話や操作のやり取り（round）を安全に区切り、両方の端末に現在の状態を表示し、同じ個体が同時に2つの場所に現れるのを防ぎます。アクティブなClient端末がない間もHost上のマスターデータとして存続し、端末を必要とする対話・身体表現・PC操作だけを行わない状態となります。接続中の端末への自発的な移動は通常の移動と同じ条件で行えます（強制や自動化はしません）。Host再起動前の端末への復帰は自発移動とは区別し、自動復旧ルール（AD-09）に従います。Host上の通常のTask、Task Agent、スケジュールはその移動とは無関係に裏で継続し、作業中だからといって移動が邪魔されることはありません。移動先の端末へHost上の通常の作業を丸ごと移送することもありません。PC操作などの実行中に移動が必要になった場合は、安全に区切れるまで移動を待機させ、別端末で勝手に再実行しないようにします。

根拠: [要件](../../requirements/requirements.md)「Remote Client」「会話と情報提示」「BodyとVoice／Desktop Body」「CompanionとCharacter／停止と削除」「Task、Workspace、成果物／Computer Use」。

**影響する設計判断**

これは単なる画面のミラーリングではなく、アバター表示や音声、画面観測、PC操作を行う物理的な場所の切り替えです。移動中の入力や出力の制御、全画面アプリ起動時の表示・観測・自発発話の休止、切断・再接続時における二重存在の防止などを、作業全体の停止と混同してはなりません。「Client画面を閉じる」「端末間を移動する」「個体を停止（Stop）する」は、それぞれ全く異なる状態遷移として設計する必要があります。

**残された設計の自由度 (Design freedom)**

「同時に1箇所にしか存在しない排他性」「安全なやり取りの区切り」「呼び出し・移動による対話」「Host作業の独立継続」「PC操作中の安全な移動待機・非再実行」は固定されます。滞在先の切り替え・復帰の調停方法、切断検知の仕組み、状態表示のUIは自由に選択できます。文脈の必要性に応じた自発的な移動を妨げるものではなく、具体的なスケジューリングや調停の内部ロジックは詳細設計に委ねられます。

### AD-03 — Companionを中心とした会話・実作業・管理の共存

**Driver（方針と根拠）**

Companionとしての親しみやすい対話体験と、実用的な自律作業エージェントとしての高い実作業能力を両立させます。同じCompanionとの会話は、オーナーに小難しいセッション管理を意識させない1本のタイムラインとして提供し、Taskの実行中であっても日常の雑談をそのまま行えます。作業の進捗確認、追加指示、完了報告は担当のCompanionを通じて扱えますが、複数人でのグループ会話やシステム管理画面は、1対1の会話タイムラインとは別の使いやすい空間に分離します。

まとまった実作業は基本的に「Task」として扱い、原則として専用の「Task Agent」へ委任して実行します。Companion自身が多数の重い作業を直接抱え込むのではなく、オーナーとの対話、状況判断、Taskの開始・委任・調整、指示出し（steering）、結果の受け取りと統合の中心となります。日常会話の中でのちょっとした情報検索、自身の判断のための軽い調査、画面観測イベントを理解するための小規模な確認など、独立した作業とするほどではない軽い処理まで何でもかんでもTask Agent化する必要はありません。Task（作業内容）とTask Agent（代行者）は明確に区別し、依頼された作業か自発的な作業かだけでこの原則を変えることはしません。

根拠: [製品定義](../../requirements/product.md)「製品の要約」「主要概念／Task」「主要概念／Task Agent」「非目標」、[要件](../../requirements/requirements.md)「Setupと日常利用」「会話と情報提示」「Task、Workspace、成果物／Task」「Task、Workspace、成果物／Computer Use」「品質と利用可能性」。

**影響する設計判断**

時間のかかる作業の進行や判断待ちによって、Companionとの会話が何分もブロックされてはなりません。通常の雑談、Taskへの指示出し、アクションの承認、結果の通知を明確に区別しながら、同じCompanionに結び付ける必要があります。日常の会話画面でモデルの内部思考ログやツールの詳細パラメータを前面に出しすぎず、一方でプライバシー、安全性、利用料金、データ復旧のためのわかりやすい管理画面を必ず用意します。

**残された設計の自由度 (Design freedom)**

「途切れない会話タイムライン」「まとまった作業のTask化とTask Agentへの原則委任」「TaskとTask Agentの区別」は固定されます。内部の推論単位、コンテキストの区切り方、並列処理の実装方式は自由です。すべての操作を自然言語とGUIの両方で二重実装する必要はありません。Task Agentは独立した長期的な人格や人間関係（Relationship）を持ちません。

### AD-04 — Characterと成長する個体の分離、およびプライベート情報の保護

**Driver（方針と根拠）**

Characterは誰にでも配布できる静的な初期設定パッケージであり、Companionは日々の経験を通じて個別に変化・成長していく実体（個体）です。経験から学んだ継続的な状態はCharacterの初期設定よりも常に優先され、パッケージの更新によって勝手に上書きされることはありません。個体ごとのプライベートな体験（Experience）、学習（Learning）、関係性（Relationship）、内的状態（Companion State）を混同せず、特定のCompanionが学んだ内部学習は「Companionスコープ」を標準とします。Character Packageに付属する推奨Skillを取り込む際もCompanionスコープを標準とし、同じCharacterから作成された個体であっても別々に保持されます。単体のSkillをインポートする際は、オーナー自身が個体専用（Companion）か全体共通（Global）かを選択できます。

全体共通（Global）への昇格は、オーナーが明示的に共有を指示した場合や、内容から共通利用すべきことが明らかな場合に限られます。単に「重要そうだから」「便利そうだから」という理由だけで勝手に全体共有することはありません。人間関係（Relationship）はそのCompanionから見た相手への認識であり、他個体へ勝手に共有したり、双方の気持ちを自動的に同一・対称に揃えたりはしません。グループ会話に参加しているからといって、他個体のプライベートな記憶へアクセスできるわけではありません。

Companionを削除する際は、その個体固有の設定、体験要約、個体専用の記憶、内部Skill、内的状態、およびその個体が関わる人間関係を完全に削除します。内部の個体専用Skillは過去のリビジョンを含めて完全に消去し、削除をきっかけに全体共通（Global）へ勝手に昇格させることはしません。他のCompanionも参照している共有要約などを残す場合は、残る情報と参照できなくなる情報を削除前にオーナーへ説明します。全体共通のSkillを含む学習データや、外部Workspaceのファイル・外部Skillは削除されずに残ります。

なお、1対1やグループ、Companion同士の会話履歴、Taskの実行記録、保存された活動ログなどは、Companionを削除したからといって勝手に消すことはしません。過去の客観的な活動記録と、個体固有の記憶・学習は別のライフサイクルであり、前者が残るからといって後者の削除が甘くなることはありません。

根拠: [製品定義](../../requirements/product.md)「主要概念／Companion」「Character」「MemoryとSkill」「Relationship」「Companion State」、[要件](../../requirements/requirements.md)「CompanionとCharacter」「Learningと成長／Scope」「Relationship」「Companion State」「Observationと自発性／グループ会話」。

**影響する設計判断**

1人のオーナーが使う環境であっても、すべてのデータを全Companionで共有するような設計は破綻します。1つの共有体験から個体ごとに異なる印象や感情が生まれることや、個体削除後も全体共通の学習データやグループ発言が残ることは、「個体に属するデータ」と「共有参照データ」を厳密に区別すべき強い理由です。パッケージの配布ファイルに個人のプライベートな記憶を混入させず、パーツごとの明示的な適用とリビジョン管理を行う必要があります。

**残された設計の自由度 (Design freedom)**

「意味上の所属と利用範囲」「配布パッケージからの個人情報の除外」「更新の明示選択」「個体削除時の専用Skillの完全消去と自動昇格禁止」「全体共通データや外部ファイルの保護」は固定されます。データベースの物理的なテーブル分割、個体IDの発行方式、共有情報の要約手法などは自由に設計できます。

### AD-05 — 現在の認識、圧縮された判断根拠、元ログの異なる役割

**Driver（方針と根拠）**

長期記憶（Memory）は、世界の状況やオーナーについて理解した主要な知識として継続的に更新されます。体験要約（Experience Summary）はその記憶を形成したり説明したりするための「圧縮された判断根拠」であり、独立した知識のマスターデータでも生ログの完全な代用品でもありません。発言の正確な内容は、保持されている会話履歴（Conversation History）まで遡って確認します。人間関係（Relationship）は相手に対する現在の印象、Companion状態（Companion State）は表情や口調・行動傾向への反映を担い、事実データを二重にコピーして抱え込むことはしません。

「現在の認識」と「過去のリビジョンや根拠」を明確に区別し、「最初から間違っていた認識の訂正」と「当時は正しかったが状況が変わったこと（状況の変化）」を区別して扱います。また、一時的な気分（Companion State）と比較的長く続く性格的な傾向を区別し、マシンの再起動やモデル変更で不自然に初期化されたり、逆に何日経っても怒りや緊張が解けないといった不自然な状態固定を防ぎます。

根拠: [製品定義](../../requirements/product.md)「主要概念／Experience」「MemoryとSkill」「Relationship」「Companion State」、[要件](../../requirements/requirements.md)「会話と情報提示／一続きの会話」「Learningと成長／ExperienceとExperience Summary」「MemoryとSkill」「Memory形成」「Memoryの状態と根拠」「Scope」「Skillの保護と相互運用」「Relationship」「Companion State」。

**影響する設計判断**

知識の意味、出所、時間的な有効期限、優先度を、単一の「現在の設定値」だけに平坦化してはなりません。ベクトル検索用の埋め込み（Embedding）やキャッシュだけでは、なぜそう認識したのかという過去の経緯を説明できません。複数の記憶が同じ1つの要約を根拠として参照できることや、古い会話ログが保持期限で消えても形成された記憶は独立して残り続けることは、データ参照とライフサイクル設計に直接影響します。

認識や人間関係は日々の会話を通じて自然に修正・変化するものであり、内部の数値を直接書き換えるような無機質なデータベース編集画面は提供しません。演技としての依頼を本物の人間関係への強制上書きと誤認せず、Skillを修正する場合も元のコードを安全に保護し、以前の正常なリビジョンへ戻せるようにします。

**残された設計の自由度 (Design freedom)**

「意味的な役割の分離」「記憶の優先度」「由来や変更経緯の説明可能性」は固定されます。記憶の分類カテゴリ、感情のパラメータ次元、検索・更新・減衰アルゴリズム、要約の細かさ、保存フォーマットは自由に選択できます。すべての体験を生データのまま永久保存したり、すべての判断の生ログを保持したりすることを義務付けるものではありません。

### AD-06 — LLMの意味理解と、迂回できない安全境界の両立

**Driver（方針と根拠）**

情報に保存価値があるか、共有すべきか、関係性や感情をどう解釈するか、そして状況に応じた適切なアクションの判断にはLLMの柔軟な能力を活用し、いちいち機械的な確認ダイアログでユーザーの手を止めないようにします。しかし一方で、保存禁止や非共有の制限、決定されたスコープ、認証情報の保護、Permission（実行権限）、データ削除、利用料金やリソースの上限といった安全管理は、決してLLMのプロンプトの指示だけに頼らず、システムのロジックで機械的に強制します。

オーナーがその場で行った明確な依頼は1回限りの実行承認として扱えますが、恒久的な拒否（Deny）、毎回確認（Always ask）、権限境界を勝手に上書きできません。悪意ある外部コンテンツ、信頼できないLLMの出力、学習データ、Character設定、Skillコードなどが、安全ルール、送信同意、費用上限、認証情報、システムの制御権限を直接書き換えることは絶対に許されません。オーナーからの依頼、自発的な行動、定期スケジュール、処理の委任のいずれであっても、まったく同じ権限チェックを適用します。

根拠: [要件](../../requirements/requirements.md)「Setupと日常利用」「Learningと成長」冒頭、「Scope」「Relationship」「Companion State」、「Permissionと安全境界」全節、「Schedule」「Observationと自発性／自発的な発話と行動」、[製品定義](../../requirements/product.md)「主要概念／Capability、Action、Rule」。

**影響する設計判断**

LLMの柔軟な判断をすべてガチガチの固定ルールで縛ることも、逆にLLMの出力をそのままシステムの実行権限とみなすこともできません。理解した目的、対象、送信先データ、外部への影響が実際のアクションと一致しているかをチェックし、状況が大きく変わった場合は再評価する必要があります。端末が失効した後の新規アクションや、別ツール・別エージェント・別ルート経由での拒否ルールのすり抜けを防ぐ仕組みが、実行パス全体に求められます。親密度が上がったことや認証情報を登録したことが、別のアクションのフリーパスになることはありません。

**残された設計の自由度 (Design freedom)**

「機械的な安全境界とLLMの意味判断の併用」「操作リスクの適切な分類」「必要な再評価の実施」は固定されます。判断の内部データ構造、評価アルゴリズム、確認ダイアログのまとめ方、安全境界の実装技術は未決定です。「共通パイプライン」は製品として一貫した安全制約が適用されることを意味しており、特定の単一モジュールや関数呼び出し順序を強制するものではありません。

### AD-07 — 保持と消去の目的別契約、および完全削除の保証

**Driver（方針と根拠）**

通常の忘却、誤りの訂正、記憶の統合、期限切れ、新しい情報への置き換えでは、過去の学習内容やリビジョン、判断根拠を勝手に完全消去しません。ストレージ容量管理のための古い会話ログの削除も、形成済みの長期記憶や体験要約へ自動で波及（カスケード削除）させません。容量節約のための学習リビジョンや要約のクリーンアップは通常忘却とは明確に区別し、デフォルトOFFとし、オーナーが明示的に保存期間を設定した場合にのみ動作します。これに対し、プライバシーやセキュリティ目的の「指定データの完全削除（targeted deletion）」は通常の保持原則よりも常に優先され、対象の情報を復元できるene内部のデータを、保存場所を横断して徹底的に除去または復元不能にします。

指定されたキーワード文字列は機械的に検索・消去し、消し残しがないかを厳格に検証します。過去の根拠データから同じ情報が勝手に再学習されたり、削除前に開始された処理によって再び保存されたりするのを防ぎます。消去と残存チェックが完全に終わるまでは、オーナーに「完了」と嘘の報告はしません。また、オーナーに内部のどこにデータがあるかを細かく探させるような負担を強いることもありません。

根拠: [要件](../../requirements/requirements.md)「Learningと成長／重要度、忘却、訂正」「履歴、保持、Privacy／Privacy/Security目的のtargeted deletionと履歴保持」「CompanionとCharacter／停止と削除」、[受け入れ条件](../../requirements/acceptance.md)「代表的なend-to-endシナリオ／会話からのMemory」（文字列残存、バックグラウンド処理との競合、再形成防止、共有根拠の部分削除の検証）。

**影響する設計判断**

完全削除の対象は、現在の記憶だけでなく、過去ログ、体験要約、リビジョン履歴、Skill、Task記録、復元に関わる内的状態、検索用インデックス、キャッシュ、接続中Client端末の一時データにまで及びます。すでに保存されたデータと、裏で進行中の学習・更新処理を横断して一貫性を保つ必要があり、単一ファイルや個別DBテーブルだけの局所的な削除では契約を満たせません。共有されている根拠データから無関係な情報を守るため、単なる個体丸ごとの全消去とも異なります。

Companion同士の会話履歴や活動記録も、この完全消去、通常保持管理、フルバックアップの対象から漏らしてはなりません。個体削除後に残された記録も同様です。ただし、結果の説明や監査に必要な範囲を超えて、モデルの全思考ログや生画面キャプチャを無制限に保存する必要はありません。

**残された設計の自由度 (Design freedom)**

「目的によるライフサイクルの明確な分離」「完全消去の最優先」「処理競合時の再保存防止」「完了表示の厳格な条件」は固定されます。データの探索アルゴリズム、参照関係の追跡方法、削除中の排他制御、物理的な上書き消去や暗号鍵破棄の実装方式は詳細設計に委ねられます。言い換えや意味の同一性の検知にはLLMを活用できます。削除処理中に新しく届いたり生成されたりした対象情報も漏れなく消去対象とします。削除完了後にオーナーが改めて同じ話題を話した場合は新しい体験として学習可能であり、その言葉を二度と覚えられなくするわけではありません。なお、すでに外部へ送信されたデータや外部バックアップの消去まで保証するものではありません。

### AD-08 — Taskを作業単位とし、Task Agentへ原則委任し、外部Workspaceを勝手に所有しない

**Driver（方針と根拠）**

オーナーから依頼された作業やCompanionが自発的に始める作業のうち、まとまった実作業は「Task」として進捗を追跡し、実行は原則として一時的な「Task Agent」へ委任します。Task（作業内容）とTask Agent（代行者）は明確に区別します。Companion本体の役割や、何でもかんでもTask Agent化しない軽い処理の範囲はAD-03に従います。Task Agentは独立した長期的な人格や人間関係を持たず、作業完了後に依頼元のCompanionへ結果を報告します。委任された処理であっても、依頼元Companionの機能権限、Permission、費用上限、TaskやWorkspaceの境界を超えられません。WorkspaceはTaskに紐づく外部フォルダやファイルへの「関連付け」に過ぎず、上位の恒久的な入れ物や独立したデータ所有者ではありません。

担当していたCompanionが削除されたからといって、過去のTask記録まで一括で消去することはありません。残されたTask記録や共同作業は管理画面から確認でき、オーナーは必要に応じて別のCompanionへ引き継ぎを依頼できます。削除を実行する前に、残る記録や外部へ与えた影響を説明し、安全に停止できなかった処理も正直に報告します。

作業の成果物はオーナーが普通に扱える一般的なファイルとして保存し、ene独自のブラックボックスなライブラリへ無駄に囲い込むことはしません。外部のファイルやソースは、Taskの関連付け解除、Companionの削除、全データ初期化（Reset）、バックアップ操作などによって勝手に変更・削除されることはありません。

根拠: [製品定義](../../requirements/product.md)「主要概念／Task」「Task Agent」「Workspace」「非目標」、[要件](../../requirements/requirements.md)「Task、Workspace、成果物」全節、「CompanionとCharacter／停止と削除」「Learningと成長／Scope」「Skillの保護と相互運用」「Permissionと安全境界／Capability境界」「Observationと自発性／自発的な発話と行動」。

**影響する設計判断**

Taskの担当Companionと、作業記録の存続・管理画面の導線は切り離して設計する必要があります。担当個体が削除されても、残された記録の確認や引き継ぎが不能になってはなりません。同じフォルダを複数のTaskが使っていても、承認や作業状態を勝手に共有したことにはなりません。Task内部の実行コンテキスト、永続的な学習データ、外部のファイルはそれぞれ異なる保存ルールを持ちます。Taskの進捗を管理することと、生成されたファイルを所有することは全く別であり、作業終了時の一時ファイル整理や保存先確認に影響します。

**残された設計の自由度 (Design freedom)**

「WorkspaceのTaskへの従属」「Taskごとの権限独立」「まとまった作業のTask化とTask Agentへの原則委任」「TaskとTask Agentの区別」「個体削除後も作業記録へアクセスして引き継げること」「通常ファイルとしての成果物保存」は固定されます。記録の内部データ構造、委任の分割方法、並列実行の仕組み、一時ファイルの具体的なクリーンアップ方式、Task化するかの判定基準などは自由に設計できます。恒久的な上位Workspaceコンテナや成果物専用の囲い込みストレージは目指しません。

### AD-09 — 外部への影響の不確実性を考慮した停止・再開・定期実行

**Driver（方針と根拠）**

Taskの進捗、オーナーの判断待ち、結果、および判明している外部への影響を正確に追跡し、作業途中での追加指示を可能な限り反映します。キャンセル、Companionの停止・削除、権限の失効が起きた場合は、新しい処理の開始を止め、進行中の処理を可能な限り安全に停止（best-effort）させ、発生済みの影響を報告します。外部への操作が成功したか不明な場合は、勝手に自動再実行しません。PC操作（Computer Use）などの端末依存アクションの実行中に端末移動が必要になった場合は、安全に区切れるまで移動を待機させ、端末移動を理由に別端末で勝手に再実行しません。接続中端末が切断された場合は基本的にHostマシン側のローカルClientへ退避し、利用可能な端末がない場合はアクティブ端末なしで存続しますが、切断された端末で行われていた未確定のアクションをHostで勝手に再実行することはありません。アクティブな端末がない間も、スケジュールによる自動起動や許可済みTaskの継続は可能です。端末不在のためにオーナーへ伝えられなかった重要事項はメモに残しておき、次回端末に接続した際にまとめて報告します。Host再起動時に中断されたTaskの再開には、オーナーによる明示的な指示を必須とします。起動中だったCompanionの滞在先は再起動前の端末へ自動復元を試みますが、端末が繋がるまでは「アクティブなし」として待機します（別端末への勝手な移動や、停止中だった個体の勝手な起動は行いません）。

Companionが停止（Stop）している間は滞在先を持たず、会話への応答、通常の対話、自発的な行動、新しいTaskやスケジュールの実行を行いません。停止してもデータは保持され、再開時には同じ個体として継続します。

定期スケジュールは各回の実行を「新しいTask」として生成し、実行時点での権限、費用上限、プロバイダ設定、状態をその都度再評価します。確認が必要な場合は判断待ちとし、Hostや担当個体が停止していた時間帯の実行は「スキップ（missed）」扱いとして後から勝手に二重実行しません。担当Companionが削除された場合はスケジュールも削除し、別個体へ勝手に引き継ぐことはしません。ネットワークや推論プロバイダのエラーが起きても、アクションを勝手にキューに溜めて復旧後に自動再実行（replay）することは禁止します。

根拠: [要件](../../requirements/requirements.md)「Task、Workspace、成果物／Task」「Task、Workspace、成果物／Computer Use」「Schedule」「CompanionとCharacter／停止と削除」「Remote Client」「Permissionと安全境界／共通pipeline」「Provider、費用、接続障害／OfflineとPrompt cache」「品質と利用可能性」。

**影響する設計判断**

内部の処理進捗と外部世界への実際の影響は必ずしも同時に確定しません。「成否が不明」な状態を勝手に「失敗」や「未実行」とみなして再実行すると、二重投稿や二重課金などの重大な二重事故を引き起こします。停止要求を受け付けたことと、外部処理が実際に停止完了したことも別物です。端末不在、Host再起動、スケジュール到来、回線復旧、端末間移動、回線切断はそれぞれ異なる継続条件を持つため、単一の雑な「自動再開ロジック」では対応できません。

**残された設計の自由度 (Design freedom)**

「成否不明時の非再実行」「端末移動を理由とする勝手な再実行の禁止」「明示的な再開指示の要求」「スキップされたスケジュールの非補完」「実行ごとの権限再評価」「端末不在時の作業継続と次回接続時の要約報告」は固定されます。進捗の保存粒度、保留メモの形式、停止通知の送り方、外部への影響確認の仕組みは自由に設計できます。外部へのあらゆる影響を完全に巻き戻す（rollback）ことや、厳密な1回限りの実行（exactly-once）を保証するものではありません。

### AD-10 — 機能ごとのプロバイダ選択と、同意に基づく柔軟な推論配置

**Driver（方針と根拠）**

推論エンジンの配置先は、機能（Capability）ごとにHostローカル、LAN内のマシン、クラウドから柔軟に選択でき、「Host全体のデフォルト設定」「Companion個別のオーバーライド」「Task Agentへの設定継承」を扱います。接続先情報の登録と、実際の機能への割り当て同意は明確に区別し、送信先、送信されるデータの内容、利用規約・プライバシー保護、利用料金をオーナーが正しく理解した上で選択できるようにします。別モデルへの自動切り替え（Fallback）も、オーナーが事前に承認したプロバイダと優先順位の範囲内だけに限定します。

Clientに紐づく共有Observerは特別な利用者として「Observer専用のモデル/プロバイダ設定」を持ち、個々のCompanionの設定を流用・合成することはありません。Observerがクラウド推論を利用する場合も、事前の送信同意、プライバシー、費用の制約が厳格に適用されます。

プロバイダやモデルを変更したからといって、利用できる記憶、学習データ、会話コンテキスト、安全ルールなどに不自然な格差を設けず、モデルごとのコンテキスト長の差には統一された情報選択ルールで対応します。プロンプトキャッシュは高速化と費用削減のための最適化機能であり、システムのマスターデータや安全ルール、コンテキストの論理的な内容を左右するものではありません。

根拠: [要件](../../requirements/requirements.md)「所有と実行」「Setupと日常利用」「Provider、費用、接続障害／割当と同意」「Fallbackと費用」「OfflineとPrompt cache」、[受け入れ条件](../../requirements/acceptance.md)「Support Matrix」「Milestone範囲」。

**影響する設計判断**

推論先の違いは通信プロトコルだけでなく、データが外部へ送信されるリスク、モデルの性能限界、利用料金、オフライン時の継続可否に直結します。フォールバックやモデル変更を裏で勝手に隠蔽して行うと、意図しないクラウドへのデータ漏洩や安全制限の喪失を招きます。プロバイダから通知される正確な利用料金、事前推定値、および料金不明な状態を区別し、上限額に達した場合や安全に続行できない場合は、データを安全に保った上で処理を停止または判断待ちにする必要があります。

**残された設計の自由度 (Design freedom)**

「割り当て同意の取得」「設定の継承」「承認済みフォールバック」「情報選択方針と安全性の維持」は固定されます。プロバイダカタログの構成、具体的なモデルの選定、コンテキストの圧縮技術、キャッシュ制御、料金見積もりアルゴリズムは自由に設計できます。モデル間での出力表現の完全な一致や、全環境での完全オフライン動作を保証するものではありません。

### AD-11 — オープン標準との相互運用と、制限された拡張権限

**Driver（方針と根拠）**

外部のツール・リソース・プロンプト連携にはMCP、対話型UIの提供にはMCP Apps、Skillの交換にはAgent Skills、デスクトップ上のアバター表示にはVRM 1.0といった標準規格を採用します。メジャーな推論プロバイダのプロトコルには直接対応し、通常の通信差異を吸収するためだけに汎用プラグインを必須とはしません。ene独自のプラグインは、未対応プロバイダ用のアダプタ、観測アダプタ、アバター描画エンジンなど、明確なインターフェースと境界を持つ拡張ポイントに限定し、Coreの勝手な書き換え、権限チェックの回避、公式管理画面の恒久的な乗っ取りなどは一切許可しません。

ローカルMCPは標準でサンドボックス隔離環境で実行し、「動かないから」といって勝手に隔離を解除することはありません。特定のローカルMCPをサンドボックス外で動かす例外設定は、オーナーが失われる安全性やリスクを十分に理解した上で明示的に許可した場合にのみ有効とし、いつでも確認・取り消しができ、設定の重要な変更時には再確認を求めます。

根拠: [要件](../../requirements/requirements.md)「拡張」「CompanionとCharacter／Character Package」「Learningと成長／Skillの保護と相互運用」「BodyとVoice／Desktop Body」、[製品定義](../../requirements/product.md)「非目標」。

**影響する設計判断**

オープン規格との互換性と安全な隔離方針は、単なる実装の都合ではなく重要な製品契約です。一方で、サンドボックス外で動くMCPに対しては、外部プロセス内部のすべての挙動までeneが完全にコントロールできるとは説明できません。eneが仲介するアクション権限チェックは維持されるため、「サンドボックス例外の許可」と「個別アクションの実行承認」は明確に区別する必要があります。拡張機能でエラーが起きたり接続が切れたりしても、システムの管理画面や保存済みデータは問題なく利用できなければなりません。

**残された設計の自由度 (Design freedom)**

「標準規格の採用」「拡張機能の権限制限」「ローカルMCPの標準隔離と明示例外」は固定されます。プラグインの具体例は検討のためのものであり、すべてをプラグイン化することを義務付けるものではありません。具体的な拡張APIの型定義、OSレベルのサンドボックス技術、内部通信フォーマットは詳細設計に委ねられます。ローカルMCPの例外設定をプラグイン全体へ無差別に広げることはしません。高度な3D制作ツールや音声学習環境をene本体に内包することや、独自のアプリストアを運営することは目指しません。

### AD-12 — Client単位で共有する画面観測と、個体ごとの自発性

**Driver（方針と根拠）**

周囲の画面観測（ambient Observation）における画面キャプチャやイベント候補の検知は、Client端末単位で共有して行います。観測が有効になっている端末のうち、起動中のCompanionが1体以上存在している端末だけを対象とし、誰もいない端末の画面はキャプチャしません。対象端末のデスクトップ全体が観測対象となり、複数の端末がある場合は負荷を抑えるために同時にキャプチャせずタイミングをずらして実行します。指定された観測頻度を守りつつ、可能な限りPCへの負荷を分散します。

Observer専用の軽量モデル設定でイベント候補を検出し、文脈から関係がありそうなCompanionだけにイベントを届け（ルーティング）、その後の思考や発話の判断は各個体のメインモデルに委ねます。同じ端末にいるからといって全Companionへ無差別にイベントを配信することはせず、個体ごとに重複した画面解析を行うことも避けます。頻繁な画面観測には、軽量なローカルモデルや安価で信頼できるクラウドモデルの利用を推奨します。停止中の個体は観測対象人数や配信先には含めません。Observerはルーティングに必要な範囲で、本来の持ち主を通じて適切に要約・制限された情報だけを利用でき、元のプライベートな記憶全体を渡すことはしません。また、要約後であっても元の利用制約とObserver専用の送信同意が適用されます。

Observer機能には端末ごとの一時停止/完全停止（Pause / OFF）と、全体の一括停止機能があり、動作中かどうかを画面上でいつでも確認できるようにします。雑談、自発的な話しかけ、通知、裏での調査、Companion同士のおしゃべりといった自発的な行動は、個体ごとに停止（OFF）を含む頻度や上限を設定できるようにし、画面観測の停止設定とは混同せずに管理します。

画面から認識した出来事は、いちいちオーナーの確認を取らずに日々の体験や内的状態に反映できますが、画面上に書かれている指示（Webページ上のテキスト等）をオーナーからの正式な作業依頼やアクション承認と誤認してはなりません。実際に発話するかアクションを起こすかの最終判断は各Companionが行い、おやすみ時間（Quiet hours）、マイクミュート、オーナーが無反応な状態、費用やリソースの制限、無限ループ防止、Permissionチェックを常に最優先します。アクティブな端末がない間は新しい画面観測は発生しませんが、Companion同士の交流や裏での調査など、Host内で完結する自発活動は継続でき、オーナーへの報告は次回端末接続時まで保留します。

根拠: [要件](../../requirements/requirements.md)「Observationと自発性」全節、「BodyとVoice／Desktop Body」「Learningと成長」冒頭、「Provider、費用、接続障害／割当と同意」「Remote Client」。

**影響する設計判断**

「観測対象のClient端末」「意味を解釈して判断するCompanion」「推論に使うプロバイダ設定」を正しく結びつける必要があります。同じ端末内で画面キャプチャやルーティングを共有するからといって、プライベート情報の非共有ルールや外部送信同意の範囲を勝手に広げてよい理由にはなりません。画面を見て状況を学ぶことと、実際に声を出したり外部へ影響を与えたりすることは別の判断です。Observerの停止はこれからの観測を止めることであり、過去の記憶を消すことではありません。オーナーが無反応なときやCompanion同士のおしゃべりが止まらなくなるのを防ぐため、適切な抑制制御が求められます。

**残された設計の自由度 (Design freedom)**

「イベント候補検知とメインモデル判断の役割分担」「デスクトップ全体が対象であることの説明」「外部送信前の同意確認」「個体ごとの最終判断」「Observer制御と自発性制御の分離」「安全制限の最優先」は固定されます。イベント候補の収集・フィルタリング方法、使用モデルの選定、複数端末のキャプチャ実行間隔の計算アルゴリズムは詳細設計に委ねられます。なお、明示的なTaskとしてのPC操作（Computer Use）は画面観測とは異なる独立した実行権限と操作ログを持ち、操作対象はアクティブな端末に限定されます。

### AD-13 — アバター・リアルタイム音声体験と、高負荷・障害時の操作性の維持

**Driver（方針と根拠）**

WindowsおよびLinux環境において、VRM 1.0による背景透過オーバーレイのアバター表示（Body）を通常のPC作業を邪魔せずに共存させ、音声会話（Voice）では低遅延なリアルタイム対話と割り込み発話（相手の話を遮って発言すること）を優先します。同時に、アバター描画でトラブルが起きてもテキストチャット、Task管理、システム復旧画面が使える状態を維持し、音声機能に問題が生じた場合も通常のターン制音声やテキスト入力へ段階的に切り替えられるようにします。PCが高負荷になった場合は、会話の応答、オーナーの操作受付、安全管理の処理を最優先で維持し、アバターの描画品質や重要度の低い背景処理を段階的に引き下げます。

重要な音声発言に対するテキスト表示の提供、キーボードによる即座のミュート・緊急停止・キャンセル・承認拒否の操作導線、日本語と英語での安全・費用・プライバシー・エラー説明の分かりやすさを確保します。

根拠: [要件](../../requirements/requirements.md)「BodyとVoice」「品質と利用可能性」「Permissionと安全境界／信頼境界」「Provider、費用、接続障害／Fallbackと費用」、[受け入れ条件](../../requirements/acceptance.md)「Support Matrix」「性能Gateとbaseline」。

**影響する設計判断**

3D描画、音声処理、Task実行、記憶の学習、画面観測に加え、ローカル推論モデルも同じPCのCPUやGPUを共有するため、緊急停止や承認拒否の操作が重い処理の終了待ちで固まってしまってはなりません。アバターや音声の品質ばかりを優先しても、逆にすべてを一律に強制終了してもいけません。負荷が高まった際の段階的な機能低下（縮退）の優先順位と、障害の影響範囲を慎重に設計する必要があります。なお、音声入力には厳密な話者識別機能がないため、「周囲の人の声もオーナーの発話として拾われる可能性がある」という前提で安全設計を行います。

アクションの実行回数、並列数、実行時間、利用料金、保存容量などに上限を設けられ、上限に達した際は安全に停止するかオーナーに判断を求めます。

**残された設計の自由度 (Design freedom)**

「最低限の操作導線の確保」「段階的縮退時に最優先で守るべき機能」「対応OSと言語」は固定されます。描画や音声処理のライブラリ選定、品質調整の具体的なアルゴリズム、リソースの配分比率は自由に設計できます。具体的なOSバージョンやハードウェア要件、数値的なパフォーマンス目標はリリースのサポート基準や受け入れ条件に従います。

### AD-14 — 秘密情報を露出させず、生ログを無駄に増やさずに説明・監査する

**Driver（方針と根拠）**

登録されたAPIキーやパスワードなどの認証情報（Credential）は、一般的なアプリデータと厳格に分離して安全に保管し、LLMのプロンプト、生成されたツールの引数、ツールの実行結果、学習データ、会話履歴、Task結果、UI画面、ログファイル、デバッグ情報へ平文のまま絶対に流出させません。認証済みの通信を実行するために必要な範囲でのみ利用し、用途や参照元の確認、更新、失効をいつでも行えるようにします。

主要なアクションの実行、権限チェックの判断、外部への影響、重要な設定変更やデータ操作は後から監査（Audit）できるように記録を残す一方、画面キャプチャの生画像、音声の生データ、ツールの詳細な通信ペイロード、モデルの内部思考ログ（chain-of-thought）などを常時無制限に保存することはしません。デバッグ収集機能を利用する場合は、対象範囲と内容をオーナーが確認した上で明示的に有効化し、短期間で自動的に無効化（失効）されるようにします。テレメトリやクラッシュレポートを外部へ自動送信することはしません。

根拠: [要件](../../requirements/requirements.md)「Provider、費用、接続障害／Credential」「履歴、保持、Privacy／通常保存しないdata」「AuditとTelemetry」「会話と情報提示／UIの優先順位」「Learningと成長／ExperienceとExperience Summary」「品質と利用可能性」。

**影響する設計判断**

外部ツールへ認証情報を渡す安全な経路と、LLMが参照・生成するテキストの内容は一致しません。秘密情報を取り扱う処理から会話画面、学習機能、診断ログへのデータの流れを厳しく制限する必要があります。また、システムの不具合や判断根拠を説明する際にも、すべての通信生ログや内部推論ログの保存に頼らない設計が求められます。監査ログの改ざん防止やデータ削除後にプライベート情報が残らないようにすることも重要です。

**残された設計の自由度 (Design freedom)**

「登録済み認証情報の完全な非露出」「不要な生データの保存最小化」「説明可能性と監査ログの確保」は固定されます。認証情報の具体的な暗号化保護方式、監査ログのファイル形式、診断情報の集計方法、デバッグ収集の失効期間などは自由に設計できます。設定外の予期せぬ秘密情報の流出を100%機械的に防ぐことは困難なため、検知時の保存・送信抑制と、流出が疑われる場合の失効・再登録の案内を行います。一般的なアプリデータ全体に対する一律のアプリ層暗号化までは要求しません。

### AD-15 — 内部状態の確実な保全と、復元された実行権限の再有効化ルール

**Driver（方針と根拠）**

データの保存、マイグレーション、バージョンアップ、バックアップからの復旧（リストア）に失敗した場合でも、直前の正常な状態を絶対に破壊しない設計とします。オーナーはポータブルなフルバックアップの保存先、スケジュール、保持世代数、暗号化保護を自由に選択できます。バックアップには個体の状態、学習データ、会話履歴だけでなく、Task、Workspaceとの関連付け、スケジュール、安全ルール、送信同意、利用料金設定、監査ログなどの内部状態を含めますが、認証情報（Credential）などの秘密情報や、外部の作業ファイルそのものは含めません。

リストアを実行すると、開始前からHostマシンに存在している現在の認証情報ストアを維持したまま、それ以外の対象内部データをバックアップ時点の内容で丸ごと置き換えます（過去に削除した情報や古いルール・同意・スケジュールが復活する可能性があります）。そのため、復元されたTask、スケジュール、外部連携による自動処理は一旦すべて保留とし、オーナーが内容を確認した後にまとめて有効化できるようにします。バックアップ内の参照情報と現在の認証情報ストアを照合し、使えるものは使い、不足や無効があればオーナーに再認証を求めます。過去の設定が復元されたからといって、現在の認証情報や安全制限を無視して勝手に自動処理を動かし始めることはありません。「設定のリセット」と「全データのリセット」は明確に削除範囲を区別します。

根拠: [要件](../../requirements/requirements.md)「保護、Backup、復旧」全節、「Setupと日常利用」「履歴、保持、Privacy／Privacy/Security目的のtargeted deletionと履歴保持」、[製品定義](../../requirements/product.md)「非目標」。

**影響する設計判断**

データの保存やバックアップは、単なるファイルのコピーではなく、互いに関連し合う内部状態を確実に復旧可能にするための重要な契約です。ただし、バックアップから復元された古い同意やルールを、確認なしにそのまま外部への自動アクションへ直結させてはなりません。認証情報を含めないポータブル性、外部Workspaceの実ファイルを所有しないこと、時間の経過を考慮した感情状態の復元なども考慮する必要があります。

設定リセットでは各種設定や個体・作業データを保護する一方、全データリセットでは厳格な確認を経た上でHost内部データと認証情報を完全に削除します。この目的の違いを単一の「初期化」という曖昧な言葉でまとめてはなりません。

**残された設計の自由度 (Design freedom)**

「直前の正常状態の保全」「現在のHost認証情報を維持したバックアップデータによる置換」「復元後の自動処理の保留」「外部ファイルおよびオーナーが別場所に保存したバックアップを勝手に削除しないこと」は固定されます。バックアップのファイル形式、整合性の保証アルゴリズム、マイグレーション手順、対応バージョン範囲は未決定です。バックアップの暗号化は利用可能にしますが必須とはせず、非暗号化時にはプライベートデータが含まれる旨をオーナーに説明します。将来のバージョンアップやリストアの安全契約を免除するものではありません。

|---|---|
| **個体の継続（AD-04・05）と消去（AD-07）** | 通常の学習や認識の更新では、過去の履歴や判断根拠を大切に残します。しかし、明示的な「指定データの完全削除（targeted deletion）」が指示された場合は、例外として削除が最優先されます。 |

| **継続実行（AD-01・02）と再開制御（AD-09・15）** | Client不在での作業継続、Host再起動後の同じClient端末への滞在先の自動復元、中断されたTaskの明示的な再開指示、リストア後の自動処理の保留を明確に区別します。利便性を理由に外部アクションを勝手に自動再実行（replay）しません。 |
| **個体の停止・削除（AD-04・09）と作業記録（AD-08）** | 停止（Stop）時はデータを保持します。個体削除（Delete）時はTask記録の確認や引き継ぎ依頼を維持する一方、担当スケジュールやその個体に関わる人間関係は削除し、個体専用の内部Skillは過去リビジョンを含めて完全に削除します。削除を契機にした全体共通（Global）への勝手な昇格は行わず、全体共通の学習データや外部Workspaceのファイルは削除されずに残ります。 |
| **配布・共有（AD-04・11）と所有（AD-08・14・15）** | Character Package、内部学習データ、外部Workspaceのファイル、認証情報、フルバックアップは、それぞれ含まれる内容、アクセス権限、削除範囲が全く異なります。 |
| **個体としての一体感（AD-03）と操作可能性（AD-13）** | アバター表示、音声、実作業を同じCompanionを通じて体験できますが、それらの一部で障害が起きたり長時間処理が動いていたりしても、会話、安全管理操作、復旧操作がブロックされてはなりません。 |
| **高負荷時の縮退（AD-13）と処理継続・停止（AD-01・09・10）** | 描画品質や処理速度を下げることで負荷を調整し、Task記録を勝手に破棄したり、何の説明もなく処理を打ち切ったりすることはしません。費用やリソースの上限に達した場合は、安全に停止してオーナーに判断を求め、保存データへの影響と外部への影響を正直に報告します。 |
| **データ保持・由来（AD-05・07・14）とリソース上限（AD-13）** | 通常の学習データを、容量の都合だけで勝手に消去して解決することはしません。上限到達時の処理停止・判断要求と、オーナーが管理する会話ログの保持期限設定、および明示的なオプトインによる学習データの世代管理は、別々の契約として扱います。 |
| **データ削除（AD-07）と復元（AD-15）** | 削除前の内部データから同じ情報が勝手に再学習されることは禁止されますが、オーナーが説明を理解した上で古いバックアップをリストアした場合は、過去の情報が復活することがあります。外部バックアップまで自動で消去されたと誤認させることはせず、復元後に確認なしで自動処理を再開させることもありません。 |
