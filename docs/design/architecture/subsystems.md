# Subsystem Decomposition（サブシステムの分解と責務境界）

本ドキュメントの対象: [要件定義書（Baseline）](../../requirements/README.md)、[アーキテクチャ設計方針（Architecture Drivers）](architecture-drivers.md)、[システム文脈（System Context）](system-context.md)、[ランタイム構成（Runtime Topology）](runtime-topology.md)。
本書は、Eneシステムを構成するサブシステムの責務境界を決定し、[状態所有権（State Ownership）](state-ownership.md)および[依存規則（Dependency Rules）](dependency-rules.md)の設計根拠を示します。

## 1. Overview（概要）

Eneの内部構造を、**異なる関心事・存続条件・保護レベルを引き受ける12のサブシステム**に分解します。
ここで定義するサブシステムとは、「システムとしてどのような結果に責任を持つか」という責務のまとまりであり、単一のプロセス、単一のデータベース、単一のコードモジュールを指すものではありません。同じサブシステム内であっても、ライフサイクルや意味が異なるデータは厳格に区別して扱われます。

| サブシステム | 本書での略称 | 中心となる責任 |
|---|---|---|
| **個体継続・対話調整** | **個体調整** | 同じパートナーとして一貫した活動を続け、オーナーとの対話、状況判断、タスク委任、指示変更、結果の取りまとめを調整します。 |
| **Character構成・配布** | **Character** | パートナーの会話経験を含まない「静的なキャラクター定義」と、その編集・パーツ差し替え・インポート／エクスポート・配布パッケージ更新を管理します。 |
| **作業遂行・実行管理** | **作業** | タスクの進捗を追跡・制御し、一時的なタスク実行エージェントによる遂行や、スケジュールの各回の自動起動を管理します。 |
| **経験に基づく認識・学習** | **認識・学習** | 日々の対話や作業経験をもとに、知識・スキル・関係性・内面状態を形成・更新し、その判断根拠をいつでも説明できるようにします。 |
| **Client接続・存在調停** | **接続・存在** | 各端末（クライアント）の接続状態を管理し、パートナーが同時に複数端末に重複して現れないよう、排他的な存在場所（プレゼンス）と移動を調停します。 |
| **Owner入出力・体験提示** | **入出力・提示** | 3Dアバター、テキスト、音声による入出力と、公式クライアントとしての管理機能・緊急停止操作を、現在の状況に合わせてオーナーへ提供します。 |
| **共有観測・関連付け** | **共有観測** | 端末単位でデスクトップ画面のキャプチャや変化検知を効率よく共有し、関係するパートナーだけに必要な観測イベントを届けます。 |
| **推論利用** | **推論** | 各サブシステムからの要求に応じてAIプロバイダー（モデル）を呼び出し、モデル間の能力差の吸収、安全なフォールバック、トークン消費量・費用の計算を行います。 |
| **Action実行・拡張受入** | **実行・拡張** | 許可された範囲でファイルやOS、外部ツールに対する実際の操作を実行し、外部コード（MCPやプラグイン）との安全な連携と成否の確認を担います。 |
| **権限・利用制約** | **権限・制約** | オーナーが設定したセキュリティルール、送信同意、利用制限を管理し、AIの出力だけで勝手に危険な操作が実行されないよう厳格にブロックします。 |
| **認証秘密の保護** | **認証秘密** | APIキーやパスワードなどの機密情報を安全に隔離・保管し、認証に必要な通信経路でのみ使用して、AIプロンプトやログへの流出を絶対に防ぎます。 |
| **内部データ保全・消去** | **保全・消去** | データの整合保存、バックアップ、リストア、指定データの完全削除（Targeted deletion）がシステム全域で正しく完了したかを、各サブシステムと連携して検証します。 |

### ランタイム構成と責務分担の前提
ランタイム構成（Runtime Topology）で定めた通り、**Hostがマスターデータの保持とバックグラウンド処理の継続を担当し、ClientはHostから必要な一時データを受け取って表示します**。
端末固有の接続トークンやペアリング鍵は、Hostから同期する会話履歴やAPIキーとは別の枠組みとして扱い、「接続・存在」「認証秘密」「権限・制約」が連携して安全に保護します。

また、本ドキュメントにおいて「アクティブな端末がない状態での活動継続」が認められるのは、稼働中のパートナー（Running）に限られます。
停止中（Stopped）のパートナーはどの端末にもHostにも存在（プレゼンス）を持たず、Host側のデータ保持や復帰用のメモはプレゼンスとはみなしません。パートナー停止時の新規活動禁止とタスク中断は、端末に依存しないすべての処理に例外なく適用されます。

## 2. Decomposition Rationale（サブシステム分解の論理的根拠）

なぜシステムをこの12個に分解したのか、その理由を5つの観点から説明します。

### 1. 「長く続くもの」と「その場限りのこと」を混同しない
パートナーとしてのアイデンティティ（個体調整）、追跡されるタスク（作業）、一時的な実行プロセス（Task Agent）、今いる端末（接続・存在）、画面や音声の提示（入出力・提示）は、それぞれ寿命がまったく異なります。
重いタスクの処理中や3Dアバターの描画がもたついているときでも、パートナーとの会話や緊急停止操作がブロックされないよう、対話の調整役（個体調整）と作業の進行役（作業）を明確に分離しました。

### 2. 「経験の解釈」「初期設定」「元の記録」を同じデータにしない
キャラクター定義の配布パッケージを更新したからといって、これまでの会話経験から育ったパートナーの記憶が上書きされてはなりません。そのため、配布パッケージを扱う「Character」と、経験から学ぶ「認識・学習」を分離しました。
また、実際に話した発言記録（会話履歴）と、そこからAIが解釈した「知識（Memory）」も別物です。学習機能が過去の発言ログを勝手に改ざんしたり、生ログの保管庫を兼ねたりすることはありません。

### 3. 「柔軟な思考」と「機械的に守るべき安全制限」を分ける
AIが文脈に応じて柔軟に状況を判断することは重要ですが、AI自身が「許可された」と思い込んで勝手に危険な操作を行ってはなりません。
状況の理解（個体調整、作業、認識・学習）と、オーナーが決めたセキュリティルールの厳格な適用（権限・制約）を明確な境界線で分けました。
さらに、APIキーやパスワードはAIのプロンプトに絶対に渡してはならないため、「認証秘密」として独立させて物理的に隔離しています。

### 4. 「端末単位の共有処理」と「パートナー個別の判断」を分ける
画面のキャプチャや画面変化の検知は、端末（PC）単位で行う方がリソース効率が良く、コストも抑えられます。
しかし、その画面を見て「どう解釈し、発話するか」は各パートナーの個性や関係性に依存します。
そこで、端末単位で効率よく画面を見守る「共有観測」を独立させ、パートナー個別の対話ロジックと切り離しました。

### 5. 「外部との接点」と「システム全域のデータ管理」を見分ける
外部のAIモデルを呼び出す処理（推論）と、ローカルファイルやツールを操作する処理（実行・拡張）は、失敗したときの挙動やリスクが根本的に異なります。そのため両者を分離しました。
また、データの完全削除（Targeted deletion）やバックアップ・リストアは、一部のデータベースを更新するだけでは完結せず、システム全体で整合性を検証する必要があります。そのため、全体を取りまとめる専門の進行役として「保全・消去」を独立させました。

## 3. Subsystems（12のサブシステムの詳細定義）

### 個体継続・対話調整

**Purpose（目的）**
同じパートナーとして一貫した存在感を保ち、オーナーとの対話、状況判断、タスク委任、指示変更、結果の取りまとめの中心となります。

**Responsibilities（責務）**
- 同じキャラクター定義から生まれた場合でも独立した別個体として管理し、起動・停止・削除などのライフサイクル操作を確実に反映します（停止や削除はAIの応答可否に依存せず確実に実行されます）。
- テキストや音声を一続きの自然な会話として解釈し、最近の文脈やこれまでの記憶を踏まえて応答します。正確な過去の発言を引用する際は、会話履歴の原文を参照します。
- パートナー同士の会話（オーナー不在の交流）も会話履歴として記録します。画面観測の気づきや通知などの活動記録も保持し、パートナーが削除された場合でも、客観的な事実記録としては安全に残します。
- オーナーからの依頼を受け止め、条件を確認し、必要に応じて断り、まとまった作業は「タスク」として委任し、途中の指示変更（Steering）を反映し、完了結果を取りまとめてオーナーへ報告します。
- 画面観測イベントを各パートナーの個性や文脈に合わせて解釈し、自発的な声かけや通知、パートナー同士の会話を自発的に始めるか判断します。オーナーが集中している時間帯（Quiet hours）やミュート設定、リソース上限を最優先し、勝手な連続発話を防ぎます。
- 複数パートナーとのグループ会話を調整し、アクティブな端末が一時的に存在しない場合でもHost側で可能な処理を継続し、次に端末へ戻ったときに未伝達事項をまとめて報告します。

**Non-responsibilities（担当しないこと）**
長時間の重いタスクを対話ループの中で直接実行すること、タスク実行エージェントを長期的な別の人格として育てること、画面描画や音声処理の実装、端末間の排他制御、キャラクター定義のパッケージ化、記憶の物理保存、権限ルールの自己変更は担当しません。

**Why this boundary exists（境界の根拠）**
パートナーとしての存在感や判断は、端末の切断やAIセッションの切れ目を越えて継続します。タスクの実行と対話ロジックを一緒にしてしまうと、重い作業の処理待ちでオーナーとの会話が止まってしまいます。また、対話や自発性の判断をバラバラのサブシステムに分けると、1人のパートナーとしての一貫性が失われてしまいます。

**Runtime relation（実行時の関係）**
Host上でパートナーの存在と判断を継続します。オーナーとのテキスト・音声対話は、「接続・存在」および「入出力・提示」を通じて、現在アクティブな端末へ結び付きます。

**Key collaborations（主な連携）**
- 「Character」から初期設定を受け取り、「認識・学習」へ日々の経験を伝えて知識や判断根拠を参照します。
- 「作業」へタスクの目的や追加指示を渡し、進捗や結果を受け取ります。
- 「共有観測」から画面の変化イベントを受け取り、必要に応じて「接続・存在」へ端末移動を依頼します。
- 「権限・制約」へユーザーの指示内容を提示し、必要な確認を「入出力・提示」へ伝えます。
- パートナー削除時は、「作業」「認識・学習」「保全・消去」と連携して、消去するデータと残す記録の範囲を調整します。

**Traceability（要件・方針との対応）**
AD-01〜05, 08, 09, 12。要件「個体性」「停止と削除」「一続きの会話」「自発的な発話と行動」「グループ会話」「Task」「Remote Client」。

### Character構成・配布

**Purpose（目的）**
配布可能な「静的なキャラクター定義」のライフサイクルを、日々の経験で成長するパートナー個別のライフサイクルから明確に独立させます。

**Responsibilities（責務）**
- 基本的な性格設定、3Dアバター（VRM 1.0）、音声・モーション設定、同梱スキルをひとまとめにした「キャラクター定義（Character Package）」として扱い、編集、パーツの差し替え、インポート／エクスポートを支えます。
- 配布パッケージの更新をバージョンとして識別し、既存のパートナーに対して「どのパーツを更新するか」をオーナーが選べるようにします。
- 配布パッケージの中に、個別の会話経験、記憶、関係性、APIキー、権限設定などのプライベートなデータが絶対に混入しないよう保護します。

**Non-responsibilities（担当しないこと）**
パートナー自身の成長や現在の記憶の管理、3Dアバターの描画、音声合成の計算、スキルの自動改善、外部の配布元ファイルの所有権管理、高度な3D・音声制作ツールの提供は担当しません。

**Why this boundary exists（境界の根拠）**
キャラクターパッケージの更新はオーナーが明示的に行う構成管理であり、日々の会話による自然な学習とは全く異なります。これらを一緒にしてしまうと、パッケージ更新のたびにパートナーの思い出が消えてしまったり、逆にエクスポートしたパッケージに個人的な秘密が漏洩したりする原因になります。

**Runtime relation（実行時の関係）**
キャラクター設定のマスターデータはHostが保持します。クライアントは編集画面の表示やアバター素材の表示に利用します。

**Key collaborations（主な連携）**
- 「個体調整」へ初期設定や更新パーツを渡し、「入出力・提示」へ表示用のアバター素材を提供します。
- 同梱されているスキルを取り込む際は「認識・学習」と連携し、そのパートナー専用の内部スキルとして登録します。
- パッケージのインポートやエクスポート時のファイル操作は「実行・拡張」および「権限・制約」と連携し、内部保存は「保全・消去」と協調します。

**Traceability（要件・方針との対応）**
AD-04, 11, 15。製品定義「Character」「同梱Character」、要件「Character Package」。

### 作業遂行・実行管理

**Purpose（目的）**
タスクの開始から、自律遂行、判断待ち、結果確認、再開に至る一連のプロセスを、パートナーとの通常の雑談や端末の切断から完全に独立して管理します。

**Responsibilities（責務）**
- オーナーからの依頼や自発的な行動計画に基づいてタスクを登録・追跡し、実行、判断待ち、完了、失敗、キャンセル、タスク履歴の管理を行います。依頼主のパートナーが削除された場合でも、タスクの客観的な完了記録は安全に残します。
- 原則として、まとまったタスクは一時的な「タスク実行エージェント（Task Agent）」に委任し、許可された権限・費用・フォルダ（Workspace）の範囲内で作業の分割や並列実行、進捗管理を行います（エージェント自身が長期的な人格を持つことはありません）。
- 作業中の追加指示（Steering）を可能な限り反映し、反映できない場合はその理由と選択肢を返します。キャンセル指示を受け付けたことと、外部ツールの停止が完了したことを明確に区別して報告します。
- Host再起動時に途中だったタスクは勝手に再開せず「オーナーの再開指示待ち」とし、成否不明な操作の自動再実行や、端末移動による勝手なリプレイは行いません。待機処理のためだけにAIモデルをループ呼び出しすることも避けます。
- スケジュール設定（指定時刻や定期実行）の作成・変更・停止・即時実行、タイムゾーンの保持、各回のタスク生成を管理します。停止中にスキップされた回を慌てて自動実行することはありません。
- 作業フォルダ（Workspace）の関連付け、成果物の保存先確認、作業中の一時ファイルの整理を担当します。

**Non-responsibilities（担当しないこと）**
パートナーとしての人格の維持、通常会話の独占、記憶への自動昇格、勝手なPC操作の実行、外部ファイルの所有、セキュリティルールの自己変更は担当しません。エージェントが「成功した」と報告しただけで、外部への操作が本当に成功したと鵜呑みにはしません。

**Why this boundary exists（境界の根拠）**
タスクの記録は、エージェントのプロセス終了やパートナーの削除を越えて長期間残る必要があります。これらを対話ロジックやツール実行の中に埋め込んでしまうと、途中で中断した作業の安全な再開ができなくなります。また、スケジュール実行とタスク管理を密結合させつつも、スケジュール設定、実行エージェント、外部成果物のライフサイクルを厳密に区別するためにこの境界が必要です。

**Runtime relation（実行時の関係）**
タスクやスケジュールはHost上で自律して継続します。端末画面の操作などクライアントに依存する部分のみ、その端末が利用可能なときに行われます。

**Key collaborations（主な連携）**
- 「個体調整」からタスクの委任や追加指示を受け取り、進捗や結果を返します。
- 状況判断には「推論」と「認識・学習」を利用し、外部への操作は「実行・拡張」へ依頼します。
- 「権限・制約」から最新のパーミッションや上限設定を受け取り、画面操作を伴う場合は「接続・存在」と連携します。
- タスク完了時の経験を「認識・学習」へ共有し、タスク記録の保全やリストア時の保留は「保全・消去」と連携します。

**Traceability（要件・方針との対応）**
AD-01〜03, 08, 09, 15。要件「Task、Workspace、成果物」「Schedule」「停止と削除」。

### 経験に基づく認識・学習

**Purpose（目的）**
パートナーが日々の経験から自然に成長することと、その知識や変化の根拠・由来をいつでも人間に分かりやすく説明できることを両立させます。

**Responsibilities（責務）**
- 対話、タスク、ツール利用、画面観測などの経験から、何を記憶として残し、何を更新すべきかを文脈に基づいて判断します（すべての出来事を無差別に丸暗記するわけではありません）。
- 蓄積する情報を、客観的な知識（Memory）、再利用可能な手順（Skill）、相手との関係性の理解（Relationship）、現在の気分や態度に影響する内面状態（Companion State）に明確に分類して管理します。
- 複数の記憶や状態の根拠として「経験の要約（Experience Summary）」を生成し、必要に応じて元の会話ログの大まかな位置を辿れるようにします。
- 現在の知識、過去のバージョン、判断の根拠、誤りの訂正、時間の経過による変化を正しく区別します。知識が古くなったからといって、過去の記録や判断根拠まで勝手に消去することはありません。
- 記憶の共有範囲（パートナー個別か、全体共有か）を適切に判断します。個別パートナーの記憶をデフォルトとし、単に重要度が高いというだけで勝手に全体共有にすることはありません。また、オーナーからの「保存禁止」「非共有」ルールを厳格に遵守します。
- スキル（Skill）については、オープン標準（Agent Skills）との相互運用、原本の保護、過去バージョンへのロールバックを支えます。
- 一時的な内面状態（気分等）と長期的な性格傾向を区別し、時間の経過に応じた自然な変化を表現します。

**Non-responsibilities（担当しないこと）**
会話の生ログの代替保管、百科事典的な一般知識の丸抱え、関係性の一方的な押し付け、キャラクターの初期設定の書き換え、アバターや音声の直接出力、セキュリティルールの変更は担当しません。また、指定データの完全削除（Targeted deletion）はこのサブシステムの単独処理だけでは完了しません。

**Why this boundary exists（境界の根拠）**
共通の経験から「知識」「手順」「関係性」のどれをアップデートすべきかは密接に関連しており、誤った知識の訂正や由来の説明も同じ文脈で行う必要があります。これらを別々のサブシステムに分けると、データの重複や不整合が起きます。一方で、会話の生ログ保管やその場の雑談応答まで一緒にしてしまうと、元の記録と主観的な解釈が混ざり合ってしまいます。

**Runtime relation（実行時の関係）**
記憶や学習データのマスターデータはすべてHostが管理します。クライアントには表示に必要な一時データのみを渡します。

**Key collaborations（主な連携）**
- 「個体調整」や「作業」から日々の経験や訂正指示を受け取り、知識やスキルを返します。
- 「共有観測」に対しては、画面の関連付けに必要な最小限の文脈情報を提供します。
- 思考プロセスには「推論」を利用し、オーナーの保存禁止ルールは「権限・制約」と連携して確実に適用します。
- 「保全・消去」に対しては記憶の根拠関係を提示し、データ完全削除の際に古いインデックスや遅延結果から記憶が勝手に復活することを防ぎます。

**Traceability（要件・方針との対応）**
AD-04〜07, 10, 12, 14, 15。要件「Learningと成長」「一続きの会話」「Privacy/Security目的のtargeted deletionと履歴保持」。

### Client接続・存在調停

**Purpose（目的）**
各端末（クライアント）との通信接続を管理し、パートナーが同時に複数の端末に重複して現れないよう、排他的な存在場所（プレゼンス）と安全な端末移動を調停します。

**Responsibilities（責務）**
- ローカル端末（Host PC）やリモート端末（スマホ・別PC）の接続、切断、再接続、利用可能な機能を管理します。リモート接続時はHost側でのペアリング確認や暗号化通信を「権限・制約」と連携して徹底します。
- 稼働中の各パートナーについて、**同時に1台の端末にのみ存在（アクティブ）する状態**を維持します。呼び出しや自発的な移動、切断時の復帰を安全に調停します。Host再起動後は、稼働中だったパートナーを再起動前の端末へ自動復帰させます（元端末が利用可能になるまではアクティブ端末なしとし、停止中だったパートナーは復帰させません）。
- パートナーが停止（Stopped）された場合はアクティブな端末帰属を直ちに解除し、どの端末にも画面観測の対象にも含めないようにします。
- 会話の区切りや画面操作の安全なタイミングを関係サブシステムと確認し、端末移動をスムーズに行います。排他性が確認できない端末では、操作や発話を行わせません。
- 接続中の端末が切断された場合は、利用可能であればHost PC側のクライアントへ移動し、利用可能な環境がなければ「アクティブ端末なし」としてHost内部で個体を存続させます。

**Non-responsibilities（担当しないこと）**
会話の流れから「今移動すべきか」を判断すること、パートナー自体の生成・停止・削除、タスク全体の移送・再実行、PC操作の許可判定、画面や音声の直接出力は担当しません。ペアリング済みであることは、直ちに操作を許可されたことを意味しません。

**Why this boundary exists（境界の根拠）**
「パートナーが今どの端末にいるか」という排他性は、会話、アバター表示、画面観測、PC操作のすべてに関わる厳格に守るべき制約です。個別のUI機能に分散させてしまうと、端末間で二重存在が発生してしまいます。一方で、単なる接続端末の一覧と、パートナーごとの存在場所を同一視してしまうと、接続しただけで勝手に行動を始めてしまいます。

**Runtime relation（実行時の関係）**
HostとClientの双方にまたがって動作します。Hostが全体の帰属を統括し、Client側も通信切断時には安全に動作を停止します。

**Key collaborations（主な連携）**
- 「個体調整」から移動や停止の要求を受け取り、現在の存在場所を通知します。
- 「入出力・提示」や「実行・拡張」から、会話や操作の安全な区切りを受け取ります。
- 「共有観測」へ、どの端末にどのパートナーが存在しているかの変化を知らせます。
- 「権限・制約」と連携して端末の失効を適用し、「保全・消去」に対しては接続中端末の一時データの把握を支援します。

**Traceability（要件・方針との対応）**
AD-01, 02, 06, 09, 12, 13。要件「Remote Client」「Computer Use」。

### Owner入出力・体験提示

**Purpose（目的）**
同じパートナーを通じて会話やタスクを心地よく利用できる体験を提供するとともに、システム障害時でも確実に操作できる公式クライアントの管理・緊急安全操作を提供します。

**Responsibilities（責務）**
- 3Dアバター（Body）、テキスト、音声（Voice）を通じた入出力を統括し、通常の1対1会話、グループ会話、タスク管理画面を分かりやすく画面に表示します。
- WindowsおよびLinuxにおけるVRM 1.0のオーバーレイ表示、ウィンドウ移動、リサイズ、最小化、活動状態のアニメーションを管理します。
- 音声の入出力、発話検知（VAD）による常時待機、即時ミュート、割り込み発話（Barge-in）、双方向音声からプッシュ・トゥ・トークやテキストへの柔軟な切り替えを支えます（話者認証は行わないことを明示します）。
- 初期セットアップ、機能の段階的な有効化、セキュリティ許可、費用管理、プライバシー、バックアップ・復元へ迷わずアクセスできる管理画面を提供します。
- UIの表示言語、アバターや音声の一般設定、Hostの自動起動設定を管理します。
- キーボードによる緊急停止（ミュート、停止、キャンセル、確認ダイアログの拒否）、音声内容の字幕表示、多言語での分かりやすい説明を提供します。
- 全画面アプリの起動やPC高負荷、デバイス障害を検知し、アバターや音声が失敗してもテキストチャットや緊急停止画面は確実に利用できるように保護します。外部ツールUI（MCP Apps）も安全な隔離枠内で表示します。

**Non-responsibilities（担当しないこと）**
タスクの成否判定、記憶の形成、パーミッションの妥当性判断、バックアップ復元の成否判定を独断で行うことはありません。画面を閉じたことをタスクキャンセルと誤認したり、UIの入力を検証なしにシステム設定へ直接書き込んだりしません。また、アバターの描画やAIの応答が遅れても、管理操作がブロックされることはありません。AIの思考ログを生で表示したり、好感度メーターのような短絡的なUIを表示したりすることもありません。

**Why this boundary exists（境界の根拠）**
ユーザーへの表示や入力受付は、システム内部のデータを人間向けに表現する責任であり、データそのもののマスターデータではありません。ビジネスロジックと画面描画を結合させてしまうと、描画が重くなっただけでシステム全体が不安定になります。また、アバター、音声、テキスト、管理画面を別々のサブシステムに分解しすぎると、入力の切り替えや緊急停止の連携が複雑になります。

**Runtime relation（実行時の関係）**
オーナー向けの直接の窓口および物理的な入出力はClientが担当します。Hostは表示に必要な状態や説明文を提供します。

**Key collaborations（主な連携）**
- 「個体調整」へユーザーの会話入力を渡し、「作業」へタスクの操作指示を、「権限・制約」へユーザーの承認・拒否を伝えます。
- 「接続・存在」と対話の区切りを調整し、「共有観測」の稼働状態を画面に表示します。
- 「推論」と連携して音声モデルを呼び出し、「実行・拡張」と連携してアバター描画や外部ツールUI（MCP Apps）を安全に表示します。
- 「保全・消去」と連携して、端末上の一時データの消去や保護を行います。

**Traceability（要件・方針との対応）**
AD-02, 03, 11〜15。要件「Setupと日常利用」「会話と情報提示」「BodyとVoice」「拡張」「品質と利用可能性」。

### 共有観測・関連付け

**Purpose（目的）**
端末（クライアント）単位でデスクトップ画面の観測コストと処理を効率よく共有し、各パートナーの判断に必要なイベントだけに絞り込んで届けます。

**Responsibilities（責務）**
- 画面観測がONになっており、パートナーが1体以上存在している端末のデスクトップ画面全体をキャプチャします（パートナーの出入りに合わせて対象端末を見直します）。
- 指定されたキャプチャ頻度を満たしつつ、複数端末を同時にキャプチャせず順番にタイミングをずらすことで、PCへの負荷を分散します。全画面アプリの起動、一時停止（Pause）やOFF設定、費用やリソースの制限を、定期キャプチャよりも最優先します。
- 端末に紐づけられた「画面観測専用のAIモデル／プロバイダー割り当て」を使って画面の変化や作業内容を検知し、その端末にいる関係するパートナーだけにイベントを届けます（すべてのパートナーに無差別にばら撒くような無駄は避けます）。
- 画面観測の稼働状態や観測範囲を画面で分かりやすく説明できるようにし、カメラや画面の生映像（Raw Observation）は通常保存しません。共有処理においても、パートナーごとの情報境界、送信同意、機密保護を厳格に守ります。

**Non-responsibilities（担当しないこと）**
各パートナーの最終的な発話判断やアクション判断、パートナー個別の自発性設定、形成された記憶の削除、PC操作（Computer Use）の実行や承認は担当しません。画面に映った文字を「オーナーからの直接の指示」と勝手に誤認することもありません。

**Why this boundary exists（境界の根拠）**
画面キャプチャの制御単位は「端末（PC）」であり、各パートナーの自発性とは管理単位が異なります。パートナーごとの対話ロジックに組み込んでしまうと、複数パートナーがいる場合に画面キャプチャが重複してPCが重くなってしまいます。また、PC操作機能と一緒にしてしまうと、「画面を見る許可」が「PCを勝手に操作する許可」へと勝手に拡大解釈される危険があります。

**Runtime relation（実行時の関係）**
画像の取得元はClientですが、観測の制御やパートナーへのイベント配送はHostが管理します。画像認識処理の計算をどこで行うかは柔軟に選択できます。

**Key collaborations（主な連携）**
- 「接続・存在」から対象端末とそこにいるパートナーの情報を受け取り、「入出力・提示」から全画面アプリの起動状態を受け取ります。
- 「個体調整」や「認識・学習」から、イベントの関連付けに必要な最小限の文脈情報を受け取り、関心を持ちそうなパートナーへイベントを通知します。
- 画像認識には「推論」を利用し、「権限・制約」が定めた送信同意やプライバシー制限を適用します。
- 「保全・消去」と連携し、キャプチャ画像や処理中の一時データを適切に破棄・管理します。

**Traceability（要件・方針との対応）**
AD-02, 06, 07, 10, 12〜14。要件「Observation」「自発的な発話と行動」「Desktop Body」。

### 推論利用

**Purpose（目的）**
AIモデルを呼び出す各サブシステムを、特定のAIプロバイダー（OpenAI、Anthropic、ローカルモデル等）の接続仕様、APIプロトコル、セッション管理、費用計算の差異から解放し、承認された安全な範囲でスムーズに利用できるようにします。

**Responsibilities（責務）**
- 機能ごとのHost既定モデル、パートナーごとの個別設定、タスクエージェントへのモデル継承を正しく解決し、必要な能力が不足している場合は呼び出し前にエラーを通知します。
- 画面観測（Observer）専用のモデル割り当ても解決し、パートナー個別の設定とは混同せずに独立して管理します。利用量をプロバイダー別・全体の費用上限枠に正しく結び付けます。
- 各AIプロバイダーのAPIに直接接続し、障害時にはあらかじめオーナーが承認したフォールバック先へ安全に切り替えます（ローカルモデルだからといって送信同意を勝手に省略することはありません）。
- 各サブシステムが要求する論理的なコンテキスト（プロンプト情報）と、AIモデルの最大コンテキスト長を適切に調整します。プロバイダーの違いによって送る情報の選択方針が不自然にブレないようにします。
- 推論結果、トークン消費量、API費用の実績値（または見積もり値）を正確に計算し、「権限・制約」サブシステムへ報告して費用上限の判定に役立てます。
- プロンプトキャッシュを活用してパフォーマンスの向上と費用の削減を図ります（キャッシュの有無によって送信データやセキュリティ境界が変わることはありません）。

**Non-responsibilities（担当しないこと）**
「何を記憶すべきか」「どんなアクションを実行すべきか」という業務レベルの最終判断は行いません。また、セキュリティルールの変更、APIキーの平文保管、プロバイダー側のセッション情報へのデータ依存、回線復旧時の勝手な操作再実行は担当しません。

**Why this boundary exists（境界の根拠）**
AIモデルの呼び出し処理を一箇所にまとめる理由は、単に通信プロトコルを共通化するためだけではなく、モデル割り当ての解決、能力差の吸収、安全なフォールバック、費用集計といった共通の利用ルールを一貫して適用するためです。各機能が勝手に外部APIを叩く構造にすると、利用上限の突破や安全ルールのすり抜けが発生します。

**Runtime relation（実行時の関係）**
Hostが管理する設定やセキュリティルールの下で、外部またはローカルのAIプロバイダーと通信します。必要に応じてClientから直接通信する経路もサポートします。

**Key collaborations（主な連携）**
- 「個体調整」「作業」「認識・学習」「共有観測」「入出力・提示」からプロンプト情報を受け取り、AIの推論結果を返します。
- 「権限・制約」から送信同意や費用上限の適用を受け、「認証秘密」から安全に認証情報を受け取ってAPI通信を行います。
- 「保全・消去」と連携し、内部キャッシュや処理中コンテキストの完全消去に対応します。

**Traceability（要件・方針との対応）**
AD-01, 05, 06, 10, 11, 13, 14。要件「所有と実行」「Provider、費用、接続障害」「拡張」。

### Action実行・拡張受入

**Purpose（目的）**
指示された操作を、ローカルファイルやOS、外部ツールに対する制限された安全なアクションとして実行し、外部コード（MCPやプラグイン）との連携や、操作の不確実性をシステム側で責任を持って管理します。

**Responsibilities（責務）**
- ファイルシステム、ネットワーク、シェル、OSデバイスに対する操作を、許可されたセキュリティ境界（フォルダ範囲、操作種別など）を厳格に守って実行します。ディレクトリトラバーサルや不正なシンボリックリンクによる境界外アクセスは確実に拒否します。
- 実際に実行された操作、未完了の操作、成否が確認できなかった操作（成功不明）、中断できなかった処理を、呼び出し元へ正確に報告します。操作の中断要求を受け付けたことと、外部での停止が完了したことを明確に区別し、成否不明な操作を別ツールで勝手に再実行することはしません。
- PC操作（Computer Use）は、タスクを依頼したパートナーが現在アクティブになっている端末に限定し、端末ごとのデバイス許可と通常のパーミッションを厳格に適用します。端末が移動する際の安全な区切りや、切断時の安全な中断を「接続・存在」へ通知します。
- 外部ツール連携規格（MCP: Model Context Protocol）のツール、リソース、プロンプトの接続と実行結果の受け入れを管理します。Host上のローカルMCPはデフォルトのサンドボックス内で実行し、明示的な例外許可がない限り勝手に解除しません。
- プラグインを制限された拡張ポイントで安全に受け入れ、外部コードの実行範囲や障害を隔離します（外部コードがシステムの管理権限を乗っ取ることを防ぎます）。
- ツールが提供する一時UI（MCP Apps）の表示と操作を「入出力・提示」と連携して制御し、ツールUIを閉じたこととバックグラウンドタスクの終了を明確に区別します。

**Non-responsibilities（担当しないこと）**
オーナーの許可を勝手に拡大解釈すること、タスク全体の計画立案、端末移動先の決定、AIモデルの割り当て、記憶の管理、外部成果物の所有、外部操作の確実なロールバックは担当しません。

**Why this boundary exists（境界の根拠）**
「アクションを実行したい」というAIの判断と、「実際にファイルやOSに何が作用したか」を正確に把握する責任は根本的に異なります。ツール実行の境界をタスク管理の中に埋め込んでしまうと、ちょっとした対話中の操作や外部ツールUIからセキュリティの抜け穴が生じます。外部コードを制限された環境で安全に動かす責任をここに集約しています。

**Runtime relation（実行時の関係）**
Host上での作業とClient上でのPC操作の双方に関係し、OS、ファイル、MCPサーバー、プラグインと直接接します。

**Key collaborations（主な連携）**
- 「作業」や「個体調整」からアクションの実行要求を受け取り、実行結果と成否の確定度を返します。
- 「権限・制約」と連携してセキュリティルールをチェックし、「認証秘密」から必要な認証情報を安全に受け取ります。
- 画面操作を伴う場合は「接続・存在」と連携して対象端末を特定します。
- 「保全・消去」に対しては、一時データや実行結果ログの消去に参加します。

**Traceability（要件・方針との対応）**
AD-01, 02, 06〜09, 11, 14。要件「Computer Use」「Capability境界」「信頼境界」「Credential」「拡張」。

### 権限・利用制約

**Purpose（目的）**
AIの柔軟な文脈理解を活かしながらも、オーナーが定めたセキュリティルール、送信同意、費用制限を、いかなる実行経路でも絶対にすり抜けられない確固たる境界線として強制します。

**Responsibilities（責務）**
- システムの機能境界（Capability境界）、操作パーミッション、恒久的な拒否（Deny）、毎回確認（Always ask）、自然言語によるルール、端末ごとのデバイス許可、AIプロバイダーへの送信同意、費用上限を管理します。これらを一つの曖昧な「全許可」にまとめることはありません。
- オーナーからの「今だけやっていい」という単発の承認と、「今後ずっとこうしてほしい」という恒久ルールの設定を明確に区別します。ルールの適用範囲の表示、ルールの取り消し（Undo）、矛盾や曖昧さがある場合のオーナー確認を支えます。
- AIが生成したテキストや外部から読み込んだファイルの内容によって、セキュリティルールが勝手に緩和されることを絶対に防ぎます。
- オーナーが指示した「保存禁止」「他パートナーとの非共有」といったプライバシー制約を、記憶の形成、検索、外部送信、ツール実行などのあらゆるパイプラインで確実にブロックします。
- パーミッションの失効、パートナーの停止、端末の登録解除、費用上限への到達が発生した場合は、新規のアクションを即座にブロックし、実行中の処理に対して安全な中断要求を発行します。
- APIの利用費用が不明で安全に続行できない場合でも、データを破壊することなく処理を安全に停止し、オーナーに選択肢を提示します。
- ローカルMCPに対するサンドボックス外アクセスの例外許可を厳格に管理し、他のツールやプラグインへ勝手に例外を拡大させないようにします。

**Non-responsibilities（担当しないこと）**
ルールをきっかけにして自発的に行動を起こすこと、記憶や関係性の内容決定、AIモデルの選定や費用見積もりの計算、APIキーの値の保管、OSレベルのプロセス隔離の実装、外部操作の成否判定は担当しません。

**Why this boundary exists（境界の根拠）**
セキュリティ制限が機能ごとにバラバラに実装されていると、別のツール経路や委任エージェントを経由したルールの抜け道が生まれます。また、対話ロジックと権限判定を一体化させてしまうと、「パートナーと仲良くなったから危険な操作も許可された」というような重大なセキュリティインシデントに繋がります。「状況を解釈する責任」と「決定されたルールを厳格に強制する責任」を明確に分けるために、このサブシステムが存在します。

**Runtime relation（実行時の関係）**
Host上で一元管理されるセキュリティ制約を、HostおよびClientのすべての実行箇所に対して確実に適用します。外部のプロバイダーやツールにセキュリティ判定の主導権を渡すことはありません。

**Key collaborations（主な連携）**
- 「個体調整」や「作業」からユーザーの指示や文脈を受け取り、「入出力・提示」を通じてオーナーからの承認・設定操作を受け取ります。
- 「推論」「実行・拡張」「共有観測」「接続・存在」「認識・学習」に対してセキュリティルールや上限枠を適用し、最新の利用状況を把握します。
- 「認証秘密」に対して認証情報の利用制限を伝え、「保全・消去」に対してはデータ消去やリストア中の実行停止を指示します。

**Traceability（要件・方針との対応）**
AD-04, 06, 07, 09〜15。要件「Permissionと安全境界」「Scope」「割当と同意」「自発的な発話と行動」「拡張」。

### 認証秘密の保護

**Purpose（目的）**
AIプロバイダーや外部ツールの利用に必要な認証情報（APIキー、パスワード、トークン等）を安全に利用できることと、その機密値がAIプロンプトや一般のデータ経路へ絶対に漏洩しないことを両立させます。

**Responsibilities（責務）**
- オーナーによる手動入力や認証フロー（OAuth等）を通じてAPIキーやパスワードを登録・更新・失効させ、一般のアプリケーションデータから物理的に厳格隔離して保護します。
- 外部APIとの通信など、認証にどうしても必要な最小限の通信経路でのみ秘密情報を使用し、AIのプロンプト、ツールの引数や戻り値、画面UI、記憶データ、ログ、デバッグ情報の中に平文の機密値が混入することを絶対に防ぎます。
- 認証失敗や有効期限切れの通知を行う際も、機密値そのものは含めずに安全に伝えます。
- **フルバックアップからの除外**: APIキーやパスワードはバックアップファイルには保存しません。リストア時もHost側の現在のキー情報を維持し、不足があればオーナーに再入力を案内します。全データリセット時には完全に抹消します。

**Non-responsibilities（担当しないこと）**
認証が通ったことを理由に危険な操作を無条件で承認すること、セキュリティルールの変更、一般データ全体の暗号化、外部アカウントそのものの所有権管理は担当しません。

**Why this boundary exists（境界の根拠）**
APIキーやパスワードなどの機密情報は、一般的な設定データとは全く異なる保護・更新・バックアップ除外のルールを必要とします。これらをプロバイダー設定や権限説明の中に混ぜてしまうと、AIの思考プロンプトやログの中に秘密情報が紛れ込むリスクが極めて高くなります。

**Runtime relation（実行時の関係）**
Host側で機密情報を厳重に隔離・保管し、外部の認証サーバーとの通信時のみ安全に利用します。

**Key collaborations（主な連携）**
- 「入出力・提示」を通じてオーナーからの安全な入力を受け取り、「推論」や「実行・拡張」の通信処理へ認証情報を提供します。
- 「権限・制約」が定めた利用ルールに従い、「保全・消去」と連携してバックアップからの機密情報除外や全データリセット時の完全抹消を徹底します。

**Traceability（要件・方針との対応）**
AD-06, 10, 11, 14, 15。要件「Credential」「信頼境界」「Local data」「Backupとrestore」「Reset」。

### 内部データ保全・消去

**Purpose（目的）**
システム全体のデータ整合性の保護、保持期間の管理、指定データの完全削除（Targeted deletion）、バックアップ、リストアについて、一部の処理成功を「全体の成功」と早合点せず、オーナーに対して安全で確実な完了を保証します。
本サブシステムは**システム横断の進行役（Coordinator）**であり、すべてのデータを単独で独占する神のような巨大データベースではありません。日常的なデータの意味判断は各サブシステムが担当し、本サブシステムは全体に関わる重要なライフサイクル操作を統括します。

**Responsibilities（責務）**
- 各サブシステムが扱うデータの正常保存やデータ移行（マイグレーション）、バージョンアップを支援し、移行に失敗した場合でも直前の正常な状態を絶対に破壊しないように保護します。
- 会話履歴やタスクログ、監査ログの保持期間ルールを管理し、古いログが削除された場合でも、そこから形成された記憶や要約まで連鎖して勝手に消えないように保護します。
- 記憶の過去バージョンや要約の自動クリーンアップ（容量削減）は**デフォルトOFF**とし、オーナーが明示的に設定した場合にのみ各担当と連携して安全に適用します。
- オーナーから指定されたプライバシー／セキュリティ目的の**完全削除（Targeted deletion）**を統括します。オーナーに保存場所を探させることなく、会話履歴、ログ、記憶、要約、インデックス、キャッシュ、処理中キューなど、システム全域から指定情報を徹底的に抹消・復元不能化し、残存がないかを検証します。
- 削除処理の途中で遅れて届いたAI推論結果などから、消去対象の情報が再び保存されることを確実にブロックします。
- 機密情報（APIキー等）や外部作業フォルダを除外し、整合性の取れたポータブルなフルバックアップファイルを作成します。
- バックアップからのリストア時、Host側の現在のAPIキー情報を保護しつつ、安全に内部データを過去時点へ全置換します。リストア直後は自動タスクや定期実行をいったん保留し、オーナーが確認して一括で安全に再開できるようにします。
- 一般設定のみを初期値に戻す「設定リセット」と、強い確認を経て内部データとAPIキーを完全消去する「全データリセット」を明確に区別して管理します。
- システム内で何が起きたかを客観的に確認できる監査ログ（Audit）の記録順序を保ち、トラブル調査用のデバッグ情報の短期間での自動失効を管理します（テレメトリやクラッシュレポートを勝手に外部送信することはありません）。

**Non-responsibilities（担当しないこと）**
すべてのデータの意味の決定者、唯一の書き込み役、単一のデータベースになるわけではありません（会話記録の意味は「個体調整」、タスク記録は「作業」、記憶の意味は「認識・学習」、秘密情報は「認証秘密」が責任を持ちます）。また、外部に送信済みのメールやAPIデータ、外部作業フォルダのファイルを勝手に消去できません。

**Why this boundary exists（境界の根拠）**
データの完全削除やバックアップ、リストアは、1つのサブシステムの中だけで完結するものではなく、システム全体を横断して整合性を確認する責任が必要です。各機能にバラバラに任せてしまうと、キャッシュやインデックスの消し忘れ、遅れて届いたAI結果によるデータのゾンビ復活といった事故が起きます。一方で、すべてのデータアクセスをここに集中させてしまうと、巨大で扱いにくいモノリシックなストレージ層になってしまいます。そのため、「全体進行役」として独立させました。

**Runtime relation（実行時の関係）**
Host側が中心となって全体の保存や一括操作を統括し、Client上の一時データの消去や保護も確実に連携して行います。

**Key collaborations（主な連携）**
- すべてのサブシステムからデータ範囲、過去バージョン、キャッシュ、処理中データの情報を集約し、保存・消去・復旧を調整します。
- 「権限・制約」「作業」「個体調整」「接続・存在」と連携して、リストア後の安全な保留と再開を実現します。
- 「認証秘密」と連携してバックアップからの機密情報除外を徹底し、「入出力・提示」を通じてオーナーに正確な進捗と検証結果を報告します。

**Traceability（要件・方針との対応）**
AD-01, 04, 05, 07〜09, 14, 15。要件「履歴、保持、Privacy」「保護、Backup、復旧」「停止と削除」「Remote Client」。


## 4. Subsystem Relationship Overview（サブシステム間の連携概要）

以下に示すのは、各サブシステム間の**「依頼」「通知」「参照」という論理的な連携関係（コラボレーション）**です。
矢印の向きは説明の起点を示しているだけであり、特定のIPC通信方式や関数の呼び出し順序、モジュールの依存方向を固定するものではありません。

| 連携関係 | 依頼・通知・参照と責任の受け渡し |
|---|---|
| **入出力・提示 → 個体調整 → 作業** | オーナーとの会話を解釈し、まとまった仕事をタスクとして「作業」へ委任します。<br>「作業」が進捗管理を引き受け、「個体調整」は通常の雑談や指示変更、完了結果の取りまとめを続けます。<br>※画面からのタスクキャンセルや履歴確認は、AIの返信可否に関わらず確実に実行されます。 |
| **Character → 個体調整 ↔ 認識・学習** | 配布パッケージの初期設定をパートナーの出発点として適用しつつ、会話経験から育った記憶を優先します。<br>パッケージの更新時はオーナーが適用パーツを選び、経験データが配布物に混入・逆流することを防ぎます。 |
| **個体調整・作業 ↔ 認識・学習** | 日々の対話やタスクの結果を「経験」として渡し、必要な知識やスキル、判断根拠を参照します。<br>過去の発言ログ（会話履歴）と、そこから抽出した要約・知識（Memory）を明確に区別します。 |
| **接続・存在 ↔ 入出力・提示／共有観測／実行・拡張** | どの端末にパートナーが存在しているか、会話の区切り、PC操作の区切りを安全に対応付けます。<br>端末を移動しても、Host側のタスクは中断せず、古い操作を移動先で勝手に再実行することもありません。 |
| **共有観測 → 個体調整 → 認識・学習／作業** | 画面のキャプチャと変化検知を経て、各パートナーが自身の文脈に合わせてイベントを理解します。<br>それを記憶に残すか、声をかけるか、タスクを始めるかは各パートナーの判断であり、画面観測の許可が勝手なPC操作の許可になることはありません。 |
| **各判断サブシステム ↔ 推論** | プロンプト情報と必要なコンテキストを渡し、AIの推論結果や利用量を受け取ります。<br>その結果が何を意味するかは呼び出し元が判断し、プロバイダー側のキャッシュをマスターデータにはしません。 |
| **個体調整・作業等 ↔ 実行・拡張** | 目的と対象を指定してファイル操作やツール実行を依頼し、成否や不明な状況を受け取ります。<br>スキルファイルを読み込んだからといって、システムの管理権限が奪われることはありません。 |
| **入出力・提示／各判断 ↔ 権限・制約 ↔ 各利用箇所** | オーナーからの依頼や管理操作をセキュリティルールに結び付けます。<br>各サブシステムは最新のルールや上限枠を適用し、AIの出力だけで勝手にルールが変更されることを防ぎます。 |
| **推論・実行・拡張・接続・存在 ↔ 認証秘密** | 認証先と通信用途を限定して、APIキーなどの秘密情報を受け渡します。<br>通常のプロンプトやログ、ツール結果には絶対に秘密値を流しません。 |
| **入出力・提示 ↔ 実行・拡張 ↔ 外部MCP Apps** | 外部ツールが提供するUI（MCP Apps）の表示と操作を、安全な制限下で管理します。<br>ツールUIを閉じたことと、裏で動いているタスクの終了は別物です。 |
| **保全・消去 ↔ 全参加サブシステム** | データの整合保存、バックアップ、リストア、完全削除（Targeted deletion）を全域で統括します。<br>一部のテーブルから行を消しただけでは完了とみなさず、全サブシステムでの確実な消去を検証します。 |

### 境界を横断する代表的な協調シナリオ

1. **作業中の端末移動・切断**:
   - パートナーが別の端末へ移動する場合、「個体調整」が移動を要求し、「接続・存在」が「入出力・提示」や「実行・拡張」と連携して、会話やPC操作の安全な区切りを待ちます。
   - Host側で動いているバックグラウンドタスクは中断されずにそのまま継続します。
   - 新しい端末へ移動したからといって、過去の操作を勝手に再実行することはありません。接続端末がゼロになった場合、オーナーへの通知はいったん保留され、承認待ちのアクションは実行されずに待機します。

2. **パートナーの停止と完全削除**:
   - パートナーの停止時、「個体調整」が活動を停止し、「入出力・提示」はアバターを非表示にし、自発的な行動や新しいタスクの開始をストップします。「作業」は実行中タスクを安全にキャンセルします。
   - パートナーの完全削除時は、オーナーによる厳格な確認（強い確認）を経て、「保全・消去」が主導して個別設定、記憶、関係性、スケジュールを完全に消去します。
   - 一方で、会話ログそのものやタスク完了記録、全体共有の知識（Global Learning）、外部の作業ファイルは削除されずに安全に残ります。

3. **指定データ完全削除（Targeted deletion）の徹底**:
   - オーナーから指定された文字列や機密情報を消去する際、「保全・消去」が全サブシステムを指揮します。
   - データベース内の記憶だけでなく、処理待ちキュー、遅延して届いたAIの推論結果、検索インデックス、キャッシュからも徹底的に抹消し、古いデータから記憶が自動復活しないよう検証します。

4. **リストア（Restore）と安全な再開**:
   - バックアップから復元する際、「保全・消去」がHost側の現在のAPIキー情報を保護した上で、内部データを過去時点へ全置換します。
   - リストア完了直後は、タスクやスケジュールの自動実行はいったん「保留」されます。
   - オーナーが画面で復元内容を確認し、一括で安全に再開指示を出すことができます。

## 5. Boundary Decisions（境界設計の判断理由と残す区別）

| 設計判断 | 分離・統合の理由と、維持すべき区別 |
|---|---|
| **パートナーの対話調整とタスク遂行の分離** | オーナーからの依頼を受け止め、対話や結果報告を行う責任（個体調整）と、重い作業を自律的に進める責任（作業）は寿命が異なります。タスクの実行待ちで会話がブロックされるのを防ぎます。 |
| **タスク・実行エージェント・スケジュールを作業内に統合** | これらはすべて「目的と制限を持った作業を遂行する」という共通の関心事に属します。ただし、タスク記録、一時的なエージェントプロセス、スケジュール設定、外部成果物のライフサイクルは別物として厳密に区別します。 |
| **スケジュールをすべての時間待ち機能へ一般化しない** | スケジュールは「指定時刻にタスクを開始する」ための機能です。画面観測の定期キャプチャやバックアップの定期実行は、それぞれの専門サブシステムが直接管理します。 |
| **Character（静的定義）と日々の成長を分離** | 配布パッケージの更新によって、これまで育った思い出や記憶が上書きされるのを防ぎます。また、エクスポートしたパッケージに個人的な秘密が混入するのを防ぎます。 |
| **知識・スキル・関係性・内面状態を認識・学習に統合** | 共通の経験から何をどう学ぶかを一貫して判断するためです。ただし、客観的事実（Memory）、手順（Skill）、関係性（Relationship）、気分（State）のデータ構造や役割は独立して保ちます。 |
| **会話の生ログを独立したストレージサブシステムにしない** | 発言の記録は対話の文脈（個体調整）と密接に関連しています。生ログの保管と、そこから抽出された要約・知識を明確に区別します。 |
| **端末調停と画面提示を分離し、Host/Client別に複製しない** | 「パートナーがどこに存在するか（排他性）」はシステム全体の重要な制約です。画面や音声のUI描画ロジックと分離しつつ、Hostが統括して二重存在を防ぎます。 |
| **アバター・音声・テキストを入出力・提示へ統合** | 同じパートナーを通じた一貫した利用体験を提供するためです。ただし、アバターや音声がクラッシュしても、テキストチャットや緊急停止画面は確実に利用できるように保護します。 |
| **画面観測と自発的行動・PC操作を分離** | 画面キャプチャは端末単位で効率よく共有し、そこからどう行動するかはパートナー個別に判断します。画面を見る許可が、勝手なPC操作の許可へエスカレーションするのを防ぎます。 |
| **推論利用とアクション実行を分離** | AIモデルの呼び出し（推論）と、ローカルファイルやOSへの操作（実行）は、失敗時のリスクや安全対策が根本的に異なるため分離します。 |
| **思考・判断、権限制約、認証秘密の分離** | AIがどれだけ賢く状況を判断しても、セキュリティルールを勝手に書き換えることはできません。また、APIキーなどの秘密情報はプロンプトやログから物理的に隔離します。 |
| **保全・消去を独立した進行役とする** | データの完全削除やバックアップ復元はシステム全体を横断するため、専門の進行役が必要です。ただし、すべてのデータを抱え込む巨大なモノリスストレージにするわけではありません。 |

## 6. Cross-cutting Responsibilities（横断的責務の分担）

システム全体に関わる重要な関心事について、どのサブシステムがどのように責任を分担するかを整理します。

| 横断的責務 | 責任の配置と分担 |
|---|---|
| **パーミッション・同意・利用制限** | 「権限・制約」が一元管理し、推論、ファイル操作、画面観測、データ保存の各パイプラインで機械的にブロックします。 |
| **APIキーなどの機密情報の保護** | 「認証秘密」が物理隔離して保管し、AIプロンプト、ログ、ツール引数、UI、バックアップへの平文流出を完全に防ぎます。 |
| **指定データの完全削除（Targeted deletion）** | 「保全・消去」が全体を取りまとめ、全サブシステムが責任を持ってキャッシュやキュー、インデックスから情報を抹消・検証します。 |
| **データ保存・バックアップ・リストア** | 「保全・消去」が進行役を務め、APIキーの除外、リストア直後の自動処理の保留、安全な再開を各担当と実現します。 |
| **監査ログ（Audit）・エラー説明** | 各サブシステムが客観的な事実（操作履歴、エラー内容）を供給し、「保全・消去」が改ざん不能な順序で記録し、「入出力・提示」が人間向けに分かりやすく説明します。 |
| **費用・リソース上限による制限** | 「権限・制約」が上限枠を判定し、「推論」が利用量を計算し、各機能が安全に縮退・停止します。 |
| **時間管理・待機処理** | 各サブシステムが必要なタイムゾーンや時刻を管理し、待機処理のためだけにAIモデルを無駄にループ実行することを防ぎます。 |
| **全画面アプリ・パートナー停止・端末切断** | 全画面アプリ時は「入出力・提示」がアバターを隠し、「共有観測」がキャプチャを休止します。パートナー停止時はシステム全域で活動を止めます。 |
| **コンテキスト管理とデータ最小化** | 各担当が必要な情報のみを絞り込んでプロンプトに渡し、無駄なデータ送信やプライバシー侵害を防ぎます。 |
| **生データの非保存原則** | カメラや画面の生映像、マイクの生音声、AIの思考ログは長期間保存せず、目的が終わり次第破棄します。 |
| **障害・キャンセル・成否不明の扱い** | 操作の中断要求と実際の停止を区別し、結果が確認できないものは「成否不明」として正直に記録・報告します。 |
| **外部コード（MCP・プラグイン）の信頼境界** | 「実行・拡張」が外部コードをサンドボックス内で安全に実行し、システムの管理権限を奪われないように保護します。 |
| **言語設定・アクセシビリティ・初期設定** | 「入出力・提示」が多言語表示やキーボード操作、分かりやすい初期設定画面を提供します。 |

## 7. 状態所有と依存規則への接続

本ドキュメントでは「各サブシステムが何に責任を持つか」という責務の境界を定義しました。
- 各データがどのサブシステムに属し、どのように更新・削除されるかについては、[状態所有権（State Ownership）](state-ownership.md)で詳しく定義しています。
- サブシステム間の許可される呼び出し方向や禁止された結合については、[依存規則（Dependency Rules）](dependency-rules.md)で詳しく定義しています。

## 8. Design Freedom（後続設計に委ねる自由度）

本ドキュメントが定めた責務境界とセキュリティ原則を遵守する限り、以下の実装方式は後続の詳細設計や実装フェーズで柔軟に決定して構いません。

- **モジュール・コード構成**: クレート（crate）やモジュールの分割、Rustの構造体・トレイト設計、内部API設計、IPC通信プロトコル。
- **プロセスとスレッド**: プロセス分割数、非同期タスク（Tokio）の構成、イベントバスの実装方式。
- **データベースと永続化**: SQLiteのテーブル設計、リポジトリ層の実装、トランザクションの粒度、ロック制御方式。
- **アルゴリズムと内部表現**: プロンプトの組み立て方式、記憶の検索スコアリング計算、画面変化の検知アルゴリズム。
- **セキュリティ機構**: OSサンドボックスの具体技術、プラグインのプロセス分離方式、暗号化ライブラリの選定。
- **バックアップの形式**: アーカイブ形式（zip, tar.zst等）、暗号化アルゴリズム。

※ただし、「実装の自由」を口実にして、本ドキュメントで定めた原則（Hostがマスター、APIキーを漏らさない、停止と削除の分離など）を勝手に変更・緩和することは絶対に認められません。

## 9. Traceability and Completeness（要件追跡性と網羅性）

### ランタイム構成とのマッピング（Runtime Mapping）

| サブシステム | Host側の役割 | Client側の役割 | 外部との接点 |
|---|---|---|---|
| **個体調整** | パートナーの存在、対話判断、タスク委任、未伝達事項の保持 | アクティブ端末での対話への接続 | AIプロバイダー（推論経由） |
| **Character** | キャラクター定義の管理、適用パーツの解決 | 編集画面、アバター素材の表示 | キャラクター定義ファイル（VRM等） |
| **作業** | タスク進捗、エージェント実行、スケジュールの自律継続 | 進捗確認、操作指示の受付 | 外部作業フォルダ、ローカルMCP |
| **認識・学習** | 記憶、スキル、関係性のマスターデータ管理 | 表示に必要な一時データの利用 | AIプロバイダー、外部スキルファイル |
| **接続・存在** | 端末接続の管理、パートナーの排他的存在調停 | 端末の接続・切断、二重存在の防止 | ローカルLAN、ペアリング端末 |
| **入出力・提示** | 画面表示用の状態や説明文の提供 | 3Dアバター描画、音声対話、管理画面 | OSウィンドウ、マイク・スピーカー |
| **共有観測** | 観測の統括、パートナーへのイベント配送 | デスクトップ画面のキャプチャ | 画面映像、画像認識モデル |
| **推論** | モデル割り当ての解決、API直接通信、費用計算 | （必要に応じた直接通信経路） | 各種AIプロバイダー（クラウド／ローカル） |
| **実行・拡張** | ファイル操作、ローカルMCPのサンドボックス実行 | アクティブ端末でのPC操作（Computer Use） | OS、外部ファイル、MCPサーバー、プラグイン |
| **権限・制約** | セキュリティルール、送信同意、費用上限の一元管理 | 各種操作におけるルールの厳格な適用 | システム全体の安全境界 |
| **認証秘密** | APIキー・パスワードの物理隔離保管 | 秘密値を露出しない設定画面 | 外部認証サーバー |
| **保全・消去** | データの整合保存、バックアップ、完全削除の統括 | 端末上の一時データの完全消去 | バックアップファイル、エクスポート先 |

### アーキテクチャ方針の網羅性（Driver Coverage）

本書のサブシステム分割は、[アーキテクチャ設計方針（Architecture Drivers）](architecture-drivers.md)のすべての項目（AD-01〜AD-15）を確実に満たすように設計されています。

- **AD-01（ローカル優先・自律継続）**: 「個体調整」「作業」「接続・存在」「保全・消去」により、Host側でマスターデータとタスクが自律継続します。
- **AD-02（マルチクライアントと排他性）**: 「接続・存在」「入出力・提示」により、パートナーが同時に複数端末に現れることを防ぎます。
- **AD-03（パートナー中心の体験）**: 「個体調整」「作業」「入出力・提示」により、重い作業中でも会話や管理操作がブロックされません。
- **AD-04（個体の独立性と配布パッケージ）**: 「Character」と「認識・学習」を分離し、パッケージ更新で思い出が消えないようにします。
- **AD-05（知識・手順・記憶の区別）**: 「認識・学習」により、客観的事実と主観的な解釈、判断の根拠を明確に区別します。
- **AD-06（セキュリティルールの厳格適用）**: 「権限・制約」により、AIの出力だけで勝手に危険な操作が実行されるのを防ぎます。
- **AD-07（完全削除の保証）**: 「保全・消去」により、指定されたデータをシステム全域から徹底的に抹消します。
- **AD-08（タスクと作業環境の分離）**: 「作業」「実行・拡張」により、タスクと外部作業フォルダを安全に管理します。
- **AD-09（安全な中断と成否不明の扱い）**: 「作業」「実行・拡張」により、成否不明な操作の勝手な再実行を防ぎます。
- **AD-10（AIプロバイダーの柔軟な利用）**: 「推論」により、モデル間の能力差や費用上限を安全に管理します。
- **AD-11（オープン規格の採用）**: 「実行・拡張」「認識・学習」により、MCPやVRM、Agent Skillsと安全に連携します。
- **AD-12（効率的な画面観測）**: 「共有観測」により、端末単位で効率よく画面を見守り、負荷を分散します。
- **AD-13（快適な操作性と段階的縮退）**: 「入出力・提示」により、高負荷時でもテキストチャットや緊急停止を保護します。
- **AD-14（プライバシーと機密保護）**: 「認証秘密」により、APIキーなどの秘密情報をAIプロンプトやログから物理隔離します。
- **AD-15（バックアップと安全な復元）**: 「保全・消去」により、安全なバックアップと、APIキーを保護するリストアを実現します。
