# Subsystem Detailed Design — 権限・利用制約 / 認証秘密の保護 / Action実行・拡張受入 / 推論利用

本書は Step 12 Subsystem Detailed Design として、次の4つのサブシステムを一つの「実行・強制クラスタ」としてまとめて詳細設計を定める。

- 権限・利用制約（以下、権限・制約サブシステム）
- 認証秘密の保護（以下、認証秘密サブシステム）
- Action実行・拡張受入（以下、実行・拡張サブシステム）
- 推論利用（以下、推論サブシステム）

本書内の C / S / E / I 番号は各サブシステムの内部責務の参照用であり、製品要件IDではありません。
K番号は、サブシステム間のデータ受渡し（semantic contract）の参照用です。

## 0. 位置付けと不変条件

上位設計との優先順位や矛盾が生じた場合の扱いは、[設計文書 README](../README.md#設計文書の優先順位と信頼できる情報源) に従います。[Context Assembly](../critical-areas/context-assembly.md)、[Action Execution](../critical-areas/action-execution.md)、[Targeted Deletion](../critical-areas/targeted-deletion.md)、[Client Presence Transition](../critical-areas/client-presence-transition.md)（以下、Presence Transition）、[Backup / Restore](../critical-areas/backup-restore.md)の一般契約は、確定済みの契約としてそのまま利用し、再定義したり所有権を勝手に移転したりしません。本書内の SO は [State Ownership](../architecture/state-ownership.md) の節番号を指し、CC / RF / RT 番号は対応するアーキテクチャ文書（[artifact 一覧](../README.md#artifact-一覧)）の契約IDです。

本書は、新しいデータの担当責任者（semantic owner）や第二のマスターデータとなる万能マネージャー（万能Security Pipeline、何でも実行する Execution Manager、Policy Engine、Inference Service、統一Permissionステートマシン、共通Context層など）を新設しません。

## 1. 選定理由

この4つのサブシステムは、「あらゆる実行経路において、全く同一のセキュリティ強制ルール（contract）を確実に成立させる」という一点で密接に相互依存しており、個別に分けると全く同じ対応付けを4箇所に重複して定義することになります。同時に、後続の実装において誤って「一つの巨大な万能サブシステム」へと安易に統合してしまいがちな重要な境界を最も多く含んでいます。

- **権限・制約と推論**を分けずに設計すると、推論機能がコンテキスト全体・権限ルール・利用コストのすべてを牛耳る構造になったり、AIモデル自身の「許可します」という自己申告だけでセキュリティ制御が変わってしまうような致命的な脆弱性が生まれます。
- **権限・制約と認証秘密**を分けずに設計すると、「権限の許可を説明するためにコンテキストに渡せる安全な情報」と「パスワードなどの秘密値そのもの」の区別が崩れ、秘密情報がAIプロンプト、ツールの引数、監査ログへと流出してしまいます。
- **権限・制約と実行・拡張**を分けずに設計すると、上流で「許可された」という一言だけでセキュリティチェックが完了した気になってしまい、実際の操作対象の解決（パストラバーサルの防止等）、重要な変更の検知、権限失効の即時反映、特定端末への操作制限が失われてしまいます。
- **推論と実行・拡張**を統合してしまうと、「AI推論の呼び出し失敗」と「実世界への外部作用の成否不明」が同じ単なる再試行の問題として扱われてしまい、結果が不明な処理を勝手に自動再実行（replay）して二重実行を引き起こしてしまいます。
- **拡張受入を実行・拡張**から切り離してしまうと、MCP、プラグイン、シェルコマンド、Computer Use（画面操作）ごとに拒否・停止・成否不明のルールがバラバラになり、実行経路を変えることでセキュリティ拒否（Deny）をすり抜ける抜け穴が生まれてしまいます。

最初のマイルストーン（ワークスペースフォルダを対象とするタスクエージェントへのファイル作業委任、ファイル削除・シェル・ネットワーク・MCP・ワークスペース外アクセス・パストラバーサルの拒否と迂回防止、認証情報の漏洩防止、OpenAI等の利用量と費用の確認、外部作用不明時の自動再実行防止）は、この4者の連携が閉じて初めて検証できます。音声合成（Voice）、画面観測（Observation）、タスクスケジュール、リモートアクセス、フォールバック、全体共有（Global）は後続のマイルストーンですが、本書ではそれらの確定済み契約を正しく踏まえ、将来の受渡しを塞がない形で詳細を定めます。

## 2. 内部責務の分離

### 2.1 権限・利用制約

AIモデルの文脈判断を活用しつつも、ユーザーに由来する明確な許可・同意と、機械的に守るべき制約を、実行経路に依存しない強固な契約とします。セキュリティ強制のチェックポイントを、特定の単一プロセスや固定の関数呼び出し順序だけに依存させません。

| 内部責務 | 正規の判断権限（authoritative）を持つもの | 持ってはならないマスターデータ |
|---|---|---|
| C-1 Capability境界・Deny・Always ask・Rule | ユーザーが許可した目的、対象、操作、および将来の基本方針。自然言語で書かれた明確なルールの解釈、適用範囲の表示、保存、取り消し（Undo）、ならびにルールが曖昧・矛盾・過度に広範・重大な影響を持つ場合のユーザー確認。ルール保存をアクションのトリガーにしないこと。現在の明確な依頼に対する「一回限りの承認」としての解釈範囲。異なる許可を安易に一つの包括承認にまとめないこと。 | タスク達成、作用成功、報告完了の確定。学習の意味内容や共有スコープの意味付け（認識・学習機能が担当）。パスワード等の認証情報値（認証秘密機能が担当）。 |
| C-2 個別Permission判断・Owner判断待ち | 現在のユーザー依頼やルール、対話の文脈と、具体的なアクションとの対応関係。ユーザー確認の要否、現在の利用可否の確定。依拠したユーザーの意図やルールの対応付け。既存の依頼・同意・ルールから判断できる事項について、無駄な再確認を抑止すること。 | 個別のアクションが及ぼした作用の確定度の独自更新（実行・拡張機能が担当）。タスクへの指示受理・反映・達成（作業機能が担当）。会話上の受付や結果の統合（個体調整機能が担当）。 |
| C-3 Provider割当同意・承認済みfallback順序 | 機能（Capability）ごとに選択されたAIプロバイダやモデル、送信先、送信データ、利用用途、取り扱い基準、費用の範囲。Host既定の設定、コンパニオンごとの上書き設定（override）、共有観測（Observer）専用の割り当てとその同意。事前に承認されたプロバイダとその優先順位。接続設定の登録と、実際の割り当て同意の厳密な区別。 | 接続先、プロトコル、モデル名などの非秘密登録情報、プロバイダの能力観測（推論機能が担当）。パスワード等の秘密値、認証用途の利用可能性（認証秘密機能が担当）。 |
| C-4 費用・資源・反復・並列等の上限 | プロバイダ別およびシステム全体の利用コスト上限（cap）、リソース消費、反復回数、並列数などの制限に対する、現在の利用可否および継続可否の判定。上限到達やコスト不明によって安全に処理を継続できない場合に、対象処理を安全に停止し、ユーザーの判断待ちにすること（既存データは保持）。上限適用を、既に行われた作用の取消成功やデータの勝手な破棄にすり替えないこと。 | 利用実績の元の生ログ記録（推論・作業・実行・拡張などの各利用機能が担当）。利用コストの推定計算やプロバイダからの報告値そのもの（推論機能が担当）。 |
| C-5 device許可・失効、Local MCPの個別sandbox外例外 | ユーザーの指示に基づく端末（device）ごとの許可機能や失効などの制御状態。特定のローカルMCPに対するコマンド、設定の由来、既知のアクセス権、リスク、免除されるセキュリティ境界の説明、保存、失効、および設定変更時の再確認。この例外を、個々のアクションの承認やプラグインへの例外許可へ勝手に流用しないこと。 | 滞在（presence）の成立そのもの（接続・存在機能が担当）。実際の操作対象への適用結果（実行・拡張機能が担当）。パスワード等の秘密値（認証秘密機能が担当）。 |
| C-6 保存禁止・非共有等のcontrol constraintの強制調整 | ユーザーが明示した「保存禁止」「共有禁止」などの指示を、適用対象と範囲を持ったセキュリティ制約（control constraint）として扱い、データ参照・共有・知識形成・アクション実行などの別経路から迂回されないよう確実に強制すること。各利用箇所との協調として処理すること。 | 学習状態としてのスコープ形成や変更（認識・学習機能が担当）。各ドメインのデータの意味決定。 |
| C-7 現在の利用可否の照合 | 保存された許可条件に加え、コンパニオン個体の活動状態、タスクと委任の範囲、端末への滞在帰属、現在の利用コスト残高、失効の有無、システム横断操作やリストア復元直後の保留状態などを総合的に照合した判断。過去の判定結果のキャッシュは、前提条件の変化を無視してよい権限ではありません。 | 参照した各ドメインデータの内容更新。学習内容全体や秘密値の無制限な取得。タスク達成やアクション成功の勝手な確定。 |
| C-8 失効・停止・cap到達等への新規禁止と停止要求の結合 | 権限失効、コンパニオン停止、端末失効、コスト上限到達などに対応して、新規処理の開始を直ちに禁止すること。また、実行中の処理に対する停止要求を関係する各機能へ確実に伝達すること。委任や実行経路の変更による制限の回避を禁止すること。無関係なHost上の通常タスクまで一律に中断（Cancel）しないこと。 | 外部への作用の停止完了や取消成功の勝手な確定（実行・拡張機能が担当）。タスク記録の意味変更（作業機能が担当）。 |

C-1〜C-8は同じサブシステムに属しますが、一つの状態、一つのライフサイクル、あるいは一つの失効範囲にひとまとめにされるものではありません。権限、同意、上限枠は、それぞれ内部で独立した意味と失効範囲を維持します。端末の制御ルールは権限・制約サブシステムが扱い、接続・存在サブシステムがそれを端末の滞在調停へ反映し、実行・拡張サブシステムがアクション実行時に最新の条件を適用するという責任分担を守ります。

### 2.2 認証秘密の保護

認証に必要な秘密情報（APIキーやパスワードなど）を安全に利用できることと、その生値をAI推論や通常のデータ経路へ絶対に漏洩させないことを両立します。

| 内部責務 | 正規の判断権限を持つもの | 持ってはならないマスターデータ |
|---|---|---|
| S-1 登録・更新・失効 | ユーザーによる明示的な設定、プロバイダやMCP等の正規の認証フロー、明示的な接続設定を通じた認証情報の登録、用途および参照元の確認、個別の更新および失効。一般的なアプリデータ（App Data）から物理的・論理的に分離して保護すること。AIモデルの自由記述テキスト出力から秘密情報を自動登録・変更しないこと。 | アクションの承認、セキュリティルール、プロバイダ割当同意の変更（権限・制約機能が担当）。一般データ全体の暗号化。外部サービスのアカウント自体の所有権。 |
| S-2 秘密値と非秘密参照の分離・照合 | 登録された秘密値そのものと、接続設定側が持つ「どの認証用途を必要とするか」という秘密を含まない識別参照、利用用途、参照関係、利用可能性との照合。認証情報の登録・失効ステータスと、外部接続における認証成否の厳密な区別。認証が成功したことを理由に、外部アカウントの所有権を得たとしたりアクションを包括承認したとみなさないこと。 | 参照元の接続設定の管理（推論や実行・拡張などの接続担当機能が担当）。権限の可否判断（権限・制約機能が担当）。 |
| S-3 認証用途に限定した秘密利用の供給 | ユーザーが設定・認証した接続の実行に必要な最小限の範囲でのみ秘密値を利用すること。AIモデルのプロンプトコンテキスト、LLMが生成するツール引数、通常の処理結果、画面UI、記憶や学習内容、会話履歴、タスク結果、ログ、デバッグ記録、監査ログ、バックアップへの平文露出を完全に防止すること。認証先のエラーメッセージやレスポンスによる秘密の反射（エコバック）に対しても、受入・保存・提示の各機能と連携して非露出を徹底すること。 | 通常のデータ経路の抱え込み。AI推論結果やアクション作用結果の勝手な確定。 |
| S-4 認証失敗・失効・再認証必要性の通知 | 認証失敗、キーの失効、再認証の必要性を、秘密値の生情報を含めずに安全に通知すること。用途、参照元、失効、再認証の説明はすべて秘密情報を含まない形式で行うこと。 | プロバイダ同意やセキュリティルールの確定。処理全体の実行可否の勝手な確定。 |
| S-5 backup除外・現在store維持・Reset参加 | フルバックアップからの秘密値の確実な除外。リストア（復元）開始前にHostに存在していた現在の認証情報ストアを安全に維持すること（バックアップから秘密を復元・巻き戻ししないこと）。復元された参照と現在の用途・有効性を照合すること（利用可能なら現在のキーを使い、不足・無効なら再認証を要求）。全データリセット時の削除、設定リセット時の安全な維持への参加。 | バックアップ対象の意味決定（保全・消去機能および各データ担当機能が担当）。復元された割り当てや同意情報から自動で処理を開始してよいかの判断（権限・制約機能および活動担当機能が担当）。 |

S-2における「接続の存在」「認証用途」「有効性」「秘密を含まない参照（non-secret reference）」「プロバイダやMCPの割り当て」は、それぞれ全く異なる意味を持ち、安易に一つの認証ステータスにひとまとめにしてはいけません。登録、認証、存在、実行可能性は別々であり、設定内容とその時点での利用可否も別々です。なお、システムに登録されていない未知の秘密情報を100%完全に自動検出することまでは保証しません。

### 2.3 Action実行・拡張受入

意味的な依頼を、実際の対象に対する制限された安全な作用へと正しく対応付け、外部コードの受け入れや作用の不確実性をEne側で安全に統制します。

| 内部責務 | 正規の判断権限を持つもの | 持ってはならないマスターデータ |
|---|---|---|
| E-1 実対象への制限された作用 | ファイルシステム、ネットワーク、シェル、端末デバイス、外部アカウント等に対するアクションを、目的・対象・操作・データ・送信先に対応する最新の制限範囲内で実行すること。ファイルシステムでは操作の種類（読み取り・新規作成・編集・削除・実行などのリスク区分）と許可された範囲を厳格に守り、パストラバーサル（相対パスによる脱出）、シンボリックリンク、マウントポイント等による境界外アクセスを確実に拒否すること。 | ユーザーの意図や許可の勝手な拡大。タスクの全体計画の策定。プロバイダ割り当てや意味判断。知識学習。外部ファイルそのものの所有権。 |
| E-2 作用の把握・確定度・停止結果 | 依頼された作用について、実際の対象、操作内容、送信先、実行の受付、確認できた作用、未完了・成否不明な状態、停止要求と停止結果を把握すること。これは外部の世界そのもののマスターデータではなく、「Eneが何を実行し、何を確認できたか」という客観的事実のマスターデータです。作業エージェントの「完了しました」という自己申告だけでアクションの成功を確定してはいけません。 | 権限の付与（権限・制約機能が担当）。タスク全体の達成判定（作業機能が担当）。ユーザーへの報告完了の判定（個体調整機能が担当）。 |
| E-3 Computer Useの現在presence限定 | 操作を行うタスクの委任元コンパニオンが、現在アクティブに滞在しているクライアント端末のみに操作対象を限定すること。端末別の許可設定と通常の権限チェックの適用（これは適用の結果であり、許可の意味自体は権限・制約機能に残ります）。端末移動時の安全な区切りと、切断時のベストエフォートでの停止要求を接続・存在機能へ伝達すること。Hostと同居しているクライアントであっても全く同じ滞在制限を適用すること。 | 移動先の決定（個体調整機能および接続・存在機能が担当）。権限の意味付け（権限・制約機能が担当）。 |
| E-4 MCP Tool / Resource / Promptの接続・利用・結果受入 | MCPの接続、ツールやリソースの利用、結果の受け入れ。Host上で動作する作業用ローカルMCPを、Host側の既定サンドボックス内で安全に実行すること。明示的に許可された特定のMCP例外を除き、サンドボックスを勝手に解除しないこと。取得した案内、スキル、プロンプトの由来（provenance）を安全に保持すること。 | 各機能の意味付け（利用元の機能が担当）。外部ツールをEne内部のマスターデータや制御機構（control plane）へ勝手に昇格させること。外部サーバーが保持するデータの所有権。 |
| E-5 Pluginの限定受入 | 未対応のプロバイダ通信プロトコル、画面観測アダプター、デスクトップ描画（Body）レンダラーなど、明確な型と境界が定義された拡張ポイントへのプラグイン受け入れ。利用機能と連携した外部コードの実行範囲の制限、停止処理、障害の処理。外部コードを公式（第一者）のマスターデータや制御機構へ昇格させないこと。ローカルMCPの例外設定をプラグインへ勝手に流用しないこと。 | Eneのコア機能の勝手な改変、制御機構の変更、権限チェックの回避、公式UIの恒久的なすり替え。すべての機能を安易にMCPやプラグインにしてしまうこと。 |
| E-6 MCP Appsの制限 | MCP Appsの画面リソースや操作、MCP側が及ぼす作用を、入出力・提示機能と連携して厳格に制限すること。ツールUIの終了と、サーバー・タスク・アクション自体の終了を明確に区別すること。画面の再表示をアクション再実行のトリガーにしないこと。 | 公式（第一者）としての承認や設定権限の付与。「ツールUIが閉じた＝タスクが終了した」という安易な推定。 |

E-1における「適用」とは、アクション実行時に最新の条件を適用した結果のことであり、許可のルールそのものは権限・制約サブシステムに残ります。E-2における「中断要求を受け付けたこと」は「作用が停止したこと」ではなく、「通信が成功したこと」は「外部への作用が成功したこと」ではありません。E-4〜E-6において、外部プロセス内部にまでEneと同じセキュリティ強制が及ぶという非現実的な保証は追加しません。確認できない作用は、すべて「結果不明」として安全に扱います。

### 2.4 推論利用

推論を利用する各機能を、特定のAIプロバイダの能力、通信プロトコル、セッション、費用報告の差異から切り離し、承認された範囲内で安全に利用できるようにします。汎用的な「知能の中心」にはしません。

| 内部責務 | 正規の判断権限を持つもの | 持ってはならないマスターデータ |
|---|---|---|
| I-1 割当解決 | 機能（Capability）ごとのHost既定設定、コンパニオンごとの上書き設定（override）、作業エージェントへの継承の解決。クライアント共有の観測（Observer）専用の割り当ての解決（コンパニオンの上書き設定に依存させないこと）。解決された通信経路は一時的な派生データであり、設定や同意が変更された後に古い選択を有効とし続ける根拠にはなりません。Task Agent は委任元 Companion の割り当てを継承し、実装段階の closed world では消費主体（TaskAgent）＋委任元の既存 Capability（Dialogue）＋ターン専用 Purpose（TaskAgentTurn）の明示的な組で許可します。割り当ては受付のたびに委任元の現在の同意から解決し、委任行に独立した割り当て identity を保存しません。 | 割り当て同意そのものの意味（権限・制約機能が担当）。認証情報のマスターデータ（認証秘密機能が担当）。 |
| I-2 能力不足の事前提示 | AIプロバイダやモデルが必要な機能（Capability）の要件を満たしていない場合に、処理を開始する前にユーザーへ能力不足を提示すること。 | 何を学習するか、何を依頼として受け入れるか、どのアクションを開始するかの最終的な意味判断（利用元の各機能が担当）。 |
| I-3 論理的contextとProvider能力の対応付け | 各機能が必要とする論理的なコンテキストと、プロバイダの能力やコンテキスト長の制限との対応付け。利用可能な情報をプロバイダごとに意図的に差別化せず、同じ情報選択方針を維持すること。コンテキスト圧縮によって必須条件を満たせなくなった場合は、無理に進めずに能力不足を返すこと。 | コンパニオン個体情報の独立した選択方針、データの意味状態、最終的な採否判断（利用元およびデータ担当機能が担当）。 |
| I-4 実利用ごとの成立と送信 | 最初の送信、フォールバック、再送、補助推論、継続的な送受信の各ステップについて、現在の活動や用途との対応、解決された割り当てと実際の送信先・データ・用途・取り扱い・費用の同意との対応、現在の認証用途・制限・保留・利用コスト上限の充足、送信データと元の要求・許可範囲との対応を確認すること。クライアント直結の通信やプロトコルプラグインにも全く同じ条件を引き継ぐこと。すべての通信データをHost経由で中継する構造は固定しません。 | 権限、同意、上限枠の変更。AIプロバイダ側のセッションやキャッシュにコンパニオンの状態を依存させること。接続回復後に過去のアクションを勝手に再実行すること。 |
| I-5 承認済みfallback | ユーザーが事前に承認したプロバイダと優先順位の範囲内でのみフォールバックを行うこと。Host、LAN、クラウドといったサーバーの所在地だけを理由に、同意手続きを省略してはいけません。候補ごとに現在の用途、データ範囲、プライバシー、認証情報、コスト上限の条件をすべて満たす必要があります。 | 未承認のクラウドプロバイダへの勝手なデータ送信。安価であることを理由にしたセキュリティ例外の作成。 |
| I-6 結果・利用量の返却 | AIプロバイダから得られた応答結果、能力不足、接続失敗、利用量の返却。利用コストについて、プロバイダからの確定報告値、Eneによる推定値、成否不明な状態を厳格に区別すること。コスト上限などの適用に必要な情報を権限・制約サブシステムへ供給すること。未報告の利用量を勝手に「ゼロ」として扱わないこと。 | タスク達成、学習内容の保存、画面提示完了の勝手な確定。推定コストを請求確定値へと勝手に昇格させること。 |
| I-7 cache・sessionの最適化限定 | プロンプトキャッシュを性能向上やコスト削減のための純粋な最適化技術として扱い、キャッシュのヒット・ミス・有効期限切れによって論理的なコンテキスト、権限、永続化のルールを変更しないこと。プロバイダ側のセッションやキャッシュにしか状態が残らないような脆弱な構造を作らないこと。 | 会話履歴、サマリー、記憶（Memory）、タスク状態のマスターデータ。権限許可の唯一の根拠。 |

I-1における共有観測（Observer）の解決では、対象クライアントのObserver機能とその利用用途に基づいて専用の割り当てを解決し、その場にいるコンパニオンの上書き設定や同意を勝手に選んだり組み合わせたりしません。画面のキャプチャ、発言候補の検知、発言の振り分けを行う処理と、振り分け後に各コンパニオンが思考する処理は別々の利用者（consumer）であり、後者のみが各コンパニオンの設定に従います。すべてのクライアントでモデルを共通化するか、クライアントごとにUIを分けるか、Hostの既定設定からの継承構造をどうするかなどは、本書では固定しません。

## 3. 管理する logical state / control state

ここで説明する状態は、特に「外部」「コピー」「一時データ」と明記されているものを除き、Host側で管理される内部状態を指します。永続化の具体的な実装担当、保存単位、排他制御の書き込み役、トランザクション方式などは固定しません。また、通常のデータ担当責任者は、正当なシステム全体のデータ消去要求への参加を拒絶できません。

### 3.1 権限・制約が意味ownerとなる state

- **Capability境界・永続Deny・Always ask・Rule（SO 4.19）**: ユーザーが許可した目的、対象、操作、および将来の基本方針。自然言語ルールの解釈、適用範囲、取り消し（Undo）。ルールは自発的行動のトリガーではありません。
- **個別Permission判断・Owner判断待ち（SO 4.19）**: 現在の依頼やルール、対話の文脈と、具体的なアクションとの対応関係。過去の承認ログやタスクの判断待ち表示そのものは、使い回しが可能な包括承認ではありません。
- **Provider割当同意・承認済みfallback（SO 4.19）**: 選択されたプロバイダやモデル、送信先、データ、用途、取り扱い基準、費用の範囲。Host既定、コンパニオンの上書き、Observer専用の割り当て。Observer専用では送信され得るデータに限定されたルーティング文脈を含め、元データの利用制約を維持します。接続設定の登録や認証成功だけでは同意は成立しません。
- **device許可と失効、Local MCPの個別sandbox外許可（SO 4.19）**: 前者は確認された端末の機能範囲、後者はコマンドや設定の由来・権限に対応付けられた個別のサンドボックス例外。それぞれ個別に失効可能であり、MCP例外の重要な変更時は再確認を求め、個々のアクション承認やプラグインへの例外許可へ転用してはいけません。
- **ユーザーが明示した保存禁止・非共有（SO 4.19）**: 意味判断側が読み取ったユーザーの意図を、適用対象と範囲を持ったセキュリティ制約（control constraint）として扱います。記憶の重要度が高いことやAIモデルの判断を理由に解除してはいけません。学習内容のスコープ自体の意味付けの責任は認識・学習機能に残ります。
- **Provider別・全体の費用cap、利用・資源・反復等の上限（SO 4.19）**: タスクの委任、並列処理、別経路を通じた利用であっても、同一の枠組みを確実に適用します。
- **制約上の現在の利用可否（SO 4.19）**: 保存された許可条件に加え、コンパニオン個体の活動状態、タスクと委任の範囲、端末への滞在帰属、現在の利用コスト残高、失効の有無、システム横断操作やリストア復元直後の保留状態などを総合的に照合した最新の判断。この判断の責任は権限・制約サブシステムにあり、各利用・実行箇所が実効的に適用します。過去の判定のキャッシュ、保存された許可ログ、復元直後の古い記録は、現在の条件ではありません。

AIモデルのテキスト出力、キャラクター定義、記憶、スキル、サマリー、関係性、コンパニオン状態、MCP、プラグイン、外部コンテンツを、これらのセキュリティ制御状態の直接の変更指示として受け入れることは決してありません。

### 3.2 認証秘密が意味ownerとなる state

- **登録された秘密値とその登録・更新・失効、許された認証用途（SO 4.21）**: 一般のアプリデータから分離して厳重に管理します。ユーザーによる明示的な設定、正規の認証フロー、明示的な接続設定によって登録され、AIモデルの出力から自動登録・変更されることはありません。
- **用途・参照元・認証状態の非秘密の対応（SO 4.21）**: 接続設定側が持つ「どの認証用途を必要とするか」という情報は、パスワード等を含まない安全な識別参照であり、秘密値のコピーではありません。参照元の接続設定は推論や実行・拡張などの機能が管理し、認証秘密機能が用途、参照関係、利用可能性を照合します。認証情報の登録・失効ステータスと、外部接続における認証成否を明確に区別します。
- **認証に必要な利用経路の限定（SO 4.21・8）**: AIプロンプト、ツール引数、通常の処理結果、画面UI、会話履歴、サマリー、記憶、関係性、コンパニオン状態、タスク結果、ログ、監査ログ、デバッグ記録へ秘密値を絶対に露出させません。用途、参照元、失効、再認証の説明はすべて非秘密情報で行います。
- **secretのbackup除外・現在store維持・Reset範囲（SO 4.21・6.5）**: フルバックアップから秘密値を確実に除外します。リストア時は開始前からHostに存在していた現在の認証情報ストアを安全に維持し、古い秘密の復元や巻き戻しを行いません。設定リセットでも維持され、全データリセットにおいてのみ完全に削除されます。コンパニオンやタスクから参照されているからといって、認証情報全体が個体やタスクの所有物として道連れで消去されることはありません。

クライアント固有の接続材料のうち秘密に属する部分は、バックアップから復元しません。復元された端末の参照や許可情報は、現在の接続や認証の成立状況と照合して検証します（SO第8節）。

### 3.3 実行・拡張が意味ownerとなる state

- **Actionの実行状況・作用の確定度・停止結果（SO 4.12）**: 依頼された作用について、実際の対象、操作内容、送信先、実行の受付、確認できた作用、未完了・成否不明な状態、停止要求と停止結果を管理します。これは外部世界そのもののマスターデータではなく、「Eneが何を実行し、何を確認できたか」という客観的事実のマスターデータです。タスク内のアクションはタスクや委任関係に対応付けられ、タスクの進捗や作用報告はこの結果を参照・集約します。同じ確定度を作業機能側で勝手に独自更新してはいけません。
- **MCP・Pluginの接続 / 受入設定と外部実行状態（SO 4.22）**: 利用するMCPの非秘密接続設定、実行コマンド、設定の由来、プラグインの限定された拡張ポイントへの受け入れ、有効化、利用状況を管理します。ローカルMCPのサンドボックス外許可のマスターデータは権限・制約機能が持ち、パスワード等の秘密値は認証秘密機能が持ちます。外部サーバーの保持データや外部プロセスの継続状態は外部の所有物であり、Eneが把握した接続状況や停止結果と明確に区別します。
- **実行中の一時バッファと永続記録の区別**: 実行中のメモリバッファは一時データですが、処理の再開、二重実行の防止判断、結果説明に必要な作用の事実や成否不明な状態は、バッファの寿命を超えてHost側で安全に保持します。処理終了後の記録保持は関連する活動や監査の取り決めに従い、すべてのツール引数やペイロードを丸ごと保存することは要求しません。内部データの削除は作用記録の消去であり、外部の世界へ及ぼした作用の巻き戻し（ロールバック）ではありません。
- **MCP Appsの表示・操作中データ（SO 4.22）**: 入出力・提示機能が扱う一時的な画面表現であり、MCP側の業務データやEneの権限ルールのマスターデータではありません。

権限評価のマスターデータは権限・制約機能、外部作用の客観的把握は実行・拡張機能、タスクの判断待ちや全体達成は作業機能に残ります。「アクションが許可されたこと」は「実行が成功したこと」ではなく、「中断要求を受け付けたこと」は「作用が停止したこと」ではありません。

### 3.4 推論が意味ownerとなる state

- **Provider接続情報・能力情報と割当の解決（SO 4.18）**: 接続先、通信プロトコル、モデル名などの非秘密の登録情報を管理し、プロバイダが提供する能力や利用可能性の観測結果を扱います。接続情報を登録したことと、そのモデルを特定の機能（Capability）に利用してよいことは別問題です。解決された通信経路は派生物であり、設定や同意が変更された後に古い選択を有効とし続ける根拠にはなりません。
- **コンパニオン側の割当モデルとObserver専用割当の分離**: 「Host既定 → コンパニオン上書き → タスクエージェント継承」は、コンパニオン側の割り当てモデルです。クライアントに紐づく共有観測（Observer）は特殊な利用者（consumer）として、権限・制約機能が管理するObserver専用の割り当てとその同意を使用します。Task Agent は委任元の割り当てを継承し、独立した割り当て同意・予算枠・プロバイダ上書きを作りません。割り当ては利用のたびに委任元の現在の同意から解決し、過去の解決結果を生きた許可として使い回しません。
- **利用量・費用の記録（SO 4.20）**: プロバイダ利用量、プロバイダからの確定報告値、Eneによる推定値、成否不明の区別、および費用推定の根拠を管理します。プロバイダからの報告値は外部からの報告という元の記録であり、推定コストや画面表示用の集計値は派生値として区別します。Ene側の推定値を、プロバイダの請求確定値へと勝手に昇格させてはいけません。推論以外のアクション実行回数、実行時間、並列稼働数などは、その利用を管理する各機能が客観的事実を供給し、権限・制約機能がそれらの事実を用いて利用コスト上限枠に対する現在の利用可否を判定します。
- **派生物としての有効Provider経路・費用集計（SO 5.2）**: 古い派生値を、現在の同意や利用可能残高の独立したマスターデータとして勝手に編集してはいけません。

登録情報が変更され、送信先などの同意の意味が大きく変わった場合は、以前の同意のまま利用してはいけません。プロバイダのセッション、プロンプトキャッシュ、通信プロトコル上の一時的な継続情報は利用のための補助に過ぎず、会話、学習、タスクの唯一のマスターデータにはなり得ません。

### 3.5 canonical / derived / temporary / external reference の扱い

- **canonical（マスターデータ）として参照するもの**: ユーザーに由来する制御条件（ルール、Deny、Always ask、割当同意、フォールバック順序、コスト上限枠、端末許可、サンドボックス例外、保存禁止、非共有）とその時点での評価済み有効性。パスワード等の秘密値とその登録・失効・用途（認証秘密機能）。Eneが把握した外部への作用、確定度、停止結果（実行・拡張機能）。プロバイダからの確定報告値という原記録（推論機能）。なお、保存された許可ログ、判定結果のコピー、解決済み経路、プロンプト内の許可文、キャッシュされた判定、有効なプロバイダ経路、画面表示用コスト集計は、決してマスターデータとして扱いません。
- **derived（派生物）として扱うもの**: 解決済みの割り当て経路、有効なプロバイダ経路、次回スケジュール表示、コスト集計値、報告用要約、由来説明、進捗表示、ベクトルデータ（embedding）、検索インデックス、類似度スコア、プロンプトキャッシュ、プロバイダセッション、一時コンテキスト。派生物を生成・保持・破棄する各機能は、元データとの対応関係や利用範囲を正しく説明し、訂正・スコープ変更・Targeted Deletionへ責任を持って参加します。古い派生物から、現在の状態や権限を勝手に復活させてはいけません。
- **temporary（一時データ）として扱うもの**: 推論中のコンテキスト、ツール実行バッファ、観測候補データ、クライアント側の表示コピー、入力途中のテキスト、音声バッファ、MCP Appsの表示データ、I-7のセッションやキャッシュ、E-2の実行中バッファ。失われてもよいのはこれらの一時的な表現形式のみであり、正式に受理した指示、必要な作業記録、未伝達メモ、作用不明の記録、システム横断操作の未完了状態まで失ってよいわけではありません。
- **external reference（外部参照）として扱うもの**: 外部ワークスペースの実体ファイル、外部アカウント、外部ソース、AIプロバイダやMCPサーバー側の固有状態や保持コピー、外部パッケージ、スキルの原本、エクスポートされたコピー、ユーザーが保存したバックアップ。内部に保持している一時コピーや内部に取り込んだデータ、Eneの管理下にある一時データは、内部の利用・消去責任の対象に戻ります。「外部コードに由来するデータだから」という理由だけで消去対象から除外してはいけません。

データを保存することと、それがマスターデータであることは全く別です。判断の記録は監査、説明、対応関係の確認のための材料であり、現在動いている生きた許可のマスターデータではありません。

## 4. Subsystem間の受渡し（semantic contract）

「AがBの関数を呼ぶ」といった実装構造を先に決めるのではなく、要求の開始、正規の判断、受渡内容、失ってはならない前提条件、結果の受入れという一連の対応関係を定めます。非同期メッセージ、同期呼び出し、共有メモリなどの具体的な実現メカニズムは、下位設計の自由度として残します。

### K-1 Owner意図から制御変更まで

- **開始の契機**: 会話の中から生じたユーザーの管理意図は、入出力・提示機能および個体調整機能が受け取り、設定画面などの管理面からの操作は入出力・提示機能から担当機能へ直接渡されます。権限・制約サブシステムは、ユーザーの意図と解釈の対応関係を確認し、「現在の依頼に対する一回限りの承認」「将来に向けたルール」「プロバイダ割り当ての同意」「コスト上限の変更」などを明確に区別して確定します。認証情報の登録や更新は、認証秘密サブシステムが明示的な設定や正規の認証フローを通じて受け付けます。
- **判断**: ユーザーからの入力の由来、対象、それが現在の一回限りの依頼なのか将来の恒久ルールなのかという判断材料は、利用目的を持つ機能（個体調整機能や作業機能など）が供給し、権限・制約サブシステムが確認の要否とセキュリティ制御の変更を正式に確定します。AIモデルのテキスト出力、学習内容、キャラクター定義、スキル、外部コンテンツなどは意味判断のための単なる材料に過ぎず、ユーザーに由来する明確な管理意図との裏付けがない限り、権限、ルール、認証情報、プロバイダ同意、コスト上限、その他の制御機構（control plane）を変更することは決してできません。データの中継、要約、保存を経たとしても、この原則は変わりません。
- **受渡内容**: 対象となる活動、目的、担当コンパニオン、タスクや委任、クライアント端末、会話ラウンドなどの対応関係、および依拠したユーザーの意図やルールの対応関係。引用された指示文、画面内に映り込んだテキスト、ワークスペース内の案内ファイル、MCPプロンプトなどをAIが要約したとしても、それらをユーザー自身の管理操作へ勝手に昇格させてはいけません。音声入力についても、話者認証を行わないという既存の基本原則に従います。
- **禁止事項**: ルールの保存、認証情報の登録、プロバイダの認証成功、システムのリストア復元、端末の再接続を、別のアクションを開始するための口実に混同してはいけません。ローカルMCPに対する個別のサンドボックス外例外の許可を、仲介される個々のアクションに対する無条件の承認とみなしてはいけません。自然言語ルールが保存されたこと自体を、アクション実行のトリガーにしてはいけません。
- **結果の受入れ**: 明確なルールは、解釈内容と適用範囲を提示した上で保存され、ユーザーがいつでも取り消し（Undo）できます。ルールが曖昧、矛盾している、過度に広範、あるいは重大な影響を持つ場合は、ユーザーへの必要な確認を行います。現在の明確なユーザー依頼は一回限りのアクション承認になり得ますが、永続的な拒絶（Deny）、都度確認（Always ask）、機能（Capability）の境界を黙って勝手に上書きすることはできません。

### K-2 判断記録と生きた許可の区別・現在条件の適用

- **判断**: 過去の認可判断の記録（過去に何についてどう判断したか）と、その後の各利用時点で有効な生きた許可（今その操作をしてよいか）は、全く別の意味を持ちます。前者は監査ログ（Audit）、説明、対応関係の確認のための材料であり、後者のマスターデータではありません。
- **受渡内容**: 権限・制約サブシステムが現在の利用可否を判定し、データ送信、参照、保存、アクション実行を担う各機能がそれを実効的に適用します。処理の開始ごとに、権限、ルール、拒絶（Deny）、都度確認（Always ask）、機能境界（Capability）、タスク・委任・ワークスペースの範囲、端末依存条件、認証用途・有効性、コスト上限・リソース・並列数・反復回数の上限、停止・保留などの該当する最新の条件を、実際の操作対象へ適用します。適用の責任は実行・拡張（外部作用）、推論（外部送信）、各参照・保存機能に残り、許可のルールそのものは権限・制約機能に残ります。
- **失ってはならない前提条件**: 目的、対象、送信先、データ、作用の重要な変更、権限の失効、担当コンパニオンや滞在先の変更、コスト上限への到達、保留の発生。過去に保存された許可ログ、委任時に渡されたコピー、事前の判定結果、復元された古いルールや同意、プロンプトコンテキスト内の許可文、キャッシュされた判定、解決済みの通信経路などを、そのまま現在の有効な条件として再利用してはいけません。
- **結果の受入れ**: 事前の判定結果をキャッシュして再利用することは、権限失効、スコープ変更、個体停止、滞在先切り替え、コスト上限到達、指示の更新（steering）、データ消去、リストア保留の発生を無視してよい理由にはなりません。一方で、無関係な軽微な変更が発生するたびにすべての処理で都度再承認を求めるような煩わしい設計も要求しません。再評価が必要かどうかは、「重要な変更があったか」によって判断します（K-8）。

### K-3 scope意味と強制の分離

- **判断**: 学習内容、その由来、共有スコープ（個体限定か全体共有か）の形成や変更に関する意味的な責任は「認識・学習」機能に残り、権限・制約機能がその意味付けそのものを所有することはありません。一方で、一度決定されたスコープや、ユーザーが明示した「保存禁止」「共有禁止」といったセキュリティ制約を、何人たりとも迂回できないように確実に強制する責任は、権限・制約機能と各利用機能との協調に属します。具体的な依存方向、API、制約の表現形式は本書では固定しません。
- **受渡内容**: 認識・学習機能が、学習内容、由来、共有の必要性を通常の意味判断として確定し、権限・制約機能と各利用機能が決定された制限を確実に適用します。ユーザーが明示した「保存禁止」「共有禁止」などのセキュリティ制約（control constraint）は、AIの意味状態とは明確に区別して扱います。
- **禁止事項**: 学習内容や外部プロンプト自身の内容だけに基づいて、ルール、権限、プロバイダ同意、コスト上限などを勝手に書き換えること。重要度が高いことだけを理由に全体共有（Global化）すること。要約やデータ変換を行ったことだけを理由に、セキュリティ制約や同意が不要になったとみなすこと。
- **結果の受入れ**: 元の生ログ、検索機能、共有機能、プロンプトコンテキスト、データ送信、保存、派生データ、クライアント画面表示の各利用箇所が、最新の内容へのアクセスだけでなく、判断根拠、派生データ、処理中の利用に至るまで、最新のスコープ制限に確実に従わせます。

### K-4 秘密値と非秘密参照・認証利用の受渡し

- **開始の契機**: 推論機能、実行・拡張機能、接続・存在機能が、設定・認証された正規の接続用途に限定して秘密情報の利用を要求し、キーの失効や不足の確認を認証秘密サブシステムへ依頼します。
- **判断**: 認証秘密サブシステムと、実際に認証を行う機能が、事前に設定された接続、用途、有効性を照合し、必要最小限の範囲でのみ秘密値を利用します。認証情報への参照（Credential reference）は、接続や用途を識別するための秘密を含まない安全な情報であり、その参照文字列をAIモデルがプロンプト内で勝手に記述したからといって、秘密が利用可能になるわけではありません。
- **受渡内容**: 認証用途の制限、参照元と接続先、認証結果の客観的事実を、秘密の生値を含めずに監査ログや画面提示へ返します。用途、参照元、失効、再認証の説明は、すべて秘密情報を含まない安全な形式で行います。
- **失ってはならない前提条件**: 秘密の生値を必要とする認証利用と、秘密を含まない用途参照や説明の厳格な区別。認証のために秘密値を利用した後であっても、外部サービスからのエラーメッセージやレスポンスによる秘密の反射（エコバック）を、通常のツール実行結果として安易に受け入れてはいけません。データを受け入れ・保存・表示するすべての機能が、秘密を露出させないための保護に参加します。
- **結果の受入れ**: 実際に認証を行う最小限の処理箇所でのみ秘密値を扱い、データの受け入れ、処理結果、画面提示、ログ記録の各ポイントで通常のデータ経路への流出を徹底的に防ぎます。「認証が成功したこと」は「アクションが承認されたこと」や「同意が得られたこと」を意味しません。システムに登録されていない未知の秘密情報が検知された場合も、不要な送信や保存を抑制しますが、完全な自動検出を保証することは求めません。
- **秘密の絶対隔離**: 秘密の生値を、AIモデルのプロンプトコンテキスト、LLMが生成するツール引数、会話テキスト、会話サマリー、記憶（Memory）、相手との関係性、コンパニオン状態、スキル定義、通常のツール実行結果、画面UI、会話履歴、タスク結果、通常のログ、監査ログ、デバッグ記録、バックアップファイルへ絶対に渡してはいけません。登録済みの認証情報値は、たとえユーザーからの明示的な指示（「このAPIキーを覚えておいて」など）があったとしても、サマリーや記憶へ保存してはいけません。

### K-5 推論の実利用ごとの成立

- **開始の契機**: 個体調整、作業、認識・学習、共有観測（Observer）、入出力・提示などの利用元が、利用用途と必要な論理的コンテキストを定義します。各データの担当機能は、現在アクセスが許可されている内容、根拠、スコープを提供します。
- **判断**: 推論機能が最新のモデル割り当て、接続設定、能力を照合し、権限・制約機能が現在のユーザー同意、禁止事項、コスト上限、リソース、活動状態、リストア復元直後の保留状態などに基づいて利用可否を判定し、実際の通信・送信箇所がそれを適用します。利用元が持つ「情報選択の基本方針」をプロバイダの能力やコンテキスト長に合わせて適応させますが、同意されていない情報を勝手に送信して情報量を揃えるようなことは決してしません。
- **受渡内容**: 利用者（consumer）と機能（Capability）、割り当て、ユーザー同意（送信先、データ、用途、取り扱い基準、費用の範囲）、データおよび利用用途、認証情報の利用可能性、コストおよびリソースの制約、フォールバックの候補と順序、実行結果および利用実績の対応関係。最初の送信、フォールバック、再送、補助推論、継続的な送受信の各ステップについて、それぞれ独立した「実際の利用」として成立させます。
- **失ってはならない前提条件**: 「参照できたこと」と「外部へ送信してよいこと」の厳格な区別。事前に解決された送信先を、無制限な送信許可と誤認しないこと。ユーザー同意の不足を、送信テキストを勝手に減らすだけで「同意された」と偽ってはいけません。
- **結果の受入れ**: 条件を満たせない通信経路は決して使用せず、能力不足や失敗を呼び出し元へ返します。プロンプトキャッシュやセッションは、この安全な契約を満たした上での純粋な最適化技術に限定されます。権限判断やデータ消去探索のために補助的にAI推論を利用する場合でも、その推論自身に対する割り当て同意、認証用途、利用コスト制限を正しく適用し、審査対象となっているアクションの許可や実行を先行条件にしてはいけません。推論の前提条件が不足している場合は、無理に進めず、不足や判断待ちの状態を管理面へ返します。

### K-6 fallbackの非迂回

- **判断**: フォールバックは、ユーザーが事前に承認したプロバイダと優先順位の範囲内でのみ行われます。ローカル環境やLAN環境から、未承認のクラウドプロバイダへデータを自動で送信することは絶対に禁止します。
- **受渡内容**: 候補となるプロバイダごとに、現在の用途、データ範囲、プライバシー、認証情報、コスト上限の条件を満たしている必要があります。接続先の変更、コンパニオンの上書き設定の解除、モデルやプロトコル、送信経路の変更によって同意の意味が大きく変わる場合は、以前の同意をそのまま使い回してはいけません。
- **共有観測（Observer）への適用**: Observerに対しても全く同じ条件を適用し、専用の割り当て先がクラウドプロバイダである場合も、ユーザー同意、プライバシー保護、費用上限の確認を省略しません。Observerの利用量は、対象クライアントおよび専用割り当てに対応付けてプロバイダ別・全体のコスト上限へ算入し、同席しているコンパニオンの数に応じて重複計上したり、各コンパニオンの設定へ勝手に付け替えたりしません。
- **結果の受入れ**: 推論における承認済みフォールバックは、「外部への作用の成否が不明なときに再実行して解決するための仕組み」ではありません。安価であることや機能不足を口実にして例外を作ってはいけません。フォールバックが発生したこと、エージェントが終了したこと、ログ整理が行われたこと、キャッシュが破棄されたこと、クライアントを移動したことなどを理由に、利用コストの実績を勝手にリセットしてはいけません。

### K-7 利用実績と制御の循環

- **開始の契機**: 推論機能がプロバイダからの報告値、Eneによる推定値、成否不明の区別とその根拠を供給し、作業機能が委任エージェントの稼働状況、実行・拡張機能がアクション実行実績、保全・消去機能が保存データ量などを供給し、権限・制約機能がそれらを同一のプロバイダ別・全体の上限枠へ正しく結び付けます。
- **判断**: 会話、学習、音声合成、画面観測、タスクエージェントが並行して利用される場合でも、各処理が同じ利用可能残高を互いに知らずに独立して使い切ってしまうような危険な構造を排除します。タスクエージェントに独立した予算枠を持たせてはいけません。Observerによる検知は、対象クライアントと専用割り当てにおける「1回の利用」として扱い、同席しているコンパニオンの人数分を重複計上してはいけません。振り分け後に各コンパニオンが思考する処理は、別の実際の利用として同じ全体の上限枠に含めます。
- **受渡内容**: プロバイダ報告値、Ene推定値、成否不明、処理中の消費の明確な区別、および対象クライアント、専用割り当て、利用者との正しい対応関係。費用の報告値、推定値、不明、処理中の消費は、元の利用用途と実際の利用先へ正しく対応付けます。処理が失敗したこと、フォールバックしたこと、コンテキストを再構築したことを口実に、利用量を勝手にゼロに戻してはいけません。
- **結果の受入れ**: 未報告の利用量を勝手にゼロと扱わず、並行処理がそれぞれ同じ残高を独立して使い切れるような甘い管理を排除します。利用コスト上限に到達した、あるいは費用が不明で安全に継続できない場合は、既存のデータを安全に保持した上で対象の処理を停止し、ユーザーの判断待ちにします。事前の利用枠予約、集計期間、価格推定の具体的な実装メカニズムは、下位設計に委ねられます。
- **循環の防止**: セキュリティ制約の判定を行うために、審査対象のアクションを先に実行してしまうような本末転倒な設計は禁止します。また、客観的事実をユーザーへ報告するために、次の新しいアクションの許可が必要になるような循環依存も禁止します。

### K-8 Action候補と認可と実作用と結果確定の分離

- **開始の契機**: 個体調整や作業などの利用元の機能がアクションの候補（目的、対象、データ、送信先、作用の解釈）を作成し、権限・制約機能へ現在の利用条件の確定を求め、実行・拡張機能へ実際の対象に対する作用の実行を要求します。コンパニオン本体が直接行う軽微なアクションであっても、他へ委任する本格的な作業であっても、全く同じ境界ルールに従います。これは「すべての処理をタスク化しなければならない」という意味ではありません。
- **判断**: 意味判断の供給は個体調整・作業・認識・学習機能、認可判断は権限・制約機能、実際の作用とその客観的把握は実行・拡張機能、タスクの目的と達成判定は作業機能、ユーザーへの報告管理は個体調整機能および入出力・提示機能、認証情報の秘密保護は認証秘密機能、滞在や活動条件の確認は接続・存在機能、記録の安全な保全は保全・消去機能および各参加機能が担当します。Action Execution第3節・第6節の対応関係を厳格に維持します。
- **受渡内容**: 実行主体と委任の連鎖、タスクとワークスペースの範囲、目的、実際の操作対象と操作内容、使用する主なデータと用途、コストやリスク、依拠したユーザーの指示やセキュリティルール。判断時に指示された対象の文字列と、実行時の実際の対象の文字列がたまたま一致しているだけでは、正しく対応が取れているとはみなせません。パスの解決、変数展開、別名（エイリアス）、シンボリックリンク、マウントポイント、UI要素の特定などを経て実際の対象が確定する場合は、その解決プロセスを正しく経た上で対応関係を確認します。
- **実行直前の最新条件の適用**: 実行・拡張機能は、要求された意味と、実際の操作対象、操作内容、データ、送信先、外部への作用との整合性を厳格に守り、最新の制限範囲内で作用を及ぼします。認可判断が行われてから実際に実行されるまでの時間差の間に、対象や前提条件が変化した場合、古い判定コピーでセキュリティ制約を迂回することはできません。重要な前提条件（対象の同一性、操作種別の拡大、目的や指示の変更、タスクや委任範囲の変更、ワークスペースやスコープの変更、端末依存アクションにおける滞在先クライアントの変更、依拠したルールや同意・端末許可・認証情報の有効性の変更、コストやリスクの重大な変化、停止 or 保留の発生）が変化した場合は、最新の条件で必ず再評価を行います。ただし、無関係な軽微な変更が発生するたびにすべての処理で再承認を求めることはしません。
- **結果の受入れ**: 入力の受付、タスクの受理、認可判断、実際の作用の開始、確認できた作用、内部記録の保存、タスクの達成、ユーザーへの報告は、すべて別々の客観的事実であり、安易に「一つの成功」としてひとまとめに混同してはいけません。作業エージェントの自己申告を、作用の客観的証拠の代わりにすることは禁止します。確認された成功、確認された失敗、成否不明な状態を厳密に区別し、確認できないことを勝手に「未実行」「失敗」「成功」のいずれかへ変換してはいけません。「試行（試み）」と情報（実際の影響）は別の関係として扱い、リトライや再実行は「同じ試行の単なる継続」ではなく、「新しい試行」として扱います。

### K-9 拡張受入の均一強制と外部processの限界

- **開始の契機**: 作業機能や個体調整機能などからアクション要求を受け取り、推論機能、共有観測機能、入出力・提示機能などから限定された拡張ポイントの利用を受けます。機能の意味付けは利用元の機能が担い、外部コードの受け入れと制限は実行・拡張機能が担います。
- **判断**: 複数のツールを組み合わせた処理、シェルコマンド、MCP、スキル付属のスクリプト、Computer Use、AIプロバイダが生成したアクション要求、MCP Appsからの追加要求であっても、実際の作用に対して全く同一のセキュリティ境界を適用します。セキュリティ拒否（Deny）された同等の作用を、名前、呼び出し経路、ツール、表現形式を変えて実行することはできません。通常のツールの実行許可を口実にして、Ene自身のデータ保存領域、内部管理の入り口、公式の承認UIへ裏から回り込むことは禁止します。許可されたComputer Useを用いて、Ene自身の承認ボタンや設定画面を勝手に操作し、ユーザーの操作を偽装することは厳格に禁止します。
- **受渡内容**: 対象、操作内容、データ、送信先、作用との対応関係、MCPの非秘密接続設定、実行コマンド、設定の由来、プラグインの限定拡張ポイントへの受け入れ・有効化・利用状況、MCP Appsの一時的なツールUIとMCP側の作用・データ授受の制限。
- **外部プロセスの限界**: ローカルMCPに対するサンドボックス外例外は、権限・制約機能が管理する個別の隔離例外であり、プラグインへの勝手な流用や個々のアクション承認への転用は禁止します。外部プロセス内部への完全な強制力や、確実な停止を保証したかのように偽って報告してはいけません。外部プロセス内部で何が起きたか確認できない作用は、すべて「結果不明」として扱います。リモートMCPの内部は外部の管理下にあり、ローカルサンドボックスと同じ強制力や確実な停止・ロールバックを保証することはできません。Eneが仲介するアクションの制限は厳格に保ちますが、外部プロセスの内部にまで同じ強制が及んでいるかのように偽って表示してはいけません。
- **結果の受入れ**: ツールや拡張機能自身が、権限（Permission）、認証情報（Credential）、マスターデータ（canonical state）の決定権を持つことはありません。外部コードやその実行結果を、無条件に信頼された制御指示（control）として扱ってはいけません。ツールが動かないからといって、サンドボックス隔離を黙って勝手に解除してはいけません。MCP Appsの操作は外部ツールUIの一時的な入力に過ぎず、公式（第一者）の制御変更や権限承認を直接成立させることはありません。ツールUIの表示、終了、再表示を、タスクやサーバー、アクション自体の終了や再実行のトリガーにしてはいけません。

### K-10 Client依存作用の限定と移動・切断との接続

- **判断**: Computer Use（画面操作など）を実行するためには、接続・存在機能が管理する最新の滞在帰属と、権限・制約機能が管理する端末許可の両方が必要です。Hostが動作しているPC自身であっても、Host上のクライアントに当該コンパニオンが滞在しているときのみ操作対象になります。タスクエージェントが操作対象のクライアントを勝手に選ぶことはできず、端末移動の要求は個体調整機能および接続・存在機能の責任へと戻します。
- **受渡内容**: 委任元コンパニオンが現在アクティブに滞在しているクライアント端末、端末ごとの操作許可、アクションの権限チェック、実際の利用可能性がすべて同時に満たされていること。端末移動時の安全な区切りと、切断時におけるベストエフォートでの停止要求を接続・存在機能へ伝達すること。排他制御が確認できないクライアントにおいては、対象となる操作活動を直ちに停止すること。
- **失ってはならない前提条件**: 「現在のクライアントに滞在していること」は「アクションの実行を許可されたこと」を意味しないこと。環境観測（ambient Observation）が有効化されていることを、画面操作の承認とみなさないこと。移動先のクライアントが利用可能になったからといって、前のクライアントで結果が不明になったアクションを勝手に自動再実行しないこと。
- **結果の受入れ**: クライアント依存のアクションを実行している最中に端末移動や切断が必要になった場合、安全に処理を区切れるポイントまで移動の確定を遅らせることができます。端末を移動したことを理由に、元のクライアントで実行していたアクションを別のクライアントやHost上で勝手に自動再実行してはいけません。クライアントの切断に伴う停止処理はベストエフォートとし、停止できなかった処理、確認された作用、結果が不明な作用を正確にユーザーへ提示します。コンパニオン個体の移動と、未確定のアクションの再実行は完全に別問題として扱います。

### K-11 失効・停止・保留の伝播と遅延到着・不明の扱い

- **開始の契機**: 権限・制約機能における失効、個体調整機能における停止、保全・消去機能における保留などが成立した場合、各処理の開始箇所は自身がその対象に含まれているかを判定し、新規処理の開始を直ちに禁止します。複数の理由が重なっている場合、どれか一つの理由が解消されたからといって、他の禁止事項まで勝手に解除してはいけません。
- **判断**: 中断（Cancel）要求は、公式（第一者）の管理経路から作業機能へ直接届き、本体LLMやエージェントの正常終了を待つことなく直ちに受け付けられます。作業機能は対象タスクの遂行を停止し、実行・拡張機能は進行中の作用をベストエフォートで停止します。「停止要求を受け付けたこと」と「外部への作用が停止したこと」は明確に区別します。Hostのシャットダウンや再起動が発生した場合でも、処理の継続に必要な進捗、作用不明の記録、未伝達メモ、システム横断操作の未完了状態をHost側で確実に保全します。
- **受渡内容**: 停止要求、失効、保留の対象と理由。把握できた停止状況、成否不明な状態、確認された作用、未保存の作業内容。遅れて届いた処理結果と、元の要求アクションやタスクとの正しい対応関係。
- **失ってはならない前提条件**: 失効前の作用や判断記録を勝手に巻き戻さないこと。別のエージェント、別のクライアント、別のツールへと迂回して制限を回避しないこと。無関係なHost上の通常タスクまで一律に中断（Cancel）しないこと。「中断や失効が行われたこと」は「すべての事実報告を禁止する」という意味ではなく、逆に「事実を記録できたこと」が「次の処理を勝手に開始してよい理由」になるわけでもないこと。
- **結果の受入れ**: 中断（Cancel）、指示変更（steering）、失効、端末移動、削除、リストア復元などが行われた後に、ツールの実行結果、承認、推論結果が遅れて届いたとしても、次の実行を自動で開始してはいけません。必要な作用の客観的事実は元の要求アクションやタスクに対応付け、タスクとしての採用や達成の判断は現在のタスクに対応付けます。外部への作用が成功したか不明な場合は、自動で再実行することは決してせず、二重実行の可能性をユーザーに分かりやすく説明した上で判断を仰ぎます。ユーザーからの再開指示は、無条件の再実行許可ではなく、結果不明な各試行の重複リスクと最新の前提条件に照らして個別に扱います。報告、監査、復旧の各フェーズにおいて、事実の確定度を勝手に強めてはいけません。

### K-12 監査・説明の非秘密と確定度保持

- **開始の契機**: 各事実の発生元が必要な客観的事実のみを供給し、保全・消去サブシステムが監査ログ（Audit）の追記順序と保持期間を管理します。入出力・提示機能がそれをユーザーへ説明します。
- **判断**: 元の記録の意味は発生元に残り、監査ログの記録順序を外部世界の絶対的な発生順や現在の許可ルールのマスターデータへと昇格させてはいけません。監査記録を元にして過去の処理を再生したり、自動実行の入力として使い回したりしてはいけません。
- **受渡内容**: 主要なアクション、権限判断、外部への作用、プロバイダ割り当て、認証情報の参照、重要な設定変更などの客観的事実。秘密を含まない識別参照、キー失効、認証失敗の事実。利用コストについて確定報告値、推定値、不明の区別。
- **禁止事項**: 監査ログ、デバッグ記録、診断情報の共有データの中に、会話テキスト、ファイル本文、パスワードなどの秘密値、削除されたプライベートな内容を通常時から含めること。完了記録や監査ログ自体を、削除データの復元源にしてしまうこと。デバッグ記録に登録済みの認証情報値を含めること。
- **結果の受入れ**: 由来、失敗、停止不能、未保存の変更、次の安全な選択肢などは、内部の思考ログや詳細なプロンプト本文を晒すことなく説明します。デバッグ記録は、ユーザーが明示した対象・内容、および短期失効・停止・削除のルールに厳格に従います。テレメトリやクラッシュレポートを外部へ自動送信することは決してせず、手動で共有する場合もユーザー自身が内容と送信先を確認して行います。

## 5. Lifecycleとの関係

ライフサイクルの変更の多くは、データの担当責任者（owner）が別の人間に移るのではなく、「同じ担当責任者が管理する状態について、存続期間・利用可能性・参照できる範囲が変化する」ことを意味します。目的の異なる複数の操作を、安易に一つの初期化処理や一つのステートマシン（状態遷移機械）にひとまとめにして混同してはいけません。

| 事事象 | 本クラスタ（権限・秘密・実行・推論）が変更する意味 | 独立して維持・分離すべき意味 |
|---|---|---|
| Ruleの保存・変更・Undo | 権限・制約機能が、解釈、適用範囲の提示、ユーザー確認を経て制御条件を変更します。ルールが保存されたこと自体をアクションのトリガーにしてはいけません。 | 保存されたルールを自発的アクションのトリガーにしないこと。過去のアクション結果を勝手に書き換えないこと。AIモデルの出力だけでルールを直接変更させないこと。 |
| Provider接続登録・Credential登録・割当同意 | 推論機能が非秘密の登録情報を管理し、認証秘密機能が秘密値と用途を管理し、権限・制約機能が割り当て同意を確定します。登録や認証が成功したことだけを理由に、送信やアクションを自動開始してはいけません。 | 接続登録＝同意、認証成功＝同意、認証成功＝アクション承認とみなさないこと。プロンプト内の許可文をマスターデータにしないこと。 |
| Task Agentの委任開始・再委任・並列化 | 権限・制約機能の最新条件、委任範囲、共通の利用上限枠への参加を維持します。推論機能は担当コンパニオンの条件を継承し、実行・拡張機能は作用と確定度を委任関係に対応付けます。 | エージェント独自の独立した許可、認証情報、プロバイダ上書き設定、予算枠、長期的な人格、関係性、独自スコープの記憶を作らないこと。別タスクの承認や認証情報、前任者の私的な学習内容を勝手に流用しないこと。 |
| 追加指示（steering） | 権限・制約機能が目的や対象などの重要な変更の有無を判定し、実行・拡張機能は過去の判定の再利用可否を扱います。変更前の古い指示に対する遅延結果を、新しい指示の達成結果として自動採用してはいけません。 | 発言記録（個体調整機能）、タスクへの反映（作業機能）、承認の有効性（権限・制約機能）を明確に分離すること。古い承認を使って中断（Cancel）や失効を勝手に解除しないこと。 |
| Cancel・個体停止 | 権限・制約機能と各実行箇所が新規処理の開始を止め、作業機能のベストエフォートでの中断と、実行・拡張機能による停止不能・確認済み・成否不明な作用の報告へとつなぎます。停止処理の名目で新しい未承認アクションを開始してはいけません。 | 要求受付と処理完了を分離すること。無関係なHost上の通常タスクまで一律に中断しないこと。停止前の作用記録や判断ログを勝手に巻き戻さないこと。 |
| 許可・同意・Credential・deviceの失効 | それだけを根拠とする新しいアクション、データ送信、保存、画面提示の開始を直ちに禁止します。依存している進行中の処理はベストエフォートで停止します。 | 別エージェント、別クライアント、別ツールへ迂回して制限を回避しないこと。無関係なHostタスクを一律に中断しないこと。 |
| 費用cap到達・費用不明 | 既存のデータを安全に保持したまま、対象処理を停止してユーザーの判断待ちにし、選択肢を提示します。処理中、遅延報告、成否不明な消費を勝手にゼロとして扱ってはいけません。 | 既に行われた作用の取消成功やデータの勝手な破棄にすり替えないこと。保存容量不足を通常の学習内容の削除で勝手に解決しないこと。使用量実績をリセットしないこと。 |
| Task終了・Task Agent終了 / 失敗 | 実行・拡張機能が把握した作用や確定度をタスクに対応付け、推論機能の利用実績を共通の上限枠へ反映します。エージェント自身の終了と、タスク全体の達成を明確に区別します。 | タスク記録、コンパニオン、スケジュールを勝手に削除しないこと。エージェントが長期的な人格を残さないこと。エージェントの自己申告だけで成功を確定しないこと。 |
| Client移動・切断 / activeなし | 実行・拡張機能がクライアント依存作用の安全な区切りや成否不明な状態を接続・存在機能へ伝達し、推論機能は前の滞在先のコンテキスト、キャッシュ、セッションを新しい滞在先で使い回しません。クライアントに依存するステップのみを判断待ちにします。 | コンパニオン個体、Host上の通常作業、内部状態の担当責任者を移転させないこと。未確定のアクションを移動先で勝手に再実行（replay）しないこと。Host作業をクライアントへ移送したり一律停止したりしないこと。 |
| Host再起動 | 推論機能における過去の要求の実利用許可や過去の実行を勝手に再開しません。実行・拡張機能における成否不明な状態を勝手に「未実行」に戻しません。中断されたタスクは明示的な再開指示を待ちます。 | 過去の作用不明、未伝達メモ、未完了のデータ消去を「なかったこと」にしないこと。滞在先（presence）が復旧したことだけを理由にタスクを自動再開しないこと。 |
| Provider / model変更・障害・cache失効 | 推論機能が利用可能性、能力、承認済みの通信経路を適切に扱い、同じ情報選択方針と安全境界を維持します。接続が回復したからといって、過去のアクションを勝手に再実行しません。 | コンパニオン、会話履歴、学習内容などを初期化しないこと。プロバイダのセッションやキャッシュにコンパニオンの状態を依存させないこと。 |
| Targeted deletion | データを保持・利用する各機能が、派生データや遅れて届く結果に至るまで完全消去へ参加し、削除対象の本文テキストを作用記録や監査ログに残しません（第7.3節）。機械的な条件検証はLLMに依存せず、補助推論にも自身の利用条件を適用します。 | 通常のデータ担当責任者を移転させないこと。消去完了後にユーザーから新たに提供されたデータや、外部にバックアップされたコピーの消去保証とは明確に区分すること。 |
| Backup / restore | データのコピーを作成し、ユーザーからの明示的なリストア要求が成功した際には、現在の認証情報ストアを除く対象内部データをバックアップ時点の状態へと一括全置換します（第7.5節）。復元された役割割り当て、同意設定、セキュリティルールが存在することだけを理由に、自動で処理を開始してはいけません。 | バックアップコピーは現在動いているマスターデータではないこと。復元後も実行は一時保留され、外部の世界は巻き戻らないこと。認証情報は現在の安全なストアを維持して照合すること。 |
| 設定Reset / 全データReset | 設定のリセットは一般設定を既定値に戻す操作であり、全データのリセットは厳重な確認を経た上で内部データや認証情報を完全に削除する操作です。各設定の担当責任者が既定値への復帰と保護対象データの保持を確認します。 | 設定リセットで保護すべきデータ（個体、履歴、学習内容、タスク、スケジュール、認証情報、ルール、同意、コスト上限）と、全データリセットで外部に残すべきデータ（外部ワークスペース、外部スキル、ユーザーが保存したバックアップ）を混同しないこと。 |
| Schedule到来・Run now | 作業機能が担当コンパニオンやHostの状態、最新の前提条件を確認し、各回の処理を「新しいタスク」として対応付けます。スケジュールの作成依頼を永続的な実行許可証とみなしてはいけません。 | 停止中に予定時刻を過ぎた回はスキップ（missed）のままとし、自動補完しないこと。ユーザー確認が必要な場合は勝手に実行せず判断待ちを維持すること。 |

全体共有（Global）として形成・変更された学習内容は、その後に元のコンパニオン個体が削除された場合でも、全体共有の知識として安全に残ります。ただし削除の際には、なぜその知識が残るのかという根拠と、元のコンパニオンという情報源が失われることをユーザーに分かりやすく説明します。一方で、相手との関係性（Relationship）や一時的なコンパニオン状態（Companion State）は、スコープ変更による共有対象にはならず、常に個体に固有です。

## 6. failure / cancellation / restart時の責任

タスクが中断（Cancel）されたり通信が切断されたりしたことだけを理由に、「外部への作用が取り消された」「最初から作用などなかった」と勝手に都合よく推測してはいけません。また、結果が不明な処理を勝手に「未実行」に戻してはいけません。内部の状態を参照したことや、クライアント間を移動したことなどを口実に、アクションを勝手に再実行（replay）してはいけません。

- **権限・制約**: 権限失効、コンパニオン停止、コスト上限到達、保留の発生を、新規処理の開始禁止へと確実に接続します。古い判定結果や解決済みの通信経路だけを頼りにして新規利用を開始させてはいけません。事実の報告や中断要求の受付を、次の許可待ちに戻して止めてはいけません。制約を判断するために、審査対象のアクションを先に実行させてはいけません。並行処理、タスクの委任、別経路を通じた利用であっても、全く同一の制限を成立させます。補助的な推論が失敗したからといって、機械的な権限検証、安全停止、操作の拒絶、管理機能へのアクセスを塞いではいけません。
- **認証秘密**: 認証失敗、キーの失効、再認証の必要性を、秘密の生値を含めずに速やかに伝え、現在の安全な認証情報ストアの維持と復元参照の照合を確実に保ちます。認証先のエラーメッセージやレスポンスによる秘密の反射を、通常のデータ経路へ通してはいけません。データを受け入れ・保存・表示する各機能と連携して非露出を徹底します。内部に露出した認証情報コピーの消去と、外部サービス側で有効なAPIキーの失効・更新は、別の操作としてユーザーに説明します。
- **実行・拡張**: 進行中の作用のベストエフォートでの停止と、確認された作用、停止不能だった処理、成否不明な状態、未保存の作業内容の安全な保持・報告を引き受けます。停止要求の受付、新規開始の禁止、状態の参照を、外部プロセスの終了や全タスクの正常終了待ちにして遅らせてはいけません。試行と作用の区別、判断・目的・実際の対象・処理段階・確定度・停止保留との対応関係を保持・区別できなければ、成功や未実行と勝手に推定してはいけません。確認された失敗と成否不明な状態を、安易に同じ再試行経路へひとまとめにしてはいけません。成否不明な試行の再実行には、重複のリスクを明示した上でのユーザー自身の判断を必ず求めます。
- **推論**: プロバイダの通信失敗、能力不足、コスト不足が発生した場合に、成功したかのように捏造した結果を返すのではなく、呼び出し元へ不足、失敗、成否不明の状態を対応関係とともに正確に返します。許可されたフォールバックを行う際もK-5およびK-6の安全ルールを厳格に適用し、既存のマスターデータを保護します。利用量の確定報告値、推定値、成否不明、処理中の消費という対応関係を途中で切断してはいけません。判定が行われてから実際にデータ送信されるまでの前提条件の変化を、古い判定結果で迂回させてはいけません。
- **共通の原則**: 要求の受付、処理の開始、外部への作用、記録の保存、タスクの達成、ユーザーへの報告は、すべて別々の客観的事実であり、安易に「一つの成功」としてひとまとめに混同してはいけません。事実の確定度を変更する場合は、その事実の担当責任者が新たに直接確認した客観的な証拠に基づかなければなりません。バックグラウンド作業やスケジュールによる無人実行も全く同じ条件に従い、クライアントが不在であること、予定時刻が到来したこと、システムの復元が成功したことなどを理由に、必要な権限を自動承認してはいけません。ユーザーによる確認が必要な操作は、勝手に実行せず必ず判断待ちにします。管理経路は、LLMの機嫌、長時間タスクの完了、デスクトップ動作（Body）、音声合成（Voice）、外部拡張機能の成否などに一切従属させません。

障害からの再構築が可能であるということは、「すべての会話文脈や内部の推論ログを永遠に丸ごと保存しなければならない」という意味ではありません。処理を安全に継続するために必要な作用不明の記録、システム横断操作の未完了状態などを本来の担当責任者が安全に保全していれば十分です。一時的なメモリバッファが消失したことを、タスクの成功や完了の根拠にしてはいけません。

## 7. Step 11 contractへの参加

各契約の一般的な条件は第0節に挙げた重要領域ドキュメントに定義されており、本書では重複を避けて再掲しません。本節では、権限・制約、認証秘密、実行・拡張、推論の各機能が提供・参加する固有の約束事項のみを記載します。

### 7.1 Context Assemblyへの参加

- **権限・制約**: ユーザーに由来する制御ルール、同意設定、明示的な非共有・保存禁止指示、および現在の利用条件を、各担当機能の客観的事実と照合します。コンテキスト内だけで勝手に更新できるような許可フラグ、同意、スコープの意味付けは持ちません。権限解釈を用途別に受け入れる際は、元のユーザー意図と操作対象を正しく照合して制御上の判断を確定します。「AIモデルが許可した＝セキュリティ制御が更新された」とみなしてはいけません。また、「一度許可された＝将来に向けた恒久ルールである」とみなしてはいけません。
- **認証秘密**: 認証用途に限定して秘密情報を供給し、通常のコンテキストへ秘密値を渡すことは決してありません。認証先のエラーメッセージやレスポンスが登録済みの認証情報を反射してしまう経路に対しても、受け入れ、変換、推論利用、送信、保存、画面提示、完全消去を含むすべてのデータ取り扱いにおいて非露出を徹底します。「送信前にプロンプトに入れなかったこと」だけをもって、保護が成立したとみなしてはいけません。
- **実行・拡張**: 外部ファイルやMCPリソースの取得は、既存のセキュリティ境界を厳格に通します。取得した案内ファイル、スキル、MCPプロンプトは、その由来を保持した単なるコンテンツとして利用し、そこに含まれる指示文をユーザー自身の管理操作へ勝手に昇格させてはいけません。作用や利用量などの必要な客観的事実は、本来の担当責任者が元の利用やアクションへ対応付けます。タスク中断後はすべての事実を破棄してはならず、「結果不明＝未実行」とみなしてはいけません。また、「事実を記録できた＝後続処理を実行可能である」とみなしてはいけません。
- **推論**: 最新のモデル割り当ての解決、プロバイダの能力への適応、データ送信、利用量や失敗の対応を担います。「利用元が用途と論理的な情報選択を担当し、情報担当機能が現在の内容・根拠・スコープを担当する」という構造を維持します。プロバイダごとに独立したコンパニオン像を勝手に作ることなく、制約の範囲内で同じ選択方針を適用します。最初の送信、フォールバック、再送、補助推論、継続部分の各々を実際の利用として成立させ、事前に解決された送信先を、独立した設定のマスターデータや無制限の送信許可と誤認してはいけません。キャッシュ、セッション、通信経路の再利用時であっても、範囲、用途、現在性を必ず再確認し、キャッシュヒットを理由に制約の確認を省略してはいけません。権限解釈やデータ消去探索の補助推論も例外とせず、審査対象となっているアクションの許可や実行を先行条件にしてはいけません。
- **共有観測（Observer）**: 専用の割り当てに対する送信条件と、元情報が持つ利用制約の両方を満たして参加します。コンパニオン側の上書き設定や同意を勝手に選んで組み合わせ、代用してはいけません。

### 7.2 Action Executionへの参加

- **権限・制約**: 認可判断（ユーザーに由来する意図・ルールと具体的なアクションとの対応、ユーザー確認の要否、現在の利用可否）を正式に確定します。判断対象と実際の利用との対応関係を安全に保持、またはマスターデータから解決できるようにし、必要な対応関係を失ってしまった要求は実際の作用へと進めません。「判断の記録」と「生きた許可」を明確に分け、重要な変更が発生した場合は必ず再評価を行います。判定のために行う補助推論に対しても、その推論自身の利用条件を正しく適用します。
- **認証秘密**: 接続、用途、有効性の照合と、必要最小限の範囲での秘密利用を担当します。認証情報への参照は秘密を含まない用途識別子であり、AIモデルがプロンプト内で記述しただけでは利用可能になりません。認証先のエラーメッセージやレスポンスが秘密を反射した場合であっても、通常のツール結果、説明文、会話履歴、学習内容、監査ログ、デバッグ記録へ流出させません。アクションの承認、同意、実行可否の確定権限は持ちません。
- **実行・拡張**: 実際の操作対象に対する制限された作用、停止結果、確認できた作用と確定度を管理します。処理の開始ごとに、該当する最新の条件を実際の対象へ適用します。実際の対象解決プロセスを経て対応関係を確認し、解決できない場合や対応しない場合は処理を開始しません。
- **推論**: 補助推論やフォールバックを含め、各実利用の成立と、利用量・失敗結果の返却を担当します。推論の失敗やコスト不明が発生した際に成功を捏造することなく、不足や判断待ちを返します。推論における承認済みフォールバックを、外部への作用が不明な場合の再実行の口実にしてはいけません。通信プロトコル上のパケット再送と論理的な試行を明確に区別し、重複のリスクがある再送を「同じ試行の単なる継続」として成否不明・重複管理から勝手に除外してはいけません。

### 7.3 Targeted Deletionへの参加

- **権限・制約**: ルール、権限判断ログ、同意、禁止事項、利用上限枠の記録の中から、対象となる個人情報を完全に消去します。過去に保存された許可ログや判定コピーを、現在の条件として再利用してはいけません。データ利用時のセキュリティ強制として、参照、変換、送信、保存、提示、作用の各ポイントで消去条件を確実に適用します。コンテキスト内の自由記述テキストだけで消去制約を勝手に解除できるような穴を作ってはいけません。
- **認証秘密**: 登録済み認証情報の用途、有効性、除外ルールを適切に処理し、会話履歴、サマリー、記憶、タスク結果、ログ、デバッグ記録などへ誤って露出してしまった認証情報のコピーを、各機能と連携して完全に消去します。内部に露出したコピーの消去と、外部サービス側で有効な認証情報の失効・更新は別の操作として説明し、片方が完了したからといって他方も完了したと誤認させてはいけません。消去対象であることを理由にして、外部サービスのAPIキーを自動で失効させるような処理は行いません。
- **実行・拡張**: 把握した作用の記録や確定度の中から削除対象の本文テキストを除去し、必要な客観的事実の記録と両立させます。データ消去が行われたことを理由に、過去の作用の確定度を書き換えてはいけません。内部に取り込んだ結果、保持している結果、一時データを消去に参加させます。「外部コードだから」と言い訳して対象外に逃がしてはいけません。ただし、外部サーバーが保持しているコピーの消去まで内部完了の保証に含めてはいけません。
- **推論**: Eneの管理下にあるキャッシュ、ベクトルデータ（embedding）、検索結果、圧縮されたコンテキスト、セッション、派生データを消去に参加させます。キャッシュにヒットしたことだけを理由にして、元のデータ参照やセキュリティ制約の確認を省略してはいけません。AIプロバイダ側が外部で保持しているコピーまで内部消去の保証に含めないことと、その外部コピーをEneが勝手に再利用してよいことは別問題であり、現在の条件を満たせない古いセッションを再利用してはいけません。データ消去のための補助推論を行う場合であっても、その推論自身に対する割り当て同意、認証用途、利用コスト制限を正しく適用し、推論が利用できない場合は意味判断の不足として処理します。

### 7.4 Client Presence Transitionへの参加

- **権限・制約**: ペアリング許可、端末許可、プロバイダ同意、コスト上限、失効の現在の有効性を確定し、各利用箇所がそれを適用します。端末への滞在帰属の成立、タスク達成、作用成功の勝手な確定権限は持ちません。古い一時データから、現在の許可、同意、スコープを勝手に復活させてはいけません。
- **認証秘密**: 接続情報や認証情報の用途、有効性、除外ルールを扱い、滞在帰属、許可、実行可否の確定権限は持ちません。クライアント固有の接続材料の秘密保護に参加します。
- **実行・拡張**: 実際の対象への作用、停止結果、確認できた作用と確定度を管理し、移動中や切断中に届いたメッセージや結果を元の滞在帰属、元の会話ラウンド、元の試行に対応付けて用途別に受け入れます。許可の付与、タスク達成の判定、移動可否の判定権限は持ちません。
- **推論**: 前の滞在先のコンテキスト、キャッシュ、セッションを、新しい滞在先の最新コンテキストとして使い回してはいけません。プロバイダのセッションに前の滞在先の情報が残っている場合、現在使えない情報を含むセッションへの新規依頼は、現在のコンテキストを短く渡すだけでは成立させません。滞在帰属の判断や移動可否を判定するためのAI推論が通信不通やコスト不足になった場合でも、未承認のアクションや無条件の移動を勝手に先行実行してはならず、不足の状態を管理面へ返します。

### 7.5 Backup / Restoreへの参加

- **権限・制約**: 拒絶（Deny）、同意、コスト上限、失効、保留状態の最新の有効性確認と、保留解除の確定を担います。復元された過去の許可条件の記録が存在することだけを理由に、直ちに処理を開始してはいけません。保留を解除した後であっても、現在の認証情報の利用可能性、拒絶ルール、機能境界、同意範囲、コスト上限、成否不明な外部作用などを必ず再評価します。「復元が成立したこと」と「処理の実行を再有効化すること」は明確に分離して確認します。
- **認証秘密**: リストア開始前の安全な認証情報ストアを維持し、接続設定の担当機能と復元された参照を現在の用途・有効性と照合します。バックアップから秘密情報を勝手に復元したり巻き戻したりしません。利用可能であれば現在の安全なキーを使い、不足や無効があればユーザーへ再認証を要求します。復元された割り当てや同意情報が存在することだけを理由にして、現在の認証情報、制約、リストア直後の保留状態を無視して自動処理を開始してはいけません。
- **実行・拡張**: 復元されたデータ内容の参照および利用可能性の確認に参加し、リストア前に動いていた古い稼働状態の処理、遅れて届いた結果、クライアント側の一時コピーを、復元後の新しいマスターデータと混同しない前提条件を揃えます。
- **推論**: 復元された古い接続情報、能力観測結果、割り当て解決を、現在の利用可能性とみなしてはいけません。最新の割り当て、接続設定、能力、同意、コスト状況を照合し、承認済みのフォールバックと優先順位のみを使用します。復元された過去の利用量報告値、推定値、成否不明、処理中の消費を、現在の消費残高のマスターデータにしてはいけません。未報告の利用量を勝手にゼロと扱わず、リストアを消費リセットの口実にしてはいけません。

## 8. boundaryを越える際に保持すべき意味

後続の詳細なインターフェースや状態表現の設計においては、特定のAPIや実装メカニズムを固定しなくても、システム境界をデータが通過する際に少なくとも以下の対応関係を正しく表現・解決・照合できなければなりません。「確認できない情報」を、勝手に「現在有効である」「許可されている」「完了している」と都合よく推定する方式は決して採用できません。

- **利用者と用途、担当コンパニオン、タスク・委任との関係、目的や指示（steering）の前提、元の入力・出来事・管理操作との関係、クライアント依存であれば取得クライアント・会話ラウンドや観測候補との関係、停止前と再開後・Host再起動前後・リストア前の稼働状態と復元後の活動を明確に区別できる継続関係、利用先**: （Context Assembly第3節の対応）。必要な対応関係を失ってしまった処理結果は、移動先の現在の活動へ勝手に付け替えてはならず、その用途では受け入れられないものとして利用元が安全に処理します。
- **実行主体と委任の連鎖、タスク・ワークスペースの範囲、目的、実際の操作対象と操作内容、使用する主なデータと用途、コストやリスク、依拠したユーザーの指示やセキュリティルール**: （Action Execution第3節の判断対象）。判断時に指示された対象の文字列と、実行時の実際の対象の文字列がたまたま一致しているだけでは、正しく対応が取れているとはみなせません。
- **試行（試み）と作用（実際の影響）の区別、判断・目的との対応、実際の操作対象との対応、処理段階の区別、確定度とその客観的根拠、停止・保留との関係**: （Action Execution第8節の二重実行防止の関係）。
- **秘密の生値と非秘密の参照・用途・有効性の厳格な区別、認証用途の限定、参照元と接続先の対応**: AIモデルがプロンプト内で勝手に記述した参照文字列だけで、秘密が利用可能になってはなりません。
- **割当同意・承認済みfallback順序・費用cap・端末許可・保存禁止・非共有と、現在の活動・委任・滞在帰属・利用量・保留状態との照合関係**: 過去に保存された許可ログ、判定コピー、解決済み経路、キャッシュされた判定を、現在の有効な条件と誤認してはいけません。
- **消去要求・対象の指定・消去対象期間との対応、各利用箇所が個別に照合できる消去条件**: （Targeted Deletion第3節・第5節）。単純な単一フラグや共通の有効値へと安易にひとまとめにして混同することは禁止します。
- **Hostが権限を持つ正規の帰属先と、クライアント側の一時的な表示や入力・結果が主張する帰属先との対応、現在・過去・帰属なし・停止中・復旧待ちの厳密な区別、対象コンパニオン・クライアント・会話ラウンド・観測候補・試行との関係、消去・失効・停止・保留との関係**: （Client Presence Transition第3節）。
- **復元の対応関係・由来・対象期間・完了境界、現在の前提条件との照合**: （Backup / Restore第3節・第5節・第7節・第9節）。

AIの思考に用いるテキスト本文と、セキュリティを強制するための制御情報を明確に分離し、強制側の制御フラグや権限情報がAIモデルの自由記述テキストによって勝手に作成されたり上書きされたりしないように保護します。テキストの中に「ユーザーからの指示です」「承認済みです」「全体共有（Global）です」という文字列が含まれているからといって、それだけで制御側のステータスが変わってしまうような脆弱な設計は禁止します。モデルが過去のユーザー入力への参照を示せたとしても、その参照が存在すること自体は承認の客観的な証拠にはなりません。

パスワードやAPIキーなどの認証情報（Credential）の生値は、通常の会話テキストやコンテキストに含めてはいけません。登録済みの認証情報値は、たとえユーザーからの明示的な指示があったとしても、サマリーや記憶（Memory）へ保存してはいけません。用途、参照元、失効、再認証などの説明は、秘密情報を含まない安全な形式で行います。事前に登録されていない秘密情報が検知された場合も、不要な保存や送信を抑制する安全策を維持しますが、完全な自動検知を保証することは求めません。

## 9. 本書が固定する契約と残す Design Freedom

下位の詳細設計は、以下の項目を本書が固定した不変の契約として利用できます。

- **ユーザー意図の解釈とセキュリティ制御変更の厳格な分離**: ユーザーの意図の解釈と、制御変更の確定は別物であり、生成されたコンテンツや保存済みコンテンツから新しい権限を勝手に新設することはできません。「判断の記録」と「生きた許可」は別物であり、処理を開始する直前に最新の前提条件と実際の操作対象の解決を必ず成立させ、重要な変更が発生した場合は必ず再評価を行います。ただし、無関係な軽微な変更で都度再承認を求めることはしません。
- **学習スコープとセキュリティ強制の分離**: 学習内容のスコープの意味付けは「認識・学習」機能に残り、決定された制限を迂回不能に強制する責任は権限・制約機能と各利用機能の協調に属します。秘密の生値と非秘密の識別参照は別物であり、認証用途に限定して秘密を利用し、通常のデータ経路へは絶対に流出させません。
- **推論割り当ての派生性とフォールバックの厳格性**: 推論の割り当て解決は一時的な派生データであり、実際の利用ごとに最新の用途、データ範囲、ユーザー同意、認証情報、利用コスト、保留状態を必ず照合します。フォールバックは事前に承認された候補と優先順位に厳格に従い、候補ごとに最新の前提条件を照合します。未承認のクラウドへの勝手なデータ送信や、安価であることを理由にしたセキュリティ例外は一切認められません。
- **委任による権限拡大の禁止**: タスクの委任や呼び出し経路の変更によって、元のタスク、ユーザーの意図、権限、ワークスペース、クライアント端末の境界を勝手に広げてはいけません。タスクエージェントに独立した許可、認証情報、プロバイダ上書き設定、予算枠を持たせることはできません。AIの生成コンテンツ、ツールUIへの入力、サンドボックスの個別例外から、新しい権限を勝手に作り出してはいけません。
- **事実の客観性と確定度の保持**: 要求の受付、処理の開始、外部への作用、内部記録の保存、タスクの達成、ユーザーへの報告は、すべて別々の客観的事実であり、通信が成功したことやツールが「完了しました」と申告したことだけを理由に「作用が成功した」とみなしてはいけません。試行と作用、判断、実際の対象、処理段階、確定度、保留状態の対応関係を保持・区別できなければ、成功や未実行と勝手に推定してはいけません。
- **拡張機能への均一なセキュリティ強制**: 外部拡張に対してもすべての実行経路で全く同一のセキュリティ強制ルールを適用し、ツールや拡張機能自身が権限の決定権を持つことはありません。外部プロセス内部への完全な強制力や確実な停止を保証することはできません。確認できない作用は、すべて成否不明として安全に保持します。
- **Computer Useの厳格な滞在制限**: 操作を行うコンパニオンが現在アクティブに滞在している端末のみに対象を限定し、安全な区切りまでの遅延、切断後の成否不明の安全な保持、別の端末やHostでの勝手な自動再実行の禁止を徹底します。「滞在していること」は「アクションの実行を許可されたこと」を意味しません。
- **中断・変更・失効時の安全な対応**: 中断（Cancel）、指示変更（steering）、権限失効の後に遅れて届いた結果は、元の要求アクションやタスクへ正しく帰属させ、過去の古い承認を使って制限を解除したり、古い作業結果を新しい目的の達成として勝手に採用したり、後続処理を自動開始したりしてはいけません。成否が不明な作用は確実に維持し、勝手に自動再実行してはいけません。リトライや再開は「新しい試行」として最新の前提条件の下で扱い、成否不明な試行の再実行には、重複のリスクを提示した上でのユーザー自身の判断を必ず求めます。
- **利用実績の正確な管理**: 利用実績の元の生記録は各利用機能に残し、権限・制約機能がそれらを同一の上限枠へ正しく結び付けます。並行処理、処理中の消費、成否不明な消費を同一の上限枠へ正しく反映し、利用実績を勝手にリセットしてはいけません。
- **完全削除とリストア復元の安全性**: データを保持・利用する各機能は、消去処理中に新しく届いたデータの取り込み防止、再保存の防止、未完了状態の安全な保全に責任を持って参加します。復元されたデータの範囲と、それが現在も有効であるかどうかの再確認は明確に分離して行います。データが復元されたことだけを理由に「直ちに実行可能である」とみなすインターフェースは採用できません。
- **監査・説明の非秘密性と確定度の保護**: 報告、監査、復旧の各フェーズにおいて、事実の確定度を勝手に強めてはいけません。削除対象となった本文テキストを、作用記録や監査ログの中に残してはいけません。パスワード等の秘密値を監査ログ、デバッグ記録、バックアップファイルへ流出させてはいけません。

本書が明確に禁止し、除外するアンチパターンは以下のとおりです。
- すべての設定や学習内容を一つの編集可能なコンテキストへ集約すること
- 委任元の前提条件を作業エージェントへ丸ごと無批判にコピーすること
- 権限拒絶（Deny）されたアクションを同等の別のアクションで迂回すること
- 内部の管理機能へツール経由で裏から回り込んでアクセスすること
- 古い判定結果、キャッシュされた許可、解決済みの通信経路を使って新しい処理を開始すること
- 成否不明な処理を勝手に未実行・失敗・成功へと変換して自動で再実行（replay）すること
- 遅れて届いた結果を新しい目的の達成として勝手に採用すること
- 過去の古い承認を使って中断（Cancel）・失効・クライアント移動を解除すること
- AI推論の結果からセキュリティ制御や権限ルールを直接変更すること
- パスワード等の秘密値を通常のデータ経路へ混入させること、プロンプト内の参照記述だけで利用可能にすること
- 未承認のクラウドプロバイダへ勝手にフォールバックすること、上書き設定を勝手に解除してデータ送信を拡大すること
- タスクエージェントに独立した予算枠やプロバイダ上書き設定を作ること
- サンドボックスを黙って勝手に解除すること、ローカルMCPの個別例外をプラグインへ流用すること、ツールUIへの入力を公式承認とみなすこと
- 外部プロセスの内部にまで完全なセキュリティ強制が及んでいるかのように偽って保証すること
- クライアント側の一時コピーでHost側のマスターデータを上書きすること、未伝達通知を勝手に再キューイングすること
- 古い根拠から知識を勝手に自動再形成すること、キャッシュヒットを理由に制約確認を省略すること、プロバイダセッションを無条件に再利用すること
- 確認できない処理を成功とみなすこと、部分的なデータだけで勝手にマスターデータとみなすこと、権限の確認を後回しにして処理を先行復活させること、未完了なのに完了と表示すること
- 要約や復旧を行う際に事実の確定度を勝手に強めること

いずれも上位のセキュリティ原則や整合性を破壊するため、決して採用できません。

## 10. 横断検証

要件定義（requirements）、上位アーキテクチャ設計、重要領域（critical-area）の契約、および他のサブシステム設計に対する整合性の横断検証は以下のとおりです。単に固定のテストシナリオを網羅するだけでなく、正常系に加えて、本クラスタにとって特に重要な障害、データ鮮度の低下（stale）、中断（cancellation）、再起動（restart）、データ削除（deletion）のケースを選定して検証を行います。

[Action Execution](../critical-areas/action-execution.md)第10節で定義された検証シナリオは、K-8〜K-12の実行・強制ルールを通じても全く同じ結果を達成しなければなりません。本節では、権限・秘密・推論に固有の交差部分のみを記載します。

| 検証領域・交差部分 | 検証シナリオと達成すべき結果 | 本書における成立根拠 |
|---|---|---|
| 委任されたファイル操作作業の正常系 | ワークスペースフォルダの指定 → タスク化 → エージェントへの委任 → 権限認可の判断 → 実際の操作対象の解決 → 安全な作用の実行 → タスク達成 → ユーザーへの報告、という一連の流れがそれぞれ独立して完結します。エージェント自身の自己申告を作用の客観的証拠にせず、ワークスペースへの既定保存や、最終保存前のユーザー確認を厳格に守ります。ファイル削除、シェルコマンド、ネットワーク通信、MCP、ワークスペース外アクセス、パストラバーサルを確実に拒否し、決して迂回させません。 | K-8・K-9、第2節・第6節。要件RF-02、横断関心事CC-01・CC-07、状態所有SO 4.10〜4.13・4.19・4.22を維持。 |
| 秘密情報の非露出： 明示的な記憶指示と登録済み認証情報 | ユーザーから「このAPIキーを覚えておいて」という明示的な依頼があった場合でも、登録済みの認証情報値をサマリーや記憶（Memory）へ保存しません。プロンプトコンテキスト、ツール引数、会話履歴、タスク結果、ログ、監査ログ、デバッグ記録、バックアップファイルへ秘密値を流出させません。一方で、正規の認証用途における利用は安全に成立します。 | K-4、第2節〜第3節。要件共通推論区間、CC-02、SO 4.21を維持。 |
| 利用量と利用コスト： 報告値・推定値・不明の区別 | プロバイダからの確定報告値と、Eneによる推定値や成否不明な状態を混同せず、並行処理、処理中の消費、成否不明な消費を同一の上限枠へ正しく反映し、使用量を勝手にリセットしません。コスト上限到達や費用不明が発生した場合は、データを安全に保ったまま処理を停止し、ユーザーの判断待ちにします。 | K-7、第3節〜第4節。CC-06、SO 4.20を維持。 |
| タスクエージェント委任： 別経路でのDeny迂回、別タスクの承認・認証情報の流用、独立予算 | 委任の連鎖、実際の操作対象の制限、共通の利用枠の適用により、あらゆる迂回経路を塞ぎます。エージェント独自の許可、認証情報、プロバイダ上書き設定、予算枠を作ることは決してありません。軽微なアクションであっても全く同じ境界ルールに従います。 | K-8、K-7、K-4。CC-01・CC-02を維持。 |
| プロバイダのフォールバック： 未承認クラウド・上書き解除・安価さの例外防止 | ユーザーが事前に承認したプロバイダと優先順位のみを使用し、候補ごとに最新の前提条件を照合します。ローカル環境やLAN環境から、未承認のクラウドへデータを勝手に移送しません。共有観測（Observer）に対してもユーザー同意、プライバシー保護、費用上限を厳格に適用します。 | K-6、第2節・第4節。CC-01・CC-02、SO 4.18・4.19を維持。 |
| 補助推論の失敗： 権限解釈や消去探索におけるプロバイダ不通 | 補助推論が利用できない場合でも、未承認のアクションを勝手に先行実行することは決してなく、不足の状態を管理面へ返します。安全停止、操作の拒絶、機械的な残存検証は推論なしで確実に継続できます。審査対象のアクションの許可を、実行の先行条件にしません。 | K-5、第7.1節・第7.3節。CC-01・CC-06を維持。 |
| MCP Appsおよびサンドボックス例外を経る作用 | ツールUIへの入力を勝手に権限承認とみなさず、ローカルMCPのサンドボックス例外を包括承認やプラグインへ勝手に流用しません。外部プロセスの内部で何が起きたか確認できない作用は成否不明として扱い、確実な停止や強制ができたかのように偽って報告しません。 | K-9。CC-01を維持。 |
| Observerの発言振り分け： 専用割り当てと個体側の同意の分離 | 共有の画面・発言検知は専用の割り当てで行い、発言振り分け後に各コンパニオンが思考する処理は、その個体の設定と同意に基づいてそれぞれ独立して成立させます。コンパニオン側の上書き設定を勝手に合成せず、利用量を二重計上しません。複数のコンパニオンの発言が混ざり合った文を無条件に配送しません。 | K-5、K-6、第7.1節。要件RF-03、CC-02、SO 4.16・4.18を維持。 |
| 監査ログとユーザー報告： 確定度の保持と秘密の保護 | 事実の確定度を厳格に保ったままユーザーへ報告し、未完了の作業や次に必要な判断を明示します。要約や演出によって勝手に成功へと確定度を強めません。監査ログやデバッグ記録へ、パスワード等の秘密値、会話本文、削除されたプライベートな内容を残しません。 | K-12、第7節。CC-07を維持。 |

横断関心事CC-01〜CC-07に対して維持すべき一般的な特性は、各重要領域ドキュメントの横断検証と完全に同一です。本書がさらに追加で保証するのは、以下の点です。
1. プロバイダ適応の一般契約を前提として利用し、アクション固有の判断へと情報選択のマスターデータ責任を勝手に移さないこと（CC-02）
2. 認証情報の非露出を、通常のデータ経路とは別の独立した仕組みで確実に維持すること（CC-02）
3. 作業エージェント独自の許可、認証情報、プロバイダ上書き設定、予算枠を絶対に作らないこと（CC-01、CC-06）

他のサブシステム設計との照合においても、各データの担当責任者は状態所有規則（SO第4節）の定義どおりに残り、本書のK-1〜K-12はその受渡しの対応付けを明確にしたものです。タスクエージェントがデータを所有しない原則、Observerの専用割り当て、スコープの意味付けとセキュリティ強制の分離、認証情報の非露出、フォールバックの迂回禁止、成否不明な状態の安全な保持に関する各契約は、すべての文書において完全に同一です。
