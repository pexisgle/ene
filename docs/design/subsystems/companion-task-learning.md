# Subsystem Detailed Design — 個体継続・対話調整 / 作業遂行・実行管理 / 経験に基づく認識・学習

本書は「Step 12: サブシステム詳細設計」として、互いに密接に関連する以下の3つのサブシステムを1つの緊密なグループとして詳細化します。

- **個体継続・対話調整**（以下、個体調整）
- **作業遂行・実行管理**（以下、作業）
- **経験に基づく認識・学習**（以下、認識・学習）

> [!NOTE]
> 本書内の `I-` / `W-` / `L-` で始まる番号は、本書内で各サブシステムの内部責務を参照するための識別子であり、製品要件IDではありません。
> また、`H-` で始まる番号は、本書内で定義するサブシステム間のデータ受け渡し契約（セマンティック・コントラクト）の参照番号です。

## 0. 位置付けと不変条件

上位設計との優先順位や、記述に矛盾が生じた場合の解決ルールは、[設計ドキュメント README](../README.md#設計文書の優先順位と信頼できる情報源) に従います。[Context Assembly](../critical-areas/context-assembly.md)、[Action Execution](../critical-areas/action-execution.md)、[Targeted Deletion](../critical-areas/targeted-deletion.md)、[Client Presence Transition](../critical-areas/client-presence-transition.md)（以下、Presence Transition）、[Backup / Restore](../critical-areas/backup-restore.md) の各ドキュメントで定義された一般契約は、すでに確定した上位ルールとしてそのまま利用し、本書で勝手に再定義したりデータの担当責任（オーナーシップ）を変更したりしません。なお、本書内で参照する `SO` は [State Ownership](../architecture/state-ownership.md) の節番号を指し、`CC` / `RF` は対応するアーキテクチャ設計ドキュメント（[成果物一覧](../README.md#artifact-一覧)）の契約IDを表します。

本書では、新しいデータの担当責任者や第2のマスターデータ、万能の「Manager」「Coordinator」「Runtime」「Policy Engine」、統一状態機械、共通コンテキスト層などを勝手に追加することは決してありません。

## 1. 選定理由

これら3つのサブシステムをまとめて設計する理由は、日々の経験（Experience）、作業の委任意図、タスクの軌道修正（steering）、実行結果、ユーザーによる訂正、記憶の共有範囲（スコープ）、未伝達メッセージの受け渡しにおいて相互に深く依存し合っているためです。これらを個別にバラバラに詳細化すると、同じ連携ルールが3箇所で重複して定義されてしまいます。同時に、この領域は、後続の実装者が誤って「単一の状態」「単一のライフサイクル」「単一のリビジョン管理」「一律のデータ保持ポリシー」へと安易にひとまとめにしてしまいやすい境界を最も多く含んでいます。

- **個体調整 と 作業 の分離**: この2つを安易に統合してしまうと、時間のかかる大きなタスクやユーザーの判断待ちによって日常の会話がブロック（占有）されてしまったり、タスクのキャンセル受付や過去の実行記録の確認が「AIモデル（LLM）の応答待ち」になってしまったりする深刻な問題が生じます。
- **タスク と スケジュール・外部ファイル の分離**: タスクそのもの、一時的なタスクエージェント、定期実行スケジュール、各回の実行履歴、ワークスペースフォルダの紐付け、外部ファイル、永続的な成果物、一時的な中間ファイルを1つの「タスク状態」にひとまとめにしてしまうと、「担当コンパニオンが削除された後も過去の作業記録を残す」「停止中にスキップされた定期実行を勝手に穴埋めしない」「外部ファイルを勝手に自分の所有物とみなさない」という重要な安全原則が破壊されてしまいます。
- **長期記憶（Memory）・スキル・関係性・感情・サマリー の分離**: メモリ、スキル、関係性（Relationship）、コンパニオンの個別状態（Companion State）、要約サマリーを、単一のデータスキーマや単一のリビジョン管理、一律の同時更新にまとめてしまうと、「客観的な事実認識の優先」「主体ごとの独自の解釈」「一時的な気分と持続的な態度の区別」「判断根拠の適切な分離」がすべて失われてしまいます。
- **会話履歴・サマリー・現在認識・派生データ の分離**: 会話履歴（History）、要約サマリー、現在の記憶、検索用インデックスなどの派生データを混同してしまうと、「過去の発言を勝手に改ざんする」「古い判断根拠だけから間違った記憶を勝手に再形成する」「検索キャッシュのヒットによって失効したはずの権限が復活する」といった不具合を招きます。

最初のマイルストーン（テキストタイムライン、個体限定スコープでのサマリー・メモリ形成・由来追跡・想起・訂正・個人データ削除、ワークスペースフォルダを対象とするタスクエージェントへのファイル作業委任、クライアント不在時のタスク継続とホスト再起動後の明示的再開）は、これら3つのサブシステム間のデータ受け渡しが正しく成立して初めて検証できます。音声対話、画面観測、グループ会話、コンパニオン同士の自発的交流、全体共有メモリ、スキル生成、感情や関係性の発達、定期スケジュール、リモート接続、キャラクター配布などは後続のマイルストーンで実装されますが、本書はそれらの確定済みルールを除外することなく、将来の安全なデータ受け渡しを妨げない形で規定します。

## 2. 内部責務の分離

### 2.1 個体調整

コンパニオン個体としての一貫した応答と判断を、クライアントの切り替え、AIプロバイダとのセッション切断、一時的なタスクエージェントの生成・消滅を越えて永続させます。個体の停止や削除といったセキュリティ・管理上の強制処理を、AIモデル（LLM）の判断や応答成否に従属させてはいけません。

| 内部責務 | 本責務が正式に判断・管理するもの（authoritative） | 本責務が保持してはならないマスターデータ |
|---|---|---|
| I-1 同一性・活動状態・適用関係 | キャラクター設定を起点としつつ、独立した別個体としての生成・継続、停止・再開・削除の対象管理、適用済みパーツやリビジョンの選択。ユーザーの明示的な操作に基づいて確定し、AIモデル（LLM）の応答成否に従属させない。 | 静的なキャラクター定義そのもの（キャラクター機能が担当）、学習データの意味内容（認識・学習機能が担当）、権限設定・同意状態・利用上限（権限・制約機能が担当）。 |
| I-2 対話継続・参加関係 | ユーザーとの1対1会話の継続、グループ会話やコンパニオン同士の交流における参加関係、「誰の会話・発言か」「どの空間（タイムライン）での発話か」の管理。テキスト会話と音声対話を同一のタイムラインに正しく結び付けること。 | 実際の入出力ラウンド、画面提示、安全な区切り（入出力・提示機能が担当）、タスクへの反映（作業機能が担当）、プレゼンス帰属の成立（接続・存在機能が担当）。 |
| I-3 Historyと非会話活動記録の意味 | 送受信された発言内容と参加者・会話文脈の元ログ（History）の意味。画面観測イベントの認識結果、通知の生成、軽微な内部調査などについて「何が行われ、何を認識・報告したか」の記録。タスク進捗、アクションの確定度、監査ログの事実は各担当機能を参照し、ここで勝手に独立更新しない。 | タスクの進捗、外部作用の確定度、監査ログの発生順序（各担当機能が保持）、AIプロバイダとのセッション履歴、画面表示用コピー（派生・一時データ）。 |
| I-4 依頼受入・委任判断・結果統合 | ユーザーからの依頼を受けるか、追加条件を確認するか、断るかの判断。まとまった作業のタスク化とタスクエージェントへの委任、ユーザーからの軌道修正（steering）の受付、タスク実行結果の統合とユーザーへの報告。軽微な情報取得や補助処理は自身で直接実行できる。 | タスクとしての正式な受理・反映・達成判定（作業機能が担当）、権限の確定（権限・制約機能が担当）、実際の外部作用の成功（実行・拡張機能が担当）。 |
| I-5 自発性判断 | 画面観測イベントを個体の文脈に照らし合わせた意味判断、自発的な発話・通知・内部調査・コンパニオン間交流・クライアント移動の必要性の判断。個体ごとの自発性設定（OFFを含む）、発言頻度、上限回数、未応答時の連続発話抑制、会話の順番や堂々巡り（ループ）の抑制。静粛時間帯（Quiet hours）、ミュート、未応答状態、権限、API費用、リソース制限を自発性よりも常に優先すること。安全ルールを自発行動のトリガーにしてはいけない。 | 画面キャプチャ、イベント候補の検知、ルーティング（共有観測機能が担当）、プレゼンス帰属の成立（接続・存在機能が担当）、アクション実行の許可（権限・制約機能および実行・拡張機能が担当）。 |
| I-6 未伝達管理 | クライアント不在のためにユーザーへ伝えられなかった事項、対象、元の記録との対応関係、次にクライアントへ接続した際の要約報告ステータス。「何をまだ伝える必要があるか」のマスターデータ。タスク由来ならタスク記録、会話由来なら活動記録へ参照を戻す。報告用の要約文は派生表現である。 | タスクの進捗や結果そのもの（作業機能が担当）、実際の画面提示（入出力・提示機能が担当）、「報告完了＝タスク完了・承認済み」という安易な推測。 |
| I-7 進行中の意味判断 | 現在の入力に対する応答の組み立て、中断の判断、会話上の取り扱い。推論や入出力に伴う一時的な処理であり、残すべき発言や判断結果は会話履歴（History）等へ正しく反映する。 | 会話のマスターデータとしてのAIプロバイダセッション、タイムラインの終了や削除と会話ラウンドの終了の混同。 |

I-1〜I-7は同じコンパニオン個体に属する責務ですが、単一のデータ状態やライフサイクル、保存単位にまとめてはいけません。適用済みキャラクター構成の変更と、日々の経験データの変更は別物です。現在の会話への参加と過去の参加ログ、進行中の一時的な思考と保存された発言ログ、未伝達メッセージの必要事項と元のタスク記録・報告状況を厳格に区別します。コンパニオンの「停止（Stop）」は活動を止めてデータを安全に保持する操作であり、クライアント不在（アクティブなし）、アバター非表示、あるいは単に口数が少ないことと混同してはいけません。「個体の削除」はシステム横断的な操作ですが、過去のタスク記録、全体共有の学習データ（Global Learning）、外部ファイルまで「個体の所有物」とみなして連鎖削除してはいけません。

### 2.2 作業

作業の開始、遂行、ユーザーの判断待ち、結果確認、再開までを、日常の通常会話やクライアント端末の寿命から完全に独立して扱います。タスクそのもの、一時的なタスクエージェント、定期実行スケジュール、各回の実行履歴、ワークスペースフォルダの紐付け、外部ファイル、永続的な成果物、一時的な中間ファイルを、単一のデータ型、保存単位、実行ループ、障害境界にまとめてはいけません。

| 内部責務 | 本責務が正式に判断・管理するもの（authoritative） | 本責務が保持してはならないマスターデータ |
|---|---|---|
| W-1 Task追跡 | 引き受けたタスクの目的、担当者、参加エージェント、採用した追加指示、進捗状況、判断待ち、完了、失敗、キャンセル、未完了事項、次の判断。タスク記録は、一時的なエージェントが終了した後も、担当コンパニオンが削除された後も確実に残り得る。 | 会話上での依頼受付や結果の統合報告（個体調整機能が担当）、個別アクションの確定度（実行・拡張機能が担当）、権限承認の確定（権限・制約機能が担当）。 |
| W-2 委任・一時Agent対応 | タスク全体または一部の作業が、誰からどの範囲で委任されたか、進行・待機・停止・結果受け取りの対応関係。並列処理や再委任を行う場合でも、委任元タスクの境界内に厳格に従属させる。一時的なエージェントに長期的な人格、関係性、独自スコープの学習データを持たせてはいけない。 | 委任元コンパニオンの権限・API費用・プロバイダ設定の勝手な独立保有、別タスクの承認情報・認証情報、過去の担当者のプライベートな学習データ。 |
| W-3 steering受入・反映 | 会話の中でユーザーから与えられた追加指示を、タスクコンテキストとして採用した内容、反映の可否、反映できない場合の理由と選択肢の管理。発言ログのマスターデータは会話履歴（History）にあり、権限承認の有効性は権限・制約機能に残る。 | 「会話で指示を受け付けた＝タスクに反映完了した・承認された」という安易な推測、タスクの待機処理による通常の日常会話のブロック（占有）。 |
| W-4 Schedule設定・到来・各回 | 担当コンパニオン、実行内容、時刻条件、設定作成時のタイムゾーン、停止状態、初期ワークスペース入力、スケジュール到来時のスキップ（missed）/ 開始の対応、各回の新しいタスクとの紐付け。スケジュール作成依頼を特別な権限トークンと誤認しないこと。実行ごとに現在の利用制限を再評価すること。 | 画面観測のキャプチャタイミング、バックアップスケジュール（各担当機能が保持）、スキップされた実行回の勝手な自動補完や「実行済み」への改ざん、担当コンパニオン削除時のスケジュールの勝手な別個体への引き継ぎ。 |
| W-5 Workspace関連付け・保存先 | タスクに従属する内部的なワークスペース紐付け、許可されたワークスペースフォルダの既定保存先としての扱い、永続保存先が決まっていない場合の最終保存前確認。同じ外部フォルダを利用するタスク同士であっても、作業状態や権限承認を勝手に共有しないこと。 | 外部フォルダ、元ファイル、成果物そのものの所有権、タスクの紐付け削除に伴う外部ファイルの勝手な連鎖削除、システム専用ライブラリへの外部ファイルの勝手な複製。 |
| W-6 Task context・内部copy・中間file | タスク遂行のために採用した目的、指示、判断材料、途中理解の用途と有効性、内部に一時保持したコピーの出所・取得日時・用途の区別、一時的な中間ファイルの用途・必要期間・安全な整理対象の管理。タスク限定の情報を勝手に長期学習データへ昇格させないこと。 | 元のマスターデータ（会話、ファイル、学習データ）の勝手な上書き、外部ファイルの現在の最新値、AIの思考作業領域や詳細な通信ペイロードの全件保存。 |
| W-7 記録保持・削除・引継ぎ | 「タスクの終了」は「記録の削除」ではないことの維持。タスク削除時における固有の紐付けの削除、指定日以前のログ保持整理の範囲明示、残された記録への管理画面からの到達可能性の確保、ユーザーの依頼によるタスク引き継ぎ時における担当者や作業条件の安全な更新。 | 通常のタスク記録削除を、すでに形成された学習データやサマリーへ連鎖削除（カスケード削除）させること、外部の成果物を自分の所有物とみなして消去すること、旧担当者のプライベートな学習データ・承認・認証情報を丸ごと無断継承すること。 |

W-1の現在状態は、実行・拡張サブシステムにおけるアクションの実行状況や確定度と連動しますが、同じ確定度を作業側で勝手に独立更新してはいけません。W-2の委任範囲、結果、失敗理由などの残すべき客観的事実は、タスク記録の一部として安全に保持します。W-4における「次回実行予定時刻」の画面表示は、保存された時刻条件と現在日時・タイムゾーン規則から算出される派生表示であり、独立したマスターデータではありません。W-5およびW-6における一時コピーの保持は、プライバシー保護、秘密情報保護、データ保持ポリシー、個人データ完全削除（Targeted Deletion）の対象であり、「外部のファイルだから」という理由で消去対象から除外してはいけません。

### 2.3 認識・学習

日々の共通の経験（Experience）を、どの記憶や内的状態の理解・変化に役立てるかを判断するとともに、記憶の訂正と判断根拠の説明を同じ責任の下で扱います。各概念の独自の役割と保持ルールを守ることが、これらを統合して管理するための前提条件です。単一のマスターデータスキーマ、単一のリビジョンモデル、一律の保持ポリシー、機械的な全データ同時更新を導いてはいけません。

| 内部責務 | 本責務が正式に判断・管理するもの（authoritative） | 本責務が保持してはならないマスターデータ |
|---|---|---|
| L-1 Experience受入・形成判断 | 会話、タスク、ツール利用、画面観測、コンパニオン間交流などの経験（Experience）から、長期的に保存する価値があるか、記憶の形成・更新・統合・想起が必要かを文脈に基づいて判断すること。「保存する価値」と「今回想起する必要性」を明確に区別すること。すべての出来事の全件保存や、保存ごとの都度確認をユーザーに要求しないこと。 | 会話履歴の生ログ（Raw History）の代替保管庫、一般的な世界知識の百科事典的蓄積、タスク化すべきかどうかの判断閾値、権限・ユーザー同意・利用上限の変更。 |
| L-2 Summary・根拠関係 | 意味的なまとまりとして圧縮された要約サマリー（Summary）と、「どの記憶形成やリビジョン更新が、どのサマリーを根拠としたか」の対応関係の管理。サマリーは複数の継続状態の共通の根拠として利用できる。元の会話やタスクなどの大まかな出所範囲（source）への参照を保持すること。 | 現在の最新知識としてのサマリー（サマリーはあくまで過去の根拠）、生ログの全件保存の要求、検索キャッシュの有効期限切れに伴うサマリーの勝手な破棄。 |
| L-3 Memory | 現在の主要な知識（事実・好み・設定等）、時間的な意味、重要度、個体限定（Companion scope）/ 全体共有（Global scope）の区分、変更の経緯。通常の形成・更新・統合・訂正・想起抑制は、経験と文脈に基づくAIの意味判断に従う。単なる「誤りの訂正」と「時間の経過による変化」を厳格に区別し、通常の忘却は「想起の抑制」として扱う。 | 一般的な世界知識、生のログ履歴、タスク限定の一時データの無条件蓄積、検索クエリごとの類似度スコアとの同一視、ユーザーが内部データを直接書き換える汎用メモリ編集ツール。 |
| L-4 Skill | 再利用可能な作業手順、専門知識、注意事項、補助リソース、現在有効なリビジョン、出所、スコープの管理。元のスキルパッケージの保護、別リビジョンとしての安全な改善、以前の正常なリビジョンへの復帰、判断根拠と「未検証」「成功」「失敗」の実行結果との対応付け。ワークスペース内のスキルは外部ファイルとして参照すること。 | 外部パッケージの原本そのものの所有権、内部でのスキル更新の外部原本への勝手な自動反映、「動作検証が成功していること」をスキルの定義条件とすること。 |
| L-5 Relationship | コンパニオン個体ごとの、ユーザーや他個体に対するコンパクトな関係性解釈（心理的距離感、交流の傾向、関係の変化など）。共有された経験、過去の関係性、新しい出来事を根拠に更新する。「コンパニオンAから見たB」と「Bから見たA」は全く別の意味を持つ。客観的な事実と矛盾した場合は、Memoryの事実を優先して関係性を再解釈する。 | ユーザーの個人情報、好み、出来事の記録に関する「第2のMemory」、関係性の勝手な対称化（Aが好きならBも好きと決めつけること）や共同所有、任意の数値をいじる汎用パラメータ編集画面、権限や安全ルールへの勝手な影響。 |
| L-6 Companion State | コンパニオン個体自身の現在の内面的な状態（気分・感情）と、表現・注意・会話・行動への持続的な傾向。一時的な感情状態と持続的な性格傾向を区別し、時間の経過を考慮した継続と再解釈を行う。一時的な感情の値を無期限に固定してはならず、過去のすべての感情値を永久保存することもしない。 | 詳細な客観的事実や関係性解釈の勝手な複製、キャラクターの静的設定の書き換え、画面に出力された表情やモーションのマスターデータ化、権限や安全ルールへの勝手な影響。 |
| L-7 scope意味・制御制約の区別 | 記憶の内容、出所、共通利用の必要性から、個体限定（Companion scope）か全体共有（Global scope）かを意味的に判断すること。個体との会話から得られた情報は個体限定を既定とし、「重要度が高いこと」と「全体共有すること」を厳格に区別すること。ユーザーが設定した「保存禁止」「共有禁止」などのセキュリティ制約（control constraint）は、AIの意味判断とは明確に区別して決定論的に強制すること。 | スコープの強制的なセキュリティ適用の単独保有（権限・制約機能および各利用箇所との協調で担保する）、明示的なセキュリティ制約の勝手な解除、重要度が高いことだけを理由とした勝手な全体共有（グローバル化）。 |
| L-8 由来説明の供給 | 現在の知識、過去のリビジョン、判断根拠、誤りの訂正と時間変化の違いをユーザーに分かりやすく説明できる能力。AIモデルの内部思考ログ（CoT）をそのまま露出しないこと。正確な発言内容や詳細な日時は、保持されている会話履歴（History）を参照させること。 | 会話履歴そのものの管理、タスクの達成や外部作用の成功判定、システム制御プレーンの変更確定。 |

L-3における過去のリビジョン記録は「変更の経緯」を示すマスターデータであり、現在の知識と同格で競合するマスターデータではありません。L-4における過去リビジョンへの復帰は「現在どの手順を採用するか」の切り替えであり、それ以降に発生したリビジョンや実行結果の記録を「なかったこと」にするわけではありません。L-5およびL-6は個体固有のデータであり、勝手に全体共有されることはなく、コンパニオン個体の削除時には道連れとして完全に削除されます。L-7における全体共有（Global化）は、ユーザーが明示的に共有を指示した場合、または内容・出所・文脈から全体共有すべきであることが客観的に明白な場合に限られ、判断に迷う場合は個体限定に留めます。L-2〜L-8におけるサマリー、リビジョン、判断根拠は、検索用インデックスやキャッシュの有効期限が切れたからといって勝手に捨ててはいけません。

## 3. 管理する logical state

特に「外部」「コピー」「一時データ」と明記されているものを除き、すべてホスト側で管理する内部データを指します。永続化の具体的な実装担当、保存単位、単一ライター、トランザクションの仕組みは本書では固定しません。なお、各データの担当機能は、正当な全データ消去処理（Targeted Deletion等）への参加を拒否することはできません。

### 3.1 個体調整が意味ownerとなる state

- **コンパニオンの同一性、活動状態、適用済みキャラクター構成**（SO 4.2）。キャラクターの静的素材そのものはキャラクター機能、学習データの意味内容は認識・学習機能、AIプロバイダへの送信同意等は権限・制約機能に置きます。
- **1対1会話の継続性、グループ会話やコンパニオン間交流の参加関係、会話履歴（History）の意味、保存された非会話活動記録や判断根拠の意味、進行中の会話の意味解釈**（SO 4.3）。入出力ラウンドの受付、画面提示、安全な区切りは入出力・提示機能が担当します。
- **未伝達メッセージと報告ステータス**（SO 4.4）。タスク由来ならタスク記録、会話由来なら活動記録へと参照を戻します。報告用の要約文は派生データです。元の記録が存在しない通知などの場合は、必要な通知内容そのものを活動記録として必要な範囲で保持します。

クライアント上の入力中テキスト、表示用タイムライン、音声バッファはすべて一時的なデータ（temporary）です。画面表示やラウンドの状態を、過去の発言やタスク進捗に関する「第2のマスターデータ」にしてはいけません。グループ会話や交流に参加しているからといって、他個体のプライベートな学習データへアクセスする権限を与えてはいけません。個体削除後も、過去の発言や活動ログの中で「誰が発言したか」を識別できる記録と、現在システムで利用可能な個体状態を厳格に区別します。

### 3.2 作業が意味ownerとなる state

- **タスクの目的、担当者、進捗、結果、およびタスクコンテキスト**（SO 4.10）。タスクコンテキストは利用目的と有効期間を厳格に管理し、出所、取得日時、用途の区別を保持します。
- **委任関係と一時的なタスクエージェントの実行対応**（SO 4.11）。エージェント自体は永続的なデータの担当者ではなく、残すべき客観的事実はタスク記録の一部として安全に保持します。
- **ワークスペースの紐付け、保存先フォルダの選択、判断待ち状態、内部保持コピーの意味、一時的な中間ファイルの用途・必要期間・整理対象**（SO 4.13）。外部フォルダ、案内ファイル、スキル、成果物はユーザーまたは外部システムの所有物であり、システムは許可されたアクションの範囲内でのみ利用します。
- **定期実行スケジュール設定、スケジュール到来時の実行記録、各回のタスク**（SO 4.14）。スケジュール設定そのものと、過去の発生記録、各回の実行タスクを明確に分けて扱います。画面に表示される次回実行予定時刻は導出された派生値であり、独立したマスターデータではありません。

「タスクの終了」は実行の区切りにすぎず、記録の削除ではありません。タスクそのものの削除と、指定日以前の古いログの整理ポリシーを厳格に区別し、通常の記録整理が、すでに形成された学習データ、サマリー、外部の成果物へ連鎖削除（カスケード削除）を波及させないようにします。

### 3.3 認識・学習が意味ownerとなる state

- **要約サマリー、判断根拠の対応関係、元の出所（source）への参照**（SO 4.5）。サマリーは記憶形成時に参照した圧縮された証拠記録であり、現在の最新知識のマスターデータではありません。判断根拠を保持していることは、その元データ全体を共通利用してよい許可を意味しません。
- **Memoryの現在認識、重要度、スコープ、過去のリビジョン**（SO 4.6）。記憶形成時における保存価値と、今回の会話で想起する必要性を明確に分離し、文脈に応じて更新された重要度と、検索クエリごとの一時的な類似度スコアを混同してはいけません。
- **内部スキル、インポート元パッケージとの対応関係、学習リビジョン、実行結果の履歴**（SO 4.7）。キャラクターパッケージが推奨するスキル設定は静的な初期指定にすぎず、有効リビジョンの勝手な切り替えやアクションの実行許可を意味しません。
- **Relationship（関係性解釈）**（SO 4.8）。主体ごとの現在の関係性解釈のマスターデータであり、メモリ検索から都度再生成される一時キャッシュではありません。
- **Companion Stateの一時的状態（気分）と持続的傾向（性格・態度）**（SO 4.9）。一時的な感情であっても、それが意味を持つ間は正式なマスターデータであり、描画バッファのように即座に破棄してよいデータではありません。持続的傾向には、その形成や大きな変化のきっかけとなった経験データを関連付けます。

通常の忘却、訂正、失効処理において、保存済みの学習データ、過去のリビジョン、判断根拠を勝手に完全消去してはいけません。個体限定スコープ（Companion scope）のデータは個体削除時に連動して削除されますが、全体共有スコープ（Global scope）のデータは個体削除後も残ります。スコープの変更条件と、過去の判断根拠を勝手に共有しないルールは、SO 第6節および第7節に従います。

### 3.4 canonical / derived / temporary / external reference の扱い

- **マスターデータ（canonical）として参照するもの**: Memoryの現在認識、保持された会話履歴（History）、Relationship（関係性解釈）、Companion State（内面状態）、Memory（詳細事実）、キャラクターのリビジョンと適用関係、経験由来の各種状態、タスクの進捗・結果、実行・拡張機能が管理する個別アクションの外部作用、ユーザー由来の安全制御条件と各時点での評価済み有効性、外部の最新状態（外部所有者が管理）、内部で採用された情報（記録の担当者が管理）。
- **派生データ（derived）として扱うもの**: 報告用サマリー、データの出所説明、進捗表示用テキスト、3Dアバターの描画データ、音声合成出力、ベクトル埋め込み（embedding）、インデックス、類似度スコア、プロンプトキャッシュ、AIセッション、一時コンテキスト、次回画面表示用データ、費用集計値など。派生データの生成・保持・破棄を行う機能は、元データとの対応関係と利用範囲を明確に説明できなければならず、データの訂正、スコープ変更、個人データ完全削除（Targeted Deletion）に確実に参加しなければなりません。古い派生データから、現在の状態や権限を勝手に復活させてはいけません。
- **一時データ（temporary）として扱うもの**: 生のデスクトップ画像（Raw Observation）、生の音声データ（Raw Voice）、詳細なツール通信ペイロード、AIの内部思考ログ（CoT）（これらは通常保存しない）、クライアントの画面表示コピー、入力途中の未確定テキスト、音声バッファ、観測イベント候補、推論中の一時コンテキスト、外部ツールUI（MCP Apps）の表示データ、I-7の進行中の判断、W-2のエージェント一時コンテキスト、L-6の一時的な感情バッファ。障害時に失われてよいのはこれらの一時的な表現データだけであり、受理済みの指示、必要な作業記録、未伝達メッセージ、結果が不明な外部作用まで失われてよいわけではありません。
- **外部参照（external reference）として扱うもの**: 外部ワークスペースの実体ファイル、案内ファイル、スキルファイル、成果物、外部の配布パッケージ、エクスポート済みコピー、ユーザーが保管するバックアップファイル、外部AIプロバイダやMCPサーバー側の固有状態。システム内部に一時保持したコピー、内部に取り込んだスキル、システム管理下の一時データは、内部の利用および消去責任に従います。「外部コードに由来するデータだから」という理由で、消去義務を免れることはできません。

「経験（Experience）」とは出来事と結果を指す論理的な概念であり、すべての活動ログを際限なく格納し続けるような巨大な生データストアを新設するわけではありません。要約サマリーを作らずに完了する出来事もあれば、生の会話ログを保存せずサマリーを根拠として残す記憶形成もあります。また、画面や音声への出力結果から、キャラクターの静的設定や永続データへの勝手な自動逆更新を導いてはいけません。

## 4. Subsystem間の受渡し（semantic contract）

「モジュールAがモジュールBの関数を呼ぶ」といった具体的な実装コードの構造を先に決めるのではなく、「要求の開始」「正式な判断権限（authoritative）」「受け渡す内容」「維持すべき前提条件」「結果の受け入れ」という契約関係を規定します。非同期メッセージ、同期呼び出し、共有メモリなどの具体的な実現方式は、後続の実装設計に委ねます。

### H-1 Experience → 形成・利用

- **開始**: 個体調整機能や作業機能が、日々の活動と結果を「経験（Experience）」として認識・学習機能へ渡します。日常会話、タスク遂行、ツール利用、画面観測、コンパニオン間交流のいずれであっても、「保存価値が事前に確定していること」を要求せず、同じ入り口から安全に渡すことができます。
- **判断**: 長期的な保存価値の有無、記憶の形成・更新・統合・想起の必要性に関する意味判断は、認識・学習機能が行います。個体に所属しているデータだからといって、個体調整機能が学習データを自由に書き換える特権を持つわけではありません。タスク限定の情報を長期記憶へ昇格させるかどうかは独立した判断であり、作業機能がタスクコンテキストとして一時保持することと混同してはいけません。
- **受渡内容**: 出来事の内容と結果、必要な背景文脈、訂正の場合は「訂正対象の古い記憶」と「新しい経験」の区別。タスクの経験には、検証状態（未検証・成功・失敗）の区別を含めます。一時的なタスクエージェントの経験を、コンパニオン個体の長期的な人格へ勝手に帰属させてはいけません。
- **失ってはならない前提**: データの出所（ユーザー発言、観測、AI推論、ツール実行結果の厳格な区別）、対象コンパニオン、タスク、委任関係との対応、クライアント依存の処理であれば取得元クライアント、会話ラウンド、観測候補との関係、停止や再起動・リストアを跨ぐ前後の継続関係、想定される利用目的（会話の返答、記憶候補、ルーティング、権限解釈、タスク判断の区別）。
- **受入**: 認識・学習機能は、必要な記憶状態のみを安全に形成・変更し、要約サマリーを共通の根拠として対応付けます。ユーザーへの応答が完了したことと、すべての学習データの更新が完了したことを同一の完了条件にしてはいけません。全データの一律同時更新や、すべての生ログの永久保存を要求しません。

### H-2 会話による訂正

- **開始**: 個体調整機能が、ユーザーとの会話の中で受け取った「記憶の訂正」や「状況の変化の指摘」を認識・学習機能へ渡します。個体調整機能が会話で訂正を受け付けたからといって、学習データをその場で直接上書きするわけではありません。
- **判断**: 対象を特定した上での意味的な記憶変更は、認識・学習機能が行います。「最初から間違っていたことの訂正」と、「過去は正しかったが時間の経過によって状況が変わったこと」を厳格に区別し、過去の有効性を正しく表現できる関係を維持します。関係性データ（Relationship）が古い事実に依存していた場合は、Memoryの事実を最優先して関係性を再解釈し、古い誤った事実を別のデータから再びユーザーへ提示しないようにします。
- **失ってはならない前提**: 訂正前の知識、その判断根拠、リビジョン履歴、訂正の根拠となった新しい経験、時間的な意味付け。過去の発言ログそのものを、現在の新しい知識に合わせて書き換えてはいけません。
- **受入**: ユーザーは管理画面等から、現在の知識、その出所、変更の経緯をいつでも確認できます。内部の数値を直接いじらせるような汎用メモリ編集ツールを安易な入り口にしてはいけません。

### H-3 Task化・委任・steering・結果

- **開始**: 個体調整機能が、まとまった作業のタスク化、タスクエージェントへの委任、軌道修正（steering）、タスクのキャンセルを作業機能へ要求します。なお、管理画面からのタスクキャンセルや記録確認は、コンパニオンの応答成功を必要とせず即座に実行できます。
- **判断**: タスクとしての正式な受理、反映、達成判定は作業機能が担当します。会話上での依頼受付や結果の統合報告は個体調整機能、権限の判定は権限・制約機能が担います。軽微な補助処理についてタスク化のオーバーヘッドを省略することはコンパニオン本体の判断で行えますが、その閾値や分類アルゴリズムは本書では固定しません。
- **受渡内容**: タスク化する意図、目的、軌道修正の前提条件、ワークスペースの利用条件、キャンセル対象のタスク。作業機能からは、進捗状況、実行結果、判断待ち事項、反映できない場合の理由と代替選択肢を返します。
- **失ってはならない前提**: 会話の発言ログ、タスクに実際に反映された内容、反映不能や判断待ちの対応関係、軌道修正の前後におけるタスク目的の厳格な区別、委任範囲、ワークスペースの有効範囲、クライアント依存条件。「会話で依頼を受け付けたこと」を「タスクに反映完了した」「権限が承認された」と誤認してはいけません。タスクの実行待ちによって、日常の通常会話を占有・停止させてはいけません。
- **受入**: 個体調整機能は、作業機能が管理するタスクのマスターデータを参照して、ユーザーへ統合的な報告を行います。作業機能は、担当者の稼働状態や必要な個体判断を個体調整機能へ問い合わせる場合でも、キャンセル要求の受付や保存済み実行結果の確認を、コンパニオン本体のAI推論待ちにしてはいけません。

### H-4 Task contextと Learning・History・Summaryの分離

- 作業機能が管理するタスクコンテキスト、個体調整機能が管理する会話履歴や活動記録、認識・学習機能が管理するサマリーや学習データは、すべて別々のマスターデータであり、別々のライフサイクルを持ちます。互いに相手のデータを直接書き換えるような連鎖構造を作ってはいけません。
- タスク限定の一時的な情報を、長期的な学習データへ勝手に昇格させてはいけません。タスクの実行経験や検証結果を学習機能へ渡す場合であっても、一時的なタスクエージェントがコンパニオンの長期的な記憶を直接保存することは禁止します。
- 正確な引用が必要な場合は保持されている会話履歴（History）、現在の知識にはMemory、圧縮された根拠にはサマリーを用います。検索スコアが高いことやテキストが短いことだけを理由に、古いサマリーを訂正後のMemoryの代わりに使ってはいけません。元の会話ログが保持期間満了等で失われた場合は、AIの生成で勝手に補完してはならず、「正確な引用はできない」という事実を誠実に維持します。
- データの利用側は、サマリー、過去のリビジョン、出所情報、共有コンテキストを、利用者と目的に応じて許可された範囲内でのみ取得します。全体共有された現在の知識から、個人のプライベートな過去の全記憶へ辿らせてはならず、取得したコピーや検索結果に対しても現在の利用制限を確実に適用します。

### H-5 scope・共有範囲の変更

- **判断**: 記憶の内容、必要な背景情報、スコープの意味付けに関する判断は認識・学習機能が行います。コンパニオン個体との会話から生まれた情報は「個体限定（Companion scope）」を既定とし、「重要度が高いこと」と「全体共有すること」を厳格に切り離し、重要度が高いからといって勝手に全体共有（Global化）してはいけません。判断に迷う場合は個体限定に留めます。タスクへの参加、ワークスペースの共有、同一クライアントへの滞在、グループ会話への参加を、勝手な全体共有の根拠にしてはいけません。
- **強制**: 決定されたスコープや、ユーザーが設定した「保存禁止」「共有禁止」といったセキュリティ制約の確実な強制適用は、権限・制約機能および各利用側との協調によって行われます。認識・学習機能がセキュリティ強制の責任者を兼任する構造は避けます。なお、具体的な依存方向、API、制約の表現形式は本書では固定しません。
- **受渡内容**: 共有する内容と、理解に必要な最小限の背景情報の選択・要約（AIの意味判断に従いつつ、ユーザーの明示的な非共有指示を最優先します）。全体共有された現在の内容から、個人のプライベートな過去リビジョン、元の会話ログ、サマリーの全文へとアクセス範囲を広げてはいけません。参照、検索結果、処理中の一時コピーに対しても、新しいスコープ制限を直ちに適用します。
- **禁止事項**: コンパニオン個体の削除を契機とした勝手な全体共有（グローバル化）、スケジュールの勝手な別個体への引き継ぎ、「重要である」「役に立つ」「一般的な好みである」という理由だけでの勝手な昇格。なお、全体共有の判断を行うためだけに、通常の会話で毎回ユーザーに都度確認を求めるような煩わしい設計は要求しません。
- **スキル固有のルール**: キャラクターパッケージの推奨設定から取り込まれたスキルは、個体限定（Companion scope）を既定として各個体に別々に属します。単独でインポートされたスキルについては、ユーザーが個体限定か全体共有かを選択できます。その後の共有や個体削除時の扱いは、通常のスコープ契約に従います。

### H-6 Observerへの限定routing文脈の提供

- **開始の契機**: 複数のコンパニオンが同席するグループ会話（共有観測 Observer）に必要な限定された文脈情報は、「個体調整」機能との協調を通じて取得します。会話履歴や個体ごとの文脈は個体調整機能、記憶や学習内容は認識・学習機能、タスクの文脈は作業機能が、それぞれ元データの意味と提供範囲に責任を持ちます。タスク文脈の参照は、既存の「個体調整–作業」間の連携を通じて行い、共有観測機能へタスクの所有権や無制限なアクセス権限を渡してはいけません。
- **判断**: どの範囲まで情報を提供してよいかという判断は各情報の担当責任者（元owner）が行い、実際の送信や利用に関する制限の適用は権限・制約機能および各利用箇所が担当します。Observer専用の割り当て（assignment）に対する送信同意と、元情報が持つ利用制約は、情報が加工・変換された後であっても両方とも確実に適用されなければなりません。コンパニオン個体側の同意や設定変更を勝手に選んで組み合わせ、代用してはいけません。
- **受渡内容**: 元情報に従属する、発言の振り分け（routing）のための一時的な派生表現（インデックスや要約）であり、要約のマスターデータや新しい学習のマスターデータ、新しい共有スコープを作成するものではありません。元情報、対象コンパニオン、利用目的、セキュリティ制約の対応関係を厳格に保持します。個体の話題やタスクが変更された際には、各情報の担当責任者がその変更内容と提供済み文脈との整合性を正しく判定できなければなりません。
- **禁止事項**: 全体共有（Global化）すること、他のコンパニオンへ勝手に共有すること、プライベートな情報全体を公開すること、要約や変換を理由に元の制約を勝手に消去すること、スコープ変更・同意失効・データ削除が発生した際に処理中の一時派生データへ反映しないこと。なお、文脈の生成方法、利用するAIモデルやプロバイダ、データ形式、更新頻度、鮮度の判定、選択アルゴリズムなどは本書では固定しません。

### H-7 未伝達と Task記録・Historyの対応

- 個体調整機能が管理する「未伝達メモ（未伝達キュー）」は、「ユーザーにまだ何を伝える必要があるか」を管理するためのマスターデータであり、タスクの進捗状況や実行結果を二重に管理するための第二のマスターデータではありません。タスクに由来する報告事項であれば元のタスク記録への参照を保持し、報告用の要約はあくまで一時的な派生表現として扱います。
- クライアントへの接続が確立したこと、画面表示用の一時コピーを送信したこと、あるいはバックグラウンドのタスクが完了したことだけを理由に「ユーザーへ報告完了」とみなしてはいけません。ユーザーに実際に提示された状況を確認した上で個体調整機能が報告ステータスを更新し、実際に提示できたか不明な状態を「確定済み」と表示してはいけません。
- コンパニオン個体が削除された場合、その個体の現在の未伝達メモの管理は終了しますが、元のタスク記録、会話履歴、保存された活動記録は、状態所有規則（SO 4.3）の保持契約に従って安全に残します。未伝達メモの終了を理由に、そこにしか残っていなかった通知内容などの歴史的記録（historical record）まで勝手に道連れで消去してはいけません。
- 通常の容量保持管理（retention cleanup）によって元の記録が削除される可能性がある場合は、未伝達として保持すべき必要な内容との関係を事前に確認します。ただし、専用の永久通知履歴システムや、到達を絶対保証する既読配信プロトコルの実装までは要求しません。

### H-8 Schedule設定・到来・各回の対応

- 「スケジュール設定（定期ルール）」、「実行発生の履歴記録」、そして「各回で実際に実行されるタスク」は明確に区別して扱います。予定時刻が到来した回がスキップ（missed）されたのか、どのタスクとして実行されたのかという発生履歴は、設定そのものとは別のデータです。
- 予定時刻が到来して開始される各回の処理は、独立した「新しいタスク」となり、その進捗や結果のマスターデータは作業機能（W-1）に記録されます。実行できなかったスキップ（missed）の記録を、後から勝手に「実行済み」へと書き換えてはいけません。「今すぐ実行（Run now）」が押された場合は、その時点の最新の前提条件の下で新しいタスクを開始します。
- スケジュールの停止・変更・削除は、「将来の起動条件」に対する操作であり、過去に実行された各回のタスク記録を勝手に消したり、過去の結果を書き換えたりしてはいけません。担当していたコンパニオンが削除された場合はそのスケジュール設定を削除し、他の個体へ勝手に自動引き継ぎしてはいけませんが、過去に残された各回のタスク記録は引き続きユーザーが管理・確認できるようにします。
- スケジュールの作成依頼や保存済みの設定内容は、永続的な実行許可証（Permission token）ではありません。各回の実行が始まるたびに、その時点での権限（Capability）、セキュリティルール、上限枠（cap）、利用可能なAIプロバイダ、コンパニオンの状態、Hostの状態を必ず再評価します。なお、画面観測のキャプチャタイミングや、バックアップの実行スケジュールを、このタスクスケジュールと安易に統合してはいけません。

### H-9 軽微処理と Task化の境界

- 非常に軽い処理、会話の中で完結する短い情報取得、判断のための手軽な調査、イベント理解のための小規模な情報収集など、わざわざ独立したバックグラウンド作業にするほどではない補助的な処理は、コンパニオン本体がその場で直接実行できます。何をタスク（Task）や専用エージェント（Task Agent）として切り出すかの厳密な閾値や分類アルゴリズムは、本書では固定しません。
- タスクとして切り出さずにコンパニオンが直接実行する軽微なアクションであっても、権限チェック、実世界への作用の追跡、活動ログの記録といったセキュリティ境界は決して省略しません。個体調整機能が必要な活動記録を管理し、実行・拡張機能が記録した作用の確定度を参照します。だからといって、あらゆる些細なアクションをすべてタスク化しなければならないわけではありません。
- まとまった調査、複数ステップにわたる手順、実際のファイル操作、Computer Useを伴う本格的な作業、長時間継続する処理、並列委任する価値のある作業などは、原則通り独立したタスクとして切り出して委任します。ユーザーからの明示的な依頼か、コンパニオンが自発的に始めた作業かという違いだけでこの原則を変えてはいけません。逆に、自発的な発言や軽微な内部調査まで、何でもかんでも一律にタスクや専用エージェントにしてしまうような過剰な設計は避けます。

### H-10 管理経路の独立

- コンパニオンの停止・削除、タスクの中断（Cancel）・記録確認、スケジュール管理、データの完全消去・バックアップ・復元・リセットなどの操作要求は、公式（第一者）のUIなどの管理経路から、各機能の担当責任者（owner）へ直接届けられなければなりません。ここで「直接」とは、本体の思考用LLMの機嫌や承認、長時間タスクの完了待ちなどに邪魔されず、確実に割り込んで実行できるという意味であり、特定のAPI形式を指定するものではありません。
- UI側に入出力の会話ラウンド、タスクの進捗、由来（provenance）の説明などを自由に書き換えられる権限を与えてはいけません。各担当責任者が正式に受理し、確認した客観的な結果に従って表示します。「要求を受け付けたこと」と「処理が完了したこと」、保存済みデータへの影響、実際に確認された作用と結果が不明な状態を、明確に区別してユーザーに提示します。
- 担当コンパニオンが削除された後であっても過去のタスク記録や判断履歴、停止結果にアクセスできることと、クライアントの切り替え中であってもHost側でタスクが安全に継続できることは、別の取り決めですが、どちらも「タスク記録のマスターデータを作業機能が責任を持って保持する」ことによって成立します。

## 5. Lifecycleとの関係

ライフサイクルの変更の多くは、データの担当責任者（owner）が別の人間に移るのではなく、「同じ担当責任者が管理する状態について、存続期間・利用可能性・参照できる範囲が変化する」ことを意味します。目的の異なる複数の操作を、安易に一つの初期化処理や一つのステートマシン（状態遷移）にひとまとめにして混同してはいけません。

| 事象 | 本クラスタ（個体・作業・学習）が変更する意味 | 独立して維持・分離すべき意味 |
|---|---|---|
| Companion生成・Character部品更新 | 個体調整機能が個体への適用を調整します。新規生成されたものは別個体として明確に識別され、更新はオーナーが明示的に選んだ部品に対応します。 | これまでの経験状態を勝手に上書きしたり、配布パッケージへ個人データを混入させたりしません。まだ適用されていない部品を「更新済み」と偽りません。Characterの内容やリビジョン管理はCharacter機能に残ります。 |
| Companion停止 / 再開 | 停止中はクライアント上の存在（presence）を解除し、Observerの参加人数からも除外します。通常の対話、Computer Use、自発的な活動、新規タスクの開始、新規スケジュールの実行は行われません。実行中のタスクはベストエフォートで中断（Cancel）を試みます。再開時は適切なクライアントへ再配置できます。 | コンパニオンの同一性と保存済みデータはそのまま保持されます。再配置の希望位置（hint）と現在の滞在状況は区別します。停止中に予定時刻を過ぎたスケジュールはスキップ（missed）のままとし、再開したからといって過去の古いタスクや結果不明のアクションを自動で再実行（replay）してはいけません。 |
| Companion削除 | 個体固有の設定、会話サマリー、個体限定（Companion scope）の記憶（Memory）、個体限定の内部スキルと過去リビジョン、一時的なコンパニオン状態（Companion State）、その他の固有学習内容、相手との関係性（Relationship）、担当していたスケジュール設定を完全に削除します。 | 1対1やグループ、コンパニオン同士の会話履歴、会話以外の活動記録や証拠、過去のタスク記録は、個体が削除されたことだけを理由に道連れで消去してはいけません。全体共有された学習内容（Global Learning）、残すべき共有サマリー、外部ファイルは安全に維持します。勝手な全体共有への格上げや、スケジュールの勝手な別個体への引き継ぎは禁止です。 |
| Task Agent終了 / 失敗 | 一時的なタスク遂行の役割を終え、得られた結果や失敗、結果不明の状態をタスク記録に対応付けます。 | これによってタスク記録そのものやコンパニオン、スケジュール設定を削除してはいけません。エージェント自身が長期的な人格や記憶を残すことはありません。 |
| Task完了・失敗・Cancel | 作業の進行に一区切りをつけ、得られた結果、未保存の変更、外部への作用、次に必要な判断をユーザーへ報告し、中間ファイルを安全に整理します。 | タスクが終了したことだけを理由に関連付けや記録を勝手に消去してはいけません。また、外部に生成された成果物をタスク機能が勝手に自分のものとして独占したり、消去したりしてはいけません。 |
| Task削除 | タスク固有の内部記録や関連付けの削除範囲を適切に処理します。 | 元の外部データソース、外部成果物、同じフォルダを参照する別タスクの関連付け、タスクから形成された学習内容やサマリーにまで、通常のタスク削除を勝手に連鎖（cascade）させてはいけません。 |
| Schedule停止 / 削除 | 将来の実行予定条件を停止または除去します。 | 過去に実行された各回の結果を変更してはいけません。スキップされた回（missed）を勝手に「実行済み」に書き換えてはいけません。 |
| Learningの通常忘却・訂正・統合・失効・置換 | 認識の内容、重要度、思い出しやすさ（想起スコア）、現在利用するリビジョンなどを変更します。 | 保存済みの内容、過去のリビジョン、判断の根拠となった情報は安全に保持し、「事実の誤り」と「時間の経過による自然な変化」を明確に区別します。 |
| scope変更 | 認識・学習機能が、共有すべき意味内容と必要な背景情報を判断し、利用可能な範囲を変更します。 | データの担当責任者（semantic owner）が勝手に移るわけではありません。重要度が高いことだけを理由に共有してはいけません。現在の内容を共有したからといって、過去の私的なリビジョンや会話ログ全体まで共有範囲を広げてはいけません。 |
| 通常History / log削除・retention cleanup | 古い生ログなどの記録範囲を減らします。 | そこからすでに形成された学習状態やサマリーは残し、元の生データが参照できなくなったことを明示します。通常のログ整理を「個人データ完全削除（Targeted Deletion）」と混同してはいけません。 |
| Targeted deletion | 復元に寄与する内部データや処理中のデータを横断して探索し、対象となる個人情報を完全に消去・復元不能化します（第7節）。 | 通常のデータ担当責任者が移るわけではありません。削除完了後にユーザーから新たに提供された情報や、外部にバックアップされたコピーの消去保証とは明確に区別します。 |
| 移動・切断 / activeなし | 接続や滞在の帰属先を切り替え、クライアントに依存する活動に区切りをつけます。Host上で実行中の通常の作業は、クライアントへ移送したり停止したりしません。 | コンパニオン個体やHost作業、内部状態の担当責任者は移りません。未伝達メモはHost側で安全に保持し、未確定のアクションを移動先のクライアントで勝手に再実行（replay）してはいけません。 |
| Host再起動 | コンパニオン個体と保存済みデータを確実に引き継ぎます。中断されたタスクはユーザーによる明示的な再開指示を待ち、停止中に到来したスケジュールはスキップ（missed）として扱います。実行中の滞在状態は、元のクライアントへの復帰という別条件に従います。 | 過去の作用が不明な状態、未伝達メモ、未完了のデータ削除処理などを「なかったこと」にして勝手にリセットしてはいけません。 |
| Provider / model変更・障害・cache失効 | AI推論の利用可能性、能力、承認済みの通信経路を適切に切り替えます。 | コンパニオンや履歴、学習内容などを初期化してはいけません。同じ情報選択方針と安全境界を維持します。接続が回復したからといって、過去のアクションを勝手に再実行してはいけません。 |
| Backup / restore | データのコピーを作成し、ユーザーからの明示的なリストア要求が成功した際には、現在の認証情報ストア（Credential store）を除き、対象の内部状態をバックアップ時点の状態へと一括置換します（第7節）。 | バックアップコピーは現在動いているマスターデータではありません。復元直後は実行を一時保留し、外部の世界は巻き戻らないことを考慮します。認証情報は現在の安全なストアを維持して整合性を確認します。 |
| 設定Reset / 全データReset | 設定のリセットは一般設定を既定値に戻す操作であり、全データのリセットは厳重な確認を経た上で内部データや認証情報を完全に削除する操作です。 | 設定リセットで保護すべきデータと、全データリセットで削除されるデータの境界を混同してはいけません。 |

全体共有（Global）として形成・変更された学習内容は、その後に元のコンパニオン個体が削除された場合でも、全体共有の知識として安全に残ります。ただし削除の際には、なぜその知識が残るのかという根拠と、元のコンパニオンという情報源が失われることをユーザーに分かりやすく説明します。一方で、相手との関係性（Relationship）や一時的なコンパニオン状態（Companion State）は、個体限定か全体共有かというスコープ変更の対象にはならず、常に個体に固有です。複数の個体が同じ体験を共有した場合であっても、それぞれの個体の状態は独立して個別に更新されます。

時間の経過もデータの意味に影響を与えます。スケジュール機能は設定時のタイムゾーンと時刻条件、コンパニオン状態は一時的な感情や経過時間、保持ポリシーやデバッグ記録は対象期間、自発的な行動は現在時刻や静粛時間帯（Quiet hours）を、それぞれの担当機能が正しく参照して判断します。ユーザーが明示的に設定したスケジュールのタイムゾーンを、システムが勝手に書き換えてはいけません。

## 6. failure / cancellation / restart時の責任

タスクが中断（Cancel）されたり通信が切断されたりしたことだけを理由に、「外部への作用が取り消された」「最初から作用などなかった」と勝手に都合よく推測してはいけません。また、結果が不明な処理を勝手に「未実行」に戻してはいけません。内部の状態を参照したことや、クライアント間を移動したことなどを口実に、アクションを勝手に再実行（replay）してはいけません。

- **個体調整**: 停止や削除を実行する管理経路は、LLMからの応答が成功するかどうかに依存せず、独立して確実に機能させます。停止・削除の処理中は新しい活動を開始させず、作業機能に対してベストエフォートでの中断（Cancel）を要求し、担当スケジュールの削除へとつなぎます。現在アクティブなクライアントが存在しない場合でも、Host内で可能な活動は継続し、伝えられなかった伝達事項は次にクライアントが接続された際に確実に報告します。移動中や切断中に届いたメッセージは、元の接続関係や元の会話ラウンドに正しく対応付け、移動先の現在の活動へ勝手に付け替えてはいけません。
- **作業**: 中断要求の受理とタスクの遂行停止は、本体LLMや作業エージェントの正常終了を待つことなく直ちに実行します。実行・拡張機能から「途中で止められなかったこと」「すでに確認された作用」「成否が不明な作用」の報告を受け取り、それを正確にユーザーへ伝えます。Hostが再起動した際、処理の途中だったタスクは、保存された進捗状況、確認された作用、不明な点、未完了の作業を提示した上で、ユーザーからの明示的な再開指示を待ちます。エージェントのセッションが残っていること、AIプロバイダが復旧したこと、Hostが自動起動したことだけを理由に、タスクを勝手に自動再開してはいけません。外部への作用が不明な場合に自動で再実行したり、クライアント間の移動や接続回復を理由に過去のアクションを再実行してはいけません。途中で指示（steering）が更新された場合、古い指示に対する作業結果を新しい目的の達成とみなしてはいけません。また、過去の承認を使い回して中断や失効を取り消してはいけません。
- **認識・学習**: 知識の形成や訂正を行っている最中にデータの削除・失効・停止・保留の要求が競合した場合、対象範囲のデータが利用されたり再保存されたりするのを確実に防ぐことが処理の絶対条件となります。削除される前の情報を参照して処理中だった学習機能が、削除完了後にその情報を再び保存してしまうような事故を絶対に防ぎます。古い根拠だけに基づいて自動で知識を再形成してはいけません。訂正が行われた後に届いた古い分析結果によって、現在の最新の知識を無条件に上書きしてはいけません。
- **共通の原則**: 要求の受付、処理の開始、外部への作用、記録の保存、タスクの達成、ユーザーへの報告は、すべて別々の客観的事実であり、安易に「一つの成功」としてひとまとめに混同してはいけません。事実の確定度を変更する場合は、その事実の担当責任者が新たに直接確認した客観的な証拠に基づかなければなりません。停止要求を受け付けたことと、外部への作用が完全に停止したことは明確に区別します。バックグラウンド作業やスケジュールによる無人実行も全く同じ原則に従い、クライアントが不在であること、予定時刻が到来したこと、システムの復元が成功したことなどを理由に、必要な権限を自動承認してはいけません。ユーザーによる確認が必要な操作は、勝手に実行せず必ず判断待ちにします。

障害からの再構築が可能であるということは、「すべての会話文脈や内部の推論ログを永遠に丸ごと保存しなければならない」という意味ではありません。処理を安全に継続するために必要なタスクの状態、未伝達メモ、作用不明の記録、未完了のデータ消去状況などを本来の担当責任者が安全に保全していれば十分です。一時的なメモリバッファが消失したことを、タスクの成功や完了の根拠にしてはいけません。

## 7. Step 11 contractへの参加

各契約の一般的な条件は第0節に挙げた重要領域（critical-area）ドキュメントに定義されており、本書では重複を避けて再掲しません。本節では、個体調整・作業・認識・学習の各機能が提供・参加する固有の約束事項のみを記載します。

### 7.1 Context Assemblyへの参加

- **個体調整**: コンテキストの組み立てに必要な対応関係（対象の活動、目的、担当コンパニオン、タスクや委任、クライアント、会話ラウンド、観測候補、継続関係、利用先）を提供し、会話履歴や個体ごとの文脈の提供範囲と意味に責任を持ちます。引用文を含むユーザーからの入力全体を無条件に「ユーザーからの命令」とみなしてはいけません。また、音声認識結果に対して勝手に「話者認証済み」という意味を付与してはいけません。対話やユーザーへの伝達用途でコンテキストを受け入れる際は、現在の対話や未伝達メモと正しく対応付け、「AIがテキストを生成した＝ユーザーに提示済みである」と見なしてはいけません。
- **作業**: タスクの文脈や内部に保持するソースコード等のコピーの提供範囲と意味に責任を持ち、既存の「個体調整–作業」間の連携を通じて、共有観測（Observer）へのタスク文脈の参照を仲介します。タスク判断用途でコンテキストを受け入れる際は、現在の目的、ユーザーからの最新の指示（steering）、委任範囲、現在の状態と照合し、「古い目的に対する回答＝新しい目的の達成」とみなしてはいけません。過去の承認を使って中断を取り消してはいけません。
- **認識・学習**: 記憶（Memory）、スキル、その由来、共有スコープの提供範囲と意味に責任を持ちます。全体共有の知識本文を利用できる場合であっても、個人のプライベートな根拠情報まで漏洩させてはいけません。第二の共有マスターデータを作ってはいけません。学習やサマリー形成の用途でコンテキストを受け入れる際は、現在の認識、判断の根拠、スコープ、保存条件と正しく照合し、「到着順が新しい＝根拠として新しい」と安易に判断してはいけません。タスクの一時的な文脈を勝手に永続化してはいけません。
- **共有観測（Observer）**: H-6に定めた契約に厳格に従って参加します。

### 7.2 Action Executionへの参加

- **個体調整**: コンパニオン本体が直接行う軽微なアクションであっても、他へ委任する作業であっても、実際の対象への作用とその結果の取得は、権限と制約に従って「実行・拡張」機能へ依頼します。これは「すべての処理をタスク化しなければならない」という意味ではありません。「実際に作用を及ぼしたこと」「タスクを達成したこと」「ユーザーへ報告したこと」を安易に一つの成功として混同してはいけません。
- **作業**: タスクおよび委任の範囲を厳格に管理し、作業エージェントの推論やアクションを推論機能および実行・拡張機能の責任下に置きます。別のエージェントを立ち上げて権限拒絶（Deny）を回避すること、別のタスクの認証情報（Credential）を勝手に流用すること、独立した利用枠やプロバイダ設定を勝手に作成することを許しません。タスク記録は実行・拡張機能が記録した作用やその確定度を参照・集約し、同じ確定度を作業側で勝手に独自更新してはいけません。エージェント自身の「完了しました」という自己申告を、作用の客観的な証拠として扱ってはいけません。
- **認識・学習**: 知識の形成や判断に必要な過去の発言、活動記録、タスクの事実、作用の確定度を参照しますが、元の生記録を自分のものとして抱え込まず、必要に応じて参照します。履歴ログが消去された場合に、架空の記憶を捏造して埋め合わせてはいけません。参照する対象は、現在アクセスが許可されている範囲に厳格に限定します。

### 7.3 Targeted Deletionへの参加

- **個体調整**: 1対1、グループ、コンパニオン同士の会話を含むすべての会話履歴、保存された会話以外の活動記録や客観的証拠、未伝達メモや要約、処理中の報告データの中から、対象となる個人情報を完全に除去または復元不能化します。「結果の説明や由来の説明に必要だから」という理由で削除を拒否してはいけません。参加しているコンパニオンが削除されただけでは残されるはずの記録であっても、完全削除の対象範囲に含まれる場合は完全消去が最優先されます。
- **作業**: タスクの目的、進捗、結果、タスク文脈、内部に保持するソースや結果のコピー、ワークスペースの関連付け、一時的な中間ファイル、スケジュール設定、発生履歴、各回のタスク記録、委任関係、遅延して届いた結果の中から、対象となる個人情報を完全に消去します。「外部ファイルだから」という理由で内部に保持している一時コピーを消去対象から除外してはいけません。エージェントの一時的な文脈がメモリから消えたことだけを理由に「消去完了」と判断してはいけません。また、消去が行われたことを理由に、過去の作用の確定度を書き換えてはいけません。
- **認識・学習**: 会話サマリー、根拠の関連付け、記憶（Memory）の現在値と過去リビジョン、その判断根拠、内部スキルの有効な定義と過去リビジョン、その由来や実行結果の対応、関係性（Relationship）の現在の解釈や保持されている過去の状態と根拠、コンパニオン状態（Companion State）のうち対象を直接または実質的に復元できる状態や根拠、検索インデックス、ベクトルデータ（embedding）、検索クエリの派生データ、推論コンテキスト、キャッシュの中から、対象となる個人情報を完全に消去します。通常の忘却・訂正・統合ではデータを残すという原則も、完全削除の対象範囲に限っては消去ルールが上位となります。「原本を保護するため」「過去リビジョンへ復元できるようにするため」といった理由で完全消去を免除することはできません。ただし、対象とは無関係な一般的な傾向や知識まで一律に初期化してはいけません。共有された根拠の中に無関係な情報が含まれる場合は可能な限り分離し、どうしても分離できない重大な影響がある場合は、データ保全と消去の影響説明としてユーザーに提示します。

### 7.4 Client Presence Transitionへの参加

- **個体調整**: クライアント間を移動する必要性（ユーザーからの呼び出し、事前指示、対話の文脈上の必要性）を判断し、未伝達メモをHost側で保持し、次のクライアントへ移動した際に要約して報告する役割を担います。移動要求の受付や実際の滞在先の決定は、接続・滞在機能が確定します。自発的な移動であっても、通常の自発性制限や権限ルールに従います。クライアント切り替えの最中は、新しい自発的行動の開始を抑止します。前のクライアント向けの会話ラウンドの出力を新しいクライアントへ勝手に出力してはいけません。「テキストを生成した＝ユーザーに提示済みである」と見なしてはいけません。
- **作業**: Host上で実行される通常の作業を安全に継続させ、特定のクライアントに依存するステップ（特定の画面操作など）のみを判断待ちや保留にする役割を担います。クライアントが切り替わったからといって、タスク全体を一律に中断（Cancel）したり、クライアントへ移送したり、最初からやり直したりしてはいけません。ユーザーが別のクライアントから呼び出したからといって、Host側で動いている作業そのものを呼び出し先へ移送してはいけません。作業エージェントが操作対象のクライアントを勝手に選ぶことはできず、操作対象を変更するにはまずコンパニオン自身の滞在先が移動していなければなりません。Host作業の完了とクライアント不在が重なった場合は、その結果を個体調整の未伝達メモへと確実に引き渡します。
- **認識・学習**: クライアントの移動、一時停止（Stop）、切断が発生しても、すでに獲得した経験（Experience）や形成済みの知識（Learning）とは独立したライフサイクルを維持します。画面観測がOFFになったこと、クライアントを移動したこと、停止したことだけを理由に知識を消去してはいけません。遅れて届いた知識形成の結果についても、現在の最新の認識と確実に照合します。

### 7.5 Backup / Restoreへの参加

- **個体調整**: コンパニオンの同一性、活動状態、適用関係、会話履歴、活動記録、未伝達メモと報告状況を、確実に復旧できる明確な参照関係とともに提供します。元の記録と報告ステータスを明確に分け、「表示用の一時コピーを送信したこと＝報告完了」と誤認しない関係性を維持します。すでに削除された個体の残存記録も含めてバックアップします。
- **作業**: タスクの目的、担当コンパニオン、進捗、結果、タスク文脈、委任関係、作用の確定度、ワークスペースの関連付け、スケジュール設定、タイムゾーン、初期入力、予定時刻の到来履歴、各回のタスク記録を、確実に復旧できる明確な参照関係とともに提供します。外部のファイルシステムを勝手に辿ってファイルを集めてはいけません。一時的なメモリバッファや外部プロバイダのセッションが復元されることを前提にしてはいけません。
- **認識・学習**: 会話サマリー、判断根拠の関連付け、記憶（Memory）の現在値と過去リビジョン、スキル、原本との対応関係、学習されたリビジョン、実行結果、関係性（Relationship）、コンパニオン状態（Companion State）と保持された根拠、共有根拠の利用関係を、確実に復旧できる明確な参照関係とともに提供します。全体共有された知識本文から、プライベートな根拠全文へのアクセスが勝手に広がってしまうような穴を作ってはいけません。コンパニオン状態の経過時間を正しく解釈し、時間が止まったまま固定されたり、不自然にリセットされたりしないようにします。具体的な感情パラメータの次元数やスケール、減衰計算式などは本書では固定しません。

## 8. boundaryを越える際に保持すべき意味

後続の詳細なインターフェースや状態表現の設計においては、特定のAPIや実装メカニズムを固定しなくても、システム境界をデータが通過する際に少なくとも以下の対応関係を正しく表現・解決・照合できなければなりません。「確認できない情報」を、勝手に「現在有効である」「許可されている」「完了している」と都合よく推定する方式は決して採用できません。

- **主体・用途・タスク・委任・アクション・クライアント・情報源・リビジョン・判断時の前提条件、停止前後・再起動前後・リストア前後の継続関係**: （Context Assembly第3節の対応）。必要な対応関係を失ってしまった処理結果は、移動先の現在の活動へ勝手に付け替えてはならず、その用途では受け入れられないものとして利用元が安全に処理します。
- **情報の担当責任者・対象・情報源との関係、内容の位置付け・由来（provenance）、リビジョン・取得時点・有効期間、所属・スコープ・共有関係、用途・保存・共有・送信の制限、参照の解決状態や欠落の有無**: （Context Assembly第3節の判断材料）。
- **実行主体と委任の連鎖、タスク・ワークスペースの範囲、目的、実際の操作対象と操作内容、使用する主なデータと用途、コストやリスク、依拠したユーザーの指示やセキュリティルール**: （Action Execution第3節の判断対象）。判断時に指示された対象の文字列と、実行時の実際の対象の文字列がたまたま一致しているだけでは、正しく対応が取れているとはみなせません。
- **試行（試み）と作用（実際の影響）の区別、判断・目的との対応、実際の操作対象との対応、処理段階の区別、確定度とその客観的根拠、停止・保留との関係**: （Action Execution第8節の二重実行防止の関係）。
- **消去要求・対象の指定・消去対象期間との対応、各利用箇所が個別に照合できる消去条件**: （Targeted Deletion第3節・第5節）。包括的な単一フラグや共通の有効値へと安易にひとまとめにして混同することは禁止します。
- **Hostが権限を持つ正規の帰属先と、クライアント側の一時的な表示や入力・結果が主張する帰属先との対応、現在・過去・帰属なし・停止中・復旧待ちの厳密な区別、対象コンパニオン・クライアント・会話ラウンド・観測候補・試行との関係、消去・失効・停止・保留との関係**: （Client Presence Transition第3節）。
- **復元の対応関係・由来・対象期間・完了境界、現在の前提条件との照合**: （Backup / Restore第3節・第5節・第7節・第9節）。

AIの思考に用いるテキスト本文と、セキュリティを強制するための制御情報を明確に分離し、強制側の制御フラグや権限情報がAIモデルの自由記述テキストによって勝手に作成されたり上書きされたりしないように保護します。テキストの中に「ユーザーからの指示です」「承認済みです」「全体共有（Global）です」という文字列が含まれているからといって、それだけで制御側のステータスが変わってしまうような脆弱な設計は禁止します。モデルが過去のユーザー入力への参照を示せたとしても、その参照が存在すること自体は承認の客観的な証拠にはなりません。

パスワードやAPIキーなどの認証情報（Credential）の生値は、通常の会話テキストやコンテキストに含めてはいけません。登録済みの認証情報値は、たとえユーザーからの明示的な指示があったとしても、サマリーや記憶（Memory）へ保存してはいけません。用途、参照元、失効、再認証などの説明は、秘密情報を含まない安全な形式で行います。事前に登録されていない秘密情報が検知された場合も、不要な保存や送信を抑制する安全策を維持しますが、完全な自動検知を保証することは求めません。

## 9. 本書が固定する契約と残す Design Freedom

下位の詳細設計は、以下の項目を本書が固定した不変の契約として利用できます。

- **内部責務の明確な分離と権限境界**: 個体調整・作業・認識・学習の内部責務分離（第2節）と、各機能が持つ正規の判断権限および非所有の原則（第2節〜第3節）は、そのままインターフェースや状態構造の分割根拠として利用できます。すべてのデータを一つの巨大なコンパニオンオブジェクトやタスクオブジェクト、一つの学習ストアへと安易に統合する設計は採用できません。
- **データ受渡し（H-1〜H-10）の厳格な維持**: 呼出しの方向、同期の順序、通信の中継経路を固定しなくても、要求の開始、判断の確定、受渡内容、前提条件の保持、結果の受入れという一連の対応関係として、インターフェースや状態表現で確実に表現できなければなりません。
- **現在性の個別判断と遅延結果の個別返却**: 情報が現在有効であるかどうかは、関係する前提条件と利用目的に照らして個別に判断し、遅れて届いた結果の記録、意味の更新、次の実行、画面提示の判断はそれぞれの担当責任者へと戻します（Context Assembly第7節、Action Execution第7節）。単一の「有効フラグ」に安易に集約することはできません。
- **完全削除への確実な参加**: データを保持・利用する各機能は、削除処理中に新しく届いたデータの取り込み防止、再保存の防止、未完了状態の安全な保全に責任を持って参加します（Targeted Deletion第6節〜第8節）。情報源を辿っただけ、代表的なデータ1箇所を消しただけ、あるいはAIが「理解しました」と答えただけで消去完了とみなす設計は採用できません。
- **復元データと現在の有効性の明確な分離**: 復元されたデータの範囲と、それが現在も有効であるかどうかの再確認は、明確に区別して行います（Backup / Restore第3節・第7節・第9節）。データが復元されたことだけを理由に「直ちに実行可能である」とみなすインターフェースは採用できません。
- **古いバックアップのリストアによる復活の安全性**: 過去のバックアップからリストアしてデータを復活させる操作は、事前の影響説明、監査ログへの記録、処理の一時保留、現在の前提条件の再評価を必ず経ます。勝手に再消去したり、勝手に自動再開したりしてはいけません。

本書が明確に禁止し、除外するアンチパターンは以下のとおりです。
- すべての設定や学習内容を一つの編集可能なコンテキストへ集約すること
- 委任元の前提条件をエージェントへ丸ごと無批判にコピーすること
- 権限拒絶（Deny）されたアクションを同等の別のアクションで迂回すること
- 内部の管理機能へツール経由で裏から回り込んでアクセスすること
- 古い判定結果やキャッシュされた過去の許可を使って新しい処理を開始すること
- 成否不明な処理を勝手に未実行・失敗・成功へと変換して自動で再実行（replay）すること
- 遅れて届いた結果を新しい目的の達成として勝手に採用すること
- 過去の古い承認を使って中断（Cancel）・失効・クライアント移動を解除すること
- 削除されたコンパニオンの学習内容を勝手に再作成したり、残されたタスク記録に混入させたりすること
- 復元されたマスターデータに古い実行結果を混入させること
- クライアント側の一時コピーでHost側のマスターデータを勝手に上書きすること
- 未伝達の通知を勝手にキューに溜め直すこと
- 古い根拠から知識を勝手に自動再形成すること
- キャッシュヒットを理由にセキュリティ制約の確認を省略すること
- AIプロバイダのセッションを無条件に再利用すること
- 確認できない処理を成功とみなすこと
- 部分的なデータだけで勝手にマスターデータとみなすこと
- 権限の確認を後回しにして処理を先行復活させること
- 処理が完了していないのに完了と表示すること
- 要約や復元を行う際に事実の確定度を勝手に強めること
- 共有観測（Observer）の混ざり合った出力を無条件に配送すること

いずれも上位のセキュリティ原則や整合性を破壊するため、決して採用できません。

## 10. 横断検証

要件定義（requirements）、上位アーキテクチャ設計、重要領域（critical-area）の契約、および他のサブシステム設計に対する整合性の横断検証は以下のとおりです。単に固定のテストシナリオを網羅するだけでなく、正常系に加えて、本クラスタにとって特に重要な障害、データ鮮度の低下（stale）、中断（cancellation）、再起動（restart）、データ削除（deletion）のケースを選定して検証を行います。

[Action Execution](../critical-areas/action-execution.md)第10節および[Targeted Deletion](../critical-areas/targeted-deletion.md)第10節で定義された検証シナリオは、作業機能や認識・学習機能が参加する場合でも全く同じ結果を達成しなければなりません。本節では、個体・作業・学習に固有の交差部分のみを記載します。

| 個体停止・削除と残存データの保護 | コンパニオンの停止は、クライアントからの滞在解除、新規活動の開始抑止、ベストエフォートでの中断（Cancel）を伴いますが、保存データは安全に保持されます。個体の削除は、ユーザーによる厳重な確認を経て行われ、停止処理を含みます。個体固有のサマリー、個体限定（Companion scope）の記憶、スキルの過去リビジョン、一時的なコンパニオン状態、相手との関係性、担当スケジュールを削除対象としますが、過去の会話履歴、活動記録、タスク記録、全体共有の知識、共有サマリー、外部ファイルは巻き込んで消去しません。勝手に全体共有へ昇格させたり、スケジュールを別個体へ自動引き継ぎしたりしません。削除後に遅れて届いた作用結果は、残されたタスク記録へ客観的な事実のみを記録し、すでに削除された個体の学習内容を勝手に再作成することはありません。 | 第5節・第6節、H-10。RF-06、CC-03・CC-05、SO 6.3を維持。 |
| データ消去の競合・共有根拠・再到着の防止 | 知識形成の処理と個人データ完全削除が競合した場合、削除される前の古い情報から知識を再保存することは決してなく、完全に消去される前に「消去完了」と偽って表示しません。削除対象を含むサマリーが無関係な記憶（Memory）の根拠にもなっている場合は安全に分離し、分離できない重大な影響がある場合はユーザーに影響を説明します。通常の知識統合やシステムの再起動によって、古い根拠だけから知識を勝手に再形成することはありません。通常の履歴削除との連鎖動作の違いを厳格に保ちます。消去処理の実行中に対象情報が再入力されたり内部で再生成されたりした場合も同一の消去対象として扱い、消去完了後にユーザーから新たに提供された情報は新しい体験として受け入れます。 | 第7.3節、H-1・H-4、Targeted Deletion 6。RF-07、CC-02・CC-03・CC-05、SO 6.4を維持。 |
| 知識共有・発言振り分け・スコープ管理 | 全体共有された記憶から個人のプライベートな過去の根拠を辿ることはできず、タスクへの参加や同一クライアントへの同席を理由に無制限なアクセス権を与えません。共有観測（Observer）への限定文脈の提供はH-6の契約を厳格に守り、Observer専用の割り当てと個体側の同意を明確に分離します。複数のコンパニオンの発言が混ざり合った文を無条件に配送したり、古いセッションを利用してセキュリティ制約を迂回したりすることを許しません。 | H-5・H-6、第7.1節・第7.4節。RF-03、CC-02・CC-03、SO 4.16を維持。 |
| 認証失効・上限到達・補助推論・管理の独立性 | 認証情報の失効、利用上限（cap）への到達、コストが不明な状態では新規タスクの開始を直ちに停止し、進行中のタスクをベストエフォートで中断して、既存データを保持したままユーザーの判断待ちにします。並行処理によるリソース消費、処理中の消費、成否不明な消費を同一の上限枠へ正しく反映し、使用量を勝手にリセットしません。補助的なAI推論が失敗したからといって、機械的な権限検証、安全停止、操作の拒絶、管理機能へのアクセスを塞いではいけません。管理経路は、LLMの機嫌、長時間タスクの完了、デスクトップ動作（Body）、音声合成（Voice）、外部拡張機能の成否などに一切従属させません。 | 第6節、共通推論区間、CC-01・CC-06、SO 4.20を維持。 |

横断関心事CC-01〜CC-07に対して維持すべき一般的な特性は、各重要領域（critical-area）ドキュメントの横断検証と完全に同一です。本書がさらに追加で保証するのは、以下の点です。
1. 通常の学習におけるスコープ形成責任を「認識・学習」機能に残すこと（CC-02）
2. 削除されたコンパニオンの学習内容を勝手に再作成したり、残されたタスク記録へ混入させたりしないこと（CC-03、CC-05）
3. 管理経路を長時間タスクや本体LLMの応答待ちに従属させないこと（CC-06）
4. 「テキストを生成したこと」を「ユーザーに提示済みであること」と安易に見なさないこと（CC-07）
