# Subsystem Detailed Design — 内部データ保全・消去

本書は Step 12 Subsystem Detailed Design として、**内部データ保全・消去（以下、保全・消去サブシステム）**単独の詳細設計を定める。

本書内の PE 番号は内部責務の参照用、DP 番号はサブシステム間のデータ受渡し（semantic contract）の参照用であり、製品要件IDではありません。

## 0. 位置付けと不変条件

上位設計との優先順位や矛盾が生じた場合の扱いは、[設計文書 README](../README.md#正本と優先順位) に従います。[Context Assembly](../critical-areas/context-assembly.md)、[Action Execution](../critical-areas/action-execution.md)、[Targeted Deletion](../critical-areas/targeted-deletion.md)、[Client Presence Transition](../critical-areas/client-presence-transition.md)（以下、Presence Transition）、[Backup / Restore](../critical-areas/backup-restore.md)（以下、Backup-Restore）の一般契約は、確定済みの契約としてそのまま利用し、再定義したり所有権を勝手に移転したりしません。本書内の SO は [State Ownership](../architecture/state-ownership.md)、DR は [Dependency Rules](../architecture/dependency-rules.md) の節番号を指し、CC / RF 番号は対応するアーキテクチャ文書（[artifact 一覧](../README.md#artifact-一覧)）の契約IDです。

本書は、新しいデータの担当責任者（semantic owner）や第二のマスターデータ（正本）となる万能マネージャー（何でも消せる Deletion Manager、何でも復元する Restore Manager、全データを抱え込む Persistence Owner、Policy Engine、統一ステートマシン、共通Context層、共通Clientセッション層など）を新設しません。また、個人データ完全削除（Targeted Deletion）やバックアップ・復元（Backup-Restore）というシステム全体の重要操作そのものを勝手に再設計することもしません。保全・消去サブシステムがそれらの契約を確実に成立させるために何を担い、各データの担当責任者へ何を要求し、何を受け取ってシステム全体の完了を判断するのかを具体的に定めます。

## 1. 選定理由

保全・消去サブシステムは、一見すると「システム内の全データを触る万能の存在」のように見えやすいため、後続の実装において誤って次のようなアンチパターンに陥る危険があります。

- Eneのすべてのデータのマスターデータ所有者（canonical owner）、中央永続化オーナー、汎用リポジトリオーナーへと勝手に格上げしてしまうこと。
- 全ドメインに対する通常の書き込み役、単一トランザクションの管理者、内部の全データ構造へ無制限にアクセスできる万能コーディネーターへと肥大化させてしまうこと。
- 個人データ完全削除（Targeted Deletion）、通常の忘却、訂正、失効、置換、統合、履歴ログの整理、容量制限（retention）、コンパニオン個体の削除、設定リセット、全データリセット、バックアップ復元という、全く目的の異なる操作を、安易に一つの「削除・初期化」としてひとまとめに混同してしまうこと。
- 監査ログ（Audit）やデバッグ記録（Debug capture）を、パスワードなどの秘密の隠し場所や、データ削除の抜け道、古いデータの正本化、事実の確定度を勝手に強める口実にするような「データの別保管庫」にしてしまうこと。
- 一部を局所的に削除・コピーしただけ、AIが「理解しました」と納得しただけ、通信できないクライアントを放置したまま、あるいは再起動したことだけを理由に、システム全体の処理が完了したと誤認してしまうこと。
- 通常時のデータアクセスやデータ変更まで、必ずこの保全・消去サブシステムを経由しなければならない必須の中央経路にしてしまうこと。

同時に、各サブシステムが個別に対応するだけでは、以下の「システム横断的な整合性」を保証できないため、保全・消去サブシステムを配置しないという選択肢も採れません。

- ユーザーに保存場所を意識させずに個人データを完全に消去し、削除後の再保存を確実に防止すること。
- 対象時点、参照関係、除外ルールを正しく揃えたフルバックアップを作成し、認証情報を確実に除外して、外部ファイルを勝手に集めないことを保証すること。
- 現在の認証情報を安全に維持し、外部の現実を巻き戻さず、単一の正本を守り、復元直後は処理を一旦保留して一括有効化する、安全なリストア（復元）を実現すること。
- 保護すべきデータを安全に守る「設定リセット」と、端末の信頼関係失効を伴う「全データリセット」を明確に区別すること。
- 既定でOFFになっている容量整理（retention）と、自然な記憶の忘却を混同しないこと。
- 再起動や再接続、リストアを跨いでも、未完了の処理や保留状態をHost側で確実に保全すること。
- 秘密情報や会話本文をログに残さずに処理完了をユーザーへ説明し、客観的な監査可能性を両立すること。

最初のマイルストーン（Targeted Deletionにおけるテキスト残存防止、知識形成との競合防止、再形成防止、共有根拠の部分削除、容量不足時の非自動削除、主要障害時のデータ保全など）は、保全・消去サブシステムの参加調整が正しく機能して初めて検証できます。バックアップからの復元やHostの自動起動は後続のマイルストーンですが、本書では確定済みの契約を正しく踏まえ、将来の受渡しを塞がない形で詳細を定めます。具体的な保存単位、データ消去クエリ、検証実装、端末の到達性確認方式などは本書では固定しません。

## 2. 内部責務の分離

内部責務は論理的な判断責任の分離であり、コンポーネント、Rustクレート、プロセス、サービス、スレッドの具体的な物理分割を指定するものではありません。PE-1〜PE-7は同じ保全・消去サブシステムに属しますが、一つの状態、一つのライフサイクル、一つの保存単位、あるいは一つのステートマシン（状態遷移機械）にひとまとめにされるものではありません。

| 内部責務 | 正規の判断権限（authoritative）を持つもの | 持ってはならない正本（マスターデータ） |
|---|---|---|
| PE-1 Targeted Deletionの参加調整 | ユーザーの明示的なプライバシー・セキュリティ目的と、対象の指定・影響・除外の対応付け。参加すべき領域の特定支援、各機能の局所結果・検証結果・未完了・保留の集約、システム全体の完了確定（Targeted Deletionに限る）。消去対象期間と、各利用箇所が個別に照合できる消去条件の対応付け。 | 記憶の重要度、相手との関係性の解釈、タスク達成やアクション成功の再判定。各機能の通常データの変更権限や任意ドメインの編集権限。外部サービスの認証情報の自動失効、外部コピーの消去保証。単一トランザクションや内部全構造への無制限アクセス権。 |
| PE-2 正常保全とBackup作成の調整 | 正常なデータ保存、マイグレーション、バージョンアップ時の復旧可能性の調整。各担当責任者による意味的整合性の確認の取りまとめ。バックアップの対象時点・内部範囲・参照関係・除外対象・暗号化保護の照合と作成結果の確定。保存先、バックアップ独自スケジュール、保持世代数、保護選択の管理。 | 各ドメインの意味決定。認証情報の秘密値の所有や復元。外部の実ファイルの収集。タスクスケジュール化。バックアップ作成にコンパニオンやタスクの稼働を必須とすること。バックアップコピーを現在動いているマスターデータ（正本）とみなすこと。 |
| PE-3 Restoreの調整 | リストア要求の受理・影響説明・処理の隔離・照合・置換成立・復元後の一時保留・一括有効化の調整。現在の認証情報ストアを維持することの確認。外部現実の非巻戻し・単一正本・データの非混合・権限の先行復活禁止の確認。古いバックアップとの交差（第4.4節）の説明と新しい正本扱いの確定。リストア失敗時に復元前の正常状態を維持することの確認。 | 外部の現実を巻き戻すこと。秘密情報を勝手に復元・巻き戻すこと。復元された参照や同意情報から自動で処理を開始すること。古い情報を現在の事実とみなすこと。古い実行結果やクライアント側の一時コピーを混入させること。復元されたデータが存在することだけを理由に「直ちに実行可能」とみなすこと。 |
| PE-4 Resetの調整 | 設定リセットの範囲調整と保護対象データの保持確認。全データリセットにおける削除対象の列挙・厳重な確認・内部消去・処理中データやクライアント一時コピーの扱い・端末信頼関係の失効の調整。 | 各設定の意味決定。外部ワークスペース・外部スキル・ユーザーが保存した外部バックアップの勝手な削除。コンパニオン削除との混同。監査ログの別保管庫化。通信できないクライアントの物理的消去を「確認済み」と偽ること。 |
| PE-5 保持方針・retention / cleanupの調整 | 通常の会話履歴やログの削除・保持期間変更の調整。学習リビジョンや会話サマリーに対する明示的なオプトイン設定（retention cleanup）の適用調整。自動クリーンアップの既定OFFの維持。通常の忘却・履歴整理と、個人データ完全削除（Targeted Deletion）・コンパニオン削除の目的の分離。 | 記憶の意味・重要度・スコープの意味の決定。自動削除を勝手に既定で有効化すること。自然な忘却を物理削除にすり替えること。履歴整理を学習内容やサマリーへ勝手に連鎖（cascade）させること。容量不足を理由に黙って勝手にデータを削除すること。 |
| PE-6 Audit / Debugの保全上の扱い | 監査ログ（Audit）の追記順序と保持期間のマスターデータ管理。デバッグ記録（Debug capture）の明示的な対象・内容・短期失効・停止・削除と全体の成立管理。本文の別保管庫化の禁止、事実の確定度を勝手に強めないことの維持。 | 元の事実の意味の再判定（アクション成功、権限の妥当性、タスク達成等）。会話テキストやファイル本文・秘密情報・削除されたプライベート情報の保持。監査ログを元にした処理の再生や自動実行の入力化。テレメトリの自動送信。すべての生データを恒久保存することの要求。 |
| PE-7 全域操作状況のHost保全とOwner説明 | 操作の同一性、参加関係、消去条件、保留状態、再保存防止のHost側での安全な保全。再起動・再接続・リストアを跨いでの状態維持。処理中（pending）・通信不能（unreachable）・検証失敗（failed verification）の明確な区別保全。客観的事実と会話本文を分離したユーザー説明用材料の管理。 | 各ドメインへの通常書き込み役、単一トランザクション、内部全構造への無制限アクセス権。削除対象の本文を保持して完了の根拠とすること。一時バッファが消えたことだけを理由に完了とみなすこと。AIが納得したことだけを理由に完了とみなすこと。 |

各責務の関係の要点は次のとおりです。

- PE-1〜PE-4は操作種別ごとの調整役であり、互いのライフサイクルを共有しません。個人データ完全削除、バックアップ、リストア、設定リセット、全データリセット、コンパニオン削除、通常削除、容量整理を、安易に一つのステートマシンや一つの完了条件にひとまとめにしてはいけません。
- PE-7はPE-1〜PE-4を横断する共通の保全・説明責任であり、独立した第8の操作ではありません。PE-1〜PE-4のいずれも、PE-7によるHost側での安全な状態保全なしにはシステム全体の完了を確定できません。一方で、PE-7単独でいずれかの操作を完了させることもできません。
- PE-5（保持方針）は、PE-1（個人データ完全削除）とは全く異なるデータ保持の取り決めであり、PE-1へ勝手に読み替えたり、PE-1のルールを流用したりしてはいけません。PE-6はPE-1〜PE-4の完了説明に必要な材料を受け入れますが、元の事実の意味を再判定することはありません。
- PE-2の正常保全はPE-3のリストア（復元）と対になりますが、通常の再起動をリストアのような一律の全データ復元確認へと不必要に拡大してはいけません。PE-4の全データリセットは、PE-1の個人データ完全削除とは消去範囲が異なり、過去の歴史的記録（historical record）の扱いも異なります（第5節）。

保全・消去サブシステムは、以下のような権限（authority）を取得しません。
- 記憶（Memory）を書き換える権限
- タスクの状態（Task state）の意味を決定する権限
- 会話履歴（History）の内容を勝手に生成する権限
- 権限ルール（Permission）を変更する権限
- 認証情報（Credential）の秘密値を所有する権限
- クライアントへの滞在状態（Client presence）を決定する権限
- AIプロバイダの割り当てや能力の意味を決定する権限
- アクションが成功したかを勝手に確定する権限
- ユーザーへの報告が完了したかを勝手に確定する権限

システム横断的な操作で変更が必要な場合でも、必要な意味判断や局所的なデータ操作は既存の担当責任者が行い、本書第4節の受渡し契約（semantic contract）を通じて参加します。

## 3. 管理する logical state

ここで説明する状態は、特に「外部」「コピー」「一時データ」と明記されているものを除き、Host側で管理される内部状態を指します。永続化の具体的な実装担当、保存単位、排他制御の書き込み役、トランザクション方式などは固定しません。また、通常のデータ担当責任者は、正当なシステム全体のデータ消去要求への参加を拒絶することはできません。

### 3.1 保全・消去が意味ownerとなる state

保全・消去サブシステムが以下の状態の担当責任者（owner）となる理由は、保持方針が「記録の保全期間や消去範囲」、操作状況が「横断処理の成立や未完了の事実」、バックアップ設定・結果が「復旧用コピーの作成と管理」、監査ログの順序やデバッグ記録が「データ保全に関する固有の契約」をそれぞれ表しているためです。元となる客観的事実の意味は、発生元のサブシステムに残します。この明確な理由を持たない一般的な運用設定まで抱え込んではいけません。Hostの自動起動設定は、入出力・提示機能が管理します（SO 4.17）。

| State（論理状態） | 管理する意味・立場 | 他の状態との違い |
|---|---|---|
| History / 対象log / Audit等の保持方針 | ユーザーが選択した記録対象、保持期間、手動削除の対象範囲と影響。 | データの種類ごとの個別の取り決めを守り、学習内容や判断根拠へ一律の保持期間を機械的に適用しません。自動削除は既定では行いません。 |
| Learning revision・Summary等の容量管理方針 | 自動容量整理（retention / cleanup）の既定OFF設定。ユーザーの明示的なオプトインによる有効化設定。 | 通常の自然な忘却や、履歴ログの保持整理とは明確に区別します。認識・学習機能が対象の意味や根拠、復元への影響を示し、保全・消去機能が明示された方針の適用を調整します。 |
| Targeted Deletion・Reset・Restore等の操作状況 | 操作の目的、対象範囲、参加している各機能、影響、完了した範囲、未完了・失敗・検証結果、必要な処理の一時保留。 | 完了の客観的証拠は参加している各担当責任者から取得します。各ドメインの通常のデータ変更判断や許可状態を抱え込まず、共通の単一ステートマシンを押し付けません。 |
| Backup設定・作成結果 | 保存先の指定、バックアップ独自の定期スケジュール、保持世代数、暗号化保護の選択、対象時点、整合性、成功・失敗の結果。 | タスクの実行スケジュールとは別物です。バックアップ作成のためにコンパニオンやタスクが稼働中であることを必須としません。 |
| 作成済みbackup | 内部状態の対応関係を正しく保持した外部コピー。 | 現在動いている最新のマスターデータ（正本）ではありません。保存先が同じHost上であっても外部コピーとしての境界を厳格に保ちます。明示的なリストア操作を経ずに、その内容を通常の実行用マスターデータへ戻してはいけません。 |
| Auditの追記順・保持 | 各機能から提供された客観的事実を、どの順序で監査記録として受け入れ、保持しているか。 | アクションの成功や権限の妥当性を再判定するものではありません。追記順序が保証されていることは、「永久に不変で絶対に削除できない」という意味ではありません。 |
| Debug captureの成立 | ユーザーが明示的に指定した記録対象、内容、有効期間、停止、削除、およびキャプチャ全体の成立状況。 | 通常のログ記録とは異なり、短期的に明示的に有効化される取り決めです。実際のキャプチャ処理には各対象機能が参加します。 |

バックアップの暗号化保護はユーザーが選択できます。暗号化せずにバックアップを作成する場合は、プライベートなデータが含まれることを事前にユーザーへ明示します。システム内部からのデータ削除と、ユーザーが設定したバックアップ保持世代数に基づく古いコピーの整理は、全く別の操作です。

システム横断的な操作の未完了状態や再保存防止ルールなど、安全のために継続して守る必要のある状態は、クライアントや一回きりのメモリ処理だけに頼るのではなく、Host側で確実に保全します（PE-7）。処理の途中でHostが再起動した場合であっても、勝手に「完了した」と誤認したり、保留状態を黙って解除したりしてはいけません。また、完了の証拠を残すためと称して、削除対象のパスワードやプライベートな本文をログに書き残してはいけません。

リストア復元後の「保留理由」と「復元の成立」は保全・消去サブシステムが担当し、現在の実行許可や制約の有効性は権限・制約サブシステムが判断し、タスクなどの実際の再開は各活動の担当責任者が行います。これらの異なる状況を、安易に単一の「保存済み / 実行可能」というフラグにひとまとめにしてはいけません。

### 3.2 保全・消去が所有しない state（既存ownerに残る）

保全・消去サブシステム以外のドメイン状態は、状態所有規則（SO第4節）で定められた各担当責任者に残り、保全・消去サブシステムがそれらを奪うことはありません。保全・消去サブシステムを取り除いたとしても、各ドメインデータの担当責任者は一意に説明できます（第10節末尾）。クライアント固有の接続情報は端末側に属する別枠であり、利用・更新・再ペアリングは接続・存在機能、秘密の保護は認証秘密機能、Host側の信頼・許可・失効は権限・制約機能が担当します。

通常時のデータアクセスやデータ変更において、保全・消去サブシステムを必須の中央経路にしてはいけません。通常のデータ参照、知識形成、タスク委任、メッセージ送信、データ保存、画面提示、アクション実行は、各担当責任者と各利用箇所の直接の契約によって成立し、保全・消去サブシステムを経由しません。保全・消去サブシステムが関与するのは、システム全体の横断操作の調整、保持方針の適用調整、監査・デバッグ記録の保全、操作状況の保全のみです。通常の学習形成、タスク遂行、会話、画面観測、AI推論の利用を、保全・消去サブシステムの応答待ちにしてはいけません。管理経路の確立においても、LLMの応答、長時間タスクの完了、デスクトップ動作（Body）、音声合成（Voice）、外部拡張機能の成否などに一切従属させません（DR 7.4）。

### 3.3 canonical / derived / temporary / external reference の扱い

- **canonical（マスターデータ / 正本）として参照するもの**: 各ドメインの意味責任者が管理する最新の認識、元の記録、タスク進捗、作用の確定度、制御ルール、認証用途など（第3.2節）。保全・消去サブシステムが管理する保持方針、操作ステータス、バックアップ設定、監査順序、デバッグ成立状況。なお、保存された許可ルール、判定結果のコピー、解決済み経路、AIプロンプトコンテキスト内の許可文、キャッシュされた判定、次回表示予定データ、コスト集計値、クライアント上の表示、過去の滞在記録、再配置の希望位置（hint）、復旧先記録、AIプロバイダのセッション残骸、バックアップコピー、部分的な置換途中の状態などは、決して正本として扱いません。
- **derived（派生物）として扱うもの**: 報告用の要約、由来（provenance）の説明、進捗表示、BodyやVoiceへの出力、ベクトルデータ（embedding）、検索インデックス、類似度スコア、プロンプトキャッシュ、AIプロバイダのセッション、一時的な推論コンテキスト、解決済みの通信経路、次回表示データ、コスト集計値、解決済みの割り当て経路。派生物を生成・保持・破棄する各機能は、元データとの対応関係や利用範囲を正しく把握し、訂正・スコープ変更・Targeted Deletionへ責任を持って参加します。古い派生物から、現在の状態や権限、滞在先を勝手に復活させてはいけません。
- **temporary（一時データ）として扱うもの**: 生の画面観測データ、生の音声データ、ツールの詳細なペイロード、内部の思考プロセス（chain-of-thought。これらは通常保存しません）、クライアント側の表示用コピー、入力途中のテキスト、音声バッファ、観測候補データ、推論中のコンテキスト、MCP Appsの表示データ、実行中のメモリバッファ。失われてもよいのはこれらの一時的な表現形式のみであり、正式に受理したユーザー指示、必要な作業記録、未伝達メモ、作用不明の記録、システム横断操作の未完了状態まで失ってよいわけではありません。
- **external reference（外部参照）として扱うもの**: 外部ワークスペースの実体ファイル、案内ファイル、外部スキルファイル、外部成果物、外部キャラクターパッケージ、スキルの原本、エクスポートされたコピー、ユーザーが保存したバックアップ、AIプロバイダやMCPサーバー側の固有状態や保持コピー。内部に保持している一時コピーや内部に取り込んだデータ、Eneの管理下にある一時データは、内部の利用・消去責任の対象に戻ります。「外部コードに由来するデータだから」という理由だけで消去対象から除外してはいけません。

体験（Experience）とは出来事と結果を表す概念であり、すべての活動ログを丸ごと溜め込むような新しいマスターデータ保管庫（canonical Raw store）を設けることはありません。会話サマリーは保持すべき客観的証拠（evidence）であり、バックアップは保護された外部コピーであって、どちらも現在の記憶（Memory）の代用正本にはなり得ません。

## 4. Subsystem間の受渡し（semantic contract）

「AがBの関数を呼ぶ」といった実装構造を先に決めるのではなく、要求の開始、正規の判断、受渡内容、失ってはならない前提条件、結果の受入れという一連の対応関係を定めます。非同期メッセージ、同期呼び出し、共有メモリなどの具体的な実現メカニズムは、下位設計の自由度として残します。

DP番号は本書内の契約参照用です。

### DP-0 協調の共通原則（ownership takeoverの禁止とglobal completionの必要性）

- システム横断的な操作では、調整役（Coordinator）が操作全体の成立条件を揃え、各データの担当責任者（state owner）が自分自身のデータの意味、対象範囲、利用中データへの影響、処理結果に責任を持ちます。調整役が全ドメインの通常の意味判断を勝手に代行する構造にしたり、参加者全員が共同所有として互いに責任を押し付け合ったりする構造にしてはいけません。
- 通常のデータ担当責任者は、正当なシステム全体の消去、復元、リセット、保持整理への参加を拒否できません。同時に、保全・消去サブシステムも各データの通常変更権限を勝手に取得することはありません。将来の設計で新しいデータの保存先や利用先を追加する場合は、この横断操作への参加責任も必ず定義しなければなりません。
- 参加責任には、対象となる状態、元の記録、判断根拠、リビジョン、共有参照、派生データ、内部コピー、現在処理中のデータ、遅れて届く結果の把握、必要なデータ変更や処理保留、完了または未完了の正確な報告が含まれます。「自分の手元で消した」「保存した」という局所的な結果だけでは、システム全体の横断操作の完了を証明したことにはなりません。
- 各担当責任者は、システム全体の完了を待たずに局所的な処理結果を調整役へ返すことができますが、結果を返したことだけを理由に必要な保留状態を勝手に解除してはいけません。対象外の通常の活動まで一律に停止させる必要はありませんが、「対象範囲のデータが利用されたり再保存されたりするのを確実に防ぐこと」が操作成立の絶対条件となります。
- 処理完了の説明は、参加した各機能が確認した客観的な証拠に基づいて行われなければならず、AIが「理解しました」と納得したという要約文で代用してはいけません。各担当責任者は、自身の管理するデータだけでなく、保持しているコピー、過去リビジョン、根拠、共有参照、派生データ、処理中の利用、遅れて届く結果との関係も含めて参加させます。

### DP-1 Targeted Deletionの受渡し

重要領域ドキュメント `targeted-deletion.md` の一般契約を、PE-1とPE-7の調整および各担当責任者の参加へと具体化します。一般契約そのものを再定義するものではありません。

| 構成要素 | 正規の判断権限を持つ責務 | データの受渡し・参加内容 |

| 対象指定の二層構造 | 保全・消去サブシステムが、機械的条件（必須・LLMに依存しない）と意味的条件（補助・完全性は保証しない）の区別を厳格に保ちます。 | 意味的な探索のために補助的にAI推論を利用する場合でも、その推論自身に対するモデル割り当ての同意、認証用途、利用コスト制限を正しく適用します。審査対象となっているアクションの許可や実行を、この処理の先行条件にしてはいけません。 |

| 各参加者の局所結果 | 各担当責任者。自身の管理範囲における対象データの除去または復元不能化、必要な保留・再保存防止の適用、範囲内の検証。 | 局所的な処理結果を返したことだけを理由に、必要な保留状態を勝手に解除してはいけません。対象外の通常の活動まで一律に停止させることは必須としません。 |

| 再起動を跨ぐ未完了の保全 | 保全・消去（PE-7）がHost側で安全に保全します。 | 参加している各担当責任者はシステム全体の完了前に局所結果を返すことができますが、局所結果を返したことだけを理由に再保存防止の制限を解除してはいけません。 |

| ユーザーへの説明 | 保全・消去（PE-7）が客観的事実と会話本文を明確に分けて説明を作成し、入出力・提示機能が管理画面へ表示します。 | 保持すべき客観的事実と、保持してはならない削除対象本文の区別（第4.7節）を厳格に守ります。外部へ送信されたデータ、エクスポートされたファイル、バックアップ済みの外部コピーまで削除されたかのように偽って表示してはいけません。内部に露出した認証情報コピーの消去と、外部サービス側でのAPIキー失効・再発行は、別の操作として説明します。 |

新規処理の開始禁止と進行中処理の扱い、用途別のコンテキスト受け入れにおける消去条件の適用、事実の確定度の保持、LLMに依存しないセキュリティ強制境界、消去処理中の再到着・再生成データの取り込み、古い由来と新規提供データの区別、キャッシュ・セッション・通信経路の再利用禁止、共有根拠の分離は、`targeted-deletion.md` 第5節〜第6節の契約をそのまま適用し、本書で勝手に緩和してはいけません。権限・制約機能および各利用箇所が、データの参照・変換・送信・保存・提示・作用の各ポイントで消去条件を確実に適用します。データ消去が行われたことを理由に、過去のアクション結果の確定度を勝手に成功・失敗・未実行へと書き換えてはいけません。

**コンパニオン削除との関係**: コンパニオン個体の削除ライフサイクル調整は、個体調整機能に残ります。保全・消去サブシステムは、内部データ削除がシステム全体で正しく成立するための調整にのみ参加します（SO 6.3、DR 7.5）。コンパニオン削除は「その個体固有の現在の状態や学習データ」を削除する操作であり、過去の会話履歴や活動ログを消す操作ではありません。Targeted Deletionの対象となる個人情報が含まれている場合は、コンパニオン削除後に残された会話履歴やログからもその情報を完全に除去します。会話サマリーを「歴史的ログだから」という理由で分類し直して残すことは禁止します。

重要領域ドキュメント `backup-restore.md` 第3節・第6節の一般契約を、PE-2とPE-7の調整および各担当責任者によるデータ提供へと具体化します。

| 構成要素 | 正規の判断権限を持つ責務 | データの受渡し・参加内容 |

| システム全体の成立 | 保全・消去（PE-2）が確定します。 | 処理中のメモリ空間を丸ごとダンプして保存するような過剰な設計は要求しません。意味の上で処理を継続するために必要な内部状態を正しく対応付け、一時バッファや外部プロバイダのセッション等の復元を前提にしてはいけません。実行中のアクションや成否不明な処理がある場合、最後に正常記録された状態が外部世界の最新状態と一致しているとは限らないことを前提とします。結果不明な処理を勝手に「未実行」に戻して正常なコピーと偽ってはいけません。 |

通常のデータ保存、データベースマイグレーション、バージョンアップに伴う移行処理も、PE-2の調整対象です。各担当責任者の意味的整合性と、保全・消去サブシステムの復旧可能性を正しく対応させ、処理が完全に成功するまで直前の正常状態を確実に保護します。アップグレード前にはバージョン互換性や必要なバックアップの有無を確認し、失敗時にはその理由を明確に示します。互換性のないダウングレードが成功することを前提とせず、起動前にユーザーへ警告します。

### DP-3 Restoreの受渡し

重要領域ドキュメント `backup-restore.md` 第3節〜第5節・第7節・第9節の一般契約を、PE-3とPE-7の調整および各担当責任者による確認へと具体化します。

### DP-4 旧backupのRestoreの受渡し（Owner decisionの落とし込み）

以下は確定済みの製品判断（Product Decision）であり、本書で勝手に変更することはありません。重要領域ドキュメント `backup-restore.md` 第8節の確定契約に従い、各参加機能へと具体化します。

- 過去に作成されたバックアップを、個人データ完全削除（Targeted Deletion）が完了したからといって自動で改ざんしたり勝手に再消去したりしません。バックアップ作成後に完全削除された個人情報が古いバックアップファイル内に含まれていたとしても、すでに保存されているバックアップファイルを黙って勝手に書き換えてはいけません。
- リストアを実行する前に、「過去に削除された個人情報が再びシステム内に復帰する可能性があること」をユーザーへ分かりやすく説明します。古いセキュリティルール、同意設定、スケジュール設定が復活し得る点と合わせて、PE-3の受付・説明フェーズで明示します。
- ユーザーがそのリスクを理解した上で明示的にリストアを実行した場合、それは「ユーザーが過去の状態を意図的に再導入した」とみなして扱います。復元された情報は新しいマスターデータ（正本）として扱われ、その後の新しい体験（Experience）の根拠になり得ます。これは「削除前の古い根拠から勝手に知識を再形成することの禁止」ルールに対する抜け道ではありません。
- 過去に実行されたTargeted Deletionを、リストア完了後に自動で再適用することはありません。復元された情報を改めて消去したい場合は、ユーザーが明示的に新しいTargeted Deletionを実行する必要があります。ただし、これを「削除前の古い根拠だけに基づいて知識を自動再形成してよい」という例外にしてはいけません。
- キャッシュ、プロバイダセッション、遅延して届いた結果などによって「意図せず勝手にデータが再出現してしまう現象」とは明確に区別します。前者はPE-1の再保存防止ルールによってシステムが厳格に防ぐべき事故であり、後者はユーザー自身の明示的な判断に基づく正当な操作です。復元が成立した後の「一時保留」「一括有効化」「最新の前提条件の再評価」というステップを経ることなく、復元された情報を送信・アクション・学習へ自動で利用してはいけません。
- リストアが実行されたという客観的事実は監査ログ（Audit）に記録して検証可能にしますが、削除対象の本文テキストを「監査のため」と称して別保管してはいけません。完了記録、監査ログ、ユーザーへの説明文そのものに、削除対象となったプライベートな本文を再保存してはいけません。リストアによって情報が復活したからといって、外部送信、エクスポート、バックアップ済みの外部コピーに対する消去保証の境界を混同してはいけません。
- 未完了の消去処理とバックアップ・リストアが重なった場合は、セキュリティ制約を無視した「何事もなかったかのような即実行可能なコピー」を作らず、未完了状態、保留、再保存防止ルールをHost側で安全に保全します。再起動、再接続、リストアの後であっても、未完了の認識と必要な保留状態を確実に維持します。
- 消去処理の実行期間中に、リストアに由来して削除対象情報が再び持ち込まれた場合、各受け入れ・保存箇所が現在進行中の消去条件を適用し、古い根拠だけからの再形成や遅延した再保存を確実に防ぎます。指定された文字列は、機械的な検索、除去、残存検証の対象に必ず参加させます。

本書で勝手に新しいプライバシー規約を策定することはありません。上記は、すでに決定済みの「自動再形成の禁止」と「ユーザーによる明示的なリストア」を両立させるための設計であり、外部コピーの消去保証や、復元後の自動実行を許可するものではありません。

### DP-5 Resetの受渡し

| 操作 | 調整役（Coordination）と各参加機能の責任 | 成立条件 |

| 全データReset | 保全・消去（PE-4）が削除対象の列挙、ユーザーによる厳重な確認、内部データの完全消去、処理中データやクライアント一時コピーの扱い、端末信頼関係の失効を調整し、認証秘密を含む全機能の担当責任者が参加します。 | Host内部のすべてのEneデータおよび認証情報が完全に削除され、古い処理や一時コピーから内部状態が勝手に復旧しないようにします。Host側の端末ペアリングやデバイス信頼関係も完全に失効し、古い端末の認証情報だけで勝手に再接続・復活することはできません。通信できないクライアントの物理的な消去を「確認済み」と偽ってはいけません。通常のコンパニオン削除とは異なり、内部の歴史的記録（historical record）も保持対象外となり消去されます。外部ワークスペースの実ファイル、外部スキル、ユーザーが別の保存先へ作成したバックアップは削除せず、何が外部に残るかをユーザーに明確に説明します。局所的なデータ削除や、画面の初期化だけで「全データリセット完了」とみなしてはいけません。 |

リセット完了後は、何が削除され、何が外部に残っているかをユーザーが確認できるようにします。「設定リセット」「全データリセット」「バージョンアップ」「バックアップ復元」「通常の再起動」を、安易に同じ復旧操作として混同してはいけません。

### DP-6 retention / cleanupの受渡し

通常の容量整理（retention）は、個人データ完全削除（Targeted Deletion）とは全く異なります。**容量の都合による自動削除は既定（デフォルト）では一切行わず、ユーザーが明示的に自動容量整理（retention / cleanup）を有効化（オプトイン）した場合にのみ行います。**

| 操作 | 調整役（Coordination）と各参加機能の責任 | 成立条件 |
|---|---|---|
| 通常History / log削除・保持期間変更 | 保全・消去（PE-5）が、ユーザーが指定した対象、影響範囲、保持期間の適用を調整します。個体調整や作業などの各機能が対象ログを確認し、認識・学習機能が残る根拠関係を確認します。 | 指定されたログ情報が安全に整理され、そこからすでに形成された学習内容やサマリーへ勝手に削除が連鎖（cascade）していないことを確認します。失われた元の参照についてユーザーに説明でき、外部コピーまで消去したかのように偽って表示しません。既定では自動削除しません。 |
| Learning revision・Summary等の明示retention cleanup | 保全・消去（PE-5）が、ユーザーのオプトイン設定に従って適用を調整し、認識・学習機能などの既存の担当責任者が、対象データと残る参照関係の整合性を処理します。 | 既定OFFであり、ユーザーの明示的な設定がない限り、ディスク容量不足を理由にして過去のリビジョンや判断根拠を勝手に削除してはいけません。設定された範囲と、判断根拠への参照や過去リビジョンへの復元に対する影響をユーザーへ分かりやすく説明し、自然な忘却や個人データ完全削除へと勝手に読み替えてはいけません。すでに削除されたリビジョンや根拠について「まだ保持されている」「復元できる」と偽ってはいけません。具体的なデータ分類（data class）、保持期間、容量制限、優先順位、削除アルゴリズムなどは本書では固定しません。 |

容量整理（retention）によって、記憶（Memory）の意味上の「忘却」や学習リビジョンを暗黙のうちに上書きしてはいけません。通常の忘却とは「思い出しやすさ（想起スコア）の抑制」であり、保存済みの内容、過去のリビジョン、判断根拠を物理削除するものではありません。有効期限切れ（失効）、置換、統合についても同様であり、容量上限を言い訳にしてデータ保持原則を迂回してはいけません。通常の会話履歴やログを整理する場合でも、すでに形成された学習内容やサマリーは残し、元の生データが参照できなくなったことのみを明示します。容量不足が発生したことだけを理由に「ユーザーがオプトインした」とみなすことは禁止します。

コンパニオン削除、Targeted Deletion、容量整理（retention）、リセット、リストアは、それぞれ全く異なる目的を持つ操作です。内部で同じファイル削除の仕組みを利用できたとしても、操作の目的や保証範囲を混同してはいけません。

### DP-7 Audit / Debugの受渡し

監査ログ（Audit）やデバッグ記録（Debug data）が、新しい秘密情報の隠し場所、Targeted Deletionの抜け道、古いデータの正本化、あるいはアクション結果の確定度を勝手に強める口実になってはなりません。一方で、システム横断操作の成立、失敗、リストアの事実などをユーザーへ説明し、客観的に検証するために必要な「非秘密・非本文」の情報まで失わせてはいけません。

| 構成要素 | 正規の判断権限を持つ責務 | データの受渡し・参加内容 |
|---|---|---|
| Auditの元記録の意味 | 各事実の発生元。アクション結果は実行・拡張機能、権限や同意の変更は権限・制約機能、認証情報の参照や失効は認証秘密機能、タスク状態は作業機能、データ削除・リセット・リストアの成立は保全・消去機能が、客観的な事実データを供給します。 | 監査ログの記述から元の状態を勝手に再構成したり、直接逆流して更新したりするような、逆転した正本関係を作ってはいけません。現在の有効な状態については、必ず元の担当責任者へ参照を戻して確認します。 |
| Auditの順序・保持 | 保全・消去（PE-6）。提供された事実をどの順序で監査記録として受け入れ、保持しているかを管理します。 | 元のアクションの成功や権限の妥当性を勝手に再判定してはいけません。訂正情報についても由来と発生順序を正しく保持します。追記順序で確認可能であることは、「永久に不変で絶対に削除できない」という意味ではありません。 |
| 保持する内容 | 各供給元が必要な事実のみを供給し、保全・消去機能がそれを受け入れます。 | 監査ログには通常、会話テキスト、ファイル本文、パスワードなどの秘密値、削除されたプライベートな内容を含めません。各機能は不要な本文や秘密値を出力せず、記録側もデータの別保管庫を作らないようにします。保持方針、保存容量、削除時の影響はユーザーが管理できます。Targeted Deletionが実行された場合は、監査ログ内に残った対象情報も完全に除去または復元不能化します。完了記録、監査ログ、ユーザーへの説明文そのものに、削除対象本文を再保存してはいけません。 |
| Debug capture | 保全・消去（PE-6）が、明示的な記録対象、内容、有効期間、停止、削除、および全体の成立を管理し、実際のキャプチャ処理には各対象機能が参加します。 | 通常のログ記録とは異なり、短期的に明示的に有効化される取り決めであり、登録済みの認証情報値を含めることは決してありません。内部の思考プロセスや生の全データを通常時から恒久保存する理由にしてはいけません。デバッグ記録に登録外の秘密値や不要な本文が含まれる可能性をユーザーへ事前に示し、ユーザー自身の操作でいつでも停止や削除ができるようにします。 |
| 確定度の扱い | 各事実の担当責任者。 | 由来、失敗、停止不能、未保存、次の安全な選択肢などの説明は、内部思考ログや詳細なプロンプト本文を晒すことなく行います。タスク達成、作用、保存、提示、監査の確定度を、要約、翻訳、復元などの処理を通じて勝手に強めてはいけません。監査記録を元にして過去の処理を再生したり、自動実行の入力として使い回したりしてはいけません。遅れて届いた報告や訂正された報告も、元の対象との対応関係を正しく維持します。 |
| テレメトリ（Telemetry） | ユーザー自身。 | 外部への自動送信は決して行いません。外部と共有する場合は、ユーザー自身が内容と送信先を確認した上で、手動でエクスポートして送信します。 |

認証情報（Credential）の秘密値は、バックアップに決して含めません。リストア時も、現在の安全な認証情報ストアを維持します（DP-3）。監査ログ、デバッグ記録、バックアップファイルへ秘密の生値を流出させないことは、認証秘密機能と、データを受け入れ・保存・表示する各機能との連携によって確実に守られます。

### DP-8 全域完了とfailure / restartの共通扱い

具体的なステートマシンやトランザクションプロトコルは固定しませんが、後続設計は少なくとも以下の4つの論理的な状態区分を厳格に保持しなければなりません。

- **局所完了（Local completion）**: ある参加先が、自身の管理・利用範囲について、対象データの除去または復元不能化、データの提供、整合性確認、保留の適用、範囲内の検証を完了した状態。局所的な結果を返したことだけを理由に、必要な保留状態を勝手に解除してはいけません。
- **保留中 / 通信不能（pending / unreachable）**: データ消去、復元、リセットの処理中に、ネットワーク切断や再起動などが発生し、一部の範囲の処理・検証・確認が未確定となっている状態。通信不能や確認不能を勝手に「成功」と読み替えてはいけません。
- **検証失敗（failed verification）**: 機械的な残存検証で削除対象の文字列が検出された、依存関係が解消できない、意味的な対象範囲を確定できない、参照関係が揃わないなど、完了を確定できない状態。どの部分が不足しているかを明示します。
- **システム全体の完了（Global completion）**: 保全・消去サブシステムが、参加しているすべての機能の局所完了、検証結果、未完了状態を照合し、内部全域において処理が完全に成立したと確定した状態。局所完了の単なる寄せ集めではなく、DP-1〜DP-5の各成立条件をすべて満たす必要があります。

完了扱いにしてはいけないアンチパターンは以下のとおりです。
- 一部を局所的に削除・コピーしただけで、別の保存先、コンテキスト、クライアントからデータが戻る可能性を放置している場合
- 通信不能（unreachable）や未完了（pending）が残っているのに、必要な確認を省略して完了とみなす場合
- 機械的な残存検証が失敗した、あるいは未実施であり、データが残っていないことを証明できない場合
- 消去処理の期間中に再到着・再生成されたデータの取り込み、遅延した再保存の防止、古い根拠からの再形成防止のいずれかが成立していない場合
- 意味的な探索の検出限界を理由にして、既知の依存関係の追跡をサボったり、未確認の範囲を完了とみなしたりする場合
- 外部コピーの消去を、内部の完全消去の完了条件に混ぜてしまう場合
- Eneの管理下にある内部コピーを「外部データだから」と言い訳して消去対象から除外する場合
- 完了記録、監査ログ、説明文に削除対象本文を書き戻してしまい、完了の証拠自体がデータの復元源になってしまう場合
- 部分的な置換、データの混同、権限の先行復活が存在する場合

参加している各担当責任者は、自身の局所的な処理や検証結果を、システム全体の完了を待たずに返すことができます。調整役はこの責任分担に依拠し、内部の全データ構造に対する無制限なアクセス権を要求しません。互いが相手の承認や成功を無限に待ち続けるような循環依存を、アーキテクチャの前提にしてはいけません。

## 5. Lifecycleとの関係

ライフサイクルの変更の多くは、データの担当責任者（owner）が別の人間に移るのではなく、「同じ担当責任者が管理する状態について、存続期間・利用可能性・参照できる範囲が変化する」ことを意味します。目的の異なる複数の操作を、安易に一つの初期化処理や一つのステートマシン（状態遷移機械）にひとまとめにして混同してはいけません。

| Backup / restore | PE-2、PE-3、PE-7の調整対象です。データのコピーを作成し、ユーザーからの明示的なリストア要求が成功した際には、現在の認証情報ストアを除く対象内部状態をバックアップ時点の状態へと一括置換します。 | バックアップコピーは現在動いているマスターデータ（正本）ではありません。復元直後は実行を一時保留し、外部の世界は巻き戻らないことを考慮します。認証情報は現在の安全なストアを維持して整合性を確認します。 |

全体共有（Global）として形成・変更された学習内容は、その後に元のコンパニオン個体が削除された場合でも、全体共有の知識として安全に残ります。ただし削除の際には、なぜその知識が残るのかという根拠と、元のコンパニオンという情報源が失われることをユーザーに分かりやすく説明します。一方で、相手との関係性（Relationship）や一時的なコンパニオン状態（Companion State）は、スコープ変更による共有対象にはならず、常に個体に固有です。

時間の経過もデータの意味に影響を与えます。スケジュール機能は設定時のタイムゾーンと時刻条件、コンパニオン状態は一時的な感情や経過時間、保持ポリシーやデバッグ記録は対象期間、自発的な行動は現在時刻や静粛時間帯（Quiet hours）を、それぞれの担当機能が正しく参照して判断します。ユーザーが明示的に設定したスケジュールのタイムゾーンを、システムが勝手に書き換えてはいけません。また、バックアップに含まれるコンパニオン状態をリストアする場合でも、バックアップ後に実際に経過した時間を無視して、一時的な感情などの状態を保存時点の値のまま無期限に固定してはいけません。

## 6. failure / cancellation / restart時の責任

タスクが中断（Cancel）されたり通信が切断されたりしたことだけを理由に、「外部への作用が取り消された」「最初から作用などなかった」と勝手に都合よく推測してはいけません。また、結果が不明な処理を勝手に「未実行」に戻してはいけません。内部の状態を参照したことや、クライアント間を移動したことなどを口実に、アクションを勝手に再実行（replay）してはいけません。

- **保全・消去サブシステム共通**: 未完了状態や確認不能な状態をHost側で確実に保全し、クライアントの切断、システムの再起動、管理画面の終了などから「完了した」と勝手に推測してはいけません。完了の説明は参加した各機能が確認した客観的根拠に基づきます。通信不能や確認不能を「成功」や「現在有効」と読み替えてはいけません。局所的な処理結果の報告をシステム全体の完了待ちにして循環依存させてはいけません。保留状態や再保存防止ルールは必要な期間確実に維持し、「保留の解除」と「局所完了」を同じ意味として扱ってはいけません。完了の証拠を残すためと称して、削除対象のパスワードやプライベートな本文をログに残してはいけません。一時的なメモリバッファが消失したことを、成功や完了の根拠にしてはいけません。
- **PE-1（個人データ完全削除）**: Hostの再起動、クライアントの切断、担当機能の一時的な利用不能、残存検証の失敗、遅れて届いた結果、消去処理中の再到着データがあった場合でも、未完了を「成功」へと勝手に変換せず、再保存防止ルールを決して失わせません。削除される前の情報を参照して処理中だったタスクや学習機能による再保存を確実に防ぎます。古い根拠だけに基づいて知識を自動再形成することを防ぎます。確認が取れないクライアントや外部処理を勝手に「成功」と読み替えず、局所的な完了をシステム全体の完了とみなしてはいけません。
- **PE-2（保全・Backup）**: 通常保存やデータベースマイグレーションの最中に障害が発生した場合でも、直前の最後の正常な保存状態を決して破壊しません。未完了のデータ消去や復旧処理と重なったバックアップを、「正常で即実行可能なコピー」と偽ってはいけません。実行中のアクションについて結果が不明なものがある場合、最後に正常記録された状態が外部世界の最新状態と一致しているとは限らないことを前提とします。
- **PE-3（Restore）**: リストアの処理中に中断や再起動が発生した場合でも、復元前の正常状態を破壊せず、部分的に置換された不完全な状態を新しい正本にしてはいけません。リストア前の古い稼働結果やクライアント側の一時コピーを、復元された正本へ混入させてはいけません。保留中や確認の途中で再起動した場合であっても、復元された割り当てや同意情報だけで自動処理を開始してはいけません。未完了だったデータ消去の保留状態を、リストアの全置換によって勝手に解除してはいけません。
- **PE-4（Reset）**: 全データリセットの実行後に、古い処理の残りカスやクライアント側の一時コピーから内部状態を勝手に復旧させてはいけません。Host側の信頼関係を完全に失効させ、古い端末情報だけで再接続の信頼を復活させてはいけません。通信できないクライアントの物理的な消去を「確認済み」と偽ってはいけません。
- **PE-5（retention）**: ディスク容量不足、AIプロバイダの利用コスト、LLMの利用不能などを理由にして、機械的なデータ消去、残存検証、正常保存、必要な事実の記録を追加のAI推論待ちにして止めてはいけません。保存容量が不足したからといって、通常の学習内容、過去のリビジョン、判断根拠を黙って勝手に削除して解決してはいけません。
- **PE-6（Audit / Debug）**: 監査ログの追記順序の確認と保持管理を行い、削除完了後にプライベートな内容をログに残さないことを徹底し、診断用データが無制限に溜まる「データの別保管庫」にならないようにします。デバッグ記録の短期失効、停止、削除ルールを厳格に守ります。
- **共通の原則**: 要求の受付、処理の開始、外部への作用、記録の保存、タスクの達成、ユーザーへの報告は、すべて別々の客観的事実であり、安易に「一つの成功」としてひとまとめに混同してはいけません。事実の確定度を変更する場合は、その事実の担当責任者が新たに直接確認した客観的な証拠に基づかなければなりません。バックグラウンド作業やスケジュールによる無人実行も全く同じ条件に従い、クライアントが不在であること、予定時刻が到来したこと、システムの復元が成功したことなどを理由に、必要な権限を自動承認してはいけません。ユーザーによる確認が必要な操作は、勝手に実行せず必ず判断待ちにします。管理経路は、LLMの機嫌、長時間タスクの完了、デスクトップ動作（Body）、音声合成（Voice）、外部拡張機能の成否などに一切従属させません。

### 6.1 Hostで保全すべきpersistent property

具体的なジャーナル、WAL（Write-Ahead Logging）、トランザクション、ロック、分散合意プロトコルなどは固定しません。後続設計は、以下の性質を確実に満たす永続化方式を選択しなければなりません。

- データ消去要求の目的、対象の指定、影響範囲、除外対象、必要な確認事項との正しい対応関係。
- 参加している各機能の処理結果、検証結果、未完了・失敗・未確認の範囲。
- 対象範囲のデータ利用や再保存を制限するための消去条件と、その有効期間および完了境界。
- 局所完了とシステム全体完了の厳格な区別、保留中（pending）・通信不能（unreachable）・検証失敗（failed verification）の明確な区別。
- バックアップの対象時点、参照関係、除外対象、未完了状態、作成結果、失敗理由。
- リストア要求の受理、説明、隔離、照合、置換成立、復元後保留、一括有効化の対応関係、および単一正本・データ非混合の成立状況。
- リセットにおける対象の列挙、厳重な確認、信頼失効の対応関係。
- 保持方針、明示的なオプトイン設定、その適用範囲と影響。
- 監査ログの追記順序と保持状況、デバッグ記録の対象・内容・有効期間・停止・削除。
- 再起動、再接続、リストアを跨いでも、未完了の認識と必要な保留状態・再保存防止ルールを確実に維持すること。処理の途中で再起動した場合であっても、勝手に完了と誤認したり保留を黙って解除したりしないこと。
- 記録の中に削除対象の秘密値やプライベートな本文テキストを残すことは、完了の客観的証拠にはならないこと。

システム横断操作の未完了状態や再保存防止ルールなど、安全のために継続して守る必要のある状態は、クライアントや一回きりのメモリ処理だけに頼るのではなく、Host側で確実に保全します。処理を安全に継続するために必要なタスクの状態、未伝達メモ、作用不明の記録、未完了の操作状態などを本来の担当責任者が安全に保全します。

障害からの再構築が可能であるということは、「すべての会話文脈や内部の推論ログを永遠に丸ごと保存しなければならない」という意味ではありません。通常保存しない生の画面観測データ、生の音声データ、ツールの詳細ペイロード、内部の思考ログなどを恒久保存する理由にしてはいけません。

## 7. Step 11 contractへの参加

各契約の一般的な条件は第0節に挙げた重要領域ドキュメントに定義されており、本書では重複を避けて再掲しません。本節では、保全・消去サブシステムが提供・参加する固有の約束事項のみを記載します。

### 7.1 Context Assemblyへの参加

- 保全・消去サブシステムは、コンテキストを保持・変換・送信・受け入れする各機能が、自分自身の参加範囲を正しく説明できることを要求します。元データの担当責任者だけでなく、処理中のコンテキスト、検索・要約の派生データ、Eneの管理下にあるキャッシュ、クライアントや拡張機能の一時コピー、遅れて戻ってくる可能性のある処理結果も含めます。
- データを保持・利用する各機能は、対象の情報源や対象データとの関係、処理中の利用状況、局所的な処理と検証、再保存防止、確認不能・未完了の状態を正しく対応付けます。参照関係そのものに対象データが残っている場合も、完全消去へ参加させます。
- 外部ワークスペースの実ファイル、ユーザーが保存した外部バックアップ、AIプロバイダが保有するコピーの消去を、内部コンテキスト消去の成功条件に混ぜてはいけません。一方で、Eneの管理下にある内部コピーは決して消去対象から除外しません。

### 7.2 Action Executionへの参加

- 保全・消去サブシステムは、客観的な作用事実の説明とデータ消去への参加の両立を各受け入れ先へ要求します。必要な客観的事実の記録と、対象情報の除去を両立させ、「作用の記録だから」という言い訳で削除対象の本文を残してはいけません。外部へ送信されたデータ、エクスポートされたファイル、バックアップ済みの外部コピー、外部ワークスペースのファイル消去、および外部サービス側でのAPIキー失効は、作用記録の完了範囲外であるとしてユーザーに説明します。
- データ消去が行われたことを理由に、過去のアクション結果の確定度を勝手に成功・失敗・未実行へと書き換えてはいけません。タスク記録は実行・拡張機能が記録した確定度を参照・集約し、同じ確定度を作業側で勝手に独自更新してはいけません。

### 7.3 Targeted Deletionへの参加

- 保全・消去（PE-1・PE-7）は、ユーザーの明示的なプライバシー・セキュリティ目的と対象情報を、保存場所を意識させずにシステム全体の消去対象へと対応付けます。意味的な対象の特定には個体調整機能や認識・学習機能が参加し、各データの担当責任者は保持している内容、過去リビジョン、サマリーや証拠データ、元データ、内部コピー、派生物、処理中の利用を漏れなく提示します。権限・制約機能および各実行箇所は、再保存を防ぐ制約ルールへと参加します。
- 完了条件は `targeted-deletion.md` 第8.2節の全体要件です。保全・消去サブシステムが各参加先の局所完了、検証結果、未完了状態を照合し、内部全域における処理の成立を確定します。局所完了の単なる寄せ集め以上の厳格な条件を必要とします。
- 切断されたクライアントを放置したまま、そこに永続的なコピーが残ってしまうことを許しません。消去処理中の接続切断や確認不能は保全・消去サブシステムへ通知され、必要な確認を省略して勝手に成功とみなすことはありません。到達性の確認やデータ無効化の具体的手法は、下位設計に残します。
- Targeted Deletionに伴い、通常のデータ保持原則（判断根拠の保持や、履歴ログと学習状態の独立性など）に反するデータ変更が発生することは、この操作の目的および対象範囲に厳格に限って認められます。容量制限（retention）はDP-6の明示的なオプトインに従う全く別の操作です。保全・消去サブシステムが、記憶（Memory）の重要度や人間関係の解釈を普段から勝手に編集できるような権限は一切生じません。

### 7.4 Client Presence Transitionへの参加

- 保全・消去サブシステムは、接続中のクライアントが保持する一時データを扱う参加先の把握を支援します。接続・存在機能が消去処理中のクライアント接続変化や確認不能を参加先へ結び付け、入出力・提示機能などが画面表示や一時操作データの消去状況を報告します。通信不能を「消去成功」と勝手に読み替えてはいけません。

### 7.5 Backup / Restoreへの参加

- 保全・消去（PE-2・PE-3・PE-7）は、対象時点、内部範囲、除外対象、作成結果、操作ステータス、保留状態を調整します。各データの担当責任者は、自身の管理・利用範囲について対応関係、参照整合性、利用可能性を確認します。
- 古いバックアップからリストアしてデータを復活させる操作は、自動再形成ルールの例外ではなく、ユーザーの意思による全く別の操作であり、事前のリスク説明、監査ログへの記録、処理の一時保留、現在の前提条件の再評価を必ず経ます（DP-4）。未完了のデータ消去に伴う保留状態は、リストアの全置換によって勝手に解除してはいけません。

## 8. boundaryを越える際に保持すべき意味

後続の詳細なインターフェースや状態表現の設計においては、特定のAPIや実装メカニズムを固定しなくても、システム境界をデータが通過する際に少なくとも以下の対応関係を正しく表現・解決・照合できなければなりません。「確認できない情報」を、勝手に「現在有効である」「許可されている」「完了している」と都合よく推定する方式は決して採用できません。

- **消去要求の同一性**: ユーザーの明示的なプライバシー・セキュリティ目的と、通常の自然な忘却等との厳格な区別、対象の指定、消去対象期間、消去完了後にユーザーから新たに提供されたデータとの境界、参加機能の対応付け（Targeted Deletion第3.1節）。
- **対象指定の二層構造**: 機械的な条件（完全性を検証可能）と意味的な条件（補助的・完全性は保証しない）の区別、完全な自動検出を保証しない範囲の明示。
- **追跡すべき関係性**: 対象の情報源や対象データとの関係、処理中の利用との関係、局所的な処理や検証との関係、再保存防止ルールとの関係。これらを本文テキストを保持することなく安全に維持できること。
- **各利用箇所が個別に照合できる消去条件**: 包括的な単一フラグや共通の有効値へと安易にひとまとめにして混同することは禁止します。
- **Hostが権限を持つ正規の帰属先と、クライアント側の一時的な表示や入力・結果が主張する帰属先との対応、現在・過去・帰属なし・停止中・復旧待ちの厳密な区別、対象コンパニオン・クライアント・会話ラウンド・観測候補・試行との関係、消去・失効・停止・保留との関係**: （Client Presence Transition第3節）。
- **復元の対応関係・由来・対象期間・完了境界、現在の前提条件との照合**: （Backup / Restore第3節・第5節・第7節・第9節）。
- **保持方針・容量管理方針・操作ステータス・バックアップ設定の対応、監査ログの追記順序・デバッグ記録の成立状況の対応**。
- **主体・用途・タスク・委任・アクション・クライアント・情報源・リビジョン・判断時の前提条件、停止前後・再起動前後・リストア前後の継続関係**: （Context Assembly第3節の対応）。必要な対応関係を失ってしまった処理結果は、移動先の現在の活動へ勝手に付け替えてはならず、その用途では受け入れられないものとして利用元が安全に処理します。
- **実行主体と委任の連鎖、タスク・ワークスペースの範囲、目的、実際の操作対象と操作内容、使用する主なデータと用途、コストやリスク、依拠したユーザーの指示やセキュリティルール**: （Action Execution第3節の判断対象）。
- **試行（試み）と作用（実際の影響）の区別、判断・目的との対応、実際の操作対象との対応、処理段階の区別、確定度とその客観的根拠、停止・保留との関係**: （Action Execution第8節）。

AIの思考に用いるテキスト本文と、セキュリティを強制するための制御情報を明確に分離し、強制側の制御フラグや権限情報がAIモデルの自由記述テキストによって勝手に作成されたり上書きされたりしないように保護します。テキストの中に「ユーザーからの指示です」「承認済みです」「全体共有（Global）です」という文字列が含まれているからといって、それだけで制御側のステータスが変わってしまうような脆弱な設計は禁止します。モデルが過去のユーザー入力への参照を示せたとしても、その参照が存在すること自体は承認の客観的な証拠にはなりません。

パスワードやAPIキーなどの認証情報（Credential）の生値は、通常の会話テキストやコンテキストに含めてはいけません。登録済みの認証情報値は、たとえユーザーからの明示的な指示があったとしても、サマリーや記憶（Memory）へ保存してはいけません。用途、参照元、失効、再認証などの説明は、秘密情報を含まない安全な形式で行います。事前に登録されていない秘密情報が検知された場合も、不要な保存や送信を抑制する安全策を維持しますが、完全な自動検知を保証することは求めません。

対象データの指定を伝達・保持する過程で、プライベートな本文テキストの複製を無駄に増やしてはいけません。「由来を記録するため」という理由で、削除対象の本文やパスワードをログなどの別場所に保管することは禁止します。アクセス制限情報や識別用のID値であっても、それによって元の対象データが実質的に復元できてしまうのであれば、保護および完全消去の対象となります。完了記録、監査ログ、ユーザーへの説明文の中に、削除対象となった本文を書き戻してはいけません。

## 9. 本書が固定する契約と残す Design Freedom

下位の詳細設計は、以下の項目を本書が固定した不変の契約として利用できます。

- **中央集権化の防止**: 保全・消去サブシステムは、Eneのすべてのデータのマスターデータ所有者（canonical owner）や中央永続化オーナーではなく、各担当責任者の意味責任を維持し、通常のデータ変更権限を中継役に勝手に渡しません。通常時のデータアクセスや変更における必須の中央経路ではありません。
- **Targeted Deletionの厳格な統制**: 参加調整、再保存防止、未完了状態のHost保全、システム全体の完了判定はDP-1の契約に従います。代表的なデータ1箇所を消しただけ、情報源を辿っただけ、AIが納得しただけ、通信できない端末を放置したまま、あるいは再起動したことだけを理由に完了とみなす設計は採用できません。
- **Backupの整合性保証**: 対象時点、参照関係、除外対象、作成結果はDP-2の契約に従います。単に各部分のコピーファイルを出力できたことだけでバックアップ成功とみなす設計は採用できません。
- **Restoreの安全な原則**: 一括全置換、現在の安全な状態の維持、単一正本の厳守、データの非混合、権限の先行復活禁止、復元後の一時保留、一括有効化はDP-3の契約に従います。復元されたデータが存在することだけを理由に「直ちに実行可能である」とみなすインターフェースは採用できません。
- **古いバックアップのリストアの取り決め**: 過去のバックアップからのリストアは、DP-4に定める独立した操作契約に従います。バックアップファイルの勝手な改変、自動再消去、過去の消去ルールの自動再適用、意図しないデータの再出現との混同、本文テキストの別保存はいずれも禁止します。
- **Resetの目的別分離**: 設定リセットと全データリセットの明確な区別、保護対象の厳守、外部ファイルの除外、端末信頼関係の失効はDP-5の契約に従います。安易に一つの初期化処理にひとまとめにすることは禁止します。
- **容量整理（retention）の厳格な境界**: 既定OFF、明示的なオプトイン、通常の忘却との明確な分離、連鎖削除の禁止はDP-6の契約に従います。ディスク容量不足を口実にして、ユーザーに黙って勝手にデータを削除することは禁止します。
- **Audit / Debugの安全原則**: 追記順序の保証、保持管理、短期失効、本文テキストの非保持、事実の確定度を強めない原則はDP-7の契約に従います。本文データの別保管庫化、古いデータの正本化、確定度の勝手な強化は禁止します。
- **状態区分の厳格な維持**: 局所完了と全体完了の区別、保留中（pending）・通信不能（unreachable）・検証失敗（failed verification）の明確な区別、再起動やリストアを跨いだHost保全、客観的事実と会話本文の分離説明はDP-8および第6.1節の契約に従います。未完了や成否不明な処理を勝手に成功とみなす設計は採用できません。

本書が明確に禁止し、除外するアンチパターンは以下のとおりです。
- 全ドメインへの通常書き込み役化、単一トランザクション化、内部全構造への無制限アクセス権の付与
- 通常の意味判断の中央集約、通常アクセスの中央経路化
- すべての設定や学習内容を一つの編集可能なコンテキストへ集約すること
- Targeted Deletionと、通常の忘却、訂正、履歴整理、コンパニオン削除、容量整理、リセットとの目的混同
- コンパニオン削除を口実にした勝手な全体共有への昇格や、サマリーを歴史的ログへ分類し直して残すこと
- 容量不足を理由にした黙った削除や、通常の履歴整理を学習内容へ勝手に連鎖させること
- 古いバックアップファイルの自動改変、自動再消去、削除ルールの自動再適用
- 復元された参照や同意情報からの自動実行、外部世界の勝手な巻き戻し、古い情報の正本化、古い稼働結果の混入、クライアント一時コピーによるHostの上書き、未伝達通知の勝手な再キューイング
- 確認できない処理を成功とみなすこと、部分的な正本化、データの混同、権限の先行復活、未完了なのに完了と偽って表示すること
- 要約や復旧を行う際に事実の確定度を勝手に強めること
- 監査ログや完了記録へ本文テキストを再保存すること、秘密情報を別の場所に保管すること

いずれも上位のセキュリティ原則や整合性を破壊するため、決して採用できません。

対象データの探索、残存検証、端末の到達性確認、バックアップとの交差処理などの具体的な仕組みは、下位設計の自由度として委ねられます。ただし、必要な確認やユーザー判断の省略、現在の同意範囲の勝手な拡大、未完了や結果不明な処理の成功扱い、外部作用のロールバックや一度きりの実行（exactly-once）を勝手に保証することなどは、自由度の範囲には含まれません。

## 10. 横断検証

要件定義（requirements）、上位アーキテクチャ設計、重要領域（critical-area）の契約、および他のサブシステム設計に対する整合性の横断検証は以下のとおりです。単に固定のテストシナリオを網羅するだけでなく、正常系に加えて、本サブシステムにとって特に重要な障害、データ鮮度の低下（stale）、再起動（restart）、データ削除（deletion）のケースを選定して検証を行います。

[Targeted Deletion](../critical-areas/targeted-deletion.md)第10節および[Backup / Restore](../critical-areas/backup-restore.md)第10節で定義された検証シナリオは、保全・消去サブシステムの参加調整（DP-1〜DP-4）を通じても全く同じ結果を達成しなければなりません。本節ではそれらに加えて、保全・消去サブシステムが担当責任者となる固有の交差部分のみを記載します。

| 検証領域・交差部分 | 検証シナリオと達成すべき結果 | 本書における成立根拠 |
|---|---|---|
| バックアップ作成と未完了の消去処理の重なり | 未完了の個人データ完全削除や復旧処理の実行中に、バックアップ作成要求が重なった場合を検証します。セキュリティ制約を無視した「何事もなかったかのような即実行可能なコピー」を作ることなく、処理を安全に待機させるか、未完了状態や制約も含めて復旧可能な形でバックアップします。 | DP-2、第6節。要件RF-08、横断関心事CC-05を維持。 |
| リストアと未完了消去の保留の維持 | 過去のバックアップから明示的にリストアする場合、事前のリスク説明、監査ログへの記録、処理の一時保留、現在の前提条件の再評価を経る独立した操作として扱います。未完了だったデータ消去に伴う保留状態は、リストアの全置換によって勝手に解除されることはありません。 | DP-3、DP-4。要件RF-08、状態所有SO 6.5・SO 7を維持。 |
| 通常の履歴整理・容量整理と完全削除の区別 | 通常の手動削除や、明示的にオプトインされた容量整理（cleanup）を実行しても、そこから形成された学習内容やサマリーへ勝手に連鎖削除（cascade）することはありません。また、通常の削除要求を勝手に個人データ完全削除（Targeted Deletion）へと読み替えることもありません。自動削除が既定でOFFになっていることを確実に守ります。 | DP-6。要件RF-01・RF-07、CC-05、SO 6.5を維持。 |
| 設定リセットと全データリセットの分離 | 一般設定の初期化と、システム内部の全データ削除を厳格に分離し、設定リセットで保護すべきデータや、全データリセットで外部に残すべきデータの境界を守ります。古い処理の残りカスや一時コピーから内部状態が勝手に復旧しないことを確認します。 | DP-5。第5節、要件RF-08、SO 6.5・SO 7を維持。 |
| 監査・デバッグ記録と秘密・本文の保護 | 事実の確定度を勝手に強めず、本文テキストやパスワードなどの秘密値を溜め込む「データの別保管庫」を作りません。監査記録を過去処理の再生や自動実行の入力として使い回さないことを確認します。デバッグ記録の短期失効ルールを確実に守ります。 | DP-7。Action Execution第9節、CC-02・CC-07を維持。 |

横断関心事CC-01〜CC-07に対して維持すべき一般的な特性は、各重要領域ドキュメントの横断検証と完全に同一です。本書がさらに追加で保証するのは、以下の点です。
1. データ消去条件の適用を、コンテキスト内の自由記述テキストによって勝手に解除させないこと（CC-01）
2. 操作の目的に応じた独立したライフサイクルを厳格に保つこと（CC-05）
3. 会話本文や秘密情報の「データの別保管庫」を作らないこと（CC-07）

他のサブシステム設計との照合においても、各データの担当責任者は状態所有規則（SO第4節）の定義どおりに残り、本書のDP-1〜DP-8はそのデータ受渡しの対応付けを明確にしたものです。スコープの意味付けとセキュリティ強制の分離、認証情報の非露出、フォールバックの迂回禁止、成否不明な状態の安全な保持、古いバックアップとの交差処理に関する各契約は、すべての文書において完全に同一です。

### 保全・消去サブシステムを除いても各データの担当責任者を一意に説明できることの確認

本書第3.2節で示したとおり、保全・消去サブシステムを取り除いたとしても、以下の各ドメインデータの担当責任者は一意に定まり、曖昧になることはありません。
- キャラクターの定義
- コンパニオンの同一性
- 会話履歴
- 会話サマリー
- 記憶（Memory）
- スキル
- 相手との関係性
- コンパニオン状態
- タスク
- 作業エージェント
- アクション実行
- ワークスペース
- スケジュール
- クライアント接続
- 滞在帰属
- 画面観測
- 一般設定
- AIプロバイダ
- セキュリティルール
- 利用量・コスト
- 認証情報
- MCP受入

保全・消去サブシステムが担当責任者（owner）として所有するのは、保持方針、容量管理方針、操作ステータス、バックアップ設定、バックアップ対応関係、監査ログの追記順序、デバッグ記録の成立状況のみに限られ、いずれも各ドメインの通常のデータそのものではありません。したがって、本サブシステムは通常時のデータアクセスやデータ変更における「必須の中央経路」になっておらず、その必要性を再検討しなければならないような不健全な中央集権化は一切行っていません。通常のデータ参照、知識形成、タスク委任、メッセージ送信、データ保存、画面提示、アクション実行は、保全・消去サブシステムを経由することなく安全に成立します。
