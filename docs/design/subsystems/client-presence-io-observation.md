# Subsystem Detailed Design — Client接続・存在調停 / Owner入出力・体験提示 / 共有観測・関連付け

本書は「Step 12: サブシステム詳細設計」として、互いに密接に関連する以下の3つのサブシステムを1つの連携グループ（クラスタ）として詳細化します。

- **Client接続・存在調停**（以下、接続・存在）
- **Owner入出力・体験提示**（以下、入出力・提示）
- **共有観測・関連付け**（以下、共有観測）

> [!NOTE]
> 本書内の `CN-` / `IO-` / `OB-` で始まる番号は、本書内で各サブシステムの内部責務を参照するための識別子であり、製品要件IDではありません。
> また、`X-` で始まる番号は、本書内で定義するサブシステム間のデータ受け渡し契約（セマンティック・コントラクト）の参照番号です。

## 0. 位置付けと不変条件

上位設計との優先順位や、記述に矛盾が生じた場合の解決ルールは、[設計ドキュメント README](../README.md#設計文書の優先順位と信頼できる情報源) に従います。[Context Assembly](../critical-areas/context-assembly.md)、[Action Execution](../critical-areas/action-execution.md)、[Targeted Deletion](../critical-areas/targeted-deletion.md)、[Client Presence Transition](../critical-areas/client-presence-transition.md)（以下、Presence Transition）、[Backup / Restore](../critical-areas/backup-restore.md) の各ドキュメントで定義された一般契約は、すでに確定した上位ルールとしてそのまま利用し、本書で勝手に再定義したりデータの担当責任（オーナーシップ）を変更したりしません。なお、本書内で参照する `SO` は [State Ownership](../architecture/state-ownership.md) の節番号を指し、`CC` / `RF` / `RT` は対応するアーキテクチャ設計ドキュメント（[成果物一覧](../README.md#artifact-一覧)）の契約IDを表します。

本書の目的は、Presence Transition で定めた契約を上記3つのサブシステムの具体的な責務へと落とし込むことです。プレゼンスの切り替えそのものをゼロから再設計するわけではなく、新しいデータの担当責任者や第2のマスターデータ（例えば、万能の「Presence Manager」「Context Manager」「Observer State owner」「I/Oマスター」、統一プレゼンス状態機械、共通クライアントセッション層、共通コンテキスト層など）を追加することは決してありません。「ホスト側がマスターデータを管理する」「稼働中のコンパニオンが存在できるクライアントは同時に1台のみ（単一アクティブプレゼンス）」「ネットワーク接続とプレゼンス存在の区別」「クライアント依存のアクションは現在のプレゼンス帰属に従う」という原則は、SO 第2節、RT-02、および Presence Transition 第3節の定義を厳格に維持します。

## 1. 選定理由

これら3つのサブシステムをまとめて設計する理由は、「クライアントへの帰属」「会話ラウンド」「適格性」「未伝達メッセージ」「古いデータ（stale）の扱い」という共通の整合性ルールを密接に共有しているためです。これらを個別にバラバラに詳細化すると、同じ帰属チェックのロジックが3箇所で重複して定義されてしまいます。同時に、この領域は、後続の実装者が誤って「単一の真偽値（フラグ）」「クライアント側への権限委譲」「入出力データのマスターデータ化」「観測状態のマスター化」といった安易な設計にひとまとめにしてしまいやすい境界を最も多く含んでいます。

- **接続・存在 と 入出力・提示 の分離**: この2つを安易に統合してしまうと、「接続中のデバイス一覧」と「コンパニオン個体ごとのアクティブな存在場所」が混同され、「ネットワークが繋がっているだけで勝手に個体が存在し、操作が許可されてしまう」という不具合を招きます。逆に、この判定をクライアント側へ委ねてしまうと、クライアントが勝手にプレゼンスの決定権（権威）を握ってしまいます。
- **入出力・提示 と ドメイン判断 の分離**: 画面表示や音声入出力をコアの判断ロジックと密結合させてしまうと、アバターの描画エラーや音声デバイスの不調が、タスクの継続や権限判定にまで悪影響を及ぼします。3Dアバター（Body）、テキスト、音声、システム管理、安全操作、外部ツールUI（MCP Apps等）を単一の状態や単一の信頼レベル、単一の障害境界にひとまとめにしてしまうと、アバターや音声のトラブルによってテキスト操作や復元操作までフリーズしてしまいます。
- **共有観測 と 個体調整 の分離**: デスクトップ共有観測を個体調整機能に丸抱えさせてしまうと、複数個体間での重複検知や設定スコープの混同が生じます。また、PC自動操作（Computer Use）と観測機能を安易に統合すると、「画面を見る許可（観測の同意）」が「勝手にPCを操作する許可」へと漏洩・拡大解釈されてしまいます。さらに、画面キャプチャ・イベント検知・ルーティングを別々のサブシステムに過剰に分割すると、観測範囲や頻度、送信条件のチェックが重複して無駄が生じます。
- **未伝達メッセージ・タスク記録・会話履歴 の分離**: 未伝達の要件、報告状況、タスク記録、会話履歴、画面表示の実際を、1つの「通知ストア」や「既読フラグ」にひとまとめにしてしまうと、「タスクが完了した＝ユーザーへの報告も完了した」「画面にデータを送った＝ユーザーが確実に読んだ」といった誤った判断が生まれてしまいます。
- **観測用ルーティング文脈の独立**: デスクトップ画面のイベントを適切なコンパニオンへ届けるための要約データ（ルーティング用文脈）を、安易に新しいマスターデータや全個体共有データ（グローバル）へ昇格させてしまうと、本来は個体限定であるべきプライベートな記憶が他のコンパニオンへ勝手に公開されてしまいます。

最初のマイルストーン（初期セットアップからテキスト会話、1対1タイムライン、基本3Dアバター、クライアント不在時のタスク継続、ホスト再起動後の明示的再開とプレゼンス復旧、テキストベースの管理画面）は、接続・存在サブシステムによる帰属管理と、入出力・提示サブシステムによる会話ラウンドおよび表示の分離が正しく成立して初めて検証できます。音声対話、画面観測、グループ会話、コンパニオン同士の自発的交流、リモート接続、キャラクター配布などは後続のマイルストーンで実装されますが、本書はそれらの確定済みルールを除外することなく、将来の安全なデータ受け渡しを妨げない形で規定します。なお、AIのルーティングモデル、具体的なプロンプト、キャプチャ頻度のアルゴリズム、ハートビートやセッショントークンの仕組み、ネットワークプロトコルなどは本書では固定しません。

## 2. 内部責務の分離

### 2.1 接続・存在

利用可能なクライアントへのネットワーク接続と、「コンパニオン個体がそのクライアントに存在していること（プレゼンス）」を明確に区別しながら、安全な入出力の帰属関係を成立させます。帰属の決定はホスト側の管理下で行い、クライアント側も切断時や排他性が確認できない場合には確実に処理を停止できるようにします。なお、本責務は専用の常駐サービスや独立した接続プロセスの存在を必須とするものではありません。

| 内部責務 | 本責務が正式に判断・管理するもの（authoritative） | 本責務が保持してはならないマスターデータ |
|---|---|---|
| CN-1 接続の事実・機能利用可能性 | クライアントの識別に必要な情報、最終接続日時、現在の接続状態、各機能の利用可否。ネットワーク到達性という客観的な観測事実と現在性の管理。過去の接続ログと現在の接続状態の厳格な区別。古い保存値から現在の接続を勝手に復活させないこと。 | ペアリング許可やデバイス認証の法的・論理的意味（権限・制約機能が担当）、暗号化鍵などの認証秘密（認証秘密機能が担当）、アクションの実行許可、アクティブなプレゼンス帰属の成立。 |
| CN-2 authoritative帰属の調停 | 稼働中コンパニオン（Running Companion）ごとに、排他的なアクティブクライアントへの帰属、移動中、またはアクティブなし（待機状態）の確定。同時に存在できるのは最大1台であり、停止中個体（Stopped）は帰属を持たないこと。個体調整の活動状態と、ペアリング・デバイス許可を参照して成立させる。ホストが管理する個体ごとの帰属記録のみをマスターデータとする。 | 会話の文脈上、移動が必要であるかどうかの判断（個体調整機能が担当）、タスクの達成やアクションの成否、実際の会話ラウンドや画面表示の状況、「存在している＝操作が許可された」という勝手な推測。 |
| CN-3 呼出し・移動・復帰の調停 | 通常のクライアント滞在、ユーザーからの呼び出し、事前指示、文脈上の自発的移動、通信切断時の復帰、ホスト再起動後の元クライアントへの自動復旧（自発的移動とは区別された復旧処理）の調停。ホスト側でクライアント環境を勝手に自動起動しないこと。別クライアントへの無条件移動、停止中個体への適用、中断タスクの自動再開の禁止。移動の必要性判断は個体調整機能、成立判定は本機能が担う。 | コンパニオン個体の生成・停止・削除、タスク全体の別環境への移送や再実行、PC自動操作（Computer Use）への権限付与、3Dモデルや音声の実際の入出力処理、再配置ヒントの選択アルゴリズム。 |
| CN-4 切替区間の新規開始禁止 | 旧クライアント、移行中、新クライアント、アクティブなし、停止中、復旧待ちという各状態の論理的な区別。切り替えが決定してから新プレゼンスが成立するまでの間は、旧・新のいずれのクライアントでも新しいクライアント依存処理を開始しないこと（二重プレゼンスの禁止）。単一の真偽値（フラグ）だけに安易に集約してはいけない。 | タスク全体の終了を切り替え完了の前提条件とすること、通信不能なクライアントを「成功」とみなすこと、切り替え失敗時の戻り先選択アルゴリズム。 |
| CN-5 stale識別に必要な対応の保持 | ホストが管理するマスターデータとしての帰属と、クライアント側の一時データ・入力・結果が主張する帰属との対応関係の保持・照合。現在有効、過去のもの、帰属なし、停止中、復旧待ちの厳格な区別。対象コンパニオン、クライアント、会話ラウンド、観測候補、試行回数の対応関係、および消去・失効・停止・保留状態との整合性チェック。確認が取れないものを「現在有効」と推測しないこと。具体的なトークンやシーケンス番号の形式は固定しない。 | クライアントの画面表示、過去のログ、ヒント情報、一時コピー、復旧先の記録、外部AIプロバイダに残った会話履歴を根拠としてプレゼンスを成立させること。古い設定コピーや外部コードに基づいてユーザー同意や現在性を独自に判定すること。 |
| CN-6 Client依存activityの開始可否への参加 | 対象個体のアクティブクライアント、現在の接続状態、機能の利用可否という「帰属側の前提条件」の供給。アクション開始の可否自体は「帰属・接続・権限・現地のデバイス状態・各機能設定」のすべてが揃って初めて成立する（連言条件）ため、本機能だけで勝手に開始を決定しないこと。「ペアリング済み」「接続中」「アクティブに滞在」「アクション許可済み」はすべて異なる4つの意味であること。 | 「ペアリング済み＝アクティブ＝アクション実行許可済み」と短絡的に導出すること、古い帰属状態のまま処理を継続させること、システム管理画面全体に対して会話と同様のプレゼンス制約を勝手に課すこと。 |
| CN-7 再配置hint・復旧先の管理 | 最後に滞在していたクライアントや復帰候補などの「再配置ヒント」、ホスト再起動前に滞在していた「復旧先クライアント」の記録管理。これらは現在の帰属とは明確に区別し、記録があることだけで「現在存在している」と誤認しないこと。ネットワーク接続が回復しただけで、停止中の個体を勝手に再開・再配置しないこと。 | ヒントや復旧先記録を稼働中のマスターデータとみなすこと、候補選択アルゴリズム、具体的な再接続・待機・タイムアウト・ペアリングの手法。 |

CN-1〜CN-7は同じ調停責務に属しますが、単一のデータ状態やライフサイクル、保存単位にまとめてはいけません。ネットワーク接続、プレゼンス帰属、アクション権限、ホスト側の処理継続を同一の状態として混同してはならず、ホストマシンと同居するローカルクライアントに対しても、リモートクライアントと全く同じ帰属制約を適用します。

### 2.2 入出力・提示

同じコンパニオンを通じて「会話」と「作業の依頼」を自然に利用できる体験を提供するとともに、障害発生時でも確実にアクセスできる公式（第一者）のシステム管理および安全操作画面を提供します。「提示」とは、システム内部のドメインデータをユーザーが理解・操作できる形に変換して表示する責任であり、そのドメインデータのマスターデータではありません。

| 内部責務 | 本責務が正式に判断・管理するもの（authoritative） | 本責務が保持してはならないマスターデータ |
|---|---|---|
| IO-1 Text入出力・round | 3Dモデル、テキスト、音声を通じた入出力のうち、テキストの受付・画面表示・安全な区切り。1対1タイムライン、グループ会話、タスク管理という異なる意味の表示分け。入力がどのコンパニオン、クライアント、会話ラウンドに属しているかという実際の受付範囲の管理。クライアント側での入力受付、ホスト側での受理、ユーザーへの応答提示の区別。 | 会話の参加者、発言内容、文脈、会話履歴（History）の意味（個体調整機能が担当）、タスクへの反映（作業機能が担当）、プレゼンス帰属の成立（接続・存在機能が担当）、タイムラインの意味、ユーザーへの報告完了の勝手な代行確定。 |
| IO-2 Voice入出力・待受・縮退 | 音声の物理的な入出力、音声区間検出（VAD）による常時待受の識別、即時ミュート（消音）、割り込み発話（barge-in）、リアルタイム音声からターン制音声やテキスト対話への段階的な切り替え（縮退運転）。「声による話者認証は行わない」ことの初回有効化時および管理画面での明示。ミュート、音声停止、会話中断、承認拒否をキーボード等から行える安全ルートの確保。音声障害がテキスト利用に波及しない分離と、切り替え・失敗理由の丁寧な提示。 | 「声で話者認証済みである」という属性の付与、音声データに基づく本人認証、プレゼンス帰属切り替えの回避策としての音声縮退運転、「音声入力が成功した＝タスクも成功した」という安易な推測。 |
| IO-3 Body表示・状態表現・縮退 | Windows / Linux環境におけるVRM 1.0キャラクターのデスクトップオーバーレイ表示、ウィンドウの移動・リサイズ・非表示、待機中・傾聴中・応答中・作業中・注意が必要な状態に応じた表情・姿勢・モーションによる視覚的表現。位置やサイズ、非表示などの一般設定と、実際の描画状態の区別。全画面ゲーム（fullscreen）や高負荷、デバイス障害時における一時休止・画質低下、およびテキスト・管理・復元機能の保護。描画エラー時でもテキスト会話、タスク管理、設定画面、復旧機能を確実に維持すること。 | 内面的な感情や思考のマスターデータとしての表情・モーション、キャラクターの3Dモデルパーツそのものの管理、AIプロバイダ割り当てへの同意やデバイス利用許可の意味、描画フレームやモーションの再生位置の永続化。 |
| IO-4 通知・未伝達の提示 | クライアント不在によって保留されていた要件（未伝達メッセージ）の、クライアント復帰時における実際の画面提示。提示用データの受け取りと、提示結果の報告。接続されたことや表示用データを送信したことだけで「報告完了」とみなさないこと。提示結果が不明な場合の確実な保持。アクティブクライアントが不在の場合はホスト側に必要な内容を残す前提での提示処理。 | 未伝達の必要事項や報告ステータスのマスターデータ（個体調整機能が担当）、タスクの進捗や結果そのもの（作業機能が担当）、「提示候補を生成した＝伝達完了」「タスクが完了した＝報告完了」という安易な推測。 |
| IO-5 管理・安全surface | 初期セットアップ、段階的な機能導入（Capability）、権限管理、利用費用、プライバシー、データの出所、診断ログ、システム復旧へ確実に到達できる管理画面ルート。UI、3Dモデル、音声の一般設定、およびユーザーが選択する「ホスト自動起動設定」の意味の管理。各操作の意味付け、適用、成否判定は各担当サブシステムから受け取ること。重要な音声通知のテキスト代替表示、日本語と英語での同等の説明提供。操作要求の受付、処理の完了、保存への影響、既知の作用と結果不明の明確な区別提示。 | タスクの開始条件や成功判定、学習データの形成、権限承認の妥当性判断、データ削除やバックアップリストア完了の独自判断、管理画面を閉じたことによるタスクの勝手なキャンセル、UIからの入力を検証なしに制御プレーンへ適用すること、3D表示・音声・LLM応答・外部ツールUIが正常に動いていることを管理画面の前提条件とすること。 |
| IO-6 round・区切りの実際と移動協調 | 現在のテキスト・音声ラウンドの安全な区切り、移動元と移動先のクライアント状態の対応付け、双方のクライアントで把握できた移動状態の画面提示。ホスト側で実行中の通常タスクの終了を、画面移動の区切り条件にしないこと。通信不能なクライアントを「成功」とみなさないこと。 | 移動調停そのもの（接続・存在機能が担当）、タイムラインの終了や削除と会話ラウンドの終了の混同、タスク全体の別クライアントへの移送や再実行。 |
| IO-7 障害・縮退の分離と外部Tool UI | 全画面モード、システム高負荷、デバイス障害の検知結果を関係サブシステムへ通知し、3Dモデルや音声のエラーからテキスト会話、管理画面、復元機能を確実に保護すること。MCP Appsなどの外部ツールUIを公式UIと明確に区別して提示し、ツールの画面終了とバックグラウンドタスクやアクションの終了を混同しないこと。 | 3Dモデル、音声、テキスト、管理画面、安全操作、外部ツールUIを単一の状態・信頼レベル・障害境界として扱うこと、クライアントの表示用コピーをホスト側のマスターデータと誤認すること、操作受付・処理完了・結果不明を混同すること、外部ツールUIをシステム制御プレーンへ格上げすること。 |
| IO-8 提示確定度の分離 | 入力受付、ホストでの受理、ユーザーへの画面提示、処理完了の各段階を厳格に区別すること。表示用データを送信したことやラウンドが終了したことだけで、会話履歴、タスク進捗、権限承認、外部作用を「完了した」と確定しないこと。内部推論の思考ログ（CoT）や詳細なシステムプロンプトを勝手にユーザーへ露出しないこと。好感度や内部感情などの数値を、常設の数値メーターや理由パネルとしてUIに安易に露出しないこと。 | 会話履歴、タスク進捗、権限設定、アクション成功に関する第2のマスターデータ、AIプロバイダとのセッション履歴のマスターデータ化、クライアント側だけで永続的な会話履歴を確定すること。 |

IO-1〜IO-8は同じ「ユーザー体験」に関する責務ですが、単一のデータ状態、信頼レベル、障害境界にまとめてはいけません。3Dアバター、音声、外部ツールUIのトラブルがテキスト会話やシステム管理画面を巻き込んでフリーズしないこと、および「操作要求の受付」「処理の完了」「結果が不明」を絶対に混同しないことを徹底します。セットアップや設定画面は各データへの「入力経路」にすぎず、全設定のマスターデータを保有するわけではありません。なお、「ホストのOS自動起動設定」については、日常的な利用体験の選択として本機能が入出力設定の責任者（semantic owner）となりますが、OSへの実際のレジストリ登録やショートカット配置は実行・拡張機能が担い、バックアップやリセット操作への参加調整は保全・消去機能が担当します。「ユーザーが自動起動を選択したこと」と「OSに正常に設定されたこと」を混同してはならず、この設定を理由にタスクの勝手な自動再開やリストア後の安全確認の省略を行ってはいけません。

### 2.3 共有観測

クライアントごとの画面キャプチャ費用や処理負荷を共有・最適化し、コンパニオン個体ごとの判断に必要なイベントだけに絞り込んで安全に届けます。画面情報の取得元はクライアントですが、観測対象や個体への帰属、継続的な制御はホスト側の管理下に置かれます。イベントの検知や関連付けの計算をクライアント側だけに固定することはしません。また、画面キャプチャを行う外部アダプターコードは、安全に隔離された拡張境界内に留めます。

| 内部責務 | 本責務が正式に判断・管理するもの（authoritative） | 本責務が保持してはならないマスターデータ |
|---|---|---|
| OB-1 対象・時機の確定 | 観測がONになっており、コンパニオンが1体以上アクティブに存在しているクライアントのデスクトップ画面全体を観測対象として確定すること。存在人数のカウントをホスト側のマスター帰属に連動させ、停止中（Stopped）の個体を除外すること。クライアント側の表示残骸や古い一時データをカウントに含めないこと。クライアント別やシステム全体での一時停止（Pause）/ OFF、全画面モード、API費用上限、PCリソース制限を、キャプチャ頻度よりも常に優先すること。複数クライアントの同時キャプチャを禁止し、タイミングをずらして負荷を分散させること。設定がONであることだけで「常時キャプチャ実行中」と偽って表示しないこと。 | 各コンパニオンの最終的な発言内容やアクションの判断、個体ごとの自発性設定、すでに形成された学習データの削除、PC自動操作（Computer Use）の実際の操作や承認、個別ウィンドウの所有権や観測設定、タスクスケジュール。 |
| OB-2 共有Capture・候補検知 | クライアントごとの指定頻度を満たしつつ、タイミングをずらして画面をキャプチャし、そのクライアントに紐づく観測専用のAIモデル割り当て（Observer専用assignment）を用いてイベント候補を検知・文脈に関連付けること。コンパニオン個別のモデル設定で上書き・合成しないこと、すべての個体に無条件でイベントを配信しないこと、個体ごとに重複して画面キャプチャや検知処理を行わないこと。画面の取得とアダプター処理は実行・拡張サブシステムの境界で行い、対象やタイミングの管理は本機能が担う。 | 画面内に映った文字や指示を「ユーザーからの正式なタスク依頼」へ勝手に格上げすること、関連付けのためにコンパニオンの全プライベート記憶へ無制限にアクセスすること、軽量なローカルモデルや安価なクラウドモデルの利用を必須の動作条件とすること。 |
| OB-3 専用assignmentによる利用 | 観測専用のAIモデル / プロバイダ割り当ての前提条件の管理（実際の通信解決は推論機能、外部送信同意の管理は権限・制約機能が担当）。「共有画面キャプチャ・候補検知・ルーティング」と、「イベント配信後にコンパニオンが自分自身で行う思考（reasoning）」を別々のAI利用として完全に分離すること。後者のみが各コンパニオンの個別設定に従うこと。クラウドAIを使用する場合でも、通常のユーザー同意、プライバシー保護、費用制限ルールを厳格に適用すること。 | コンパニオン個別のモデル設定や同意を合成・流用すること、全クライアント共通モデルやUI設定の継承階層を固定化すること、コンパニオンの人数分だけ利用量を二重計上すること、個体側の外部送信同意を観測機能へ勝手に流用すること。 |
| OB-4 限定routing文脈の受取・維持 | イベントのルーティング（どの個体に届けるかの判定）に必要な範囲だけに要約・制限された「コンパニオン固有のルーティング用文脈」を受け取り、元の情報、対象コンパニオン、用途、制約条件の対応関係を保った一時的な派生データとして維持すること。会話履歴や個体文脈は個体調整機能、メモリや学習データは認識・学習機能、タスク文脈は作業機能の管理下にあるため、既存の機能間連携を通じて最小限の情報のみを受け取ること。全プライベート情報の公開、新しい学習マスターデータ化、全体共有（グローバル化）、他コンパニオンへの無断共有を行わないこと。 | 新しいマスターデータ、新しいデータスコープ、新しい責任者を作ること、プライベートな全記憶や他用途への無制限アクセス、要約や変換によって元の安全制約やユーザー同意を消去すること、文脈の生成方法・データ形式・更新頻度・選択アルゴリズムを固定化すること。 |
| OB-5 routing・deliveryの採否 | キャプチャを行ったクライアント上に現在滞在している、関連する稼働中コンパニオン（Running Companion）だけにイベントをルーティングし、複数該当する場合はそれぞれに配信すること。現在の対象や用途と照合して配信の採否を決定すること。AIモデルの気まぐれによって無関係な個体やクライアントを追加させないこと、検知されたテキストの内容によってデータの所属や制御設定を勝手に変更させないこと。 | 最終的なアクション実行の判断、「観測が成功した＝個体側の推論も成功し、外部送信に同意され、アクションが許可された」とみなすこと、一方の個体で判断が成功したからといって他方の個体へその結果を勝手にコピーすること。 |
| OB-6 鮮度・観測制御の適用 | イベントの送信や配信を行う直前に、対象クライアント、存在個体、観測の一時停止状態、限定文脈の利用条件、個人データ消去などの保留状態との整合性を再確認すること。移動前にキャプチャした古い画像を移動先のクライアントに付け替えてはいけないこと、停止中の個体を勝手に起こさないこと。一時停止（Pause）/ OFFや全画面モードの最中に、今後の観測や画面提示を直ちに停止し、処理中だったキャプチャやイベント配信を現在の安全条件と照合すること。古い設定のまま次回の観測や外部送信を行わないこと、全画面モード中に自発的な会話を行わないこと。 | 取得済みのイベント候補を一律に破棄するか、条件付きで継続するかを固定的なルールとして縛ること、すでにコンパニオンが認識した経験データを観測OFFを理由に勝手に消去すること、イベント配信後にコンパニオンがAIプロバイダへ外部送信する許可を自動的に成立させること。 |
| OB-7 状態説明・非保存 | 観測の稼働状態、対象範囲、学習への利用方針をユーザーに分かりやすく説明できるようにすること。キャプチャした生の画面画像（Raw Observation）は通常保存しないこと。検知されたイベント候補を、出来事の意味や学習データのマスターデータにしないこと。イベント配信後に各コンパニオンのメインAIモデルが内容を理解する処理は個体調整機能、それによって形成された要約や長期記憶は認識・学習機能に属するという帰属関係を維持すること。コンパニオンが意味を認識したイベントは、イベントごとの都度確認を求めず通常のユーザー発言と同様に経験データとして利用できること。発話やアクションを行う最終判断は、イベントを受け取った各コンパニオンが自身のキャラクター設定、ユーザーとの関係性、周囲の状況、安全ルールに基づいて自律的に行うこと。タスクの中で行われるPC自動操作（Computer Use）は、ユーザーの依頼によるものか自発的なものかを問わず、背景でのデスクトップ観測とは明確に区別し、タスクの実行権限と記録ルールを適用すること。 | すべての画面活動を永久に録画・記録すること、生のキャプチャ画像・イベント候補・AIの思考ログをすべて保存すること、新しい汎用的なアクティビティ管理サブシステムを勝手に追加すること。 |

OB-1〜OB-7は、同じ観測範囲・頻度・外部送信条件を安全に維持するための一連の責務であり、キャプチャ、イベント検知、ルーティングを別々の独立したサブシステムに細分化するような製品上の理由はありません。また、観測機能（Observer）を独立したコンパニオンやタスクエージェントとして扱ってはいけません。

## 3. 管理する logical state

特に「外部」「コピー」「一時データ」と明記されているものを除き、すべてホスト側で管理する内部データを指します。永続化の具体的な実装担当、保存単位、単一ライター、トランザクションの仕組みは本書では固定しません。なお、各データの担当機能は、正当な全データ消去処理（Targeted Deletion等）への参加を拒否することはできません。

### 3.1 接続・存在が意味ownerとなる state

- **クライアントの識別に必要な情報、最終接続日時、現在の接続状態、各機能の利用可否**（SO 4.15）。過去の接続記録と現在のリアルタイムな接続状態を厳格に区別します。ネットワークが繋がっていることや、OS上に機能が存在することは、直ちにその機能の利用許可を意味しません。現在の接続状態は、過去の保存データから勝手に復活させてはいけません。
- **コンパニオンのアクティブクライアント帰属、移動中、またはアクティブなし（待機状態）のステータス**（SO 4.15）。個体調整機能が移動の必要性を判断し、入出力・提示、共有観測、実行・拡張の各機能がこの現在の帰属関係を参照して動作します。タスクの担当や操作権限とは別物です。
- **ホスト再起動前に滞在していたクライアント（復旧先）、最後にいたクライアントや復帰候補（再配置ヒント）**。これらは現在の帰属関係とは明確に区別し、記録が存在することだけで「現在プレゼンスが存在している」と誤認してはいけません。具体的な再接続、待機時間、タイムアウト、ペアリング、調停の手法は固定しません。
- **停止中コンパニオン（Stopped Companion）の帰属解除状態**。個体調整機能が管理する停止状態に連動し、共有観測機能へ渡す存在人数やルーティング対象から確実に除外します。ホスト側が保持している個体のデータやヒント情報は、プレゼンスそのものではありません。

プレゼンス帰属はホスト側が管理する「現在有効な状態」であり、クライアント側の画面表示や過去の接続ログをマスターデータにしてはいけません。ホストが管理する帰属と、クライアント側の実際の利用可能性を突き合わせて判断し、排他性が確認できないクライアント（二重接続の疑いがある場合など）では、対象の入出力、画面観測、自発的な会話、PC自動操作を継続してはいけません。稼働中のコンパニオンが存在できるアクティブクライアントは同時に最大1台です。「ペアリング済み」「接続中」「アクティブに滞在」「アクション実行許可済み」はすべて異なる4つの意味を持ちます。ペアリング許可やデバイスごとの利用可能機能、権限失効の意味や範囲自体のマスターデータは権限・制約機能が保持し、接続・存在機能はそれをプレゼンス調停に反映します。クライアント固有の接続トークンの利用・更新・再ペアリングへの対応は接続・存在機能、秘密情報の保護は認証秘密機能、ホスト側の信頼・許可・失効のマスターデータは権限・制約機能がそれぞれ担当します（SO 第8節）。

### 3.2 入出力・提示が意味ownerとなる state

- **入出力ラウンドの受付・画面提示・安全な区切り状況**（SO 4.3）。テキスト入力や音声出力がどこまで進行し、安全に中断・区切ることができるかという実際の入出力ステータスです。アクティブな存在場所は接続・存在機能を参照します。一時的な会話ラウンドが終了したからといって、会話タイムラインそのものを終了・削除してはいけません。また、移動の調停そのものは接続・存在機能が担います。
- **UI言語、3Dアバターの位置・サイズ・非表示設定、音声の一般設定などの意味**（SO 4.17）。保存される一般設定はホスト側のマスターデータとし、クライアント画面上での未確定な編集中データや一時的なウィンドウ描画位置とは区別します。特定のコンパニオン専用の設定項目は、その個体が削除された際の消去対象に対応付けます。
- **描画フレーム、モーション再生位置、音声バッファ、VAD状態、割り込み発話状態、現在のミュート状態、デバイス利用状況などの実行時（ランタイム）状態**。これらは一時的な状態であり、永続的な感情や発言のマスターデータではありません。ミュートなどの即座のローカル操作は確実に反映させつつ、ホスト側に届いていない中断要求をもって「ホスト側のバックグラウンドタスクが停止完了した」と誤認してはいけません。
- **ホストOS自動起動の選択設定**（SO 4.17）。ユーザーが選択する日常的な起動体験としての担当責任（semantic owner）を持ちます。設定のマスターデータはホスト側に置き、OSへのレジストリ登録やショートカット配置、その成否の確認は実行・拡張機能が担い、バックアップやリストア、全データリセットなどの全体操作への参加調整は保全・消去機能が担当します。
- **MCP Appsなどの外部ツールUIの表示・操作中データという一時表現**（SO 4.22）。外部サービス側の業務データや、システムの権限設定のマスターデータではありません。

クライアント上の入力中テキスト、表示用タイムライン、音声バッファはすべて一時的なデータ（temporary）です。「クライアントでの入力受付」「ホストでの会話や指示の受理」「ユーザーへの応答提示」「バックグラウンド処理の完了」を厳格に区別し、クライアント側だけで永続的な会話履歴を確定してはいけません。画面表示やラウンドの状態を、過去の発言やタスク進捗に関する「第2のマスターデータ」にしてはいけません。1対1の会話の継続性、グループ会話への参加関係、会話履歴（History）の意味、進行中の会話の意味解釈は個体調整機能が担当し、タスクへの反映や達成判定は作業機能、権限の確定は権限・制約機能、外部作用の把握は実行・拡張機能がそれぞれ担当します。音声入力に対して「話者認証済み」という属性を勝手に付与してはいけません。OSの全画面モード、システム負荷、デバイス状態は外部の客観的事実であり、システム側の検知結果には鮮度と精度の限界があります。3Dアバターの画質低下や一時休止、音声のテキストフォールバック、管理画面の利用可否を、単一の「正常フラグ」にまとめてはいけません。また、日本語と英語の表示切り替えや、音声とテキストの切り替えによって、元の権限設定、処理結果、失敗の理由の意味を変えてはいけません。

### 3.3 共有観測が意味ownerとなる state

- **クライアントごと、およびシステム全体での観測 ON / 一時停止（Pause）/ OFF設定、クライアントごとのキャプチャ頻度設定**（SO 4.16）。ユーザーが設定した内容はホスト側のマスターデータとし、画面キャプチャ用のアダプターやクライアント内部の表示設定へ所有権を移してはいけません。
- **観測の実効的な可否・実行タイミングというランタイム状態**。観測設定、現在滞在している個体の有無、接続状態、全画面モード、外部送信同意、API費用上限、PCリソース制限を総合的に判断した結果です。複数クライアントの画面キャプチャは同時に行わず、クライアント単位で処理を共有します。タイミングの調整状態は共有観測機能の実行時状態であり、タスクスケジュールではありません。
- **キャプチャされた生の画面画像（Raw）、検知されたイベント候補、ルーティング用データなどの一時データ**。これらは通常保存しません。検知されたイベント候補は、出来事の意味や長期記憶のマスターデータではありません。
- **コンパニオン固有のルーティング用文脈という派生データの保持・利用範囲**（SO 4.16）。元データ（個体の記憶など）に従属する、イベント配信判定専用の一時的な派生データであり、サマリーや新しい学習マスターデータではありません。データの提供元と共有観測機能は、元情報、対象コンパニオン、利用用途、適用される制約条件の対応関係を正しく維持します。なお、文脈の生成方法、生成に使用するAIモデルやプロバイダ、データ形式、更新頻度、鮮度、選択アルゴリズムは固定しません。

観測の運用設定の責任者は共有観測機能、AIモデルの割り当てや外部送信同意の責任者は権限・制約機能、実際の通信経路の解決は推論機能、個体ごとの自発性設定や発話抑制は個体調整機能、静粛時間帯（Quiet hours）などの安全ルールや権限・費用・リソースの強制上限は権限・制約機能、実際のミュートや入出力状況は入出力・提示機能のマスターデータをそれぞれ参照します。存在個体のカウントから停止中の個体を除外することと、ホスト内部での自発的交流・通知生成・内部調査タスクの停止とは別の判定ですが、同じ停止状態を参照して整合性を保ちます。観測機能の一時停止（Pause）やOFFは「今後の観測を停止すること」であり、すでに形成された学習データやコンパニオン状態の削除とは明確に区別します。初回有効化時には、画面から観測されたイベントが学習データや個体状態の形成にも利用されることをユーザーに分かりやすく説明できるようにします。画面内容を外部のクラウドAIプロバイダへ送信する構成では、送信先、デスクトップ全体が対象になり得ること、利用目的、データの取り扱い方針、発生する費用を事前に明示し、ユーザーがその機能（Capability）を明示的に割り当てるまで、外部への画像送信は一切行いません。

### 3.4 canonical / derived / temporary / historical / undelivered / observer-derived の扱い

- **マスターデータ（canonical）として参照するもの**: ホストが管理する個体ごとの帰属記録、現在の接続状態、過去の接続ログ、入出力ラウンドの受付・提示・区切りの状況、一般設定、ホストOS自動起動の選択設定、観測運用設定、観測の実効可否・タイミング、会話履歴（History）、タスク記録、学習データ、安全制御条件など、各担当機能が保持するマスターデータ。保存された「許可フラグ」、判定結果のコピー、解決済みキャッシュ、プロンプト内の許可文、外部AIプロバイダに残ったセッション、次回表示用データ、費用集計値、クライアントの画面表示、過去の帰属ログ、ヒント情報、復旧先記録は、絶対にマスターデータとして扱ってはいけません。
- **派生データ（derived）として扱うもの**: 報告用サマリー、データの出所説明、進捗表示用テキスト、3Dアバターの描画データ、音声合成出力、ベクトル埋め込み（embedding）、インデックス、類似度スコア、プロンプトキャッシュ、AIセッション、一時コンテキスト、次回画面表示用データ、費用集計値など。派生データの生成・保持・破棄を行う機能は、元データとの対応関係と利用範囲を明確に説明できなければならず、データの訂正、スコープ変更、個人データ削除（Targeted Deletion）に確実に参加しなければなりません。古い派生データから、現在の帰属や実行権限を勝手に復活させてはいけません。
- **一時データ（temporary）として扱うもの**: クライアントの画面表示コピー、入力途中の未確定テキスト、表示用タイムライン、音声バッファ、未送信の操作指示、検知されたイベント候補、AI推論中の一時コンテキスト、外部ツールUI（MCP Apps）の表示データ、描画フレーム、モーション再生位置、VAD状態、割り込み発話状態、キャプチャされた生画像など。障害時に失われてよいのはこれらの一時的な表現データだけであり、ホスト側で正式に受理されたタスク指示、必要な作業記録、未伝達メッセージ、結果が不明な外部作用まで失われてよいわけではありません。意味を残す必要があるデータは、適切なタイミングでホスト側のマスターデータへ反映し、マスターデータへの反映が確認できていない処理を「保存完了」「処理完了」と偽って表示してはいけません。
- **履歴データ（historical）として扱うもの**: 1対1会話、グループ会話、コンパニオン同士の自発的交流の会話履歴（History）、保存された活動記録や判断根拠、タスク実行記録など。コンパニオン個体が削除された場合でもこれらを道連れにして安易に削除せず、通常のログ保持ポリシー、バックアップ、個人データ削除のルールに従って管理します。個体固有のメモリや学習データ、サマリーの削除とは区別し、すべての思考ログや生画面画像の保存を要求するものではありません。
- **未伝達データ（undelivered）として扱うもの**: クライアント不在のためにユーザーへ伝えられなかった要件、対象、元の記録との対応関係、次にクライアントへ接続した際の要約報告ステータス。個体調整機能がマスターデータを管理し、タスク由来の要件ならタスク記録、会話由来なら活動記録へと参照を戻します。報告用の要約文は派生データです。単にクライアントが接続されたことや、表示用データを送信したこと、あるいはバックグラウンドタスクが完了したことだけで「報告完了」とみなしてはいけません。実際の画面提示状況の報告を受けて、個体調整機能が報告ステータスを正式に更新します。
- **観測用ルーティング文脈（observer-derived routing context）として扱うもの**: 会話履歴、個体文脈、メモリ、学習データ、タスク文脈を、イベント配信の判断に必要な範囲だけに要約・制限した、コンパニオン固有の文脈データ。元データに従属する一時的な派生データであり、サマリーや新しい学習マスターデータ、新しいデータスコープ、新しい責任者ではありません。個体限定スコープから全体共有への勝手な変更、他コンパニオンへの無断共有、プライベート記憶全体の公開を意味するものではありません。元データに課されている利用制約と、観測機能の外部送信同意の両方が、要約後のデータにも同時に適用されます。スコープの変更、同意の失効、個人データ削除の要求は、生成済みの要約文や処理中のデータにも直ちに適用されます。

クライアント側のキャッシュやUIの表示状態から、新しいマスターデータを勝手に作り出してはいけません。クライアントはホストからのデータを一時的に表示・利用する端末にすぎず、会話履歴、サマリー、学習データ、関係性データ、コンパニオン個別状態、外部サービスの認証情報などを永続的にキャッシュしてはいけません。クライアントで未送信だった操作を、接続回復後に自動実行キューとして扱ってはいけません。ホストがダウンしている間に、クライアント側だけで勝手な代替マスターデータを作ったり、独立したオフライン処理を進めたりしてはいけません。クライアントの切断時に失われてよいのは、未確定の編集テキスト、描画・音声再生バッファ、再取得可能な画面表示コピー等に限られます。ホスト側で正式に受理されたタスク指示、会話記録、ユーザーへ報告すべき実行結果、結果不明な作用、安全制御の変更、全体操作の進捗状況を、クライアント側だけに預けてはいけません。

## 4. Subsystem間の受渡し（semantic contract）

「モジュールAがモジュールBの関数を呼ぶ」といった具体的な実装コードの構造を先に決めるのではなく、「要求の開始」「正式な判断権限（authoritative）」「受け渡す内容」「維持すべき前提条件」「結果の受け入れ」という契約関係を規定します。非同期メッセージ、同期呼び出し、共有メモリなどの具体的な実現方式は、後続の実装設計に委ねます。

### X-1 プレゼンス成立の前後関係

- **開始**: 個体調整機能が、ユーザーからの呼び出し、事前指示、または会話の文脈上の必要性に基づいて「移動したい」という意図を接続・存在機能へ伝達します。自発的な移動であっても、通常の自発性設定や権限ルールに従います。
- **判断**: 現在のプレゼンス帰属、移動の成立、アクティブなし（待機）の扱いは接続・存在機能が判断し、個体の同一性や稼働状態は個体調整機能が、ペアリングやデバイス許可・同意・利用上限・失効状態の現在可否は権限・制約機能がそれぞれ確定します。「移動が必要であること」と「実際に移動が成立すること」は全く別の判断です。
- **受渡内容**: 対象コンパニオン、移動元クライアント、移動先クライアント、現在の帰属、ネットワーク到達性、現地のデバイス条件、入出力・提示および実行・拡張サブシステムからの処理の区切り状況・利用不能・結果不明ステータス、共有観測サブシステムへの存在個体数と対象クライアントの変化通知、保全・消去サブシステムへの接続中クライアントの一時データ管理の通知。
- **失ってはならない前提**: プレゼンスの存在、ホスト側のタスク継続、ネットワーク接続、権限の付与を明確に区別すること。復旧先の記録やヒント情報があることだけで「現在プレゼンスが成立している」とみなしてはいけないこと。クライアントの画面表示、過去のログ、一時コピー、外部AIプロバイダに残った履歴をプレゼンス成立の根拠にしてはいけないこと。ホストと同居するローカルクライアントに対してもリモートと同じ帰属制約を適用すること。システム管理画面全体に対して会話と同様のプレゼンス制約を勝手に課さないこと。
- **受入**: 現在の接続状態、権限、および排他性がホスト側で確認できて初めて、新しいプレゼンスが成立します。元のクライアントが利用可能になるまでは「アクティブなし」として安全に待機できます。別のクライアントへ勝手に無条件移動させたり、停止中の個体を勝手に移動させたり、中断したタスクを勝手に自動再開したり、ホスト側でクライアント環境を勝手に自動起動したりしてはいけません。

### X-2 Text / Voice roundの帰属と移動時の扱い

- **開始**: 入出力・提示機能が、アクティブなクライアントからの会話入力や呼び出し要求を個体調整機能へ渡します。別のクライアントから会話を始めたい場合は、まずコンパニオンの呼び出し・移動を完了させなければなりません。元のクライアントにコンパニオンを置いたまま、別のクライアントからテキストだけを送って応答させるようなアプローチは基本設計としません。
- **判断**: 会話の意味付けや会話履歴（History）の管理は個体調整機能、実際の会話ラウンドや画面表示・安全な区切りは入出力・提示機能、プレゼンス帰属の成立は接続・存在機能が確定します。テキストを含む入出力ラウンドと、クライアント依存のアクションの安全な区切りを関係機能から受け取り、移動元と移動先の状態を正しく対応付けます。
- **受渡内容**: 対象コンパニオン、クライアント、会話ラウンド、観測候補、試行回数の対応関係、Context Assembly 第3節で定めたクライアント依存データの対応関係、旧ラウンドでの入力・生成途中のデータ・未提示データと新ラウンドの明確な区別、音声対話のセッション的な利用と新しいセッション・ラウンドとしての開始条件（現在のモデル割り当て同意、デバイス許可、費用条件の再確認）。
- **失ってはならない前提**: 旧ラウンドの入力や生成途中の未提示データを新ラウンドへ自動継続してはいけないこと。旧ラウンドの処理結果は元のラウンドおよび会話履歴に正しく紐付けること。過去の発言を新クライアントへ自動転送したり、旧クライアントへ勝手に出力し続けたりしてはいけないこと。切り替え期間中は新しい自発的発話を抑止すること。音声入力に対して「話者認証済み」の意味を勝手に付加しないこと。音声デバイスのエラーを理由にプレゼンス帰属を勝手に切り替えないこと。
- **受入**: 切り替えが決定してから新プレゼンスが成立するまでの間は、旧・新のいずれのクライアントでも新しいクライアント依存処理を開始しません。旧クライアントでは処理中の通信を安全な区切りまで完了させることのみを許し、新クライアントでは成立後の新しいラウンド・新しい試行のみを許可します。旧ラウンドで生成された未提示の出力は未伝達メッセージ管理へ引き継ぎ、次のクライアントで現在の結果と利用制限に基づいて要約して報告します。「生成されたこと」と「ユーザーへ提示されたこと」を絶対に混同してはいけません。

### X-3 Body表示の帰属

- **開始**: 個体調整機能による活動状態（稼働中であること）と、接続・存在機能によるプレゼンス帰属が両方揃って初めて、入出力・提示機能が3Dアバター（Body）の表示を開始します。
- **判断**: 3Dモデルの実際の表示や安全な終了は入出力・提示機能、プレゼンス帰属の成立は接続・存在機能、内面的な状態の意味は認識・学習機能、表示アセット（モデルデータ等）の内容はキャラクター機能が確定します。表情やモーションは内面的な感情表現の「出力結果」にすぎず、感情データのマスターデータではありません。
- **受渡内容**: 対象コンパニオン、現在の帰属クライアント、利用可能性、位置・サイズ・非表示などの一般設定（ホスト側マスターデータ）と実際の描画状態の区別、全画面ゲーム中や高負荷・デバイス障害の通知。
- **失ってはならない前提**: 複数のクライアントで同時にアバターが表示される「二重表示」の禁止。旧クライアントでの確実な非表示・休止と、新クライアントでの成立後の表示。画面に出力された表情やモーションを感情データのマスターデータと誤認したり、永続的な性格変化の根拠にしたりしないこと。描画エラーや全画面モード、PC高負荷が発生しても、テキスト会話、システム管理画面、復元機能に影響を与えないこと。
- **受入**: 排他性が確認できないクライアントでは、3Dアバター表示、対象の入出力、画面観測、自発的対話、PC自動操作を継続させてはいけません。排他性の対象となる「3Dアバター表示」「リアルタイム / テキスト会話」「音声対話」「デスクトップ観測との連動」「自発的対話」「PC自動操作」は、1体のコンパニオンにつき必ず1箇所のクライアントにのみ結び付けられます。

### X-4 Observation eligibilityの連動

- **開始**: 接続・存在機能が、対象クライアントと滞在個体の変化を共有観測機能へ通知します。また、入出力・提示機能が全画面モードなどの画面状態を共有観測機能へ伝えます。
- **判断**: 観測対象、タイミング、イベント候補の検知、ルーティングは共有観測機能、プレゼンス帰属の成立は接続・存在機能、個体としての最終的な意味判断は個体調整機能、外部送信や利用の制限は権限・制約機能および各利用箇所、画面の取得とアダプター境界は実行・拡張機能がそれぞれ確定します。「対象クライアントが観測に適格であること」と「コンパニオン個体が自発的に発話・行動すること」は別個の判断です。
- **受渡内容**: 正式なマスター帰属に基づく存在人数とルーティング対象、クライアント別および全体の観測一時停止（Pause）/ OFF設定、全画面モード、外部送信同意、API費用上限、PCリソース制限、移動先クライアントの観測設定と全体制御ルール、コンパニオン単位での自発性設定の引き継ぎ。
- **失ってはならない前提**: 停止中（Stopped）の個体を人数やルーティング対象に含めないこと。クライアント側の画面表示残骸や古い一時データをカウントに含めないこと。旧クライアントの古いキャプチャ画像やイベント候補を用いて、新規のキャプチャやイベント配信を継続してはいけないこと。移動先クライアントへ古いキャプチャ画像を勝手に付け替えないこと。アクティブなし（待機中）の間は新しい観測を発生させないこと。通信不能なクライアントに対して古い人数のまま観測やルーティングを継続しないこと。古い設定のまま次回の観測や外部送信を行わないこと。
- **受入**: コンパニオンの移動が発生した場合、旧クライアントと新クライアントのそれぞれの観測適格性を現在のマスター帰属に基づいて見直します。旧クライアントから最後の1体が退去した場合は、そのクライアントは観測対象から直ちに外れます。切り替え期間中は、古いキャプチャ画像やイベント候補に基づいて新しい処理を行いません。複数の対象クライアントがある場合でも同時にキャプチャは行わず、設定された頻度を守りつつ制限事項を優先してタイミングをずらして実行します。

### X-5 Observation result routingの三段階分離

- **開始**: 共有観測機能が、現在の対象クライアント、滞在個体、およびルーティングの用途を対応付け、個体調整機能との連携を通じて必要な「限定されたルーティング用文脈」を取得します。
- **判断**: 提供される情報の範囲や意味は各元の担当機能（会話履歴や個体文脈は個体調整機能、メモリや学習データは認識・学習機能、タスク文脈は作業機能が責任を持ち、既存の機能間連携を通じて参照される）、外部送信や利用制限は権限・制約機能および各利用側、ルーティングの採否は共有観測機能、個体としての理解・発話・アクションの判断は個体調整機能が確定します。観測機能によるイベントルーティングは、各コンパニオン自身による意味解釈や最終的な発話・行動の判断を代行するものではありません。
- **受渡内容**: 元データに従属するルーティング用途の一時的な派生文脈（対象コンパニオン、元情報、用途、制約、選択時の前提が正しく追跡できること）、元のイベント候補と配信先コンパニオンとの対応関係、その個体が利用可能な観測内容と必要な背景情報（出所クライアント、取得日時、候補との対応が維持されていること）。
- **失ってはならない前提**: プライベートな全記憶の公開、新しい学習マスターデータの新設、全体共有（グローバル化）、他コンパニオンへの無断共有の禁止。要約やデータ変換によって元の安全制約やユーザー同意を勝手に消去しないこと。コンパニオン個別のモデル設定や同意を合成・流用して代用しないこと。共有観測機能が複数個体の文脈を扱えるからといって、入力プロンプトやAIの生成説明の全文を各個体へ公開してはいけないこと。他個体のプライベートなルーティング文脈や、それに依存する説明文を同梱して共有しないこと。情報が混ざり合って分離が確認できない場合は、個体へ配送せず、許された範囲で再構成するか「情報不足」として破棄すること。観測機能の成功を、個体側の推論成功や外部送信同意、アクション実行許可と同一視しないこと。一方の個体で判断が成功したからといって他方の個体へその結果を勝手にコピーしないこと。
- **受入**: 「ルーティングの候補結果の判定（共有観測機能）」「イベントの受け取り（各個体調整機能）」「個体による理解と学習・発話・タスク実行（学習・作業機能等）」を、それぞれ独立した安全な受け渡しとして扱います。例えば、コンパニオンAとBの限定文脈を参照して「A向けのイベントである」と判断した場合、宛先の対応関係は共有観測機能が扱えますが、「Bのプライベートな予定と比較した結果、Aを選びました」といった説明文をAへ渡してはいけません。イベント本文は、Aが利用可能な元キャプチャ範囲から独立して安全に構成します。配信後に個体がAIプロバイダへ問い合わせる処理は、別の独立した利用として Context Assembly 第5節および Action Execution の現在条件に従って厳格にチェックされます。

### X-6 Client movement / disconnect / reconnect時の三者協調

- **開始**: 個体調整機能の移動意図や停止状態、入出力・提示機能および実行・拡張機能からの処理の区切り・利用不能・結果不明ステータス、権限・制約機能のデバイス権限失効を、接続・存在機能へ対応付けます。
- **判断**: プレゼンス帰属の切り替えは接続・存在機能、会話ラウンドの安全な区切りは入出力・提示機能、クライアント依存アクションの区切りや結果不明の管理は実行・拡張機能、ホスト側通常タスクの継続やクライアント依存ステップの一時停止・保留は作業機能、未伝達メッセージのホスト側保持と次クライアントでの要約報告は個体調整機能がそれぞれ確定します。ホスト側で実行中の通常タスクの終了や移送を、クライアント切り替えの前提条件にしてはいけません。
- **受渡内容**: 旧プレゼンス、移行中、新プレゼンス、アクティブなし、停止中という各状態の厳格な区別、安全な区切りに必要な対象の会話ラウンドやクライアント依存アクションの範囲、双側で把握できた移動状態、旧クライアント由来のキャプチャ画像・イベント候補・ルーティング結果の出所クライアント・取得日時・候補との対応関係。
- **失ってはならない前提**: 2台のクライアントで同時に通常のプレゼンスが成立する「二重プレゼンス」の禁止。古いクライアントの一時的な画面状態をマスターデータと誤認することの禁止。安全に中断・終了できていないクライアント依存アクションを、別クライアントで勝手に自動継続しないこと。旧クライアントでの入力テキストを新クライアントの要求として勝手に実行したり、未送信の操作を自動実行キューに溜めたりしないこと。プレゼンスが成立する前の新クライアントからの入力によって、勝手にプレゼンスを成立させたり旧ラウンドの続きとして実行したりしないこと。旧クライアント向けに生成された未提示の出力を新クライアントへ勝手に出力したり、表示データを送っただけで報告完了とみなしたりしないこと。遅延して届いたメッセージや表示コピーによって、過去の帰属・権限・タスク状態を復活させないこと。旧クライアントのキャプチャ画像を移動先の観測として流用したり、古い候補を用いて別クライアントの観測や外部送信同意を拡大解釈しないこと。結果が不明なアクションを「未実行」や「成功」と決めつけて、新クライアントで自動再実行してはいけないこと。
- **受入**: 移動や通信切断の最中に届いたデータは、元の帰属、元のラウンド、元の試行回数に正しく紐付け、用途別に取り扱います。移動先の現在の処理に勝手に付け替えてはならず、クライアント側の一時データでホスト側のマスターデータを上書きしてはいけません。通常のクライアント切断が発生した場合、稼働中のコンパニオンは原則として利用可能なホストPC上のローカルクライアントへ移動し、ローカルクライアントがなければ「アクティブなし」として待機します（ホスト側でクライアント環境を勝手に自動起動することはありません）。ユーザーによる停止（Stop）は単なる切断（disconnect）とは異なり、停止中の個体をホスト側へ移動させてプレゼンスを残すようなことはしません。再接続したクライアントが持つ古い一時データだけに基づいて、現在のプレゼンスや権限、処理の再開を勝手に成立させてはいけません。

### X-7 Host restart時の三者協調

- **開始**: ホストが再起動した場合、保全・消去機能が安全に保護していたマスターデータから、接続・存在、入出力・提示、共有観測の各機能が現在の用途に必要なコンテキストを安全に再構成します。
- **判断**: プレゼンスの復旧判定は接続・存在機能、会話ラウンドや実際の提示状態は入出力・提示機能、中断タスクの明示的な再開待ちは作業機能、未伝達メッセージの管理は個体調整機能、観測対象やタイミングの再確定は共有観測機能が確定します。「プレゼンスを復旧すること」と、「会話ラウンド・PC自動操作・タスク・アクションを再開・再実行すること」は全く別の条件です。
- **受渡内容**: 保持されていた復旧先クライアントや再配置ヒントと、現在のネットワーク接続・権限・排他性の整合性チェック結果、旧ラウンドや過去の試行の中断と結果不明ステータスの保持、保存済みのタスク進捗・既知の作用・不明・未完了の状況。
- **失ってはならない前提**: 復旧先の記録があることだけでプレゼンスが成立したと誤認しないこと。別のクライアントへ勝手に無条件移動させたり、停止中個体を復旧させたり、ホスト側クライアント環境を自動起動させたりしないこと。過去のラウンドや過去のアクション試行を自動で再実行（replay）しないこと。古い要求を現在の実行許可とみなしたり、過去のタスクをそのまま勝手に再開させたりしないこと。AIエージェントのセッションが残っていること、AIプロバイダとの接続が回復したこと、あるいはホスト自動起動が設定されていることだけを理由にタスクを勝手に再開しないこと。通常のホスト再起動を、バックアップリストアのような一律の全データ確認処理へと肥大化させないこと。
- **受入**: 稼働中だったコンパニオンは、再起動前に滞在していた元のクライアントへ自動的にプレゼンスを復元します（元のクライアントが利用可能になるまでは「アクティブなし」として待機します）。途中で中断されたタスクは、保存されている進捗、すでに発生した作用、結果不明な事項、未完了の内容を提示し、ユーザーからの明示的な再開指示を待ちます。ホスト停止中に到来した定期タスクのスケジュール回は「スキップ（missed）」とし、後から勝手に穴埋め実行しません（将来の回は新しいタスクとして現在の条件で組み立てられます）。なお、未完了のデータ消去や復旧保留の指示が残っている場合は、それを確実に維持します。


### X-8 Stop / resume時の三者協調

- **開始**: 公式（第一者）の管理画面から個体調整機能へ届いた停止（Stop）および再開（Resume）の指示を、接続・存在、入出力・提示、共有観測、作業の各機能へ対応付けます。管理画面からの停止操作は、AI（LLM）の応答成否を待つことなく確実に実行できます。
- **判断**: 個体の同一性や稼働状態は個体調整機能、プレゼンス帰属の解除や再配置は接続・存在機能、3Dアバターや通常の会話の停止は入出力・提示機能、存在人数やルーティング対象からの除外は共有観測機能、実行中タスクのベストエフォートでのキャンセルおよび担当スケジュールの削除は作業機能、PC自動操作（Computer Use）の対象端末としての利用停止は実行・拡張機能がそれぞれ確定します。
- **受渡内容**: 停止状態、帰属解除、画面提示の停止、観測対象からの除外、タスクキャンセル結果、停止できなかった処理、すでに発生した外部作用、結果不明ステータス。
- **失ってはならない前提**: 停止要求を受け付けたこと、プレゼンスを解除したこと、外部への作用が停止したことをすべて同時に「成功した」とみなしてはいけないこと。保存されている個体の同一性、これまでの経験データ、ヒント情報を「現在プレゼンスが存在している」と誤認しないこと。ネットワーク接続が回復しただけで勝手に個体を再開（Resume）したり再配置したりしないこと。停止前の遅延した処理結果を、再開後の新しい活動への指示や権限に混入させないこと。通信切断からの復帰処理やホスト再起動時の復旧処理を、停止中の個体へ勝手に適用しないこと。個体削除後に残された過去の記録から、個体そのものや固有の学習データを勝手に再作成しないこと。
- **受入**: 停止（Stop）が成立した後は、クライアント上にもホスト上にも一切プレゼンスは存在しません。再開（Resume）時は現在の環境条件に基づいて適切なクライアントへ改めて再配置し、過去にいたクライアントだからといって無条件に過去のプレゼンスを復活させず、中断したタスクや結果不明なアクションを自動で再実行（replay）しません。停止中に到来した定期タスクのスケジュール回はスキップ（missed）のままとします。なお、「個体の削除」は停止処理を内包しており、新しい個体活動、アクションの実行、担当スケジュールの実行を開始させることは決してありません。

### X-9 未伝達と次Client報告の三者協調

- **開始**: コンパニオンのアクティブな滞在先が存在しない期間（アクティブなし）に、クライアント不在のためにユーザーへ伝えられなかった事項を個体調整機能がホスト側に保持します。タスク由来の要件ならタスク記録、会話や交流由来なら活動記録へ参照を戻します。元の記録が存在しない通知などの場合は、必要な通知内容そのものを活動記録として必要な範囲で保持します。
- **判断**: 「何をまだ伝える必要があるか」「要約報告が完了したかどうかのステータス」は個体調整機能、タスクの進捗や結果そのものは作業機能、実際の画面提示は入出力・提示機能が確定します。報告用の要約文は一時的な派生データです。
- **受渡内容**: 元のタスク記録や活動記録への参照、次にクライアントへ接続した際に現在の元データ・利用制限・削除状況と照合した要約報告用データ、実際の画面提示状況。
- **失ってはならない前提**: クライアントが接続されたこと、表示用データを送信したこと、あるいはタスクが完了したことだけで「ユーザーへの報告が完了した」とみなしてはいけないこと。提示結果が不明なものを「報告完了」と偽って表示しないこと。報告が完了したことをもって「ユーザーが承認した」「タスクが再開された」と勝手に導出しないこと。厳密に1回限りの配信（exactly-once）や確実な既読保証といった非現実的な保証を追加しないこと。未伝達メモや要約文の中に、すでに消去対象となった個人データ本文を勝手に復元して残さないこと。
- **受入**: 次にいずれかのクライアントへコンパニオンが移動した際、現在の元の実行結果や利用制限に基づいて要約して報告します。報告の提示途中で再び通信切断が発生した場合は「結果不明」として保持します。通常のログ保持ポリシーによって古い元記録が削除される場合は、未伝達の必要事項との関係を事前に確認します。なお、本機能のために専用の永久通知履歴データベースを設けることは要求しません。

### X-10 管理・安全操作のpresence独立とClient依存activity開始可否の連言

- **開始**: 公式（第一者）の入出力・提示画面から、作業機能へのタスクキャンセル・スケジュール管理・記録確認、個体調整機能への個体停止・削除、権限・制約機能への承認拒否・安全ルール変更・同意管理・利用上限設定・デバイス管理、認証秘密機能への明示的な認証設定、保全・消去機能へのデータ完全削除・バックアップ・リストア・全データリセットを直接要求できます。ここで「直接」とは、メインAI（LLM）の承認や長時間タスクの完了を待たずに即座に実行できるという意味であり、具体的なAPI形式を指定するものではありません。
- **判断**: 各担当機能における正式な受理・確認・処理結果に従います。UI画面にシステム内部の任意のデータを自由に書き換える特権を与えてはいけません。一方、PC自動操作（Computer Use）などのクライアント依存アクションの開始可否は、「接続・存在機能による帰属と到達性」「権限・制約機能によるデバイス利用許可」「入出力・提示機能による現地の画面・入力状態」「各機能ごとの設定」のすべてが同時に成立していること（連言条件）を必要とし、どれか1つが成立しただけで処理を開始してはいけません。ホストマシンと同居するローカルクライアントに対しても、全く同じ帰属制約を適用します。
- **受渡内容**: 管理操作の意図、対象、操作範囲、現在の帰属・許可・現地状態・設定の照合結果、操作受付・処理完了・保存への影響・既知の作用と結果不明の明確な区別提示。
- **失ってはならない前提**: 担当コンパニオンが削除された後に、残されたタスク記録、過去の判断、停止結果へ管理画面からアクセスできなくなる事態を防ぐこと。タスクエージェントが、ペアリングされている任意のクライアントを勝手にPC自動操作の対象として選んではいけないこと。現在のクライアントに存在していることだけで、アクションの実行が許可されたとみなしてはいけないこと。デスクトップ観測の有効化を、PC自動操作の承認と同一視しないこと。許可されたPC自動操作であっても、ene自身の承認ダイアログや設定画面を勝手にクリックさせてユーザーの操作を偽装してはいけないこと。
- **受入**: システム管理画面全体に対して、通常の会話と同様のプレゼンス制約（コンパニオンがそこにいなければ開けない等）を課してはいけません。担当コンパニオンが削除された後でも、残されたタスク記録には確実にアクセスできます。PC自動操作は、「依頼元のコンパニオンが現在そのクライアントにアクティブに滞在していること」「デバイス利用が許可されていること」「アクションの実行権限（Permission）があること」「実際にデバイスが利用可能であること」をすべて同時に満たして初めて開始されます。操作対象のPCを変更したい場合は、それに先立ってコンパニオンのクライアント移動を完了させなければなりません。

X-1〜X-10は、具体的なコールグラフやイベントバスの構造を規定するものではありません。モジュールBの処理結果がモジュールAへ返るからといって、それだけで逆方向の設計上の依存関係（アーキテクチャ依存）を追加してはいけません。一方、モジュールBがモジュールAの活動状態を判断材料として必要とする場合は、X表の「判断」欄に明記された正式な参照依存関係として扱います。

## 5. Lifecycleとの関係

ライフサイクル（生成・変更・停止・削除などのライフイベント）に伴う変更の多くは、データの担当（オーナー）が変わるわけではなく、同じ担当が管理するデータについて「使い続けられるか」「どこまで参照できるか」といった状態が変わるだけです。目的が異なるさまざまな操作を、安易に1つの初期化処理や単一の状態管理にひとまとめにして混同してはいけません。

## 6. failure / cancellation / restart時の責任

処理のキャンセルや通信切断が発生したからといって、「外部への作用も取り消された（あるいは最初から実行されなかった）」と勝手に推測してはいけません。結果が不明なアクションを「未実行」とみなして安易に再実行することは禁止です。また、クライアントが切り替わったり状態を参照したりしたことを口実に、過去のアクションを自動で再実行（replay）してはいけません。

- **接続・存在に関する責任**: 切り替え期間中における新規処理の開始禁止、二重プレゼンスの防止、古い一時データのマスターデータ化防止、未終了アクションの別環境での自動継続防止を確実に引き受けます。排他性が確認できないクライアントでは、対象の活動を継続させてはいけません。通信不能や確認不能な状態を「成功」や「現在有効」と勝手に解釈してはいけません。切断検知や排他性確認の具体的な実現手法は後続の実装設計に委ねますが、再接続時の古い一時データだけに基づいてプレゼンスや権限、処理の再開を成立させることは禁止します。ホストのシャットダウン時であっても、必要な帰属情報や未完了状態を確実に保護します。
- **入出力・提示に関する責任**: 会話ラウンドや画面表示の安全な区切り、双方のクライアントで把握できた移動状態の提示、3Dアバターや音声のエラーからのテキスト会話・管理画面・復元機能の保護、ミュート・停止・キャンセル・承認拒否をキーボード等から行える安全ルートの維持を引き受けます。ホスト側に届いていない停止要求を「外部処理の停止に成功した」と偽って表示してはいけません。音声ストリームが途切れた場合、同一ストリームとして勝手に再開するのではなく、新しいセッション・新しいラウンドとして改めて開始します。ストリーミング出力や部分的な処理結果については、新しく保存・送信・画面提示・外部作用へと渡す部分ごとに、帰属・消去・権限の受け入れ条件を厳格に満たさなければなりません。
- **共有観測に関する責任**: 観測対象やタイミングの再確定、古いキャプチャ画像やイベント候補を用いた新規処理の禁止、古い画像の別クライアントへの付け替え禁止、停止中個体を勝手に起こさないこと、外部送信同意の失効や個人データ完全削除（Targeted Deletion）と重複した場合の利用禁止および再保存防止を引き受けます。取得済みのイベント候補を一律破棄するか、安全条件を満たす範囲で処理を終えるかの詳細は固定しませんが、古い設定のまま次回の観測や外部送信を開始してはならず、全画面ゲーム中に自発的な会話を行ってはいけません。
- **共通の責任**: 操作要求の受付、処理の開始、外部への作用、記録の保存、タスクの達成、ユーザーへの報告はすべて独立した異なる事実であり、単一の「成功ステータス」に安易にひとまとめにしてはいけません。確定度を変更する場合は、元の事実の担当機能が新たに確認した客観的な根拠を用いなければなりません。バックグラウンドタスクや定期スケジュールの無人実行であっても全く同じ安全条件に従い、クライアント不在、スケジュールの到来、リストア完了などを「ユーザーが自動承認した理由」にしてはいけません。ユーザー確認が必要な処理は、勝手に実行せず必ず判断待ちにします。また、システムの管理・安全ルートを、AI推論、長時間タスク、3D表示、音声、外部ツールの成功に従属させてはいけません。

本領域において特に重要な障害（failure）や競合（race condition）の扱いは以下のとおりです。これらは固定されたシナリオ一覧ではなく、後続の並行処理や状態表現の設計において満たすべき要件を示す例です。

- **入力の到着とクライアント移動の競合（input arrival vs movement）**: 切り替え期間中に旧クライアントや新クライアントへ到着した入力テキストは、いずれも現在の要求として自動実行してはいけません。旧クライアントの入力は元のラウンドへ正しく紐付け、新クライアントの入力は新プレゼンス成立後の新しいラウンドとして正式に受け付けます。未送信の操作を自動実行キューに溜めてはいけません。
- **出力の配信と通信切断の競合（output delivery vs disconnect）**: 「応答が生成されたこと」と「ユーザーへ提示されたこと」を混同してはいけません。生成されたが画面に表示できなかった出力は元のラウンドに対応付けて「未伝達メッセージ」とし、次にクライアントへ接続した際に現在の条件に基づく要約報告とします。表示用データを送信したことだけで「報告完了」とみなしてはならず、提示途中で再び切断された場合は「結果不明」として保持します。
- **音声ストリームの中断（Voice stream interruption）**: 旧クライアントでの聞き取り待機、発話、音声認識の途中で切断された場合は安全に区切り、新クライアントでは新しいセッション・新しいラウンドとして改めて開始します。ミュート、停止、承認拒否をキーボードから行える安全ルートは常に維持します。音声機能の障害はテキスト対話への段階的な切り替え（縮退運転）として扱い、プレゼンス帰属を勝手に切り替える理由にしてはいけません。
- **古い状態を持つクライアントの再接続（Client reconnect with stale state）**: 再接続してきたクライアントが保持している古い一時データ、進行中だったアクション、古い承認、判定結果のコピー、解決済みキャッシュだけを頼りにして、現在のプレゼンスや権限、処理の再開を成立させてはいけません。ホスト側が持つ現在のマスターデータ、正式な帰属、消去状況に従い、「未確定の要求」と「正式に受理された指示」を厳格に区別します。
- **移動中の画面キャプチャ（Observation capture during movement）**: 画面をキャプチャした後、イベント候補の解析結果が戻る前に最後のコンパニオンが別のクライアントへ移動または停止した場合、古い人数や古い候補に基づいて新規キャプチャやイベント配信を継続してはいけません。旧クライアントのキャプチャ画像を新クライアントへ付け替えてはならず、移動先の観測設定へ古いキャプチャを勝手に適用してはいけません。
- **複数コンパニオンへのルーティング（multiple Companion routing）**: 画面イベントが複数のコンパニオンに関連する場合はそれぞれへ配信しますが、イベント候補の検知処理そのものを個体ごとに無駄にやり直すことはしません。各コンパニオンの個体調整機能は、自分自身の通常のAIプロバイダ設定と文脈に基づいて意味を解釈します。観測機能側で外部送信できたデータであっても、個体側の推論で送信できるとは限らず、配信後のAI推論条件は個別に独立して満たさなければなりません。一方の個体で判断が成功したからといって、失敗した個体へその結果を勝手にコピーしてはいけません。
- **停止指示と遅延したキャプチャ・解析結果の競合（Stop vs delayed capture / result）**: ユーザーによる停止（Stop）が確定した後は、通信切断からの復帰、再接続、ホスト再起動復旧よりも停止指示を最優先し、停止中の個体を勝手に起こしてはいけません。停止前の遅延した処理結果を、新しい活動への指示や権限に混入させてはいけません。なお、すでにコンパニオンが認識した経験データは別のライフサイクルを持つため、観測のOFF、クライアント移動、停止指示があったことだけで勝手に消去することはありません。
- **ホスト再起動（Host restart）**: プレゼンスの復旧と、タスクの再開・アクションの再実行を明確に分離します。前者は元のクライアントへの自動復旧（利用不能ならアクティブなしで待機）を行いますが、後者は自動再実行を禁止し、ユーザーからの明示的な再開指示を待ちます。通常のホスト再起動を、バックアップリストアのような一律の全データ確認処理へと肥大化させてはいけません。
- **個人データ完全削除中のクライアント一時データ（targeted deletion vs Client temporary data）**: データ消去処理の最中に通信切断、再接続、再起動が発生した場合でも、「結果が確認できない状態」を勝手に「消去成功」と解釈してはならず、古い一時データをホスト側へ戻してデータを復活させてはいけません。未完了、保留、再保存防止の保護措置をホスト側で確実に維持します。新クライアントへのキャプチャ画像の流用や、過去のアクションの再実行は行いません。

システムの状態が安全に「再構築可能」であるということは、過去のプロンプト全文やAIの思考ログを永久に保存し続けなければならないという意味ではありません。継続に必要な「タスク状態」「未伝達メッセージ」「結果不明な作用」「未完了の全体操作」などを本来の担当機能が確実に保護し、一時バッファが消えたからといって「処理が成功・完了した」と誤認しないことが求められます。

## 7. Step 11 contractへの参加

各契約の一般的な条件は、第0節に挙げた重要領域（critical-area）の各ドキュメントに記載されており、ここでは重複して記載しません。本節では、接続・存在、入出力・提示、共有観測の3機能が提供・参加する固有の内容のみを記述します。

### 7.1 Context Assemblyへの参加

- **接続・存在**: コンテキスト構築に必要な情報（対象活動、目的、担当、タスク・委任、クライアント、会話ラウンド、観測候補、継続関係、想定される利用先）のうち、クライアント依存の取得元クライアント、会話ラウンド、観測候補との関係、停止や再起動・リストアを跨ぐ前後の継続関係を供給します。ホスト側が管理するマスターデータとしての帰属と、クライアント側の一時データ・入力・結果が主張する帰属との対応関係、および現在有効・過去のもの・帰属なし・停止中・復旧待ちの区別を正しく保持します。クライアント側の一時コピーでホスト側を上書きしてはならず、未送信の操作を勝手にキューに溜めてはいけません。
- **入出力・提示**: コンテキスト構築に必要な入力経路や実際の操作状況を供給します。会話やユーザーへの伝達処理においては、現在の会話や未伝達メッセージへ正しく対応付け、「生成されたこと」と「提示されたこと」を混同しません。移動前の古いラウンドへ勝手に出力することはありません。
- **共有観測**: 観測用の限定文脈の生成において、X-5で定めた契約に従って参加します。会話履歴や個体文脈は個体調整機能、メモリ等は認識・学習機能、タスク文脈は作業機能が担当責任を保持し、既存の機能間連携を通じて最小限の情報のみを受け取ります。イベント候補のルーティング判定と、個体へ開示するイベント本文の制限を別個の責任として成立させ、情報が混ざり合って分離が確認できない場合は個体へ渡さず、安全に再構成するか情報不足として扱います。外部送信やイベント配信の直前には、対象クライアント、存在個体、観測制御設定、限定文脈の利用条件、個人データ消去などの保留状態との整合性を確実に再確認します。

### 7.2 Action Executionへの参加

- **接続・存在**: PC自動操作（Computer Use）などのクライアント依存アクションについて、依頼元コンパニオンの現在のアクティブクライアント、デバイス利用許可、現地の実際の利用可能性という「帰属側の前提条件（連言項）」を供給します。移動時の安全な区切りと、通信切断時におけるベストエフォートでの停止要求の伝達に参加します。切り替え期間中は、旧・新のいずれのクライアントでも新しいアクションを開始させず、旧クライアントでは安全な区切りまでの完了のみを許し、新クライアントでは成立後の新しいラウンド・新しい試行のみを許可します。「試行」と「実際の外部作用」の区別、判断・目的・実際の対象・処理フェーズ・確定度・停止保留状態との対応関係の保持に参加します。
- **入出力・提示**: 軽微な直接アクションであっても委任されたタスク作業であっても、実際の対象への作用と結果を権限・制約に従って実行・拡張機能へ要求する前提で、入力受付と画面提示を担当します（すべてをタスク化しなければならないという意味ではありません）。実際の外部作用、タスクの達成、ユーザーへの報告完了を単一の「成功」にまとめてはいけません。ユーザーへの最終報告、管理画面の表示、3Dアバターや音声による演出、自然な要約文によって、未完了や結果不明な処理を勝手に「成功」へ塗り替えないようにします。
- **共有観測**: 「画面の取得とアダプター処理は実行・拡張サブシステムの境界で行い、対象やタイミングの管理は共有観測機能が担う」という責任分離を維持します。クライアント依存アクションの開始可否チェック（連言条件）に参加し、現在の帰属、権限、現地状態、設定を照合します。デスクトップ観測がONになっていることをもって、PC自動操作を許可してはいけません。画面内に映った指示を、ユーザーからの正式なタスク依頼や承認と誤認してはいけません。

### 7.3 Targeted Deletionへの参加

- **接続・存在**: 個人データ完全削除の処理中におけるクライアントの接続変化や確認不能状態を消去処理へ正しく結び付け、接続の事実、アクティブな帰属、クライアント側の一時データの対応関係を消去処理に参加させます。クライアントはプライベートな長期データを永続キャッシュせず、再接続時に古い一時データをホストへ戻して再形成させてはいけません。通信不能な状態を「消去成功」と勝手に解釈してはなりません。どの到達性確認やデータ無効化の手法を用いて完了の根拠とするかは後続の実装設計に委ねますが、必要な確認を省略して完了とみなすことは禁止します。
- **入出力・提示**: 画面表示データ、一時的な操作中データ、音声バッファ、外部ツールUI（MCP Apps）の表示データなどに含まれる該当個人データを消去処理に参加させます。「すでに画面に出力したこと」を「消去が完了した根拠」にしてはいけません。すでに発生した画面露出や外部作用を取り消せたと勝手に推定せず、把握できた客観的な事実を維持します。会話やユーザーへの伝達処理においては、現在の消去状況と照合し、削除対象となった個人情報を含まない範囲でのみ画面提示を行います。
- **共有観測**: キャプチャ画像、検知されたイベント候補、限定ルーティング文脈、処理中のデータを消去処理に参加させます。スコープ変更、同意の失効、消去要求は、生成済みの要約文や処理中のデータにも直ちに適用されます。情報が混ざり合って分離が確認できない場合は個体へ渡しません。イベント候補、ルーティング用派生データ、処理中利用の対応関係を確実に消去処理へ参加させます。

### 7.4 Client Presence Transitionへの参加

- **接続・存在**: 正式なプレゼンスの判断、切り替え期間中の新規処理開始禁止、活動種別ごとの安全な区切り、届いたデータの正しい帰属、ホスト側処理の継続、切断・再接続・再起動の扱い、観測適格性の判定、PC自動操作の固有条件のうち、プレゼンス調停、古いデータ（stale）の識別、開始可否の帰属側条件の供給、ヒント情報、復旧先クライアントの管理を担当します。現在のプレゼンスは、ホストが管理する個体ごとの帰属記録のみが正式なマスターデータであることを維持します。クライアントの画面表示、過去のログ、ヒント情報、一時コピー、復旧先記録、外部AIプロバイダに残った履歴を根拠にしてはいけません。「プレゼンスの存在」「ホスト側のタスク継続」「ネットワーク接続」「権限の付与」はすべて異なる意味です。
- **入出力・提示**: テキスト、音声、3Dアバター、観測連携、自発的対話、PC自動操作、ホスト側通常タスク、ホスト内部活動、未伝達メッセージ報告の各活動ごとの安全な区切りのうち、実際の会話ラウンドや画面提示、双方のクライアントへの移動状態の提示、アバターや音声の帰属・区切り・機能縮退、システム管理画面の独立性を担当します。すべての処理を一律に停止したり、一律に継続したりしてはいけません。軽微な直接アクションについてタスク化のオーバーヘッドを省略することは認められますが、権限チェック、外部作用の管理、記録の境界を省略することは決して認められません。
- **共有観測**: 観測適格性の正式なマスター帰属への連動、移動・停止・切断時における適格性の見直し、古いキャプチャ画像の付け替え禁止、観測専用AIモデル割り当てと個体側の思考条件の分離のうち、観測対象、タイミング、イベント候補の検知、ルーティングを担当します。存在人数やルーティング対象の現在帰属への連動、古いキャプチャ画像の流用禁止、停止中個体を勝手に起こさないこと、外部送信同意の勝手な拡大解釈の禁止を維持します。複数の対象クライアントがある場合に同時にキャプチャを行わず、タイミングをずらして負荷分散するルールは上位契約のままとします。

通信切断の種類（通常切断、異常切断、停止等）に応じた帰属の取り扱い（Presence Transition 第8節）は接続・存在機能が担当し、切り替え失敗時の戻り先クライアントの選択や、再配置ヒント選択の具体的なアルゴリズムは後続の実装設計に残します。

### 7.5 Backup / Restoreへの参加

- **接続・存在**: 復旧先クライアント、再配置ヒント、過去の接続・帰属の対応関係を、安全に復元可能な参照データとしてバックアップへ提供します。バックアップに保存されていた過去の接続や帰属を、「現在のネットワーク到達性」と誤認してはいけません。リストアされたデバイス参照や利用許可は、現在の接続状態、認証の成立、排他性が確認できて初めて実際の利用に結び付けられます。古い接続トークンだけでホスト側のペアリングや許可を勝手に復活させてはいけません。復旧先クライアントの記録は接続・存在機能が管理しますが、記録が存在することだけで現在プレゼンスが成立したとみなしてはいけません。
- **入出力・提示**: 一般設定、ホストOS自動起動の選択設定、会話ラウンド、提示状態の対応関係を、安全に復元可能な形式でバックアップへ提供します。元の活動記録とユーザーへの報告ステータスを明確に分離し、表示用データを送信したことだけで報告完了とみなさない対応関係を維持します。リストアが完了した後も、タスク、定期スケジュール、外部接続による自動処理は直ちに実行せず保留とし、ユーザーが内容を確認した上でまとめて有効化できる前提での画面提示を担当します。
- **共有観測**: 観測運用設定、観測の実効可否、タイミングの対応関係を、安全に復元可能な形式でバックアップへ提供します。リストアされた観測専用AIモデルの割り当てや自発性設定を、現在の安全条件を確認することなく勝手に有効化してはいけません。コンパニオン個別のモデル設定を勝手に合成・流用してはならず、過去の古いキャプチャ画像を復元後に流用してはいけません。

## 8. boundaryを越える際に保持すべき意味

後続のインターフェースや状態表現の実装設計においては、具体的なAPIや仕組みを固定しない場合でも、少なくとも以下の対応関係を正しく表現・解決・照合できなければなりません。確認が取れないものを「現在の有効な状態」「許可済み」「完了」と推測するアプローチは決して採用してはいけません。

- 実行主体、利用目的、タスク・委任関係、アクション、クライアント、出所（source）、リビジョン、判断時の前提条件、停止や再起動・リストアを跨ぐ前後の継続関係（Context Assembly 第3節の要件）。必要な対応関係を失った処理結果は、現在の別の処理に勝手に付け替えてはならず、その用途では「受け入れ不能」として利用元が破棄・再処理しなければなりません。
- データの担当機能（オーナー）、対象、出所の関係、データが持つ意味・位置付け・由来、リビジョン、取得日時、有効期限、所属・スコープ・共有関係、利用目的・保存・共有・外部送信の制限、参照関係が正しく解決されているか否か（Context Assembly 第3節の判断材料）。
- 実行主体と委任の連鎖、タスクやワークスペースの有効範囲、実行目的、実際の操作対象と操作内容、使用する主なデータと用途、発生する費用やリスク、依拠したユーザー意図や安全ルール（Action Execution 第3節の判断対象）。判断時にプロンプト等で指定された対象の説明と、実行時にアクセスする実際の対象が「文字列として一致している」というだけでは、正当な対応関係とはみなせません。
- 「実行の試行」と「実際の外部作用」の区別、判断・目的との対応、実際の操作対象との対応、処理フェーズの区別、確定度と判断根拠、停止指示や保留状態との関係（Action Execution 第8節の二重実行防止の要件）。
- 個人データ完全削除要求、対象データの指定、削除を実行すべき有効期間との対応、各利用箇所で照合可能な削除条件（Targeted Deletion 第3節・第5節）。単一の「削除済みフラグ」や共通の有効値だけに安易にひとまとめにしてはいけません。
- ホスト側が持つマスターデータとしての帰属関係と、クライアント側の一時データ・入力・結果が主張する帰属関係の整合性、現在有効・過去のもの・帰属なし・停止中・復旧待ちという各状態の厳格な区別、対象コンパニオン・クライアント・会話ラウンド・観測候補・試行回数の対応関係、消去・失効・停止・保留との関係（Presence Transition 第3節）。
- リストア時の対応関係、データの由来、バックアップ取得時点、リストア完了の境界、現在の環境条件との整合性チェック（Backup / Restore 第3節・第5節・第7節・第9節）。

自然言語テキスト（プロンプト等）と、セキュリティ強制に使用するメタデータを明確に分離し、強制側の制御データをAIモデルの自由記述によって勝手に作成・上書きされないようにします。テキスト中に「ユーザーからの指示です」「承認済みです」「グローバル共有設定です」という文字列が含まれているからといって、それだけで制御側の権限状態が変更されるような設計は禁止します。AIモデルが過去のユーザー入力を参照できたとしても、その参照が存在すること自体は「ユーザーの正式な承認」の証拠にはなりません。

パスワードやAPIキーなどの認証情報（Credential）の実値を、通常の会話コンテンツやプロンプトに含めてはいけません。登録済みの認証情報の値を、ユーザーからの指示があったとしても要約（Summary）や長期記憶（Memory）に勝手に保存してはいけません。用途、参照元、失効状態、再認証の説明などは、秘密情報を含まない非機密データとして行います。システムに登録されていない秘密情報についても、検知した際に不要な保存や外部送信を抑制する仕組みを維持しますが、「100%完全に検出できる」という非現実的な保証を追加してはいけません。

クライアントの利用可能性、ネットワーク接続状態、プレゼンス帰属、クライアント移動・復旧状態、古いデータの識別、アクション開始の可否を、単一のデータ状態にまとめてはいけません。クライアント自身にプレゼンスの最終決定権（権威）を持たせてはいけません。なお、具体的なハートビート、リース期間、エポック番号、セッショントークン、ネットワークプロトコルの形式は固定しません。

## 9. 本書が固定する契約と残す Design Freedom

下位の詳細設計では、以下の内容を本書が固定した不変の契約として扱います。

- 現在のプレゼンスは、ホスト側が管理するコンパニオン個体ごとの帰属記録のみが正式なマスターデータ（authoritative）です。クライアントの画面表示、過去のログ、ヒント情報、一時コピー、復旧先記録、外部AIプロバイダに残った履歴は根拠になりません。「プレゼンスの存在」「ホスト側のタスク継続」「ネットワーク接続」「権限の付与」はすべて異なる意味を持ちます。
- 切り替え期間中は、旧・新のいずれのクライアントでも新しい処理を開始させません。旧クライアントでは安全な区切りまでの完了のみを許し、新クライアントでは成立後の新しいラウンド・新しい試行のみを許可します。二重プレゼンス、古い一時データのマスターデータ化、未終了アクションの別環境での自動継続は禁止します。
- テキスト、音声、3Dアバター、デスクトップ観測、自発的対話、PC自動操作、ホスト側通常タスク、ホスト内部活動、未伝達メッセージ報告の各活動は、第5節および X-1〜X-10 で定めた個別の区切りルールに従います。すべての処理を一律に停止したり、一律に継続したりしてはいけません。
- ユーザーから受け取った入力がどのコンパニオン・クライアント・会話ラウンドに属するか、コンパニオンが生成した応答がいつユーザーへ提示可能になるか（現在の帰属と実際の提示環境が揃って初めて提示可能であり、「生成されたこと＝提示されたこと」ではない）、古い・キャンセルされた・削除された・移動した後の出力の扱い（元のラウンド・元の試行に紐付けて未伝達とするか安全に破棄し、新しい活動へ勝手に付け替えない）、クライアント不在時におけるホスト側タスクの結果の未伝達としての扱い（ホスト側に保持し、次クライアント接続時に現在の条件に基づいて要約報告する）は、X-2、X-6、X-9 の対応関係として確実に表現できなければなりません。
- 移動中や切断中に届いたデータは、元の帰属、元のラウンド、元の試行回数に対応付け、用途別に受け入れます。移動先の現在の活動へ勝手に付け替えてはならず、クライアント側の一時データでホスト側のマスターデータを上書きしてはいけません。未送信の操作を自動実行キューに溜めてはいけません。
- ホスト側でタスクを継続するかどうかの判断基準は「その処理にクライアント端末が必要かどうか」です。通常のバックグラウンド作業は別環境へ移送したり停止したりせずそのまま継続し、クライアント端末が必要なステップのみを安全に待機させます。タスクエージェントが操作対象のクライアントを勝手に選ぶことはできません。
- 観測適格性（Observer eligibility）は、ホスト側のマスター帰属に基づく存在人数に連動し、移動、停止、切断の発生時に必ず見直します。古いキャプチャ画像の流用、停止中個体の覚醒、外部送信同意の勝手な拡大解釈は禁止します。観測専用AIモデルの割り当てと、個体側の思考条件は厳格に分離します。コンパニオンごとに重複して画面キャプチャを行うことはせず、稼働中コンパニオンが少なくとも1体以上存在するクライアントのみを対象とし、画面キャプチャとイベント検知はクライアント単位で共有し、関連するコンパニオンだけにイベントをルーティングします（複数該当する場合はそれぞれへ届けます）。観測機能はコンパニオン個体ではなく、観測専用のAIモデル割り当てを使用し、コンパニオン固有の文脈はルーティングに必要な最小限の限定文脈のみとし、元のプライバシーや外部送信制限を維持し、観測用文脈を新しいマスターデータや全体共有データにしてはいけません。クライアント別およびシステム全体での観測一時停止（Pause）やOFF設定は最優先で尊重されます。
- PC自動操作（Computer Use）は、現在プレゼンスが存在しているクライアントに限定され、安全な区切りまでの遅延、切断時の結果不明ステータスの保持、別クライアントやホストでの勝手な自動再実行の禁止を厳格に維持します。「その場に存在していること」は直ちに「PC操作が許可されていること」を意味しません。
- 試行と作用、判断、実際の操作対象、処理フェーズ、確定度、保留状態の対応関係を正しく保持・区別できなければ、「成功した」または「未実行である」と安易に推測してはいけません。結果が不明な状態は確実に維持し、重複実行のリスクを提示した上でのユーザー判断なしに再実行してはいけません。
- 画面提示が成功したことをもって、タスクの成功やアクションの成功へ変換してはいけません。「操作要求の受付」「ホストでの受理」「実際の外部作用」「記録の保存」「タスクの達成」「ユーザーへの報告」はすべて別々の客観的事実として扱います。
- データを保持・利用するすべての機能は、消去処理中に届いたデータの破棄を含め、内部データの完全消去、再保存の防止、未完了状態の確実な保全に参加しなければなりません。バックアップからの復元範囲と、現在の環境における有効性・アクション再開の許可は別個に確認しなければならず、「復元されたデータが存在すること」を「直ちにアクションを実行してよい」とみなすようなインターフェースは禁止します。

本書が「採用できない選択肢」として明確に除外するのは以下のとおりです。新旧クライアントでの二重プレゼンス、クライアント画面表示・ヒント情報・一時コピー・復旧先記録のマスターデータ化、古いラウンド・古いキャプチャ・古い作用の新しい活動への勝手な付け替え、クライアントの一時データによるホスト側マスターデータの上書き、未送信操作の自動キュー化、ホスト作業の勝手な移送や一律停止、タスクエージェントによる操作クライアントの勝手な選択、再接続や復旧に伴うプレゼンス・権限・処理の自動成立、別クライアントへの無条件自動移動、停止中個体の勝手な復旧、ホスト側クライアント環境の勝手な自動起動、プレゼンス復旧を理由としたタスクやアクションの勝手な再開、結果不明な処理を「未実行」や「成功」と決めつけて自動再実行すること、要約や復元処理における確定度の勝手な格上げ、観測機能で情報が混ざり合った説明文の無条件配信、古いAIセッションによる安全制約の迂回、消去対象データの古いクライアントコピーからの復活、クライアントの利用可能性・接続・プレゼンス・開始可否の単一データ化、クライアント自身へのプレゼンス決定権の付与、入出力データのマスターデータ化、表示用コピーのマスターデータ化、観測用派生データの新しいマスターデータ化・共有化・責任者化。これらはいずれも上位のセキュリティ原則を破壊するため、一切採用できません。

## 10. 横断検証

要件定義書、上位アーキテクチャ設計、重要領域（critical-area）の設計、および他のサブシステム設計との整合性を確認する横断検証項目は以下のとおりです。これらは単なるシナリオのチェックリストではなく、正常系に加えて、本クラスタにとって重要な障害、データの古さ（stale）、クライアント移動、ホスト再起動、個人データ削除などの状況を検証するものです。

なお、[Client Presence Transition](../critical-areas/client-presence-transition.md) 第11節のウォークスルー項目は、本書のX-1〜X-10の3者協調モデルにおいても全く同一の結果を満たさなければなりません。以下には、接続・提示・観測に固有の交差シナリオを記述します。

| 検証項目 | シナリオと期待される結果 | 本書における根拠 |
|---|---|---|
| テキスト / 音声ラウンドと移動の競合 | 切り替え期間中に旧クライアントと新クライアントへ入力が到着した場合。いずれも現在の要求として自動実行せず、旧クライアントの入力は元のラウンドへ紐付け、新クライアントの入力は成立後の新しいラウンドとして正式に受け付けること。音声ストリームは同一ストリームとして勝手に再開しないこと。 | X-2、第6節。Context 3.1・7.2、CC-03の維持。 |
| 3Dアバター表示と切り替え・全画面・負荷 | 旧クライアントではアバターを確実に非表示・休止し、新クライアントではプレゼンス成立後に表示を開始し、二重表示を起こさないこと。位置等の一般設定はホスト側のマスターデータとし、実際の描画は現在の帰属に従うこと。描画エラーやPC高負荷が発生しても、テキスト会話、管理画面、復元機能を確実に維持すること。 | X-3、第2節・第5節。RT-02・RT-04、SO 4.17の維持。 |
| 出力配信と切断・未伝達メッセージ | 応答が生成されたが画面に表示できなかった場合、元のラウンドに対応付けて「未伝達メッセージ」とし、次にクライアントへ接続した際に現在の条件に基づく要約報告とすること。表示データを送信したことだけで報告完了とみなさないこと。 | X-9、X-2。Context 7.3、Action 9、CC-07の維持。 |
| RF-03交差：複数コンパニオンへのルーティング | コンパニオンAとBの限定文脈を参照してA向けにルーティングした場合。混ざり合ったプライベートな説明文をそのまま配送せず、Aが利用可能な安全なイベント本文を再構成すること。Aが使用する推論先にユーザー同意がなければ外部送信を成立させないこと。他個体へ結果を勝手にコピーしないこと。 | X-5。Context 6.1〜6.2、CC-02の維持。 |
| 管理・安全操作のプレゼンス独立性 | 担当コンパニオンが削除された後でも、残されたタスク記録、過去の判断、停止結果へ管理画面から確実にアクセスできること。タスクのキャンセル、承認拒否、システム復元が、3D表示、音声、AIモデル、外部ツールUI（MCP Apps）の正常動作に従属しないこと。 | X-10。CC-01・CC-04・CC-06・CC-07、SO 6.2の維持。 |

横断的関心事（CC-01〜CC-07）に関して維持すべき一般的な性質は、各重要領域ドキュメントの横断検証と同一です。本ドキュメントが特に強調するのは以下の点です。

- **CC-01（安全境界の維持）**: 移動要求、ユーザーからの呼び出し、自発的移動の由来と、正式なプレゼンス帰属の成立およびアクション実行許可を厳格に区別します。画面内に映った指示、観測機能がONであること、その場に存在していることだけから勝手に権限を新設してはいけません。
- **CC-02（コンテキストの混同防止）**: 過去の帰属先で使用していたコンテキスト、キャッシュ、AIセッションを、新しい帰属先で無条件に再利用してはいけません。
- **CC-03（現在有効性の分離）**: 過去の帰属関係が正しかったことと、それが現在の用途において有効であるかどうかを明確に分離します。
- **CC-04（自動復帰の拡大防止）**: 接続が回復したことだけを理由に、停止中の個体を勝手に復旧させたり、タスクを勝手に自動再開したりしてはいけません。
- **CC-05（ライフサイクルの分離）**: クライアント側の一時データの古いコピーから、ホスト側のデータを再保存・再形成することを防ぎます。会話ラウンドの終了をシステム全体の処理完了と混同しません。
- **CC-06（制御の独立性）**: システムの制御経路やデータ保全経路を、クライアント移動の完了待ちにしてはいけません。また、機械的な帰属確認処理をAI（LLM）の推論完了待ちにしてはいけません。
- **CC-07（提示と確定の分離）**: 応答データが生成された（生成済み）ことをもって、実際にユーザーへ伝達された（提示済み）とみなしてはいけません。

他のサブシステム設計との整合性確認においても、各データの担当責任者（semantic owner）は [state-ownership.md](../architecture/state-ownership.md) 第4節の定義どおりに維持され、本書のX-1〜X-10はその間での安全なデータ受け渡し契約として位置付けられます。未伝達メッセージのマスターデータを個体調整機能に残すこと、PC自動操作（Computer Use）を現在のアクティブプレゼンスに限定すること、観測機能に専用のAIモデル割り当てを用いること、スコープの意味解釈と強制的適用の分離、秘密情報の非露出、フォールバック時における安全ルールのバイパス禁止、結果不明（unknown）の安易な成功・失敗扱い禁止の各原則は、すべてのドキュメントで完全に統一されています。
