# サブシステム詳細設計 — キャラクター構成・パッケージ配布

本書は、Eneシステムにおける**キャラクター構成・パッケージ配布（以下、キャラクター機能）**の詳細設計仕様書です。
キャラクターの静的な外見・人格定義・音声設定・スキルのパッケージングと、ユーザーによる個体作成や更新適用の境界を明確にします。

※ 本書内の `CH-` 番号は本サブシステム内の内部責任の参照記号、`CD-` 番号は他サブシステムとの連携契約（セマンティック・コントラクト）の参照記号です。

## 1. 本サブシステムを独立して設計する理由

キャラクター機能は、**「配布パッケージのバージョン（改定）や部品の選択」という静的な構成変更**を扱います。一方で、認識・学習機能は**「日々の会話や出来事を通じた経験による認識の成長」**を扱います。
この2つを明確に区別して設計しないと、以下のような致命的な問題が発生します：

1. **プライバシーの漏洩**: キャラクターをエクスポートして他人に配布する際、ユーザーとの私的な会話履歴や個体の学習データ（Memory）が誤ってパッケージに混入してしまう。
2. **記憶の勝手な上書き**: キャラクターのパッケージを更新（バージョンアップ）しただけで、ユーザーと築いてきた大切な記憶、関係性（Relationship）、個体状態（Companion State）が無断でリセットされてしまう。
3. **主従関係の混乱**: キャラクター機能が個体の日々の状態まで管理してしまったり、逆に学習機能がキャラクターの静的な原本データを勝手に書き換えてしまう。
4. **「更新版の存在」と「適用」の混同**: 新しいバージョンがリリースされたからといって、ユーザーが望んでもいないのに稼働中のキャラクターへ自動適用されてしまう。
5. **セキュリティの突破（権限昇格）**: 外部からキャラクターパッケージをインポートして検証が成功しただけで、危険なツール実行権限やAPIキーの利用権限まで自動的に許可されてしまう。
6. **スキルの無断共有（グローバル化）**: 特定キャラクター用のスキルが勝手にシステム全体（全キャラクター共通）へ共有されてしまったり、キャラクター削除時にスキルだけが意図せず全体に残ってしまう。

キャラクターの静的な資材（人格テキスト、3Dアバターモデル、音声設定）と、個体の動的な経験（Memory、成長）のライフサイクルを完全に分離し、安全でクリーンな受渡しを実現するために本ドキュメントを策定します。

## 2. 内部責任の分離（CH-1 〜 CH-7）

本サブシステムが果たすべき論理的な責任を以下のように明確に分離します（これらは単一の巨大なクラスやプロセスにまとめるものではありません）。

| 内部責任 | 正規の判断対象（Authoritative） | 持ってはならない権限（越権の禁止） |
|---|---|---|
| **CH-1 キャラクター同一性と静的定義** | 配布可能な静的構成としての同一性の管理。静的な人格、アバター（Body）、音声（Voice）、モーション、推奨スキルの組み合わせの定義。ユーザーによる基本編集・部品差し替え・インポートの受付。外部パッケージ原本と内部取り込み設定の区別。 | 個体の活動状態や適用関係（個体管理の管轄）、経験に基づく記憶（認識・学習の管轄）、権限・同意・利用上限（権限管理の管轄）、APIキー等の認証情報（認証管理の管轄）。 |
| **CH-2 部品構成と推奨設定の管理** | 既存パーツの選択や差し替え、デフォルト設定や推奨設定の管理。推奨スキルと、取り込み後の内部スキルの有効バージョン・学習改善の区別。「推奨すること」は「実行を許可すること」でも「有効化すること」でもないという原則の維持。 | 内部スキルの有効バージョン変更や学習による改善（認識・学習の管轄）、実際の画面描画や音声合成処理、外部原本の直接書き換え、ツール実行許可の確定。 |
| **CH-3 基本編集機能** | 静的な人格プロンプトのテキスト編集、既存部品（モデルや声）の選択・差し替え。高度な3Dモデリングや音声学習、複雑なコード編集は外部ツールで行う前提とし、Ene内部に過剰な制作環境を抱え込まないこと。 | 個体の記憶や経験の直接書き換え、外部制作環境の所有、高度なスキルの業務ロジックの決定。 |
| **CH-4 改定（リビジョン）識別と差分提示** | パッケージ更新を「新しいリビジョン」として識別し、既存のキャラクターへ適用可能な部品や差分内容をユーザーへ提示。「新版が存在すること」と「適用済みであること」を区別し、未適用の部品を更新済みと錯覚させないこと。 | 個体への適用関係の確定（個体管理の管轄）、経験データのリセット、自動適用の強行。 |
| **CH-5 インポート・検証・由来管理** | 外部パッケージの受入、ファイル構造やメタデータの安全確認（バリデーション）、信頼できない入力としての安全な取り扱い、内部コピーと由来情報の管理。バリデーション成功をもって実行権限やセキュリティ許可と誤認しないこと。 | 権限・同意・コスト上限の確定、シークレット値の所有、外部ファイルの実行許可。 |
| **CH-6 エクスポート・配布準備** | 内部のキャラクターデータから「静的な構成のみ」を抽出し、外部へエクスポートする前の内容確認やライセンス・著作権の注意喚起を提示。個体固有の経験、会話履歴、パスワード、権限が外部へ漏洩するのを絶対に防ぐこと。 | 個体固有の記憶の編集・持ち出し、外部マーケットプレイスの運営。 |
| **CH-7 個体への適用資材の供給** | キャラクター新規作成時の初期設定の供給、および既存個体へ新しいリビジョンを適用する際の差分データの供給。ユーザーによる部品ごとの明示的な選択を前提としてデータを提供し、適用結果そのものは所有しないこと。 | 個体への適用可否の決定（個体管理の管轄）、記憶や学習の改ざん、バックグラウンドでの無断上書き。 |

## 3. 管理する論理状態（State）

### 3.1 本サブシステムがマスターとなる状態

- **静的人格・Body・Voice・モーション構成・推奨スキルおよびそのリビジョン（SO 4.1）**:
  Ene内部に取り込まれた静的構成のマスターデータです。ユーザーによる編集や部品差し替え、インポートによって更新されます。外部ファイルが書き換わったからといって、内部データが勝手に更新されることはありません。
- **推奨スキルの構成指定（SO 4.7）**:
  「このキャラクターにはこのスキルが推奨されている」という静的なメタデータです。これによって内部スキルの有効バージョンが勝手に切り替わったり、ツールの実行が許可されたりすることはありません。スキルの改善や以前のバージョンへの切り戻しは認識・学習機能の管轄です。
- **インポート済みパッケージの内部コピーと由来情報**:
  外部から受け入れたパッケージのコピーと、その入手元、受入日時、対象キャラクター、リビジョンの対応記録です。
- **リビジョン差分の提示データ**:
  新バージョンにおいて何が変更されたのかを示す差分情報です。「新バージョンが存在する」ことのマスターであり、「稼働中の個体が現在どのバージョンを使っているか」は個体管理機能がマスターを持ちます。

### 3.2 本サブシステムが所有「しない」状態（他機能がマスター）

以下のデータは本サブシステムでは所有せず、それぞれの担当機能がマスターを保持します：
- キャラクター個体の同一性、稼働状態、現在どの部品を適用しているか（個体管理機能の管轄：SO 4.2）
- 経験に基づく要約（Experience Summary）、記憶（Memory）、スキル（Skill）、関係性（Relationship）、個体状態（Companion State）（認識・学習機能の管轄：SO 4.5〜4.9）
- 権限ルール、ユーザー同意、コスト上限（権限・制約管理の管轄）
- APIキーなどのシークレット情報（認証管理機能の管轄）

個体の振る舞いや会話においては、**キャラクターの初期設定よりも、日々の実際の経験から形成された記憶が優先**されます。キャラクターパッケージの更新によって、個体の記憶が勝手に上書きされることは決してありません。

### 3.3 データの分類と取り扱い（正規・派生・一時・外部参照）

- **正規データ（Canonical）**:
  Ene内部に取り込まれた静的構成・リビジョン、インポート由来情報、個体管理が保持する適用関係、学習機能が保持する記憶・スキルなど。外部の元ファイルや、古いバックアップ、推論モデルのプロンプト内に書かれた文章などは正規データとはみなしません。
- **派生データ（Derived）**:
  ユーザーへ見せるための差分プレビュー、エクスポート前の確認表示、画面描画用のメッシュデータ、検索用インデックス、プロンプト用キャッシュなど。これらは元データから再生成可能であり、個人データの完全削除時には確実に破棄されます。古い派生データから正規データを勝手に復活させてはなりません。
- **一時データ（Temporary）**:
  編集中の未確定データ、入力途中のテキスト、音声バッファ、推論中の一時メモリなど。これらが消えてもシステムのマスターデータは失われませんが、完了した操作の記録まで消してよいわけではありません。
- **外部参照（External Reference）**:
  ローカルのVRMファイルや音声モデルファイル、外部スキルのパスなど。内部に取り込んだものだけをEneが管理し、外部ファイルそのものをEneが所有しているかのように誤認してはなりません。

## 4. 他サブシステムとの連携契約（Semantic Contract）

### CD-1 キャラクター個体の新規作成時における資材提供

- **処理の開始**: ユーザーが新しいキャラクター個体を作成する操作を行い、個体管理機能がキャラクター機能へ初期構成データを要求します。
- **責任の境界**: 静的な設定やリビジョンのマスターはキャラクター機能が持ち、新しい個体として独立して存続させることや適用関係の決定は個体管理機能が行います。資材を受け取ったからといって、過去の他個体の記憶や経験が共有・継承されることはありません。
- **提供する内容**: 対象キャラクターのリビジョン、各種パーツ（人格、モデル、声など）の静的データ、推奨設定、推奨スキルの原本情報。
- **禁止事項**: 個体作成をもって、APIキーの利用、権限の昇格、ユーザー同意の成立、外部ツールの無制限実行を自動許可してはなりません。また、推奨スキルが含まれているからといって、スキルが自動的に有効化されたり実行許可されたりすることもありません。

### CD-2 稼働中個体への新しいリビジョンの適用

**「新しいバージョンが存在すること」と「その個体に適用されていること」は全く別の概念です。**
キャラクター機能はバージョンのマスターを持ち、個体管理機能は各個体の適用状態のマスターを持ちます。適用されていない部品を「更新済み」と偽ってはならず、パッケージの更新を理由に個体の記憶をリセットしてはなりません。

- **処理の開始**: キャラクター機能が新バージョンと変更差分を提示し、個体管理機能が「ユーザーが明示的に選択した部品」のみを個体の適用関係へ反映します。
- **責任の境界**: 適用するかどうかの最終決定はユーザーと個体管理機能が行います。キャラクター機能が勝手に適用を強制することはできません。
- **更新部品の性質区分**:

| 更新の性質 | 内容と影響 | 適用時の取り扱いルール |
|---|---|---|
| **静的置換** | 将来のデフォルト動作や外見に影響するが、これまでの記憶や経験には影響しない変更（例: 3D衣装のテクスチャ変更など）。 | ユーザーの明示的な選択によって安全に適用できます。 |
| **要判断** | 会話の口調や行動の傾向など、これまでの個体の性格や関係性に影響を与えうる変更。 | 記憶への影響をユーザーへ分かりやすく提示し、納得した上での明示的な選択を得ます。システムが勝手に代行判断してはなりません。 |
| **競合** | 個体がこれまでの経験を通じて独自に学習・成長した内容と真っ向から衝突する変更。 | 黙って上書きしたり巻き戻したりしてはなりません。現状維持か、上書きか、別個体として分岐させるかを必ずユーザー自身に選択させます。 |
| **適用禁止** | キャラクターのバージョン更新として配布してはならない危険なデータ（APIキー、管理者権限、ツールの無制限実行権限、全体共通ルールなど）。 | パッケージに含めること自体を禁止します。万一含まれていても無視し、適用対象外とします。ユーザーが同意したとしても権限昇格は成立しません。 |

### CD-3 スキル（Skill）の受渡し境界

**キャラクター機能は、学習やスキルのセマンティック・マスター（意味の所有者）にはなりません。**
スキルの推奨と、実際の内部スキルの有効化・学習改善は別の機能が管理します。

- **Companionスコープが既定**:
  キャラクターパッケージに含まれる推奨スキルは、**その個体専用のスキル（Companionスコープ）**として取り込まれるのが原則です。同じキャラクターから複数の個体を作成した場合でも、それぞれ独立した別々のスキルとして扱われ、勝手に共有されることはありません。
- **自動グローバル化の絶対禁止**:
  キャラクターの推奨スキルが、システム全体（Globalスコープ）へ勝手に格上げされることはありません。また、その個体が削除された場合、個体専用のスキルも一緒に消去され、システム全体へ自動残留することもありません。
- **単独インポート時の選択**:
  スキルを単体でインポートする場合は、ユーザー自身が「この個体専用にするか」「システム全体で共有するか」を明示的に選択します。
- **原本の保護**:
  インポートされたスキルの原本ファイルは安全に保護され、AIが学習によってスキルを改善・修正する場合は「別の新しいバージョン」として保存されます。原本が勝手に破壊されることはありません。

### CD-4 インポート・検証とセキュリティ境界

- **信頼できない入力（Untrusted Input）としての扱い**:
  外部から取り込むキャラクターパッケージは、悪意のあるスクリプトやプロンプトインジェクションが含まれている可能性がある「信頼できない入力」として厳格に扱います。
- **パッケージに含めてよいもの**: 静的な人格テキスト、VRM 1.0形式の3Dアバター、音声合成パラメータ、モーションデータ、推奨スキル定義。
- **パッケージに含めてはならないもの（排除対象）**: 特定ユーザーとの過去の会話履歴、記憶（Memory）、関係性、個体状態、パスワードやAPIキー、管理者権限、ツールの無制限実行許可。これらが含まれていた場合は読み込みを拒絶します。
- **外部ファイル参照の安全性**: VRMアバターや音声モデルなどの外部ファイルを指定している場合、パスの参照情報としてのみ保持し、外部の実ファイルをEneが完全に所有しているかのように扱ってはなりません。
- **「検証成功」＝「実行許可」ではない**: パッケージのファイル構造が正常であること（バリデーション成功）は、「そのスキルやスクリプトを安全に実行してよい承認が得られた」こととは全く別です。実際のツール実行時には、実行エンジンと権限管理機能による直前の安全審査が必ず行われます。

### CD-5 エクスポートと配布時のプライバシー保護

- **静的な情報のみを抽出**:
  キャラクターを外部ファイルとしてエクスポートする際、キャラクター機能は「静的な構成データ」のみを選択して出力します。
- **個人データの混入防止**:
  ユーザーと築いた日々の会話履歴、学習された記憶（Memory）、プライベートな関係性データ、APIキー、付与された権限などは、**1ビットたりともエクスポートファイルへ混入させてはなりません**。
- **外部コピーの独立性**:
  一度エクスポートされたファイルは、Eneの管理外にある外部データです。Ene内部でキャラクターを削除したからといって、すでに配布された外部ファイルまで消去されたかのように誤認させてはなりません。

### CD-6 表示資材の受け渡しと編集確認

- 画面表示機能に対して、アバター（Body）の3Dモデルや音声（Voice）パラメータ、モーションデータを安全に提供します。
- ユーザーがパーツの変更やエクスポートを行う際は、事前に変更内容やライセンス上の注意点を分かりやすく画面に提示し、納得を得た上で処理を実行します。

### CD-7 ライフサイクル・削除・バックアップへの参加

- **キャラクターの削除**:
  共有キャラクター定義を削除した場合でも、**すでに作成されて活動している既存個体の記憶や経験データは絶対に削除しません**。削除後はそのキャラクターから新しい個体を作れなくなるだけであり、既存の個体は直前の静的スナップショットと大切な思い出を保持したまま、同じ個体として生き続けます。
- **個体の削除**:
  特定の個体を削除する場合、その個体固有の記憶（Memory）や個体専用スキルは消去されますが、元となったキャラクターの静的パッケージ定義まで巻き添えで削除されることはありません。
- **バックアップと復元**:
  内部のキャラクター設定やリビジョン、インポート情報はフルバックアップの対象に含まれます。バックアップから復元した直後は、古い設定によるツールの自動実行は一旦保留され、ユーザーの確認を経てから有効化されます。
- **個人データの完全削除（Targeted Deletion）**:
  キャラクターの静的リビジョンに万が一特定の個人情報が含まれていた場合は、完全削除処理に確実に参加してデータを消去します。
- **設定初期化（Reset）との区別**:
  一般設定の初期化（Reset）によって、キャラクターや個体の記憶が勝手に消去されることはありません。全データ初期化の場合のみ、強いユーザー確認を経て内部データが完全に消去されます。


## 5. Lifecycleとの関係

ライフサイクル（生成・変更・停止・削除などのライフイベント）に伴う変更の多くは、データの担当（オーナー）が変わるわけではなく、同じ担当が管理するデータについて「使い続けられるか」「どこまで参照できるか」といった状態が変わるだけです。目的が異なるさまざまな操作を、安易に1つの初期化処理や単一の状態管理にひとまとめにして混同してはいけません。

| 事象 | 本サブシステムが変更する内容 | 維持・分離すべき境界 |
|---|---|---|
| Character作成 | 静的なキャラクター定義や初期リビジョンを確定します。元の外部ファイルや制作物の所有権はシステムに移りません。 | 個体の生成や、会話を通じた経験データの作成とは明確に分離します。同じキャラクターから作られた別個体同士が経験データを共有することはありません。 |
| Character編集 | 静的な人格設定テキストの修正や、既存パーツ（モデルや声など）の選択・差し替えを確定します。 | 会話で蓄積された経験データを上書きしたり、外部の制作環境を勝手に複製したりしません。適用されていないパーツを勝手に「更新済み」として扱いません。 |
| Character import | 外部のパッケージやファイルをシステム内のキャラクターとして受け入れ、その出所（由来情報・来歴）を紐付けます。 | 元の外部ファイルの所有権は移りません。また、これだけで権限（Permission）、認証情報（Credential）、ユーザー同意、アクション実行権限（execution authority）が勝手に成立することはありません。 |
| Character更新（新revision） | 新しいリビジョンが存在すること、適用可能なパーツ、変更内容を提示します。「新しいバージョンが存在すること」と「それを個体に実際に適用すること」は別物です。 | 既存の経験データや会話履歴、付与された権限を初期化しません。自動適用や無断の上書きは行いません。 |
| Character export | 静的な設定の範囲（定義やモデルなど）のコピーを外部ファイルとして出力し、内容や著作権・利用規約などの注意事項を明示します。 | 個体固有の経験データ、会話履歴、秘密情報、付与された権限を外部ファイルに混入させません。出力したコピーをシステム稼働中のマスターデータとして扱ってはいけません。 |
| Companion作成 | 個体の初期設定（どのキャラクター設定を使うか）を提供します。新しく生成されたコンパニオンは独立した別個体として識別されます。 | 別個体との経験の共有、権限の自動成立、勝手な実行許可の付与とは明確に切り離します。 |
| 既存Companionへのrevision適用 | オーナー（ユーザー）が選択したパーツについて、適用関係を更新します（CD-2で定めた4つの性質区分に従います）。 | 会話や経験から生まれた状態（メモリ・関係性など）、履歴、付与された権限を初期化しません。適用が禁止されている内容を勝手に実行権限として扱ってはいけません。 |
| Character削除 | 静的な定義やリビジョンを削除し、そのキャラクターから新しい個体を作成できないようにします。 | すでに作成されている既存コンパニオンの個体や、これまでの経験・記録は削除しません。削除によって必要な元の素材（VRMモデルなど）が見つからなくなった場合は「未解決の参照切れ（dangling）」として扱い、勝手に別の素材で代替したり過去のアクションを再実行（replay）したりしません。 |
| Companion停止 / 再開 | キャラクター設定を適用する相手として、その個体が存在しているという参照関係を維持します。 | コンパニオンの同一性とデータを保持します。停止中に発生するはずだった定期タスクの回は「スキップ（missed）」のままとし、再開したからといって過去の古いタスクや結果が不明なアクションを自動で再実行（replay）してはいけません。 |
| Companion削除 | キャラクター設定の適用関係を終了することを確認します。 | 会話履歴、活動ログ、タスク記録、グローバル共有メモリ、共有サマリー、外部ファイルなどを道連れにして削除しません。個体のデータを勝手にグローバルデータへ昇格させたり、別の個体へ勝手に引き継いだりしません。また、サマリーやリビジョンを単なる履歴ログに分類し直してこっそり残すことも禁止します。 |
| Task Agent終了 / 失敗・Task完了・失敗・Cancel | 結果が不明な外部作用、未伝達の通知、完了していないシステム全体への操作などを安全に保全する範囲で、既存のルールに従います。 | タスク記録、コンパニオン、スケジュールを勝手に削除しません。タスクが終了したからといって記録や紐付けを削除したり、外部の成果物を勝手に自分のものにしたり消去したりしません。 |
| Task削除・Schedule停止 / 削除 | 通常削除に伴う保持データの整理・調整について既存のルールに従います。 | 過去の実行結果を改ざんしたり、スキップされた実行回を「実行済み」と偽ったりしません。また、すでに形成された学習データやサマリーに連鎖削除（カスケード削除）を波及させません。 |
| Learningの通常忘却・訂正・統合・失効・置換・scope変更 | キャラクター適用後も継続して学習や再解釈を行えるよう、既存のルールを維持します。 | 保存済みの内容、過去のリビジョン、判断根拠を正しく保持し、単なる「誤りの訂正」と「時間の経過による変化」を区別します。スコープの意味（個体限定か共有か）は認識・学習システム側に明確に残します。 |
| 通常History / log削除・retention cleanup | 保持期間の満了に伴い、元ログの記録範囲を整理・削減する範囲で既存のルールに従います。 | すでに形成された状態やサマリーは残しつつ、元データが参照不能になったことを明示します。通常のログ整理を、法的な個人データ完全削除（Targeted Deletion）と混同してはいけません。 |
| Targeted deletion | 該当データを復元できる内部データや処理中の作業を横断して完全に消去・復元不能化する処理に参加します。 | データの担当責任（オーナーシップ）自体は移転しません。また、削除完了後にユーザーが新しくデータを提供することや、バックアップ等の外部コピーの消去保証とは明確に区別します。 |
| 移動・切断 / activeなし | 接続中クライアントの一時データを整理し、どのクライアントと通信しているかを把握する範囲で既存のルールに従います。 | 個体そのものや、ホスト側で行っている通常の作業、内部状態の担当責任は移転しません。未確定のアクションを移動先のクライアントへ勝手に再送信・再実行（replay）しません。 |
| Host再起動 | 未完了のタスク、保留中の処理、再保存の防止措置など、ホスト側で保護すべき状態を維持します。 | 過去に結果が不明になった作用や、未伝達の通知、未完了のデータ消去を「なかったこと」にしてはいけません。途中で止まったタスクはユーザーの明示的な再開指示を待ち、停止中にスキップされた定期実行はmissedのままとし、実行中だったプレゼンスは元のクライアントへの復旧ルールに従います。 |
| Provider / model変更・障害・cache失効 | AI推論の利用可否、モデルの能力、承認済み経路のルールを前提としつつ、システム的な機械的検証・停止・拒否・管理処理を妨げないようにします。 | 個体のデータ、会話履歴、学習データなどを勝手に初期化しません。同じ情報選択方針と安全境界を厳格に維持します。 |
| Backup / restore | データのコピーを作成し、明示的なリストアが成功した場合は、現在の認証情報ストア（Credential store）を除き、対象の内部状態をバックアップ時点の状態へ完全に置き換えます。 | バックアップコピーは稼働中のマスターデータではありません。リストア完了後もアクションの自動実行は保留され、外部の世界（送信済みメール等）が勝手に巻き戻ることはありません。また、認証情報はリストアで巻き戻さず、現在のストアを維持して整合性を確認します。 |
| 設定Reset / 全データReset | 設定リセットは一般設定を初期値に戻す操作であり、全データリセットは厳格な確認を経た上で内部データや認証情報を完全に削除する操作です。 | 設定リセットで保護すべきデータと、全データリセットで対象外となる外部リソースを混同してはいけません。過去の処理や一時的なコピーから、古い内部状態を勝手に復活させてはいけません。 |

グローバル（全個体共通）として形成・変更された学習データは、その後に元となったコンパニオンが削除されたとしても、グローバルデータとして残ります。ただし、個体削除時には「残された判断根拠」と「失われた元の参照先」の関係を明確に説明できなければなりません。また、関係性（Relationship）やコンパニオンの個別状態（Companion State）は、個体ごとの固有データであるため、学習スコープを変更して勝手に共有対象にしてはいけません。たとえ複数個体で共有された経験（同じイベントの体験など）があったとしても、各個体の状態はそれぞれ独立して更新されます。

時間はデータや状態の意味にも重大な影響を与えます。スケジュールは「設定時に選択されたタイムゾーンと時刻条件」、コンパニオンの状態は「一時的な状態であることと経過時間」、保持ポリシーやデバッグログは「対象となる期間」を、それぞれの担当機能が正しく扱います。設定済みのスケジュールタイムゾーンを勝手に書き換えてはいけません。また、バックアップに含まれるコンパニオンの状態を復元（リストア）する際も、バックアップ後に経過した時間を無視して、本来は一時的だった感情や状態を「バックアップ時の値のまま無期限に固定」してはいけません。

## 6. failure / cancellation / restart時の責任

処理のキャンセルや通信切断が発生したからといって、「外部への作用も取り消された（あるいは最初から実行されなかった）」と勝手に推測してはいけません。結果が不明なアクションを「未実行」とみなして安易に再実行することは禁止です。また、クライアントが切り替わったり状態を参照したりしたことを口実に、過去のアクションを自動で再実行（replay）してはいけません。

- **Characterに関する責任**: 人格の編集・インポート・エクスポート・設定適用の処理が中断されたとしても、それを理由にコンパニオン個体・タスク・学習データの意味を勝手に変更してはいけません。適用が完了する前の古いリビジョンや古い適用関係を破壊してはならず、途中で失敗した部分的な適用を新しいマスターデータとして扱ってはいけません。インポートやバリデーション（妥当性検証）が失敗したからといって、直前まで正常だった内部のキャラクター定義を壊してはいけません。エクスポートやバックアップ出力が失敗したのに「成功した」と偽って表示してはいけません。設定適用の失敗を、経験データの初期化や権限の自動成立とみなしてはいけません。
- **共通の責任（個体調整・タスク・認識・学習との連携）**: 停止や削除を管理する安全制御ルートは、LLM推論の応答成否から完全に独立していなければなりません（LLMがダウンしていても停止・削除は確実に実行できる必要があります）。設定適用の遅延した結果によって、ユーザーが行った訂正を無条件に上書きしてはいけません。削除前の古い情報を参照している実行中の学習処理によって、すでに削除されたはずの個人情報が再び保存されてはいけません。古い判断根拠だけに基づいて自動で再学習・再形成を行ってはいけません。
- **共通の責任（権限・実行クラスタとの連携）**: 権限の失効、停止指示、実行制限（cap）、保留が発生した場合は、新しい処理の開始を直ちに確実に禁止しなければなりません。古い判定結果や過去に解決された実行経路だけを頼りにして、新しい処理を開始させてはいけません。バリデーション（形式チェック）の成功を「生きた実行許可」とみなしてはいけません。また、パスワードやAPIキーなどの秘密情報を通常のログやデータフローに流してはいけません。
- **共通の責任（接続・提示・観測との連携）**: クライアントの切り替え中は新しい処理の開始を禁止し、同じ個体が二重に活動（二重プレゼンス）することを防ぎ、一時的な表示用データをマスターデータと誤認させない仕組みを維持します。クライアントの画面表示、過去のログ、ヒント情報、一時コピー、復旧先の記録、外部AIプロバイダに残った会話履歴などを、キャラクター適用関係の正当な根拠として扱ってはいけません。
- **共通の責任（保全・消去との連携）**: 未完了の処理や結果を確認できない状態はホスト側で確実に保護し、クライアントの切断・再起動・画面終了を「処理が完了した」と勝手に解釈してはいけません。一部の処理の完了報告を待つために全体がフリーズしてデッドロック（循環待ち）を起こさないようにします。再保存防止などの保護措置は必要な期間確実に維持し、「保護の解除」と「局所的な処理完了」を同じ意味として扱ってはいけません。

本領域において特に重要な障害（failure）や競合（race condition）の扱いは以下のとおりです。これらは固定されたシナリオ一覧ではなく、今後の並行処理や状態表現の設計において満たすべき要件を示す例です。

- **編集と新リビジョンの競合（edit vs revision race）**: ユーザーが設定を編集中に、外部から新しいリビジョンがインポートされた場合、編集中の一時的な内容を勝手に「確定済みリビジョン」として扱ってはいけません。確定したリビジョンと未確定の編集内容を厳格に区別し、個体への適用には確定済みの内容のみを使用します。
- **インポートと適用の競合（import vs apply race）**: インポートが完全に確定する前に、既存コンパニオンへの適用を開始してはいけません。インポートの失敗やバリデーションの失敗を「適用完了」と誤認してはいけません。
- **適用と学習の競合（apply vs learning race）**: 設定を適用した直後に、バックグラウンドで動いていた認識・学習の結果が戻ってきたとしても、キャラクターの静的設定と個体の経験データを混同してはいけません。設定の適用によって経験データを勝手に上書きしてはならず、学習結果の反映によって設定適用を取り消してはいけません。
- **適用と個人データ削除の競合（apply vs targeted deletion race）**: 設定適用と個人データ削除（Targeted Deletion）が同時に行われる場合、削除対象の個人データを適用内容・エクスポート内容・完了報告に含めてはいけません。各受け入れ側で削除条件と照合し、古い処理結果から対象データが復活しないようにします。
- **Character削除と適用済みCompanionの競合（Character deletion vs applied Companion）**: キャラクターの削除が確定した後は、そのキャラクター設定の新たな適用処理を開始してはいけません。一方で、既存のコンパニオンがすでに適用している設定スナップショットやこれまでの経験データを勝手に削除してはいけません。必要な元素材（VRMモデルなど）が失われた場合は「未解決の参照切れ（dangling）」として扱い、勝手に他の素材に差し替えたり再実行したりしません。
- **インポート / 適用 / エクスポート中のホスト再起動（Host restart during import / apply / export）**: 処理の途中でホストが再起動した場合、再起動前に正常だった内部キャラクター定義や適用関係を破壊してはならず、途中で中断した不完全な適用やインポートを新しいマスターデータとして扱ってはいけません。途中で止まったタスクはユーザーの明示的な再開指示を待ち、停止中にスキップされた定期実行はmissedのままとし、実行中だったプレゼンスは元のクライアントへの復旧ルールに従います。
- **リストアと適用関係の競合（restore vs applied relation）**: バックアップからリストアする際、リストア前の古い稼働データや遅延していた処理結果を、復元されたマスターデータに混入させてはいけません。また、復元されたキャラクター適用関係を、現在の到達性や正当な権限を確認することなく勝手に有効化してはいけません。「データの復元が完了したこと」と「アクションの実行を再開すること」は別個に確認しなければなりません。

システムの状態が安全に「再構築可能」であるということは、過去のプロンプト全文やAIの思考ログ（内部推論）を永久に保存し続けなければならないという意味ではありません。継続に必要な「キャラクター適用関係」「未伝達の通知」「結果不明な作用」「未完了の全体操作」などを本来の担当機能が確実に保護し、一時バッファが消えたからといって「処理が成功・完了した」と誤認しないことが求められます。

## 7. Step 11 contractへの参加

各契約の一般的な条件は、第0節に挙げた重要領域（critical-area）の各ドキュメントに記載されており、ここでは重複して記載しません。本節では、キャラクターおよび配布機能が提供・参加する固有の内容のみを記述します。

### 7.1 Context Assemblyへの参加

- キャラクターの静的な設定内容、リビジョン、変更差分の提示、出所情報（provenance）の提供範囲と意味を正しく管理します。コンテキスト構築に必要な情報（対象キャラクター、リビジョン、パーツ、適用先コンパニオン、ユーザーの選択、継続関係、想定される利用先）を正確に供給します。引用文を含むユーザー入力全体を無条件に「ユーザーからの命令」とみなしてはならず、パッケージ内の説明文を「システム管理の指示」と誤認してはいけません。また、パッケージのバリデーション（形式検証）が成功したからといって、後段のアクション実行権限を勝手に新設してはいけません。

### 7.2 Action Executionへの参加

- キャラクターのインポート・エクスポートや設定適用に伴って外部ファイルへのアクセスが必要な場合、付与された権限と制約に従ってアクション実行機能（Action Execution）へ処理を依頼します。システム内部での通常のデータ保存処理を、すべて外部アクションとして再分類してはいけません。何を出力するかという意味や選択はキャラクター機能が担当し、実際の外部ファイル操作はアクション実行機能が担います。パッケージ内の記述から勝手にアクション実行権限を作り出してはいけません。

### 7.3 Targeted Deletionへの参加

- 静的なリビジョン、インポートされたパッケージのコピーや来歴情報、変更差分の提示データ、エクスポート確認画面の表示用データなどに含まれる該当個人データを、完全に消去・復元不能化する処理に参加させます。通常、キャラクター静的データには会話経験由来の個人データは含まれませんが、もし対象情報を復元できるデータを含んでいる場合は、同様に厳格な消去原則に従います。削除対象リストからの単なる記載漏れを理由に削除を免除してはいけません。「元パッケージの保護」や「リビジョンの履歴提示」を理由に、消去義務を免れることはできません。

### 7.4 Client Presence Transitionへの参加

- クライアントへの設定適用や表示アセット（モデル・画像など）の配信において、対象キャラクター、リビジョン、パーツ、適用先コンパニオン、会話ラウンド、試行回数の正しい対応関係を提供します。ホスト側が管理するマスターデータとしての帰属関係と、クライアント側の一時的な表示・入力・結果が主張する帰属関係との整合性を維持します。クライアント側の一時コピーでホスト側のデータを勝手に上書きしてはならず、未送信の操作を勝手にキューに詰めて後から自動送信してはいけません。

### 7.5 Backup / Restoreへの参加

- 静的な設定構成、リビジョン、インポート済みパッケージのコピーや来歴情報、変更差分の提示データを、復旧可能な形式でバックアップに提供します。外部のダウンロード元パッケージをネットワーク経由で再取得して集めるようなことはしません。キャラクター設定の適用関係は個体調整機能が提供し、本機能はキャラクター設定そのもののデータを提供します。一時的なキャッシュデータや派生データは、独立した復元対象には含めません。

## 8. boundaryを越える際に保持すべき意味

後続のインターフェースや状態表現の実装設計においては、具体的なAPIや仕組みを固定しない場合でも、少なくとも以下の対応関係を正しく表現・解決・照合できなければなりません。確認が取れないものを「現在の有効な状態」「許可済み」「完了」と推測するアプローチは決して採用してはいけません。

- 対象キャラクター・リビジョン・パーツ、適用先のコンパニオン、ユーザーの選択内容、適用時点、想定される利用目的（新規生成・既存適用・画面表示・エクスポートの区別）、停止や再起動・リストアを跨ぐ前後の継続関係（Context Assembly第3節の要件）。必要な対応関係を失った処理結果は、現在の別の処理に勝手に付け替えてはならず、その用途では「受け入れ不能」として利用元が破棄・再処理しなければなりません。
- データの担当機能（オーナー）、対象、出所（source）の関係、データが持つ意味・位置付け・由来、リビジョン、取得日時、有効期限、所属・スコープ・共有関係、利用目的・保存・共有・外部送信の制限、参照関係が正しく解決されているか否か（Context Assembly第3節の判断材料）。「キャラクターの静的設定」「適用関係」「個体の経験データ」「外部の元ファイル」を絶対に混同してはいけません。
- 実行主体と委任の連鎖、タスクやワークスペースの有効範囲、実行目的、実際の操作対象と操作内容、使用する主なデータと用途、発生する費用やリスク、依拠したユーザー意図や安全ルール（Action Execution第3節の判断対象）。判断時にプロンプト等で指定された対象の説明と、実行時にアクセスする実際の対象が「文字列として一致している」というだけでは、正当な対応関係とはみなせません。
- 「実行の試行」と「実際の外部作用」の区別、判断・目的との対応、実際の操作対象との対応、処理フェーズの区別、確定度と判断根拠、停止指示や保留状態との関係（Action Execution第8節の二重実行防止の要件）。
- 個人データ削除要求、対象データの指定、削除を実行すべき有効期間との対応、各利用箇所で照合可能な削除条件（Targeted Deletion第3節・第5節）。単一の「削除済みフラグ」や共通の有効値だけに安易にひとまとめにしてはいけません。
- ホスト側が持つマスターデータとしての帰属関係と、クライアント側の一時的な表示・入力・結果が主張する帰属関係の整合性、現在有効・過去のもの・帰属なし・停止中・復旧待ちという各状態の厳格な区別、対象コンパニオン・クライアント・会話ラウンド・観測候補・試行回数の対応関係、消去・失効・停止・保留との関係（Presence Transition第3節）。
- リストア時の対応関係、データの由来、バックアップ取得時点、リストア完了の境界、現在の環境条件との整合性チェック（Backup-Restore第3節・第5節・第7節・第9節）。
- キャラクター・リビジョン・パーツと適用関係の対応、出所情報（provenance）と外部原本の区別、推奨スキルと内部スキルの由来およびリビジョン対応、スコープ選択の対応。

自然言語テキスト（プロンプト等）と、セキュリティ強制に使用するメタデータを明確に分離し、強制側の制御データをAIモデルの自由記述によって勝手に作成・上書きされないようにします。テキスト中に「ユーザーからの指示です」「承認済みです」「グローバル共有設定です」「安全です」という文字列が含まれているからといって、それだけで制御側の権限状態が変更されるような設計は禁止します。AIモデルが過去のユーザー入力やパッケージ内の記述を参照できたとしても、その参照が存在すること自体は「ユーザーの正式な承認・同意・権限付与」の証拠にはなりません。

パスワードやAPIキーなどの認証情報（Credential）の実値を、通常の会話コンテンツやプロンプトに含めてはいけません。登録済みの認証情報の値を、ユーザーからの指示やパッケージ内の記述があったとしても、要約（Summary）や長期記憶（Memory）に勝手に保存してはいけません。用途、参照元、失効状態、再認証の説明などは、秘密情報を含まない非機密データとして行います。システムに登録されていない秘密情報についても、検知した際に不要な保存や外部送信を抑制する仕組みを維持しますが、「100%完全に検出できる」という非現実的な保証を追加してはいけません。

対象データの指定やパッケージ内容の伝達・保持のために、プライベートな会話本文や秘密情報の複製を無駄に増やしてはいけません。「データの出所（由来）を記録するため」という口実で、削除されたはずの本文や認証情報を別の場所に隠し持ってはいけません。アクセス制限情報や内部識別用のIDであっても、それらを辿ることで対象の個人データを復元できるのであれば、保護および消去の対象となります。完了ログ、監査ログ、説明文の中に、消去対象となった本文を書き戻してはいけません。

## 9. 本書が固定する契約と残す Design Freedom

下位の詳細設計では、以下の内容を本書が固定した不変の契約として扱います。

- キャラクターの静的設定、適用関係、個体の経験データの担当責任の分離（第2節〜第3節）と、各担当が持つ正式な判断権限・非所有の原則は、そのままインターフェースや状態構造の分割根拠として利用できます。1つの「キャラクター」オブジェクトに経験データを統合したり、1つの「コンパニオン」オブジェクトに静的設定と経験を統合したり、1つの「学習ストア」に静的設定と経験を混同して保存したりする設計は採用できません。
- 受け渡し契約（CD-1〜CD-7）は、関数の呼び出し方向、同期待ちの順序、データの転送経路を固定せずとも、「要求の開始」「判断の確定」「受け渡す内容」「前提条件の維持」「結果の受け入れ」の対応関係としてインターフェースや状態表現で確実に表現できなければなりません。
- 「新しいリビジョンが存在すること」と「それが個体に適用されていること」は全く別の意味であり、適用にはユーザー（オーナー）によるパーツごとの明示的な選択が必要です。CD-2で定めた4つの性質（静的置換・要判断・競合・適用禁止）は、具体的な差分比較（diff）やマージ処理の実装方式に依存することなく、適用の可否を判断する前提条件として表現できなければなりません。
- パッケージに含まれる推奨スキルの取り込みは、個体限定（Companion scope）を既定とし、各個体に独立して属します。単独インポート時のスコープ選択、勝手な全体共有（グローバル化）の禁止、個体削除時に所属スキルが道連れとなるルールは、インターフェースやデータ構造で表現できなければなりません。キャラクター機能が学習データの担当責任者（semantic owner）になるようなインターフェースは禁止します。
- パッケージのインポートやバリデーション（形式チェック）が成功したからといって、権限、認証情報、ユーザー同意、アクション実行権限、全体共通スキル（Global Skill）が自動的に成立することはありません。パッケージ内の記述や生成されたコンテンツから勝手に新しい権限を新設するインターフェースは禁止します。
- データの鮮度や現在有効であるかどうかは、関連する前提条件や利用目的に応じて個別に判断し、遅延して届いた処理結果の記録、意味の更新、次の実行、画面提示などは、それぞれの担当機能へ正しく戻さなければなりません（Context Assembly第7節、Action Execution第7節）。単一の「有効フラグ」だけに安易に集約してはいけません。
- データを保持・利用するすべての機能は、消去処理中に届いたデータの破棄を含め、内部データの完全消去、再保存の防止、未完了状態の確実な保全に参加しなければなりません（Targeted Deletion第6節〜第8節）。「元の参照先を消しただけ」「インデックスのレコードを1つ消しただけ」「LLMが納得したから完了」といった不完全な消去は認められません。
- バックアップからの復元範囲と、現在の環境における有効性・アクション再開の許可は、別個に確認しなければなりません（Backup-Restore第3節・第7節・第9節）。「復元されたデータが存在すること」を「直ちにアクションを実行してよい」とみなすようなインターフェースは禁止します。
- 古いバックアップから意図的に復元されたデータについて、復元は独立した操作として事前のユーザー説明、監査ログ記録、安全な保留、現在の環境に基づく再評価を経る必要があります。システムが勝手に再削除したり、安全確認なしに自動で再利用したりしてはいけません。
- キャラクターが削除されたとしても、既存コンパニオンの経験データや記録を削除してはならず、必要な元素材（VRMモデルなど）が見つからない場合は「未解決の参照切れ（dangling）」として扱います。勝手に別の素材で代替したり、過去のアクションを再実行したり、勝手にデータを復活させたりするインターフェースは禁止します。

本書が「採用できない選択肢」として明確に除外するのは以下のとおりです。1つの編集可能なコンテキストへの静的設定・経験・制御の統合、キャラクター機能による個体状態や学習データの直接更新、認識・学習機能によるキャラクター静的定義の書き換え、新リビジョンが存在することによる自動適用、設定適用の自動実行や勝手な上書き・巻き戻し・グローバル化、パッケージ由来スキルの勝手な全体共有（グローバル化）や個体削除時の勝手な昇格、単独インポート時のスコープ選択の省略、インポートやバリデーション成功を理由とした権限・秘密・同意・実行権限の勝手な新設、パッケージ内記述をユーザーからの指示やシステム制御変更と誤認すること、バリデーション成功を実行許可とみなすこと、エクスポートファイルへのプライベート情報の混入、キャラクター削除に伴う既存個体の経験や記録の道連れ削除、元素材喪失時の勝手な代替や再実行、古い判定結果やキャッシュされた許可・過去の実行経路を用いた新規処理の開始、結果不明のアクションを「未実行」「失敗」「成功」と勝手に決めつけて自動再実行すること、遅延して届いた古い結果を別の新しい目的に勝手に流用すること、古い判断根拠だけからの自動再学習、キャッシュヒットを理由とした安全制約の省略、AIプロバイダとのセッションの無条件な再利用、結果確認不能な処理を「成功」とみなすこと、不完全なデータの一括マスター化や混同、安全確認に先立つ権限の復活、未完了処理の「成功」表示、要約や復元処理における確定度の勝手な格上げ。これらはいずれも上位のセキュリティ原則を破壊するため、一切採用できません。

上記の責務対応関係があるからといって、システムに「統一Contextレイヤー」「統合Policy Engine」「Character Manager」「Package Service」「Distribution Coordinator」といった新しい肥大化したコンポーネントを追加してはいけません。既存の12の責務、データの担当責任（semantic owner）、ホストとクライアントの配置、および信頼境界の枠組みの中で最適な実現方法を選択します。

必要な安全確認やユーザー判断の省略、現在の同意の勝手な拡大解釈、未完了・結果不明な処理の「成功」扱い、外部作用のロールバック保証、exactly-once（厳密に1回限り）の実行保証といった非現実的な保証を新設することは、自由度には含まれません。

横断的関心事（CC-01〜CC-07）に関して維持すべき一般的な性質は、各重要領域ドキュメントの横断検証と同一です。本ドキュメントが特に強調するのは以下の点です。

- **CC-01（安全境界の維持）**: パッケージ内の記述やバリデーション成功から勝手に権限を新設せず、設定適用・インポート・エクスポートの由来と、権限の成立・アクションの実行許可を厳格に区別します。
- **CC-02（コンテキストの混同防止）**: 過去の適用や古いリビジョンで使用したコンテキスト、キャッシュ、AIセッションを、新しい設定適用時に無条件で再利用してはいけません。
- **CC-03（現在有効性の分離）**: 過去に適用された設定が正しかったことと、それが現在の環境や用途において有効であるかどうかを明確に分離します。
- **CC-05（ライフサイクルの分離）**: キャラクターの静的設定と、個体の経験データのライフサイクルを絶対に混同しません。
- **CC-06（制御の独立性）**: システムの制御経路やデータ保全経路を、設定適用の完了待ちにしてはいけません。
- **CC-07（提示と確定の分離）**: クライアントへデータを配信した（適用供給済み）ことをもって、実際に適用が完了した（適用済み）、あるいは画面に表示された（提示済み）とみなしてはいけません。

他のサブシステム設計との整合性確認においても、各データの担当責任者（semantic owner）は [state-ownership.md](../architecture/state-ownership.md) 第4節の定義どおりに維持され、本書のCD-1〜CD-7はその間での安全なデータ受け渡し契約として位置付けられます。スコープの意味解釈と強制的適用の分離、秘密情報の非露出、フォールバック時における安全ルールのバイパス禁止、結果不明（unknown）の安易な成功・失敗扱い禁止、古いバックアップからの復元時の安全原則は、すべてのドキュメントで完全に統一されています。

重点確認5項目の検証結果は以下のとおりです。

- **CharacterがCompanion個体状態の責任者（owner）になっていないこと**: 設定適用関係の確定、個体の継続性、経験データの意味変更は個体調整・認識・学習機能が担当し、キャラクター機能は静的な設定内容、リビジョン、差分提示、出所情報の提供に専念します（CH-1〜CH-7、CD-1・CD-2・CD-7、第3節・第5節）。
- **LearningがCharacter静的定義を書き換える責任者になっていないこと**: 学習の形成、訂正、スコープ管理は認識・学習機能が担当しますが、対象は経験データに限られます。静的定義の更新は、ユーザーによる明示的な編集、インポート、リビジョン更新としてキャラクター機能が正式に受け付けます（CH-1・CH-3・CH-4、CD-3、第3節）。
- **リビジョン適用がMemory / Relationship / Companion State等の暗黙のリセットになっていないこと**: 「新リビジョンの存在」と「実際の適用」の分離、パーツごとの明示的な選択、4つの性質区分、経験データを上書き・巻き戻し・グローバル化しない原則を固定しています（CD-2、第5節・第6節）。
- **importがPermission / Credential / 実行権限を勝手に生成しないこと**: 外部パッケージを信頼できないもの（untrusted）として扱い、プライベート情報を混入させず、バリデーションと実行許可を厳格に分離し、AIプロバイダ・秘密情報・アクション実行の各担当機能への依存関係を固定しています（CD-4、第7.1節・第7.2節）。
- **パッケージ由来のSkillが勝手に全体共有（グローバル化）しないこと**: 個体限定（Companion scope）を既定とし、各個体で独立して管理し、個体削除時に連動して削除され、単独インポート時はユーザーがスコープを選択し、勝手なグローバル化を禁止することを固定しています。キャラクター機能がスキルの意味やスコープを勝手に支配することはありません（CD-3、第5節）。
