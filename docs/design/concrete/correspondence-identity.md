# 対応関係・識別の具体設計 — Step 13 Concrete Design (Correspondence & Identity)

このドキュメントは、ene における**「識別子（ID）、リビジョン、世代、およびデータ間の対応関係（Correspondence & Identity）」**に関する具体的な設計仕様書です。
システム全体で必要となる「何と何がどう関連づいているか」「そのデータは最新の前提に基づいているか」という対応関係を、具体的な Rust の型定義や照合処理に落とし込めるレベルまで明確化します。
上位の設計原則との優先関係や矛盾が生じた場合の判断基準は、[設計文書 README](../README.md#正本と優先順位) に従います。また、文中の「SO」「DR」「CC」は、それぞれ [状態の所有権（state-ownership.md）](../architecture/state-ownership.md)、[依存関係ルール（dependency-rules.md）](../architecture/dependency-rules.md)、[横断的関心事の設計（cross-cutting.md）](../architecture/cross-cutting.md) を指します。

## 1. 対象と非対象

### 1.1 本書が具体化するもの

- **保持・照合すべき対応関係の体系化**: 実装において永続化し、正当性を確認しなければならないデータの関連付けの一覧（第3節）。
- **共通化できる概念と個別に分離すべき概念の境界**: システム共通の汎用概念にしてよいものと、ドメイン固有の独立した型として厳密に分けるべきものの線引き（第4節・第5節）。
- **Rust における型設計の基本方針**: newtype パターン、enum、struct の使い分け方針と擬似コード（第5節）。クレートの物理的な分割そのものは固定しません。
- **識別子・リビジョン・世代・対応関係の表現方針**: それぞれの役割と安全な比較のルール（第4節）。
- **再起動を跨いで永続化すべきプロパティ**: データベースに保存すべき必須項目（第7節）。テーブル定義そのものは固定しません。
- **一時状態（メモリ上のみ）と派生データの扱い**: 再起動時に消えても安全なデータの整理（第7節）。
- **シリアライズ境界での基本ルール**: 境界を越えてデータを受け渡す際のルール（第4節・第8節）。
- **並行処理における照合単位**: 「何と何を突き合わせて一致すれば、現在の最新データとして受け入れられるか」という判定条件（第6節）。具体的なロック方式やトランザクションプロトコルはここでは固定しません。

### 1.2 本書が決めないもの

- プロジェクト全体のクレート構成、モジュール分割、プロセスやスレッドの物理配置。
- データベース製品の選定、完全な `CREATE TABLE` 定義、インデックス設計、マイグレーション手順。
- プロセス間通信（IPC）の具体的なプロトコル、通信メッセージのバイナリ形式、ネットワークプロトコル、ハートビートやリースの有無・数値。
- キューの長さ、リトライ回数、タイムアウト秒数、タスクスケジューリングアルゴリズム、埋め込み計算や類似度スコアリング、プロンプトの組み立て手順。
- 各サブシステムの完全な API 一覧（ただし、「境界面で決して落としてはならない必須情報」は第8節で固定します）。
- 暗号化方式、バックアップアーカイブ形式、電子署名方式、外部マーケットプレイスや中継サーバー（これらは ene の製品目標に含まれません）。

### 1.3 用語

- **識別子（identity）**: ある存在、要求、アクション試行、操作などを他と一意に区別するための永続的なIDです。そのデータが「正しい」「有効である」という内容の意味までは保証しません。
- **リビジョン（revision）**: 同一の識別子を持つデータの内容が、担当機能（owner）の判断によって変更された履歴を追うための単調増加カウンターです。これ単体では現在の有効性の唯一の証拠にはなりません。
- **世代（generation）**: 同一のライフサイクル（端末の滞在先、バックアップ復元、データ削除区間など）が切り替わったり再成立したりしたことを追うための単調増加カウンターです。新旧の比較ではなく、「どの時間区間に属しているか」を識別するために使います。
- **対応関係（correlation）**: 2つの識別子・リビジョン・世代の間に存在する、向きを持った関連付けです（例: 実行結果 → 元の試行、要約 → 元の発言範囲、画面提示 → 会話ラウンド）。システム全体の巨大な関連グラフをひとつのオブジェクトにまとめてはいけません。
- **境界トークン（boundary token）**: 正当性の照合のために呼び出し元から渡される、「期待する前提状態のコピー」です（例: `expected_task_revision`）。これ自体が権限を持つのではなく、最新状態と比較するための材料として使います。
- **担当責任者（semantic owner）**: [状態の所有権（state-ownership.md）](../architecture/state-ownership.md) で定めた、データの意味、通常の変更、ライフサイクルの管理責任を持つ機能です。本書で定義するレコードやIDそれ自体が担当責任者になるわけではありません（第2節）。

## 2. 原則

### 2.1 Ownership を奪わない（責任境界の維持）

本書で定義するデータ構造は、各担当機能が持つ意味を**プログラム上で安全に保持・照合するための表現**にすぎず、データの管理責任そのものを奪うものではありません。以下の原則をすべて維持します：

- IDは区別のための記号、correlationは関連の記録にすぎません。内容を採用するか、タスクが達成されたか、現在も有効かどうかの判断は、常に各ドメインの担当機能が行います（第6節の照合条件は「受け入れ可能かどうかの前提チェック」であり、担当機能の判断を代行するものではありません）。
- データの由来（どこから来たか）は参照や説明のための記録であり、最新知識のマスターデータ（正本）ではありません。最新の認識は長期記憶（Memory）、タスク、ルールなどの担当機能が保持します。
- プロンプト文脈（Context）は、特定の用途のために一時的に組み立てられる派生データにすぎません。システム共通の巨大な `Context` オブジェクトや、共通コンテキストデータベースを新設してはいけません。
- タスク、アクション試行、端末滞在、データ削除区間、バックアップ復元は、それぞれ完全に独立したライフサイクルを持ちます。これらを単一の汎用な `Status` 列挙型や共通の状態遷移表に無理やりまとめてはいけません。
- 過去の認可ログ、委任時に渡されたコピー、キャッシュされた判定結果を生きた許可として再利用してはいけません。現在のアクションを実行してよいかは、権限・制約サブシステムが最新のルールや条件と照らし合わせてその都度確定します。
- 試行によって「外部に何が起きたか」は実行・拡張サブシステムが把握し、「タスクの目的が達成されたか」は作業サブシステムが判断します。アクション試行レコードが存在することや外部APIが成功を返したことと、タスクの完了を同一視してはいけません。
- パートナーが今どの端末に滞在しているかの正式な権限は、ホストPCが一元管理する帰属記録のみが持ちます。クライアント端末側の一時セッションや接続主張は、照合のための材料にすぎません。
- データ完全削除における進捗記録、保留フラグ、再保存防止条件は、システム全体の削除を円滑に進めるための調整記録であり、各ドメインのデータ内容を勝手に書き換える権限ではありません。各データの消去はそれぞれの担当機能が責任を持って実行します。

### 2.2 過度の共通化をしない

実装上の手軽さを理由に、以下のような過度な共通化を行ってはいけません：

- 万能の `UniversalContext`、`UniversalOperation`、`UniversalEvent`、`UniversalState`、`UniversalCorrelationGraph` などの巨大構造体を作らない。
- すべてのIDをひとまとめにした `ContextId`、`OperationId`、`CorrelationId` や、何でも入る `Status`、`Event` enum を作らない。
- システム全体のすべての状態変更を単一のグローバルな連番カウンターや完全な時間順序（全順序）で管理しようとしない。
- 全ドメイン共通の「汎用状態ストア」「共通リポジトリ」「統合マネージャー」「グローバルコーディネーター」にすべての管理を集約しない。

共通化してよいのは、第4節で述べる**抽象的な性質**（不透明性、単調増加、向きを持った対応関係、安全な比較パターン）のみです。具体的な型、内部状態、ライフサイクルは、ドメインの業務ルールが異なる限り厳格に分離します。

### 2.3 型方針

1. **内部表現が同じプリミティブであっても、意味の異なる型は厳格に分ける**: たとえ内部が同じ 128bit UUID であったとしても、`CompanionId` と `TaskId` は Rust の別個の newtype として定義し、お互いに暗黙の型変換（`From` / `Into`）や値の直接比較ができないようにします。本番コードで何でも入る汎用 ID enum を使ってはいけません。
2. **newtype パターンを標準とする**: ドメイン境界を越えて生の `String`、`u64`、`Uuid` などを不用意に受け渡してはいけません。フィールド名だけで区別するのではなく、コンパイラの型システムによって意味を取り違えないように保護します。
3. **リビジョンや世代を生の数値だけで単独で持ち歩かない**: 必ず `(identity, revision)` または `(lifecycle, generation)` のペアとして扱います。IDを無視してリビジョン番号の大小だけで新旧や有効性を判断してはいけません。
4. **対応関係（correlation）は向きを持ったペアとして明示する**: 暗黙の時系列順、メッセージの到着順、IDの大小関係などを、データが関連づいていることの根拠にしてはいけません。

## 3. 必要な対応関係の体系化

システム内で正しく保持し、照合しなければならない重要な対応関係を8つの領域に整理します。

### 3.1 Context の由来・用途・consumer との対応

- リクエストの同一性は、単一のコンパニオンIDやタスクIDだけではなく、`(利用主体, 利用目的, 担当コンパニオン, タスク・委任関係, 目的・追加指示の前提, 元の入力や操作, クライアント依存なら取得元端末・ラウンド・候補, 活動の継続関係, 期待する送信先)` という一連の組み合わせによって初めて一意に確定します。
- プロンプトに含める情報の単位ごとに、`(担当機能, 情報源との関係, 由来, リビジョンや取得日時, 共有スコープ, 送信や保存の制限, 参照の解決状態)` を保持するか、マスターデータから確実に辿れる必要があります。

### 3.2 Owner 意図 / Permission 判断 / 実対象との対応

- アクションの認可判断に必要な材料は、`(実行主体と委任チェーン, 対象タスクとワークスペースの範囲, 目的, 具体的な操作対象と種別, 送信先と想定される外部作用, 使用するデータ, コストやリスク, 依拠したユーザーの意図やルール)` の完全なセットです。

### 3.3 Task / delegation / Task Agent との対応

- タスクは、`(目的, 担当コンパニオン, 適用された追加指示, 進捗状況, 待機理由, 完了・失敗・キャンセル状態, 最終結果, 未完了事項や次の判断)` を追跡します。タスクコンテキストは `(採用した目的・指示・材料・途中理解, 由来, 取得日時, 有効性)` のセットです。
- 委任関係は、`(誰から, どの範囲を, どの一時エージェントへ委任したか, 進捗・待機・停止・成果の受領状況)` を追跡します。
- 会話ログに記録されたユーザーの発言そのものと、タスクに実際に反映された内容、および保留中の指示は明確に区別します。

### 3.4 Action の判断 / 試行 / 実作用 / outcome との対応

- アクションの進行状態は、`(受付, 開始, 把握された外部作用, 結果の確定度, 停止要求, 停止結果)` を厳密に区別します。内部ログの保存成功と外部への作用成功は別であり、外部通信の成功と内部保存の成功も別です。
- 結果の確定度は、少なくとも `確認済み成功（ConfirmedSuccess） / 確認済み失敗（ConfirmedFailure） / 成否不明（Unknown）` を区別します。キャンセルを受け付けたことと停止が完了したこと、通信が通ったことと操作が成功したこと、画面に表示されたことと認可されたことはそれぞれ全く別の事象です。
- 重複の可能性がある再送やリトライは、すべて新しい試行として扱い、成否不明や二重実行の管理対象とします。「同じ試行が続いているだけ」として管理をスキップしてはいけません。
- 遅延して届いた結果は元の試行履歴に記録し、現在のタスクの達成や次のアクションへ無条件に自動採用してはいけません。

### 3.5 Companion / Client / presence / round との対応

- 端末間の切り替え期間中は、`旧端末に滞在 / 移行中 / 新端末に滞在 / アクティブ端末なし / 一時停止中 / 復旧待ち` を厳密に区別し、単なる真偽値（boolean）や単一のアクティブフラグに安易に潰してはいけません。
- 会話ラウンドは `(コンパニオン, 端末, ラウンドID, 候補や試行)` の対応関係であり、端末移動や切断、再起動を理由に、古いラウンドの入力や未提示の出力を新しいラウンドへ勝手に付け替えてはいけません。

### 3.6 Targeted Deletion の対象 / 由来 / 依存 / 区間との対応

- すべてのデータ保持者（各機能だけでなく、処理中のコンテキスト、派生データ、キャッシュ、端末側の一時コピー、返却待ちの結果を持つコンポーネントを含む）は、進行中の削除操作に対して `(情報源との関係, 処理中の利用状況, 局所的な削除・検証状況, 再保存の防止, 未確認範囲)` を説明できなければなりません。
- 元データを削除した後に依存関係まで一緒に消滅してしまい、遅れて届いた古いデータを識別できなくなるような実装は禁止します。テキスト本文そのものを残さずに、対応関係のハッシュや識別情報のみを保持して再保存を防ぐ工夫が必要です。

### 3.7 Backup / Restore での復元 state と現在環境との対応

- リストア復元の対応関係は、`(復元操作, バックアップ取得時点, RestoreGeneration, 復元後の保留状態)` です。正本切り替えの前は「復元前の正常データ」が正本であり、切り替え後は「復元されたデータ」が正本となります。両者が中途半端に入り混じった第3の混合状態を作ってはいけません。

### 3.8 delayed / stale result の元活動への帰属対応

- 遅延して届いた結果を受け入れる窓口は、用途ごとに担当機能が分かれています。会話や画面表示への反映は「個体調整機能」、タスクの達成判断は「作業機能」、記憶や要約への定着は「認識・学習機能」、権限やルールの解釈は「権限・制約機能」、外部作用やコストの記録はそれぞれの元機能が担当します。

## 4. 共通に持つ識別・correlation concept

本節では、各識別子が備えるべき**抽象的な性質**を共通化します。具体的な型やライフサイクル、カウンターをシステム全体で無理に共有することはありません。

### 4.1 Identity（永続的な識別子）

- **性質**: 不透明（opaque）であり、衝突しない程度に一意であり、使い回さず（再利用禁止）、IDの文字列自体から内容を推測できず、IDが存在すること自体がデータの正当性を主張しないこと。一度削除されたIDと同じ値を再発行してはいけません。
- **表現方針**: Rust では各ドメインの newtype の内部表現として、共通のプリミティブ（UUID v4/v7 互換の 128bit 値や、同等の不透明なバイト列）を使用して構いません。文字列として出力する際は、型ごとに勝手な接頭辞（例: `"task_"`）を付けず、フィールド名と型名で区別します。接頭辞の文字列をパースしてロジックを分岐させるようなアンチパターンは禁止します。ログやデバッグ出力では、型名と値をセットで記録します。
- **生成**: IDの発行主体は、各ライフサイクルの担当機能または調整役が定めます。AIモデルの出力や外部コンテンツ、クライアント端末の勝手な自己申告をIDの生成元にしてはいけません。万一衝突が発生した場合は新しいIDを発行し、古いIDを上書きしてはいけません。
- **共有しないもの**: 採番の仕組み、発行タイミング、生存期間、削除時の扱い。例えばコンパニオンIDの発行（個体調整）とアクション試行IDの発行（実行・拡張）は全く別の生成系列であり、単一のグローバルシーケンスを共有しません。

### 4.2 Revision（担当機能ごとの内容順序）

- **性質**: 同一の識別子を持つデータに対して、担当機能の判断によって内容が変更された順序を示す単調増加カウンターです。リビジョン番号の大小比較は、同一の `(identity, owner)` のペアの中でのみ意味を持ちます。異なるID間や異なる機能の間でリビジョン番号を比較してはいけません。リビジョン番号は飽和（saturation）やオーバーフロー（wrap-around）、値の再利用を行いません。次の相異なるリビジョンを永続化データとして確定できない場合（後続リビジョンが存在しない、あるいは後続値を永続化表現へ写せない場合）は、リビジョン枯渇として `Ok` 側のドメイン判定結果（domain outcome）として報告し、技術的エラーや暗黙の最大値張り付きにしてはなりません。
- **表現方針**: Rust では `Revision(u64)` のような共通の内部構造を持っても構いませんが、単独で持ち歩かず、必ず `(Id, Revision)` のペアとして扱います。データのハッシュ値（ダイジェスト）は検証用の付随情報として添えてもよいですが、リビジョンの代わりにはなりません。ハッシュの一致だけで同一の意味とみなしてはいけませんし、担当機能による確定が常に優先されます。
- **時刻との関係**: 時計の時刻や取得日時はリビジョンの代わりにはなりません。時刻は人間への説明や表示、スケジュール計算のために保持し、データの新しさの判定は第6節の照合ルールに従います。システム共通の論理時計や全順序、一律のTTLを強制しません（CA §7.2）。

### 4.3 Generation（ライフサイクルごとの区間順序）

- **性質**: 同一のライフサイクル（滞在先帰属、リストア復元、データ完全削除区間など）が切り替わったり再確立された順序を示す単調増加カウンターです。新旧の優劣ではなく、「どの区間に属しているか」を特定するために使います。異なるライフサイクル同士で数値を比較してはいけません。
- **表現方針**: Rust では `Generation(u64)` を内部表現として使っても構いませんが、型とフィールド名でライフサイクルを厳密に区別します（例: `PresenceGeneration` と `RestoreGeneration` は別の型として定義します）。
- **グローバルな連番カウンターを設けない**: すべての状態に共通する単一のカウンターやスナップショットIDを前提としません。複数の機能にまたがるデータに対して共通のスナップショットを要求してはいけません。

### 4.4 Correlation（向きを持った対応関係）

- **性質**: `from → to` の向きを持ったペアです。少なくとも `(from_id, from_rev_or_gen, to_id, to_rev_or_gen, 利用目的)` を含みます。システム全体の関連グラフを巨大な永続オブジェクトとして保持する必要はなく、必要な関連を辿れるように記録します。
- **表現方針**: Rust では各ドメインに応じた関連構造体を個別に定義します。何でも入る汎用の `Correlation { from: String, to: String }` を本番コードで使ってはいけません。関連が存在すること自体に、承認やタスク達成の意味を持たせてはいけません。
- **本文の非複製**: 関連を記録するために、プライベートなテキスト本文をあちこちに複製してはいけません。識別用の値であっても対象情報を復元できてしまう場合は保護や削除の対象となります。由来を記録したいからといって、削除されたはずの本文やAPIキーを別場所に保存してはいけません。

### 4.5 Boundary token（期待する前提の写し）

- **性質**: 照合処理の入力として渡される、「呼び出し側が前提としている相手の状態」のコピーです（例: 認可判断時に確認した `expected_task_revision` や、送信前に解決した `expected_presence_generation`）。これ自体が権限を持つのではなく、最新状態と比較するための材料です。一致しない場合は処理を開始せず、保留、拒絶、または最新状態での再評価に戻します。
- **表現方針**: 各インターフェースは必要な境界トークンを明示的な引数として受け渡します。「暗黙的に最新のものを使う」といった曖昧な指定は禁止します。トークンが渡されなかった場合は「制約なし」と解釈するのではなく、「照合不能のため不受理」として安全に拒絶します。

### 4.6 シリアライズ境界での基本ルール

- ホストPCの永続化、ホストとクライアント間の通信、監査ログやデバッグ記録においては、ID、リビジョン、世代、対応関係を独立したフィールドとして明確にシリアライズします。自由記述のテキスト本文の中に埋め込まれた文字列をパースして照合に使ってはいけません。
- クライアント端末、AIプロバイダ、MCPサーバー、プラグインとの境界面において、ホスト内部の生ID体系をそのまま無制限に露出する必要はありません。外部に渡す場合は用途を限定した非秘密の参照（opaque な参照値）に留めます。APIキーなどの認証秘密値は通常の通信ペイロードに載せてはいけません。
- 時刻情報は ISO 8601 形式の文字列と作成時のタイムゾーンを保持します。ユーザーが設定したスケジュールのタイムゾーンを勝手にローカル時刻に書き換えてはいけません。

## 5. ドメイン固有の型・状態表現

本節に示す型名やフィールド名は設計の具体例（疑似コード）です。実装時にわかりやすい名前に調整することは認められますが、型の分離とフィールドの意味付けは厳格に維持してください。

> [!IMPORTANT]
> **共通の禁止事項**
> `CompanionId` と `TaskId` の内部表現が同じであっても相互に型変換してはいけません。`ActionAttemptId` の存在からタスク達成を勝手に導いてはいけません。`PresenceGeneration` から勝手に滞在状態を創設してはいけません。`DeletionOperationId` から勝手に他ドメインのデータを直接消去してはいけません。`RestoreGeneration` から勝手に古い権限を復活させてはいけません。

### 5.1 個体・キャラクター・適用関係

```rust
struct CompanionId(/* 不透明なID */);
struct CharacterId(/* 不透明なID */);
struct CharacterRevision(/* 不透明なリビジョン番号 */);
enum CharacterPart { Persona, Body, Voice, SkillRef }

/// 個体調整機能が管理する「どのキャラクター定義が適用されているか」のマスター表現。

struct CompanionCharacterApplication {
    companion: CompanionId,
    character: CharacterId,
    revision: CharacterRevision,
    parts: Vec<AppliedPart>,
    selected_by_owner_at: WallClockWithTz,
}

/// パーツごとの適用状態。未確認のパーツを勝手に適用済みに更新してはならない。
struct AppliedPart {
    part: CharacterPart,
    applied_revision: CharacterRevision,
    owner_selection: OwnerSelectionRef,
}

/// ユーザーによる管理操作との対応関係（操作日時や操作IDを含む）。

```

- 新しいリビジョンが存在することだけを理由に、「すでに適用された」「適用すべきである」と勝手に推測してはいけません。
- キャラクターパッケージの更新によって、これまで培った会話の記憶や成長記録を勝手にリセットしてはいけません。パッケージ内に権限、認証情報、ユーザー同意、システム設定を書き換えるような内容が含まれていたとしても、それらを適用対象から完全に除外します。

### 5.2 会話・ラウンド・未伝達メッセージ

```rust
struct RoundId(/* 不透明なID */);
struct ClientId(/* 不透明なID */);

/// 入出力・提示機能が管理する会話ラウンドの実際の状態。
struct ConversationRound {

/// 個体調整機能が管理する未伝達メッセージの参照情報。
/// タスク由来はタスクレコード、日常会話由来は活動レコードがマスターデータであり、
/// 本構造体は伝達状況を確認・照合するためのものである。第2のタスク正本にしてはならない。
struct UndeliveredRef {

enum ReportStatus {
```

- メッセージを生成したこととユーザーに提示されたこと、送信したことと伝達が完了したこと、報告済みであることとユーザーから承認されたことは、それぞれ全く別の事象です。
- 会話ラウンドの終了は、会話タイムラインの終了や過去ログの消去を意味しません。

### 5.3 タスク・委任・タスクコンテキスト・ワークスペース・スケジュール

```rust
struct TaskId(/* 不透明なID */);
struct TaskRevision(u64); // 同一タスクに対する指示や目標の変更順序。
struct DelegationId(/* 不透明なID */);
struct TaskAgentEphemeralId(/* 一時的なエージェントID。永続データの責任者にはならない */);
struct WorkspaceAssocId(/* 不透明なID */);
struct ScheduleId(/* 不透明なID */);
struct ScheduleOccurrenceId(/* 不透明なID */);

struct TaskRef {
    task: TaskId,
    revision: TaskRevision,
}

struct TaskPurposeRef {
    task: TaskId,
    adopted_revision: TaskRevision, // 目的を採用した revision。本文の正本は task_revision snapshot。引き継いだ目的は現在 revision より前を指し得る
}

struct SteeringPremiseRef {
    expected: TaskRef,               // 依拠した現在 revision
    purpose: TaskPurposeRef,         // 依拠した現在目的（比較材料。authority ではない）
}

struct TaskContextEntryId(/* opaque */);

struct DelegationRef {
    delegation: DelegationId,
    task: TaskRef,               // 委任元の親タスクとその前提リビジョン
    delegator: AssigneeRef,      // 委任元の担当者（タスク側前提。CompanionIdを直接インポートしない）
    agent: TaskAgentEphemeralId, // 一時的な作業主体。独自の長期人格や親愛度は持たない
    scope: DelegationScope,      // 委任されたタスクとワークスペースの範囲のコピー
}

// タスクコンテキストの識別子群は TaskContextEntry（採用された識別子・由来・取得日時）としてタスク側に定義します。
// 採用目的の本文のマスターデータは task_revision snapshot であり、採用指示の本文のマスターデータは由来レコード（History）です。
// context entry は本文を複製しません。採用目的の採用識別子は TaskPurposeRef であり、採用指示の採用識別子は entry 自身の
// TaskContextEntryId です（由来レコードの生IDとは明確に区別されます）。採用指示 entry は採用リビジョンで 1 度だけ書き込み、
// 現在有効な指示は現在リビジョンまでの採用指示 entry 全体として解決します。

struct ScheduleOccurrenceRef {
    schedule: ScheduleId,
    occurrence: ScheduleOccurrenceId,
    // スケジュールの各実行回は独立した新しいタスクとなる。
    // 実行できなかった回（missed）を勝手に実行済みに書き換えてはならない。
    started_task: Option<TaskId>,
    occurrence_status: OccurrenceStatus,
}

enum OccurrenceStatus { Missed, Started, CancelledAsTaskContract }
```

- タスクレコードの寿命は、担当コンパニオンへの参照によって勝手に決められるものではありません。担当コンパニオンが削除された後であっても、残されたタスクレコードには管理画面等から安全にアクセスできなければなりません。
- すべての軽微な操作を無理にタスク化する必要はありませんが、まとまった一連の外部作業をタスク化せずに雑に実行することも禁止します。

### 5.4 アクション・試行・作用・確定度

```rust
struct ActionAttemptId(/* 不透明なID */);
enum ActionCertainty { 
    ConfirmedSuccess, // 確実な成功の証拠が確認された
    ConfirmedFailure, // 確実な失敗の証拠が確認された
    Unknown,          // 外部通信が途切れるなどして成否が不明
}

/// 実行・拡張機能が管理する、把握された外部作用の記録。
struct ActionAttemptRef {
    attempt: ActionAttemptId,
    task: Option<TaskRef>,          // 軽微な日常アクションでは None（活動レコードと紐付く）
    delegation: Option<DelegationId>,
    workspace: Option<WorkspaceAssocId>,
    real_target: RealTargetRef,     // パス解決等を経た具体的な操作対象（単なる文字列一致ではない）
    operation: OperationKind,       // Read | Create | Edit | Delete | Execute を混同しない
    relied_permission: PermissionEvaluationRef, // 判断時の根拠（生きた許可そのものではない）
}

/// 認可判断の記録を生きた許可と区別するための、判断当時の対応の写し。
struct PermissionEvaluationRef {
    evaluation: PermissionEvaluationId,
    // 当時「何についてどう判断したか」の記録。監査や説明のための材料。
}
struct PermissionEvaluationId(/* 不透明なID */);
```

- アクションの受付、開始、作用、確定度、タスクの達成、制御変更、未伝達メッセージ、監査ログは、それぞれ独立した事実であり別個の機能が管理します。
- 外部サービスからの「成功」レスポンスは、対象や作用の対応関係を確認した上で初めて証拠として扱います。AIエージェントの自己申告を成否の証拠にしてはいけません。
- 再試行やリトライは新しい `ActionAttemptId` を発行して実行します。重複実行のリスクがある処理を「同じ試行が続いているだけ」とみなしてはいけません。

### 5.5 権限・制約・認証情報・推論割当・利用量

```rust
struct UsageAttributionRef {

struct CurrentPermissionBoundary {
```

- 会話の中でのユーザーからの明確な依頼は一回限りの承認になり得ますが、永続的な拒絶（Deny）、都度確認（Always ask）、機能境界（Capability）をユーザーに無断で上書きすることはできません。
- APIキーなどの認証秘密値（Credential）は、上記のいかなる構造体にも直接含めてはいけません。外部への参照は非秘密のリファレンスに留めます。AIモデルの出力から勝手にAPIキーを登録・更新してはいけません。


### 5.6 presence・接続・Client 主張

```rust
struct PresenceGeneration(u64); // コンパニオンごとの滞在ライフサイクル順序。唯一のマスター権限はホストPCの記録。

/// 接続・存在機能が管理する個体ごとの滞在帰属記録。唯一のマスターデータ（正本）。
struct PresenceAttribution {
    companion: CompanionId,
    state: PresenceState,
    active_client: Option<ClientId>,
    generation: PresenceGeneration,
}

enum PresenceState {
    Present,        // いずれかの端末に滞在している（active_client が Some）
    NoActive,       // 稼働中（Running）だが現在アクティブな端末が存在しない正常な状態
    InTransition,   // 端末間を移動中。新旧どちらの端末でも新規処理を開始しない
    Stopped,        // 一時停止中。滞在権限はなく、再開ヒントや保存データとは別個
    RecoveryWait,   // ホスト再起動後の端末復旧待ち。アクティブ端末なし
}

/// 再配置ヒントおよび再起動前の復旧先。単なる参考記録であり、これ自体が滞在権限になるわけではない。
struct RelocationHint {
    companion: CompanionId,
    last_client: ClientId,
    recovery_destination: Option<ClientId>,
}
```

- クライアント端末側が主張する一時的な状態（端末が自称する世代番号、ラウンドID、入力候補など）は、入力受付インターフェースを通じて受け取りますが、ホストPC側の正規の滞在記録とは明確に区別します。
- `PresenceGeneration` が一致していることだけでは不十分であり、実際のネットワーク疎通、必要な機能の可用性、最新の権限ルール、保留状態も合わせて照合します。疎通が確認できない状態を「おそらく繋がっているだろう」と勝手に現在有効とみなしてはいけません。
- ヒントや復旧先の保存は「接続・存在機能」が行いますが、現在の正当性の確認なしに古い情報から勝手に滞在を復活させてはいけません。

### 5.7 Observer の限定 routing 文脈

```rust

/// 共有観測機能が保持する、ルーティング用の派生表現。

struct RoutingContextRef {
```

- タスクストアから勝手にデータを読み出してはいけません。タスクコンテキストは、正規の「個体調整機能」と「作業機能」の連携を通じてのみ受け取ります。
- 画面監視（Observer）専用のAI割り当てと、通常の個体設定を混同してはいけません。ルーティングの権限は、「検知した候補をどのコンパニオンへ通知してよいか」という関連付けを成立させるためだけに使います。

### 5.8 Learning・Summary・根拠・scope

```rust
struct LearningId(/* 不透明なID */); // 記憶（Memory）、スキル、関係性、個体状態の各内容ID
struct LearningRevision(u64);    // 認識・学習機能が管理する内容更新の順序
struct SummaryId(/* 不透明なID */);
struct SourceRangeRef { /* 元の会話やタスクの大まかな範囲。正確な逐語引用は会話履歴を参照 */ }

/// 要約（Summary）と、記憶の形成・改訂時に参照された根拠データとの対応関係。
/// 要約自体を最新知識のマスターデータ（正本）にしてはならない。
struct SummaryGroundsRef {
    summary: SummaryId,
    used_grounds: Vec<GroundsRef>,
    formed_or_revised: Vec<(LearningId, LearningRevision)>,
}

struct GroundsRef {
    source_range: SourceRangeRef,
    // 根拠となったテキスト本文の重複コピーは不要。参照によって元データを辿れるようにする。
}
```

- 「体験（Experience）」は起きた出来事と結果を捉えるための概念であり、システム全体の全活動をひとまとめに放り込むような巨大な生データストアを新設することはありません。
- 知識の全体共有（Global化）は、内容とその背景を慎重に判断して決定されるべきものであり、個々のプライベートな会話ログや要約文の全文まで無差別に全体へ公開してはいけません。
- 過去の知識が誤っていた場合の「訂正」と、後から状況が変わったことによる「更新」を区別し、後者の場合は「過去のある時点では確かにそうだった」という時間的な有効性を失わないようにします。

### 5.9 消去・backup・復元・保持

```rust
struct DeletionOperationId(/* 不透明なID */);
struct DeletionSweepGeneration(u64); // 消去処理の実施世代。対象時間区間の識別に用いる。

/// 保全・消去機能が管理する、システム全体の削除操作の調整記録。
/// 各ドメインのデータ内容を直接所有するわけではない。
struct DeletionOperationRef {
    operation: DeletionOperationId,
    sweep: DeletionSweepGeneration,
    purpose_target_impact_exclusion: OperationScopeRef,
    participant_completions: Vec<ParticipantCompletionRef>,
    hold_conditions: Vec<HoldConditionRef>,
}

/// 消去条件。各データ保持者や受入箇所が、処理中のデータ利用や再保存を防止するために適用する。
struct ErasureConditionRef {
    operation: DeletionOperationId,
    sweep: DeletionSweepGeneration,
    valid_interval: ErasureInterval, // 削除開始から検証完了までの時間区間（区間内の再到着を含む）
}

struct BackupPointId(/* 不透明なID */);
struct RestoreGeneration(u64); // バックアップ復元が成功するごとに進む世代番号。復元前の旧環境と区別する。

struct RestoreRef {
    generation: RestoreGeneration,
    backup_point: BackupPointId,
    post_restore_hold: HoldConditionRef,
}

struct HoldConditionRef { /* 権限失効、コスト上限、復元後保留、削除中保留などの制約条件 */ }
struct OperationScopeRef { /* 削除の目的、対象範囲、影響、除外対象、確認事項の対応関係 */ }
struct ParticipantCompletionRef { /* 各コンポーネントにおける処理・検証の完了・未完了・失敗範囲 */ }
```

- `DeletionOperationRef` の完了は「保全・消去機能」がシステム全体として確定しますが、各ドメインにおけるデータの実際の消去はそれぞれの担当機能が行います。調整役が勝手に他機能のデータを直接変更する権限を持ってはなりません（DR-09）。
- `HoldConditionRef` は保全・消去が保持するシステム全域操作の調整参照であり、個々の制約条件（失効や利用量上限は権限・制約担当、消去保留は保全・消去担当、停止は個体調整担当）の現在有効性の判断は各担当責任者に残ります。各処理の受入箇所はこの条件を自身の前提構造体（hold-check premise）に写し、同一のコミット照合（commit compare）内で検証します（IB §4）。
- 過去のバックアップから明示的にデータを復元（リストア）することは、自動的な再学習とは全く別の操作であり、事前の十分な説明、監査ログの記録、復元後の安全保留、最新条件との再評価を必ず経ます（PE-3、BR §8）。

## 6. 現在性・照合単位（concurrency の比較内容）

具体的な実装メカニズム（ロック、MVCC、キュー、トランザクションなど）を選択する前に、「何と何を突き合わせて一致すれば、最新の前提として受け入れてよいか」という**照合の判定ルール**を明確に定めます。システム共通のグローバルな連番カウンターを前提としてはいけません。

### 6.1 一般形

新しいデータの利用、タスク成果の採用、アクションの実行は、少なくとも以下の照合を満たす場合に限り安全に受け入れます。満たさない場合は保留、拒絶、または最新状態での再評価に戻し、古い判定や解決済み経路だけを根拠に処理を開始してはいけません：

1. **対象の識別子（identity）が一致していること**。
2. **前提としていたリビジョンや世代番号が、現在の最新のリビジョン・世代と正しく対応していること**（同一であるか、安全に継承・再評価されたものであること）。
3. **根拠とした認可、ユーザー同意、端末条件、コスト枠、保留状態、削除条件、復元条件が、現在の最新条件と一致していること**。
4. **クライアント端末に依存する処理であれば、現在の滞在世代番号、実際の接続疎通、機能の可用性が一致していること**。
5. **時間がかかって遅れて届いた処理結果であれば、元の試行やタスクの履歴として正しく紐付けられ、現在の最新タスクの達成成果へと勝手に自動採用されないこと**。

「最新の値を読んだはず」「キャッシュにヒットした」「到着順で最後だった」という事実は、それ単体では受け入れを認める根拠にはなりません。

### 6.2 用途別の照合一覧表

| 実行しようとする処理 | 確定直前に突き合わせて比較するもの | 不一致だった場合の安全な扱い |
|---|---|---|
| **文脈（Context）の参照・選択** | 要求の `(利用主体, 用途, タスク・委任, 目的・追加指示の前提, 活動継続関係)` × 各情報の `(担当機能, 情報源範囲, リビジョン, スコープ, 制限)` × 現在のセキュリティ制約 | 目的が成立しないとして文脈不足に戻します。別の無関係な活動へ勝手に付け替えてはいけません。 |
| **プロバイダへの実送信（初回・フォールバック・再送・継続）** | 論理的な選択範囲 × 解決された割り当て経路と実送信先・データ・用途・取り扱い・費用の同意 × 最新の認証用途・制限・保留・利用量 × 元の要求範囲 | 送信を阻止します。同意が得られていない不足を、テキストを勝手に削ることでこっそり解消してはいけません。 |
| **アクションの新規開始** | アクション試行が前提とする `(タスクリビジョン, 委任スコープ, ワークスペース範囲, 具体的操作対象と種別, 依拠した権限)` × 現在の `(最新タスクリビジョン, 委任の有効性, ワークスペースの有効性, 解決された実対象, 最新の許可・端末・コスト・停止・保留・消去・復元条件)` × 端末依存なら滞在世代と接続状況 | 処理を開始しません。古い判定や解決済み経路だけで開始してはいけません。ユーザー確認待ちの場合は実行せず待機します。 |
| **重要変化の再評価** | 操作対象の変更、操作種別の変更、外部作用の拡大、タスクの目的や追加指示の変更、委任やワークスペースの変更、滞在端末の変更、ルールや同意・認証情報の変更、コストやリスクの増大、停止や保留の発生 | 該当する場合は権限を再評価します。無関係な画面テーマの変更や音声の準備完了などを理由に余計な再評価を強制してはいけません。 |
| **タスク達成の受入** | 到着した結果の `(試行ID, タスクリビジョン前提, 目標)` × 現在の `(最新タスクリビジョン, 最新目標・追加指示)` | 古い目標で作られた結果を、新しい目標の達成成果として勝手に採用してはいけません。元の試行履歴への記録と、現在のタスクへの採用を明確に分離します。 |
| **結果の長期記憶・要約化** | 到着した結果の `(情報源範囲, 取得日時, 依拠リビジョン)` × 現在の `(最新記憶リビジョン, スコープ, 制約)` | 遅れて届いた記憶形成処理が、現在の最新記憶を無条件に上書きしてはいけません。到着順だけを理由に新旧を決めてはいけません。 |
| **権限・ルール解釈の採用** | モデルによる「許可」の出力、外部引用、過去の許可ログ、復元ルール、プロンプト内の文脈、キャッシュ判定 × 現在の `(最新ルールリビジョン, 同意, 端末条件, コスト上限, 失効・停止・消去・復元保留)` | セキュリティ制御を勝手に変更してはいけません。恒久的なルール変更は、解釈結果と適用範囲を提示し、保存と取り消し（Undo）の枠組みを経ます。 |
| **クライアント依存活動の開始・継続** | 端末が申告する世代番号 × ホストPCが管理する最新滞在世代番号 × 実際の接続疎通と機能の可用性 × 最新の権限や保留状態 | 接続や状態が確認できない場合は処理を継続しません。古い一時キャッシュや過去の承認情報だけで成立させてはいけません。 |
| **端末切り替え期間中の処理** | `旧端末に滞在 / 移行中 / 新端末に滞在 / アクティブなし / 停止中 / 復旧待ち` の区別 × 処理がどちらの端末に紐付いているか | 移行期間中は新旧どちらの端末でも端末依存の新規処理を開始しません。移動元の処理は安全な区切りまで完了させ、未終了の外部作用を別端末へ勝手に引き継ぎません。 |
| **削除区間中のデータ受入・生成・再保存** | 届いた・生成された情報の `(情報源との関係, 取得日時, 削除区間との関係)` × 進行中の消去条件 `(operation, sweep, valid_interval)` × 各機能の局所検証 | 削除区間に該当するデータはすべて消去対象とし、実行中の処理が誤って再保存しないようにブロックします。削除が完了していないのに完了と表示してはいけません。 |
| **バックアップ復元後の処理利用** | 処理が前提とする `(復元世代番号, 同意リビジョン, 認証情報, 依拠ルール)` × 現在の `(最新復元世代, 最新認証ストア, 最新制約, 復元後の保留状態)` | 復元前の古いセッションや古い同意情報だけで、外部通信やタスクを自動実行してはいけません。一括有効化が行われた後も現在の最新条件を守ります。 |
| **利用コスト・リソース枠の継続判定** | 消費の `(用途・送信先, 報告済み/成否不明/処理中の区分)` × 現在の上限枠やリソース状況 | 処理中や成否不明な枠を勝手にゼロとみなさず、並行リクエストによる上限超過を防止します。安全な継続が判断できない場合は、データを保持したまま安全に停止し、ユーザーの判断を待ちます。 |

### 6.3 試行・重複・不明の扱い

- リトライ、再送、フォールバック、再委任は、新しいアクション試行ID（`ActionAttemptId`）を発行して実行します。重複実行のリスクがある再送処理を「同じ試行が続いているだけ」とみなしてはいけません。
- **成否不明（Unknown）な状態は粘り強く維持します**。単にキャンセルを受け付けた、通信が成功した、画面に表示された、再接続された、復元されたといった間接的な出来事だけで、勝手に成功や失敗に書き換えてはいけません。事実確認が取れた確実な証拠がある場合にのみ確定度を更新します。
- 遅れて届いた結果の帰属は、「試行 → タスクリビジョン → 現在のタスク」の順に辿って検証します。目的は依拠したリビジョンの `task_revision` スナップショットから解決し、本文文字列の一致では照合しません。「元の試行履歴に事実として残すこと」と、「現在の会話やタスクへ採用すること」は明確に分離します。

### 6.4 世代タグの付与規則

- 端末の滞在状態に依存する会話ラウンド、アクション試行、入力候補、画面観測データには、`PresenceGeneration` を付与します。世代が変わった場合、古い世代のデータだけを根拠に新しい処理を開始してはいけません。
- バックアップ復元を跨ぐ可能性のある参照（タスク、ルール、同意、未伝達メッセージなど）には、`RestoreGeneration` を付与します。古い世代の参照だけで復元後に勝手に外部通信を行ってはいけません。
- 個人データ完全削除の区間を跨ぐ可能性のあるデータやキャッシュ、端末側の一時コピーには、`DeletionOperationId` と `DeletionSweepGeneration` を付与します。削除区間中に再到着したデータの消去や、古い根拠からの勝手な再学習を確実に阻止します。
- リビジョン番号と世代番号を混同してはいけません。タスクの目標変更は `TaskRevision` の前進であり、世代番号の変化で代替するようなことはしません。

## 7. 永続化（再起動を跨ぐものと跨がないもの）

データベースの完全なテーブルスキーマは固定しません。ここで定めるのは、「どの対応関係がホストPCの再起動後も保持されなければならないか」という必須の永続化プロパティです。物理的なデータベースを共有しているからといって、各機能の責任境界をひとつに統合してはいけません。

### 7.1 永続化が必須な対応関係

ホストPCのマスターデータとして、再起動後も確実に保持されなければならないデータ一覧です：

| 対応関係の対象 | 保持すべき永続化プロパティ | 備考 |
|---|---|---|
| **個体・キャラクター適用関係** | `(CompanionId, CharacterId, CharacterRevision, 適用パーツ群, OwnerSelectionRef)` | 編集途中やエクスポートの中断があっても、直前の正常状態と適用関係を保持します。未確認の編集データを勝手に正本にしてはいけません。 |
| **会話ログ・活動記録・未伝達メッセージ** | 会話履歴の元データ（発話者、文脈）、保存された活動記録、進行中の意味判断、`UndeliveredRef` と伝達状況 | 画面描画用の一時バッファや音声バッファは消えても構いませんが、ユーザーから受理した指示や未伝達メッセージは決して失ってはいけません。 |
| **タスク・委任・コンテキスト・ワークスペース・スケジュール** | `(TaskId, TaskRevision, 目標・担当・進捗・待機・結果・未完了事項)`, `(DelegationId, TaskRef, 委任元・範囲・進捗・停止・成果)`, `TaskContextEntry`（採用された識別情報・由来・取得日時）, ワークスペース関連付け, スケジュール設定とタイムゾーン | 中断されたタスクは、保存済みの進捗や成否不明な状態を示してユーザーの明示的な再開指示を待ちます。エージェントの終了やコンパニオンの削除によってタスク記録を勝手に消してはいけません。 |
| **アクションの把握された外部作用・成否不明・停止結果** | `(ActionAttemptId, タスク・委任対応, 具体的操作対象と種別, 確定度, 根拠対応, 保留状態)` | メモリ上のバッファが消えても作用の記録を保持します。成否不明（Unknown）を勝手に未実行に戻してはいけません。 |
| **長期記憶・要約・根拠・スコープ** | 要約データと `SummaryGroundsRef`, 長期記憶（現在値・重要度・スコープ・過去履歴）, スキル（有効リビジョン・過去履歴・原本対応）, 関係性（現在値・根拠）, コンパニオン状態 | 派生データ（ベクトルインデックス、キャッシュなど）は独立した復元対象とせず、古い派生データから勝手に権限や状態を復活させてはいけません。 |
| **権限・制約・同意・コスト上限・利用実績** | ルール本文・解釈・スコープ・`RuleRevision`・取り消し履歴, 認可判断ログ, プロバイダ同意・端末条件・禁止ルール・コスト上限, 利用実績（報告済み・不明・処理中の区分） | 過去の許可ログを現在の生きた許可として復活させてはいけません。コスト上限用の利用実績は、キャッシュクリアや再起動を理由に勝手にゼロにリセットしてはいけません。 |
| **認証情報（Credential）** | 最新の認証情報ストア（秘密値、用途、参照、有効性、登録・更新・失効状態） | バックアップファイルに秘密値を含めてはいけません。リストア復元によって古いAPIキーへ巻き戻してはいけません。 |
| **接続・滞在先帰属・ヒント・復旧先** | 個体ごとの滞在帰属記録、最新の接続管理情報、`PresenceGeneration`、再開ヒントと復旧先 | 過去に保存された接続情報から勝手に滞在を復活させてはいけません。稼働中だった個体は、接続が確認できた場合にのみ元の端末へ自動復元し、確認できなければアクティブ端末なしとします。 |
| **画面観測・自発性・一般設定** | 画面監視の設定、自発性の設定、一般設定、ホスト自動起動の選択 | 設定の変更履歴と実際のOSへの適用状態を正しく管理します。 |
| **消去・バックアップ・復元・監査ログ** | 削除要求の目的・範囲・影響・除外、参加者ごとの進捗と残存検証、消去条件と有効区間、バックアップ取得時点と結果、リストア復元の受理・隔離・保留状態、監査ログの追記順 | 処理中の再起動を完了と誤認して保留を勝手に解除してはいけません。完了の証拠の中に削除対象の本文や秘密値を残してはいけません。 |
| **プロバイダ登録・能力・割当解決** | 非秘密のプロバイダ登録情報、能力観測結果、解決された割り当て経路、画面監視専用の割り当て | 解決された通信経路を、独立した恒久的な権限とみなしてはいけません。 |

### 7.2 プロセス内の一時状態でよいもの（再起動で消えて安全なもの）

- クライアント端末側の入力途中のテキスト、画面描画フレーム、3Dモデルのモーション再生位置、音声再生バッファ、音声区間検出（VAD）、割り込み検知（barge-in）、現在のマイクミュート状態。
- 画面監視の生キャプチャ画像、検知候補、ルーティング用の一時データ、推論セッション、期限切れの派生データ。
- プロバイダとの通信セッション残存、端末側で直接送信された一時コピー、MCPツールのUI表示用一時データ。
- 会話中の途中思考プロセス、エージェントの一時的な作業バッファ。
- 未確定の編集データ、ユーザーへの提示前の表示用キャッシュ。

> [!CAUTION]
> 「一時的だから消えてよい」と認められるのは上記のものに厳格に限られます。ユーザーから受理したタスク指示、必要な作業記録、未伝達メッセージ、成否不明な外部作用、システム全体の未完了処理を、勝手に一時状態とみなして消滅させてはいけません。

### 7.3 再起動を跨ぐ必要がある重要データのまとめ

- **成否不明なアクション結果**: 確定度 `Unknown`、根拠の対応関係、保留フラグ。
- **遅延結果の帰属に必要な情報**: `(試行ID, タスクリビジョン前提, 情報源範囲, 世代番号)` の対応関係（本文の重複コピーは不要）。
- **個人データ完全削除の再保存防止に必要な情報**: 消去条件、有効時間区間、完了境界、保留フラグ。
- **リストア復元の整合性保護に必要な情報**: `RestoreGeneration` と復元操作自体の受理・隔離・保留対応（切り替え成立まで復元前の正常データを破壊しない）。
- **古い端末メッセージの識別に必要な情報**: `PresenceGeneration` と滞在帰属、接続状況、復旧ヒントの対応関係。
- **未伝達メッセージとタスクの継続に必要な情報**: `UndeliveredRef` と伝達状況、タスク、委任、ワークスペース、スケジュール設定。

### 7.4 鮮度落ち（Stale）や遅延結果の判定に必要な情報

- 各情報の `(担当機能, リビジョンや取得日時, スコープ, 制約)` と、要求の `(利用目的, 指示の前提, 活動の継続関係)`。
- 各アクション試行の `(試行ID, タスクリビジョン前提, 委任スコープ, 具体的操作対象と種別, 依拠した権限)` と、現在の最新条件のセット。
- 各滞在帰属の `(世代番号, 現在の接続・可用性, 許可・停止・保留状態)`。
- 各削除操作の `(操作ID, 世代番号, 有効区間)` と、各データの `(情報源との関係, 取得日時)`。
- 各復元操作の `(世代番号, バックアップ時点, 復元後保留)` と、各利用の `(前提世代番号, 同意リビジョン, 認証情報の照合)`。

これらを単一の時刻やTTL、到着順、IDの大小だけで判定してはいけません。前提と最新条件に矛盾がある場合は安全に不受理・再評価とします。

### 7.5 システム全域の操作と対応付ける必要があるもの

- すべてのデータ保持者や通信機能が、自身の保持するスコープを「保全・消去機能」へ説明できること。
- バックアップ作成時に、対象時点、参照関係、除外対象、保護状態が正しく照合できること（外部フォルダの実体を勝手に辿って収集しないこと、秘密値を除外すること）。
- リストア復元時に、受理、説明、隔離、照合、正本切り替え、復元後保留、一括有効化という段階を厳格に踏むこと（単一のフラグに潰さないこと）。
- データ初期化（Reset）において、設定のみの初期化と、全データの完全削除を混同しないこと。
- 監査ログやデバッグ記録を、秘密情報の保管場所やデータ削除の抜け道にしてはいけません。

## 8. インターフェースが落としてはならない情報

各インターフェースの具体的な関数定義は [インターフェース境界（interface-boundaries.md）](interface-boundaries.md) が定めます。本節では、各機能間でデータを受け渡す際に決して欠落させてはならない必須情報を固定します。

### 8.1 受け渡し一般の必須情報

- **要求の同一性を特定する情報**: `(利用主体, 利用目的, 担当コンパニオン, タスク・委任関係, 目的・追加指示の前提, 元の入力や操作, クライアント依存なら取得元端末・ラウンド・候補, 活動の継続関係, 期待する送信先)` のうち該当するもの。これらが欠落している場合は「制約なし」と解釈するのではなく、「不受理」として安全に拒絶します。
- **情報の単位を特定する情報**: `(担当機能, 情報源との関係, 由来, リビジョンや取得日時, スコープ, 送信や保存の制限, 参照の解決状態)` のうち該当するもの。制限の異なるデータを雑に混ぜ合わせた単位で渡してはいけません。
- **境界トークン**: 呼び出し側が前提としている相手の状態の写し（`expected_task_revision`, `expected_presence_generation`, `expected_restore_generation`, 消去条件の参照など）。
- **不足や省略の理由**: データが空だったり切り詰められた場合に、それを「該当する事実が存在しなかった」「承認が不要だった」と勝手に都合よく解釈してはいけません。不足している明確な理由を添えて伝達します。

### 8.2 用途別の必須情報一覧表

| 境界面での受け渡し | 決して落としてはならない必須情報 |
|---|---|
| **文脈の参照・選択・変換** | 第8.1項の要求情報、情報の単位、境界トークン、不足理由。データ変換を行う際は依存元とセキュリティ制約を確実に引き継ぐこと。モデルの自己申告だけで依存関係を勝手に解除しないこと。 |
| **プロバイダへの実送信** | 論理的な選択範囲、解決された割り当て経路、実送信先・データ・用途・取り扱い・費用の同意対応、認証用途・制限・保留・利用量、元の要求範囲。費用の報告済み・不明・処理中の区分。 |
| **タスク化・委任・追加指示・結果統合** | 意図、目標、追加指示の前提、ワークスペース条件、キャンセル対象、進捗、結果、待機理由、反映できなかった理由と代替案の対応。会話ログとタスク反映内容の区別。 |
| **アクション要求・試行・停止・結果** | アクション試行参照（試行ID、タスク、委任、ワークスペース、実対象、操作種別、依拠した権限）、認可判断の参照、対象解決の前提、コスト・停止・保留・消去・復元の各条件、把握された作用と確定度。 |
| **権限判断の依頼と回答** | 判断対象（主体、委任、タスク、ワークスペース、目的、操作対象、送信先、データ、作用、コストリスク）、依拠したルールと同意の対応、重要変化の有無、現在の有効性の確定結果。判断ログと生きた許可の区別。 |
| **滞在先・ラウンド・入出力** | 滞在帰属情報（個体、状態、アクティブ端末、世代番号）、端末からの入力候補、会話ラウンドID、新旧・移行中・アクティブなし・停止中の区分。生成と提示の区別、送信と報告完了の区別。 |
| **画面監視（Observer）のルーティング** | ルーティングコンテキスト（情報源、対象、目的、制約、選択前提）、取得元端末、取得日時、候補の対応関係。異なる文脈が混ざったデータを無条件に配送しないこと。対象コンパニオンが利用可能な背景のみを渡すこと。 |
| **長期記憶・要約・根拠** | 要約と根拠の参照、訂正と状況変化の区別、過去の時間的有効性、スコープと制約。古い要約文を訂正後の最新記憶の代わりに使わないこと。 |
| **消去・保持・バックアップ・復元** | 削除操作参照と消去条件（目的、範囲、影響、除外、要確認、参加者、残存検証、保留フラグ）、バックアップ時点と参照関係、復元世代番号と復元後保留、監査ログの記録。完了の証拠にテキスト本文や秘密値を残さないこと。 |
| **利用量・コスト** | 用途と送信先の対応、報告済み・成否不明・処理中の区分、コスト上限とリソースの最新条件。未報告や成否不明な枠を勝手にゼロとみなさないこと。 |

## 9. 検証（Validation / Walkthrough）

本設計で具体化した型や対応関係が既存のライフサイクルを破壊せず、必要な関連付けを失わないことを、以下のシナリオを通じて検証します。いずれも**「古い前提で作られたデータを勝手に自動採用・自動再実行・自動復活させないこと」**が合格の基準です。

### 9.1 プロンプト文脈の組み立て（Context Assembly）

- 用途限定の一時的な派生表現に留まり、勝手な第2のマスターデータを作らないこと。第8.1項の必須情報によって、要求の同一性とセキュリティ制約が正しく運ばれること。
- 情報の不足や省略が後続処理へ正しく伝わり、データが空であることを「事実が存在しなかった」「承認が不要だった」と誤認しないこと。
- データの変換や要約を行っても元の制約を引き継ぎ、分離できないデータはすべての入力制約に厳格に従うこと。

### 9.2 アクションの実行（Action Execution）

- **遅延結果の隔離**: キャンセル、追加指示、権限失効の後に遅れて届いた結果は、元のアクション試行やタスク履歴にのみ記録し、過去の承認を勝手に復活させたり、新しい目標の達成として採用したり、後続処理を自動開始したりしないこと。
- **リトライ**: 新しいアクション試行IDを発行して実行し、重複実行のリスクをユーザーに提示すること。別ルートを使ってこっそり再実行するような迂回を行わないこと。
- **キャンセル**: 要求の受付と実際の停止完了を明確に区別し、停止できなかった外部作用や成否不明な状態を正直に記録・報告すること。AIモデルの正常終了を待たずに即座に応答すること。
- **ホスト再起動**: 中断されたタスクは、保存済みの進捗や成否不明な状態を示してユーザーの明示的な再開指示を待つこと。成否不明な外部作用を勝手に自動再実行しないこと。
- **タスクエージェントへの委任**: 委任元の親が持たない権限を勝手に付与せず、独立したAPIキー、独立したコスト上限、独自の長期人格などを持たせないこと。

### 9.3 個人データ完全削除（Targeted Deletion）

- **削除中の再到着**: 削除処理の実行中に再到着・再生成された対象データも消去条件（`ErasureConditionRef`）によって確実に捕捉し、消去対象とすること。
- **遅延再保存の防止**: 削除前の古い情報を参照している実行中処理による再保存をブロックし、過去の根拠データだけで自動再学習を行わないこと。検証が終わる前に完了と表示しないこと。
- **再起動時の保全**: 削除が未完了のまま再起動した場合でも、保留状態と消去条件を維持し、再起動したことだけを理由に完了したと誤認して保留を解除しないこと。
- **削除完了後**: 完了後にユーザーが新たに提供した情報は新しい体験として受け入れ、過去のバックアップからの復元は別操作として事前の説明と確認を経ること。キャッシュや古いセッションから削除されたはずのデータが勝手に復活しないこと。

### 9.4 端末間の移動と滞在（Client Presence Transition）

- **端末移動**: 切り替え期間中は新旧どちらの端末でも新規処理を開始せず、移動元の処理は安全な区切りまで完了させ、2台の端末で同時にアクティブになる事故を防ぎ、未終了の外部作用を別端末へ勝手に引き継がないこと。
- **会話ラウンド**: 古い入力は元のラウンド、新しい入力は移動後の新ラウンドに紐付け、未提示の出力は次端末向けの要約報告へと安全に引き継ぐこと。画面へ送信したことだけを理由に報告完了とみなさないこと。
- **古い端末メッセージの隔離**: ホスト側の正規の滞在記録と端末側の主張を照合し、世代番号（`PresenceGeneration`）を用いて古い世代のメッセージによる新規処理の開始をブロックすること。確認が取れない状態を現在有効と推定しないこと。
- **Computer Use**: 現在アクティブな端末でのみ実行を許可し、移動時は安全な区切りまで移動を待機させ、切断時は可能な限り停止を試みて成否不明を残し、別端末やホスト側で勝手に再実行しないこと。

### 9.5 バックアップと復元（Backup / Restore）

- **復元前後の実行結果の混同防止**: 復元前に開始された古い処理結果が復元後の新しいデータベースに混入することを防ぎ、用途ごとに厳格に照合すること。古い権限や古い通信経路を勝手に現在有効とみなさないこと。
- **旧環境の安全な隔離**: `RestoreGeneration` を用いて古い世代の参照による自動処理を阻止し、復元後は一旦保留状態としてユーザーによる一括有効化を待つこと。復元が完了したことだけを理由に外部処理を勝手に自動再開しないこと。
- **認証情報**: 最新の認証情報ストアを維持し、バックアップから古いAPIキーを復元して巻き戻さないこと。不足している場合はユーザーに再認証を求めること。

### 9.6 全サブシステム共通

- 個体、キャラクター、作業、学習、接続、入出力、観測、推論、実行、権限、秘密、保全の各担当機能が、本設計の型を用いて正しく対応関係を維持できること。各機能の判断責任をIDや関連付けが勝手に代行しないこと。
- 通常の忘却、会話履歴の整理、容量上限による保持終了、コンパニオンの削除、個人データ完全削除、設定初期化（Reset）を混同せず、明確に区別して制御すること。
- 画面表示、監査ログの記録、障害復旧の処理によって、結果の確定度を勝手に強めないこと（成否不明を成功とみなさないこと）。思考プロセス（CoT）や生の音声を不要に永続保存しないこと。

## 10. 意図的に残した設計の自由度（Design Freedom）

本設計では、システムの信頼性とセキュリティを守るための対応関係を厳格に固定する一方で、実装の詳細については将来の改善や技術選定の柔軟性を確保するため、意図的に自由度を残しています。

- クレート、モジュール、プロセス、サービス、スレッドの物理的な分割と配置。
- 使用するデータベース製品、テーブルスキーマ、インデックス設計、リポジトリパターンの分割、トランザクションやロックの具体的な実装方式。
- プロセス間通信、キュー、イベント通知、チャンネルの種類と各種パラメータ（リトライ回数、タイムアウト秒数など）。
- ID生成器の実装詳細（UUID v4 または v7 の選定、採番主体の配置など。衝突しない一意性、再利用禁止、AI非依存の原則は維持します）。
- コンテンツダイジェスト（ハッシュ値）の有無やアルゴリズム（リビジョンの代わりにはしない範囲で任意）。
- タスク化の判定基準や分類アルゴリズム、要約の粒度、埋め込みベクトルの計算方式、キャッシュキーの設計、プロンプトの組み立て手順。
- バックアップファイルの暗号化方式、復元手順、サンドボックスの具体的な分離技術、UIレイアウト、3Dレンダラーの実装方式。
- 未伝達メッセージの保持方式、タスク記録の内部保持形式、端末移動の検知アルゴリズム、画面監視のルーティング文脈の生成方式や頻度。

これらはホストPCとクライアント端末の信頼境界、および各機能の責任分担を遵守した上で、最もシンプルで信頼性の高い実装手法を選択します。
