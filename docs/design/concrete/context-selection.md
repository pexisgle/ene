# Context Selection / Continuity — 会話とTaskの文脈選択

このドキュメントは、[プロンプト文脈の組み立て（context-assembly.md）](../critical-areas/context-assembly.md) で定めた「用途限定」「参照の正確さ」「データ加工のルール」「文脈不足への対処」「現在性の保証」という基本原則を、**日々変化する会話や長時間のタスクにおいてどのように具体化するか**をまとめた設計仕様書です。
上位の設計文書との優先関係は [設計文書 README](../README.md) に従います。また、[パートナー・タスク・学習サブシステム（companion-task-learning.md）](../subsystems/companion-task-learning.md)、[インターフェース境界（interface-boundaries.md）](interface-boundaries.md)、[データ永続化と復旧（persistence-recovery.md）](persistence-recovery.md)、[並行処理制御（concurrency-control.md）](concurrency-control.md) で定義された既存の責任範囲やデータ分類をそのまま活用します。新しいサブシステムや、知識を管理する別の独立データベース、巨大な共通コンテキスト管理マネージャーなどを勝手に新設することはありません。

## 1. 採用判断

ene が採用するのは、**「処理の目的ごとにトークン予算を設定して必要な文脈を選び出し、必要が生じたときに元の記録（会話履歴など）からピンポイントで取得し直す方式」**です。
Codex などの実験的な外部コンテキスト管理機能にそのまま依存したり、会話の全体像をすべてAIモデル任せのメモ（notes）に委ねてしまうような方式は採用しません。設計上の構造的な美しさと、実際に測定して確かめるべき応答品質や利用コストの改善を明確に区別して判断します。

| 検討した選択肢 | メリット | ene における制約と判断 |
|---|---|---|
| **長い過去ログを毎回すべてプロンプトに含める** | 直前の会話の流れやニュアンスをそのまま維持しやすい。 | コンテキスト長が肥大化し、コストと応答遅延が増え続け、いずれモデルの上限に達します。予算枠内での比較用ベースラインとしては有用ですが、無制限な全件送信は採用しません。 |
| **ひとつの要約文を毎回繰り返し更新し続ける** | 少ない文脈消費（低トークン）で会話を長く継続できる。 | 要約を重ねるうちに重要な情報が抜け落ちたり、過去の誤った解釈が後の要約に固定化してしまう危険があります。特定目的のための補助的な圧縮としては使えても、正式な会話履歴や最新の記憶の代わりにはしません。 |
| **モデル自身にメモ（notes）を管理させ、文脈窓がいっぱいになったら丸ごとリセットする** | 作業の途中で必要な情報だけをモデル自身が選んで次の窓へ引き継げる。 | 何を保存し何を読み戻すかの判断をモデルの性能やツール呼び出し能力に過度に依存し、障害時の復旧も難しくなります。日常会話の標準方式としては採用せず、タスクの文脈圧縮としてもこれ単一には固定しません。 |
| **作業中状態（Working State）やエピソード記憶を新しい専用の永続化領域として新設する** | 現在の話題や未完了タスクを専用の枠組みで明示できる。 | 既存の長期記憶（Memory）やタスク文脈との重複が生じ、話題の切れ目の誤判定や、データ削除・更新の管理責任が複雑化します。必須の共通基盤としては採用しません。 |
| **直近の会話履歴と最新の記憶をベースに選び、必要に応じて元の記録から補う（採用方針）** | 既存の責任構造を崩さず、話題の変更や「さっきの話題に戻る」といった自然な流れを同一の仕組みで扱える。 | 検索漏れや古い情報の混入、追加取得による応答遅延を適切にコントロールする必要があります。ene ではこれを基本方針として採用します。 |

> [!NOTE]
> この選定は「新しい方式の方が絶対に高精度で低コストである」と盲信したものではありません。補助的な継続ヒントやインデックスの追加は、第7節の比較検証において明確な効果が確認できた場合にのみ採用し、効果が薄い場合はシンプルな基本経路を維持します。

## 2. 所有と時間軸

システム内で扱う時間軸やデータのまとまりについて、以下の3つを明確に区別します：
1. **ユーザーに見せる一続きのタイムライン**（日々の自然な会話の流れ）
2. **経験の要約（Experience Summary）としての意味的なまとまり**（記憶として定着させる単位）
3. **AIモデルへの1回の推論リクエストに載せる文脈範囲**（トークン予算に合わせた一時的な切り出し）

ユーザーの話題が変わったこと、モデルのトークン上限に近づいたこと、会話のひと区切り（round）が終わったことのいずれも、それ単体では「会話の終了」「タスクの完了」「覚えたことの忘却」を意味しません。システム内部で話題の分類を行う場合でも、「現在のアクティブな話題はこれ1つだけ」といった排他的な決めつけは行わず、複数の話題が入り混じった状態や、過去の飛び飛びの履歴からの参照を柔軟に扱えるようにします。

通常の会話における文脈選択は「個体調整機能」が、タスクにおける文脈選択は「作業機能」が担当し、各データの正式な管理者から必要な情報の提供を受けます。長期記憶（Memory）は最新の知識と時間的な意味を保持し、要約は形成の根拠を保持し、関係性（Relationship）や個体状態（Companion State）はパートナーの内的な状態を保持します。「この情報は一時的なものだから」という理由だけで、長期記憶から別の怪しい保存場所へ勝手にデータを移してはいけません。

会話の継続ヒント（hint）を利用する場合、それは個体調整機能が一時的に生成する派生データとして扱い、現在の話題、未解決の参照先、なぜその情報を選んだのかという簡単な手がかり程度に留めます。「元の発言やタスクの指示を消してしまっても、ヒントさえ残っていれば大丈夫」というような歪んだ構造にしてはいけません。タスクのチェックポイントも、既存のタスクコンテキストから再開するための表現にすぎず、独立した別の学習データではありません。また、ヒントや検索結果を読み返したこと自体を、新しい体験や同じ事実を裏付ける独立した根拠として扱ってはいけません。

ヒントの省略、再生成、キャッシュの破棄は、元の会話履歴や長期記憶、タスク記録を削除・変更することではありません。逆に、ユーザーによって元データが削除・訂正された場合、古いヒントを使って勝手にデータを復活させてはいけません。

## 3. 変化する会話の選択と再参照

### 3.1 現在の入力を起点にする

日常会話では、各ターンの「現在のユーザー入力」「直近の生の会話履歴」「利用可能な最新の長期記憶」などを起点として必要な文脈を組み立てます。
相づち、代名詞（「それ」「あれ」）、比較（「前より良くなった」など）を正しく理解するためには、直近の生のやり取りが最も重要です。単なるキーワード検索の結果だけで直近の会話を置き換えてはいけません。固定のメッセージ件数やメモリ件数は読み取り量の上限枠としては使えますが、本当に必要な文脈が揃っているかどうかの保証にはなりません。

「話題A → 話題B → 再び話題Aへ戻る」という自然な会話において、話題Bに移ったことだけを理由に話題Aの未完了タスクを勝手に破棄してはいけません。また、話題Bを話している間中、話題Aの全履歴をプロンプトに常時注入し続けるような無駄なことも行いません。「さっきの件」といった曖昧な指示は直近の履歴と関連候補から推測し、どうしても特定できなければユーザーに自然に確認します。日常の短い雑談を、無理やり「タスクの目的」「進捗率」「ネクストアクション」といった堅苦しい形式に変換してはいけません。

訂正や状況の変化については、過去に記憶した内容と直近のユーザー入力を明確に区別します。長期記憶の更新処理がバックグラウンドで完了する前であっても、直近の会話で行われた新しい発言や訂正は、その場の返答に即座に反映できるようにします。ただし、「新しい発言だから絶対にすべて真実である」「引用された発言だから無条件に従わなければならない」といった極端な決めつけは行いません。

「明日」「来週」といった相対的な時間表現は、それが発言された当時の日時とタイムゾーンをもとに解釈し、後からログを読み返した時点の日時で勝手に解釈し直してはいけません。話題からしばらく離れていたことやホストの再起動を、予定が完了した証拠として誤認してはいけません。

### 3.2 原記録を必要な範囲だけ読む

必要な情報の所在（メッセージIDやリファレンス）があらかじめ分かっている場合は、直接その記録を取得することを優先します。所在が分からない場合は、現在の目的に対してアクセス権のある範囲を検索し、ヒットした元の記録を読み取ります。
本文の文字列が一致していることだけで「同じ発言だ」と安易に同一視してはいけません。同一の記録を重複してプロンプトに注入しないよう制御し、現在のユーザー入力は一度だけ含めます。ただし、長期記憶（確定した事実）とその根拠となった元発言のように、意味付けが異なるデータは、たとえ文章が似ていても混同してはいけません。

検索結果はあくまで「関連する情報がどこにあるか」の手がかりにすぎず、それ自体が確定した真実ではありません。元の記録の発話者、発言日時、どの会話空間での発言かといった文脈を保持し、現在の認識について回答する場合は、その後に訂正や変更がなかったかを必ず確認します。「当時どうだったか」を説明する際には当時の有効性を維持し、現在の状況を尋ねられているのに古い記録だけを答えるような間違いを防ぎます。

日本語の表現の揺れや言い換え、過去の話題への再訪は、完全一致のキーワード検索だけでは捉えきれません。検索の仕組みはひとつに固定せず、必要に応じて意味検索（セマンティック検索）などの導入効果を検証します。インデックス作成の遅延、検索の失敗、保存期間の終了、権限による閲覧制限によってデータが見つからなかった場合は、「そんな事実は存在しなかった」と混同せず区別して扱います。

文脈の検索と本文の取得の両方において、現在の利用目的、会話空間、コンパニオン、タスク、共有スコープ、送信同意を厳格に適用します。全体共有の記憶や同一ワークスペースを理由に、プライベートな会話履歴を勝手に取得してはいけません。また、過去の会話履歴から読み出したテキストであっても、それをユーザーからの正式な管理操作や権限の付与へ勝手に昇格させてはいけません。

## 4. 予算、応答性、Provider適応

トークンの予算管理は、メッセージの件数だけでなく、**「AIプロバイダへ最終的に送信するリクエスト全体」**に対して適用します。
現在使用しているモデルの入力枠の上限、返答生成に必要な出力枠、システム指示（instructions）、ツール定義（schema）、画像や音声データのトークン消費量を、各プロバイダの計算方式に合わせて考慮します。文字数、バイト数、トークン数はそれぞれ異なる単位であり、文字数制限や通信サイズの上限も独立して遵守します。

トークン予算を配分する際は、「現在のユーザー入力」「その解釈に必要な直近のやり取り」「安全性・目的に不可欠な指示」の枠を最優先で確保し、残りの余裕枠に過去の背景情報を割り当てます。不要な背景情報は、文章の意味が壊れない適切な単位で縮小します。ツール呼び出しと結果の対応関係や、肯定・否定・訂正の文脈を途中で乱暴に寸断してはいけません。どうしても必要な情報が枠内に収まらない場合は、末尾を黙って切り捨てるのではなく、「文脈が不足している」として安全に処理します。

トークナイザーやモデルの上限が正確に分からない場合は、安全側に倒した保守的な上限値を使用します。「厳密に計算できた」と偽って上限ギリギリを攻めることはしません。モデルやプロバイダを切り替える際は、トークン予算や表現力を再評価します。

通常の会話のたびに、話題の分類やヒントの更新、検索計画のために余計なLLM呼び出しを強制してはいけません。会話の応答速度を最優先とし、過去の記録の検索が必要不可欠な場合にのみ取得を待つか、情報が不足している旨を伝えます。音声会話（Voice）では、確定した発話とユーザーへの提示状況を正確に対応させ、聞き取り途中の未確定データや未提示の返答を会話の既成事実にしてはいけません。

追加の検索や情報取得を行う場合でも、1回のリクエスト内での試行回数、累積トークン量、所要時間、費用の安全上限を設定します。進展のない検索や要約のループを防止し、背景情報の取得に失敗した場合は安全に機能を縮小し、不可欠な根拠の取得に失敗した場合は処理を保留します。

プロンプトキャッシュ（Prompt Caching）は、同一の論理的な文脈を効率よく送信するための最適化としてのみ利用します。キャッシュヒット率を上げたいからといって、ユーザーからの訂正や最新時刻の反映、権限変更の適用を遅らせてはいけません。

## 5. 長時間Taskの文脈縮小

長時間のタスクは日常会話と異なり、複数のステップやツール実行結果の蓄積によって、プロンプトのサイズが急速に増大します。
文脈を圧縮する必要が生じた場合、不要な情報の切り捨て、目的に応じた要約、チェックポイントからの再構成などを比較検討し、特定の圧縮方式をシステム全体に画一的に強制することはしません。特にセキュリティや権限に関わる安全判断の根拠を、曖昧な要約や想起に頼ってはいけません。

コンテキストウィンドウを切り替える（リセットする）場合、タスクの担当機能は、切り替え後も必要となる「確定した目標」「追加指示」「進捗状況」「未完了タスク」と、それらの元記録への参照関係を確実に永続化します。すでに実行された外部作用や、成否不明なツール結果は、元のアクション履歴に正しく紐付けます。手元に保存されていない詳細データや、すでに変更されてしまった外部ファイルの内容を、「当時のまま復元できるはずだ」と過信してはいけません。

文脈を切り替える前に、後続の処理が必要とする継続記録を確実にディスクへ永続化（durable）します。保存に失敗したり参照が失われた場合は、必要な情報を欠落させたまま次のアクションへ進んではいけません。安全に継続できない場合は処理を保留します。

追加指示やキャンセルが文脈切り替えと競合した場合でも、古いチェックポイントで勝手に状態を巻き戻してはいけません。また、結果が不明なツール呼び出しを勝手に自動再実行してはいけません。ホスト再起動後のタスク再開は、ユーザーからの明示的な指示を待つ原則を崩さず、チェックポイントが存在することだけを理由に勝手にバックグラウンドで再開してはいけません。

## 6. 保持と消去への参加

新しく生成されたヒント、検索結果のキャッシュ、部分的な読み取りデータ、チェックポイントなどを保持するコンポーネントは、すべて [個人データ完全削除（targeted-deletion.md）](../critical-areas/targeted-deletion.md) の対象範囲に正しく参加します。

プライバシー保護やセキュリティのための個人データ完全削除を、AIモデルによるメモの書き換えや要約、想起の抑制などでごまかしてはいけません。通常の会話履歴の保持期間が終了して削除された場合、それは「逐語的な参照ができなくなった」状態であり、それによって過去に形成された長期記憶まで自動的に連鎖削除されるわけではありません。また、外部のAIプロバイダ側のデータ保持を完全に消去できたと偽って表示してはいけません。

## 7. 導入順と検証

既存の [実装ロードマップ（docs/implementation/README.md）](../../implementation/README.md) は変更しません。
最初はトークン総量を確実に検査できる文脈選択と情報源の追跡を整え、必要に応じて過去の記録を安全に検索・取得できる仕組みを繋ぎます。タスクの文脈継続は、タスク機能とツール実行ループが確立された段階で追加します。専用の巨大なファイルシステムや、常時稼働する話題分類エージェントなどをいきなり先行して作り込んではいけません。

会話ヒントや高度な検索機能は、直近の会話履歴と既存の長期記憶だけでは対応できない具体的な課題を確認した上で追加します。

| 検証シナリオ | 確認すべきポイント |
|---|---|
| **複数の話題の交錯・過去の話題への再訪・短い相槌** | 最新の話題だけに無理に固定されたり、無関係になった古い話題が常時注入されたりせず、直前の自然な文脈を正しく捉えられること。 |
| **ユーザーからの訂正・予定変更・日付を跨いだ会話** | 長期記憶の更新前後の食い違い、遅れて届いたヒント、相対的な時間表現において、現在と過去の事実を混同しないこと。 |
| **同一発言の再送・日本語の言い換え** | 単なる文字列の完全一致に頼らず、発言の識別性を保ちながら適切に意味を理解できること。 |
| **過去の正確な引用・省略・保持期間終了** | 引用は実際に取得できた原文からのみ行い、手元にない情報を勝手な想像で捏造しないこと。 |
| **プライベートな会話・グループ会話・共有タスク** | テキスト本文だけでなく情報の所在情報に対してもアクセス制限を適用し、私的な会話が漏洩しないこと。 |
| **引用された指示文・画面に映り込んだプロンプト** | 外部コンテンツや過去ログに含まれる指示を、ユーザーからの新たな管理権限や命令として勝手に昇格させないこと。 |
| **長大な入力・巨大なツール結果・小さなモデルへの切替** | トークン予算の上限、必須情報の維持、枠内に収まらない場合の安全なエラー処理が正しく動作すること。 |
| **ヒントの生成失敗・検索障害・音声の中断** | 任意の背景情報の失敗であれば安全に縮退し、必須情報の失敗であれば処理を保留すること。補助的な処理の失敗で会話全体を止めないこと。 |
| **チェックポイント保存失敗・キャンセル競合・成否不明** | 古い指示のまま処理を続けたり、二重実行したりしないこと。再起動時はユーザーの明示的な再開指示を待つこと。 |
| **認証情報の更新・個人データ完全削除・再接続** | 派生データやプロバイダの古いセッションを通じて、削除されたはずのデータや古い認証情報が再露出しないこと。 |

品質や応答速度の評価は、同一の入力条件・モデル・予算設定のもとで、ベースライン（直近履歴＋長期記憶）との比較を厳密に行います。測定を行う前に「〇〇%高速化」「コスト大幅削減」といった根拠のない主張をしてはいけません。明確な改善効果が確認できない過度な最適化や追加インデックスは採用しません。
