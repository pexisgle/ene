# 個人データの完全削除（Targeted Deletion） — 全域成立と再出現防止の詳細設計

ユーザーがプライバシー保護やセキュリティのために「特定の情報そのものを完全に消去してほしい」と明示した際、Eneの内部システム（ストレージ保存、派生データ、メモリ、処理中の一時データ、再利用キャッシュなど）のどこにあっても確実に消去し、古いコピー・遅れて届いた推論結果・再接続してきたクライアント端末・再起動・バックアップからの復元などによって**絶対に復活させない**ための論理的な設計仕様を定めます。
本ドキュメントは後続の実装設計が安全に依存できる共通ルールを明確に定義し、個々の具体的なアルゴリズムや実装方式には自由度を残します。

## 1. 解決すべき課題と本ドキュメントの適用範囲

「個人データの完全削除（Targeted Deletion）」を単に「データベースから対象レコードをDELETE文で消すだけの処理」と考えてしまうと、システム全体としての完全な消去が達成できません。
後続の実装設計で陥りやすい誤りと、本ドキュメントが定める明確なルールは以下のとおりです。

| 陥りやすい誤り（アンチパターン） | 本ドキュメントが定めるルール |
|---|---|
| マスターのデータベースだけ消して完了とし、派生データや処理中の一時メモリ、遅れて届く推論結果を放置してしまう。 | 追跡・識別すべき対象の範囲を明確にし、既知の派生データや依存関係を漏れなく追跡して消去します。 |
| 実行中のタスク、推論、外部ツール呼び出しと消去が同時に起きた際、単なる到着順や1つのフラグだけで適当に処理してしまう。 | 対象データを含む新規処理の開始を直ちに禁止し、進行中の処理は安全に縮小・停止させ、各機能がデータを受け取る段階で消去ルールを厳密に照合します。 |
| 局所的にデータを削除した後に、古いプロンプト、キャッシュ、端末側の一時コピーからデータが戻ってきたのを「新しい経験」として勝手に再登録してしまう。 | 消去処理の開始から完了までの間に新しく届いたり生成されたデータも消去対象とし、「過去の由来」と「ユーザーによる新規提供」を厳密に区別して復活を防ぎます。 |
| クライアント端末の切断、Hostサービスの再起動、バックアップからの復元を跨ぐと、未完了の消去タスクや再保存防止ルールが消えてしまう。 | 消去の未完了状態や再保存防止の制約はHost側で確実に永続化し保全します。クライアント側のデータは正本とはみなしません。 |
| 1つのデータベースで削除が成功したことや、LLMが「忘れました」と返答したことだけで「システム全体の消去が完了した」とみなしてしまう。 | 各機能での「局所的な完了」と「システム全体の全域完了」を明確に分け、通信不能や検証失敗がある状態では完了とみなしません。 |
| 実行履歴や監査ログ、ユーザーへの完了報告メッセージの中に対象の秘密データや個人データをそのまま残してしまう。 | 「記録として残すべき客観的事実」と「消去しなければならない対象本文」を厳密に区別します。 |

本ドキュメントが扱う範囲は、消去要求の識別、対象データの追跡・特定、既存各機能の参加範囲、実行中タスクとの競合制御、データの再保存防止、再起動や復元を跨ぐ状態保全、全域完了の判定条件、および「事実の記録と本文の消去の分離」です。
なお、プロンプト生成やAIプロバイダ適応の一般契約は [Context Assembly](context-assembly.md) を、ツール実行や成否判定の一般契約は [Action Execution](action-execution.md) の取り決めをそのまま適用します。

本機能（Targeted Deletion）は、通常の記憶の忘却（忘却曲線）、情報の訂正、期限切れ、要約統合、通常の会話ログ削除、キャラクター自体の削除、システム初期化（Reset）とは**全く目的が異なるセキュリティ／プライバシー操作**です。共通の削除処理部品を利用できる場合であっても、この本質的な目的の違いを混同してはなりません。

## 2. 上位アーキテクチャとの位置関係

上位アーキテクチャ設計との優先順位は [設計文書 README](../README.md#正本と優先順位) に従います（SOは [State Ownership](../architecture/state-ownership.md)、DRは [Dependency Rules](../architecture/dependency-rules.md) の節番号を指します）。
本ドキュメントでは、全体を統括するような巨大な「万能消去マネージャー」や「単一の消去ステートマシン」を新設することはしません。既存の各コンポーネントが自身の責任範囲で消去に参加します。

| 本ドキュメント内での役割 | 各コンポーネントの正規の責任と判断 | 本ドキュメントが持ってはいけない権限（越権の禁止） |
|---|---|---|
| **消去の目的・対象の確定** | データ保全・消去機能が、ユーザーの明示的なプライバシー／セキュリティ目的、対象範囲、影響、除外事項を確定します。 | メモリの重要度、キャラクターとの関係性（Relationship）、タスクの成否などを勝手に再判定すること。 |
| **対象の意味的な特定の支援** | キャラクター管理や認識・学習機能が、データの由来や文脈を解釈して探索を補助します。 | 機械的な検索・除去・残存検証の代わりとして、LLMの「忘れました」「要約しました」という返答を採用すること。 |
| **各領域での削除処理の実行** | 各機能のマスター（semantic owner）が、自身が保持・利用しているデータの削除、無効化、検証、保留を引き受けます。 | 他ドメインのデータを勝手に書き換えたり、通常のデータ意味論を変更すること。 |
| **利用時の強制チェック** | 権限・制約管理と各実行エンジンが、データの参照・送信・保存・画面表示・アクション実行の直前に消去ルールを適用します。 | コンテキストの都合だけで消去制限を解除したり、権限スコープを勝手に自己変更すること。 |
| **実行事実の正確な把握** | ツール実行エンジンがアクションの確定度、タスク管理が進行状況、キャラクター管理が報告状況を管理します。 | 消去を理由に確定度を「未実行」などに改ざんしたり、外部で起きてしまった変更を巻き戻せたと錯覚すること。 |
| **認証情報（シークレット）の扱い** | 認証情報ストアが、登録済み認証情報の用途・有効性を管理します。 | 内部で漏洩した認証情報の消去を理由に、外部サービスの認証情報まで自動失効・更新させること。 |
| **システム全体の完了調整** | データ保全・消去機能が、各機能の局所的な完了、検証結果、未完了状態を集約して「全域完了」を判定します。 | 全ドメインの通常書き込み権限を持ったり、単一トランザクションで内部全構造に無制限アクセスすること。 |

## 3. 消去要求の識別と対象データの追跡

### 3.1 消去要求の同一性と前提条件

個人データの完全削除は、単に「削除」という一言で済むものではなく、プライバシーやセキュリティを守るための厳格なシステム全域操作です。すべての消去要求は、以下の情報と明確に対応付けられていなければなりません（途中で対応関係を喪失した要求を全域操作へ進めてはなりません）。

- **明確な目的の確認**: ユーザーによる明示的なプライバシー／セキュリティ上の要請であること。単なる「忘れてほしい」「話を変えよう」といった日常会話の表現だけで本操作を発動してはなりません。
- **対象の記述と影響説明**: 消去対象が何であるか（第3.2節）を特定し、それに伴う影響やユーザー確認事項を明確にします（どのテーブルを消すかなどの内部構造をユーザーに選ばせてはなりません）。
- **消去区間の定義**: 消去処理の開始から全域完了までの論理的な時間枠（消去区間）を定めます。この区間内に新しく届いたり生成された対象データも、同じ消去対象として取り込むためです。
- **完了後の新規提供との境界**: 消去が完全に完了した後に、ユーザーが改めて自発的に提供した入力は「新しい経験」として受け入れられるように、境界を明確にします（第6.2節）。
- **状態の集約先**: どの調整役（coordinator）が全体の進捗や未完了状態を管理しているかを明確にします。

「過去にどのような消去要求を受け付けたかの記録（監査・説明用）」と、「今この瞬間に各機能で適用すべき消去条件」は別物です。過去の記録をそのまま流用して現在条件として扱ってはなりません。処理を開始する直前には、現在の権限や保留状態と照合し、前提条件の変化を見落とさないようにします。

### 3.2 対象記述の2つの層（機械的条件と意味的条件）

消去対象の指定は、「機械的条件」と「意味的条件」の2層から構成されます。

- **機械的条件（必須・LLM非依存）**:
  ユーザーが指定した特定の文字列について、システム全域での完全一致検索、物理削除、および残存確認（grep的な検証）を行う条件です。これは全域完了の絶対条件であり、LLMの「要約」や「忘却表現」で代替することは絶対にできません。推論モデルがダウンしていたりトークン費用が不足していても、この機械的な削除と検証は独立して確実に実行します。
- **意味的条件（探索補助・完全性保証なし）**:
  言い換え表現や意味的に同一な情報を探し出すための補助条件です。LLMの推論を活用できますが、自然言語の意味的な完全検出までは保証できません。完全検出が難しいからといって、すでに判明している派生データや依存関係の追跡を放棄してはなりません。

意味的な探索に限界がある場合は、その検出限界をユーザーへ正直に説明します。「LLMでは完全に検知しきれなかった」ことを理由に、機械的な検索検証をサボったり、未確認の領域を勝手に「完了」とみなしてはなりません。意味的探索を行う補助推論に対しても、通常の利用同意やコスト上限を適用します。

消去対象の情報を各コンポーネントへ伝達する際に、保護すべき機密データの複製（コピー）を無駄に増やしてはなりません。「由来を記録するため」といって削除対象の本文や認証情報を別の場所にコピーして保存することは禁止です。

### 3.3 追跡すべき依存関係

本システムでは、単にデータが「どのテーブルにあるか」を一覧化するのではなく、「対象情報とどのような関係にあるか」を追跡します。本文そのものを保持せずとも、以下の関係性を追跡できるようにします。

- **元データ（source）や派生データとの関係**:
  どの会話履歴、要約、メモリ、スキル、タスク、検索インデックスが対象データから派生・依存しているか。複数の情報が混ざり合って分離できない派生データは、「対象データに依存している」と安全側に倒して判断します（「モデルが出力に含めていないと言ったから」という理由だけで依存関係を解除してはなりません）。
- **処理中の一時利用との関係**:
  現在どのプロンプト、推論リクエスト、タスクエージェント、ツール実行結果が対象データを利用中か、遅れて返ってくる可能性のある結果はどれかを把握します。
- **局所的な処理・検証状況との関係**:
  どのコンポーネントがどこまで削除・無効化・検証を完了したか、どこがまだ未確認かを追跡します。
- **再保存防止ルールとの関係**:
  データを受け取る各コンポーネントが、処理中のデータに対して消去ルールを現在も適用しているかを把握します。

既存のデータソースへの依存追跡だけでは、「消去処理中に外部から遅れて届いたデータ」を取りこぼす恐れがあります。そのため、データ受取口でのリアルタイムな消去チェック（第6節）と、指定文字列の機械的残存検証の両方を必須とし、片方だけで済ませてはなりません。

## 4. 各コンポーネントの参加範囲

### 4.1 参加の原則

各機能のマスター（semantic owner）は、自身が保持・利用しているすべてのデータ領域について完全削除処理に参加し、データ保全・消去機能がその全域完了を取りまとめます。
通常のマスターは正当な全域消去への参加を拒否することはできず、逆に取りまとめ役が他ドメインの内部データを好き勝手に改ざんすることもできません。

各マスターの参加責任には、対象データの削除、元データや根拠の無効化、派生データの除去、処理中リクエストや遅延結果の破棄、必要な保留状態の管理、および完了／未完了の正確な報告が含まれます。
**対象情報を復元できる内部データ、過去の根拠、派生データ、一時データ、処理中の利用を持つすべての機能は、ドキュメントに明記されているかどうかにかかわらず、必ず消去処理に参加しなければなりません。**

### 4.2 参加対象となる機能とデータ領域

| 保持・利用しているデータ領域 | 参加するコンポーネントの責任と対象範囲 | 根拠となる既存契約 |
|---|---|---|
| **会話履歴（1対1・グループ・キャラクター間交流）** | キャラクター管理が、元の会話ログから該当情報を削除または復元不能化します。キャラクター自体の削除では消さない過去ログであっても、個人データ完全削除では消去が優先されます。 | SO 4.3、DR 7.2、RF-07 |
| **非会話活動記録・過去ログ・エビデンス** | キャラクター管理が、認識結果・通知履歴・調査記録などから該当情報を削除します。「経緯の説明に必要だから」という理由で消去を拒否することはできません。 | SO 4.3、RF-07 |
| **未伝達メッセージと報告状況** | キャラクター管理が、端末不在時に残したメモや要約、未完了の報告から対象データが復元されないようにします。タスク記録への参照と表示用テキストを区別します。 | SO 4.4、Context 8.2 |
| **経験要約（Experience Summary）と根拠** | 認識・学習機能が、要約データおよび記憶形成の根拠から該当情報を削除します。無関係な情報は可能な限り切り離して残し、分離できない重大な影響はユーザーへ説明します。 | SO 4.5、CC-05 |
| **記憶（Memory）の現在認識と過去履歴** | 認識・学習機能が、現在の記憶内容および過去の変更履歴（revision）・参照根拠から対象を消去します。通常の忘却や統合では残すルールであっても、完全消去では消去が優先されます。 | SO 4.6、AD-07 |
| **内部スキル・学習済み改定・実行結果** | 認識・学習機能が、内部スキルの有効バージョン、過去の改定履歴、実行結果から対象を削除します。「スキルの原本だから」といって消去を免除されることはありません。 | SO 4.7 |
| **関係性（Relationship）の解釈と根拠** | 認識・学習機能が、ユーザーとの関係性に関する現在の解釈、過去の状態、根拠から対象を消去し、関係性のデータから秘密が復元されないようにします。 | SO 4.8 |
| **キャラクター個体状態（Companion State）** | 認識・学習機能が、対象データを直接または実質的に復元できる状態や根拠を消去します（無関係な基本性格までリセットする必要はありません）。 | SO 4.9 |
| **タスクの目的・進捗・作業コンテキスト** | タスク管理が、タスク記録、作業プロンプト、作業用に一時コピーしたソースコードや作業ファイルから対象を消去します。外部ファイルのコピーであっても内部にあれば消去します。 | SO 4.10・4.13、DR 7.2 |
| **一時エージェントの委任状態・遅延結果** | タスク管理が、サブエージェントへの委任内容や結果、終了後に残るタスク事実から対象を除去します。「一時エージェントが終了したから」だけで消去完了とみなしてはなりません。 | SO 4.11、Action 7.3 |
| **アクション実行状況・確定度・停止結果** | 実行エンジンが、把握した実行結果や確定度から対象本文を除去し、客観的な事実の記録と両立させます（第9節）。消去を理由に確定度を「未実行」に書き換えてはなりません。 | SO 4.12、Action 9 |
| **ワークスペース連携・中間ファイル** | タスク管理が、連携情報、内部キャッシュ、一時的な中間ファイルから対象を消去します。 | SO 4.13 |
| **定期スケジュール・到来履歴・各回タスク** | タスク管理が、スケジュール設定、実行履歴、生成された各回タスクから対象を消去します。見逃し（missed）記録を消去済みと混同してはなりません。 | SO 4.14 |
| **接続状態・端末一時データ** | 接続・プレゼンス管理がクライアントの切断や未確認状態を追跡し、入出力機能が表示用の一時データを消去します。クライアント端末が古い一時データを再接続時にHostへ戻すことは禁止です。 | SO 4.15・第8節、RT-08 |
| **画面観測・ルーティング候補・処理中利用** | 共有観測機能が、画面キャプチャ、ルーティング用の一時テキスト、処理中結果から対象を消去します。同意失効や消去は処理中の要約にも即座に適用されます。 | SO 4.16、Context 6 |
| **画面描画・音声バッファ・出力一時状態** | 入出力・提示機能が、画面表示バッファや音声合成バッファから対象を消去します。「すでにスピーカーから再生されたから」といって消去完了の証拠にはできません。 | SO 4.17 |
| **推論コンテキスト・キャッシュ・セッション** | 推論基盤および各利用元が、キャッシュ、Embeddingベクトル、検索結果、圧縮コンテキストから対象を消去します。過去の機密データが残る外部プロバイダのセッションは再利用を禁止します。 | SO 5.2、Context 5.2 |
| **検索インデックス・Embeddingベクトル** | 検索機能が、検索インデックスやベクトルデータから対象を消去します。インデックスが消えて検索精度が落ちたとしても、安全性を最優先します。 | SO 5.2、DR 4.1 |
| **権限判断・同意・利用上限の記録** | 権限・制約管理が、過去の判断履歴から対象を消去します。過去の「許可」のキャッシュを現在条件として再利用してはなりません。 | SO 4.19 |
| **利用量・トークン消費コストの記録** | 推論基盤が、消費実績から対象本文を除去しつつ、利用量の事実を残します。消去によってトークン消費実績をゼロにリセットしてはなりません。 | SO 4.20 |
| **漏洩した認証情報（Credential）のコピー** | 認証管理および各コンポーネントが、ログや会話履歴、デバッグ情報に誤って露出した認証情報のコピーを消去します。内部コピーの消去と外部サービスの失効手続きは別物です。 | SO 4.21、CC-02 |
| **外部プラグイン・MCP連携の一時データ** | 実行エンジンが、外部ツールから取得した結果や一時データから対象を消去します。「外部プラグインのデータだから」といって対象外にしてはなりません。 | SO 4.22、DR 6.2 |
| **監査ログ・診断情報・デバッグダンプ** | 保全・消去機能および各機能が、ログやダンプから対象データを消去します。完了報告や監査ログ自体に対象の個人データ本文を再保存してはなりません。 | SO 4.23 |
| **保持ポリシー・バックアップ設定・コピー** | 保全・消去機能が、バックアップ設定や内部コピーから該当情報を消去します。 | SO 4.24 |

Eneが直接管理している内部コピーは1つ残らず消去対象です。一方で、外部の作業ディレクトリ、ユーザー自身がローカルに保管している手動バックアップ、AIプロバイダ側のサーバーログなどの「外部データ」は内部消去の成功条件には含めません（内部を消去しただけで「外部のコピーも消えた」と虚偽の説明をしてはなりません）。

キャラクター自体の静的データは通常個人の経験データを含みませんが、万が一個人を特定できる情報が含まれる場合は同様に消去対象とします。参加先のドキュメント上の列挙漏れを「消去しなくてよい理由」にしてはなりません。

## 5. 実行中のタスク・推論・アクションとの競合制御

### 5.1 新規開始の禁止と進行中処理の安全な停止

消去処理が開始された対象データについて、システムは**新しい利用・保存・送信・画面表示・アクション実行を直ちに禁止**します。
この判定は、システム全体の単一フラグではなく、各実行箇所が現在の消去条件と照合して自律的に判断します（関係のない別の通常タスクまで巻き添えで全停止させる必要はありません）。

- **再保存の絶対防止**:
  消去前の古いデータを利用している実行中処理によって、削除されたはずのデータが再びストレージに書き込まれるのを防ぎます。削除や残存検証が完了していない段階で「消去完了」と表示してはなりません。
- **進行中処理のベストエフォート停止**:
  実行中のLLM推論、タスクエージェント、外部ツール呼び出しは、ベストエフォートで直ちに停止させるか、対象データを含まない範囲へと縮小します。停止できなかった処理や、すでに外部に起きてしまった影響、成否不明の状態は、正確に記録してユーザーへ報告します。外部プロセスの完全終了を待つあまり、消去の受付や新規開始の禁止が遅れてはなりません。
- **裏道での迂回禁止**:
  「停止処理を行うため」という名目で新しい未承認アクションを勝手に始めてはなりません。別のエージェントやクライアント端末を経由して消去制限をすり抜けることも禁止です。

バックグラウンド処理や定期スケジュールによる無人実行も同様です。消去処理中であることを理由に勝手に承認されたとみなして実行してはならず、ユーザー確認が必要なら停止して判断を待ちます。

### 5.2 各機能がデータを受け取る段階での消去チェック

外部推論やツールから遅れて届いた結果は、利用先となる各機能（マスター）が受け取る段階で、改めて現在の消去条件と照合します。
「後から届いたから」「最新のタイムスタンプだから」という理由だけで、新しい出来事とみなして採用してはなりません。

| 結果の利用先 | 消去条件のチェックと許可される動作 | 禁止される動作（アンチパターン） |
|---|---|---|
| **会話・ユーザーへの伝達** | キャラクター管理およびUI表示が、現在の消去状況と照合し、対象データを含まない安全な範囲でのみ画面表示します。 | 「モデルがテキストを生成した」＝「表示してよい」とみなすこと。過去の会話ターンへ勝手に出力すること。 |
| **タスクの進行・方向転換** | タスク管理が、現在の目的、委任範囲、消去状況と照合します。古い目的への回答を新しい目的の達成とみなしてはなりません。 | 遅れて届いた結果だからといって、無条件に「新しい経験」として受け入れること。 |
| **記憶（Memory）・要約の形成** | 認識・学習機能が、最新の認識、根拠、スコープ、消去状況と照合して採否を決めます。到着順が新しいからといって確実な根拠と過信しません。 | 古い根拠から自動的に記憶を再形成すること。タスクの作業データを無差別に永続記憶化すること。 |
| **権限・ルールの解釈** | 権限管理が、ユーザー本来の意図、対象リソース、消去状況と照合します。 | モデルが「実行してよい」と言ったことを権限昇格と誤認すること。消去条件を勝手に解除すること。 |
| **次のアクション候補** | 実行エンジンが、現在の実利用条件や消去による保留状態と照合します。 | コンテキストが有効だからといって、削除前の古い承認で新しいアクションを開始すること。 |
| **実行実績・コストの記録** | 各マスターが、元のアクションやリクエストと紐付けて事実を記録します。対象データの本文は決して再保存しません。 | 事実を記録できたことを「次のアクションも実行してよい」と誤認すること。「成否不明」を「未実行」と解釈すること。 |

タスクのキャンセルや同意の失効があった場合でも、「何が起きたか」という客観的な事実の記録まで禁止されるわけではありません。ただし、記録できたからといって次のアクションを実行してよいわけでもありません。必要事実の記録、処理停止の受付、機械的な残存検証は、外部タスクの完了を待たずに速やかに進めます。

ストリーミング出力や部分的な結果を受け取る場合も同様です。新しく保存・送信・表示・実行へ渡す部分ごとに消去条件を満たす必要があります。「未検証のまま先にユーザーへ見せてしまい、後から消去する」ような設計は認められません。

### 5.3 アクション結果の確定度（Outcome）の保持

個人データを消去したからといって、過去に実行されたツールの成否判定（確定度）を「成功」「失敗」「未実行」へ勝手に書き換えてはなりません。
実行エンジンが把握した「確認済み成功」「確認済み失敗」「成否不明」の区別と、その客観的な根拠をそのまま維持します。確定度を変更できるのは、事実のマスターが新しい客観的証拠を確認したときだけです。

- **事実の記録と本文消去の両立**:
  ツールを実行した事実の説明に対象データが関わっている場合、客観的な事実（実行した日時や対象ツールの種類など）は残しつつ、消去対象の個人データ本文のみを確実に除去します。「実行記録だから」という理由で個人データを残してはなりません。
- **「成否不明」を「未実行」にすり替えない**:
  ログの保存に失敗したからといって、勝手に「未実行だった」と都合よく推定してはなりません。
- **確定度を勝手に格上げしない**:
  ユーザーへの完了報告や管理画面において、未完了や成否不明のタスクを「成功」と偽ってはなりません。

タスク管理は、実行エンジンが把握した確定度を集約して参照します。タスク管理側が勝手に確定度を書き換えたり、エージェントの「成功しました」という自己申告を信じ込んで確定事実の代わりにしてはなりません。

### 5.4 LLMに依存しないセキュリティ境界の強制

特定の文字列に対する機械的な検索、物理削除、残存検証の処理を、**LLM（言語モデル）の推論に依存させてはなりません**。
LLMの「忘れました」「もう覚えていません」「重要ではないと判断しました」といった出力を、物理的なデータ削除や検証の代わりにすることは厳禁です。

意味的な類似情報の探索にLLMを利用する場合であっても、推論モデルがダウンしていたりトークン費用が不足しているときは、その旨の不足エラーを返せば十分です。LLMが動かないことを理由に、システム本来の停止・拒否・管理操作・機械的検証まで停止させてはなりません。

## 6. 再保存・再形成・再表示の防止

### 6.1 消去処理中に届いたデータの取り込み

消去処理が始まってから完了するまでの間に、外部モデルから遅れて届いたデータや内部で新しく生成されたデータも、**同じ消去対象として確実に除去**します。
「消去処理中に新しく届いたデータだから」といって、削除を免除して新しい経験として受け入れる例外は一切認めません（具体的なトランザクションやロックの方式は実装設計に委ねられます）。

データを受け取る各コンポーネントは、元データの追跡に加えて、現在進行中の消去条件をリアルタイムに適用します。指定文字列の機械的な検索・削除・残存確認を行い、局所的な削除の後に古いプロンプトや遅延結果、再接続してきたクライアント端末からデータが復活するのを防ぎます。

### 6.2 「過去の由来データ」と「完了後の新規提供」の明確な区別

消去処理が完全に完了した後に、ユーザーが改めて自発的に提供した入力は、正当な「新しい経験」として受け入れられます。同じ文字列の入力を永久に拒絶するような過剰な制限は設けません。
「過去の古いデータから復活した情報」と「新しくユーザーから提供された情報」は、単なる文字列の一致ではなく、**情報の由来と文脈（コンテキスト）**で厳密に区別します。

- **文脈情報の維持**:
  削除前の入力やタスク、エージェントへの委任、推論リクエストとの対応関係、どのクライアント端末で取得されたか、再起動や復元前の処理かといった文脈を確実に追跡します。
- **過去の処理結果の破棄**:
  削除前のデータを利用して動いていた推論、ツール結果、タスクエージェント結果、キャッシュ、外部プロバイダのセッション、クライアントの一時データから戻ってきたデータは、たとえ消去完了の後に届いたとしても「過去の古いデータ」として直ちに消去ルールに従わせます。「今届いたから新しいデータだ」と誤認してはなりません。
- **完了後の新規提供の受け入れ**:
  消去完了後にユーザーが改めて会話で入力した内容は、過去の記憶やインデックスに依存しない「新しい経験」として正常に記憶・学習されます。途中で文脈が途切れて正体不明になったデータは、現在の会話に無理やり繋ぎ込まず、受け入れ拒否とします。

過去の会話ログ、要約、インデックスから記憶を整理・統合するバックグラウンド処理においても、削除前の古い根拠だけを頼りに同じ記憶（Memory）や関係性（Relationship）、キャラクター個体状態（Companion State）を自動的に再生成してはなりません。

なお、ユーザー自身が過去の古いバックアップから明示的にシステムを復元（Restore）した際にデータが戻ることは、自動的な再形成とは異なる「ユーザー自身の明示的な操作」として正当に扱われます（第7.4節）。

### 6.3 キャッシュ・セッション・端末経路の再利用禁止

Eneが管理するキャッシュ、Embeddingベクトル、検索結果、圧縮コンテキストを再利用する際も、内容の一致だけでなく、元データのアクセス範囲、利用目的、現在性、消去状況を必ず確認します。「キャッシュにヒットしたから」といって安全確認を省略してはなりません。通常の保存期間終了で過去ログが消えた場合と、個人データの完全削除で消去された場合を厳密に区別し、後者のキャッシュを勝手に再利用することは禁止です。

外部AIプロバイダとの通信セッション内に過去のデータが残っている場合、そのデータも後続の生成に影響を与えます。消去対象データを含んでいるセッションに対しては、プロンプトを短くしただけで通信を続けてはならず、安全な新しいセッションへ切り替えます（プロバイダ側のサーバーログ消去までEneが保証できないことと、Eneがそのセッションを再利用してよいことは別問題です）。

クライアント端末からの直接送信やプラグイン通信も同様です。Hostの最新の消去状況を確認できないクライアントは処理を継続できず、端末側の一時データを正本にしてはなりません。端末が再接続してきた際に、過去の画面表示データや入力バッファをHostへ送り戻してデータを復活させることも禁止です。

### 6.4 共有根拠の安全な分離

1つの経験要約（Experience Summary）やデータソースが、消去対象データだけでなく「消去とは無関係な別の情報」の根拠にもなっている場合は、可能な限り対象データのみをピンポイントで切り離し、無関係な正常データまで巻き添えで削除しないようにします。どうしても分離できない場合は、削除による影響範囲をユーザーへ正直に提示して確認を取ります。

共有メモリ（Global Memory）の本文は利用できても、その背後にあるプライベートな根拠データは決して他者へ漏洩させません。要約データが共有されているからといって、元となった私的な会話履歴へのアクセス権まで全開放されたわけではありません。分離できない重大な影響がある場合は、黙ってデータを隠蔽したり、逆に無関係なデータを勝手に消去したりせず、ユーザーへの影響説明として正直に報告します。

## 7. 再起動・再接続・復元（Restore）を跨ぐ状態保全

### 7.1 Host側で確実に永続化・保全すべき性質

具体的なWAL（Write-Ahead Log）、トランザクション、ロック、分散プロトコルの方式は実装の自由度ですが、後続の実装は以下の重要な性質を確実に保全しなければなりません：

- **消去要求の文脈**: ユーザーの目的、対象の記述、影響範囲、除外事項、ユーザー確認の対応関係。
- **各機能の処理状況**: 各コンポーネントの削除・検証の成否、未完了・失敗・未確認の領域。
- **再保存防止の制約**: 対象データの利用や再保存を禁止するルール、その有効期間および完了境界。
- **状態の厳密な区別**: 局所的な完了とシステム全体の全域完了、処理中（pending）・通信不能（unreachable）・検証失敗（failed verification）の明確な区別。
- **環境変化に対する耐性**: Hostの再起動、端末の再接続、バックアップからの復元の後であっても、「消去がまだ未完了である」という事実や、必要な保留状態・再保存防止ルールを確実に維持すること。途中で再起動したからといって勝手に完了と誤認したり、保留を黙って解除してはなりません。
- **監査記録に本文を残さない**: 削除対象となった機密データや個人データの本文を「完了の証拠」として監査ログに残すような本末転倒な処理を行わないこと。

システム全体の未完了状態や再保存防止といった継続的に守るべき制約は、揮発しやすいクライアント端末や1回限りのプロセス任せにせず、**Hostサービス側で確実に永続化して保全**します。一時バッファがメモリから消えたことを「消去が成功・完了した証拠」と取り違えてはなりません。

なお、「再構築が可能であること」は、「すべての画面キャプチャや音声データ、推論思考プロセスの全文を永久保存せよ」という意味ではありません。通常は保存しない生データ（Raw ObservationやRaw Voice）を永久保存する口実にしてはなりません。

### 7.2 クライアント端末の切断と再接続

クライアント端末の通信切断や再接続、Hostの再起動、バックアップからの復元によって、未完了の消去タスクや再保存防止ルールが消えてしまってはなりません。
「通信できないこと」を都合よく「消去成功」と読み替えてはならず、一部の完了をもって全体完了とみなしてはなりません。

- **切断時の取り扱い**:
  消去処理中にクライアント端末が切断した場合、接続管理が「確認不能」として記録し、UI表示機能などが一時データの消去状況を報告します。通信が途絶えたことを「消去成功」とみなしてはなりません。
- **再接続時のデータ逆流防止**:
  切断したクライアント端末が再接続してきた際に、過去の画面キャッシュや入力履歴をHost側へ送り戻してデータを復活させることは禁止です。「クライアント側には長期的なプライベートキャッシュを持たせない」という基本原則を徹底します。
- **厳密な到達確認**:
  どのような手段で端末への到達性確認や無効化を行うかは実装設計の自由度ですが、必要な確認をスキップして完了にしてはなりません。
- **デバイス失効後の信頼回復**:
  デバイスの登録失効や全データ初期化（Reset）の後に、古いトークン等だけでHostの信頼関係を復活させてはならず、現在の接続と認証の成立を必ず再確認します。

通信が確認できない端末や外部処理を勝手に「成功」と決めつけず、かといって「端末からの完了報告が来るまで全体の処理が一切進まない」というデッドロックも避けます。各マスターは自身の局所的な結果を先に返しつつ、必要な保留と再保存防止は確実に維持します。

### 7.3 Hostサービスの再起動

Hostサービスが再起動した後は、永続化されているマスターデータ（正本）から、現在の目的に必要なコンテキストを改めて再構築します。キャッシュに残っていた古い派生データを再利用することは自由ですが、過去のリクエストに対する利用許可や実行処理をそのまま自動再開してはなりません。
- 途中だったタスクは、ユーザーからの明示的な再開指示を待ちます。
- 定期スケジュールは、将来の予定回として現在の条件で再評価します。
- 稼働中だったキャラクターは、元のクライアント端末への接続復旧という通常のルールに従います。

一部の機能で検証に失敗したり、途中でHostが再起動した場合、保全・消去機能は未完了の範囲と必要な保留状態をHost内に保持し続けます。再起動したからといって未完了の消去タスクを忘れてはならず、完了後も古い根拠からの自動再形成を防ぎます。Hostがシャットダウンしても、成否不明のアクションや未完了の全域操作は安全に保全し、「Hostが落ちたから外部ツールも同時に消滅しただろう」などと都合よく決めつけません。

### 7.4 バックアップ・復元（Restore）との交差

消去タスクが未完了の状態でバックアップを作成する場合、消去の制約を無視した「正常で即座に実行可能なバックアップ」を作ってはなりません（バックアップ作成を待機させるか、未完了状態の情報を含めてバックアップするかは実装の自由度です）。

- **フルバックアップの整合性**:
  単に各データベースのファイルをコピーしただけでバックアップ成功とみなしてはならず、対象時点の参照関係、必要な履歴、未完了の消去状態を正しく復元できる形で含めます。
- **復元時の認証情報と状態の孤立化**:
  バックアップから復元（Restore）する際、Host内に現在存在する認証情報ストアは維持し、それ以外の内部状態をバックアップの内容で置き換えます。復元前の実行中タスクやクライアント端末側の古いコピーが、復元後の新しいマスターデータへ混入しないようにします。
- **復元による情報復活の事前説明**:
  古いバックアップを復元すると、過去に削除した個人データや古いルール・同意・スケジュールがシステム内に戻る可能性があります。この旨を事前にユーザーへ分かりやすく説明し、了承を得た上で復元を実行します。ユーザーの明示的な指示による復元は、自動的な再形成の禁止ルールとは異なる正当な別操作です。
- **復元直後の自動実行の保留**:
  復元が完了した後であっても、タスク、定期スケジュール、外部連携による自動処理は一旦保留します。ユーザーが内容を確認し、納得した上で一括して有効化できるようにします。
- **現在の認証情報との照合**:
  バックアップデータに含まれる古い同意や設定だけで勝手に外部アクセスを再開してはなりません。現在の認証情報ストアと照合し、有効な認証情報が存在することを確認し、不足があれば再認証を求めます。

## 8. 全域完了の成立条件

### 8.1 「局所完了」と「システム全体の全域完了」の区別

個人データの完全削除において、単一のデータベースや1つの調整役の成功だけで「システム全体の消去が完了した」とみなしてはなりません。
後続の実装設計では、少なくとも以下の論理的な状態を明確に区別します：

- **局所完了（Local Completion）**:
  特定のコンポーネントが、自身の管理下にあるデータについて削除または復元不能化、保留・再保存防止ルールの適用、および範囲内の検証を完了した状態。局所完了したからといって、全体の消去が終わる前に保留を勝手に解除してはなりません。
- **処理中／通信不能（Pending / Unreachable）**:
  消去処理中にクライアント端末が切断したり、再起動が発生したことにより、一部の範囲で処理や検証がまだ確定していない状態。「通信できない」ことを「消去成功」とすり替えてはなりません。
- **検証失敗（Failed Verification）**:
  機械的な残存検索で対象文字列が見つかった、依存関係が解消できない、対象範囲が確定できない等の理由で、完了を確定できない状態。何が不足しているかを明確に示します。
- **全域完了（Global Completion）**:
  保全・消去機能が、すべての参加コンポーネントの局所完了、検証結果、未完了状態を取りまとめ、システム全域での完全消去が成立したと確定した状態（第8.2節の条件をすべて満たす必要があります）。

### 8.2 全域完了が認められる必須条件

システム全体の「全域完了」を宣言するためには、以下の**5つの条件すべて**を満たしていなければなりません（意味的な類似探索の限界と、機械的な文字列検証を混同してはなりません）。

1. **ユーザーへの説明と確認**: 対象範囲およびシステムへの重大な影響を事前にユーザーへ説明し、必要な確認を経ていること。無関係な共有データは可能な限り分離し、分離できない影響を正直に報告していること。
2. **全領域での物理削除・無効化**: 会話履歴、非会話の活動記録、未伝達メモ、要約データ、記憶（Memory）と改定履歴、関係性、キャラクター個体状態、スキル、タスク作業ファイル、画面観測データ、インデックス、Embedding、キャッシュ、推論プロンプト、監査ログ、接続中端末やプラグインの一時データなど、対象データを復元できるすべての内部データ領域から、データが完全に除去または復元不能化されていること（ドキュメントに記載のないデータ領域であっても同様です）。
3. **消去区間内の再到着・遅延結果の確実な排除**: 消去開始から完了までの間に新しく届いたり生成されたデータも消去対象として処理し、遅れて届いた推論やツール結果からの再保存、古い根拠からの自動再形成を完全に防止していること。
4. **機械的な残存検索と検証の成功**: 指定された文字列についてシステム内部のデータを機械的に検索し、完全に消滅していることを検証済みであること（LLMの「要約」や「忘却」で代用してはなりません）。
5. **未完了・失敗の完全な解消**: すべての参加コンポーネントの未完了や失敗が集約・解消されており、未確認の領域を残したまま全域完了にしていないこと。また、完了記録そのものに対象の個人データ本文を再保存していないこと。

完了の根拠は各コンポーネントの客観的な処理結果に基づくべきであり、LLMが「納得した」「忘れた」と言っているだけの要約で代用してはなりません。

### 8.3 「消去完了」扱いにしてはならない禁止ケース

以下のいずれかに該当する場合、システムは絶対に「消去完了」として扱ってはなりません：

- 一部のデータベースだけ削除が済み、他のキャッシュやクライアント端末からデータが復活するリスクが残っている場合。
- 端末の切断や再起動による「処理中／通信不能（Pending/Unreachable）」が残っており、安全の確認が取れていない場合。
- 機械的な残存検索に失敗した、または未実施であり、対象文字列が残っていないと言い切れない場合。
- 消去処理中に届いたデータの取り込み、遅れて届いた結果の再保存防止、古い根拠からの自動再形成防止のいずれかが不十分な場合。
- 「LLMでは意味的な類似表現を完全に検知しきれなかった」ことを理由に、本来追跡できるはずの派生データの消去をサボったり、未確認の領域を完了扱いにすり替える場合。
- 外部ワークスペースやユーザー自身の手動バックアップなど「外部データ」の消去を、内部完了の条件に混ぜてしまう場合（逆に、Eneが管理する内部コピーを外部扱いして消去から除外することも禁止です）。
- 完了記録や監査ログ、ユーザーへの報告文の中に対象の個人データ本文を残してしまい、完了記録自体がデータの復元源になってしまう場合。


## 9. 消去後も保持すべき「客観的事実」と、消去すべき「対象本文」の区別

システムの動作理由、失敗、停止できなかった処理、未保存のデータ、次の安全な選択肢などをユーザーへ説明する際は、AIの内部思考（CoT）や詳細なプロンプトをそのまま露出することなく、要点のみを分かりやすく説明します。
各機能は、主要なアクション実行、権限判断、外部ツール呼び出し、プロバイダ割り当て、認証情報参照、重要な設定変更、データ消去、初期化（Reset）、復元（Restore）について、必要な事実ログを記録します。保全・消去機能は監査ログ（Audit）の追記順序と保管期間を管理しますが、ログの記録順序を「現実世界で起きた厳密な時刻順」や「現在の権限許可」と混同してはなりません。

| 保持すべき「客観的事実」 | 保持してはならない「対象本文」（消去対象） |
|---|---|
| **消去操作の実行記録**: 消去操作が行われた日時、目的、対象範囲のメタ情報（本文を含まない識別子）、影響や除外事項、ユーザー確認を経たという事実。 | 削除されたプライベートな本文、復元可能な言い換え表現、対象文字列そのもの。完了記録や監査ログ自体がデータの復元源になってはなりません。 |
| **各コンポーネントの処理結果**: 各機能の削除・検証成否、未完了・失敗の有無、通信不能端末の有無、システム全体としての完了／未完了の別。 | 検証作業のために一時的に収集した対象本文のプロンプト等への集約。「検証のために参照できる」からといって、その本文を通常プロンプトや他キャラクター、外部へ送信する権限は生じません。 |
| **アクションの確定度と根拠**: 「確認済み成功」「確認済み失敗」「成否不明」の別、発生した外部影響、停止不能や未保存の事実。 | アクション履歴、タスク記録、監査ログの中に対象本文を残すこと。「事実の記録だから」を理由に対象本文を残す例外は認められません。 |
| **タスクの進捗状況**: タスクの進捗、達成状況、未完了状態、次の判断事項、タスク記録の存在と参照関係。 | タスクプロンプト、作業用コピー、タスク結果テキストの中に含まれる対象本文。 |
| **未伝達メッセージの管理状況**: ユーザーへまだ伝達できていない事項があるかどうかの管理状態。 | 伝達用の要約テキストやメモの中に含まれる対象本文。 |
| **セキュリティ制御の有効性**: 権限判断、同意状況、コスト消費実績などの制御ルールが現在有効であるかどうかの事実。 | 判断記録や監査文の中に対象本文を残すこと。また、過去のプロンプト内にあった許可文を悪用すること。 |
| **新規提供データの受け入れ事実**: 消去完了後にユーザーから新しく提供されたデータが「新しい経験」であるという対応関係。 | 削除前の古い根拠、過去の改定履歴、インデックスだけから記憶を自動的に復元すること。 |

「説明に必要な客観的事実」は安全に残しつつ、機密データの「裏の保管庫」を作ってはなりません。ログ出力元は不要な本文やパスワードを出力せず、記録側も秘密の別枠保存を行いません。監査ログには通常、会話の生テキスト、ファイル本文、シークレット値、消去済み個人データは含めません。

なお、ストレージ容量管理のための通常のログ保持期間短縮や会話履歴の削除は、個人データの完全削除（Targeted Deletion）とは区別されます。単に容量制限で古い会話ログが消えたからといって、すでに形成された長期記憶（Memory）、スキル、関係性（Relationship）、キャラクター状態（Companion State）まで連鎖的に消去することはありません（通常ログ整理の場合は、元のログが見えなくなっても形成済みの学習データを維持します）。

また、キャラクター自体の削除は「その個体固有の現在の状態や学習データ」を消去する操作であり、「過去にそのキャラクターが存在し、会話や作業を行った歴史的な事実」まで消す操作ではありません。ただし、その残された過去ログに対象の個人データが含まれている場合は、個人データの完全削除ルールが優先され、本文は確実に除去されます。

## 10. ランタイムフロー（Runtime Flows）と横断設計（Cross-cutting）の検証

[Major Runtime Flows](../architecture/runtime-flows.md) の主要フロー（RF-01〜RF-08）、[Cross-cutting Design](../architecture/cross-cutting.md)（CC-01〜CC-07）、[Context Assembly](context-assembly.md)、および [Action Execution](action-execution.md) において、競合や障害発生時に本仕様がどのように正しく機能するかを以下に示します。

| フロー・交差する場面 | 処理の流れと保証される結果 | 本ドキュメントの該当節 |
|---|---|---|
| **RF-01 会話から学習への反映と消去の競合** | 記憶（Memory）形成処理が対象情報を利用している最中に、ユーザーから消去要求が到着。認識・学習機能が消去ルールと照合し、削除前の古い情報から記憶を再保存しません。完全に消去が終わるまで「完了」と偽らず、ユーザーの訂正発言と消去要求を混同しません。 | 3、5.1〜5.2。Context 7.3・8.2、CC-03・05を維持。 |
| **RF-01 共有根拠の部分削除** | 対象データを含む要約が、無関係な別の記憶の根拠にもなっている場合。可能な限り対象データのみをピンポイントで切り離し、分離不能ならユーザーへ影響を説明して確認します。無関係なデータまで巻き添えで消去しません。 | 6.4、8.2、9。SO 4.5、CC-05を維持。 |
| **RF-02 委任タスクの遅延結果** | サブエージェントやツールの実行結果が、局所的な消去の完了後に遅れて到着。元のタスクへ必要な実行事実のみを記録し、対象本文は再保存しません。古い結果を新しい目的の達成とみなさず、後続タスクを勝手に自動開始しません。確定度も改ざんしません。 | 5.2〜5.3。Action 7.3・9、Context 7.3、CC-03・07を維持。 |
| **RF-02 キャンセル・方向修正との重なり** | タスクのキャンセルや目的変更の直後に、古い遅延結果と消去要求が重なる。元タスクへの事実記録と消去ルールを両立させ、古い承認情報でキャンセルや消去を勝手に解除しません。 | 5.2。Action 7、CC-03・04を維持。 |
| **RF-02 ツール実行結果の成否不明** | 外部ツールへの作用の成否が不明な状態で消去が発生。二重実行のリスクをユーザー判断へ戻し、自動再実行は行いません。「成否不明」を勝手に「未実行」や「成功」へ書き換えたりせず、実行記録に対象本文を残しません。 | 5.3、9。Action 8、CC-07を維持。 |
| **RF-03 共有観測と個体理解の遅延** | ルーティング用の文脈や候補データが消去区間に重なる。共有観測機能とキャラクター管理が消去ルールと照合し、生成済み要約や処理中データにも消去を即座に適用します。複数人のプライベート情報が混ざって分離できないテキストは、キャラクターへ配送しません。 | 4.2、5.2。Context 6、CC-02・03を維持。 |
| **RF-04 端末移動・切断と消去** | 消去中にクライアント端末が切断・再接続。通信不能を「消去成功」と偽らず、端末に残っていた古い画面キャッシュや入力をHostへ逆流させません。新端末への画面キャプチャの不正付け替えや、古いアクションの再実行もしません。 | 7.2。RT-02・08、CC-04・05を維持。 |
| **RF-04 端末不在期間の報告メモ** | 未伝達メモや要約テキストに対象データが含まれている場合。キャラクター管理がユーザーへの報告直前に消去状況と照合し、対象データを復元させません。端末へデータを送信しただけで勝手に「報告完了」とみなしません。 | 4.2、9。SO 4.4、CC-05・07を維持。 |
| **RF-05 再起動と未完了の消去** | 消去処理の途中でHostサービスが再起動。データ保全・消去機能が未完了状態と保留ルールをHostストレージに保持し、再起動後に検証を再開します。再起動を理由に消去完了と錯覚したり保留を解除しません。中断タスクはユーザーの明示的な再開を待ちます。 | 7.1、7.3。CC-04・05を維持。 |
| **RF-05 定期スケジュール・自発活動との競合** | 消去処理中に定期スケジュールが到来、または自発タスクが開始。現在の消去条件を再評価し、対象データを必要とする新しいタスクの開始を禁止します。 | 5.1。CC-01・04を維持。 |
| **RF-06 キャラクター削除と消去の重なり** | キャラクター削除と個人データの完全削除が重なる。キャラクター固有の学習データは削除し、残された過去ログやタスク履歴の中にある個人データ本文も完全に消去します。要約データを「過去ログ」へ分類し直して残すような抜け道は塞ぎます。 | 9。SO 6.3・6.4、CC-05を維持。 |
| **RF-06 キャラクター削除後の遅延アクション** | キャラクター削除後に、対象データを含むツール実行結果が到着。残されたタスク記録へ必要な客観的事実のみを残し、削除済みキャラクターの記憶を再作成しません。 | 5.2。Action 7.3、CC-03・05を維持。 |
| **RF-07 消去処理中のデータ再到着** | 消去開始から完了までの間に、対象データが再入力または内部生成される。同じ消去対象として確実に処理し、「新しい経験」として免除しません。消去が完全に完了した後にユーザーが自発的に提供した入力のみを「新しい経験」として区別します。 | 6.1〜6.2。CC-03・05、要件「Privacy/Security目的のtargeted deletionと履歴保持」を維持。 |
| **RF-07 外部プロバイダセッションの残存** | AIプロバイダとのセッションに対象データが残っている場合。プロンプトを短くしただけでそのセッションを再利用してはならず、安全な新しいセッションへ切り替えます。プロバイダのログ免責を理由に内部でのデータ再形成を許しません。 | 6.3。Context 5.2、CC-02・05を維持。 |
| **RF-07 検証失敗・未確認状態** | 指定文字列が見つかった、依存関係が解消できない、範囲が確定できない場合。不足を正直に報告し、全域完了にしません。LLMの「納得しました」という返答で代用しません。 | 8.2〜8.3。CC-05・07を維持。 |
| **RF-08 バックアップと未完了の消去** | 消去が未完了の状態でバックアップを作成。制約を無視した即実行可能なバックアップは作らず、作成を待機させるか、未完了状態の情報を含めて復旧可能にします。 | 7.4。SO 6.5、CC-05を維持。 |
| **RF-08 復元と旧実行結果・旧バックアップ** | 復元後に復元前の生リクエスト結果が到着したり、古いバックアップを明示的に復元して対象データが戻る場合。復元されたマスターデータに古い生結果を混ぜません。古いバックアップによるデータ復活は事前にユーザーへ説明し、自動再形成の例外にはしません。 | 6.2、7.4。Context 8.1、Action 7.3、CC-03・05を維持。 |
| **全フロー共通: 補助推論の失敗・コスト不足** | 消去の意味探索や検証を行う補助モデルがダウン、またはコスト上限に達した場合。機械的な削除や検証を推論待ちにせず、不足エラーを管理画面へ返します。安全のための停止・拒否・機械的検証は確実に継続します。 | 5.4。Context 5.2、CC-06を維持。 |
| **全フロー共通: 監査ログと完了報告** | 消去の完了報告や監査ログに対象本文を含めず、確定度を都合よく書き換えません。監査ログをデータの復元や自動実行の入力源にしません。 | 9。Action 9、CC-07を維持。 |

横断設計（Cross-cutting Design）の基本原則（CC-01〜CC-07）に対して、本ドキュメントでは以下の点を具体化しています：
- **CC-01（権限と意図）**: 個人データ消去の目的を、通常のデータ更新や権限承認と厳格に区別します。プロンプト内のテキストから勝手に消去を解除しません。
- **CC-03（現在性と受入）**: 削除前の古い根拠と、完了後にユーザーから新しく提供された入力を明確に分離します。
- **CC-05（全域操作の成立）**: 元データの削除、プロンプト生成の終了、一部の局所完了をもって「全域完了」と誤認しません。また、外部データの消去を内部消去の成功条件に含めません。
- **CC-06（安全な失敗とコスト管理）**: 機械的な削除や検証を、LLMの推論成功待ちにしません。

## 11. 本ドキュメントが固定する契約と、実装に残す自由度（Design Freedom）

後続の実装設計は、以下の原則を**固定された不変の契約**として前提にします：

1. **消去要求は全域操作の契約である**: ユーザーの目的、対象記述、消去区間、完了境界を対応付けるものであり、特定の保存場所の指定ではありません。機械的条件は必須かつLLM非依存であり、意味的条件は補助であって完全性は保証されません。既知の派生データの追跡は必須です。
2. **各マスターが参加し、保全・消去機能が調整する**: 各機能は自身の責任範囲で消去に参加し、対象データを復元できるすべての内部データ・過去の根拠・派生物・一時データ・処理中の利用は漏れなく参加します。Ene管理下の内部コピーは除外せず、外部コピーは成功条件に含めません。
3. **新規利用の禁止と確定度の維持**: 対象データを含む新規利用は直ちに禁止し、進行中処理はベストエフォートで安全に扱います。遅れて届いた結果は各受取口で消去ルールと照合します。消去を理由にアクションの確定度を書き換えてはなりません。
4. **再保存・再形成・再表示の絶対防止**: 消去処理中に届いたデータも同じ消去対象とします。過去の遅延結果と完了後の新規提供は文脈と由来で区別します。キャッシュ、セッション、端末一時データからのデータ復活を防ぎ、古い根拠だけからの自動再形成を行いません。
5. **Host側での確実な保全**: 未完了状態、保留ルール、再保存防止の制約はHost側で永続化し、再起動、切断、復元を跨いで維持します。通信不能を「成功」とすり替えず、局所完了をもって全域完了とみなしません。
6. **全域完了の厳格な条件**: 内部全域の物理削除・無効化、機械的残存検証、消去処理中の再到着の取り込み、再保存・再形成防止、未完了の完全解消のすべてが揃って初めて全域完了とします。
7. **客観的事実と対象本文の分離**: 保持すべき客観的事実と、消去すべき対象本文を厳密に区別し、完了記録や監査ログをデータの復元源にしません。

**【採用してはならない設計（アンチパターン）】**
- マスターデータベースのレコードを消しただけで完了とする方式
- 遅れて届いた推論結果を「新しい経験」として勝手に再登録する方式
- クライアント端末側のキャッシュでHostのデータを上書き・自動再実行する方式
- 古い根拠から記憶や関係性を自動的に再形成する方式
- キャッシュにヒットしたからといって消去制約のチェックを省略する方式
- 機密データを含んだAIプロバイダセッションを無条件に再利用する方式
- 通信できない端末や外部処理を勝手に「消去成功」と決めつける方式
- LLMが「忘れました」と答えたことだけで消去完了とする方式
- 外部バックアップ等の消去を内部完了の条件に含めたり、内部コピーを外部扱いして除外する方式
- 実行記録を残すという理由で対象の個人データ本文をそのまま残す方式
- 成否不明の外部作用を勝手に「未実行」や「成功」へ変換して自動再実行する方式
- ユーザー報告や復元処理の過程で確定度を勝手に格上げする方式

**【実装に委ねられる自由度（Design Freedom）】**
以下の項目は、上記の基本契約を満たす限り、具体的な実装側で自由に設計・選択して構いません：

| 設計対象 | 固定済みのアーキテクチャ原則 | 実装に委ねられる自由度（Design Freedom） |
|---|---|---|
| **対象記述と追跡の表現** | データの由来を偽装できず、消去条件を各利用先で自律的に照合できること。確認不能を許可や完了へ変換しないこと。 | 対象記述、由来、依存関係、消去区間、完了境界の内部データ構造。確認処理の集約方法、探索や機械的検証の配置、識別子や鮮度の確認プロトコル、競合解消アルゴリズム。 |
| **削除・無効化・検証の実現** | 各マスターの意味論の責任を維持し、全体管理役に他ドメインの通常書き込み権限を集中させないこと。 | 物理削除や復元不能化の具体的アルゴリズム、元データ・派生データ・処理中リクエストの追跡方式、残存検証の実装、クライアント端末の一時データ無効化プロトコル、到達性確認の方式。 |
| **競合制御と受取の通知** | 新規開始の即時禁止、ベストエフォート停止、遅延結果の適切な帰属、再実行の禁止。受付と完了の分離。確定度を改ざんしないこと。 | 停止シグナルの伝達方法、切断検知プロトコル、会話ターンの区切り方、キュー／アクター／イベントバスの採用、ロックやトランザクションの粒度、プロセス間通信（IPC）の形式、リトライやタイムアウトの秒数。 |
| **再保存防止・再形成防止の保持** | 消去処理中のデータ取り込み、過去由来と新規提供の明確な区別、キャッシュ再利用の禁止。文字列一致だけで意味的完全検出を偽らないこと。 | 識別子や対応関係の保存形式、DBスキーマ、リポジトリ構成、保持期間、永続化が必要な未完了状態の範囲、記憶の整理・統合（consolidation）の実装アルゴリズム。 |
| **再起動・復元（Restore）の整合性** | 未完了状態や保留ルールの維持、古い生結果の混入防止、復元直後の自動実行保留、外部世界の巻き戻し不可能性の遵守。 | WAL、ジャーナル、トランザクション等の永続化エンジン、整合スナップショットの生成方式、バックアップのファイル形式・暗号化方式・復旧シーケンス・バージョン互換性、部分的な障害からのリカバリ手順。 |
| **記録・報告・監査ログ** | 客観的事実の確定度、プライバシー、順序の意味を維持すること。機密本文の裏保管庫を作らないこと。 | 監査ログのフォーマット、保管期間、ユーザーへの確認ダイアログ設計、要約の詳細度、管理画面のUIレイアウト、診断ログスタック。 |
| **意味的探索とコスト管理** | 機械的条件をLLM待ちにせず、並列処理や未確定の利用もコスト上限に正確に反映すること。 | 探索補助のプロンプト設計、Embeddingモデルやスコアリングの選定、検索アルゴリズム、トークン費用の事前確保（リザーブ）や集計期間、リソース配分。 |

Rustのクレート・モジュール構成、トレイト（trait）・型定義、具体的な関数シグネチャ、ミドルウェアやインターセプター、IPCメッセージ形式、DBスキーマ、ロック機構、サンドボックス環境、外部ライブラリやOS APIの選定などは一切固定しません。
既存の12の責任領域、各マスターの権限境界、HostとClientの境界を尊重した上で、最適な実装方式を自由に選択してください。
