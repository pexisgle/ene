# Client Presence Transition — Client帰属切替とClient依存活動の区切りの詳細設計

本書は、パートナー（Companion）がクライアントに存在し、別のクライアントへ呼び出され、移動し、切断され、再接続し、Host PCの再起動後に存在（presence）を復元する過程において、**「キャラクターの存在場所」や「クライアントに依存する活動」の帰属先があいまいにならず、二重存在や古いクライアントでの不正な操作、誤った自動再実行を起こさないための論理的なルール（契約）**を詳細化するものです。後続のデータ構造、並行処理、永続化、IPC、UIなどの具象設計が安全に依存できる水準まで明確に定めます（具体的なプロトコルやライブラリなどの実装方法は固定しません）。

## 1. 詳細化する問題と範囲選定

クライアントの移動処理を「現在アクティブなクライアントID変数をパッと書き換えるだけ」のように安易に捉えてしまうと、以下のような不整合やセキュリティ問題が発生します。設計で誤りやすいポイントと、本書が定める基本ルールは以下のとおりです。

| 誤りやすい設計 | 本書が定める基本ルール |
|---|---|
| 移動前後の両方のクライアントを「現在有効」とみなしてしまい、2台の端末で同じキャラクターが同時に通常動作してしまう。 | Host PCが管理する単一の正式な帰属記録（authoritative presence）のみを有効とし、切り替え処理中は新旧どちらの端末でも新規アクションの開始を禁止します。 |
| 移動、再接続、再起動の際に、クライアント側の画面表示や一時データを「現在の正式な存在」として採用してしまう。 | クライアント側の画面表示や一時データはあくまで表示用のコピーに過ぎません。Host PC上のマスターデータのみを正式な存在とし、古い情報（staleデータ）を厳格に識別します。 |
| 移動前の古い入力、会話の途中、画面キャプチャ、操作結果を、移動先クライアントの新しい活動に勝手に流用・付け替えてしまう。 | 到着したデータは、それが実際に発生した元のクライアント・元の対話ステップ・元の試行に正しく対応付け、用途ごとに受け入れ可否を厳格に判定します。 |
| すべての処理に対して、「移動したから一律全停止」または「何でも自動継続」という極端な決め打ちを適用してしまう。 | 処理の種類ごとに安全な区切り方を個別に定義します（旧端末で完了、中断、新端末で新しい対話を開始、Host側で単独継続、結果不明として保持、の区別）。 |
| Host PC上で単独で進められる通常のタスクをクライアント依存の処理と混同し、移動時にタスクを移動先端末に転送したり停止してしまう。 | 「そのタスクに本当にクライアントが必要か」を正しく判断し、クライアントが不要なHost側のタスクは移動に関係なくそのまま継続します。 |
| キャラクターの画面表示が復旧したことを、中断されていた会話やPC操作（Computer Use）、タスクの再実行・再開の許可と混同してしまう。 | キャラクターの画面復帰と、過去の処理のリプレイ（再実行）を明確に分離します。 |
| 端末の切断やHost再起動によって外部への操作結果が不明になったものを、復旧や移動を理由に勝手に自動再実行してしまう。 | 結果不明な操作はそのまま「不明」として保持し、二重実行のリスクがある自動再実行を禁止します。 |
| 画面・音声観測（Observer）の対象判定がキャラクターの移動や切断と連動せず、移動元の古い端末で観測や通知の振り分けを続けてしまう。 | クライアント上の実際の存在人数や通知対象の判定を、Host上の現在の正式な帰属先と厳格に連動させます。 |

本書が扱う範囲は、正式な存在（authoritative presence）の判定基準、切り替え処理中の新旧端末の扱い、活動種別ごとの区切りルール、遅れて到着したデータの帰属、Host側タスクの継続条件、切断・再接続・再起動時の復旧、画面・音声観測の対象判定、PC操作（Computer Use）の固有条件です。なお、コンテキスト選択や推論連携の一般ルールは [Context Assembly](context-assembly.md) を、認可判断や実行結果の確定度は [Action Execution](action-execution.md) を、個人データの完全消去は [Targeted Deletion](targeted-deletion.md) を参照し、本書では再定義しません。また、画面・音声観測のモデル割り当て自体や、具体的なPC操作プロトコル、UIアニメーション、音声バッファの管理などは対象外です。

## 3. Authoritative presenceの契約

### 3.1 現在のpresenceとして判断するもの

稼働中（Running）のパートナー（Companion）が現在どの端末に存在しているかは、**Host PCが管理するキャラクターごとの正式な帰属記録（authoritative presence）**だけを唯一の根拠とします。管理責任は「接続・存在」サブシステムにあり、「個体調整」サブシステムの活動状態と、「権限・制約」サブシステムのペアリング・デバイス許可を参照して成立します。以下のものは、それ単体では「現在そこに存在する」根拠にはなりません。

- クライアント端末側の画面表示（キャラクターの姿（Body）が表示されている、対話履歴が残っている、音声セッションが開いているなど）。
- 過去にアクティブだった記録、直前まで使っていたクライアント、復帰候補などのヒント情報。
- クライアント端末側に残っている入力途中のテキスト、表示用タイムライン、マイクの音声バッファ、未送信の操作。
- 再接続してきたクライアントが保持している古い一時データや、実行中だったアクションの存在。
- Host PCの再起動前に保存されていた「以前の接続先」の記録そのもの。
- 外部モデルのセッション、キャッシュ、検索インデックスに残っている過去の所属情報。

復帰先の記録や再配置ヒントは「接続・存在」サブシステムが管理しますが、記録があることだけで「現在存在している」とはみなしません。現在のネットワーク接続、機器の許可、操作の排他性が確認できて初めて存在が成立します。

### 3.2 混同してはいけない四つの意味

「存在（presence）」「Host側での活動継続」「接続」「許可」は、それぞれまったく別の意味です。これらを混同してはなりません。

- **存在（presence / 帰属）**：そのキャラクターがどのクライアント端末に存在し、画面表示や音声などの端末依存アクションをどこに結び付けるかを示します。「接続・存在」サブシステムが管理し、稼働中の個体は最大1台の端末にのみ帰属します（停止中の個体はどの端末にもHostにも存在を持ちません）。
- **Host側での活動継続**：キャラクターがHost PC上で同じ個体として存続し、クライアント端末を必要としない処理を継続できることです。端末に接続されていない「クライアント不在（activeなし）」の状態であっても、キャラクターは消滅せず存続します。端末不在を「キャラクターの停止（Stop）」と混同してはなりません。
- **接続（Connection）**：クライアント端末がHost PCとネットワーク的に通信でき、機能を利用可能であるという客観的事実です。「ペアリング済みであること」や「通信が繋がっていること」は、「その端末にキャラクターが存在していること」や「操作が許可されていること」を意味しません。
- **許可（Permission）**：そのクライアント端末で特定の操作を行ってよいかというセキュリティ上の有効性です。端末に存在していることや接続されていることは、アクションの実行許可を意味しません。デバイス許可、ケーパビリティ、同意、利用枠上限、安全保留を個別に満たす必要があります。

Host PCがマスターデータを持ち処理を継続できることと、キャラクターがHost PC上に存在することとは別物です。停止中のキャラクターの保存データを「Host上に存在している」とは扱いません。また、Host PCと同じマシン上で動くローカルクライアントであっても、外部のモバイル端末などとまったく同じ帰属ルールが適用されます。

### 3.3 Staleを識別できるlogical property

具体的なセッショントークン、リース期間、ハートビート、エポック番号、シーケンス番号などの形式は実装に委ねられます。ただし後続設計は、少なくとも以下の論理的な対応関係を保持・照合できなければなりません。確認できないものを勝手に「現在も有効」と推定することは禁止されます。

- Host PCの正式な帰属記録と、クライアント側の一時データ・入力・処理結果が主張する帰属先との対応。そのデータがどの時点の帰属に対応するものかを正しく解決できること。
- 「現在の帰属」「過去の古い帰属」「帰属なし（クライアント不在）」「停止中」「再起動後の復旧待ち」の区別。過去の帰属情報を、現在の利用可能性として勝手に復活させないこと。
- 対象キャラクター、対象クライアント、対話ステップ（round）、観測イベント、アクション試行との関係性を、クライアント切り替えをまたいでも正確に維持できること。
- データ消去、権限失効、停止、安全保留との関係。クライアント側の古い一時データから、過去の許可や同意、スコープを勝手に復活させないこと。

クライアント側の古い設定コピーや外部コードが、独自に同意や最新性を決めてはなりません。Host PCの最新条件を確認できないクライアントは処理を継続してはならず、一時コピーを「第2のマスター」にしてはなりません。通信不能や確認不能を、勝手に「成功」や「現在有効」に読み替えてはなりません。

## 4. 切替途中の区別

### 4.1 必要な論理的な区別

固定的なステートマシンやハンドシェイク手順を1つに縛る必要はありませんが、後続設計は、少なくとも以下の状態を論理的に明確に区別しなければなりません。すべてを単一の真偽値（boolean）や単一のアクティブフラグに丸投げすることは禁止されます。

- **旧presence（移動元）**：切り替え前に正式だった帰属先。移動決定後は、旧端末での新しいアクション開始の根拠にしてはなりません。
- **移行中（切替区間）**：移動が要求・決定されてから、新端末での存在が正式に成立するまでの論理的な区間。旧端末でも新端末でも新しいアクションの開始を禁止します。旧端末で実行中だった処理の安全な完了と、Host側での単独継続のみが許可されます。
- **新presence（移動先）**：新端末について現在の接続、機器許可、排他性を確認して正式に成立した帰属先。成立以後のクライアント依存活動のみがここに帰属します。
- **activeなし（クライアント不在）**：キャラクターは稼働中（Running）のままですが、どの端末にも帰属していない正当な状態です。画面表示などの端末依存処理は行わず、Host側での単独タスクや未伝達メッセージの管理のみを行います。
- **停止中（Stopped）**：ユーザーの指示等によりキャラクターが停止している状態です。どの端末にもHost PCにも存在を持ちません。「activeなし」とはまったく異なる状態であり、Host側での活動継続や切断からの自動復帰、再起動後の自動復元は適用されません。

Host PC再起動後の「復旧待ち（以前の接続先は記録されているが、現在の接続や排他性がまだ確認できていない状態）」は「activeなし」の一種であり、過去の存在の自動延長ではありません。別の端末への無条件な自動移動に拡大解釈してはなりません。

### 4.2 切替区間で成立させる排他性

切り替え処理の途中のいかなる状態であっても、以下の3つの原則を必ず成立させます。

1. **2台のクライアントで同時に通常動作させない**：移動元の端末でキャラクターが動作したまま、移動先の端末でもアクティブにしてはなりません。新旧両方の端末で同じキャラクターが同時に画面表示（Body）、テキスト・リアルタイム会話、音声発話、観測への反応、自発的対話、PC操作（Computer Use）を行わないことが絶対条件です。
2. **古い端末の一時データを正式な存在として扱わない**：移動元端末に画面表示や音声バッファ、未送信の操作、実行中のアクションが残っていたとしても、それを移動の成立や再接続、再起動の根拠にしてはなりません。Host PCの最新の帰属記録をクライアント側のデータで上書きしてはなりません。
3. **安全に終了できていない端末依存操作を別端末で自動継続しない**：移動元端末で実行中だった操作の内容や結果不明な状態は、元の試行やタスクに対応付けて記録し、新端末で勝手に新しい試行として自動再実行してはなりません。キャラクターの移動と、未確定なアクションの再実行は完全に切り離して扱います。

移動が決定してから新端末での存在が成立するまでの間、新旧どちらの端末でも新しい端末依存アクションを開始してはなりません。旧端末では実行中の処理を安全な区切りの良いところまで完了させることだけが許され、新端末では存在が成立した後の新しい対話ステップや試行のみが許されます。通常のHost側タスクの終了や転送をクライアント移動の前提条件にしてはならず、Agentやワークスペース、Hostのマスターデータを移動先端末へ物理的に移送するようなことはしません。

画面の表示は、新旧両方の端末に対して現在把握できている移動状態を分かりやすく示します。区切りの報告を行うために、移動先端末への移動完了を待つ必要はありません。排他性が確認できない端末では処理を継続せず、Host側でも、現地の物理的な停止が確認できない限り勝手に「停止成功」とみなしてはなりません。

### 4.3 呼出し・移動の基本形

別の端末からキャラクターと会話や操作を行いたい場合は、まずその端末への「呼び出し（移動）」の手続きを経ます。キャラクターを元の端末に残したまま、別の端末からテキストメッセージだけを送って裏で応答させるような設計は基本モデルとしません。呼び出し先の端末は、正当な接続と必要な機能を備えている必要があり、単にペアリングされているだけでは不十分です。移動後の環境観測（ambient Observation）は移動先端末の設定に従い、自発的な行動設定はキャラクター単位でそのまま引き継ぎます。

クライアント端末の通常の切断時には、稼働中のキャラクターは基本的に利用可能なHost PC上のクライアント（デスクトップ画面など）へ自動移動します。利用可能なクライアントが存在しない場合は「activeなし（端末不在）」として安全に待機します。ただし、画面のない環境で勝手にUIを自動起動するようなことはしません。キャラクターの「停止（Stop）」は通常の切断とは異なり、停止したキャラクターをHost側に移動して存在を残すようなことはしません。

## 5. Client依存活動別の区切り

すべての活動に対して一律に「移動したから全停止」という雑なルールを適用してはなりません。活動の種類ごとに、要件定義に基づく安全な区切り方を個別に定めます。

| 活動の種類 | 帰属と区切りのルール |
|---|---|
| **テキスト会話（1対1、グループを含む）** | 現在存在するアクティブな端末に属します。対話ステップ（round）単位で安全に区切ります。旧端末での入力途中テキスト、生成途中の返答、画面に表示されていない返答を、新端末へ自動継続してはなりません。旧端末での対話結果は元の対話ステップと会話履歴に正しく記録し、ユーザーに提示できなかった内容は「未伝達メッセージ」として管理し、次に接続した端末で現在の状況に基づき要約して報告します。旧端末の返答テキストをそのまま新端末へ自動転送したり、古い対話ステップへ勝手に出力してはなりません。グループ会話でも各キャラクターが自身の存在場所を必要とし、参加したことだけを理由に他のキャラクターのプライベートデータへのアクセス権を得てはなりません。 |
| **音声会話（リアルタイム・ターン制）** | アクティブな端末に属するセッション的な処理であり、中断は可能ですが、端末をまたいで「同一の音声ストリーム」として再開することはしません。旧端末での音声待受、発話、音声認識途中の処理は安全に打ち切り、マイクミュートや緊急停止、操作拒否のためのキーボード入力経路は常に維持します。新端末では新しいセッション・対話ステップとして開始し、現在のモデル割当同意、マイク等のデバイス許可、費用条件を改めて満たす必要があります。話者認証済みの意味を勝手に追加せず、周囲の人の声の取り扱いに関する説明を維持します。音声機能の障害時はテキストへの段階的な切り替えを行いますが、それをクライアント切り替えの迂回に使ってはなりません。 |
| **身体表示（Body / デスクトップオーバーレイ）** | アクティブな端末に属する画面表示です。旧端末では非表示（hide）または休止し、新端末で存在が正式に成立した後に表示を開始します（二重表示の禁止）。表示位置やサイズ、非表示設定などの基本設定はHost PCのマスターデータとして管理されますが、実際の描画は現在の帰属先に従います。画面描画の失敗やフルスクリーン検知、PCの高負荷を、テキスト会話や管理画面、復元処理へ波及させてはなりません。出力された表情やモーションを、キャラクター状態（Companion State）のマスターデータや永続的な変化の根拠にしてはなりません。 |
| **画面・音声観測と自発的対話** | 端末の観測適格性と、キャラクター自身の自発的な行動判断は別物です。旧端末で取得した画面キャプチャ、検知イベント、振り分け結果を、新端末へ勝手に流用・付け替えてはなりません。移動、停止、一時停止（Pause/OFF）、フルスクリーン検知が重なった場合は、キャプチャ元の端末、現在の存在場所、観測条件を照合し、古いイベントで新しいキャプチャや通知送信を続けてはなりません。停止中のキャラクターを起こしてはならず、存在人数にも数えません。自発的な発話や通知を行うかどうかの最終判断は、各キャラクターが現在の帰属先、ミュート設定、おやすみ時間（Quiet hours）、費用、権限を考慮して行い、切り替え処理中の新規自発アクションは抑制します。 |
| **PC操作（Computer Use）** | 最も厳格な帰属制約を持ちます。後述の第10節のルールに従い、旧端末で安全な区切りまで完了させるかベストエフォートで停止し、新端末では「新しい試行」として改めて開始します。旧端末での試行を新端末で自動再実行してはなりません。 |
| **通常のHost側タスク・Agent・スケジュール** | クライアントの移動とは完全に独立してHost PC上で継続できます。判断基準は「その処理に本当にクライアントが必要か」です。クライアントが必要なステップ（画面確認など）だけを一時待機させ、タスク全体を一律キャンセルしたり移動先端末へ転送・停止してはなりません。ユーザーの確認が必要なアクションは、勝手に自動承認せず「ユーザー判断待ち」として安全に保留します。 |
| **キャラクター同士の交流・通知生成・内部調査** | 稼働中（Running）であれば、クライアント不在（activeなし）であってもHost PC内部でそのまま継続できます。ユーザーへの提示や報告は、次回クライアントが接続された時まで安全に延期します。ただし、キャラクターが停止中（Stop）の場合は開始しません。 |
| **未伝達事項の報告** | Host PC上に確実に記録を残し、次に接続されたクライアントで要約して報告します。単にクライアントが接続されたことや、画面表示用のデータを送信したこと、あるいはタスクが完了したことだけで「報告完了」とみなしてはならず、実際に届いたか不明な状態を正しく保持します。「報告したこと」は「ユーザーが承認したこと」や「タスクを再開したこと」を意味しません。 |

軽微なアクションにおいてタスク化の手続きを省略することは許容されますが、権限チェック、操作結果の把握、ログ記録のセキュリティ境界を省略してはなりません。まとまったファイル作業やPC操作、長期的な作業、並列実行する価値のある作業は、必ずタスク化と委任の原則に従います。

権限、デバイス許可、同意、利用枠上限の失効が発生した場合は、それらを根拠とする新規操作を直ちに停止し、別端末や別Agent、別ツールへ迂回してはなりません。ただし、それらと無関係に動いているHost PC上のタスクまで一律に巻き込んでキャンセルしてはなりません。

## 6. 移動・切断中に到着した入力・出力・Capture・作用結果の帰属

[Context Assembly](context-assembly.md) 第7節および [Action Execution](action-execution.md) 第7節の「用途別受け入れルール」に、クライアント帰属の照合を追加します。単に届いたのが遅かったというだけで出来事の順序を新しく書き換えたり、直近に届いた結果だけで現在の状態を勝手に上書きしてはなりません。必要な対応関係が失われた古い結果は、到着先の新しい活動に勝手に付け替えてはならず、その用途では受け入れ拒否（破棄）します。

| 到着したデータ | 残すべき事実・許可される対応 | 禁止される扱い |
|---|---|---|
| 切り替え区間に旧端末から届いた入力 | 元の帰属先・元の対話ステップに対応付けます。切り替え決定後の新規要求として旧端末で実行してはならず、新端末へ自動転送もしません。必要であれば、新端末で新しい対話ステップとしてユーザーが改めて入力します。 | 旧端末からの入力を、新端末の現在の要求として勝手に流用する。未送信だった操作を自動実行キューとしてそのままリプレイする。 |
| 切り替え区間に新端末から届いた入力 | 新端末での存在が正式に成立する前の要求としては扱いません。存在が成立した後に、新しい対話ステップとして正式に受理・判断します（成立前の先行実行は禁止）。 | 正式成立前の入力を使って、なし崩し的に存在を成立させる。旧端末の対話ステップの続きとして勝手に実行する。 |
| 旧端末向けに生成済みだが未提示の出力 | 「生成済み＝ユーザーに提示済み」とはみなしません。元の対話ステップに対応付けて記録し、未伝達メッセージとして管理し、次に接続した端末で最新状況に基づく要約報告とします。 | 旧端末向けの返答テキストを新端末の画面へ自動出力する。画面描画用データを送信したことだけで「報告完了」とみなす。 |
| 旧端末からの遅延メッセージや画面コピー | Host PCの現在のマスターデータ、帰属先、消去状況に従って、未確定の入力と受理済みの入力を明確に区別します。クライアント側のコピーでHostのマスターデータを上書きしてはなりません。 | 遅れて届いたメッセージによって、過去の帰属、権限、タスク状態を勝手に復活させる。 |
| 旧端末で取得された画面キャプチャや検知イベント | キャプチャ元端末、取得日時、検知イベントとの対応関係を維持します。移動先端末のものとして付け替えてはなりません。移動や停止後のイベント配信は最新の帰属先や観測条件と照合し、停止中のキャラクターを起こしてはなりません。 | 旧端末の画面キャプチャを、移動先端末の観測データとして流用する。過去のイベントを理由に、別端末での観測やデータ送信の同意を勝手に拡大する。 |
| キャンセル・指示修正・失効・移動・削除・復元後に届いたツール結果や承認 | 元のアクションやタスクに必要な操作事実のみを記録し、現在のタスクや目的への採用可否は改めて再評価します。後続アクションは自動開始しません。古い承認でキャンセルや失効、移動を取り消してはなりません。 | 古い結果を、新しい目的が達成されたものとして採用する。古い承認を使って新しい試行を開始する。 |
| クライアント依存操作の実行結果（判明／不明） | 実行・拡張サブシステムは操作事実を元の試行に対応付け、作業サブシステムは現在のタスク基準で評価します。結果不明な操作はそのまま「不明」として保持します。 | 結果不明な操作を勝手に「未実行」や「成功」に書き換える。新端末で自動再実行して解決しようとする。 |
| データ消去区間や復旧保留と重なる到着データ | 各サブシステムが消去条件や安全保留と照合し、削除対象となったデータを復活させません。復元前の古い実行結果を復元後の新マスターデータに混ぜてはなりません。 | 新しく届いたからといって新しい知識として学習する。操作ログや監査ログを理由に、削除対象の本文を再保存する。 |

ストリーミング出力や部分的な処理結果であっても、新しく保存・送信・画面提示・アクションへ渡す部分ごとに、帰属、データ消去、権限の受け入れ条件を満たす必要があります。全文が揃うまで常に待機することを強制するわけではありませんが、未検証のテキストを先に画面に露出させておいて、後から「やっぱり無効でした」と取り消すような実装は禁止されます。すでに画面に露出してしまったり外部に影響を与えてしまった操作を取り消せたと勝手に推定してはならず、客観的に把握できた事実を維持します。

推論結果は、実際にプロンプトに入力された情報範囲や帰属先に依存します。旧端末のコンテキスト、キャッシュ、セッションを、新端末の現在のコンテキストとして再利用してはなりません。外部モデルのセッションに旧端末の情報が残っている場合、現在使えない情報を含むセッションに対して、最新コンテキストだけを短く渡して推論を継続させるようなアプローチはセキュリティ上成立しません。

## 7. Host-side Taskが継続できる理由と範囲

タスクを継続できるかどうかの唯一の判断基準は、**「その処理に本当にクライアント端末が必要かどうか」**です。タスクの重要度、進行度、あるいはキャラクターが今どの端末にいるか（あるいは端末不在か）は継続可否の基準ではありません。「クライアントが必要なステップ」以外はHost PC上で継続可能であり、「クライアントに依存するステップ」のみが一時停止・待機となります。この基準により、通常のHost作業は、クライアント端末の接続状態や画面表示、移動の完了などを存続条件としません。

- 実行が許可されているHost PC上のタスク、タスクAgent、定期スケジュール、ファイル保存などは、クライアント不在（activeなし）の状態であってもそのまま継続できます。待機のためだけにLLMをループで呼び出し続ける（ポーリングする）ような無駄な実装は行いません。
- PC操作（Computer Use）や、端末画面・音声を通じたユーザー確認など「クライアント端末に依存するステップ」に到達した場合は、そのステップのみを「ユーザー判断待ち」または「保留」として待機させます。タスク全体を一律にキャンセルしたり、移動先端末へ丸ごと転送したり、最初から作り直したりはしません。
- タスクが実行中であること自体は、クライアントの切り替えや移動を妨げません。クライアントの移動とは、Host PC上で動いている通常タスクを別の端末へ物理的に移送（マイグレーション）することではありません。
- タスクAgentは、特定のキャラクターの恒久的な人格や、任意のクライアントを自由に選ぶ主体ではありません。Agentに委任されたPC操作であっても、委任元のキャラクターが現在存在しているクライアント端末でのみ実行されます。Agentが勝手に操作対象のクライアントを選ぶことはできず、操作対象端末を変えたい場合は、まずキャラクター自身がその端末へ移動する必要があります。
- クライアント不在の間にHost PC上のタスクが完了した場合、その結果は「未伝達メッセージ」として管理され、次回クライアントが接続された際にまとめて報告されます。タスクが完了したことだけで「ユーザーに報告完了した」とみなしてはなりません。
- バックグラウンド処理や定期スケジュールの無人実行も同じルールに従い、「クライアントがいないから」「予定時刻になったから」といってユーザーの承認を勝手に省略（自動承認）してはなりません。ユーザー確認が必要なアクションは、実行せずに判断待ちとして安全に保留します。
- フルスクリーン検知、観測の一時停止（Pause/OFF）、マイクミュート、PC高負荷、利用枠上限の到達などは、それぞれの該当機能のみを抑制するものであり、Host PC上で動いている通常タスクを一律キャンセルしたり、すでに形成された学習データを消去したりしてはなりません。

管理画面全体に対して、会話機能と同じような「アクティブ端末の制約」を無理に課す必要はありません。担当キャラクターが削除された後もタスク記録にアクセスできることと、クライアント切り替え中にHost側タスクが継続できることは別のルールですが、いずれも「タスク記録のマスターデータを作業サブシステムがHost PC上で管理している」ことによって整合性が保たれます。

## 8. Disconnect／reconnect／restart

### 8.1 切断の種別の区別

通信の切断が発生した際、「結果不明な操作を勝手に未実行に戻さない」「勝手に自動リプレイしない」という原則はすべてに共通しますが、キャラクターの帰属（存在場所）の扱いは切断の性質ごとに異なります。

| 切断の事象 | 帰属および活動の取り扱いルール |
|---|---|
| 一時的なネットワーク瞬断・短時間の通信途絶 | 現在の帰属先を直ちに破棄することはありませんが、操作の排他性や利用可能性が確認できない間は、新しい端末依存アクションを開始しません。実行中だった操作はベストエフォートで停止する準備を行い、通信不能を勝手に「成功」とみなしてはなりません。通信回復後も、過去の帰属の自動延長として無条件に処理を継続するのではなく、現在の帰属と権限を改めて照合します。 |
| クライアントアプリの終了・通常の切断 | 稼働中（Running）のキャラクターは、基本的に利用可能なHost PC上のクライアント（デスクトップ画面など）へ自動移動し、利用可能なクライアントがなければ「activeなし（端末不在）」として待機します。旧端末で結果が未確定だった操作を、Host側で勝手に自動再実行してはなりません。旧操作の停止はベストエフォートとし、判明した結果と不明な結果を作業サブシステムに返します。 |
| クライアント端末・OSの再起動 | 上記の通常切断と同様ですが、再起動後に再接続してきたクライアントが保持している古い一時データだけで、現在の存在、権限、処理の再開を勝手に成立させてはなりません。古い画面コピーや未送信操作をHostのマスターデータに戻してはなりません。 |
| デバイスの権限失効・許可変更 | 権限が失効した機能の新規利用を直ちに停止し、最新の制約を反映します。別の端末へ切り替えることでその失効を迂回（回避）してはなりません。ただし、失効と無関係なHost PC上のタスクまで一律キャンセルしてはならず、過去の接続トークンだけで失効後の信頼を勝手に復活させてはなりません。 |
| Host PCの再起動 | 第8.3節の復旧ルールに従います。通常の端末切断時の「Host PCへの移動」とは明確に区別します。 |
| キャラクターの停止（Stop）との競合 | ユーザーによる停止指示が確定した場合は、通常の切断復帰、再接続、再起動復旧よりも停止状態を優先します。停止中のキャラクターをHost側に移動して存在を残すようなことはせず、ネットワーク接続が回復したことだけを理由に勝手に再開（Resume）や再配置をしてはなりません。 |

切断検知や排他性の具体的な実装技術は実装に委ねられます。本質的に要求されるのは、「操作の排他性が確認できないクライアント端末では、画面・音声の入出力、環境観測、自発的対話、PC操作を継続してはならない」ということです。

### 8.2 Reconnect

再接続してきたクライアント端末が、古い一時データや実行中だったアクションの情報を持っていたとしても、それだけで現在の存在、権限、タスクの再開を勝手に成立させてはなりません。Host PCが持つ最新のマスターデータ、帰属先、消去状況に従い、未確定の入力と受理済みの入力を明確に区別します。クライアント側のコピーでHostのマスターデータを上書きしてはならず、未送信だった操作を自動実行キューとしてそのままリプレイしてはなりません。

- クライアント側に残っていた古い画面表示のコピー、入力テキスト、ツールUIのデータをHost PCに書き戻して、タスクや学習データを勝手に再作成してはなりません。
- 過去の承認ログ、判定コピー、解決済みパス情報だけで新しい操作を始めてはならず、現在の前提条件（権限、委任、ワークスペース、デバイス、費用、安全保留、削除条件）を必ず照合します。
- 個人データの削除処理中に再接続してきた場合、通信不能を「削除成功」と都合よく読み替えてはならず、古い一時データをHost PCに戻して削除対象データを再形成してはなりません。
- デバイスの登録解除や全データ初期化（Reset）の後は、過去の古い接続情報だけでHost側の信頼を復活させてはなりません。再ペアリングにはHost PC側での正式な承認手続きが必要です。

再接続とは「Host PCに保存されている進捗や結果に再びアクセスできるようにする操作」であり、過去の実行状態をそのまま復活させることではありません。切り替え前に開始された推論やツールの結果が切り替え後に届いた場合でも、復元前の古い状態を現在のマスターデータに混入させてはなりません。

### 8.3 Host再起動後のpresence復旧と再実行の分離

Host PCの再起動後は、ディスクに安全に保全されていたマスターデータから、現在の目的に必要なコンテキストを再構成します。保存されていたキャッシュ等を参考にすることは可能ですが、過去の要求に対する実行許可や過去の処理そのものを勝手に再開してはなりません。以下の3つのフェーズを厳格に区別します。

1. **存在（presence）の復旧**：稼働中（Running）だったパートナーは、再起動前に存在していたクライアント端末へ自動的に存在を復元します。これは別の端末への自発的移動とは異なる「元の場所への復帰」であり、元の端末が利用可能になるまでは「activeなし（端末不在）」として安全に待機します。別の端末へ勝手に自動移動させたり、停止中（Stopped）だったパートナーに適用してはなりません。また、画面のない環境で勝手にUIを自動起動することもありません。
2. **会話・PC操作・アクションの再開禁止**：過去の会話ステップ、PC操作、アクションを勝手に自動再実行・再開してはなりません。過去の対話ステップは終了したものとして扱い、過去の操作の結果不明な状態はそのまま「不明」として保持します。新しい対話やアクションは、現在の帰属先、権限、最新の目的を満たした上で新しく開始し、二重実行のリスクがある不明な操作はユーザーにリスクを説明して判断を仰ぎます。キャラクターの画面表示が復旧したことは、タスク再開やアクション開始の権限にはなりません。
3. **中断タスク・スケジュールの扱い**：中断されていたタスクは勝手に自動再開せず、保存されている進捗、すでに判明している外部への影響、結果不明な操作、未完了の項目を提示し、ユーザーからの明示的な再開指示を待ちます。Host PCの停止中に過ぎ去ってしまった定期スケジュールはスキップ扱い（missed）とし、勝手に過去分をまとめて穴埋め実行してはなりません。将来の実行回は、その時点の最新条件に基づいて新しいタスクとして組み立てます。Agentのセッションが残っていること、外部サービスが復旧したこと、Hostの自動起動設定が有効であることだけを理由に再開してはなりません。

通常の再起動は、バックアップ復元（Restore）のように「データ全体の内容確認と一括有効化」を要求する操作ではありませんが、未完了の個人データ削除や復元保留がある場合は、その保留を最優先で維持します。Host PCのシャットダウン時にも必要な進捗、結果不明な操作、未伝達メッセージ、全体操作の未完了状態を確実にディスクへ保全し、Hostの停止とともに外部への影響も勝手に消滅したかのように誤認してはなりません。

### 8.4 Stopとreconnectの競合

ユーザーによってキャラクターの停止（Stop）が確定した後は、そのキャラクターはどのクライアント端末にもHost PCにも存在を持ちません。識別情報やこれまでの経験データ、再配置ヒントは保存されますが、ヒントはあくまで再配置先の候補に過ぎません。端末とのネットワーク接続が回復したことだけを理由に、勝手にキャラクターを再開（Resume）させたり画面に再配置してはなりません。停止前の遅れて届いた結果を、新しく再開された活動の指示や許可と混ぜ合わせてはならず、停止中に過ぎ去ったスケジュール回もスキップされたままとなります。

キャラクターが完全に削除された後は、発生した操作の客観的事実を残存するタスクや活動ログに対応付けて記録し、管理画面から説明できるようにします。削除されたキャラクターの返信、記憶（Memory）、関係性（Relationship）などを勝手に再作成・復活させてはなりません。過去の会話履歴の中にキャラクターの存在が言及されていたとしても、そこからキャラクター自身や固有の学習データを勝手に再生成してはなりません。

## 9. Observation

画面・音声観測（Observer）はクライアント端末に紐づく共有機能であり、**「そのクライアント端末に、少なくとも1人の稼働中（Running）のパートナーが存在しているとき」**にのみ観測の対象となります。キャラクターの移動、停止、切断に伴い、観測対象としての適格性（eligibility）は以下のように変化します。

- 端末上の存在人数のカウントは、Host PCが管理する正式な帰属記録に従います。停止中（Stopped）のキャラクターは人数や通知の振り分け対象に数えません。クライアント端末側の画面表示の残骸や、古い一時データに残るキャラクター情報を人数に数えてはなりません。
- キャラクターが別の端末へ移動した場合、移動元端末と移動先端末の観測対象性を最新の帰属記録に基づいて見直します。移動元端末から最後の1人が退出した場合は、その端末の新規観測対象性は直ちに失われます。移動先端末では、その端末の観測設定と全体制御に従って動作します。自発的な行動設定はキャラクター単位でそのまま引き継ぎます。
- 切り替え処理中の区間では、移動元端末で取得された古いキャプチャや古い検知イベントに基づいて、新しいキャプチャや通知送信を続けてはなりません。移動先の観測設定に対して、古いキャプチャを勝手に流用・付け替えてはなりません。
- クライアント不在（activeなし）の間は、そのキャラクターに対する新しい環境観測イベントは発生しません。他のキャラクターが残っている端末の観測適格性は、残っている他のキャラクターの存在に基づいて判断します。
- キャラクターが停止（Stop）した場合は、共有観測の人数カウントや通知振り分けから直ちに除外します。端末に残る最後の1人が停止した場合は、その端末の新規観測対象性は失われます。
- クライアント端末が切断された場合は、通信不能となった端末の過去の人数に基づいて観測や通知振り分けを続けてはなりません。通信不能を「対象性あり」と都合よく解釈してはなりません。
- 観測の一時停止（Pause/OFF）やフルスクリーン検知が発生した場合は、それらが制限する今後の観測や画面提示を直ちに停止します。古い設定のままで次の観測やデータ送信を開始してはならず、フルスクリーン表示中に勝手に自発的な発話を行ってはなりません。
- イベント検知や関連付けは観測専用のモデル割り当てで行い、キャラクター設定の上書きを勝手に適用・合成してはなりません。限定的なプライベート文脈を利用する場合でも、元データの利用制限と専用割り当ての送信条件を両方とも満たす必要があります。イベント通知を受け取った後のキャラクター自身の推論は独立した処理であり、そのキャラクター固有の通常モデル設定と同意条件を満たす必要があります。
- イベントを受け取ったパートナーのメインLLMが、自分自身のコンテキストに基づいて意味を判断します。Observerによる通知の振り分けは、キャラクター自身の最終判断を代行するものではありません。すでにキャラクターが認識した経験データは別個のライフサイクルであり、観測のOFF、移動、停止だけで勝手に消去されることはありません。
- 同意の失効や個人データの完全削除（targeted deletion）が重なった場合は、データの利用禁止と再保存防止を最優先します。生成済みの要約や処理中の結果に対しても同様に適用されます。削除対象データと安全なデータが混ざり合って分離できない場合は、キャラクターへ渡さずに破棄するか、安全な情報のみで再構成します。

複数の対象クライアントが存在する場合、同時に画面キャプチャを取得するのではなく、システムへの負荷制限を優先しながらタイミングをずらして分散処理します。

## 10. Computer Use

PC画面操作（Computer Use）は、システムの中で最も厳格な帰属制約を持ちます。後続設計は以下のルールを厳格に維持しなければなりません。

- **現在存在しているクライアント端末に限定**：操作対象となるPC環境は、委任元のパートナーが現在アクティブに存在しているクライアント端末のみに厳格に限定されます。タスクやタスクAgentが、ペアリング済みの任意の端末を勝手に選んで操作することはできません。Host PC自体のデスクトップを操作する場合であっても、パートナーがHost上のクライアントに存在していることが必須条件です。キャラクターの存在場所と操作対象端末を分離してはなりません。
- **安全な区切りまで移動を遅延可能**：PC操作を実行中にクライアントの移動が必要になった場合は、外部への影響が曖昧にならないよう、安全に区切りの良いところまで移動を一時的に遅らせることができます。ただし、待機するのは対象のアクションに必要な区切りだけであり、無関係なHost側タスクの完了まで待つ必要はありません。通信切断や停止不能な状態を「待ち続ければいつか成功する」とみなして無限待機してはなりません。
- **切断後の操作結果不明の扱い**：端末の切断に伴う停止処理はベストエフォートとし、どうしても停止できなかった処理、すでに生じた影響、結果が不明な操作を正確に記録します。現地の物理的な停止や外部操作の取り消しが確認できない限り、勝手に「停止成功」とみなしてはならず、排他性が確認できない端末で操作を継続してはなりません。
- **別端末やHostでの自動再実行禁止**：クライアントが移動したからといって、元の端末で実行していたPC操作を別の端末やHost PC上で自動的に再実行してはなりません。結果が不明な操作を勝手に再実行してはならず、二重実行のリスクがある場合は必ずユーザーの判断を仰ぎます。キャラクターの移動と、未確定なアクションの再実行は完全に切り離して扱います。ユーザーからタスク再開の指示があった場合でも、結果不明な操作まで無差別にリプレイしてはなりません。

現在のクライアントに存在していることは、アクションの実行許可を意味しません。通常のケーパビリティ、権限チェック、デバイス許可、操作ログの記録をすべて適用し、環境観測（ambient Observation）が有効化されていることを、操作に対する無条件の承認とみなしてはなりません。また、許可されたPC操作を使って、Ene自身の権限承認ダイアログや設定画面を勝手にクリック・操作し、ユーザーの承認を偽装することは固く禁止されます。

試行と作用の区別、判断・目的・実際の操作対象・進捗段階・確定度・停止保留との対応関係の保持は、[Action Execution](action-execution.md) 第8節のルールに従います。具体的な冪等性キーの形式やDBスキーマ、ロック方式は固定しませんが、二重実行のリスクがある再送を「単一の試行が続いているだけ」とみなして管理から除外することは禁止されます。リトライは常に現在の条件を満たす「新しい試行」として扱い、結果不明な試行の再実行には、二重実行リスクを説明した上でのユーザー自身の判断が必須です。

## 11. Runtime Flows・Cross-cutting Design・他のcritical-area契約に対する横断検証

主要な実行フロー（RF-01〜08）、横断設計原則（CC-01〜07）、および他の重要設計ドキュメントと照らし合わせた、正常系および障害・競合シナリオの整合性検証（walkthrough）は以下のとおりです。

| フロー・競合シナリオ | 処理の流れと満たすべき結果 | 本ドキュメントの対応箇所 |
|---|---|---|
| RF-04 正常系: 端末AからBへの呼び出し移動 | 移動の意図 → 帰属の照合 → 対話ステップ・操作の安全な区切り → 排他的な切り替え → 新端末での利用開始 → 観測対象の見直しが正しく完結する。Host側タスクを物理移送せず、新端末でのアクティブ化を過去操作の再実行許可と誤認しない。 | 4、5、7。（CC-04, Context 8.1, Action 8.4を維持） |
| 移動要求と入力到着の競合 | 切り替え処理中に旧端末および新端末から入力が到着。どちらも現在の要求として勝手に自動実行せず、旧端末の入力は元の対話ステップへ、新端末の入力は成立後の新対話ステップとして扱う。未送信操作を自動リプレイしない。 | 4.2、6。（Context 3.1, 7.2, CC-03を維持） |
| PC操作（Computer Use）中の切断 | 結果の返答を受け取る前に通信切断。ベストエフォートで停止し、判明した結果と不明な結果を作業サブシステムに返す（移動完了を待たない）。Host PCへ移動しても旧操作を自動再実行せず、「不明」として保持する。 | 8.1、10。（Action 6.2, 8.4, CC-04, CC-07を維持） |
| 新端末への移動途中での障害 | 移動先端末Bが処理途中で通信不能になる。端末Bへの移動を「成功」と誤表示せず、成立済みの元の帰属先または「activeなし」を基準に対処する。二重存在を決して作らない。 | 4.2。（CC-04, RT-02を維持） |
| 旧端末からの遅延メッセージと画面コピー | 再接続や遅延により旧端末のデータが後から戻る。Host PCの最新マスターデータ、帰属先、消去状況と照合し、未確定と受理済みを区別する。クライアント側のコピーでHostを上書きしない。 | 6、8.2。（Context 7.3, 8.1, Action 7.3, CC-03を維持） |
| Host側タスク完了とクライアント不在 | タスク完了時にクライアントが接続されていない。結果を未伝達メッセージとして管理し、次回クライアントが接続された際に要約して報告する。データ送信だけで報告完了とみなさない。 | 5、7。（Context 7.3, Action 9, CC-07を維持） |
| Host再起動とクライアント再接続 | 中断タスクと結果不明な操作を抱えたままHostが再起動。キャラクターの存在は元の端末へ自動復旧するが、タスクはユーザーの明示再開を待ち、過去の対話ステップや試行は自動リプレイしない。元の端末が繋がらない場合は「activeなし」として安全に待機する。 | 8.3。（Context 8.1, Action 8.4, CC-04を維持） |
| キャラクター停止（Stop）と再接続の競合 | 停止指示の確定後に旧端末が再接続。通信回復だけで勝手に再開（Resume）や画面再配置を行わず、停止前の遅延結果を新しい活動の指示や許可と混ぜない。停止中に過ぎ去ったスケジュール回はスキップのまま維持する。 | 8.4。（CC-04, SO 6.3を維持） |
| RF-03交差: キャプチャ取得後に移動・停止 | イベント解析結果が返ってくる前に最後のキャラクターが移動または停止。旧端末の人数やイベントで新しいキャプチャや通知送信を続けない。古いキャプチャを新端末へ流用せず、停止中のキャラクターを起こさない。 | 9。（Context 6.3, CC-02〜04を維持） |
| RF-01交差: 応答テキスト生成と移動 | 返答テキストを生成した直後にキャラクターが移動。「生成済み＝ユーザー提示済み」とみなさず、元の対話ステップに対応付けて未伝達とする。新端末で現在の条件を満たした上で適切に報告する。 | 5、6。（Context 7.3, CC-03, CC-07を維持） |
| RF-02交差: 指示修正（steering）やキャンセルと移動 | 指示修正やキャンセルの後に移動や遅延結果が到着。元のアクションやタスクに客観的事実を残し、古い結果を新しい目的の達成とみなさず、古い承認でキャンセルを解除しない。後続アクションを自動開始しない。 | 6。（Action 7, CC-03, CC-04を維持） |
| RF-05交差: スケジュール予定時刻とクライアント不在 | クライアント不在時にスケジュール時刻が到来。Host完結の作業は開始するが、クライアント確認が必要なステップは判断待ちにする。時刻到来を自動承認とみなさず、スキップされた回を勝手に穴埋め実行しない。 | 7。（CC-01, CC-04を維持） |
| RF-06交差: キャラクター削除後の遅延アクション結果 | キャラクター削除後に、そのキャラクターのアクション結果が届く。残っているタスク記録に必要な事実のみを記録し、削除されたキャラクターの学習データを勝手に再作成しない。 | 8.4。（Action 7.3, CC-03, CC-05を維持） |
| RF-07交差: 個人データ消去中の切断・再接続・再起動 | データ消去中に端末が切断またはHostが再起動。通信不能を「消去成功」とみなさず、古い一時データをHostに戻さない。未完了状態、安全保留、再保存防止をHostで維持する。新端末へのキャプチャ付け替えや過去操作のリプレイを行わない。 | 8、9。（Targeted Deletion 7.2, Context 8.2, CC-05を維持） |
| RF-08交差: バックアップ復元後の古い実行結果 | 復元切り替え前に開始された推論やツール結果が復元完了後に到着。復元前の古い実行状態を復元後の新マスターデータに混ぜず、タスクや学習データ、権限を勝手に復活させない。 | 8.3。（Context 8.1, Action 7.3, CC-03, CC-05を維持） |
| 全般: 補助推論の失敗や費用不明との競合 | 帰属判断や移動可否の判定のための補助推論が失敗したり費用不明になった場合、未承認のアクションや無条件の移動を勝手に先行実行せず、情報不足を管理画面に返す。停止、拒否、機械的な整合性検証は阻害されない。 | 3〜5。（Context 5.2, CC-06を維持） |

横断設計の原則（CC-01〜CC-07）の一般的な定義は [Cross-cutting Design](../architecture/cross-cutting.md) に記載されています。本ドキュメントでは、クライアント切り替えの観点から特に以下の点を具体化しています。

- **CC-01（権限と同一性）**：移動要求、呼び出し、自発的移動の由来と、正式な帰属成立およびアクション許可を厳格に区別すること。画面内の指示、観測の有効化、キャラクターの存在から勝手に権限を新設しないこと。
- **CC-02（情報選択の独立性）**：旧端末でのコンテキスト、キャッシュ、外部モデルセッションを、新端末の現在のコンテキストとして再利用しないこと。
- **CC-03（競合と調停）**：過去の帰属情報の正当性と、現在の用途への有効性を明確に分離すること。
- **CC-04（停止範囲と再開）**：自動リプレイや自動復帰の適用範囲を勝手に拡大解釈しないこと。
- **CC-05（データ保全と完全消去）**：クライアント端末に残る古い一時データからのデータの再保存や再形成を防ぐこと。対話ステップの終了を、システム全体の削除完了と混同しないこと。
- **CC-06（消費の連続性）**：制御や安全保全の処理をクライアントの移動完了待ちでブロックせず、機械的な帰属確認をLLMの応答待ちに依存させないこと。
- **CC-07（不変条件の維持）**：テキストが生成されたことだけで「ユーザーに提示された」とみなさないこと。

## 12. 本書が固定する契約と残す Design Freedom

下位の具象設計（concrete design）や実装コードは、本ドキュメントが定めた以下の不変ルール（契約）を前提として利用できます。

- 現在の存在（presence）は、Host PCが管理するキャラクターごとの正式な帰属記録だけが唯一の根拠です。クライアント側の画面表示、過去の記録、ヒント、一時データ、復旧先情報、外部モデルのセッション残骸は存在の根拠になりません。存在、Host側での活動継続、ネットワーク接続、権限はそれぞれ別の意味です。
- 切り替え処理の区間中は、旧端末・新端末のいずれも新しいアクション開始の根拠にしてはなりません。旧端末では実行中処理の安全な完了のみを許し、新端末では存在が正式に成立した後の新しい対話や試行のみを許します。二重存在、古い一時データのマスターデータ化、未完了操作の別端末での自動継続を禁止します。
- テキスト会話、音声会話、身体表示、画面・音声観測、PC操作、Host側タスク、キャラクター間交流、未伝達報告は、第5節の区切りルールに従います。「移動したから全停止」あるいは「何でも自動継続」という極端な一律処理は行いません。
- 移動や切断の最中に到着したデータは、元の帰属先、元の対話ステップ、元の試行に対応付けて記録し、用途ごとに受け入れ可否を厳格に判定します。新端末の活動へ勝手に付け替えたり、クライアント側のコピーでHostのマスターデータを上書きしてはならず、未送信操作を自動リプレイしてはなりません。
- Host側タスクが継続できるかの唯一の判断基準は「その処理に本当にクライアントが必要かどうか」です。通常のタスクを別端末へ物理移送したり停止したりせず、クライアントが必要なステップだけを待機させます。タスクAgentが操作対象のクライアントを勝手に選ぶことはできません。
- 切断の性質（一時的な瞬断、アプリ終了・通常切断、端末再起動、権限失効、Host再起動、停止との競合）に応じて、帰属の扱いを適切に切り替えます。再接続してきたクライアントの古いデータだけで存在や権限、タスク再開を勝手に成立させてはなりません。
- Host再起動後の存在復旧と、対話ステップ・PC操作・タスク・アクションの再開はまったく別の条件です。存在は元の端末へ自動復元されますが（利用不能なら端末不在として待機）、タスクやアクションの勝手な自動リプレイは禁止され、ユーザーの明示的な再開指示が必要です。
- 画面・音声観測の対象適格性は、Hostが管理する稼働中キャラクターの存在人数に厳格に連動し、移動、停止、切断のたびに見直されます。古い画面キャプチャの流用、停止中キャラクターの覚醒、同意の勝手な拡大解釈を行ってはならず、観測専用のモデル割り当てとキャラクター自身の推論条件を分離します。
- PC操作（Computer Use）は、現在キャラクターが存在している端末限定、安全な区切りまでの移動遅延、切断後の結果不明の保持、別端末やHostでの自動再実行禁止を厳格に維持します。端末に存在していることは操作の許可を意味しません。
- 試行と作用、認可判断、目的、実際の操作対象、進捗段階、確定度、停止保留との関係性を正しく保持・区別できない場合は、勝手に「成功した」「未実行である」と推定してはなりません。結果不明な操作は粘り強く「不明」として保持し、二重実行リスクを説明した上でのユーザー判断なしに再実行してはなりません。

本ドキュメントでは、新旧端末での二重存在、クライアント表示や一時データ・復旧先記録のマスターデータ化、古い対話やキャプチャ・操作結果の新しい活動への付け替え、クライアント側のコピーによるHostの上書きや自動リプレイ、Host側タスクの別端末への物理移送や一律停止、タスクAgentによる操作クライアントの勝手な選択、再接続や復旧に伴う存在・権限・実行の勝手な自動成立、別端末への無条件な自動移動、停止中キャラクターへの復旧適用、画面のない環境でのUI自動起動、存在復旧に伴うタスクやアクションの勝手な再開、結果不明な操作の勝手な成功・未実行への書き換えと自動リプレイ、要約や復旧時の勝手な確定度の格上げ、観測データの無条件配信、古いセッションによる制約の迂回、削除されたデータの古いクライアントコピーからの復活を、**採用不可能な選択肢**として明確に排除します。これらはいずれも上位のセキュリティ原則や不変条件を破壊するため、決して採用できません。

一方で、以下の項目は実装や具象設計に委ねられる自由度（Design Freedom）として意図的に残されています。

| 設計対象 | アーキテクチャとして固定された性質 | 実装に委ねる設計自由度（Design Freedom） |
|---|---|---|
| 帰属・対応関係・最新性の表現 | データの由来（provenance）を偽装できず、対象の変更・失効・切り替え・削除条件を各利用先で正しく扱えること。確認不能を勝手に許可・最新とみなさないこと。 | 帰属記録、データの由来、対話ステップ、試行、実行区間、完了境界の具体的なデータ構造。確認処理のまとめ方、対象探索・帰属調停処理の配置、識別子の形式、鮮度確認や競合制御のアルゴリズム。 |
| 切り替えと区切りの伝達 | 新規開始の即時禁止、ベストエフォートでの停止、遅延結果の適切な帰属、自動リプレイの禁止。受付と完了の分離。確定度を勝手に引き上げないこと。 | 切断検知の仕組み、帰属調停のアルゴリズム、対話ステップの区切り方、安全な操作区切りの具体的方法、キュー／アクター／イベントバス／ロック／トランザクション／IPC／プロセスの配置、リトライ回数・タイムアウト値。 |
| 再接続と復旧の実現方式 | 古い一時データのマスター化禁止、自動再開の禁止、元の端末への復旧と端末不在時の安全待機、別端末への無条件移動の禁止。 | 再接続、待機、タイムアウト、ペアリング、再配置ヒントの選択アルゴリズム、切り替え失敗時の戻り先選択、提示確認のUI実装、要約の粒度、未伝達メッセージの保持期間。 |
| 画面・音声観測の実装 | 存在人数や通知対象の現在帰属への厳格な連動、古いキャプチャの流用禁止、専用モデル割り当てとキャラクター側推論条件の分離。 | キャプチャの取得タイミング、端末間の負荷分散ロジック、候補イベントの打ち切り実装、routing contextの生成・更新方式、到達性確認方式。 |
| 重複防止情報の保持 | 試行と作用、判断、実際の対象、段階、確定度、保留との対応を保持・区別し、再起動・移動・再接続をまたいで勝手にリプレイしないこと。 | 識別子や冪等性キーの具体的な形式、データ保存の単位、DBスキーマ、リポジトリ構成、ログの保持期間、永続化が必要な未完了状態の具体的なデータ構造。 |
| 記録・報告・監査ログ | 元の事実の確定度、プライバシー、順序の意味、管理画面からの到達性を維持すること。本文の隠し保管庫を作らないこと。 | 監査ログの具体的なフォーマット、保存期間、提示確認のUI実装、要約の粒度、UIレイアウト、診断ログスタックの構成。 |
| 費用・消費・縮退 | 並列処理中、処理中、結果不明な消費も同じ利用枠上限に正しく反映し、制御と保全を維持すること。 | 費用の事前予約（リザーブ）方式、集計期間、推定計算のロジック、リソース配分の優先度、無限ループや反復呼び出しを抑制する具体的な機構。 |

Rustのcrateやモジュール構成、トレイトや型の定義、具象APIやエラー型、ミドルウェアやインターセプター、イベントバスやキュー、プロセス間通信（IPC）フォーマット、DBスキーマ、ロックやトランザクションの実装方法、具体的な認証情報の暗号化保護やサンドボックスの隔離方式、利用するライブラリやOS APIの選定、セッショントークンやハートビートの形式、タイムアウト値、UIアニメーションや音声バッファの管理なども固定しません。また、上記の対応関係を実現するために、全体を統括する巨大な「Contextレイヤー」や「Policy Engine」「万能Presence Manager」といった過剰な共通モジュールを新設する必要はありません。既存の12の責務、各データのマスター担当（semantic owner）、HostとClientの境界、および信頼境界（trust boundary）の範囲内で、最もシンプルで堅牢な実装方法を選択してください。

切り替え調停、切断検知、処理の区切り、再接続や復旧の待機方式、戻り先端末の選択、到達性の確認方式などの具体的な仕組みは、下位設計の自由度として委ねられます。しかし、必要な確認やユーザー判断の省略、同意の勝手な拡大解釈、未完了・結果不明な操作の成功扱い、外部操作の自動ロールバックや厳密に一度だけの実行（exactly-once）を勝手に保証することなどは、いずれも設計自由度には含まれません。
