# Context Assembly — 受渡し・利用・結果受入の詳細設計

本書は、用途の異なるサブシステム（責務）間で情報を選び、形式を変換し、LLM等の推論へ渡し、その結果を利用する際の一連のルール（論理的な契約）を詳細化するものです。なお、「Context Assembly（コンテキストの組み立て）」は新しい独立したサブシステムでもなければ、独自のマスターデータ（正本）を持つ仕組みでもありません。

## 1. 本書の位置付け

コンテキストの組み立ては、一見すると「プロンプトに含める情報をあちこちから集めてくるだけの単純な処理」に見えるかもしれません。しかし実際には、情報の受け手、利用目的、利用される時点が大きく変化する重要なセキュリティ・整合性の境界線（Boundary）です。ここで「Eneの内部にあるデータだから安全だろう」「一度データベースから取得できたのだから外部モデルへ送信してよいはずだ」「推論が成功したのだから結果をそのまま採用してよい」といった雑な判断をしてしまうと、各サブシステムを後からどれだけ厳密に設計しても、システム全体の安全性や整合性が崩壊してしまいます。

本書は、個別の情報選択アルゴリズムに先立つ「共通の受渡しルール」を定義します。これにより、アクション実行（Action Execution）、個人データの完全削除（Targeted Deletion）、クライアント切り替え（Client Presence Transition）の各重要領域が、この受渡し関係を前提として安全かつ独立に動作できるようにします。

## 2. 上位architectureとの位置関係

上位ドキュメントとの優先順位は [設計文書 README](../README.md#正本と優先順位) に従います。主に [Cross-cutting Design](../architecture/cross-cutting.md) の CC-02（情報選択の独立性）および CC-03（最新性と用途別受入）を詳細化し、ユーザーの意図（CC-01）、活動条件（CC-04）、完全消去への参加（CC-05）、費用の連続性（CC-06）、確定度の保持（CC-07）が、コンテキストの受け渡しを経ても損なわれないようにします。

各サブシステムの役割分担は以下のとおりです。

| 役割・サブシステム | 既存の責任と正当な判断権限 | コンテキスト処理が勝手に持ってはいけない権限 |
|---|---|---|
| 利用元（個体調整、作業、認識・学習、共有観測など） | 利用目的、必要な論理的情報、推論結果を何に利用するかの決定。 | 全用途共通の単一の目的を勝手に決める権限、独立したAgent権限の作成、すべての結果の採否を一括で決める権限 |
| 情報のマスター担当（Historyは個体調整、Taskは作業、Memoryは認識・学習、Characterなど） | 各データの内容、本来の意味、由来（provenance）、リビジョン、所属関係の提供。 | コピーしたデータを独立した新マスターデータにする権限、統一された全知の知識ストアの作成、外部原本の最新状態の勝手な代行 |
| 権限・制約 | ユーザーの意図に基づく制御、同意、明示的な非共有・保存禁止設定、最新の利用可否の照合。 | プロンプトのコンテキスト内だけで完結する勝手な「許可」や同意、スコープの書き換え |
| 推論 | 現在のモデル割当（assignment）の解決、モデルの能力・コンテキスト長への適応、実際の送信、利用量やエラーの管理。 | キャラクター情報の一方的な選別方針、独自の状態管理、結果の最終的な採用判断 |
| 実際の利用・受け入れ先（参照、変換、送信、保存、提示、アクションの各箇所） | 各段階でのセキュリティ制約の適用、意味のある結果の該当マスター担当への返却。 | 「推論が成功したこと」だけを理由とする権限昇格や、未完了操作の成功扱い |
| ライフサイクルの管理元（個体調整、作業、接続・存在、権限・制約、保全・消去） | キャラクターの稼働状態、タスク進捗、クライアント帰属、権限失効、全体操作の最新条件の提供。 | すべてを1つにまとめた大雑把な稼働フラグの作成、コンテキスト処理独自のデータ削除完了判断 |

認証秘密サブシステムは、認証専用の用途にのみ秘密情報（APIキー等）を供給し、通常のプロンプトコンテキストへ秘密の値を渡すことは決してありません。外部ファイルやMCPリソース等の取得は、実行・拡張サブシステムの正規のセキュリティ境界を経由します。コンテキストの組み立てを、「情報検索のため」と称して勝手な入出力（I/O）を行ったり内部マスターデータを直接書き換えるための裏口にしてはなりません。

## 3. 受渡しで保持する論理的な対応

### 3.1 要求の同一性と利用目的

情報を利用する側（利用元）は、「何の活動のために、誰の情報を、どのような用途に使うのか」という明確な目的を確立した上で要求を出します。単にキャラクターIDやタスクIDが同じであることだけでは、要求の同一性の証明にはなりません。少なくとも以下の対応関係を正しく保持します。

- **利用主体と用途**：誰が利用するのか（consumer）、利用用途、担当キャラクター、タスクや委任関係、ユーザーからの指示や指示修正（steering）の前提条件。
- **発生元の出来事**：元の入力メッセージ、発生した出来事、管理操作との関係。クライアント端末に依存する処理であれば、入力されたクライアント端末、対話ステップ（round）、観測イベントとの関係。
- **活動の継続関係**：一時停止前と再開（Resume）後、Host PCの再起動の前後、バックアップ復元（Restore）前の古い処理と復元後の新しい活動を正しく区別できる関係。
- **期待される利用先**：推論結果を何に使うのか（ユーザーへの返答、学習データの更新候補、通知の振り分け、権限の解釈、タスクの進捗判断など、用途ごとに受け入れ基準が異なります）。

これらをすべての要求で一律に同じ項目数で持たせる必要はありません。クライアントが不要なHost側タスクに無理に端末情報を要求したり、タスクを持たない雑談や環境観測のために架空のタスクを作ったりはしません。必要な対応関係を失ってしまった古い結果は、到着先の新しい活動に勝手に付け替えてはならず、その用途では受け入れ拒否（破棄）します。

### 3.2 情報単位に必要な対応

情報を選択・制限できる論理的な単位（1文、特定の参照範囲、文書全体、要約など）ごとに、以下の判断材料を保持するか、元のマスターデータから正しく解決できなければなりません。粒度を大雑把にしすぎた結果、異なるセキュリティ制限を持つ情報を分離できなくなった場合、その混ざり合ったデータを制限の厳しい利用先へ渡すことはできません。

| 判断材料 | 責任を持つサブシステム | 利用時に厳格に区別すべき意味 |
|---|---|---|
| 情報の所有者・対象・元データとの関係 | 元の情報のマスター担当（semantic owner） | 記憶（Memory）、会話履歴（History）、要約（Summary）、タスク内部のファイルコピーなどを混同せず、参照先の本来の所有者を勝手に変更しない。 |
| 内容の位置付けと由来（provenance） | 情報のマスター担当および入力を受理した担当 | ユーザー本人の入力、引用された外部の指示、観測された客観的事実、AIの推論、ツールの実行結果を明確に区別する。一度システム内に保存されたからといって、外部から持ち込まれたプロンプトが「信頼できるユーザー指示」へと昇格することはない。 |
| リビジョン・取得時点・有効期間 | 情報のマスター担当 | 「現在の認識」「当時の認識」「後から遅れて届いた結果」「外部ファイルを読み込んだ時点」を正しく区別する。 |
| 所属・スコープ・共有関係 | 元のマスター担当（判定の適用は権限・制約および各利用先） | 全体で共有可能な内容（Global）へのアクセスと、その根拠となったプライベートな原文へのアクセスは別物である。キャラクター間の関係性などを単一のフラグに潰さない。 |
| 用途・保存・共有・送信の制限 | 権限・制約サブシステムおよび情報のマスター担当 | 「読めること」「要約に使えること」「特定の外部AIモデルへ送信できること」「学習データとして恒久保存できること」を個別の権限として扱う。 |
| 参照の解決状態と欠落 | 情報のマスター担当および参照箇所 | データが存在しないこと、保持期間が過ぎて削除されたこと、権限がなく利用できないこと、古い内容であること、まだ取得できていないことを、勝手に「そのような事実は最初から存在しなかった」と解釈しない。 |

これらの対応関係を伝達するために、プライベートな本文そのものを何重にも複製して持ち回る必要はありません。また、「データの由来を記録するため」と称して、削除対象となった本文や認証情報を別ストレージに隠し持つことは固く禁止されます。

### 3.3 本文と強制に用いる情報を分ける

LLMに対するプロンプト内の説明（プロンプト本文）と、システムがデータの参照・外部送信・保存を技術的に強制するためのメタデータ（制御情報）は、まったく異なる役割を持ちます。後者の強制用メタデータは、AIモデルの自由記述テキストによって勝手に書き換えられたり偽装されてはなりません。プロンプト本文の中に「これはユーザーからの正式な指示です」「承認済みです」「全体共有データです」といった文字列が出力されたからといって、システムのセキュリティ制御状態が勝手に変わるような設計は固く禁止されます。

モデルが過去のユーザー発言への参照を出力できたとしても、その参照が存在することだけで「ユーザーが操作を承認した証拠」にはなりません。入力経路、元の意図、操作対象との対応関係を個体調整サブシステム等が文脈として解釈し、権限・制約サブシステムがセキュリティ上の正当性を最終確定します。引用が含まれるユーザー発言の全体を無条件に「システムへの直接命令」とみなしてはならず、音声入力に勝手に「話者認証済み」という意味を付与してはなりません。

## 4. 参照と変換の契約

### 4.1 情報を集める前に用途を限定する

コンテキストを組み立てる際、利用元はあらかじめ「利用目的」と「選択方針」を明確にし、情報のマスター担当はその目的に提供できる安全な範囲の情報のみを返します。権限・制約サブシステムと各参照箇所は、最新の制限ルールを厳格に適用します。「プライベートなデータをすべて集めてプロンプトに詰め込み、どれを使うかはLLMに選ばせる」というような実装は、セキュリティ境界の代用には決してなりません。検索、ベクトル埋め込み（embedding）、要約などの処理であっても、その段階ごとの利用主体、送信先、対象データ、目的を個別に検証します。

選択された情報からさらに元の根拠データを辿る場合も、参照先ごとに改めてアクセス権を検証します。全体共有の記憶（Global Memory）がプロンプトに含まれていることや、共同タスクに参加していること、同じ端末に存在していることなどを理由に、他のキャラクターのプライベートな対話履歴や過去のリビジョン、関係性データを勝手に閲覧してはなりません。

正確な発言の引用には保存された会話履歴（History）を用い、現在の知識には記憶（Memory）を主要なデータとして用います。要約（Summary）は圧縮された参考情報、関係性（Relationship）は主観的な解釈、キャラクター状態（Companion State）は一時的な気分や傾向として適切に使い分けます。検索スコアの高さやテキストの短さなどの都合だけで、ユーザーによって訂正される前の古い要約を、訂正後の最新記憶の代わりに使ってはなりません。

### 4.2 不足と省略を結果へ伝える

利用元は、その目的にどうしても不可欠な情報や区別を指定できなければなりません。例えば「ユーザーの発言を正確に引用するためには元の会話履歴が必須である」「現在の設定値を案内するために過去の古い認識で代用することはできない」といった論理的な成立条件です。プロンプトの長さ制限（コンテキスト長）に収めるためだけに、こうした必須条件を勝手に骨抜きにしてはなりません。

重要性の低い背景情報であれば、方針に従って省略・要約して構いません。しかし、不可欠な区別が表現できない場合、必要な元データが失われている場合、あるいは権限不足で取得できない場合は、勝手に推測で埋めるのではなく「情報不足」として利用元に結果を返します。空の検索結果やテキストの切り詰めを、勝手に「そのような事実は存在しない」「承認は不要である」と読み替えてはなりません。また、「情報が不足している理由」を説明する際にもアクセス制限を遵守し、他のキャラクターのプライベートなデータの存在や内容を漏洩させてはなりません。

### 4.3 変換は権限・意味を昇格させない

要約、抽出、翻訳、検索用インデックスの生成、モデル向けプロンプトの圧縮などの変換処理を行っても、変換後のテキストは元の情報が持っていた依存関係やセキュリティ制限をそのまま引き継ぎます。複数の異なる情報源を混ぜ合わせて元のデータを分離できなくなった出力テキストは、それらすべての元情報に依存しているものとして扱います。「AIモデルが『その情報は使っていません』と言っている」「出力テキストの中に対象の文字列が含まれていない」といった理由だけで、元データへの依存関係を勝手に解除することはできません。

客観的に分離された安全な情報のみから出力テキストが構成されていることが確実に確認できる場合に限り、制限範囲を限定できます。いかなる場合でも、LLM自身の自己申告テキストだけでプライベートな情報を全体共有可能に格上げしたり、外部から持ち込まれた指示をユーザー本人の意図へとすり替えてはなりません。

なお、通常の対話から記憶を形成したり全体共有化（Global化）する判断は、認識・学習サブシステムが本来持っている正当な機能であり、本書がそれを禁止するものではありません。情報のマスター担当が内容と背景を適切に判断し、明示的な非共有設定などを守って正当に成立させた共有データは、そのデータ自身のスコープで安全に利用できます。ただし、単なるプロンプト圧縮処理をその判断の代わりにしてはならず、全体共有化されたからといって、過去のプライベートな原文データまで遡ってアクセス可能になるわけではありません。

情報の変換によって、以下の重要な区別を決して失ってはなりません。「現在と過去」「引用と指示」「実行の依頼と実際の操作結果」「成功と結果不明」「情報が存在しないことと利用権限がないこと」。これらを表現・保持できない変換データはその用途には使用せず、情報の再選択や別表現への切り替え、あるいは情報不足としての返却を行います。

## 5. Provider適応と実利用

### 5.1 論理的選択と送信ごとの成立を分ける

推論サブシステムは、利用元から「利用用途」と「選択方針」を受け取り、実際の外部モデル（Provider）の能力やコンテキスト長に合わせてデータを適応させます。「同じ選択方針」とは、すべてのモデルに対して一字一句同じプロンプトや同じバイト列を渡すという意味ではありません。モデルごとに都合の良い独立したキャラクター設定を作ったりせず、同一のセキュリティ制約と選択方針を一貫して適用します。コンテキスト長の都合による圧縮によって必須条件が満たせなくなる場合は、利用元に情報不足を返すか、許された方針の範囲内で安全に再選択を行います。

最初の送信だけでなく、フォールバック先のモデルへの再送信、通信エラー時のリトライ、埋め込みや要約のための補助的な推論、さらには継続的なやり取りを伴うセッション利用の各ステップにおいても、実際の送信ごとに以下の条件をすべて満たす必要があります。

1. 現在の活動・用途に正しく対応し、現在利用が許可されている情報のみを含んでいること。
2. 解決されたモデル割当（assignment）と、実際の送信先、送信データ、利用目的、データの取り扱い条件、費用に関するユーザーの同意が完全に一致していること。
3. 現在の認証情報、利用枠制限、該当する安全保留、利用量の上限を満たしていること（APIキーなどの秘密情報はプロンプト本文に決して含めないこと）。
4. 送信するテキスト、参照するモデル側のコンテキスト、返ってきた推論結果が、元の要求と許可された情報範囲に対応していること。

事前にモデルの送信先が設定されていること自体は、包括的な送信許可を意味しません。フォールバック処理は、ユーザーが事前に承認した候補と順序に厳格に従い、切り替え先のモデルについて改めて条件を照合します。「同意が得られていないから」といってプロンプトのテキストを勝手に削って黙って送信してはならず、実際に送信されるデータと用途について正当な同意が成立していることを確認します。

利用した費用の実績値、推計値、不明な消費は、元の用途と実際の利用先に対応付けて正確に記録します。推論の失敗、フォールバック、コンテキストの再構築が発生したからといって、これまでに消費した利用量を勝手にゼロにリセットしてはならず、複数の並列処理が同じ残り利用枠を勝手に二重消費できるようにしてはなりません。

### 5.2 cache・session・Client経路

Eneが管理するキャッシュ、ベクトル埋め込み、検索結果、圧縮済みコンテキストを再利用する場合であっても、データの内容だけでなく、元の情報範囲、利用目的、最新の有効性を必ず確認します。「キャッシュにヒットしたから」という理由だけで、元データへの参照確認やセキュリティ制約の検証を省略してはなりません。通常のログ保存期間が過ぎて元の会話履歴が失われた場合と、個人データの完全削除（targeted deletion）によってデータを消去すべき場合を厳格に区別します。前者の場合でもすでに形成された学習データを勝手に削除することはありませんが、後者の場合はキャッシュデータを代替の根拠として残してはなりません。

外部モデル側のセッション（会話履歴キャッシュなど）に過去の情報が残っている場合、その情報も今後の生成に影響を与えうる入力データとして扱います。現在使えない情報（削除されたデータや失効した権限など）が含まれているセッションに対して、最新の短いプロンプトだけを渡して推論を継続させることはできません。安全な別のセッションへ切り替えるなど、現在の条件を満たせない限り、その古いセッションを再利用してはなりません。

クライアント端末からの直接送信やプロトコルプラグインを利用する場合にも、これらとまったく同一の条件を適用します。すべての通信が必ずHost PCを中継しなければならないと強制するわけではありませんが、クライアント側の古い設定コピーや外部コードが独自に同意や最新性を決めてはなりません。Host PCの最新条件を確認できないクライアントは処理を継続してはならず、一時的なデータを「第2の正本」にしてはなりません。

外部サービスから返ってきたエラーや結果の中に、登録済みの認証情報（APIキー等）が含まれていた場合も、受け入れ、変換、推論利用、送信、保存、画面提示、消去を含むすべての箇所で非露出の保護を徹底します。プロンプトに入れる前に除外したことだけで安全とみなしてはなりません。デバッグログやエラー説明のために秘密情報を通常のログ本文に取り込んではならず、安全な失敗情報のみを扱います。

権限の判定や、個人データ削除の対象を探索するための補助的な推論も例外ではありません。その推論自体が正規の利用条件を満たしている必要があり、審査対象のアクションの実行を先行条件にしてはなりません。推論が失敗した場合は「情報不足」として返し、システム本来の安全停止、拒否、管理画面の操作、機械的な整合性検証をブロックしてはなりません。

## 6. Observerの限定routing contextへの適用

画面・音声観測（Observer）は、本書の受渡しルールが適用される代表的な複合ユースケースです。観測機能全体や自発的行動のすべてをここで設計するわけではありませんが、情報の境界を明確にするために以下のルールを定めます。

### 6.1 原ownerからの提供

共有観測機能は、現在対象となっているクライアント端末やそこに存在するパートナー、および通知振り分け（routing）という用途を明確にし、個体調整サブシステムとの協調を通じて必要な「限定されたコンテキスト」を受け取ります。会話履歴は個体調整、記憶は認識・学習、タスク情報は作業サブシステムがそれぞれ管理し、提供範囲を決定します。Observerが各サブシステムのデータベースを勝手に直接読み出すような裏口は作りません。

提供されたコンテキストは、対象キャラクター、元データ、用途、制限、選択時の前提条件が追跡可能な「一時的な派生データ」として扱います。これを保存して「Observer専用の恒久的なキャラクター状態」といった新しいマスターデータに格上げしてはなりません。キャラクターの話題や作業タスクが変化したときは、元のマスター担当がその変化と提供済みコンテキストの整合性を判定できる必要があります。

コンテキストの要約生成に推論モデルを使用する場合は、その要約処理自体のモデル割当、同意、費用条件を満たすとともに、元データの利用制限を維持します。最終的にObserverへ送信する際の許可と、要約を生成する段階での許可を混同してはなりません。

### 6.2 routingの利用範囲とdeliveryの分離

環境観測イベントの検知や担当キャラクターへの関連付けは、「Observer専用のモデル割当」で行います。キャラクター個別の設定上書きや同意を勝手に合成してはなりません。限定的なプライベート文脈を利用する場合であっても、元データの利用制限を守った上で、その情報と用途について専用モデル割当の送信条件を満たす必要があります。

この専用割り当てによって許可されるのは、あくまで「観測イベントがどのキャラクターに関連するかを判定すること」だけです。共有観測機能が複数キャラクターの文脈を扱えるからといって、その入力内容や生成された説明全文を各キャラクターへ自由に公開してよいわけではありません。以下の3つの受渡しを厳格に分離します。

| 受渡しの段階 | 成立する内容と判断 | セキュリティ境界 |
|---|---|---|
| 関連付け結果 → 共有観測 | 観測イベントと、それを受け取るべきキャラクターの対応関係。共有観測機能が現在の対象や用途と照合して採否を決定。 | AIモデルが勝手に対象キャラクターやクライアントを追加したり、イベント本文から所属や権限を変更することはできない。 |
| イベント通知 → 対象キャラクターの個体調整 | そのキャラクターが利用可能な観測内容と必要な背景情報。キャプチャ元端末、取得日時、イベントとの対応関係を維持。 | 他のキャラクターのプライベートな文脈や、その文脈に依存した説明文を一緒に添付して共有してはならない。 |
| キャラクターの理解 → 学習・発話・タスク等 | 受け取ったキャラクターが、自身の目的と現在の条件に基づいて理解し、行動の採否を決定。 | Observerでの処理成功を、キャラクター側の推論成功、送信同意、アクション実行許可と同一視してはならない。 |

例えば、キャラクターAとBの限定コンテキストを用いて「このイベントはA向けである」と判定された場合、その宛先情報は利用できます。しかし、「Bのプライベートな予定と比較した結果、Aを選びました」といった推論理由のテキストをキャラクターAのプロンプトに渡してはなりません。イベント本文は、利用可能な元のキャプチャ範囲のみから構成します。安全な情報とプライベートな情報が混ざり合って分離できない場合は、そのテキストをキャラクターへ渡さずに破棄するか、安全な情報のみで再構成します。AIモデルの「Bの情報は含めていません」という自己申告を鵜呑みにしてはなりません。

### 6.3 鮮度と観測制御

イベント通知をキャラクターへ届ける（delivery）直前には、対象クライアント端末、存在しているキャラクター、観測の停止設定、利用条件、個人データ削除の保留状態を必ず再確認します。移動前の端末で取得されたキャプチャを移動先端末のものとして流用してはならず、停止中（Stopped）のキャラクターを通知のために勝手に起こしてはなりません。プライベートな文脈の利用制限、同意の失効、データ消去が発生した場合は、生成済みの要約や処理中の結果に対しても直ちに適用します。

観測が一時停止（Pause/OFF）された際に、処理中だったイベントを破棄するか再評価するかは実装の自由度です。ただし、すでにキャラクターが認識した経験データは別個のライフサイクルであり、観測がOFFになったり端末が移動したことだけで勝手に消去されることはありません。イベントを受け取った後のキャラクター自身の推論処理は、独立した新しい利用として第5節のルールに従います。

## 7. 現在性と用途別受入の状態遷移

### 7.1 コンテキストの組み立て完了は「利用の承認」ではない

コンテキストの準備から推論結果の活用までは、以下のように段階を踏んで論理的に進みます。これらは単一の巨大な固定ステートマシンにする必要はありません。必要に応じて再選択したり、処理を分割・並列化したり、あるいは推論モデルを通さずにそのまま使うことも自由です。ただし、**「ある段階をクリアしたからといって、その先のセキュリティ境界や承認手続きをスキップしてよい」わけではありません。**

| 段階・状態遷移 | 成立条件 | 変化・失敗時の取り扱いと責任 |
|---|---|---|
| **用途の確立 → 参照・選択** | 利用元が現在の目的や活動内容を確定させ、情報マスター（owner）と参照元がアクセス可能範囲を適用します。 | 主体や目的が曖昧だからといって、勝手に広範な権限スコープへ置き換えてはなりません。情報が不足している場合は利用元へ不足エラーを返します。 |
| **選択 → 利用表現の準備** | 元データとの対応関係、重要な区別、省略や不足の有無、変換後の制約（秘密保持など）を維持したままプロンプト等を整形します。 | 途中で情報が変われば再選択・再構成します。「送信準備が整った」からといって、送信してよい承認が得られたわけではありません。 |
| **準備 → 個々の実利用** | 送信先（推論モデルや外部ツールなど）が、現在の目的・データ内容・活動状況・ユーザー同意と合致しているかを直前に照合します。 | 照合の前提条件が崩れたら即座に再評価します。条件を満たさない利用は保留または拒否します。 |
| **実利用 → 結果到着** | 推論モデル等から、元のリクエスト・入力範囲・トークン消費量・成否などの情報とともに結果を受け取ります。 | 通信（トランスポート）が成功したことと、内容が業務として正しいことは別です。モデルが対応できなかった結果を、正常な回答として取り込んではなりません。 |
| **結果到着 → 用途別の採否** | 結果を受け取る各機能（マスター）が、現在の制約や文脈と照合し、自分の用途にのみ結果を採用します。 | 履歴記録、学習、ユーザー提示、次のツール実行などは個別に採否を判断します。どこか一つの機能が採用したからといって、他の用途まで自動許可されることはありません。 |
| **処理中 → 無効化・利用終了** | 処理中に停止（Stop）、同意失効、データ消去、タスク終了などが起きた場合、遅れて返ってきた結果も含めて無効化します。 | 各コンポーネントが一時データや遅延結果の破棄を引き受けます。ただし「処理を試みた事実」や「未完了のタスク」など、記録しておくべき事実は本来のマスターへ正確に残します。 |

### 7.2 鮮度は「用途に必要な前提条件」との関係で決まる

「データを取得した時点で正しかった情報」と、「今この瞬間も利用して問題ない情報」は異なります。
各機能は、どのような前提条件（ユーザーの同意、権限、現在のタスク目的など）に依存して利用可能と判断したかを意識し、利用直前にその前提が変化していないかを検証しなければなりません。重要な前提条件の変更を見落としたまま実行してしまうような実装は禁止です（具体的な競合制御や変更検知の仕組みは実装設計で選択します）。

利用開始と制約の変更が同時に起きた場合は、どちらが先に成立したのかを矛盾なく説明できなければなりません。
- 制約変更が成立した後に新しく始まる処理には、古い判定を流用してはなりません。
- すでに開始してしまった処理には、停止要求を送り、遅れて返ってきた結果を破棄するなどのルールを適用します。
- 前提条件が現在も有効か確認できない場合は、安全側に倒し、利用を許可しません（すべてのドメインで厳密なミリ秒単位の時刻同期や単一トランザクションを求めるわけではありません）。

固定の有効期限（TTL: Time To Live）だけに頼る方式では、スコープの失効、緊急停止（Stop）、データ消去に対応できません。一方で、無関係なメモリの更新があったからといって、すべてのコンテキストを無効化してユーザーへ再承認を求めるのも過剰です。
情報の意味的な鮮度は情報マスターと利用元が管理し、制約の現在性は権限管理と実際の利用先が管理します。古い情報は「過去の出来事の記録」としては正当ですが、「現在の最新状態」や「現在の承認」の代わりとして使うことはできません。

複数の情報マスターから集めたデータを使う場合、それらが完全に同一瞬間のスナップショットである必要はありません。ただし、「ユーザーが目的を方向転換（ステアリング）したのに、以前の古い委任範囲のまま推論を継続する」といった致命的な矛盾がある場合は、結果を採用せず最初から再評価します。「データが全体として整合しているか」という判断を、コンテキスト専用の別機能に丸投げしてはなりません。

### 7.3 推論結果の依存関係と、各機能による採否判定

推論モデルから返ってきた結果は、少なくとも「プロンプトに入力したすべての情報」に依存している可能性があります。単に「同じリクエストへの返答だから」という理由で、入力データの制約を無視して自由に扱える新しいデータにしてはなりません。
モデルの出力テキストに機密データがそのまま含まれていなくても、元データにあった消去要請・非共有・保存禁止のルールをそのまま引き継ぎます。

受け取った結果を実際に採用するかどうかは、各マスターが以下のように厳密に判断します。

| 結果の利用先 | 正本としての受入・採否の判断（Authoritative） | 受入が意味「しない」こと（禁止事項） |
|---|---|---|
| **会話・ユーザーへの伝達** | キャラクターの人格・会話管理が、現在の会話の流れや未伝達事項と照合し、UI表示機能が現在の所属端末へ正しく提示します。 | 「モデルがテキストを生成した」＝「ユーザーへ提示完了した」とみなすこと。端末移動前の過去の会話ターンへ勝手に出力すること。 |
| **タスクの判断・進行** | タスク管理機能が、現在の目的、ユーザーからの方向修正（ステアリング）、委任範囲、現在の進行状態と照合します。 | 古い目的に対する回答を新しい目的の達成とみなすこと。キャンセルされたタスクを勝手に再開すること。 |
| **学習・要約（Learning）の形成** | 認識・学習機能が、現在のキャラクター認識、根拠、権限スコープ、保存条件と照合して記憶に定着させるかを決めます。 | 後から届いた結果を「より新しい確実な根拠」と過信すること。タスク用の作業コンテキストをそのまま無差別に永続記憶化すること。 |
| **権限・ルールの解釈** | 権限・制約管理機能が、ユーザー本来の意図や対象リソースと照合して、セキュリティ上の判断を確定します。 | モデルが「実行してよい」と出力したことを「権限ルールが緩和された」と誤認すること。1回の許可を恒久的な許可ルールへ格上げすること。 |
| **次のアクション・ツール実行候補** | 利用元がアクション候補を受け取り、実行エンジンおよび権限管理機能の「現在の実行条件」へ引き渡して審査します。 | 「コンテキストが有効だからアクションも承認済み」とみなすこと。モデルがツール呼び出しを出力した時点で「すでに実行された」と錯覚すること。 |
| **実行実績・トークン消費量の記録** | 実行エンジン、推論基盤、タスク管理などの本来のマスターが、元のアクションやリクエストと紐付けて事実を記録します。 | タスクがキャンセルされたからといって、実際に起きた実行事実を破棄すること。「成否不明」を「未実行」と都合よく解釈すること。「事実を記録できた」からといって「後続のアクションも自動実行してよい」とみなすこと。 |

ストリーミング出力や部分的な結果を受け取る場合も同様です。新しく保存・送信・画面表示・アクション実行へ渡す部分ごとに、上記の受入条件を個別に満たす必要があります。「必ず全文が届くまで待て」とまでは言いませんが、「未検証のまま先にユーザーへ表示してしまい、後から間違いに気づいて取り消そうとする」ようなやり方は認められません。すでにユーザーの目に触れたり外部へ作用してしまった事実を取り消すことはできないため、起きた事実を正しく把握し記録します。

## 8. 中断・再起動・データ消去への参加

### 8.1 中断・変更時の再構築ルール

実行環境やデータに変化が生じた場合、コンテキストと推論結果は次のように扱います。

| 状態の変化 | コンテキストおよび推論結果の取り扱い |
|---|---|
| **メモリの訂正・スコープ変更** | 関連する情報を現在の用途に合わせて再照合します。認識・学習機能による訂正を、古い記憶形成結果で無条件に上書きしてはなりません。また、過去の出来事の履歴そのものを改ざんしてはなりません。 |
| **ステアリング・キャンセル・委任終了** | 古い目的や以前の委任範囲で生成された推論結果を、現在のタスクへ自動的に採用してはなりません。すでに実行されてしまったツールの事実などはタスク履歴に残せますが、新しいアクションの開始とは厳密に分離します。 |
| **キャラクターの停止（Stop）・削除** | 新しい活動やコンテキスト組み立てを開始しません。再開（Resume）した際も、停止前のリクエストを現在のリクエストと混同してはなりません。削除後に監査用として残すべきタスク記録と、二度と作ってはならない個体の学習データは厳密に区別します。 |
| **クライアント端末の移動・切断** | クライアント依存の入力、出力、画面キャプチャを現在の所属端末と照合します。クライアントが切断されたからといってHost側のバックグラウンド処理まで一律停止させる必要はありませんが、「推論結果が生成されたこと」と「ユーザー端末へ実際に表示されたこと」は区別して管理します。 |
| **同意・認証情報・デバイス接続の失効** | これらに依存する新しい処理の開始を直ちに禁止し、実行中の処理はベストエフォートで速やかに停止します。別のプロバイダや別キャラクターを経由して制約を迂回してはなりません。すでに送信・実行してしまった事実を「なかったこと」にはできません。 |
| **推論失敗・能力不足・コスト上限超過** | 成功したかのようなダミー結果を捏造してはなりません。利用元へ不足・失敗・不明の事実を正確に伝えます。許可されたフォールバック処理（別モデルへの切り替えなど）を行う場合も第5節の安全基準を維持し、保存されているマスターデータを破壊しません。 |

Hostサービスが再起動した後は、永続化されているマスターデータ（正本）から、現在の目的に必要なコンテキストを改めて再構築します。キャッシュに残っていた過去の派生データを再利用することは自由ですが、過去のリクエストに対する利用許可や実行処理をそのまま自動再開してはなりません。
- 途中だったタスクは、ユーザーからの明示的な再開指示を待ちます。
- 定期スケジュールは、将来の予定回として現在の条件で再評価します。
- 稼働中だったキャラクターは、元のクライアント端末への接続復旧という通常のルールに従います。

バックアップからの復元（Restore）時は、「復元前の古い生リクエストや遅延結果」と「復元されたマスターデータ」を明確に区別します。復元後は自動処理を一旦保留し、ユーザーの確認を経てから一括で有効化します。Host内の認証情報ストアは最新のものが保持されますが、古いコンテキスト内にあった参照情報だけで勝手に認証が成立したとみなして再実行してはなりません。

「再構築が可能であること」は、「すべてのプロンプトや推論の思考プロセスを永久保存せよ」という意味ではありません。継続して必要なタスク状態、未伝達メッセージ、成否不明のアクション、未完了のデータ消去などを本来のマスターが確実に保全していれば十分です。一時バッファが消えたことを「処理が成功・完了した証拠」と取り違えてはなりません。

### 8.2 個人データの完全削除（Targeted Deletion）への参加

コンテキストを保持・変換・送信・受領するすべてのコンポーネントは、個人データの完全削除（targeted deletion）処理に対して、自分がどの範囲を消去すべきかを明確に説明できなければなりません。
データを永続化しているストレージだけでなく、以下のすべてが削除対象に含まれます：
- 現在処理中のプロンプトやコンテキスト
- 検索用のインデックスや要約・圧縮された派生データ
- Eneが管理している各種キャッシュ
- クライアント端末や拡張機能側にある一時コピー
- 外部推論モデルから遅れて返ってくる可能性のある結果

各コンポーネントは、対象の元データとの関係、処理中のリクエスト、局所的な消去と検証、再保存の防止、確認不能・未完了の状態を確実に追跡できるようにします。
「元データを削除した途端に依存関係の情報まで消えてしまい、後から遅れて届いた推論結果が削除対象かどうか識別できなくなった」という事態は絶対に防がなければなりません。本文そのものは保持せずとも「このデータに依存している」というメタデータだけは追跡できるようにします。

消去処理が始まってから完了するまでの間に、外部モデルから遅れて返ってきたデータや新しく生成されたデータも削除対象に含めます。元データの追跡だけでは漏れが生じる可能性があるため、処理中のデータに対しても消去条件を適用します。ユーザーから指定された文字列については、機械的な検索・除去・残存確認を行い、痕跡を残さないようにします（意味的に同一な表現の自然言語による完全検出までは保証しません）。

局所的な削除を行った後、古いコンテキストや遅延結果、再接続してきたクライアント端末から削除対象データが再流入してはなりません。ツールを実行した事実などは個人データの本文を含まない形で記録し、監査ログや完了報告を復元源にしてデータが復活することがないようにします。
通信が途切れたクライアント端末や外部処理について勝手に「削除成功」と決めつけてはならず、局所的な削除完了をもってシステム全体の消去完了と誤認してはなりません。

Hostサービスが再起動しても、未完了の消去タスクや必要な保留状態を失ってはなりません。消去が完了した後は、削除前の情報に基づいてデータが再形成されたり遅延保存されたりするのを防ぎます。ただし、消去完了後にユーザーが改めて自発的に提供した情報は「新しい経験（Experience）」となるため、同じ文字列の入力を永久に拒絶するような過剰な制限は設けません。

Eneが直接管理している内部コピーは1つ残らず削除対象としますが、外部ワークスペース、ユーザー自身が保管している手動バックアップ、AIプロバイダ側が保持する一時ログなどは内部コンテキスト消去の対象外です。

## 9. 主要ランタイムフロー（Runtime Flows）と横断設計（Cross-cutting）の検証

[Major Runtime Flows](../architecture/runtime-flows.md) の主要フロー（RF-01〜RF-08）および競合ケースにおいて、コンテキスト組み立てがどのように正しく機能するかを以下に示します。

| フロー・交差する場面 | 処理の流れと保証される結果 | 本ドキュメントの該当節 |
|---|---|---|
| **共通推論区間のフォールバック** | 同じタスクで軽量モデルへ切り替えます。論理的な選択ポリシーを維持し、情報の由来や現在性が失われるような過剰な圧縮は行わず、モデルごとの同意・コスト制約を個別に適用します。 | 4.2〜4.3、5.1。推論モデルは情報や権限のマスターにならない。 |
| **RF-01 会話から学習への反映** | ユーザーが前言を訂正した直後に、古い要約に基づいた記憶形成結果が到着。認識・学習機能が現在の最新認識と照合し、古い結果で無条件に上書きしません。会話履歴にない発言を勝手に捏造して補うことも防ぎます。 | 3.2、4.1、7.2〜7.3。最新の知識と客観的な根拠を維持。 |
| **RF-01 共有メモリの参照** | 共有メモリ（Global Memory）からプライベートな根拠情報を辿ろうとした場合、参照先のアクセス権限を個別にチェックします。共有メモリの要約本文は使えても、他者のプライベートな根拠は漏洩させません。 | 4.1、4.3。共有用の不正な第2の正本を作らない。 |
| **RF-02 委任タスクとアクション** | ツール実行結果のプロンプト内に「ユーザー承認済み」というテキストが含まれていても、情報の由来はあくまで「外部データ」として扱われます。実際のアクション実行には、実行エンジンによる現在の権限審査が必須です。 | 3.3、7.3。LLMの出力や委任関係によってセキュリティ制御を勝手に書き換えない。 |
| **RF-02 キャンセルとの競合** | タスクがキャンセルされた直後に、古い承認候補やツールの実行結果が到着。次のアクションは開始せず、すでに実行された事実（または成否不明の事実）のみをタスク履歴へ正確に残します。 | 7.3、8.1。結果を全破棄することも、無条件に採用することもしない。 |
| **RF-03 共有環境での観測と個体理解** | キャラクターA・Bが存在する限定空間でAへのルーティングが発生。他者のプライベートな文脈が混ざった情報は送らず、Aが利用可能なイベントのみを構成します。A側の推論プロバイダに同意がなければ送信は成立しません。 | 6.1〜6.2、5.1。専用の割り当て（assignment）とキャラクター側の同意を分離。 |
| **RF-03 観測の遅延と停止** | 画面キャプチャの要約中にスコープが変更されたり、取得後にキャラクターが停止（Stop）した場合、配送直前に再照合し、停止中のキャラクターを勝手に起こしません。すでに認識された経験データは、観測がOFFになっただけで消去されることはありません。 | 6.3、7.2。由来の管理とデータのライフサイクルを分離。 |
| **RF-04 端末移動と切断** | 移動前の端末からの入力が遅れて届き、同時にHost側のタスク結果も完成。移動前のキャプチャを新端末のものとして流用せず、完成したタスク結果は「未伝達」として保持します。 | 3.1、6.3、7.3、8.1。クライアント端末の切断を理由にHost側の処理を全停止させない。 |
| **RF-05 再起動とスケジュール** | Host再起動時、古いコンテキストキャッシュが残っていても中断タスクはユーザーの明示的な再開を待ちます。将来の定期スケジュールは新しいタスクとして現在の条件で組み立て、見逃した過去回を勝手に連続再生しません。 | 7.1〜7.2、8.1。端末への復旧（presence）とタスク再開を分離。 |
| **RF-06 キャラクター停止と削除** | 削除処理の完了後に、過去の学習候補やツールの実行結果が遅れて到着。キャラクターの記憶（Learning）を再作成することはせず、監査上必要なタスク実行記録のみを安全に管理します。 | 7.3、8.1。記録の保持を理由にキャラクターデータの削除を免除しない。 |
| **RF-07 データ消去との競合** | 内部データを消去した直後に、推論結果や新しい入力として同じデータが到着。これらもすべて消去処理へ参加させ、局所的な削除だけで「全域完了」と誤認しません。 | 8.2。元データの追跡だけで消去対象を狭めない。 |
| **RF-07 消去後のプロバイダセッション** | 外部AIプロバイダのセッションに対象データが残っている場合、プロンプトを短くしただけでそのセッションを再利用してはならず、条件を満たす安全な経路へ切り替えます。消去後にユーザーが改めて自発的に提供した入力は、過去の削除データとは区別して扱います。 | 5.2、8.2。外部ログの免責を理由に内部での再形成を許さない。 |
| **RF-08 バックアップからの復元** | 復元後に復元前の生リクエスト結果が到着しても、復元されたマスターデータへ混ぜず、過去の実行記録として分離します。認証情報は現在の最新ストアと照合し、復元直後の自動実行保留を徹底します。 | 8.1。復元された古い同意や参照情報からアクションを勝手に復活させない。 |
| **全フロー共通: 補助推論の失敗** | 権限チェックやデータ消去の探索を行う補助モデルが障害でダウンした場合、安全確認が取れていないアクションを先行実行してはならず、不足エラーを返します。安全のための停止・拒否・機械的検索は継続できます。 | 5.2、7.1。障害時であってもセキュリティ境界を迂回しない。 |

横断設計（Cross-cutting Design）の基本原則（CC-01〜CC-07）に対して、本ドキュメントでは以下の点を具体化しています：
- **CC-01（権限と由来）**: 入力の由来（provenance）はプロンプトのテキスト本文から完全に分離します。権限の最終確定は既存の権限管理機能が行い、ツールの実行可否は実行エンジンが直前に判断します。
- **CC-02（セキュリティ境界）**: 参照元、データ変換、補助推論、キャッシュ、プロバイダセッション、クライアント端末の通信経路のすべてに、一貫した権限スコープを適用します。
- **CC-03（アイデンティティと活動）**: 同一の主体（ユーザー／キャラクター）であっても、リクエストや活動が異なれば別個に扱い、「一度コンテキストが承認されたから何でもしてよい」というような単一の巨大な有効フラグに権限を集約させません。
- **CC-06（安全な失敗とコスト管理）**: プロンプト変換、再試行、フォールバックも1回の「利用」として正確にカウントし、トークン消費を追跡します。推論モデルが正常に返答するまで安全管理を待たせるようなことはしません。
- **CC-07（監査と観測性）**: データの省略、利用不可、成否不明を「成功」や「事実の不在」にすり替えてはなりません。生成されたこと、採用されたこと、ツールが実行されたこと、ログに記録されたこと、画面に表示されたことのそれぞれの確定度を明確に区別します。

## 10. 本ドキュメントが固定する契約と、実装に残す自由度（Design Freedom）

後続のサブシステム設計や具体的な実装設計は、以下の原則を**固定された不変の契約**として前提にします：

1. **コンテキストは用途限定の派生データである**: 元のマスターデータ、リクエスト、情報範囲、利用前提との対応関係を常に保持します。「すべての用途を束ねる万能のコンテキストマスター」は作りません。
2. **各フェーズの境界をスキップしない**: 参照、変換、送信、結果の保存、画面提示、ツール実行はすべて独立したセキュリティ境界です。「取得できたから送信してよい」「推論が成功したから実行してよい」という短絡は許されません。
3. **由来と制約はプロンプト本文で上書きされない**: モデルの出力テキストによってシステムの権限や由来を改ざんすることはできません。情報が混ざり合って分離できなくなった場合は、最も厳しい制約を全体に適用します。
4. **プロバイダ適応時も論理ポリシーを維持する**: 各AIプロバイダの仕様に合わせてプロンプトを整形する際も、元の選択方針や安全基準を維持します。必須の意味が表現できない場合は無理に実行せず不足エラーを返します。
5. **観測とプライバシーの厳格な分離**: 観測機能（Observer）はルーティング判断のためにプライベートな文脈を一時的に参照できますが、キャラクターへの通知本文や個体側の推論利用条件は厳密に個別に成立させます。
6. **現在性の厳格な検証**: 「過去の正しさ」ではなく「今この瞬間の前提条件」で利用可否を判定し、遅れて届いた推論結果の採否は各機能のマスターが個別に判断します。
7. **データ消去への確実な参加**: コンテキストを扱うすべての機能は、処理中のデータや遅延結果も含めた内部データの完全消去、再保存の防止、未完了タスクの確実な保全に参加します。

**【採用してはならない設計（アンチパターン）】**
- データの由来をプロンプト本文のテキスト情報だけで判断する方式
- 単一の「コンテキスト有効フラグ」だけで、その後のあらゆる利用や実行を許可する方式
- データを変換・要約したからといって、元データの制約（機密性など）を自己申告だけで解除する方式
- 観測機能が取得した複数人のプライベート情報が混ざった出力を、そのままキャラクターへ無条件に配送する方式
- 古いプロバイダセッションを再利用して、現在のアクセス権限やデータ消去の制約をすり抜ける方式

**【実装に委ねられる自由度（Design Freedom）】**
以下の項目は、上記の基本契約を満たす限り、具体的な実装側で自由に設計・選択して構いません：
- **アルゴリズムの選定**: 検索・スコアリング・情報選択・要約・記憶形成のアルゴリズム、プロンプトの具体的なテンプレート構造、情報の詳細度、ルーティング用の判定モデルや更新頻度、トークン超過時の省略優先順位。
- **鮮度管理と競合制御の方式**: データの参照関係や依存関係の内部表現形式、鮮度チェック・変更検知・失効通知のプロトコル、同時実行時の競合解消アルゴリズム、キャッシュの管理方式、セッション切り替えのトリガー。
- **一時データのライフサイクル**: 一時的なメタデータの保持期間やインメモリ／ディスクの選定、永続化が必要な未完了状態との連携方法、データ消去時の探索手順や全域完了の判定シーケンス。
- **技術スタックとコード構造**: Rustのクレート・モジュール構成、構造体（struct）・列挙型（enum）・トレイト（trait）の定義、具体的な関数シグネチャ、IPCプロトコル、DBスキーマ・SQLテーブル設計、シリアライズ形式、イベントバス・キュー・アクターモデルの採用、プロセス・スレッドの割り当て、ロックやトランザクションの粒度、タイムアウトやリトライの秒数、利用する外部ライブラリ。
