# Action Execution — 認可判断から実作用・結果確定・作用不明までの詳細設計

本ドキュメントは、オーナーの意図やセキュリティ判定（認可判断）に基づいてファイル操作やツール実行などの「実際の外部操作（Action）」が行われ、その結果がタスクや履歴、オーナーへの報告へ戻るまでの過程において、**「何を許可したのか」と「実際に何が行われたのか」の対応関係が途中で曖昧になったり失われたりしないための設計原則**を定めます。

## 1. 詳細化する問題と範囲選定（解決すべき課題と設計スコープ）

セキュリティの認可判断と、実際のファイル操作やOSへの作用の間には、時間差、委任エージェントへの引き継ぎ、通信経路の切り替え、実行環境の変化、処理の中断、通信途絶など、さまざまな要因が入り込みます。
ここで「許可されたはず」「実行したはず」「成功したはず」といった希望的観測をすべて「成功」として安易にひとまとめにしてしまうと、禁止ルールのすり抜け、同じ操作の勝手な二重実行、嘘の完了報告といった重大な事故に繋がります。

本設計書では、以下の誤りを徹底的に防ぎます：

| 誤りやすい設計 | 本書で定める安全ルール |
|---|---|
| 指示されたファイル名と、実際に触るファイル名が同じだからといって安易に実行してしまう（シンボリックリンク等でのすり抜け）。 | 操作の直前に「実際にアクセスする対象（実パスや実リソース）」を正しく解決・検証し、危険な変更があれば再評価します。 |
| サブエージェントへの委任やツール経路の変更を理由に、元のパーミッションや許可範囲（フォルダ境界等）を勝手に広げてしまう。 | 委レン連鎖を経ても、元のタスク・権限・作業フォルダ（Workspace）・端末（Client）の境界は絶対に維持されます。 |
| 通信パケットが届いたことやツールの自己申告、画面通知の表示を、すべて「操作が完全に成功した」と混同してしまう。 | 「通信の成功」「実際の操作の成否」「内部記録の保存」「タスク全体の達成」「オーナーへの報告完了」を別々の客観的事実として厳格に管理します。 |
| キャンセル指示や権限失効と、バックグラウンドの操作が競合した際に、単一のフラグだけで大雑把に片付けてしまう。 | 操作の中断要求を受け付けたことと、外部での停止が完了したことを明確に区別し、遅れて届いた古い結果を新しいタスクに誤って適用しません。 |
| 操作の成否が確認できない（結果不明）ときに、「失敗した」または「成功した」と勝手に決めつけ、自動リトライで同じ操作を二重実行してしまう。 | 成否が分からない操作は「成否不明」として正直に保持し、勝手な自動再実行を禁止して、二重実行のリスクをオーナーに確認します。 |
| 会話要約や再起動からの復旧の過程で、「たぶん成功した」と結果の確実性を勝手に強めてしまう。 | 履歴記録、画面表示、監査ログのどこにおいても、結果の確定度（確認済み成功、確認済み失敗、成否不明）を正直に維持します。 |

## 2. 上位architectureとの位置関係（アーキテクチャ上の位置付け）

本書は、システム全体のアーキテクチャ方針に基づき、各サブシステムの責務を忠実に守って適用します。
新しい万能な「Actionマネージャー」や巨大な権限パイプラインを新設するのではなく、既存のサブシステムが連携して整合性を保ちます。

| 役割 | 担当サブシステム | 担当サブシステムが勝手に越境してはならない権限 |
|---|---|---|
| **指示の意味判断** | **個体調整**、**作業**、**認識・学習** など。<br>指示の目的、操作対象、利用データ、送信先の解釈を担当。 | セキュリティルールや費用上限などの制御条件を勝手に変更・確定してはならない。 |
| **セキュリティ認可判断** | **権限・制約**。<br>オーナーの意図やルールと具体的な操作を照合し、実行の可否やオーナー確認の要否を確定。 | タスクの達成判定や、操作の物理的な成功判定、報告完了の判定を代行してはならない。 |
| **実際の操作実行と結果の把握** | **実行・拡張**。<br>許可された制限内でファイルやツールに作用し、停止結果や確認できた事実・確定度を管理。 | 勝手に権限を付与したり、タスク全体の達成を決めつけたりしてはならない。 |
| **タスクの目的と達成管理** | **作業**。<br>タスクへの反映、エージェントへの委任、追加指示（Steering）、進捗・達成・未完了を確定。 | 個別の外部操作の成否を勝手に書き換えたり、失効した承認を復活させたりしてはならない。 |
| **オーナーへの報告管理** | **個体調整**（報告内容の取りまとめ）／**入出力・提示**（実際の画面・音声提示）。 | タスク完了や操作成功を勝手に決めつけてはならない。 |
| **認証情報の管理** | **認証秘密**。<br>APIキーやパスワードの安全な保管と、必要な通信経路への安全な提供。 | 操作の承認や、送信同意の変更を行ってはならない。 |
| **端末接続と活動条件** | **接続・存在**、**個体調整**、**保全・消去** など。<br>端末の接続状態、パートナーの停止、復旧の条件を提供。 | 操作の実行権限そのものを勝手に付与してはならない。 |
| **客観的記録の保全** | **保全・消去** および各担当。<br>監査ログの順序と保存、システム全域の整合性を管理。 | 過去の事実の意味を勝手に書き換えたり、外部操作を取り消したりしてはならない。 |

## 3. 認可判断が結び付ける対応（セキュリティ認可の基本原則）

### 3.1 判断対象の論理的な要素
セキュリティの認可判断とは、単に「OK」と答えることではなく、**「誰が、何の目的で、どの対象に対して、どのような操作を行うか」という具体的な対応関係を検証・確定すること**です。
すべての操作要求において、以下の要素が正しく解決できている必要があります：

1. **実行主体と委任関係**: 誰（どのパートナー）の指示で、どのタスクの一部として、どの一時エージェントが実行しているか。
2. **タスクと作業フォルダの範囲**: どのタスクに属し、どのフォルダ（Workspace）の利用が許可されているか。
3. **操作の目的**: ユーザーの依頼、定期スケジュール、追加指示（Steering）のどれに基づく操作か。
4. **実際の対象と操作の種類**: 操作対象（ファイルパス等）と、操作種別（読み取り、作成、変更、削除、コマンド実行等のリスク分類）。
5. **扱うデータと用途**: どのデータを何のために利用するか（APIキーなどの機密値はここに含めません）。
6. **費用とリスク**: AI推論費用や外部ツール利用のリスク見積もり。
7. **根拠となったオーナーの意図・ルール**: ユーザーからの直接指示、保存済みルール、送信同意、端末許可のどれに基づいているか。AI自身が生成したテキストや過去の記憶の引用は、許可の根拠にはなりません。

### 3.2 由来の保持とAIによる「自己承認」の絶対禁止
オーナーからの直接の指示や管理操作と、外部から読み込んだファイルの内容やAIの推論テキストは、明確に区別されます。
**AIモデル、タスクエージェント、外部ツール（MCP）、シェルスクリプト、PC操作機能などが、自分自身で新しいパーミッションを作り出したり、権限を勝手に拡大・自己承認したりすることは絶対にできません。**

また、以下の事象は、それ単体では「別の危険な操作を許可された根拠」にはなりません：
- 将来ルールの保存、APIキーの登録、プロバイダー送信同意、スケジュールの作成、画面観測のON、端末のペアリング、パートナーとの親密さ、タスクの受付、エージェントの成功申告、ツールUIのクリック。
- ローカルMCPに対するサンドボックス外アクセスの例外許可は、その特定ツールに限定された隔離例外であり、他の操作を無制限に許可する「フリーパス」ではありません。

### 3.3 判断記録と「今その操作を行ってよいか」の区別
「過去にどう判定したかという記録」と、「今この瞬間にその操作を実行してよいか」は別物です。
過去の許可ログ、バックアップから復元された古いルール、AIプロンプト内の指示文、メモリ上のキャッシュされた判定を、無条件に今の実行根拠として信じてはなりません。

操作を実行するまさにその瞬間に、最新の状況（パーミッションの失効、パートナーの停止、端末の切断、費用上限への到達、緊急停止の有無など）を評価して適用します。

## 4. 委任と経路変更の不変条件（エージェント委任時の境界維持）

### 4.1 委レン連鎖によって権限境界を広げない
タスク実行エージェント（Task Agent）は、指示を出したパートナーとタスクに与えられた権限の範囲内でのみ動作します。
エージェント自身が独立した許可、専用のAPIキー、独自の予算、永続的な人格を持つことはありません。同じフォルダを使っている別タスクの許可や、他人のプライベートな記憶を勝手に流用することもできません。
委任先のエージェントが増えたり、並列で実行されたりしても、全体の権限境界や費用上限枠をすり抜けることは絶対に許されません。

### 4.2 ツールや経路の変更によって制限を回避させない
複数のツールを組み合わせたり、シェルコマンドを経由したり、MCPやPC操作（Computer Use）を利用したりする場合でも、最終的にファイルやOSに対して行われる作用には同じセキュリティ制限が適用されます。
「直接編集が拒否されたから、シェルスクリプトを作って実行する」「名前を別のツールに変えて実行する」といった迂回は確実にブロックされます。
また、外部ツールからEne自身の管理画面や承認ダイアログを勝手にクリックしてオーナーの承認を偽装することも防ぎます。

### 4.3 タスクを経ない軽微な操作も同じ安全境界を守る
ちょっとしたファイルの確認など、独立したタスクを作成しない軽微な操作であっても、セキュリティ境界や操作結果の確定度管理が省略されることはありません。

## 5. 実作用開始前の現在条件成立（操作直前の安全チェック）

### 5.1 開始前に成立させるべき条件
ファイルやOSを操作する直前に、「実行・拡張」サブシステムは以下の条件がすべて現時点で成立していることを検証します：

- **セキュリティルール**: パーミッション、恒久拒否（Deny）、毎回確認（Always ask）に違反していないか。
- **タスク・作業フォルダ範囲**: タスクが有効に継続しており、許可された作業フォルダ内の操作であるか。
- **端末依存の条件**: PC操作（Computer Use）を行う場合、指示主のパートナーが現在アクティブになっている端末であり、端末の利用許可が有効であるか。
- **費用・リソース上限**: 費用上限枠に余裕があるか。
- **中断・停止の有無**: キャンセル指示、パートナー停止、データの完全削除処理、リストア直後の保留が発生していないか。

これらの条件を満たせない操作は即座に保留または拒否され、古い判定を根拠にして強行されることはありません。

### 5.2 操作対象の厳密な解決（パスの解決と検証）
指示されたファイル名やパスは、操作の瞬間に「実際に触る物理的な対象」として正しく解決・検証されます。
ディレクトリトラバーサル（`../` を使った脱出）や、シンボリックリンク・マウントポイントを経由した許可範囲外へのアクセスは確実に遮断されます。
パスの解決に失敗した場合や、許可されたフォルダから外れている場合は、操作を開始しません。

### 5.3 重要な変更が発生した場合の再評価
操作の目的、対象ファイル、操作種別（読み取りから削除への変更など）、送信先、外部への影響が大きく変わった場合は、現在のルールに基づいて改めて再評価を行います。
ただし、画面の表示言語の変更や、無関係な雑談記憶の更新など、操作と関係のない変更によって不要な再確認ダイアログを乱発することは避けます。


## 6. 作用と確定度の分類

### 6.1 別の事実として対応付ける

アクションの受付、タスクの受理、権限チェック、実際の実行開始、外部への影響、内部ログの保存、タスク全体の達成、ユーザーへの報告は、それぞれまったく別の独立した事実です。これらは担当する責務（サブシステム）が異なっており、決して安易にひとまとめにして「成功」とみなしてはいけません。

| 確認すべき事柄 | 責任を持つサブシステム（マスター担当） | 勝手な推測で代用してはならないもの |
|---|---|---|
| アクション要求の受付と開始 | 実行・拡張（受付と開始の事実を管理） | 「権限チェックを通ったはず」「タスクが完了したはず」「処理が成功したはず」という推測 |
| 外部への実際の影響と確定度 | 実行・拡張 | 許可が出たこと、キャンセルを受け付けたこと、通信が通ったこと、Agent自身の「成功しました」という自己申告 |
| タスクの目的・達成・未完了 | 作業 | 会話で受け付けたこと、Agentプロセスが終了したこと、個々のアクションの成功 |
| 設定変更や現在の利用可否 | 権限・制約 | UI上の表示、過去の許可実績、監査ログの文面、ログイン・認証が通ったこと |
| ユーザーへの報告状況 | 個体調整（内容管理）、入出力・提示（実際の画面・音声提示） | クライアントが接続中であること、画面描画用のコピーを送信したこと、タスクが完了したこと |
| ログ保存や監査記録の成立 | 保全・消去および関係する各サブシステム | 一部の処理が終わったこと、ファイルが生成されたこと、操作画面を閉じたこと |

内部ログの保存が成功したからといって、外部システムへの操作が成功したとは限りません。逆に、外部への操作が成功していても、内部ログの保存に失敗している可能性もあります。内部保存に失敗したからといって「外部操作も行われなかった」とみなしてはならず、データベースに残っている最後の正常記録が、必ずしも現実世界の最新状態と一致しているとは限りません。

### 6.2 確定度の種類と不明の保持

実行・拡張サブシステムが把握する結果の「確定度」は、少なくとも以下の3つを厳密に区別します。結果が確認できない状態を、勝手に「未実行」「失敗」「成功」のいずれかに決めつけてはいけません。確定度を変更できるのは、その事実を管理するサブシステムが新たな客観的証拠を確認できた場合のみです。

- **確認済み成功**：対象に対して意図した変更が実際に行われたことを、タスク実行Agent自身の自己申告以外の客観的な証拠（戻り値の確認や状態取得など）で確認できた状態です。「何がどう変わったか」とその「確認根拠」をセットで記録します。
- **確認済み失敗**：操作が行われなかったこと、または意図通りに動かなかったことが確実に確認できた状態です。まったく手付かずなのか、途中で失敗したのか、処理後のクリーンアップに失敗したのかなど、必要な範囲で区別します。途中で失敗した場合でも、すでに完了した変更の記録を勝手に消してはいけません。
- **不明（結果が分からない）**：要求の送信や処理を開始したものの、成功したかどうか確認できない状態です。外部への送信直後のネットワーク切断、タイムアウト、レスポンスの喪失、クライアントの切断や移動との競合、停止要求との競合、Host PCのシャットダウン、内部ログ保存の失敗などがこれに該当します。この「不明」という状態は、新たな客観的証拠が得られるまで、そのまま「不明」として保持し続けなければなりません。

「キャンセル要求を受け付けたこと」は「処理が停止したこと」を意味しません。「通信が成功したこと」は「意図した操作が完了したこと」を意味しません。また、「画面上に表示されたこと」は「実行が許可されたこと」や「完了したこと」を意味しません。外部サービスやMCPサーバー、外部プロセスから「成功（success）」という応答が返ってきた場合でも、eneが把握した操作の客観的証拠として扱う際は、それが本当に意図した対象への操作に対応しているかを確かめて慎重に扱います。

### 6.3 部分失敗と複合作用

複数のAgentが並列で動いて一部が失敗した場合、複数ステップの処理で一部が未完了になった場合、あるいは複数の操作をまとめたツールで一部だけが実行された場合でも、すでに完了が確認できている他の結果や外部への影響を取り消されたものとして扱ってはいけません。作業サブシステムが、現在の依存関係や制約に基づいて残りの処理を続行できるかどうかを判断し、部分的な成果と未完了の内容を正しく整理します。「1つでも失敗したら全Agentを一律キャンセルする」あるいは「何があっても無条件に強行する」といった極端な決め打ちはしません。

通信レイヤー（リトライ処理など）の再送によって外部への操作が二重に実行される可能性がある場合は、それを下層の透過的な復帰として隠蔽せず、論理的な新しい試行として扱い、後述の第8節の二重実行防止の枠組みに接続します。具体的なリトライアルゴリズムやタイムアウト値は実装に委ねられますが、二重実行のリスクがある再送を「単一の試行が続いているだけ」とみなして、結果不明や二重実行の管理から勝手に除外してはなりません。

また、認証情報（Credential）への参照は、あくまで安全な「用途の識別名」に過ぎず、LLMがプロンプト内でその名前を出力しただけで勝手に利用可能になってはなりません。認証先の外部サービスから返ってきたエラーや結果に秘密情報（APIキーやトークンなど）が含まれていた場合も、それを通常の実行結果・説明・会話履歴・学習データ・監査ログ・デバッグログなどに露出させないよう、受け入れ・保存・画面提示に関わるすべての箇所で非露出の保護を徹底します。

## 7. 競合時の帰属と順序

### 7.1 停止・失効は新規開始を禁じ、進行中はbest-effortで扱う

ユーザーからのキャンセル要求は、公式クライアント（第一者Client）の管理経路から作業サブシステムに届きます。このとき、メインのLLMやAgentのキリが良い終了を待つことなく、即座に受け付けます。作業サブシステムはタスクの遂行を直ちに中断し、実行・拡張サブシステムは現在実行中の操作をベストエフォート（可能な限り速やか）で停止させます。ここで、「停止要求を受け付けたこと」と「外部の操作が実際に停止完了したこと」は明確に区別します。すでに生じてしまった影響、どうしても停止できなかった処理、結果が不明な処理、未保存の作業内容などは、すべてそのまま記録してユーザーに正確に報告します。キャンセル要求の受付、新規アクションの開始禁止、状態の確認を、外部プロセスの終了待ちや全タスクの完了待ちでブロックしてはいけません。また、「停止処理のため」と称して、ユーザーが承認していない新たなアクションを開始してはなりません。

権限の取り消し、デバイスの切断、同意の撤回、認証情報の失効、パートナー（Companion）の停止、完全削除（targeted deletion）やバックアップ復元（restore）の待機状態が発生した場合は、それらに依存する新しいアクションの開始を即座に禁止します。進行中の処理はベストエフォートで停止し、別のAgentや別のクライアント、別のツールを経由してその失効を回避（迂回）しようとしてはいけません。ただし、それらとは無関係に動いているHost全体の他のタスクまで一律に巻き込んでキャンセルしてはなりません。また、権限が失効する前に適法に行われた操作や過去の認可判断の記録を勝手に改ざん・巻き戻ししてはなりません。

Host PCのシャットダウンや再起動の際も、必要な進捗状況、結果不明な操作、未伝達の報告、全体操作の未完了状態を確実にディスクへ保全し、Hostの停止とともに外部への影響も勝手に消滅したかのように誤認してはなりません。

### 7.2 steeringは新しい目的であり、旧結果の自動採用ではない

ユーザーから途中で追加の指示や修正（steering）が入った場合、その発言自体は会話履歴（History）に記録され、それをタスクにどう反映するかは作業サブシステムのコンテキストで管理され、承認の有効性は権限・制約サブシステムで検証されます。修正後の新しい目的に対して、修正前の古い委任範囲や古い処理結果をそのまま適用すると矛盾が生じる場合は、その用途に流用せず、改めて判断をやり直します。指示変更前の依頼に対して遅れて返ってきた結果を、新しい依頼が達成された証拠として勝手に採用し、それを根拠に次のアクションを自動開始してはなりません。

ユーザーの承認が届いた時点でも、承認対象のアクション、担当する役割、制約条件が承認依頼時と変わっていないかを必ず照合します。すでにキャンセルされたタスク、権限が失効したタスク、指示が修正されたタスクを、古い承認によって勝手に復活させたり制限を解除したりしてはいけません。また、ユーザーの判断待ちやAgentの終了待ちを、LLMにループで繰り返し問い合わせさせる（ポーリングさせる）ような実装にしてはなりません。

### 7.3 遅延到着の帰属

キャンセル、指示修正、権限失効、クライアントの切り替え、削除、復元などの後に、ツールの実行結果や承認、推論結果が遅れて届いたとしても、次の実行を自動で開始してはいけません。発生した操作の事実は元の古いアクションやタスクに対応付けて正確に記録し、現在の新しいタスクに採用できるかどうかの判断は、現在のタスクのコンテキストで改めて行います。「記録に残すこと」「知識として学習すること」「次のアクションを実行すること」「ユーザーに画面提示すること」はそれぞれ別の受入判断であり、単一の「有効／無効」フラグにすべての責任を丸投げしてはいけません。

| 競合・遅延のケース | 残すべき事実・許可される対応 | 禁止される扱い |
|---|---|---|
| キャンセルや権限失効の後に、ツールの結果や承認が遅れて届いた | 実行・拡張サブシステムは操作の事実を元の古いアクションに記録し、作業サブシステムは現在のタスクの基準で結果を評価する。必要な操作ログを残した上で、後続のアクションは自動開始しない。 | 古い承認を使ってキャンセルや失効を勝手に取り消す。古い結果を新しい目的の達成とみなして次のアクションを開始する。 |
| 指示修正（steering）の後に、古い依頼の結果が届いた | 元のタスクやアクションの記録として残すことは可能。現在の新しい目的に採用するかどうかは再評価が必要。 | 古い結果を、新しい目的が達成されたものとして無条件に採用する。 |
| 個体（Companion）の削除後に、その個体のアクション結果が届いた | 残っているタスク記録や活動ログに操作の事実を記録し、管理画面から状況を説明できるようにする。 | すでに削除された個体の返信、記憶（Memory）、関係性（Relationship）などを勝手に再作成・復活させる。 |
| バックアップ復元後に、復元前の古い処理結果が届いた | 復元前の古い処理による影響の説明と、復元されたバックアップデータを明確に区別する。 | 復元前の古い実行状態を復元後のマスターデータに混入させ、タスクや学習データ、権限を勝手に復活させる。 |
| クライアント再接続時に、古い入力や画面表示のコピーが送られてきた | Host PCの現在のマスターデータ、所有権、削除状況に従って、未確定の入力と受理済みの入力を明確に区別する。 | クライアント側の古いコピーでHostのマスターデータを上書きする。未送信だった操作を自動実行キューとしてそのまま再生（リプレイ）する。 |

キャンセルや失効が行われたからといって、起きた事実の報告まで禁止されるわけではありません。また、記録に残せたからといって、それを次の処理で利用してよいわけでもありません。キャンセル後に届いた結果によってキャンセル自体を「なかったこと」にしてはならず、後続のアクションを勝手に再開してはいけません。

## 8. 作用不明の保持と重複実行の防止

### 8.1 不明にしてはならない変換

外部への操作が成功したかどうかわからない（結果不明な）場合、システムが勝手に自動で再実行してはいけません。二重に実行されてしまう可能性（重複リスク）をユーザーにわかりやすく説明し、どうするかユーザー自身の判断を仰ぎます。結果不明な操作を、別のツール、別のHost、別のクライアントから再実行したり、ネットワーク回復後に自動でリプレイしたり、クライアントの切り替えを理由に新クライアントで自動再実行したり、Host再起動後に自動で再開したり、タスク再開時にまとめてリプレイしたりして、安易に解消しようとしてはなりません。ユーザーが中断されたタスクの再開を明示的に指示した場合でも、結果不明なアクションまで無差別に自動再実行してはなりません。

また、内部ログの保存に失敗したからといって、それだけを根拠に「直前の操作は実行されなかった」と決めつけてはなりません。ログの保存に失敗した場合は、「データベースに残っている最後の正常記録が、現実世界の最新状態とは限らない」という前提を堅持します。システムの復旧や再起動時にも自動リプレイは行いません。外部サービスやネットワークの回復、MCPツールの再表示、クライアントの再接続、パートナーの復帰（Resume）、Hostの自動起動、バックアップ復元後の有効化などは、それぞれ成立した条件を整えるだけであり、過去の「結果不明」を勝手に「解決済み」に変える理由にはなりません。推論モデルのフォールバック機能も、外部操作の結果不明を再実行によってごまかすための仕組みではありません。

### 8.2 重複を防ぐために保持・区別できる必要がある関係

再接続、クライアントの移動、リトライ、Hostの再起動、タスクの再開などによって同じ操作が重複して実行されるのを防ぐため、アーキテクチャレベルで少なくとも以下の関係性を正しく保持し、区別できるように設計しなければなりません。なお、具体的な冪等性キー（idempotency key）の形式、トランザクションプロトコル、リトライ実装、キュー／アクター／イベントバスの選定、DBスキーマ、ロック方式などは特定の方式に固定しません。

- **試行と作用の区別**：eneが開始した「アクションの試行」という単位と、外部世界に何が生じたかという「実際の作用」を別のものとして扱います。リトライや再実行は「過去の試行が続いている」のではなく、「過去の結果不明と関連付けられた、新しい別の試行」として扱います。どの試行が、どの認可判断・タスク・委任に基づいているかの対応関係を保持します。
- **判断・目的との対応**：その試行が、どの認可判断、どの目的、どの指示修正の前提、どのタスク・委任、どのワークスペース条件に基づいて行われたかを記録します。指示修正やタスク再開後の新しい試行が、古い判断や古い目的のまま開始されないようにします。
- **実際の操作対象との対応**：パス解決やID解決が行われた後の「実際の操作対象・操作内容・送信先」と、ユーザーが判断した対象との対応関係を保ちます。対象や操作内容が変わった再実行を、「同じ操作の再送」として扱ってはなりません。
- **進捗段階の区別**：受付、開始、送信、把握できた作用、確定度の判定など、処理がどこまで進んだかを正確に区別します。「開始したこと」と「実際に影響を与えたこと」を混同してはならず、通信不能や確認不能を勝手に「成功」や「未実行」に読み替えてはなりません。
- **確定度とその根拠**：結果が「確認済み」なのか「不明」なのかの区別と、その判断根拠・観測者（実行・拡張サブシステムの把握、外部からの応答、現地の確認など）を記録します。「不明」は、新たな客観的根拠が得られるまで保持し続けます。
- **停止・保留との関係**：キャンセル、権限失効、クライアント移動、再起動のどれと競合して生じた「不明」なのかを記録します。競合相手の状態が解除されただけで、不明そのものが解消したとみなしてはなりません。

これらの必要な関係性を保持・参照できず、処理の正当性を確認できない場合は、勝手に「成功した」「承認済みである」「未実行である」と推定してはなりません。単に届いたのが遅かったというだけで出来事の順序を新しく書き換えたり、直近に届いた結果だけで現在の状態を勝手に上書きしてはなりません。

### 8.3 retry・再開・再接続の扱い

リトライ（再試行）は常に「新しい試行」として扱い、現在の認可判断、現在の目的、実際の操作対象、現在の前提条件をすべて満たした上で開始します。「確実に失敗しており、外部に何の影響も与えていないこと」が確認できている試行の再実行であれば、同じ内容をカバーする既存の指示・ルール・権限が有効である限り、その範囲内で自動的に開始できます。これにより、不要な再確認ダイアログでユーザーを煩わせることを防ぎます。一方で、「外部への影響が不明な試行」の再実行には、重複して実行されてしまうリスクを説明した上でのユーザー自身の明確な判断が必須であり、ユーザーの確認なしに勝手に開始してはなりません。発生しうる費用、リスク、重複の可能性を、判断に必要な粒度で分かりやすく提示します。

「失敗が確定しているケース」と「結果が不明なケース」を同じリトライ処理にひとまとめにしてはなりません。失敗確定時の安全な再実行ルールを、結果不明な試行の自動再実行に適用してはなりません。ユーザーから「タスクを再開してほしい」という指示があった場合でも、それは過去の処理を無差別にリプレイしてよいという許可ではなく、結果不明な各試行の重複リスクと現在の状況を照らし合わせて個別に対処します。ユーザーの明確な指示を得て再実行した場合でも、過去の試行の「不明」が「成功」や「失敗」に変わるわけではなく、古い試行と新しい試行の結果や確定度は別々に記録します。万が一、後から二重実行されていたことが判明した場合でも、過去の既知の操作として正しく説明できるようにします。

クライアントの再接続や移動、Hostの再起動、バックアップ復元などの後に、古い試行の結果が遅れて届いた場合でも、それらを現在のタスクや復元後のマスターデータに無条件に混入させてはなりません。復元前の古い実行状態を復元後のマスターデータに混ぜて、タスクや学習データ、権限を勝手に復活させてはなりません。また、クライアントに残っていた古い入力や画面表示のコピー、未送信だった操作を、自動実行キューとしてそのまま再実行してはなりません。

### 8.4 Client依存作用とHost再起動時の不明

PC画面操作（Computer Use）など、特定のクライアント環境に依存するアクションの実行中にクライアントの移動や切断が必要になった場合は、安全に区切りの良いところまで移動を一時的に遅らせることができます。ただし、「移動したから」という理由だけで、元のクライアントで実行していた操作を別のクライアントやHost PC上で自動的に再実行してはなりません。クライアントの切断に伴う停止処理はベストエフォートとし、どうしても停止できなかった処理、すでに発生した影響、結果が不明な操作を正確に記録します。外部への影響が不明な操作を、Host PCや他のクライアントで勝手に自動再実行してはならず、重複の可能性がある場合は必ずユーザーの判断を仰ぎます。パートナー（Companion）の表示切り替えと、未確定なアクションの再実行は完全に切り離して扱います。操作の排他性が確認できないクライアントでは作業を継続せず、Host側でも、現地の物理的な停止や外部操作の取り消しが客観的に確認できない限り、勝手に「停止成功」とみなしてはなりません。

Host PCの再起動後に残っていた中断タスクは、勝手に自動再開してはなりません。保存されている進捗、すでに判明している外部への影響、結果が不明な操作、未完了の作業を提示し、ユーザーからの明示的な再開指示を待ちます。Agentのセッションが残っていること、外部サービスが復旧したこと、あるいはHostが自動起動する設定になっていることだけを理由に再開してはなりません。再開する際も、現在の担当キャラクター、権限、同意、利用枠（cap）、ワークスペース、クライアント依存条件と結果不明な操作を照合し、二重実行のリスクがある場合はユーザーの判断に委ねます。実行中だったキャラクターの表示状態（presence）が復旧したことと、中断されたタスクを再開することはまったく別の条件であり、キャラクターが再表示されたからといってタスクの再開権限が自動的に与えられるわけではありません。

## 9. 記録・報告・監査での確定度保持

タスクの記録は、実行・拡張サブシステムが把握した客観的な操作内容と確定度を正しく参照・集約します。同じ操作の確定度を、作業サブシステム側で勝手に「成功」などと書き換えてはなりません。Agent自身の「成功しました」という自己申告を、客観的な証拠の代わりに使ってはなりません。タスク全体の達成判断は作業サブシステムが行いますが、個々のアクションが実際にどう動いたかの把握は実行・拡張サブシステムの責任です。タスク終了時には、作業結果、変更されたファイル、保存先、失敗した内容、未完了の項目、次に必要な判断などを、担当キャラクターからユーザーに分かりやすく報告します。ファイルの恒久的な保存先が決まっていない場合は、最終保存の前にユーザーに確認します。

個体調整サブシステムは、タスクのマスターデータを参照し、結果・変更・保存先・失敗・未完了・次の判断を統合してユーザーに報告します。アクティブなクライアントが存在しない場合は「未伝達メッセージ」として管理し、次にクライアントが接続された際に、現在の結果と利用制限に基づいて要約して報告します。単にクライアントが接続されたことや、画面表示用のデータを送信したことだけで「報告完了」とみなしてはならず、実際にユーザーに届いたか不明な状態を正しく保持します。「報告したこと」は「ユーザーが承認したこと」や「タスクを再開したこと」を意味しません。なお、過剰に複雑な「厳密に一度だけの配信保証（exactly-once）」や既読確認の仕組みを無理に追加する必要はありません。

ユーザーへの最終報告、管理画面の表示、キャラクターの身体動作（Body）や音声（Voice）による演出、親しみやすい会話の要約などによって、未完了のタスクや結果不明な操作を「成功した」かのように見せかけてはなりません。確定度や費用の見積もり、実績、不明な状態をそのまま正しく保持し、単なる推測や不明な数値を勝手に確定値へと格上げしてはなりません。重要な音声案内には必ずテキストの代替を用意し、画面の表示言語を変更しても、承認や合意の法的・技術的な意味が変わらないようにします。

各サブシステムは、主要なアクション、権限の認可判断、外部への影響、外部サービス（LLM Provider等）の利用枠消費、認証情報の参照、重要な設定変更などについて、必要な事実を監査ログに提供します。保全・消去サブシステムは監査ログの追記順序と保管を管理しますが、ログの追記順を「現実世界で起きた絶対的な順序」や「現在の生きた許可情報」と同一視してはなりません。監査ログには、プライバシー保護のため、原則として会話の全文やファイル本文、秘密情報、すでに削除されたプライベートな内容を含めません。到着が遅れた報告や後から訂正された報告も、元の操作対象との対応関係を保ちます。また、監査ログをシステムの内部状態の自動復元やアクションの自動再実行の入力として直接使ってはなりません。

アクションの記録説明と、個人データの完全削除（targeted deletion）が競合する場合は、「操作が行われた事実の記録」と「削除対象の個人情報の除去」を両立させ、「操作記録だから」という理由で削除対象の本文を勝手に残してはなりません。データの受け入れに関わるすべてのサブシステムが削除処理に協力し、古い結果から削除対象のデータが復活しないようにします。外部サービスへ送信・エクスポート・バックアップされたコピーや外部ワークスペースの削除、外部サービスの認証情報の無効化などは、ene内部の操作記録の完了範囲外（責任範囲外）であることをユーザーに明確に説明します。

## 10. Runtime FlowsとCross-cutting Designに対する横断検証

[Major Runtime Flows](../architecture/runtime-flows.md) 第3節（RF-01〜08）および [Cross-cutting Design](../architecture/cross-cutting.md)（CC-01〜07）と照らし合わせた、正常系および競合発生時の整合性検証（walkthrough）は以下のとおりです。

| フロー・競合シナリオ | 処理の流れと満たすべき結果 | 本ドキュメントの対応箇所 |
|---|---|---|
| RF-02 正常系: 委任ファイル作業 | ユーザー依頼 → タスク化 → Agent委任 → 認可判断 → 実対象の解決 → 実際の操作 → タスク達成 → 報告がそれぞれ独立して完結する。Agentの自己申告を成功証拠にせず、ワークスペース規定の保存ルールと最終保存前の確認を守る。 | 3.1、5.1〜5.2、6.1〜6.2、9。 |
| 認可判断後の条件変更: symlink差し替え、ワークスペース変更、ルールの失効 | 実行開始直前の実対象解決と現在条件の検証により、古い判定が無効化される。対象外への操作や失効後の新規開始を防止する。無関係な記憶の更新では不要な再承認を求めない。 | 3.3、5.2〜5.3。（CC-01, CC-03を維持） |
| 指示修正（steering）やキャンセルとの競合: キャンセル直後の操作完了、修正後の遅延結果 | キャンセル受付と停止完了を明確に分け、元の古いアクション・タスクに事実を残す。古い結果を新しい目的の達成とみなさず、古い承認でキャンセルを解除しない。後続のアクションを自動開始しない。 | 7.1〜7.3。（CC-03, CC-04, CC-07を維持） |
| タスクAgentへの委任: 別経路による拒否（Deny）の迂回、別タスクの承認の流用 | 委任チェーンと実際の操作対象の制限により迂回を防ぐ。Agentが勝手に独自の許可や認証情報、予算を持つことを禁じる。軽微なアクションでも同じセキュリティ境界に従う。 | 4.1〜4.3。（CC-01を維持） |
| PC操作（Computer Use）中のクライアント切断や移動 | 安全な区切りまで移動を遅らせ、元の操作を別クライアントやHostで自動再実行しない。ベストエフォートで停止し、判明している結果と不明な結果を作業サブシステムに返す。排他性が確認できないクライアントで操作を続けない。 | 8.4、7.1。（CC-04, RT-02を維持） |
| 外部ツールのタイムアウトやレスポンス喪失 | 「不明」として状態を保持し、二重実行リスクの説明とユーザーの判断待ちへ移行する。「失敗＝未実行」と決めつけず、別経路で再実行しない。リトライは現在の条件を満たす新しい試行として扱う。 | 6.2、8.1〜8.3。（CC-07を維持） |
| Host PCの再起動: 中断タスクと実行中の結果不明操作 | 勝手に自動再開・自動リプレイしない。保存された進捗、判明している操作、不明な状態を提示し、ユーザーの明示的な再開指示時に現在の条件と二重実行リスクを照合する。キャラクターの表示復帰はタスク再開の権限にならない。 | 8.3〜8.4、7.1。（CC-04を維持） |

| スケジュール実行（無人実行）でユーザー判断待ちに到達 | 勝手に実行せず判断待ちとして保留し、自動承認や別経路での迂回を行わない。実行ごとに現在の条件を再評価し、実行されなかった回（missed）を勝手に補完実行しない。 | 5.1。（CC-01, CC-04を維持） |
| MCPツールやサンドボックス例外を介した操作 | ツールUIへの入力をユーザーの正式承認とみなさず、サンドボックスの例外許可を包括的な承認とみなさない。外部プロセス内部の不明な状態はそのまま不明として扱い、確実に停止・強制できたと嘘の報告をしない。 | 4.2、6.2、8.1。（CC-01を維持） |
| 補助推論の失敗や費用不明との競合 | 推論失敗や費用不明のときに成功を捏造せず、情報不足や判断待ちとして返す。事実の報告やキャンセル受付は次の権限チェックを待たずに即座に行う。処理中・不明な費用消費を全体上限から勝手に除外しない。 | 3.3、5.1、9。（CC-06を維持） |

横断設計の原則（CC-01〜CC-07）の一般的な定義は [Cross-cutting Design](../architecture/cross-cutting.md) に記載されています。本ドキュメントでは、アクション実行の観点から特に以下の点を具体化しています。

- **CC-01（権限と同一性）**：判断対象と実際の操作対象の完全な一致、および委任や経路変更が行われても権限境界が変わらないことの徹底。
- **CC-02（情報選択の独立性）**：アクション固有の判断ロジックに、システム全体のコンテキスト選択の主導権を奪われないこと。
- **CC-03（競合と調停）**：単一の試行と実際の作用を区別し、遅延結果の用途別受入によって、単一の有効フラグにすべての判断責任を集約させないこと。
- **CC-05（データ保全と完全消去）**：操作事実の説明と消去要請への協力を両立させ、外部コピーの消去を内部ログ保存の成功条件にしないこと。
- **CC-07（不変条件の維持）**：通信、ツール、タスク、報告の各レイヤーにおける確定度を厳格に区別し、ログ保存、報告、監査、復旧の過程で確定度を勝手に引き上げないこと。

## 11. 本書が固定する契約と残す Design Freedom

下位の具象設計（concrete design）や実装コードは、本ドキュメントが定めた以下の不変ルール（契約）を前提として利用できます。

- 認可判断は「判断された対象」と「実際の利用」が一致していなければならず、過去のログと現在有効な生きた許可は別物です。実行開始の直前に最新の条件と実際の操作対象の解決を完了させ、重要な変更があった場合は必ず再評価します。ただし、無関係な記憶の更新などで不要な再承認を求めてはなりません。
- 委任や実行経路の変更によって、元のタスク、ユーザーの意図、権限、ワークスペース、クライアントの境界が広がることは決してありません。LLMが生成したテキスト、ツールのUI入力、サンドボックスの例外許可などから、勝手に権限を作り出してはなりません。
- 要求受付、処理開始、外部への作用、ログ保存、タスク達成、ユーザー報告はすべて別の独立した事実であり、通信の成功やツールの自己申告を「操作の成功」と同一視してはなりません。部分的な失敗が起きても、すでに確定している他の結果を勝手に消してはなりません。
- キャンセル、指示修正、権限失効の後に遅れて届いた結果は元の古いアクションやタスクに対応付け、古い承認によるキャンセルの取り消し、古い結果の新しい目的への自動採用、後続アクションの自動開始を行ってはなりません。
- 結果不明な操作は粘り強く「不明」として保持し、自動再実行や自動リプレイを行ってはなりません。リトライや再開は常に現在の条件を満たす「新しい試行」として扱い、結果不明な試行を再実行する場合は、二重実行リスクを説明した上でのユーザー自身の明確な判断が必要です。
- 試行と作用、認可判断、目的、実際の操作対象、進捗段階、確定度、停止・保留との関係性を正しく保持・区別できない場合は、勝手に「成功した」「未実行である」と推定してはなりません。
- 報告、監査、データ復旧の過程で、確定度を勝手に引き上げてはなりません。また、削除対象となった個人情報の本文を、「操作の記録だから」という理由で残してはなりません。

本ドキュメントでは、名前の一致だけで同一対象とみなすこと、委任先への無制限な権限コピー、拒否された操作を別の同等アクションで迂回すること、内部管理APIへのツールからの回り込み、古い判定結果やキャッシュされた許可による新規開始、結果不明の勝手な成功・失敗・未実行への読み替えと自動リプレイ、遅延結果の新しい目的への自動流用、要約や復旧時の勝手な確定度の格上げを、**採用不可能な選択肢**として明確に排除します。これらはいずれも上位のセキュリティ原則や不変条件を破壊するため、決して採用できません。

一方で、以下の項目は実装や具象設計に委ねられる自由度（Design Freedom）として意図的に残されています。

| 設計対象 | アーキテクチャとして固定された性質 | 実装に委ねる設計自由度（Design Freedom） |
|---|---|---|
| 判断・対応・最新性の表現 | データの由来（provenance）を偽装できず、対象の変更や失効を各利用先で正しく扱えること。確認不能を勝手に許可とみなさないこと。 | 由来情報、判断対象、試行と作用の対応の具体的なデータ構造。確認処理のまとめ方、Permission evaluatorの内部実装、識別子の形式、鮮度確認や競合制御のアルゴリズム、パス解決の配置。 |
| 作用の観測と確定 | 作用事実のマスター担当は「実行・拡張」、タスク達成は「作業」、報告は「個体調整」であること。確定度を勝手に引き上げないこと。 | 作用を確認する具体的な手段、安全に処理を区切る方法、部分失敗を扱う粒度、通信の再送と論理的な試行を切り分ける実装、具体的なリトライ回数・アルゴリズム・タイムアウト値。 |
| 停止・競合の伝達 | 新規開始の即時禁止、ベストエフォートでの停止、遅延結果の適切な帰属、自動リプレイの禁止。受付と完了の分離。 | 停止要求の伝達方式、切断検知の仕組み、競合調停のアルゴリズム、処理ステップの区切り方、キュー／アクター／イベントバス／ロック／トランザクション／IPC／プロセスの具体的な配置。 |
| 重複防止情報の保持 | 試行と作用、判断、実際の対象、段階、確定度、保留との対応を保持・区別し、再起動・移動・再接続をまたいで勝手にリプレイしないこと。 | 識別子や冪等性キーの具体的な形式、データ保存の単位、DBスキーマ、リポジトリ構成、ログの保持期間、永続化が必要な未完了状態の具体的なデータ構造。 |
| 記録・報告・監査 | 元の事実の確定度、プライバシー、順序の意味、管理画面からの到達性を維持すること。 | 監査ログの具体的なフォーマット、保存期間、提示確認のUI実装、要約の粒度、UIレイアウト、診断ログスタックの構成。 |
| 費用・消費・縮退 | 並列処理中、処理中、結果不明な消費も同じ利用枠上限に正しく反映し、制御と保全を維持すること。 | 費用の事前予約（リザーブ）方式、集計期間、推定計算のロジック、リソース配分の優先度、無限ループや反復呼び出しを抑制する具体的な機構。 |

Rustのcrateやモジュール構成、トレイトや型の定義、具象APIやエラー型、ミドルウェアやインターセプター、イベントバスやキュー、プロセス間通信（IPC）フォーマット、DBスキーマ、ロックやトランザクションの実装方法、具体的な認証情報の暗号化保護やサンドボックスの隔離方式、利用するライブラリやOS APIの選定なども固定しません。また、上記の対応関係を実現するために、全体を統括する巨大な「Contextレイヤー」や「Policy Engine」「万能Manager」といった過剰な共通サブシステムを新たに新設する必要はありません。既存の12の責務、各データのマスター担当（semantic owner）、HostとClientの境界、および信頼境界（trust boundary）の範囲内で、最もシンプルで堅牢な実装方法を選択してください。

通信の再送と論理的な試行の切り分け、パス解決の配置場所、試行IDの表現形式などは、上記の制約を満たす限り下位設計の自由度として委ねられます。しかし、必要な確認やユーザー判断の省略、同意の勝手な拡大解釈、未完了・結果不明な操作の成功扱い、外部操作の自動ロールバックや厳密に一度だけの実行（exactly-once）を勝手に保証することなどは、いずれも設計自由度には含まれません。
