# Action Execution — 認可判断から実作用・結果確定・作用不明までの詳細設計

本書は、Ownerの意図やPermission判断から実際の外部作用が発生し、その結果がTask・記録・Ownerへの報告へ戻るまでの間で、「何を許可したのか」と「実際に何が行われたのか」の対応が失われないためのlogical contractを詳細化する。後続のconcurrency／state representation／persistence／interface設計が安全に依存できる水準まで定め、具体的なmechanismは固定しない。

## 1. 詳細化する問題と範囲選定

認可判断と実作用の間には、時間差、委任、経路変更、条件変更、競合、観測不能が入る。ここで「許可されたはず」「実行したはず」「成功したはず」を一つの肯定へ潰すと、Deny迂回、重複作用、誤った成功報告が生じる。後続設計が誤りやすい点は次のとおりである。

| 誤りやすい点 | 本書で定める契約 |
|---|---|
| 判断時の対象記述と実行時の実対象のずれを、名前の一致だけで済ませる。 | 判断対象と実対象の対応、実対象解決、重要な変更時の再評価。 |
| 委任・Tool経路の変更で、元のTask／Permission／Workspace／Client境界を付け替える。 | 委任連鎖と経路不変条件。委任による権限拡大の禁止と、不必要な再確認の抑制の両立。 |
| transport成功、Toolの自己申告、Task達成、Ownerへの報告を一つの成功にする。 | 作用事実・記録保存・Task達成・報告を別の事実として対応付ける確定度契約。 |
| Cancel・steering・失効と作用の競合を、到着順や単一flagで解決する。 | 停止範囲、steering後の旧結果の扱い、遅延到着の帰属。 |
| 結果不明を未実行・失敗・成功へ変換し、retry・replayで解消する。 | 不明の保持、試行と作用の区別、自動再実行の禁止、重複防止に必要な保持・区別。 |
| 報告・要約・復旧の過程で確定度を強める。 | 記録・報告・監査での確定度保持。 |

本書の範囲は、認可判断の対象確定から、委任、開始前の現在条件成立、実作用と確定度の把握、競合時の帰属、作用不明の保持、Task・報告への対応付けまでとする。Contextの情報選択・Provider適応の一般契約は[Context Assembly](context-assembly.md)を利用する。Targeted deletionの全域完了、Client帰属の調停手順、backup／restoreの切替手順は、それぞれの既存契約を利用する隣接領域である。

## 3. 認可判断が結び付ける対応

### 3.1 判断対象の論理的な要素

認可判断は、「許可」という一言ではなく、判断対象と実利用の対応である。すべてのAction要求について、適用する範囲で次の対応を保持または正本から解決できる必要がある。全要求に同じ項目・形式を付ける指定ではなく、必要な対応を失った要求は実作用へ進めない。

- 実行主体と委任連鎖。誰の委任で、どのTask・委任範囲の一部として、どの一時Task Agentが扱うか。軽微な本体Actionでは委任元の個体調整と目的への関係。
- TaskとWorkspaceの範囲。対象Task、採用済みの目的・steering前提、関連付けられたWorkspaceとその利用条件。
- 目的。依頼・自発・Schedule各回・steeringのどれに基づく何のための作用か。将来Ruleそのものは目的にならない。
- 実対象と操作。対象の論理的指定、操作種別（Read／Create／Edit／Delete／Execute等のrisk区別）、送信先、想定する外部作用の種類。
- 主なdataと用途。利用するdataの範囲と、そのActionの用途としての利用条件。Credential値はここに含めない。
- 費用・risk。判断に必要な粒度の費用・risk。推定・不明の区別を落とさない。
- 依拠したOwner意図・Rule。現在の明確な依頼、保存済みRule、割当同意、device許可等のどれを何の対象へ適用したか。LLMの生成文・Tool result・過去Memoryの引用は、この依拠関係の代わりにならない。

判断時の対象記述と実行時の実対象が文字列として一致することだけでは対応にならない。解決・展開・別名・link・mount・UI要素の特定等を経て実対象が定まる場合は、第5.2節の実対象解決を経て対応を確かめる。

### 3.2 由来の保持と自己承認の禁止

Ownerに由来する入力・管理操作、入力中に引用された外部content、その意味の解釈、制御ownerによる確定を区別する。LLM、Task Agent、Tool、MCP、shell、Computer Use、Plugin等から生成されたcontentは、Permissionを新設・拡大・自己承認できない。中継・要約・保存・委任を経てもこの制約は変わらない。

次のものは、それだけでは別Actionの承認にならない。Rule保存、Credential登録、Provider認証、Provider同意、Schedule作成、観測ON、Clientへのpresence、個体の親密さ・関心、Taskの受付、Agentの成功申告、Tool UIのclick、MCP Appsからの追加要求、sandbox外例外の許可。sandbox外例外は特定command・由来・権限等に対応する隔離例外であり、仲介する個々のActionの包括承認ではない。

現在の明確な依頼は、その依頼を満たす一回限りの承認として解釈できる。ただし永続Deny・Always ask・Capability境界を黙って上書きしない。将来Ruleは解釈・範囲の提示・保存・Undoを経て成立し、保存自体はActionのtriggerにならない。既存の依頼・Rule・同意で判断できる事項に、入口・委任先・経路が変わっただけの理由で不必要な再確認を増やさない。

### 3.3 判断記録と生きた許可の区別

認可判断の記録（何についてどう判断したか）と、その後の各利用時点で有効な許可（今その利用をしてよいか）は別の意味である。判断記録はAudit・説明・対応付けの材料であり、生きた許可の正本ではない。保存されたAllow、委任時のcopy、事前の判定、復元されたRule・同意、推論context内の許可文、cached判定を、そのまま現在条件として再利用しない。

判断を再利用できる場合でも、各実利用・開始・保存・提示の箇所で現在の条件を適用する。事前判定の再利用は、失効・scope変更・個体停止・帰属切替・cap到達・steering・消去・restore保留の発生を無視する理由にならない。一方、無関係な変更ごとに全処理を再承認することは要求しない。再評価の要否は第5.3節の重要な変更で決める。

判定用の推論にも、その推論自身の割当同意・認証用途・費用制限を適用する。審査対象Actionの許可・実行を、その審査のための推論の先行条件にしない。推論条件が不足する場合は不足・判断待ちを管理面へ返し、明確な停止・拒否・管理操作・機械的検証を推論待ちにしない。

## 4. 委任と経路変更の不変条件

### 4.1 委任連鎖は境界を広げない

Task Agentは委任元CompanionとTaskの現在の境界に参加し、独立したAllow・Credential・Provider override・予算・長期人格・Relationship・Agent scope Learningを所有しない。同じfolderを使う別Taskの承認、別TaskのCredential、旧担当の私的Learningを流用しない。再委任・並列委任も同じ委任元の境界内へ従属し、共通の消費制約へ参加する。

委任は元のTask／Owner意図／Permission／Workspace／Client等の境界を迂回できない。委任先・並列度・実行順の変更は、新しい権限の根拠にならない。委任元が失った条件（失効・停止・scope縮小・帰属喪失）は、委任先へ引き継がない。委任元のCapability・Permission・費用・Task／Workspace境界、CompanionのProvider設定と存在場所の制約を、copyした独立権限へ変えない。

Task引継ぎはOwner依頼に基づき、担当削除からの自動引継ぎ・自動Global化・担当Scheduleの自動復活をしない。引継ぎ後も旧個体の私的Learning・承認・Credentialを包括継承しない。

### 4.2 経路・手段の変更は実対象の制限を変えない

複合Tool、shell、MCP、Skill付属script、Computer Use、Providerが生成したAction要求、MCP Appsからの追加要求も、実際の作用に対して境界を適用する。DenyされたActionを、名前・経路・Tool・表現を変えた同等のActionで迂回しない。「読取用」「成功済みSkill」という名称でnetwork・shell・外部作用を許可しない。

通常Toolの許可から、ene自身の保存領域・管理入口・第一者承認UIへ回り込まない。許可済みComputer Useでene自身の承認ボタンや設定画面を操作してOwner操作を偽装しない。内部復旧は担当ownerと保全・消去の管理契約へ戻し、Workspaceに内部保存領域を指定したstate修復を許さない。

MCP Appsの操作は外部Tool UIの一時入力であり、第一者の制御変更・承認を直接成立させない。UIの表示・終了・再表示はTask・server・Actionの終了・replay契機にしない。追加入力・Owner確認が必要なら作業が判断待ちを引き受ける。

Local MCPのsandbox外例外は権限・制約が管理する個別の隔離例外であり、Pluginへの流用・個々のAction承認への転用をしない。外部process内部への完全強制・確実な停止は報告しない。外部process内部で何が起きたか確認できない作用は、第8節の不明として扱う。

### 4.3 Taskを経ない軽微Actionも同じ境界を省略しない

軽微な本体ActionはTask受理・Agent委任を省略できるが、第3節と第5〜9節の権限・作用・記録境界は省略しない。個体調整が必要な活動記録を管理し、実行・拡張の確定度を参照する。これを理由に全ActionをTask化しない。一方、まとまった作業・file実作業・Computer Useを含むまとまった作業・長期継続・並列委任価値のある作業はTask化・委任の原則に従う。

## 5. 実作用開始前の現在条件成立

### 5.1 開始前に成立させる現在条件

実行・拡張は、要求された意味と実対象・操作・data・送信先・外部作用の対応を守り、現在の制限内で作用する。各開始について、該当する現在条件を実対象へ適用する。適用の責任は実行・拡張に残り、許可の意味自体は権限・制約に残る。

- Permission・Rule・Deny・Always ask・Capability境界。判断対象との対応、重要な変更の有無、失効の有無。
- Task・委任・Workspace範囲。担当・委任の有効性、Workspace関連付けの有効性、steering前提との一致。
- Client依存条件。Computer Use等では委任元Companionの現在のactive Client、device許可、現地の利用可能性を同時に満たす。操作対象の変更は先に個体の移動を必要とする。Host同居Clientにも同じ帰属制約を適用する。
- 認証用途・有効性。設定済み接続・用途・有効性の照合。秘密値をLLM生成argument・model context・通常resultへ補完しない。
- 費用・資源・並列・反復の上限。処理中・未報告・不明な消費をゼロとせず、Agent・用途ごとの独立残額へ分割しない。
- 停止・保留。Cancel・個体停止・失効・targeted deletionの保留・restore後の保留。いずれかが対象の新規開始を禁じる場合は開始しない。

条件を満たせない開始は保留・拒否し、古い判定・解決済み経路だけで新規利用を始めない。Background・Scheduleの無人実行も同じ条件に従い、Client不在・Schedule到来を自動承認の理由にしない。Owner確認が必要なら実行せず判断待ちにする。

### 5.2 実対象の解決

判断時の論理的指定を、作用時点の実対象へ解決する。Filesystemでは選択範囲と操作種別を守り、path traversal・link・mount等による境界外accessを拒否する。解決できない・解決結果が判断対象と対応しない場合は開始しない。解決の失敗を、近い対象への作用・広い対象への作用へ読み替えない。

判断から実利用までの時間差における対象・条件の変化は、古いcopyで迂回しない。変更成立後の新規利用に旧判定を適用せず、すでに開始した利用には第7〜8節の停止・遅延結果の契約を適用する。関係する前提の変更を見落として利用してしまう確認方式は不可とする。具体的な競合制御・確認配置・変更検知方式は後続設計で選ぶが、関係を確認できなければその新規利用を許可済みと推定しない。全domainの共通時刻順や一つの排他的transactionを要求するものではない。

### 5.3 重要な変更と再評価

目的・実対象・操作・送信先・data・外部作用等の重要な意味が変われば、現在の条件で再評価する。重要な変更には少なくとも次を含む。対象の同一性・操作種別・作用種類の拡大、目的・steering前提の変更、Task・委任範囲の変更、Workspace・scopeの変更、Client依存Actionの帰属・対象Clientの変更、依拠したRule・同意・device許可・Credential有効性の変更、費用・riskの重要な変化、停止・保留の発生。

無関係な変更ごとに全処理を再承認しない。表示locale、無関係なMemory更新、無関係なTaskの進捗、Body・Voiceの演出等は、対象Actionの再評価理由にしない。追加指示は作業が反映範囲を確定し、反映できない理由・選択肢を返す。変更前の依頼に対する遅延結果を、新しい依頼の達成結果として自動採用しない。

## 6. 作用と確定度の分類

### 6.1 別の事実として対応付ける

入力受付、Task受理、認可判断、実作用の開始、把握できた作用、内部記録の保存、Task達成、Ownerへの報告は別の事実であり、別のownerが確定する。一つの成功状態へ潰さない。

| 説明する意味 | Authoritativeな責任 | 推測で置換しないもの |
|---|---|---|
| Action要求の受付・開始 | 実行・拡張（受付・開始の事実） | Permission判断の存在、Task達成、作用成功 |
| 実対象への作用と確定度 | 実行・拡張 | Allow、Cancel受付、通信成功からの作用成功・不存在の推定、Agentの自己申告 |
| Taskの目的・達成・未完了 | 作業 | 会話での受付、Agent終了、個別作用の確定度の独立変更 |
| 制御変更・現在の利用可否 | 権限・制約 | UI表示、過去Allow、Audit内の文、認証成功 |
| 未伝達と報告状況 | 個体調整（内容管理）、入出力・提示（実際提示） | 接続・表示copy送信、Task完了からの報告済みの推定 |
| 保存・監査の成立 | 保全・消去と各参加owner | 局所完了、出力file存在、操作画面終了からの全域成功 |

内部記録の保存成功は外部作用の成功ではなく、外部作用の成功は内部記録の保存成功ではない。内部保存が失敗しても外部作用が未実行になるわけではなく、最後の正常記録が外部世界の最新状態とは限らない。

### 6.2 確定度の種類と不明の保持

実行・拡張が把握する確定度は少なくとも次を区別する。確認できないことを、未実行・失敗・成功のいずれかへ勝手に変換しない。確定度を変える場合は、その事実ownerが新たに確認した根拠を用いる。

- 確認済み成功。実対象へ想定した作用が生じたことを、Task Agentの申告以外の根拠で確認できた場合。何がどう変わったかと確認根拠を対応付ける。
- 確認済み失敗。作用しなかったこと、または意図どおりに作用しなかったことを確認できた場合。未作用、部分作用、作用後の後処理失敗等を必要範囲で区別する。部分作用では確定済みの作用を消さない。
- 不明。送信・実行の開始後に、成功したか確認できない場合。外部へ送信した直後の接続切断、timeout／response loss、Client切断・移動との競合、停止競合、Host停止、記録保存失敗を伴う場合を含む。不明は、その事実ownerが新たな確認根拠を得るまで不明として保持する。

Cancel受付済みは停止済みではなく、通信成功は作用成功ではなく、UI表示は実行許可でも完了でもない。Provider・MCP・外部processの「成功」応答は、eneが把握した作用の証拠として受け入れる場合でも、対象・作用との対応を確認して扱う。外部resultの由来と確認できた範囲を保つ。

### 6.3 部分失敗と複合作用

並列Agentの一部失敗、複数stepの一部未完了、複合Toolの一部作用は、他の確定済み結果・外部作用を消さない。作業が現在の依存・制約に応じて残りの遂行可否を判断し、部分成果・未完了を取りまとめる。全Agent一律Cancel・無条件続行という新方針は置かない。

transport層の再送・再試行で外部作用が重複し得る場合は、それを隠れた下層の回復として扱わず、論理的な試行として第8節へ接続する。具体的なretry algorithm・timeout値は固定しないが、重複し得る再送を「同じ試行の継続」として不明・重複管理から除外する方式は採れない。

Credential参照は非秘密の用途識別であり、LLMが記述しただけでは利用可能にならない。認証先のerror・resultが秘密を反射する場合も、通常result・説明・History・Learning・Audit・Debugへ通さない。各受入・保存・提示箇所が非露出へ参加する。

## 7. 競合時の帰属と順序

### 7.1 停止・失効は新規開始を禁じ、進行中はbest-effortで扱う

Cancelは第一者管理経路から作業へ届き、本体LLM・Agentの正常終了を待たず受け付ける。作業は対象遂行を止め、実行・拡張は進行中作用をbest-effort停止する。停止要求の受付と外部作用の停止完了を分ける。すでに生じた作用・停止不能・不明・未保存作業を保持して報告する。停止の受付・新規開始の禁止・状態参照を、外部processの終了や全Taskの正常完了待ちにしない。停止経路の名で新しい未承認作用を始めない。

許可・device・同意・Credentialの失効、Companion停止、targeted deletion・restoreの保留が成立した場合、それだけを根拠とする新しいActionを開始しない。依存する進行中処理はbest-effort停止し、別Agent・別Client・別Toolへの迂回で失効を回避しない。無関係なHost Taskまで一律Cancelしない。失効前の作用・判断記録を巻き戻さない。

Host shutdown・再起動でも必要な進捗・作用不明・未伝達・全域操作の未完了を保全し、外部作用がHostと同時に消えると推定しない。

### 7.2 steeringは新しい目的であり、旧結果の自動採用ではない

追加指示の発言はHistory、採用・反映範囲は作業のTask context、承認の有効性は権限・制約に残る。steering後の目的に旧委任範囲・旧結果を組み合わせる対応が矛盾する場合は、その用途で採用せず再評価する。変更前の依頼に対する遅延結果を、新しい依頼の達成結果として自動採用し、それを根拠に後続Actionを開始しない。

Ownerの承認が到着した時点でも、対象Action・担当・制約が同じかを照合する。Cancel済み・失効済み・steering済みの作業を古い承認で復帰・解除させない。判断待ち・Agent終了待ちをLLMの反復問い合わせで実現しない。

### 7.3 遅延到着の帰属

Cancel・steering・失効・移動・削除・復元等の後にTool結果・承認・推論結果が到着しても、次の実行を自動で開始しない。必要な作用事実は元のAction・Taskへ対応付け、Taskの採用・達成判断は現在のTaskへ対応付ける。記録・semantic更新・次の実行・提示は別の受入判断であり、一つの汎用valid／invalid判定へ全責任を移さない。

| 交差 | 残すべき事実・許される受入 | 禁止する扱い |
|---|---|---|
| Cancel・失効後に作用結果・承認が到着 | 実行・拡張の作用事実は元Actionへ、作業の達成判断は現在Taskへ対応付ける。必要な作用記録へ対応付けたうえで後続を開始しない。 | 古い承認でCancel・失効を解除する。旧結果を新目的の達成として採用し後続を開始する。 |
| steering後に旧目的の結果が到着 | 元Task・元Actionへの記録は残せる。現在の目的への採用は再評価を必要とする。 | 旧結果を無条件に新目的の達成とする。 |
| 個体削除後に作用結果が到着 | 必要な作用事実を残るTask／活動記録へ対応付け、管理面から説明する。 | 削除済み個体の応答・Memory・Relationship等を再作成する。 |
| restore後に旧live処理の結果が到着 | 旧実行の作用説明と復元された記録を区別する。 | 旧live状態を復元正本へ混ぜ、Task・Learning・許可を復活させる。 |
| Client再接続時に古い入力・表示copyが戻る | Hostの現在正本・帰属・消去状況に従い、未確定と受理済みを区別する。 | Client copyでHostを上書きする。未送信操作を自動Action queueとしてreplayする。 |

Cancel・失効がすべての事実報告を禁止するわけではなく、記録できたことが次の利用を許すわけでもない。Cancel後に届いた結果はCancelを無かったことにせず、後続Actionを再開しない。

## 8. 作用不明の保持と重複実行の防止

### 8.1 不明にしてはならない変換

外部作用が成功したか不明な場合は自動で再実行せず、重複の可能性を説明してOwnerの判断を求める。成功不明な外部作用を、別Tool・Host・Clientからの再実行、接続回復後の自動replay、Client移動を理由とする別Clientでの自動再実行、Host再起動後の自動再開、Task再開時の無差別replayで解消しない。Ownerが途中Taskの明示再開を選んでも、不明Actionの自動再実行にはしない。再開依頼を無差別replayにしない。

記録保存の失敗も、最後の正常記録だけから未実行を推定する理由にしない。記録保存失敗時は、最後の正常記録が外部世界の最新状態とは限らないことを保つ。復旧・再起動でも自動replayしない。Provider／Network回復、MCP Apps再表示、Client再接続、Companion Resume、Host自動起動、restore後の有効化は、それぞれ成立した条件だけを変え、不明の解消にはならない。推論の承認済みfallbackは外部作用不明を再実行で解消する契約ではない。

### 8.2 重複を防ぐために保持・区別できる必要がある関係

再接続、Client移動、retry、Host再起動、Task再開等によって同じ作用を重複実行しないために、architecture-levelで少なくとも次の関係を保持・区別できる必要がある。具体的なidempotency key、transaction protocol、retry実装、queue／actor／event bus、DB schema、lock方式は固定しない。

- 試行と作用の区別。Actionの試行（eneが開始した単位）と、外部世界への作用（何が生じたか）を別の関係として扱う。retry・再実行は同じ試行の継続ではなく、 prior不明へ対応付けられた新しい試行とする。試行の識別と、依拠した認可判断・Task・委任との対応を保つ。
- 判断・目的との対応。どの試行がどの認可判断・目的・steering前提・Task／委任・Workspace条件に基づいたか。steering・再開後の新しい試行が、旧判断・旧目的のまま開始されないようにする。
- 実対象との対応。解決済みの実対象・操作・送信先と、判断対象との対応。対象・操作が変わった再実行を、同じ作用の再送として扱わない。
- 段階の区別。受付・開始・送信・把握できた作用・確定度のどこまで進んだか。開始したことと作用したことを混同しない。到達不能・確認不能を成功・未実行へ読み替えない。
- 確定度と根拠。確認済み・不明の別と、その根拠・観測者（実行・拡張の把握、外部応答、現地確認等）。不明は新たな確認根拠が得られるまで保持する。
- 停止・保留との関係。Cancel・失効・移動・再起動のどれと競合した不明か。競合相手の解除だけで不明が解消したことにはしない。

必要な関係を保持・参照できず有効性を確認できない場合、成功・承認済み・未実行と推定しない。到着が遅いことだけで出来事を新しくせず、最新に届いた結果だけで現在値を決めない。

### 8.3 retry・再開・再接続の扱い

retryは新しい試行として、現在の認可判断・目的・実対象・条件を満たして開始する。確認済みに失敗し作用しなかった試行の再実行は、同じ内容をカバーする既存の依頼・Rule・Permissionが有効なら、その範囲で開始できる。不必要な再確認を増やさない。一方、作用不明の試行の再実行は、重複riskを説明したOwner判断を必要とし、Owner判断なしに開始しない。費用・risk・重複可能性を判断に必要な粒度で示す。

確認済み失敗と不明を同じretry経路へ潰さない。確認済み失敗の再実行を、不明試行の自動再実行の先例にしない。Ownerの再開指示は包括的なreplay許可ではなく、各不明試行の重複riskと現在条件へ対応付けて扱う。Owner判断を経た再実行でも、旧試行の不明は解消したことにならず、両試行の作用・確定度を別々に保つ。重複が後から判明した場合も、既知の作用として説明できるようにする。

Client再接続・移動・Host再起動・restore後の旧試行の結果が遅れて届いても、現在のTask・復元正本へ無条件に混入させない。旧live状態を復元後の正本へ混ぜ、Task・Learning・許可を復活させない。Clientの古い入力・表示copy・未送信操作を自動Action queueとしてreplayしない。

### 8.4 Client依存作用とHost再起動時の不明

Computer Use等のClient依存Actionを実行中に移動・切断が必要になった場合は、安全に区切れるところまで移動を遅らせられる。移動を理由に、元Clientで実行していたActionを別Client・Hostで自動再実行しない。Client切断による停止はbest-effortとし、停止できなかった処理・既知の作用・結果不明の作用を示す。成功したか不明な外部作用はHost PCその他のClientで自動再実行せず、重複の可能性がある場合はOwnerの判断を求める。Companionの移動と未確定Actionの再実行は別に扱う。排他性を確認できないClientは対象活動を継続せず、Hostも現地の物理的停止・外部作用取消を確認なしに成功扱いしない。

Host再起動後の途中Taskは自動再開せず、保存済み進捗・既知の外部作用・不明・未完了を示してOwnerの明示再開を待つ。Agent sessionの残存、Provider回復、Host自動起動の選択だけでは再開しない。再開時も現在の担当・Permission・同意・cap・Workspace・Client依存条件と不明作用を照合し、不明作用の重複riskはOwner判断へ戻す。Running個体のpresence復旧と途中Taskの再開は別の条件であり、前者の成立は後者の開始権限にならない。

## 9. 記録・報告・監査での確定度保持

Task記録は、実行・拡張が把握した作用・確定度を参照・集約する。同じ作用の確定度を作業側で独立更新しない。Agentの成功申告を作用の証拠の代わりにしない。Task全体の達成判断は作業、個々の作用の把握は実行・拡張に残る。Task終了時は結果・変更file・保存先・失敗・未完了・次の判断を担当Companionから報告する。永続保存先が未定なら最終保存前にOwnerの選択を得る。

個体調整はTask正本を参照し、結果・変更・保存先・失敗・未完了・次の判断をOwnerへ統合して報告する。active Client不在なら未伝達管理へ接続し、次Clientで現在の結果・利用制限に基づいて要約報告する。接続・表示copy送信だけで報告完了にせず、提示不明を保持する。報告済みは承認済み・Task再開済みではない。exactly-once配信・既読保証は追加しない。

Ownerへの最終報告・管理面の表示・Body・Voiceの演出・自然な要約が、未完了・不明を成功へ変えてはならない。確定度・費用の報告／推定／不明を保ち、推定・不明を確定値へ昇格させない。重要なVoice内容にはText代替を用意し、表示localeは承認の意味を変更しない。

各発生元は主要Action・Permission判断・外部作用・Provider割当・Credential参照・重要設定変更等について必要事実を供給する。保全・消去はAuditの追記順と保持を管理し、その順序を外部世界の発生順や現在の許可の正本へ昇格させない。Auditには通常、会話・file本文、秘密、削除済みprivate内容を含めない。遅延・訂正された報告も元対象との対応を保つ。監査記録を元stateの再生・自動実行の入力にしない。

作用の説明とtargeted deletionが重なる場合は、必要な事実の記録と対象情報の除去を両立させ、対象本文を作用記録という理由で残さない。各受入先は消去へ参加し、古い結果から対象情報を戻さない。外部へ送信・export・backup済みcopyや外部Workspaceの消去、Credentialの外部失効は作用記録の完了範囲外として説明する。

## 10. Runtime FlowsとCross-cutting Designに対する横断検証

[Major Runtime Flows](../architecture/runtime-flows.md)第3節とRF-01〜08、[Cross-cutting Design](../architecture/cross-cutting.md)CC-01〜07に対する、正常系と意味のある競合のwalkthroughは次のとおりである。

| Flow・交差 | Walkthroughと必要な結果 | 本書の成立箇所 |
|---|---|---|
| RF-02 正常: 委任file作業 | 依頼→Task化→委任→認可判断→実対象解決→作用→Task達成→報告がそれぞれ閉じる。Agent申告を作用証拠にせず、Workspace既定保存・最終保存前確認を守る。 | 3.1、5.1〜5.2、6.1〜6.2、9。 |
| 判断後の条件変更: symlink差替え・Workspace変更・Rule失効 | 開始前に実対象解決・現在条件で旧判定を使えない。対象外への作用・失効後の新規開始をしない。無関係なMemory更新では再承認を要求しない。 | 3.3、5.2〜5.3。CC-01・03を維持。 |
| steering・Cancel競合: Cancel直後の作用完了、steering後の遅延結果 | Cancel受付と停止完了を分け、元Action・Taskへ事実を残す。旧結果を新目的の達成にせず、古い承認でCancelを解除しない。後続を自動開始しない。 | 7.1〜7.3。CC-03・04・07を維持。 |
| Task Agent委任: 別経路でのDeny迂回、別Task承認の流用 | 委任連鎖・実対象制限で迂回を閉じる。Agentの独立Allow・Credential・予算を作らない。軽微Actionも同じ境界に従う。 | 4.1〜4.3。CC-01を維持。 |
| Computer Use中のClient切断・移動 | 安全な区切りまで移動を遅らせ、元Actionを別Client・Hostで自動再実行しない。best-effort停止と既知／不明を作業へ返す。排他性不明のClientで活動を続けない。 | 8.4、7.1。CC-04・RT-02を維持。 |
| 外部Toolのtimeout／response loss | 不明を保持し、重複riskとOwner判断を次の状態にする。失敗＝未実行とせず、別経路で再実行しない。retryは新試行として現在条件で扱う。 | 6.2、8.1〜8.3。CC-07を維持。 |
| Host restart: 途中Task＋in-flight不明 | 自動再開・自動replayしない。保存済み進捗・既知作用・不明を示し、明示再開時に現在条件と重複riskを照合する。presence復旧はTask再開の権限にならない。 | 8.3〜8.4、7.1。CC-04を維持。 |
| delayed result: 削除・復元後の到着 | 削除済み個体のLearningを再作成せず、残るTask記録へ必要な事実だけ残す。復元正本へ旧live結果を混ぜない。消去対象本文を作用記録で残さない。 | 7.3、9。CC-03・05を維持。 |
| Ownerへの最終報告: 不明・部分失敗を含むTask終了 | 確定度を保った報告・未完了・次の判断を示す。要約・演出で成功へ強めない。active不在なら未伝達として次Clientで報告する。 | 9、6.1。CC-07を維持。 |
| Schedule無人実行で判断待ちに到達 | 実行せず判断待ちにし、自動承認・別経路迂回をしない。各回の現在条件を再評価し、missedを補完実行しない。 | 5.1。CC-01・04を維持。 |
| MCP Apps・sandbox例外を経る作用 | Tool UI入力を承認にせず、sandbox例外を包括承認にしない。外部process内部の不明は不明として扱い、確実な停止・強制を報告しない。 | 4.2、6.2、8.1。CC-01を維持。 |
| 補助推論・費用不明との競合 | 推論失敗・費用不明で成功を捏造せず、不足・判断待ちを返す。事実報告・Cancel受付は次の許可を待たない。処理中・不明な消費を全体制限から落とさない。 | 3.3、5.1、9。CC-06を維持。 |

Cross-cutting契約との照合結果は次のとおりである。

| 契約 | 詳細化によって維持する性質 |
|---|---|
| CC-01 | 判断対象と実対象の対応、委任・経路変更での境界不変、生成contentからの権限新設の禁止。既存依頼・Ruleで足りる場合の再確認を増やさない。 |
| CC-02 | Credentialの分離、参照・派生物の利用範囲、Provider適応の一般契約を前提に利用。Action固有の判断へ情報選択の正本を移さない。 |
| CC-03 | 同一試行と同一作用、過去の正しさと現在有効性の分離。遅延結果の用途別受入により単一valid判定へownerを集めない。 |
| CC-04 | Client依存だけを現在帰属に結び付け、Stop・Cancel・再起動・restore保留を区別。解除一つで他の禁止・不明を消さない。自動replayしない。 |
| CC-05 | 作用事実の説明と消去参加の両立。原記録削除・context終了・局所完了を全域完了にしない。外部copy消去を作用記録の成功条件にしない。 |
| CC-06 | 並列消費・処理中・不明を同じ上限へ反映し、制御・保全経路を推論・長時間Task待ちにしない。 |
| CC-07 | transport・Tool・Task・報告の確定度を分け、不明を成功・失敗・未実行へ変換せず、保存・報告・監査・復旧で強めない。 |

本書はsemantic owner、Host／Client配置、trust／failure boundary、lifecycle、permission／consent semanticsを変更せず、新しい第二の正本・無所属の意味状態・LLMによる強制・失敗時専用の迂回・万能Action Managerを導入しない。

## 11. 本書が固定する契約と残す Design Freedom

下位設計は、次を本書が固定した契約として利用できる。

- 認可判断は判断対象と実利用の対応であり、記録と生きた許可は別である。開始前に現在条件と実対象解決を成立させ、重要な変更では再評価する。無関係な変更での再承認は要求しない。
- 委任・経路変更は元のTask／Owner意図／Permission／Workspace／Client境界を広げない。生成content・Tool UI入力・sandbox例外から権限を作らない。
- 受付・開始・作用・記録保存・Task達成・報告は別の事実であり、transport成功・Tool申告を作用成功にしない。部分失敗では確定済みを消さない。
- Cancel・steering・失効後の遅延到着は元Action・Taskへ帰属させ、古い承認での解除・旧結果の新目的への自動採用・後続の自動開始をしない。
- 作用不明は粘着的に保持し、自動再実行・自動replayしない。retry・再開は新しい試行として現在条件で扱い、不明試行の再実行は重複riskを示したOwner判断を必要とする。
- 試行と作用、判断・目的・実対象・段階・確定度・停止保留との対応を保持・区別できなければ、成功・未実行と推定しない。
- 報告・監査・復旧で確定度を強めない。消去対象本文を作用記録で残さない。

本書が採れない選択肢として除外するのは、名前一致だけの対象対応、委任先への権限copy、Denyの同等Action迂回、内部管理へのTool回り込み、古い判定・cached許可での新規開始、不明の未実行・失敗・成功への変換と自動replay、遅延結果の新目的への自動採用、要約・復旧での確定度強化である。いずれも上位契約を成立させないため採れない。

以下は意図的に残すDesign Freedomである。

| 設計対象 | 固定済みのarchitecture property | 残すDesign Freedom |
|---|---|---|
| 判断・対応・現在性の表現 | 由来の偽装ができず、対象変更・失効を各利用先で扱える。確認不能を許可へ変換しない。 | provenance・判断対象・試行と作用の対応の具体表現、確認のまとめ方、Permission evaluator、識別・鮮度確認・競合制御、実対象解決の配置。 |
| 作用の観測・確定 | 作用事実のownerは実行・拡張、Task達成は作業、報告は個体調整。確定度を強めない。 | 作用確認の手段、安全な区切りの具体的方法、部分失敗の粒度、transport再送と論理試行の切分け実装、具体retry・timeout値・algorithm。 |
| 停止・競合の伝達 | 新規開始禁止、best-effort停止、遅延帰属、replay禁止。受付と完了を分ける。 | 停止伝達・切断検知・帰属調停・round区切り・queue／actor／event bus・lock／transaction・IPC・process配置。 |
| 重複防止の保持 | 試行と作用・判断・実対象・段階・確定度・保留の対応を保持・区別し、再起動・移動・再接続を越えてreplayしない。 | 識別子・idempotency表現・保存単位・DB schema・repository・保持期間・永続化を必要とする未完了状態の範囲。 |
| 記録・報告・監査 | 元事実の確定度・privacy・順序の意味と管理到達性を維持する。 | audit format・保持期間・提示確認・要約粒度・UI layout・診断stack。 |
| 消費・縮退・費用 | 並列・処理中・不明を同じ上限へ反映し、制御・保全を維持する。 | 費用予約・集計期間・推定、資源配分、反復抑制の機構。 |

crate／module、Rust trait／type、concrete API・error型、middleware・interceptor・hook、event bus／queue／actor、IPC format、DB schema、transaction／lock、具体的Credential保護・sandbox・Plugin隔離、特定library・SDK・OS APIも固定しない。上表の対応関係から統一Context layer、Policy Engine、Manager、Service、Coordinatorの追加を導かない。既存の12責務、semantic owner、Host／Client配置とtrust boundaryの下で実現方法を選ぶ。

transport再送と論理試行の切分け、実対象解決の配置、試行識別の表現等は、既決の制約を満たす下位設計の自由度として残る。必要な確認・Owner判断の省略、現在同意の拡張、未完了・不明の成功扱い、外部作用rollback・exactly-once実行の新保証はいずれも自由度に含めない。
