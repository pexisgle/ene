# Backup / Restore — 復元範囲・マスターデータ切替・再有効化の詳細設計

本書は、バックアップ（Backup）からEneの内部状態を復元（Restore）する際に、**「何が復元され、何が現在の環境のまま維持され、何が勝手に再有効化されず、どの時点で復元された内部データを新しいマスターデータとして扱えるか」**という論理的なルール（契約）を詳細化するものです。後続のデータ構造、永続化、並行処理、UIなどの具象設計が安全に依存できる水準まで明確に定めます（具体的なファイル形式やライブラリなどの実装方法は固定しません）。

## 1. 詳細化する問題と範囲選定

バックアップ復元（Restore）を単に「バックアップの内容をデータベースに上書きコピーするだけ」と大雑把に考えてしまうと、セキュリティや整合性の破綻につながります。設計で誤りやすいポイントと、本書が定める基本ルールは以下のとおりです。

| 誤りやすい設計 | 本書が定める基本ルール |
|---|---|
| 復元された設定・参照・タスク・スケジュールが存在するだけで、「今すぐ実行可能である」とみなしてしまう。 | 復元されたデータの内容と、現在それが実行可能であるか（最新の有効性）を明確に分離します。復元後は自動実行せず、改めて有効化の確認を行います（第3〜4節）。 |
| 現在の認証情報（Credential store）を過去の状態へ巻き戻したり、復元された過去の同意だけで勝手に外部通信や操作を開始してしまう。 | APIキーなどの秘密情報はバックアップに含めず、現在の安全なストレージを維持します。復元された設定と現在の認証情報を照合し、勝手な自動送信を禁止します（第3節）。 |
| 外部のワークスペースファイルや外部サービスの保有データ、現実世界に起きた影響まで、バックアップ時点に巻き戻せると錯覚する。 | 外部の現実世界は巻き戻せません。リンク切れとなった外部参照（dangling参照）は未解決として安全に扱います（第3〜4節）。 |
| 過去の完了済み操作や結果不明な操作を、勝手に「未実行」「失敗」「成功」へと書き換え、自動リプレイで解消しようとする。 | 結果の確定度（成功・失敗・不明）を正確に保持し、勝手な自動再実行を禁止します（第4〜5節）。 |
| パートナー（Companion）の画面上の復帰と、中断されたタスクや操作の再実行を同一視してしまう。 | キャラクターが画面に再表示されることと、中断タスクの再実行は完全に切り離します。タスク再開にはユーザーの明示的な指示が必要です（第4、7節）。 |
| 復元処理の直前に動いていた古い推論結果、ツール実行結果、クライアントの画面コピーを、復元後のマスターデータに混入させてしまう。 | 復元前の古い実行結果を復元後のマスターデータに混入させてはなりません。用途ごとに結果の受け入れ可否を厳格に判定します（第5節）。 |
| ユーザーが古いバックアップを明示的に復元してデータを復活させることを、個人データ削除（targeted deletion）後の「不正な自動再生成」と同一視してしまう。 | 削除処理の完了と、ユーザーによる明示的なバックアップ復元操作を明確に区別します。ただし未完了の削除処理がある場合は保留を維持します（第8節）。 |
| データの一部だけを新しいマスターにし、古いデータと復元データを中途半端に混ぜ合わせてしまう。 | システム全体で常に単一のマスターデータを保ち、完全な全体置換が成立して初めて新マスターデータとして扱います（第3、9節）。 |
| 復元処理が完了していないのに実行権限だけ先に復活させ、失敗しているのに「復元成功」と画面に誤表示してしまう。 | 復元の成立と実行の再有効化を分離し、すべての整合性が確認できるまで成功表示を行いません（第7、9節）。 |
| 復元途中でHost PCが再起動したときに、中途半端なデータを新マスターデータと誤認したり、安全のための保留を勝手に解除してしまう。 | 再起動をまたいでもデータの整合性と未完了状態を確実に保全し、安全のための保留を勝手に解除しません（第9節）。 |

本書が扱う範囲は、復元対象と現在維持される環境の切り分け、古い情報（staleデータ）の扱い、実行中（live）の活動との隔離、バックアップ作成時の整合性、復元要求の受付から一括有効化までの成立条件、個人データ削除との交差、失敗時や再起動時の論理的安全性です。なお、コンテキスト選択や推論連携の一般ルールは [Context Assembly](context-assembly.md) を、認可判断や実行結果の確定度は [Action Execution](action-execution.md) を、個人データの完全消去は [Targeted Deletion](targeted-deletion.md) を、クライアント切り替えのルールは [Client Presence Transition](client-presence-transition.md) を参照し、本書では再定義しません。また、バックアップの実行スケジュールや世代管理は、通常のユーザータスクのスケジュールとは明確に分離して管理します。

個人データの完全削除（Targeted deletion）と、通常の履歴ログ整理・キャラクター削除・システム初期化（Reset）は、目的の異なる別個のライフサイクルとして扱います。また、外部のワークスペースや外部サービス側のデータは、バックアップされたEne内部データと同じ時間へ巻き戻るわけではない点に留意してください。

## 2. 上位architectureとの位置関係

上位ドキュメントとの優先順位は [設計文書 README](../README.md#設計文書の優先順位と信頼できる情報源) に従います。本書の記述のために、新しいマスター担当（semantic owner）や中央永続化マネージャー、万能の復元マネージャーといった巨大な管理モジュールを勝手に新設してはなりません。既存の12の責務が持つ役割分担は以下のとおりです。

| 責務（サブシステム） | 本書における役割と正当な判断権限 | 勝手に持ってはいけない権限 |
|---|---|---|
| 保全・消去 | バックアップの作成・復元の全体の進行調整、対象時点・範囲・除外設定・作成結果・保留状態の管理。 | 通常の業務データの意味を勝手に変更する権限、単一の巨大トランザクションですべてを支配する権限、全内部構造への無制限アクセス |
| 各データのマスター担当（semantic owner） | 各自が管理するデータの意味、参照関係、復元後の利用可能性の確認。 | 復元前の古い実行状態を勝手に書き換える権限、外部の現実世界を巻き戻す権限、現在の有効性を自分だけで勝手に決める権限 |
| 権限・制約 | 拒否（Deny）、同意、利用枠上限（cap）、失効、復元後の保留状態の判定。 | タスクが達成されたか、外部操作が成功したか、報告が完了したかを勝手に決める権限 |
| 認証秘密（および接続担当） | 現在の安全なCredential storeの維持、復元された参照との照合、再認証要求の管理。 | アクションの実行承認や同意、実行可否を勝手に決める権限 |
| 接続・存在、個体調整、作業など | クライアントの接続状態、キャラクター表示、未伝達メッセージ、タスク再開のための最新条件の提供。 | クライアントが接続されたことだけを理由に、タスク実行権限を勝手に付与する権限 |
| 認識・学習、作業 | キャラクター状態（Companion State）の経過時間の解釈、次回スケジュール日時の算出。 | 一時的な状態を永久に固定化する権限、過去の数値を無制限に保持する権限 |

[Cross-cutting Design](../architecture/cross-cutting.md) が定める基本原則（CC-01: 意図と実利用の一致、CC-03: 最新性と用途別受入、CC-04: 停止範囲と再開、CC-05: 目的別ライフサイクル、CC-07: 確定度の保持）を、バックアップ復元固有のルールとして具体化します。

Host PCがEne内部の永続化データの唯一のマスターデータ保持者（canonical holder）であり、バックアップファイル自体はマスターデータではありません。また、バックアップ復元を行っても外部の現実世界が過去へ巻き戻るわけではないという原則を厳格に維持します。

## 3. 復元されるもの・維持されるもの・自動再有効化されないもの

### 3.1 復元対象の対応

復元の対象となるのは、Host PC上にある現在の安全な認証情報ストレージ（Credential storeの秘密情報）を除く、Ene内部の管理データです。これはバックアップ時点の状態への「完全置換」であり、復元前に動いていた古い状態との中途半端なマージ（混ぜ合わせ）ではありません。少なくとも以下のデータについて、正しく復元可能な関係性を保つ必要があります。

- **キャラクター設定**：キャラクターの静的構成、リビジョン、および各個体への適用関係。外部から取り込んだパッケージ原本そのものはバックアップ対象外とし、内部に取り込まれた設定値のみを復元します。
- **パートナー（Companion）の個体情報**：各個体の同一性、活動状態（起動中 / 停止中の別）、適用済み設定。すでに削除された個体のプライベートデータはバックアップ時点に存在しないものとして扱い、削除後に残る歴史的記録（履歴ログ）のみを含めます。
- **会話履歴・活動記録**：会話履歴（1対1、グループ、ユーザー不在時のキャラクター同士の交流を含む）、保存された活動記録、未伝達メッセージと報告状況。元の記録と「ユーザーへの報告状況」を区別し、画面用のデータを送信したことだけで「報告完了」とみなさない対応を保ちます。
- **経験・記憶・学習データ**：経験サマリー（Experience Summary）とその根拠関係、記憶（Memory）の現在の認識と過去のリビジョン、学習済みスキル（Skill）や学習リビジョン、関係性（Relationship）、キャラクター状態（Companion State）。共有可能な根拠とプライベートな根拠の境界を守り、グローバルなデータからプライベートな根拠本文へのアクセスが勝手に拡大しないようにします。
- **タスク・アクション記録**：タスクの目的・担当・進捗・結果、タスクAgentへの委任関係、アクションの実行状況、操作結果の確定度（成功・失敗・不明）、停止処理の結果。Agentプロセスが消滅したことだけを理由に「完了した」とみなさず、タスク記録として残すべき客観的事実を復元します。
- **ワークスペース関連付け**：タスクとフォルダ・ファイル・外部ソースとの関連付け情報。ただし、関連付け先の外部ファイル実体そのものをバックアップファイル内に収集して肥大化させることはしません。
- **スケジュール設定**：スケジュール設定、作成時のタイムゾーン、初期入力パラメータ、過去の実行記録。各回のタスク記録との対応を保ち、スキップされた回（missed）を後から勝手に「実行済み」に書き換えてはなりません。
- **制御条件・権限ログ**：ルール、個別の認可判断ログ、外部サービス割当の同意、承認済みフォールバック設定、デバイス許可、利用枠上限（cap）などの記録。過去に保存された「許可ログ」を、現在の実行許可として勝手に再利用してはなりません。
- **外部サービス接続情報（非秘密）**：ProviderやMCPツールの接続先URLや設定情報、モデルの能力情報など（APIキーなどの秘密情報は含めません）。
- **利用量・費用の記録**：利用量や費用の記録（実績値、推計値、不明の別を含む）。現在の消費上限の判定ルールは第4節に従います。
- **認証情報の用途参照**：認証情報（Credential）の用途名や参照元情報（安全な識別名のみであり、パスワードや秘密キーそのものは含めません）。
- **監査ログ（Audit）**：バックアップ時点までに記録された監査ログ。完了した監査ログにプライベートな本文や秘密情報を復元させてはなりません。
- **運用設定**：データ保持ポリシー、バックアップ設定など。タスクスケジュールとは独立した運用設定として復元します。

なお、派生データ（ベクトル埋め込み（embedding）、検索インデックス、キャッシュ、外部Providerのセッション情報、集計画面データなど）は、独立した復元対象とはしません。これらは復元された元のマスターデータから必要に応じて再生成されます。過去の古いキャッシュやセッションから、現在の権限や状態を勝手に復活させてはなりません。

また、一時的なデータ（リアルタイムの画面・音声観測データ、ツールの詳細通信ペイロード、推論中の内部コンテキスト、画面描画用の一時コピー、マイクの音声バッファなど）は、復元してそのまま現在として継続利用する対象ではありません。ただし、すでに正式に受理されたユーザー指示、残すべき作業ログ、未伝達の重要報告、結果不明な操作などは、Host PCのマスターデータとして確実に復元します。

クライアント固有の接続認証情報（秘密鍵など）もバックアップからは復元しません。復元されたクライアント機器の情報は、現在の接続・認証手続きを通じて改めて照合されます。

### 3.2 現在環境から維持されるもの

以下の項目は復元対象外であり、復元処理を行う時点の「現在の環境・外部の現実」としてそのまま維持されます。バックアップデータを復元したからといって、これらが過去に巻き戻ったとみなしてはなりません。

- **Host PCの現在の認証情報ストレージ（Credential store）**：APIキーやトークンなどの秘密情報、およびそれらの現在の登録・更新・失効状態は、バックアップから復元したり過去へ巻き戻したりせず、**現在の最新状態をそのまま維持**します（全データ初期化（Reset）とは異なる契約です）。
- **外部の現実世界**：外部ワークスペースにあるファイルの内容、外部アカウントやサービスの状態、ProviderやMCPサーバー側の保有データ、すでに現実世界に生じた操作の影響、OSやデバイス・ネットワークの現在の状態、現在の日時やタイムゾーン情報。
- **現在の接続状態**：クライアントとの現在の接続、到達性、デバイスの利用可否、操作の排他性。過去に保存されていた接続情報を「今も繋がっている」とみなしてはなりません。
- **未完了の全体操作の保留状態**：復元処理の開始前に完了していなかった個人データ削除（targeted deletion）などの消去条件や再保存防止の制約は、バックアップ復元によって勝手に解除してはなりません（第8節参照）。
- **復元操作自体の管理記録**：復元前の正常な状態データは、復元処理全体の完全な成立が確認できるまで破壊せずに保持します。

なお、監査ログ（Audit）はバックアップ時点の状態へと復元されますが、今回のバックアップ復元が行われたという客観的事実（目的、対象範囲、影響、除外項目、実行結果）は、新しい監査ログとして即座に追記されます。ユーザーに対しては、「バックアップ作成日時から現在までの間の活動履歴は、マスターデータとしては残らなくなる」という点を、復元実行前に画面上で明確に説明します。

バックアップ設定自体が復元された場合、保存先やスケジュール設定はバックアップ時点のものに戻りますが、ユーザーが外部ストレージ等に作成した既存のバックアップファイルそのものを勝手に削除することはありません。

### 3.3 自動的には再有効化されないもの

バックアップから設定や同意、ルールなどが復元されたとしても、それだけで「今すぐ外部通信やタスクを開始してよい」と自動的に判断してはなりません。復元されたデータは直ちにアクションの開始根拠にはならず、保留を解除した上で、現在の最新条件と照らし合わせて再評価する必要があります。ユーザーに1件ずつの再承認を強いることはしませんが、一括有効化の際にも拒否設定（Deny）、同意の有無、利用枠上限、認証情報の不足、過去の結果不明な操作などを無視して勝手に進めてはなりません。

- **外部サービス・MCPの参照**：復元された参照情報は、Hostの現在のCredential storeと照合します。現在も有効なAPIキーが存在すればそれを利用できますが、キーが存在しない場合や無効化されている場合は、ユーザーに再認証（キーの再入力）を求めます。
- **モデル割当や同意**：復元されたモデル割当（assignment）や同意設定、フォールバック設定は、現在の認証情報や現在の制約条件を満たしていることを確認して初めて利用可能になります。
- **権限ルールや制約**：復元されたルール、個別拒否（Deny）、「常に確認する（Always ask）」設定、サンドボックス例外などは、現在のタスクや権限失効状況と照らし合わせて評価します。過去に保存されていた「許可された」というログだけで、勝手に新しい操作を始めてはなりません。
- **タスク・スケジュール・外部連携の保留**：復元完了直後は、タスク、定期スケジュール、外部サービス連携による自動処理はいったんすべて「保留（Pause）」状態にします。ユーザーが復元内容を管理画面等で確認し、まとめて「一括有効化」できるようにします。
- **スケジュールの次回実行**：復元された定期スケジュールは、過去にスキップされた回（missed）を勝手に穴埋め実行（補完実行）してはならず、現在時刻以降の次回分から新しいタスクとして開始します。中断タスクの再開にはユーザーの明示的な指示が必要であり、二重実行のリスクがある操作はユーザーの判断に委ねます。
- **クライアント機器の許可**：復元されたクライアント機器の情報は、現在のネットワーク接続、認証の成立、排他性が確認できて初めて有効化されます。過去の接続トークンだけで勝手にペアリングを復活させてはなりません。
- **Hostの自動起動設定**：Host起動時にEneが自動起動する設定が復元されたとしても、それだけで中断タスクを勝手に自動再開したり、ユーザーがいないのに勝手にクライアント画面を立ち上げたりしてはなりません。

### 3.4 新しいマスターデータとして扱える時点

以下のすべての条件が満たされて初めて、復元された内部データをHost PCの正式な「マスターデータ」として切り替えます。それまでの間は、バックアップファイルも、書き込み途中のデータもマスターデータとはみなしません。古い実行状態と競合するような「二重のマスター」を決して作ってはなりません。

1. **整合性の確認**：対象のバックアップファイルが正常に読み込め、データ形式のバージョンが適合し、参照関係が正しく、除外すべき秘密情報や外部ファイルが含まれていないことが確認されていること。
2. **全体置換の完了**：Hostの現在のCredential storeを除く対象データ全体が、論理的に矛盾なく完全に置き換わっていること（一部のテーブルだけコピーできた状態を成功とみなさないこと）。
3. **最新性の照合**：復元データの利用可否を確認するための準備（キャラクター状態の経過時間の解釈、クライアント接続の確認、認証情報の照合、権限の保留設定など）がすべて整っていること。
4. **失敗時の安全確保**：復元処理が途中で失敗した場合は、復元前の正常な状態を破壊せずにロールバックできること。不完全な復元状態を「復元成功」と誤ってユーザーに表示しないこと。

「復元処理が成立したこと」と「タスクや外部通信を再有効化すること」は明確に分離します。復元が完了しただけでは自動処理を開始せず、後述の第7節にある「ユーザーによる一括有効化」と各機能の前提条件チェックを経る必要があります。

## 4. 現在stateと復元stateの分離・staleの扱い

バックアップから復元されたデータが存在することと、それらが「現在そのまま実行可能であること」を明確に切り離します。古いバックアップから復元したことによって、期限切れ（stale）となった権限、外部サービスの前提条件、クライアントの接続状態、完了済みまたは結果不明な操作、すでに削除された外部リソースなどを、勝手に「現在も有効な事実」として扱ってはなりません。

- **権限・ルール・同意・上限**：過去に記録された認可ログと、現在の利用可否はまったく別の意味です。現在のタスク、担当キャラクター、委任関係、ワークスペース、利用枠の消費状況、最新の失効設定を必ず照合します。操作の目的や対象、送信先などの重要な前提が変わっていれば、必ず再評価を行います。ただし、操作と無関係な些細な変更によって不要な再確認ダイアログを乱発することは避けます。
- **外部サービス（Provider）の条件**：復元された接続情報やモデル割当は、現在の利用可能性を保証するものではありません。現在の設定、実際の接続状態、同意状況、費用上限を照合し、承認済みのフォールバック順序に従って利用します。ローカルやLAN向けのデータを、ユーザーの同意なく勝手に外部クラウドに送信してはなりません。
- **クライアントの接続状態**：復元された接続情報やデバイス情報は、現在の実際の接続を意味しません。現在のネットワーク接続、認証、操作の排他性が確認できて初めて、キャラクターの表示（presence）が有効になります。元のクライアントが接続されるまでは「接続なし」として安全に待機し、別のクライアントへ勝手に移動させたり、停止中のキャラクターに適用したり、画面のない環境で勝手にUIを起動したりしてはなりません。
- **外部アクションの実行結果**：復元された「確認済み成功」「確認済み失敗」「不明」の確定度と、その判断根拠をそのまま正確に維持します。復元によって、結果不明な操作を勝手に「未実行」や「成功」に書き換えたり、自動でリプレイしてはなりません。タスクAgent自身の自己申告だけで成功とみなしてはならず、内部ログの保存失敗だけを根拠に未実行と決めつけてもいけません。
- **外部リソース（ファイルやアカウント）**：復元されたワークスペース設定や外部パス情報は、外部のファイル内容やアクセス権を過去に戻すものではありません。外部ファイルがすでに存在しない場合やアクセスできない場合は処理を開始せず、勝手に「似た別のファイル」を対象にしてはなりません。また、外部ファイルを勝手に内部ライブラリに複製して抱え込むことも避けます。
- **キャラクター状態（Companion State）の経過時間**：バックアップに含まれるキャラクターの気分や疲労度などの一時的な状態を復元する際も、バックアップ作成から現在までに経過した現実の時間を考慮します。一時的な気分状態をバックアップ時の値のまま永久に固定してはなりません。一方で、長期的な性格傾向や関係性を、再起動やクライアント切り替えだけで不自然に初期化することも避けます。
- **スケジュールの時刻**：復元されたスケジュールの作成時タイムゾーンや指定時刻の設定を尊重し、現在のOSのタイムゾーン設定などで勝手に上書き変更しません。次回の実行日時は、保存された条件と現在日時から正しく再計算します。Host PCやキャラクターが停止していた間に過ぎ去ってしまった実行回（missed）はスキップされたものとして扱い、勝手に過去分をまとめて穴埋め実行してはなりません。「今すぐ実行（Run now）」が指示された場合は、現在の条件を満たす新しいタスクとして開始します。
- **利用量と費用**：復元された利用実績や推計値はバックアップ時点の情報であり、現在の外部サービス消費量の最新値ではありません。未報告の費用を勝手にゼロとみなしたり、復元された過去の数字を現在の残り利用枠の根拠にしてはなりません。利用枠上限に達している場合や費用が把握できない場合は、安全のために処理を一時停止します。バックアップ復元を「利用枠のリセット」の口実にしてはなりません。

過去の古い情報は、過去に起きた出来事の根拠としては有効ですが、現在の状態や現在の承認の代わりにはなりません。用途に必要な前提条件に矛盾がある場合は、その用途に流用せず、必ず最新の状況に合わせて再評価を行います。


## 5. Restoreとlive activity

復元処理の開始前後に動いている実行中の処理（live活動）と、復元されたデータとの関係は、処理の種類ごとに厳格に整理します。具体的なプロセス停止方法やトランザクションの仕組みは実装に委ねられますが、本ドキュメントが要求する本質的な原則は、**「復元前の古い処理から遅れて届いた結果を、復元後の新しいマスターデータに勝手に混入させてはならない」**ということです。

| 実行中の活動（live活動） | 復元後のデータとの関係・取り扱いルール |
|---|---|
| 会話・推論（応答生成、記憶形成、権限判定、削除探索など） | 復元切り替えの前に開始された推論やツールの実行結果が切り替え後に届いたとしても、復元後の新しいマスターデータに混入させてはなりません。用途ごとに結果の受け入れ可否を厳格に判定し、古い結果で最新の訂正内容を上書きしたり、過去の結果を新しい目的の達成とみなしてはなりません。また、復元前の古いコンテキストやキャッシュ、セッションを、新マスターデータのコンテキストとして再利用してはなりません。 |
| タスク／タスクAgent | バックアップ作成日時より後に実行されていたタスクの記録は、復元が完了した後はマスターデータとしては残りません（復元が完了する前の待機中は復元前の正常データをマスターデータとします）。復元前の古いタスクから遅れて届いた結果を、復元されたタスクの達成や学習データ、権限の根拠として自動採用してはならず、後続のアクションを自動開始してもいけません。復元されたタスク（バックアップ時点で進行中だったものを含む）はいったん保留され、再開にはユーザーの明示的な指示と現在の前提条件の確認が必要です。Agentセッションが残っていることや、外部サービスが復旧したことだけを理由に勝手に再開してはなりません。 |
| アクション（試行と作用） | アクションの「試行」と外部への「実際の作用」を別の関係として扱います。リトライや再実行は過去の試行の継続ではなく「新しい試行」として扱います。外部への影響が不明な操作の再実行には、二重実行のリスクを説明した上でのユーザー自身の判断が必須であり、ユーザーの確認なしに勝手に開始してはなりません。また、失敗が確定している操作と結果が不明な操作を同じリトライ処理にひとまとめにしてはなりません。 |
| 遅れて届いた結果（delayed result） | 「ログに記録すること」「知識として学習すること」「次のアクションを開始すること」「ユーザーに画面提示すること」は、それぞれ別の受け入れ判断です。個人データの削除条件、保留状態、所属関係を個別に照合します。単に届いたのが遅かったというだけで出来事の順序を新しく書き換えたり、直近に届いた結果だけで現在の状態を勝手に上書きしてはなりません。 |
| クライアント接続・一時データ | 復元前の古いクライアント側の画面コピー、未送信の操作、表示用データで、Host PCのマスターデータを上書きしてはなりません。未送信だった操作を自動実行キューとしてそのままリプレイしてはなりません。再接続時の古い一時データだけで、表示状態（presence）や権限、タスク再開を勝手に成立させてはならず、復元されたクライアント機器の情報も現在の接続手続きと照合します。 |
| 定期スケジュール | 復元前に到来した実行回と、復元されたスケジュール設定を明確に区別します。復元が完了したからといって直ちに将来の実行回を開始するわけではなく、ユーザーによる一括有効化を経た上で、各実行回をその時点の最新条件で評価します。過去にスキップされた回（missed）を勝手に「実行済み」に書き換えてはなりません。また、バックアップの自動実行スケジュールをユーザータスクのスケジュールに依存させてはなりません。 |
| 個人データ削除などの全体操作 | 第8節のルールに従います。完了していなかった削除条件や保留設定を、バックアップ復元によって勝手に解除してはならず、復元前の古い処理結果から削除対象データが再保存・再形成されるのを防ぎます。確認不能を勝手に成功とみなさず、一部の処理完了をシステム全体の完了と誤認してはなりません。 |

復元前の古い状態で開始された要求や結果と、復元後の新しい活動・マスターデータは、[Context Assembly](context-assembly.md) 第3節の対応関係（主体、用途、タスク、委任、アクション、クライアント、リビジョンなど）に基づいて厳格に区別します。必要な対応関係が失われた古い結果は、到着先の新しい活動に勝手に付け替えてはならず、その用途では受け入れ拒否（破棄）します。復元前の古い操作についてユーザーに状況を説明する場合でも、その事実の記録と復元対象データを区別し、古い結果からタスクや学習データ、権限を勝手に復活させてはなりません。

バックグラウンド処理や定期スケジュールの無人実行についても同様のルールが適用され、「クライアントが接続されていないから」「スケジュールの予定時刻になったから」「復元が完了したから」といった理由で、ユーザーの承認を勝手に省略（自動承認）してはなりません。ユーザーの確認が必要な操作は、勝手に実行せず「ユーザー判断待ち」として安全に保留します。

## 6. Backup作成の整合

ユーザーからの明示的な要求、または有効なバックアップ設定に基づいて、保全・消去サブシステムが対象時点、バックアップ範囲、参照関係、除外項目、保護方式を各データのマスター担当と照合してバックアップを作成します。タスクスケジュールや特定のキャラクターが稼働中であることは必須条件としません。暗号化しないバックアップを作成する場合は、プライベートなデータが含まれる旨を事前に分かりやすく説明し、暗号化も選択できるようにします。

- 各データのマスター担当は、正しく復元可能な関係性を保った形式でデータを提供します。削除されたキャラクターの残存ログも含め、認証秘密（パスワードやAPIキー）の除外と、外部ファイル実体を収集しないルールを徹底します。単に一部のファイルやテーブルのコピーができたことだけで「フルバックアップ成功」とみなしてはならず、対象時点、参照関係、必要な履歴、未完了状態の対応がすべて揃って初めてバックアップ成功とします。
- 個人データ削除やデータ復旧が未完了の状態でバックアップを作成する場合、その制限事項を無視して「正常で即実行可能なバックアップ」であるかのように偽って作成してはなりません。削除処理の完了を待ってから作成するか、未完了の制約条件を含めた形で安全に作成するかは実装の自由度です。
- アクションを実行中であり、外部への操作結果が不明（in-flight）なものが存在する場合、「データベースに残っている最後の正常記録が、現実世界の最新状態とは限らない」という前提を堅持します。結果不明な操作を勝手に「未実行」に戻して正常なコピーであるかのように偽ってはなりません。
- 作成されたバックアップファイルは、そのままではマスターデータにはなりません。ユーザーが明示的に復元処理を行わない限り、古いバックアップファイルを勝手にマスターデータとして読み直してはなりません。また、Ene内部でデータを削除したからといって、ユーザーが保存したバックアップファイルやエクスポートファイルまで一緒に消去されたかのように誤認させてはなりません。
- ユーザーはバックアップの保存先、スケジュール、保持世代数を選択でき、作成結果や失敗の理由を確認できます。バックアップ作成に失敗した場合でも、システムが現在保持している正常な状態を破壊してはなりません。また、失敗しているのに「成功した」と誤表示してはなりません。
- バックアップのファイル形式、保存の実装方式、整合性の担保方法、暗号化アルゴリズム、対応バージョン、復旧手順の詳細は実装に委ねられます。ただし、暗号化されていないバックアップを作成する場合は、会話履歴、要約、記憶、関係性、キャラクター状態などのプライベートな個人情報が含まれることを事前に明示します。

バックアップの作成処理は、特定のパートナーやタスクAgentが動いていることを前提とせず、管理画面の操作性や保存済みデータの安全性を、キャラクターの身体動作（Body）や音声（Voice）、外部モデルの応答などの成否に従属させてはなりません。

## 7. 受理から新しいマスターデータ確定・一括有効化まで

固定的なステートマシンを無理に定義する必要はありませんが、後続の具象設計は、少なくとも以下の論理的な順序と成立条件を満たさなければなりません。これらすべてのフェーズを単一のフラグに丸投げして省略することは禁止されます。

1. **受理と事前説明**：ユーザーが対象のバックアップを選択します。このとき、Hostの現在の認証情報ストレージ（Credential store）を維持した上でのデータ全体置換、バージョンの適合性、外部ファイルは巻き戻らないこと、過去に削除された情報や古いルール・同意・スケジュールが復活しうること、外部サービスの再認証が必要になる可能性があることの説明をユーザーに提示します（初期セットアップ時の復元も同じルールに従います）。
2. **隔離と保留**：保全・消去サブシステムが各データのマスター担当を復元処理に参加させ、復元前に動いていた古い処理、遅れて届いた結果、クライアントの画面コピーが、復元後の新マスターデータと混ざらないよう隔離します。必要なタスクや外部通信の安全な保留は、権限・制約サブシステムおよび各機能担当が適用します。復元前の古い処理が外部にすでに与えてしまった影響は消えず、結果不明な操作を復元によって「未実行」に書き換えてはなりません。
3. **整合性の照合**：各データのマスター担当が、復元データの整合性、参照関係、利用可能性を確認します。認識・学習はキャラクター状態の経過時間を解釈し、接続・存在は過去の接続情報を現在の接続とみなさないようにし、認証秘密は現在のストレージを維持して復元された参照情報と現在の有効性を照合します。外部ワークスペースのファイル内容やアクセス権はバックアップ時点に戻らないことを確認します。
4. **全体置換の成立（新マスターデータ化）**：保全・消去サブシステムがデータ全体の完全な置換を確認して初めて、復元データをHost PCの正式な「マスターデータ」として確定します。処理が失敗した場合は復元前の正常な状態を破壊せずに保持し、不完全な復元状態や古い状態と競合するデータを「成功」として扱ってはなりません。
5. **復元後の安全保留**：新マスターデータの確定後も、タスク、定期スケジュール、外部サービス連携による自動処理はすべていったん「保留」状態を維持します。保留中や確認の途中でHost PCが再起動した場合でも、復元されたモデル割当や同意設定だけで勝手に自動利用を開始してはなりません。ユーザー起点の操作であっても、現在の認証情報、制約条件、保留ルールを適用します。
6. **ユーザーによる一括有効化**：ユーザーが復元内容を確認し、まとめて「一括有効化」できるようにします（1件ずつの再承認を強いることはしません）。保全・消去サブシステムの復元成立理由、権限・制約サブシステムの最新の利用可否、各機能担当の再開条件が揃って初めて、各種の活動を再開します。一括有効化の際も、拒否設定（Deny）、同意の有無、利用枠上限、認証情報の不足、外部操作の結果不明を無視してはなりません。

ここで固定しているのは論理的な成立条件であり、プロセスの停止方法や画面遷移の具体手順ではありません。通常のHost再起動時のように「中断タスクを明示再開待ちにする」だけでは不十分であり、復元されたデータ全体の内容をユーザーが確認できるステップを必ず挟みます。なお、設定初期化（Reset）、全データ初期化、通常のバージョンアップとは、目的の異なる別個の復旧操作として区別します。

## 8. Backupと削除の交差

古いバックアップファイルには、そのバックアップが作成された後に「個人データの完全削除（Targeted Deletion）」によって削除された情報が含まれている可能性があります。本ドキュメントは、個人データ完全削除のセキュリティ原則と矛盾することなく、「ユーザーが明示的に古いバックアップを復元する」という正当な操作の意味を両立させます。

- 復元を実行する前に、「バックアップ作成後に削除された情報や、古いルール・同意・スケジュールが復活する可能性がある」旨を画面上で明確に説明します。ユーザーがその説明を理解した上で明示的に古いバックアップを復元した結果として情報が戻ることは、システムの脆弱性による不正な自動再生成ではなく、ユーザー自身の正当な意思に基づく明示的復元操作です。
- 復元によって戻った情報は「新しいマスターデータ」として扱い、システムが勝手に自動で再削除してはなりません。これは、削除完了後にユーザーが改めて同じ情報を入力してきた場合と同様であり、今後の新しい経験や対話の根拠として機能し得ます。それらを再び消去したい場合は、ユーザーが改めて「個人データの完全削除」を指示する必要があります。ただし、これを「削除前の古い根拠から勝手に知識が自動再生成されてよい例外」にしてはなりません。
- 復元完了後の保留、一括有効化、および最新条件の再評価を経ることなく、復活した情報を勝手に外部送信したり、アクションや学習に自動利用してはなりません。復活したルールや同意、スケジュールを直ちに自動処理に接続してはなりません。
- 復元が完了した記録や監査ログ、ユーザーへの説明画面自体に、削除対象となったプライベートな本文を再保存してはなりません。また、バックアップ復元によってデータが戻ることを、外部サービスやバックアップファイル側まで完全に消去されたと誤解させないようにします。
- 個人データの削除処理が未完了の状態でバックアップ作成や復元が重なった場合、制約を無視して正常なバックアップを作成してはならず、未完了状態、保留、および再保存防止の制約をHost側で確実に保全します。再起動や再接続、復元後であっても、未完了の認識と必要な保留を維持し、処理途中で再起動したからといって勝手に完了と誤認したり保留を解除してはなりません。
- 削除処理の実行区間（開始からシステム全体の完了まで）に、別の経路から再到着・再生成された対象情報は、同じ削除対象として扱います。バックアップ復元によって戻るデータが削除処理の実行区間と重なった場合は、進行中の削除ルールを適用し、古い根拠からの再形成や遅延再保存を防ぎます。
- 通常の履歴ログ整理、データ容量制限に基づく古いログのローテーション、キャラクター削除、設定初期化と、個人データの完全削除（targeted deletion）は、目的の異なる別個のライフサイクルとして維持します。通常の削除処理の連鎖によって形成済みの学習データや要約を勝手に消してはならず、逆にキャラクター削除の残存ログを個人データ完全削除の対象外にしてはなりません。

上記は、既定の「古い根拠からの自動再生成の禁止」と「ユーザーの明示的なバックアップ復元によるデータ復活」を矛盾なく両立させるためのルールであり、外部ストレージのコピーまで勝手に消去できると保証するものでも、復元後に何でも自動実行してよいとするものでもありません。

## 9. 失敗・再起動のlogical property

具体的なアトミックスワップ、ジャーナルログ、スナップショット、WAL（先行書き込みログ）、トランザクション、Copy-on-Writeなどの技術選定は実装に委ねられます。後続の具象設計は、以下の論理的性質を満たすデータ保持と切り替え方式を選択しなければなりません。

- **単一のマスターデータ**：いかなる時点においても、Host PCが保持する正式なマスターデータは常に1つだけです。復元処理が完全に成立するまでは「復元前の正常な状態」がマスターデータであり、全体置換が完全に成立して初めて「復元された内容」がマスターデータとなります。バックアップファイル自体や、書き込み途中の不完全な状態をマスターデータにしてはなりません。
- **中途半端な混合（マージ）の禁止**：古い状態と復元データを中途半端に混ぜ合わせてはなりません。「復元前のタスク進捗」と「復元された学習データ」、「復元されたルール」と「復元前の利用量実績」などを継ぎ接ぎしたような、中途半端な第3の状態を決して作ってはなりません。
- **権限の先行復活の禁止**：データ全体の復元が完了していないのに、実行権限だけを先に復活させてはなりません。復元の完全成立、ユーザーによる一括有効化、および最新の前提条件チェックが完了する前に、新しいアクションの開始、外部通信、外部への影響を伴う処理を始めてはなりません。
- **成功の誤表示の禁止**：完全に完了していない復元処理を「成功」と画面に表示してはなりません。一部のテーブルやファイルだけのコピー成功を、システム全体の復元成功と誤認してはなりません。未確認の状態、検証の失敗、保留中、通信不能な状態を、勝手に「成功」と読み替えてはなりません。失敗した場合は復元前の正常な状態を保護し、何が失敗したのか、次にどのような安全な操作が可能かをユーザーに明確に説明します。
- **再起動時の確実な保全**：保留中、確認途中、置換処理の途中でHost PCが再起動した場合でも、復元されたモデル割当や同意設定だけで勝手に自動利用を開始してはなりません。復元前の正常な状態、未完了の認識、安全のための保留、再保存防止の制約をHost PC上で確実に保全し、書き込み途中の不完全な状態を新マスターデータとして扱ってはなりません。再起動を「処理完了」や「保留解除」の理由にしてはなりません。中断されたタスクはユーザーの明示的な再開指示を待ち、停止中に過ぎ去った定期スケジュールはスキップ扱いとし、キャラクターの表示状態は元のクライアントへの復帰を試みるというそれぞれのルールに従いますが、復元後の安全保留がある場合はその保留を最優先で維持します。
- **クライアント到達不能の扱い**：クライアントとの通信不能や状態の確認不能を、「復元の成功」や「削除の成功」と都合よく読み替えてはなりません。クライアントが再接続してきた場合でも、クライアント側に残っていた古い画面コピーや入力内容、ツールUIのデータをHost PCに書き戻して、削除されたデータを再形成してはなりません。
- **記録の保全**：ログの中に削除対象の秘密情報やプライベートな本文を残すことは、処理完了の証拠にはなりません。また、一時的な通信バッファが消えたことを「処理成功」や「削除完了」の根拠にしてはなりません。継続して必要なタスク状態、未伝達メッセージ、結果不明な操作、未完了の全体操作などは、本来担当すべきサブシステムが責任を持って確実に保全します。

通常のデータ保存、データベースのマイグレーション、バージョンアップにおいても、完全に成功するまで直前の正常な状態を保護するという同一のルールに従います。未対応の古いバージョンへのダウングレードが成功することを前提とせず、起動前に安全に警告・ブロックします。

## 10. 横断検証

要件定義（requirements）、上位アーキテクチャ設計、および他の重要領域（critical-areas）の設計と照らし合わせた、正常系および異常系（障害、期限切れ、遅延、再起動など）の整合性検証（walkthrough）は以下のとおりです。

| 検証シナリオ | 処理の流れと満たすべき結果 | 本ドキュメントの対応箇所 |
|---|---|---|
| 要件「バックアップと復元」正常系 | ポータブルなフルバックアップの作成、保存先の選択、スケジュール設定、世代管理、暗号化の選択、結果の確認が正しく完結する。秘密情報の除外と、非暗号化時のプライバシー説明を徹底する。 | 3、6。（AD-15, SC-06, RT-09を維持） |
| 同意・認証情報・費用の検証 | バックアップから復元されただけで勝手に利用せず、モデル割当の同意、フォールバック設定、費用上限を現在の条件と照合する。復元された参照情報と現在のストレージを照合し、必要に応じて再認証を要求できる。 | 3〜4。（SO 4.18〜4.21, DR 5.4, 5.5を維持） |
| スケジュール・タスク・PC操作の検証 | 復元後の安全保留、ユーザーによる一括有効化、最新条件の再評価、スキップされた回の非穴埋め、結果不明な操作の自動リプレイ禁止、アクティブなクライアント限定のPC操作を守る。 | 3〜5、7。（SO 4.10〜4.14, AD-09を維持） |
| キャラクター状態と時刻の検証 | 現実世界の経過時間を正しく解釈し、一時的な気分の一方的固定や、不自然な初期化を防ぐ。スケジュールのタイムゾーンをOS設定で勝手に上書きしない。 | 4。（SO 4.9, 4.14を維持） |
| RF-08 バックアップ作成と未完了の削除 | 個人データの削除処理が未完了の状態でバックアップ作成が要求された場合、制約を無視した正常バックアップを作らず、待機するか未完了制約を含めて安全に作成する。 | 6、8。（CC-05, Targeted Deletion 7.4を維持） |
| RF-08 復元と古い実行結果の遅延到着 | 復元切り替え前に開始された推論やツール結果が切り替え後に到着した場合、復元後の新マスターデータに混ぜず、古い操作の記録としてのみ適切に扱う。 | 5。（Context 8.1, Action 7.3, CC-03を維持） |
| RF-08 古いバックアップの明示復元 | 削除済みデータや古いルールが戻り得ることを事前に説明し、復活の事実を新しい監査ログに記録する。古い根拠からの勝手な自動再生成とは明確に区別する。 | 8。（AD-15, CC-05を維持） |
| 期限切れ（stale）な権限・サービス・接続 | 復元された古い記録だけで新規操作、外部送信、クライアント帰属を成立させない。最新の条件と照合し、確認不能を勝手に「許可」や「接続中」に変換しない。 | 3〜4。（Context 7, Action 5, CC-01, CC-03を維持） |
| 完了済み・結果不明な操作の書き換え禁止 | 結果不明な操作を勝手に「未実行」「失敗」「成功」へ書き換えたり自動リプレイしない。リトライは現在の条件を満たす「新しい試行」として扱う。 | 4〜5。（Action 8, CC-07を維持） |
| リンク切れとなった外部参照（dangling参照） | 解決不能・不一致な外部ファイル参照で処理を開始せず、外部ファイルを勝手に変更・削除しない。 | 3〜4。（SC-06, DR 6.4を維持） |

| 削除処理中の切断・再起動・復元 | 確認不能を成功とみなさず、古い一時データを書き戻さない。未完了状態、安全保留、再保存防止の制約をHost側で確実に維持する。 | 8〜9。（Targeted Deletion 7, CC-05を維持） |
| 復元の失敗や途中の再起動 | 中途半端なデータでの新マスターデータ化、データの継ぎ接ぎ、権限の先行復活、成功の誤表示を行わない。復元前の正常データを保護し、再起動後も保留を維持する。 | 9。（RT-09, CC-04, CC-05, CC-07を維持） |
| 復元後の保留中にHostが再起動 | 復元されたモデル割当や同意設定だけで自動利用を開始しない。ユーザー起点の利用であっても最新の条件を適用する。 | 7、9。（CC-04を維持） |
| 画面・音声観測（Observer）や自発的行動との交差 | 復元された観測専用モデル割当や自発的行動設定を、最新条件の確認なしに勝手に有効化しない。キャラクター設定の上書きを勝手に合成せず、古い画面キャプチャを現在の状況に流用しない。 | 3〜5。（Context 6, CC-02, CC-04を維持） |
| 補助推論の失敗や費用不明との競合 | 復元内容の照合や削除探索のための補助推論が失敗したり費用不明であっても、機械的な整合性検証、停止、拒否、管理画面の動作を阻害しない。情報不足を管理画面に正しく返す。 | 3、7。（Context 5.2, CC-06を維持） |
| 監査ログとユーザー報告 | 確定度を勝手に引き上げず、本文の隠し保管庫を作らない。監査ログをシステム状態の自動再生やアクションの自動再実行の入力として使わない。 | 3、9。（Action 9, CC-07を維持） |

横断設計の原則（CC-01〜CC-07）の一般的な定義は [Cross-cutting Design](../architecture/cross-cutting.md) に記載されています。本ドキュメントでは、バックアップ復元の観点から特に以下の点を具体化しています。

- **CC-01（権限と同一性）**：復元された過去のログから勝手に権限を新設せず、復元されたルールや同意を無条件のトリガーにしないこと。
- **CC-03（競合と調停）**：削除前の古い根拠からの自動再生成と、復元完了後の新規データ提供および明示的バックアップ復元を厳格に切り離すこと。
- **CC-05（データ保全と完全消去）**：外部ストレージのバックアップコピー消去を、Ene内部の復元・削除の完了条件と混同しないこと。

## 11. 本書が固定する契約と残す Design Freedom

下位の具象設計（concrete design）や実装コードは、本ドキュメントが定めた以下の不変ルール（契約）を前提として利用できます。

- 復元対象は、Hostの現在の認証情報ストレージ（Credential storeの秘密情報）を除く対象内部データの「完全置換」であり、復元前の古い状態とのマージではありません。バックアップファイル自体はマスターデータではなく、全体置換が矛盾なく完了して初めて復元データがHostの正式なマスターデータになります。
- 現在の認証情報ストレージ、外部の現実世界、現在のクライアント到達性、未完了の安全保留はそのまま維持され、復元データに過去の参照が存在するからといって、これらを過去に巻き戻したとはみなしません。
- 復元されたモデル割当、同意、ルールが存在するだけで、現在の利用や自動処理を勝手に開始してはなりません。復元の完全成立、ユーザーによる一括有効化、および最新条件の再評価をすべて満たす必要があります。1件ずつの再承認を強いることはしませんが、拒否設定、利用枠上限、認証情報の不足、結果不明な操作を無視してはなりません。
- 期限切れ（stale）となった権限、外部サービス設定、クライアント接続、操作結果、外部ファイル参照を、勝手に「現在の事実」として扱ってはなりません。リンク切れとなった外部参照は未解決として安全に扱い、結果不明な操作は不明のまま保持し、勝手に自動リプレイしてはなりません。
- 復元前の古い処理要求、実行結果、クライアントの画面コピーを、復元後の新マスターデータに混入させてはなりません。用途ごとに結果の受け入れ可否を厳格に判定します。
- ユーザーによる明示的なバックアップ復元によるデータの復活は、個人データ削除後の「不正な自動再生成」とは異なる正当なユーザー操作であり、事前の明確な説明、新しい監査ログの追記、安全保留、最新条件の再評価を経る必要があります。未完了の削除処理がある場合の安全保留は、復元によって解除してはなりません。
- 単一マスターデータの維持、データの継ぎ接ぎ（混合）の禁止、権限の先行復活禁止、成功の誤表示禁止、再起動時の未完了保全を徹底します。

本ドキュメントでは、復元データの無条件上書きや中途半端なマージ、認証情報の過去への巻き戻しやバックアップからの復元、復元された参照や同意からの勝手な自動利用、外部現実の巻き戻しやリンク切れ参照の勝手な解消、結果不明な操作の勝手な書き換えと自動リプレイ、キャラクターの表示復帰に伴うタスクやアクションの勝手な再開、復元前の古い結果やクライアントコピーの混入・マスターデータ上書き・自動キューイング、古い根拠からの自動再生成、キャッシュヒットによる制約の省略、外部Providerセッションの無条件再利用、確認不能な状態の勝手な成功扱い、部分的なマスターデータ化、データの混合、権限の先行復活、未完了状態での成功表示、再起動による安全保留の勝手な解除、要約や復旧時の勝手な確定度の格上げを、**採用不可能な選択肢**として明確に排除します。これらはいずれも上位のセキュリティ原則や整合性を破壊するため、決して採用できません。

一方で、以下の項目は実装や具象設計に委ねられる自由度（Design Freedom）として意図的に残されています。

| 設計対象 | アーキテクチャとして固定された性質 | 実装に委ねる設計自由度（Design Freedom） |
|---|---|---|
| 復元データの対応関係と最新性の表現 | データの由来（provenance）を偽装できず、対象の変更・失効・切り替え・削除条件を各利用先で正しく扱えること。確認不能を勝手に許可・最新・完了とみなさないこと。 | 復元対応、データの由来、実行区間、完了境界の具体的なデータ構造。確認処理のまとめ方、対象探索・参照整合性チェック・照合処理の配置、識別子の形式、鮮度確認や競合制御のアルゴリズム。 |

アーカイブやファイル形式、暗号化の実装ライブラリ、DBスキーマ、シリアライズ形式、トランザクションの仕組み、ファイルシステムのディレクトリ構造、Rustの型やトレイト定義、crateやモジュール構成、IPC方式、ロック機構、進捗表示の実装、具体的なリトライやタイムアウトの数値、外部ライブラリの選定なども固定しません。また、上記の対応関係を実現するために、全体を統括する巨大な「Contextレイヤー」や「Policy Engine」「万能Restore Manager」といった過剰な共通モジュールを新設する必要はありません。既存の12の責務、各データのマスター担当（semantic owner）、HostとClientの境界、および信頼境界（trust boundary）の範囲内で、最もシンプルで堅牢な実装方法を選択してください。

対象データの探索、整合性検証、到達性の確認、バックアップと削除の交差処理などの具体的な仕組みは、下位設計の自由度として委ねられます。しかし、必要な確認やユーザー判断の省略、同意の勝手な拡大解釈、未完了・結果不明な操作の成功扱い、外部操作の自動ロールバックや厳密に一度だけの実行（exactly-once）を勝手に保証することなどは、いずれも設計自由度には含まれません。
