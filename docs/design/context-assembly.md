# Context Assembly — 受渡し・利用・結果受入の詳細設計

本書は、用途の異なる責務間で情報を選び、変換し、推論へ渡し、その結果を利用するときの契約を詳細化する。Context Assemblyは新しいSubsystemでも情報の正本でもない。以下の「要求」「利用単位」「対応」は論理的な関係であり、共通object、永続record、protocolを指定しない。

製品挙動のsource of truthは[要件Baseline](../requirements/README.md)、[製品定義](../requirements/product.md)、[要件](../requirements/requirements.md)とする。[受け入れ条件](../requirements/acceptance.md)も検証範囲へ含め、[参考資料](../requirements/references.md)は非規範として扱う。既存実装から製品挙動を補わない。

## 1. 最初に詳細化する領域の選定

比較の基準は、事故の重大さだけでなく、後続設計への依存の広さ、今詳細化しないと誤って固定しやすい境界、既決事項から契約を導ける範囲である。

| 候補 | 後続設計で誤りやすい点 | 今回の判断 |
|---|---|---|
| Context Assemblyの受渡し・利用・結果受入 | 会話、Task、学習、Observer、Permission判断で、本文へ平坦化した情報から由来・用途・制限・時点を復元できなくなる。後段の認可や消去も入力との対応を失う。 | **最優先。** 情報選択algorithmに先立つ共通契約を定めれば、複数の後続設計が安全に独立できる。 |
| Actionの認可判断から実作用までの対応 | 判断後の対象変更、委任、失効、Cancel、作用不明を経路変更で迂回しやすい。 | 次の詳細設計対象。今回定める由来・現在性・生成結果の非権威性を入力に、作用固有の契約を独立して詰める。 |
| Targeted deletionの全域成立 | 原記録だけの消去、処理中の再到着、Client確認不能、再起動後の再形成を取りこぼしやすい。 | 優先度は高いが、今回はcontextと派生結果の参加契約まで。全参加先の完了・復旧協調は独立した設計が必要。 |
| Client帰属切替と活動の区切り | presence、入出力round、Computer Use、Stop、再起動の復帰を一つの状態へまとめやすい。 | 今回はClientに依存するcontextの由来・受入条件を詳細化する。排他帰属と安全な区切りの全設計は分離する。 |

Contextは情報を集めるだけの処理に見えるが、受け手、目的、時点が変わる境界である。ここで「内部にあるから信頼できる」「取得済みだから送信可能」「推論成功だから採用可能」と扱うと、各Subsystemを後から正しく設計しても境界がつながらない。

[Architecture Review #1](reviews/architecture-review-1.md)のObserver assignment分離とLater-design Notes、[Architecture Review #2](reviews/architecture-review-2.md)の限定routing context・制約伝播・鮮度に関する指摘も選定材料にした。ただしレビュー原本の提案を再採用するのではなく、[Architecture Drivers](architecture-drivers.md)第3節と現在のarchitectureへ統合された判断に従う。特に、新scopeの追加や各CompanionのProviderによるrouting要約生成の必須化は行わない。

## 2. 上位architectureとの位置関係

主な詳細化対象は[Cross-cutting Design](cross-cutting.md)のCC-02・03である。CC-01のOwner意図、CC-04の活動条件、CC-05の消去参加、CC-06の推論利用、CC-07の事実の確定度が、contextを通っても失われない条件を接続する。

責務・正本・依存は[Subsystem Decomposition](subsystems.md)、[State Ownership](state-ownership.md)（SO）第4〜8節、[Dependency Rules](dependency-rules.md)（DR）第3〜7節を維持する。[System Context](system-context.md)のHost／外部境界、[Runtime Topology](runtime-topology.md)のClient・Provider・MCP・Plugin・MCP Appsのtrust／failure boundaryも変更しない。

| 本書内の役割 | 既存の責任とauthoritativeな判断 | Contextが持ってはならない正本 |
|---|---|---|
| 利用元 | 個体調整、作業、認識・学習、共有観測等。用途、必要な論理的情報、結果を何へ利用するかを決める。 | 全用途共通の目的、独立したAgent権限、全結果の採否 |
| 情報owner | History・個体文脈は個体調整、Task context・内部source copyは作業、Memory等は認識・学習、静的構成はCharacter等。内容・意味・由来・revision・所属を供給する。 | 内容copyを独立した正本にすること、統一Learning、外部原本の現在値 |
| 権限・制約 | Owner由来の制御、同意、明示的な非共有・保存禁止、現在の利用条件を各ownerの事実と照合する。 | context内だけで更新できるAllow、同意、scopeの意味 |
| 推論 | 現在のassignmentの解決、Provider能力への適応、送信、利用量・失敗の対応を担う。 | 個体情報の独立選択方針、semantic state、最終採否 |
| 各実利用・受入責務 | 参照・変換・送信・保存・提示・作用のそれぞれで制約を適用し、意味上の結果を該当ownerへ戻す。 | 「推論済み」を根拠とする制御変更・成功状態 |
| Lifecycleの提供元・coordinator | 個体調整、作業、接続・存在、権限・制約、保全・消去が、それぞれ活動・Task・帰属・失効・全域操作の現在条件を供給する。 | 一つの共通な稼働状態や、context専用の削除完了 |

認証秘密は認証用途だけに秘密を供給し、通常contextへ値を渡さない。外部file・MCP Resource等の取得は実行・拡張の既存境界を通す。Context Assemblyを検索の名で任意I/Oや内部正本の直接編集ができる入口にしない。

今回の範囲は、用途の確立から情報参照、変換、推論利用、用途別の結果受入、処理中dataの無効化までとする。Permission評価全体、Learning形成algorithm、Observerの検知algorithm、Action実行、全域消去完了、復元手順は、それぞれの既存契約を利用する隣接領域である。

## 3. 受渡しで保持する論理的な対応

### 3.1 要求の同一性と利用目的

利用元は、何の活動のために、誰の情報を、どの用途へ使う要求かを成立させる。同じCompanion IDやTask IDだけでは要求の同一性にならない。少なくとも、適用する範囲で次を対応付ける。

- consumerと用途、担当Companion、Task・委任との関係、目的やsteeringの前提。
- 元の入力・出来事・管理操作との関係。Client依存なら取得Client、入出力roundや観測候補との関係。
- 停止前とResume後、Host再起動前後、restore前のlive活動と復元後の活動を区別できる活動の継続関係。
- 期待する利用先。例えば返答、Learning変更の候補、routing、Permission解釈、Task判断は異なる利用である。

これらを全要求に同じ項目で付ける必要はない。通常のHost作業へactive Clientを必須にせず、Taskを持たない会話や共有観測に仮のTaskを作らない。必要な対応を失った結果は、到着先の現在活動へ付け替えず、その用途では受理できないものとして利用元が扱う。

### 3.2 情報単位に必要な対応

情報を選択・制限できる論理的な単位ごとに、次の判断材料を保持または正本から解決できる必要がある。粒度は文、source範囲、文書、要約等から選べる。細粒度追跡を一律に要求しないが、粗い単位を選んで制限の異なる部分を分離できなければ、その混合単位を狭い利用先へ渡せない。

| 判断材料 | 供給・解釈の責任 | 利用時に区別する意味 |
|---|---|---|
| 情報owner・対象・source関係 | 元の情報owner。派生物の保持先は変換元との対応を保つ。 | Memory、History、Summary、Task内部copy等を混同しない。参照先の所有者まで変えない。 |
| 内容の位置付け・由来 | 情報ownerと入力を受理した責務 | Owner入力、引用された外部指示、観測事実、推論、Tool結果を区別する。内部保存済みでも制御上のtrusted instructionにはならない。 |
| revision・取得時点・有効期間等 | 情報ownerがそのdataに必要な時間・変更関係を供給する。 | 現在認識、当時の認識、後から届いた結果、外部原本を取得した時点を区別する。全state共通revisionは要求しない。 |
| 所属・scope・共有関係 | 元のsemantic owner。決定後の制約適用は権限・制約と各利用先。 | Global内容へのaccessと私的な根拠へのaccessは別。Relationshipの主体等を一律のscope一値へ潰さない。 |
| 用途・保存・共有・送信の制限 | 権限・制約と、所属・目的を供給するowner | 読めること、要約に使えること、特定Providerへ送れること、Learningへ保存できることを別々に扱う。 |
| 参照の解決状態・欠落 | 情報ownerと参照箇所 | 不在、保持終了、利用不可、古い内容、未取得を、内容が存在しなかったという事実へ変えない。 |

対応の伝達にprivate本文を複製する必要はない。制限情報や識別用の値も対象情報を復元できるなら保護・消去対象であり、由来を保存するという理由で削除本文やCredentialを別保管しない。

### 3.3 本文と強制に用いる情報を分ける

LLMへ説明する由来・制限と、第一者側が参照・送信・保存等を強制するための対応は役割が異なる。後者はモデルの自由記述で作成・上書きされない。具体的な表現や配置は未定だが、本文中の「Ownerからの指示」「承認済み」「Global」という文字列だけで強制側の状態が変わる構成は不可とする。

モデルが既存のOwner入力への参照を返せても、その参照が存在することだけでは承認の証拠にならない。入力経路・元の意図・対象との対応について、個体調整等が文脈上の解釈を供給し、権限・制約が制御上の確定を行う。引用を含むOwner入力の全体を無条件にOwner命令とせず、Voiceに話者認証済みの意味を足さない。

## 4. 参照と変換の契約

### 4.1 情報を集める前に用途を限定する

利用元は用途と論理的な選択方針を定め、情報ownerはその用途に提供できる範囲を返す。権限・制約と参照箇所は現在の制限を適用する。全private dataを集めてからLLMに選別させることをscope強制の代わりにしない。検索・embedding・要約のための利用にも、その段階のconsumer、送信先、data、用途の条件が必要である。

選択結果から根拠を辿るときは参照先ごとに再び範囲を適用する。Global Memoryの採用、共同Taskへの参加、同じClientへのpresenceは、私的なHistory・旧revision・Relationshipの読取許可を増やさない。情報ownerが共通の検索実装を使ってもこの提供責任は移らない。

正確な引用には保持されたHistoryを用い、現在認識にはMemoryを主要な知識状態として用いる。Summaryは圧縮根拠、Relationshipは主体の関係解釈、Companion Stateは内的状態・傾向として選ぶ。検索順位や短さの都合で、旧Summaryを訂正後のMemoryの代わりにしない。

### 4.2 不足と省略を結果へ伝える

利用元は、用途成立に必要な情報や区別を指定できなければならない。これは固定の必須field一覧ではなく、例えば「逐語引用に原履歴が必要」「現在値の回答に旧認識を代用できない」という意味条件である。推論側の長さ調整だけで、この条件を緩めない。

任意の背景を省略できる場合は、利用元の方針内で縮小してよい。不可欠な区別を表現できない、必要sourceが失われた、許可範囲で取得できない場合は、該当用途の不足として戻す。空の検索結果や切り詰めを「該当事実なし」「承認条件なし」へ変換しない。不足の説明自体にも同じ利用範囲を適用し、他個体のprivate情報の存在・内容を不必要に漏らさない。

### 4.3 変換は権限・意味を昇格させない

要約、抽出、翻訳、検索用派生物、Provider向け圧縮は、元情報との依存と制限を引き継ぐ。複数入力を混ぜて分離を確認できない出力は、それらの入力に依存し得るものとして扱う。「モデルが使用していないと言った」「対象文字列が出力にない」だけでは依存を外せない。

実際に分離された入力範囲から出力を構成したと確認できる場合は、その範囲へ対応を限定できる。どの方法でも、LLMの自己申告だけでprivate情報を共有可能にしたり、外部指示をOwner意図へ変えたりしない。この条件は意味的同一情報や情報流の完全検出を新たに保証するものではなく、確認できない範囲を許可済みと推定しないための契約である。

通常のLearningのscope形成・Global化は引き続き認識・学習の意味判断であり、本書で禁止も代行もしない。共有対象の内容・必要背景をそのownerが選び、明示的な非共有等を守って成立させた現在の共有内容は、その内容自身の範囲で利用できる。ただし、単なるcontext圧縮をその判断の代わりにせず、Global化を私的な元根拠への遡及的な許可にしない。

変換によって次の区別を失ってはならない: 現在と過去、引用と指示、実行依頼と作用事実、成功と不明、情報の不在と利用不可。これらを保持できない表現はその用途に使わず、再選択・別表現・不足へ戻す。モデル出力が意味的に常に正しいという保証ではなく、owner側の採否と機械的な境界を省かないための条件である。

## 5. Provider適応と実利用

### 5.1 論理的選択と送信ごとの成立を分ける

推論は用途と選択方針を受け、実際のProvider能力・context長へ適応する。同じ方針とは同じbyte列や同じ情報量、同じ応答を要求する意味ではない。Provider別の独立した個体像を作らず、制約内で同じ選択方針を適用する。圧縮によって第4節の必須条件を満たせなくなる場合は、利用元に不足を返すか、許された方針の範囲で再選択する。

最初の送信、fallback、再送、埋込み・要約の補助推論に加え、継続的な送受信を伴う利用の各継続部分も、それぞれ実際の利用として次を満たす必要がある。

1. 現在の活動・用途に対応し、現在許される情報だけを扱う。
2. 解決したconsumer／Capabilityのassignmentと、実送信先・data・用途・取扱い・費用の同意が対応する。
3. 現在の認証用途、制限、該当する保留と利用量を満たす。Credential値は通常contentに入れない。
4. 送信する表現、参照するProvider側context、戻る結果が、元の要求と情報範囲へ対応する。

事前に解決した送信先は独立した設定正本でも包括的な送信許可でもない。Fallbackは承認済みの候補と順序に従い、変更先について条件を照合する。同意不足を本文の削減だけで黙って解消したことにせず、実際に残るdata・用途の同意成立を確認する。

費用の報告値・推定・不明・処理中利用は、元の用途と実際の利用先へ対応付ける。失敗・fallback・context再構築で利用量をゼロへ戻さず、並列要求が同じ残額を独立に使い切れる扱いをしない。予約・集計方式は本書で選ばない。

### 5.2 cache・session・Client経路

ene管理下のcache・embedding・検索結果・圧縮contextを再利用する場合も、内容だけでなく元の範囲・用途・現在性を確認できる必要がある。hitしたという理由でsource参照や制約確認を省かない。元のHistoryが通常保持で失われた場合と、targeted deletionで利用を除去すべき場合を区別する。前者で形成済みLearningを自動削除せず、後者でcacheを代替根拠にしない。

Provider sessionに過去の情報が残る場合、その情報も後続生成へ寄与し得る入力として扱う。現在使えない情報を含むsessionへの新規依頼は、現在のcontextを短く渡すだけでは成立しない。利用対象から除外できる経路へ切り替える等、現在条件を満たせなければそのsessionを再利用しない。Provider保有copyの外部保持までene内部消去の保証へ含めないことと、そのcopyをeneが再利用してよいことは別である。

Clientからの直接送信やprotocol Pluginにも同じ成立条件を適用する。全payloadのHost中継は要求しないが、Clientの古い設定copyや外部codeが独立に同意・現在性を決めてはならない。Hostの現在条件を確認できないClientは該当活動を継続せず、一時copyを第二の正本へしない。

認証先のerror・resultが登録済みCredentialを反射する経路にも、受入・変換・推論利用・送信・保存・提示・消去を含むすべての取扱いで非露出を維持する。送信前にpromptへ入れなかったことだけでは保護の成立にならない。説明やDebug captureのために秘密値を通常contentへ取り込まず、認証用途と非秘密の失敗情報を分ける。登録外の秘密は検知時の不要な保存・送信抑制を維持し、完全検出の保証は追加しない。

Permission解釈・消去対象の意味探索も例外ではない。その補助推論自身の利用条件を満たし、審査対象Actionの許可や実行を先行条件にしない。推論不可ならその意味判断の不足を返し、第一者の停止・拒否・管理・機械的検証を塞がない。

## 6. Observerの限定routing contextへの適用

Observerは今回の契約が必要になる最小の複合事例として詳細化する。観測全体や個体の自発性を一緒に設計するものではない。

### 6.1 原ownerからの提供

共有観測は、現在の対象Client・存在個体とrouting用途を対応付け、個体調整との協働を通じて必要な限定文脈を得る。Historyは個体調整、Memory等は認識・学習、Task contextは作業が提供範囲と意味を持つ。作業の情報は既存の個体調整–作業の協調で扱い、Observerが任意のTask storeを読む経路にしない。

提供した文脈は、対象Companion、元情報、用途、制限、選択時の前提を解決できる派生表現とする。保存された恒久的な「Observer用個体状態」や新scopeへ昇格させない。個体の話題やTaskが変わったときは、元ownerがその変更と提供済み文脈の対応を判定できる必要がある。更新頻度や生成方式は未定でも、変更を扱えない永久に有効な要約にはできない。

要約生成に推論を使う場合は、その生成用途自身のassignment・同意・費用を満たすとともに、元情報の利用制約も維持する。各CompanionのProviderによる生成を必須にせず、最終的なObserverへの送信許可と生成段階の許可も混同しない。

### 6.2 routingの利用範囲とdeliveryの分離

共有検知・関連付けはObserver専用assignmentで行う。Companion overrideや各個体の同意を選択・合成しない。限定private文脈を使う場合も、元情報の利用制約を維持したうえで、その情報・用途について専用assignmentの送信条件を満たす。いずれか一方の成立だけでは利用を成立させない。

この許可が成立させるのは、共有観測が候補を個体へ関連付ける判断である。共有観測が複数個体の文脈を扱えることから、その入力や生成した説明全文を各個体へ公開する許可は生じない。次を別の受渡しとして扱う。

| 受渡し | 成立する内容・判断 | 境界 |
|---|---|---|
| routingの候補結果 → 共有観測 | 元の観測候補と候補受取個体との対応。共有観測が現在の対象・用途へ照合して採否を決める。 | モデルが任意の個体・Clientを追加したり、候補本文から所属・制御を変更したりできない。 |
| event → 各個体調整 | その個体が利用可能な観測内容と必要な背景。由来Client・取得時点・候補との対応を維持する。 | 他個体のprivate routing文脈や、その文脈に依存する説明を同梱して共有しない。 |
| 個体の理解 → 学習・発話・Task等 | 個体が自身の用途と現在条件で理解・採否を決める。 | Observerの成功を個体側の推論成功・送信同意・Action許可にしない。 |

例えばA・Bの限定private文脈を用いてA向け候補を得た場合、候補の宛先対応はrouting用途の結果として共有観測が扱える。一方、「Bの私的な予定と比較してAを選んだ」という自由文をAのcontextへ渡してはならない。event本文を利用可能な元Capture範囲から構成する等、本文の提供範囲を独立に成立させる。混合生成文しかなく分離を確認できなければ、その文を個体へ渡さず、許された情報範囲で構成し直すか不足として扱う。モデルの「Bの情報は含めていない」という申告だけで通さない。

これはroutingで元文脈を利用する既決判断の具体化であり、routing自体を禁止するものでも情報流の完全な非干渉保証を追加するものでもない。宛先候補の採否と、開示する本文の制限を別責任として成立させる。

### 6.3 鮮度と観測制御

送信・delivery前には、対象Client、存在個体、観測制御、限定文脈の利用条件、消去等の保留との対応を確かめる。移動前のCaptureを移動先Clientのものに付け替えず、Stopped個体を候補受取のために起こさない。private文脈のscope変更・送信同意失効・消去は、生成済み要約や処理中結果にも適用する。

Pause／OFF等の時点で保留中候補を破棄するか、条件に応じて再評価するかの具体方針は残す。ただし、すでに個体が認識したExperienceは別lifecycleであり、観測OFFだけで消去しない。delivery後の個体Providerへの送信は別consumerの新たな利用として第5節へ戻す。

## 7. 現在性と用途別受入の状態遷移

### 7.1 組立ての完了は利用の承認ではない

次は各要求・利用・受入の論理的な段階である。一つの永続state machineや固定pipelineにはしない。再選択、分割、並列化、推論なしの利用を許すが、対応する境界を飛ばしてはならない。

| 段階・遷移 | 成立条件 | 変化・失敗時の責任 |
|---|---|---|
| 用途確立 → 参照・選択 | 利用元が対象活動・目的を成立させ、情報ownerと参照箇所が範囲を適用する。 | 不明な主体・目的をデフォルトの広いscopeへ置換しない。利用元へ不足を返す。 |
| 選択 → 利用表現の準備 | 元情報との対応、必須の区別、省略・不足、変換後の制限を保つ。 | 再選択・再構成またはその用途の不足。準備済みでも送信許可は未確定。 |
| 準備 → 個々の実利用 | 実利用先が現在の用途・data・活動・同意等を照合する。 | 関係する前提が変われば再評価。成立しない利用を保留・拒否する。 |
| 実利用 → 結果到着 | 推論が元要求・実利用先・入力範囲・利用量・失敗等との対応を返す。 | transport成功をsemanticな成功にせず、対応不能を現在の要求へ取り込まない。 |
| 結果到着 → 用途別の採否 | 該当ownerが現在の対象・制限・意味へ照合し、その用途だけを採用する。 | 記録、学習、提示、次の実行を別々に扱う。採用による他用途の自動許可はない。 |
| 処理中 → 無効化・利用終了 | 関係する停止・失効・消去・活動終了を反映し、遅延結果も識別する。 | 各保持・利用先が一時dataと遅延結果の扱いを引き受ける。必要な事実・未完了は本来のownerへ残す。 |

### 7.2 鮮度は用途に必要な前提との関係

参照時に正しかったことと、今の利用に適することを分ける。各利用箇所は、何に依存して利用可能と判断したかを対応付け、その関係する変更を利用時に扱う。必要な現在条件の変更を見落として利用してしまう確認方式は不可とする。具体的な競合制御、確認の配置・連携、変更検知方式は後続設計で選ぶ。

制約変更と利用開始が競合する場合は、対象の変更成立と当該利用の開始・受入の関係を説明できる必要がある。変更成立後の新規利用に旧判定を適用せず、すでに開始した利用には停止・遅延結果の契約を適用する。関係を確認できなければ、その新規利用を許可済みと推定しない。全domainの共通時刻順や、一つの排他的transactionを要求するものではない。

固定TTLだけではscope失効・Stop・消去を処理できない。一方、無関係なMemory更新を理由に全contextを無効化し、全操作を再承認する必要もない。意味上の鮮度は情報ownerと利用元、制約の現在性は権限・制約と実利用先が扱う。古い情報は過去の根拠として有効な場合があるが、現在値や現在の承認としては代用できない。

混在する複数ownerの情報について、共通の一時点snapshotは要求しない。ただし、用途成立に必要な対応が矛盾する場合、例えばsteering後の目的に旧委任範囲を組み合わせる場合は、その用途で採用せず再評価する。整合しているという判断もcontext専用ownerへ移さない。

### 7.3 結果の依存と採否

推論結果は少なくとも実際に入力した情報範囲に依存し得るものとして扱い、同じrequestへの回答というだけで新しい無制限dataにしない。結果が原情報を逐語で含まなくても、消去・非共有・保存禁止との対応を失わせない。用途ごとの受入は次のownerに戻る。

| 利用 | Authoritativeな受入 | 受入が意味しないこと |
|---|---|---|
| 会話・Ownerへの伝達 | 個体調整が現在の会話・未伝達事項へ対応付け、入出力・提示が現在帰属と実際の提示を扱う。 | 生成済み＝提示済み。移動前のroundへの自動出力。 |
| Taskの判断 | 作業が現在目的・steering・委任・状態に照合する。 | 旧目的への回答＝新目的達成。Cancelの解除。 |
| Learning・Summary等の形成 | 認識・学習が現在認識・根拠・scope・保存条件へ照合して採否を決める。 | 到着順が新しい＝根拠が新しい。Task contextの自動永続化。 |
| Permission・Rule等の解釈 | 権限・制約が元Owner意図と対象を照合して制御上の判断を確定する。 | モデルの「許可」＝制御更新。一度の許可＝将来Rule。 |
| 次のAction候補 | 利用元が候補を扱い、実行・拡張と権限・制約の現在の実利用条件へ渡す。 | contextが有効＝Action承認済み。生成されたTool call＝実作用済み。 |
| 作用・利用量等の必要事実 | 実行・拡張、推論、作業等の本来のownerが元の利用・Actionへ対応付ける。 | Cancel後は全事実を破棄。不明＝未実行。事実を記録できる＝後続実行可能。 |

Streaming・部分結果も、新たに保存・送信・提示・作用へ渡す部分ごとにその受入条件を満たす。全文到着を常に待つ指定はしないが、未検証の部分を先に露出して後で無効化することで制約を満たしたことにはしない。すでに起きた露出・作用は取り消せたと推定せず、把握できた事実を維持する。

## 8. 中断・再起動・消去への参加

### 8.1 中断と再構築

| 変化 | Context・結果の扱い |
|---|---|
| Memory訂正・scope変更 | 関係する情報を現在用途へ再照合する。認識・学習の訂正を古い形成結果で無条件に上書きしない。過去の出来事そのものを書き換えない。 |
| steering・Cancel・委任終了 | 旧目的・旧委任の結果を現在の遂行へ自動採用しない。必要な作用事実等は元のTask・Actionへ記録できるが、新しい作用開始とは分ける。 |
| Companion Stop・削除 | 新活動を開始しない。Resumeは停止前要求を現在要求にしない。削除後の必要なTask記録と、再作成してはならない個体Learningを分ける。 |
| Client移動・切断 | Client依存の入力・出力・Captureを現在帰属へ照合する。通常Host作業を一律停止せず、推論結果の生成と未伝達・実提示を区別する。 |
| 同意・Credential・device等の失効 | 依存する新規利用を禁止し、進行中はbest-effort停止。別Provider・Agent・Clientへ変えて迂回しない。すでに送信・作用したことを消した扱いにしない。 |
| 推論失敗・能力不足・費用不足 | 成功結果を捏造せず、利用元へ不足・失敗・不明を対応付きで返す。許されたfallbackにも第5節を適用し、既存の正本を保持する。 |

Host再起動後は、保持された正本から現在用途に必要なcontextを再構成する。保存した派生物を材料にできても、旧要求の実利用許可や旧実行をそのまま再開しない。途中TaskはOwnerの明示再開、Scheduleは将来回の通常判定、Running個体のpresenceは元Clientへの復旧という、それぞれの既存条件に従う。

Restoreでは旧live要求・結果と復元正本を区別する。復元後の自動処理保留、Ownerの確認後の一括有効化、現在条件を維持する。現在のHost Credential storeは保持されるが、旧context内の参照だけで認証成立や再実行を推定しない。旧live作用の必要説明も、復元されたTaskやLearningへ無条件に混ぜない。

再構築可能であることは、全文contextや内部推論を永続保存する要求ではない。継続して必要なTask状態・未伝達・作用不明・全域操作未完了等を本来のownerが保全し、一時bufferの消失は成功や完了の根拠にしない。

### 8.2 Targeted deletionの参加単位

Contextを保持・変換・送信・受入する各責務は、保全・消去に対して自分の参加範囲を説明できる必要がある。情報ownerだけを参加先にせず、処理中context、検索・圧縮派生物、ene管理下のcache、Client・拡張の一時copy、戻り得る結果を含める。

各保持・利用先は、対象sourceや対象情報との関係、処理中の利用、局所処理・検証、再保存防止、確認不能・未完了を対応付ける。正確な内部一覧の表現や参加先の探索方式は未定でも、sourceを消した後に依存関係も消失し、遅延結果を識別できなくなる実装は不可とする。必要な関係は本文を保持せず維持できるようにし、関係自体に対象情報が残る場合も消去へ参加させる。

消去開始から完了までに再到着・生成した対象情報も対象に含める。既知sourceへの依存追跡だけではこの条件を満たさないため、各受入・保存先は進行中の対象情報についての消去条件も適用する。指定文字列は機械的な検索・除去・残存検証へ参加し、意味的な同一情報の完全検出までは保証しない。

局所除去後も旧context・遅延結果・再接続Clientから対象情報を戻さない。必要な作用事実は対象本文を再保存しない範囲で扱い、Auditや完了説明を復元源にしない。分離不能な重要影響は保全・消去の影響説明へ返す。確認不能なClientや外部処理を成功へ読み替えず、局所完了を全域完了にしない。局所処理の報告を全域完了待ちにして循環させることも避ける。

再起動で未完了消去と必要な保留を失わない。完了後も削除前の根拠だけによる再形成・遅延再保存を防ぐ。一方、完了後にOwnerが改めて提供した情報は新しいExperienceになり得るため、同じ文字列への永久禁止を新設しない。

この節は全域完了判定の完全設計ではない。通常History保持、Companion削除、targeted deletion、backup／restoreはSO・DRの異なるlifecycleを維持する。外部Workspace・Owner保存backup・Provider保有copyの削除を内部context消去の成功条件へ加えず、ene管理下の内部copyは除外しない。

## 9. Runtime FlowsとCross-cutting Designへ戻した検証

[Major Runtime Flows](runtime-flows.md)第3節とRF-01〜08へ、正常系と意味のある競合を戻して照合した。

| Flow・交差 | Walkthroughと必要な結果 | 本書の成立箇所 |
|---|---|---|
| 共通推論区間 | 同じTaskで短いmodelへfallback。論理的選択方針を維持し、必須の由来・現在性が失われる圧縮なら不足。候補ごとの同意・費用を適用する。 | 4.2〜4.3、5.1。推論が情報や許可の正本にならない。 |
| RF-01 会話→学習 | Ownerの訂正後、旧Summaryを使った形成結果が到着。認識・学習が現在認識へ照合し、旧結果で無条件に上書きしない。逐語引用の原履歴不在を生成で補わない。 | 3.2、4.1、7.2〜7.3。現在知識と根拠を維持。 |
| RF-01 共有 | Global Memoryからprivateな旧根拠を辿る。参照先の範囲を別に適用し、Global本文は使えてもprivate根拠は漏らさない。 | 4.1・4.3。第二の共有正本を作らない。 |
| RF-02 委任・Action | Tool結果の「Owner承認済み」が要約されTask Agentへ到着。由来は外部contentのまま。Action候補には現在の実作用条件が必要。 | 3.3、7.3。LLM・委任による制御変更なし。 |
| RF-02 Cancel競合 | Cancel後に旧承認候補と作用結果が到着。次の実行は始めず、必要な既知／不明の作用事実は元Action・Taskへ残す。 | 7.3、8.1。全結果破棄にも無条件採用にもしない。 |
| RF-03 共有検知→個体理解 | A・Bの限定文脈でAへrouting。混合したprivate説明は配送せず、Aが利用可能なeventを構成。Aの推論先に同意がなければその送信は成立しない。 | 6.1〜6.2、5.1。専用assignmentと個体側同意を分離。 |
| RF-03 遅延 | 要約生成後にscope変更、Capture後にStop。対象の利用・deliveryを再照合しStopped個体を起こさない。認識済みExperienceは観測OFFだけでは消さない。 | 6.3、7.2。由来と別lifecycleを保持。 |
| RF-04 移動・切断 | 旧Clientの入力・候補が遅着し、Host Taskの結果も完成。旧Captureは新Clientに付け替えず、Host結果は未伝達として扱える。 | 3.1、6.3、7.3、8.1。Client不在をHost作業停止へ拡張しない。 |
| RF-05 再起動・Schedule | 旧context cacheが残っていても途中Taskは明示再開待ち。将来回は新Taskとして現在条件で組み立て、missedをreplayしない。 | 7.1〜7.2、8.1。presence復旧とTask再開を分離。 |
| RF-06 個体停止・削除 | 削除後に旧個体の学習候補と作用結果が到着。Learningを再作成せず、必要な残存Task記録の管理は可能。 | 7.3、8.1。記録保持を個体data削除の回避にしない。 |
| RF-07 消去競合 | 内部source除去後、推論結果と同じ対象情報の新入力が消去中に到着。両方を消去へ参加させ、局所削除のみで完了しない。 | 8.2。source追跡だけで対象範囲を狭めない。 |
| RF-07 消去後 | Provider sessionに旧情報が残る。現在入力を短くしただけで再利用せず、条件を満たす経路を使う。完了後のOwner再提供は旧結果と区別。 | 5.2、8.2。外部保持除外を再形成の許可にしない。 |
| RF-08 Restore | 復元後に旧live結果が到着。復元正本へ混ぜず、旧作用の説明と分離。Credentialは現在storeと照合し、自動処理保留を維持。 | 8.1。復元済み参照・同意から実行を復活させない。 |
| 全Flow: 補助推論の失敗 | Permission判断や消去探索のProviderが不通。未承認Actionを先に実行せず、不足を管理面へ返す。停止・拒否・機械的検証は継続可能。 | 5.2、7.1。failure時も境界を迂回しない。 |

Cross-cutting契約との照合結果は次のとおりである。

| 契約 | 詳細化によって維持する性質 |
|---|---|
| CC-01 | 入力の由来は生成本文と分離。Permission確定は既存owner、実作用強制は実利用先。既存の明確な依頼・Ruleで足りる場合の再確認を増やさない。 |
| CC-02 | 参照先・変換・補助推論・cache・session・Client経路へ同じ範囲を適用。Credentialは別経路。通常Learningのscope形成責任は維持。 |
| CC-03 | 同一主体と同一要求、過去の正しさと現在有効性を分離。用途別受入により単一valid判定へownerを集めない。 |
| CC-04 | Client依存だけを現在帰属に結び付け、Stop、Cancel、再起動、restore保留を区別。解除一つで他の禁止を消さない。 |
| CC-05 | 保持・利用先が派生物・遅延結果まで消去へ参加。原記録削除やcontext終了を全域完了にしない。 |
| CC-06 | 変換・再送・fallbackも利用として対応付け、処理中・不明を含む消費を切断しない。安全管理を推論成功待ちにしない。 |
| CC-07 | 省略・利用不可・不明を成功や事実不在へ変換しない。生成、採用、作用、記録、提示の確定度を分ける。 |

以上の範囲で、semantic owner、Host／Client、trust boundary、lifecycle、permission／consent semanticsを変更する必要は見つかっていない。新しい第二の正本・無所属の意味状態・LLMによる強制・失敗時専用の迂回を導入していない。

## 10. 後続設計への引渡しと残す自由度

後続のSubsystem／implementation designは、次を固定された契約として利用できる。

- Contextは用途限定の派生表現であり、元owner・要求・情報範囲・必要な前提への対応を失わない。全用途共通のcontext ownerは不要である。
- 参照、変換、実送信、結果の保存・提示・作用は別の利用境界である。事前の取得成功や推論成功から後段の権限を作らない。
- 強制に用いる由来・制限は生成本文で改変されず、分離を確認できない派生物は混合元の制限を免れない。
- Provider適応は利用元の論理的な選択方針を維持し、必須の意味が表現できなければ不足を返せる必要がある。
- Observerは限定private文脈を専用assignmentでroutingに使えるが、delivery本文と個体側推論の利用条件は別に成立させる。
- 現在性は関係する前提と用途で判断し、遅延結果の記録・semantic更新・次の実行・提示を個別のownerへ戻す。
- Contextの保持・利用先は、消去中の再到着も含む内部消去、再保存防止、未完了の保全へ参加する。

今回絞り込んだDesign Freedomは、由来を本文だけにする方式、包括的なcontext有効フラグだけで全利用を許す方式、変換後の制限を自己申告だけで外す方式、Observer混合出力の無条件配送、古いsessionによる現在制約の迂回である。いずれも上位契約を成立させないため採れない選択肢として明示した。

以下は意図的に残す。

- 検索・scoring・選択・要約・Learning形成algorithm、Prompt構造、情報の粒度、routing contextの生成model／Provider・更新頻度、省略の優先順位。第4〜6節の性質を満たす範囲で選ぶ。
- 参照・依存の表現、鮮度の確認・変更検知・失効通知、利用時競合の整合方法、cache再利用方式、session切替方式。確認不能を許可へ変換しないことだけを条件とする。
- 一時的な対応の保持期間・保存要否、永続化を必要とする未完了状態との接続、消去参加先の探索・検証・全域完了手順。通常のRaw非保存と必要な保全を維持する。
- Rust crate／module、struct／enum／trait、concrete function／API、IPC protocol、DB schema・SQL table、serialization、event bus／actor／queue、process／thread、locking／transaction、retry／timeout値、library／framework。これらを選ぶ工程には進んでいない。

Observer出力の配送境界とProvider sessionの再利用条件は、CC-02・03・05から導く詳細化であり、新scopeや外部消去保証ではない。後続でこれらの性質を成立させられないことが判明した場合は、黙って例外を設けずArchitecture Issueとして戻す。
