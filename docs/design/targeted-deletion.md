# Targeted Deletion — 全域成立と再出現防止の詳細設計

対象: Architecture Review #1／#2のFindingとOwner decisionsを統合済みのarchitectureに対する、Step 11 Critical Area Detailed Design。2026-09-08時点。

本書は、OwnerがPrivacyまたはSecurityのため特定情報そのものの内部消去を明示した場合に、ene内部のどこに保存・派生・処理中・再利用されていても対象を除去し、古いcopy・遅延結果・再接続・再起動・restore等によって復活させないためのlogical contractを詳細化する。後続のstate representation／persistence／concurrency／interface設計が安全に依存できる水準まで定め、具体的なmechanismは固定しない。

製品挙動のsource of truthは[要件Baseline](../requirements/README.md)、[製品定義](../requirements/product.md)、[要件](../requirements/requirements.md)とする。[受け入れ条件](../requirements/acceptance.md)も検証範囲へ含め、[参考資料](../requirements/references.md)は非規範として扱う。既存実装から製品挙動を補わない。

本書の「要求」「対象記述」「参加」「局所完了」「保留」「検証」「全域完了」「再保存防止」は論理的な関係であり、共通object、永続record、protocol、state machine、enumを指定しない。番号付きの段階は必要な前後関係を示し、すべてを直列実行する指定ではない。

## 1. 詳細化する問題と範囲選定

Targeted deletionを「各storeからdeleteする手順」へ落とすと、次の全域性が失われる。後続設計が誤りやすい点と、本書で定める契約は次のとおりである。

| 誤りやすい点 | 本書で定める契約 |
|---|---|
| canonical stateの削除で完了とし、派生物・処理中data・遅延結果を対象外にする。 | 追跡・識別すべき対象と関係、既知の派生・依存の追跡義務。 |
| 実行中Task／inference／Actionと消去の競合を、到着順や単一flagで解決する。 | 新規開始の禁止範囲、進行中の扱い、用途別受入での消去条件適用、確定度の保持。 |
| 局所削除後に旧context・cache・Client copyから戻ることを、新しいExperienceとして救済する。 | 消去区間の再到着・再生成の取込み、旧由来と新規提供の区別、再保存・再形成・再提示の防止。 |
| Client切断・Host再起動・restoreを跨ぐと未完了と再保存防止条件が失われる。 | Hostで保全すべきpersistent property。Clientを第二の正本にしない条件。backup／restoreとの交差。 |
| 一つのstoreやcoordinatorの成功、LLMの納得で全域完了にする。 | 局所完了と全域完了の分離、pending／unreachable／failed verificationの扱い、全域完了の成立条件。 |
| 作用記録・Audit・完了説明へ対象本文を残す。 | 保持すべき事実と保持してはいけない対象本文の区別。 |

今回の範囲は、消去要求の同一性、対象の追跡・識別、既存ownerの参加範囲、実行中活動との競合、再保存防止、再起動等を跨ぐ保持、全域完了、事実と本文の区別までとする。Contextの情報選択・Provider適応の一般契約は[Context Assembly](context-assembly.md)を、認可判断と実作用・確定度・不明の一般契約は[Action Execution](action-execution.md)を利用し、再定義しない。Client帰属の調停手順、backup／restoreの切替手順、Permission評価全体、Learning形成algorithmは、それぞれの既存契約を利用する隣接領域である。

Targeted deletionは、通常の忘却、訂正、失効、置換、統合、History／logの通常削除・retention、Companion deletion、設定Reset／全データResetとは異なる目的の操作である。同じ削除mechanismを使えても目的は変わらない。本書の契約はこの目的差を変えない。

## 3. 消去要求と対象の追跡・識別

### 3.1 消去要求の同一性

消去要求は、「削除」という一言ではなく、Privacy／Security目的の全域操作としての対応である。すべての消去要求について、適用する範囲で次の対応を保持または正本から解決できる必要がある。全要求に同じ項目・形式を付ける指定ではなく、必要な対応を失った要求は全域操作へ進めない。

- Ownerの明示的なPrivacy／Security目的と、通常の忘却・訂正・History整理・Companion削除ではないことの区別。「忘れてほしい」等だけでは本操作にしない。
- 対象記述（第3.2節）と、影響説明・必要な確認との対応。保存場所をOwnerへ選ばせない。
- 消去区間。開始から全域完了までの再到着・再生成を同じ対象に含めるための論理的な区間。共通時刻や単一transactionを要求しない。
- 完了後の新規提供との境界。完了後にOwnerが改めて提供した情報を新しいExperienceとして扱えるための対応（第6.2節）。
- 参加・検証・未完了の対応付け先。どのcoordinatorの調整に属する操作か。

消去要求の記録（何を対象にどう判断したか）と、各利用箇所で有効な消去条件（今その利用を禁じるか）は別の意味である。前者はAudit・説明・対応付けの材料であり、後者の正本ではない。保存された対象記述のcopy、委任時のcopy、復元された設定を、そのまま現在条件として再利用しない。開始前に現在の制約・保留と照合し、関係する前提の変更を見落として利用してしまう確認方式は不可とする。

### 3.2 対象記述の二層

対象記述は、機械的条件と意味的条件の二層からなる。両者は同じ消去要求に属するが、完了根拠としての役割が異なる。

- **機械的条件。** Ownerが指定した特定の文字列についての、内部全域での機械的な検索・除去・残存検証の条件である。全域完了の必須部分であり、LLMによる忘却、要約、重要度判断で代替しない。推論不可・費用不足を理由に追加推論待ちにしない。明確な管理操作・機械的検証をLLMの成功待ちにしない。
- **意味的条件。** 言い換えや意味的に同じ情報の探索補助の条件である。LLMを利用できるが、完全な検出を保証しない。文字列一致だけで意味的同一情報の完全検出を保証する必要はない。逆に、完全検出できないことを理由に既知の派生・依存関係の追跡を放棄しない。

意味的条件の不足・検出限界は、その不足を示してOwnerへ説明する。検出限界があること自体を、機械的条件の検証省略、既知依存の追跡省略、未確認範囲の完了扱いの理由にしない。意味的探索の補助推論にも、その推論自身の割当同意・認証用途・費用制限を適用する。審査対象Actionの許可・実行を、その審査のための推論の先行条件にしない。

対象記述の伝達・保持にprivate本文の複製を増やさない。由来を保存するという理由で削除本文やCredentialを別保管しない。制限情報や識別用の値も対象情報を復元できるなら保護・消去対象であり、完了記録・Audit・説明へ対象本文を戻さない（第9節）。

### 3.3 追跡すべき関係

対象が「どこにあるか」の一覧ではなく、「対象情報との関係」を追跡する。少なくとも次の関係を、本文を保持せず維持できる必要がある。具体的な表現・探索方式は未定でも、sourceを消した後に依存関係も消失し、遅延結果を識別できなくなる実装は不可とする。必要な関係は、関係自体に対象情報が残る場合も消去へ参加させる。

- 対象sourceや対象情報との関係。どのHistory・Summary・Memory・Skill・Task copy・index等が対象に由来・依存するか。複数入力を混ぜて分離を確認できない派生物は、それらの入力に依存し得るものとして扱う。「モデルが使用していないと言った」「対象文字列が出力にない」だけでは依存を外せない。
- 実際に分離された入力範囲から出力を構成したと確認できる場合は、その範囲へ対応を限定できる。どの方法でも、LLMの自己申告だけで依存を外さない。この条件は意味的同一情報の完全検出を新たに保証するものではなく、確認できない範囲を許可済みと推定しないための契約である。
- 処理中の利用との関係。どのcontext・推論・Task Agent・Tool結果が対象情報を利用中か、どの遅延結果が戻り得るか。
- 局所処理・検証との関係。どの参加先がどこまで除去・無効化・検証したか、どこが未確認か。
- 再保存防止との関係。どの受入・保存先が進行中の対象情報についての消去条件を適用しているか。

既知sourceへの依存追跡だけでは消去区間の再到着・再生成を扱えないため、各受入・保存先は進行中の対象情報についての消去条件も適用する（第6節）。指定文字列の機械的検索・除去・残存検証は、この依存追跡に追加する必須の検証であり、どちらか一方で他方を省略しない。

## 4. 参加範囲

### 4.1 参加の原則

各semantic ownerは、自分の保持・利用範囲についてTargeted deletionへ参加し、全域操作のcoordinatorはその成立を調整するという現在のarchitectureを維持する。通常ownerは正当な全域消去への参加を拒めず、coordinatorも任意の通常変更権を取得しない。すべてのSubsystemを新しい中央Persistence ownerへ従属させない。

参加責任には、対象state、元記録・根拠・revision・共有参照・派生物・内部copy、現在利用する処理・遅延結果の把握、必要な変更・保留、完了または未完了の報告が含まれる。探索・処理を共通実装へ委ねても参加ownerの意味責任は残る。各ownerは局所結果を全体完了前に返せるが、結果返却だけで必要な保留を解除しない。対象外の通常活動まで一律停止することは必須にせず、対象範囲の利用・再保存を確実に制限できることを成立条件にする。

以下は参加先の例示であり、固定チェックリストではない。**対象情報を復元できる内部state・過去根拠・派生物・一時data・処理中利用を持つ責務は、列挙の有無にかかわらず参加する。** 保存・利用先を増やす後続設計は、その参加責任も示す必要がある。

## 5. 実行中Task／inference／Actionとの競合

### 5.1 新規開始の禁止と進行中の扱い

権限・制約と各実行箇所は、消去条件が成立した対象範囲について、新しい利用・保存・送信・提示・作用の開始を禁じる。ここでいう消去条件は、包括的な単一flagや共通の有効値ではなく、消去要求・対象記述・消去区間との対応を各利用箇所が照合できる関係である。対象範囲の利用・再保存を確実に制限できることを成立条件にし、対象外の通常活動まで一律停止することを必須にしない。失効・停止・保留と同じく、新規開始の禁止と進行中処理のbest-effortな扱いを分ける。

- 削除前の情報を利用する実行中処理によって、削除済み情報を再保存しない。削除処理または残存検証が完了していない場合は、完了したと表示しない。
- 進行中の推論・Task Agent・Tool作用は、best-effortで停止または対象を含まない範囲へ縮小し、停止できなかった処理・すでに生じた外部作用・不明を保持して報告する。停止の受付・新規開始の禁止・状態参照を、外部processの終了や全Taskの正常完了待ちにしない。
- 停止経路の名で新しい未承認作用を始めない。別Agent・別Client・別Toolへの迂回で消去条件を回避しない。

Background・Scheduleの無人実行も同じ条件に従い、消去区間の到来を自動承認の理由にしない。Owner確認が必要なら実行せず判断待ちにする。

### 5.2 用途別受入での消去条件適用

遅延結果は用途ごとに受け入れ、各受入先が消去へ参加する。Context Assembly第7節とAction Execution第7節の用途別受入に、消去条件の照合を追加する。到着が遅いことだけで出来事を新しくせず、最新に届いた結果だけで現在値を決めない。

| 利用 | 消去条件の適用と許される受入 | 禁止する扱い |
|---|---|---|
| 会話・Ownerへの伝達 | 個体調整・入出力・提示が現在の消去状況へ照合し、対象情報を含まない範囲で提示する。 | 生成済み＝提示可能。旧roundへの自動出力。 |
| Taskの判断・steering反映 | 作業が現在目的・委任・消去状況へ照合する。旧目的への回答を新目的達成にしない。 | 遅延結果だから新しいExperienceとする。 |
| Learning・Summary等の形成 | 認識・学習が現在認識・根拠・scope・保存条件・消去状況へ照合して採否を決める。到着順が新しい＝根拠が新しいとしない。 | 古い根拠だけからの自動再形成。Task contextの自動永続化。 |
| Permission・Rule等の解釈 | 権限・制約が元Owner意図・対象・消去状況へ照合する。 | モデルの「許可」＝制御更新。消去条件の黙った解除。 |
| 次のAction候補・実作用 | 利用元・実行・拡張が現在の実利用条件・消去保留へ照合する。contextが有効＝Action承認済みとしない。 | 削除前の旧承認での新規開始。 |
| 作用・利用量等の必要事実 | 本来のownerが元の利用・Actionへ対応付ける。対象本文を再保存しない範囲で扱う。 | 事実を記録できる＝後続実行可能。不明＝未実行。 |

Cancel・失効がすべての事実報告を禁止するわけではなく、記録できたことが次の利用を許すわけでもない。消去条件も同じく、必要事実の返却・停止受付・機械的検証を同じ未承認活動の成功待ちにしない。

Streaming・部分結果も、新たに保存・送信・提示・作用へ渡す部分ごとに消去条件を満たす。全文到着を常に待つ指定はしないが、未検証の部分を先に露出して後で無効化することで制約を満たしたことにはしない。

### 5.3 確定度の保持

消去を理由に、必要なAction outcomeの確定度を成功・失敗・未実行へ変換しない。実行・拡張が把握した確認済み成功・確認済み失敗・不明の別と、その根拠・観測者を維持する。確定度を変える場合は、その事実ownerが新たに確認した根拠を用いる。

- 作用の説明と消去が重なる場合は、必要な事実の記録と対象情報の除去を両立させ、対象本文を作用記録という理由で残さない。
- 記録保存の失敗も、最後の正常記録だけから未実行を推定する理由にしない。
- Ownerへの最終報告・管理面の表示・要約が、未完了・不明を成功へ変えてはならない。確定度・費用の報告／推定／不明を保ち、推定・不明を確定値へ昇格させない。

Task記録は実行・拡張が把握した作用・確定度を参照・集約する。同じ作用の確定度を作業側で独立更新しない。Agentの成功申告を作用の証拠の代わりにしない。

### 5.4 LLMに依存しない強制境界

特定文字列の機械的な検索・削除・残存検証をLLMへ依存させない。LLMによる忘却、要約、重要度判断で代替しない。意味的な同一情報の特定にはLLMを利用できるが、完全な検出を保証しない。

Permission解釈・消去対象の意味探索のための推論にも、その推論自身の割当同意・認証用途・費用制限を適用する。推論不可ならその意味判断の不足を返し、第一者の停止・拒否・管理・機械的検証を塞がない。容量・Provider費用・LLM利用不能を理由に機械的な消去・検証を追加推論待ちにしない。

## 6. 再保存・再形成・再提示の防止

### 6.1 消去区間の再到着・再生成

消去開始から完了までに同じ対象情報が再到着・再生成した場合も同じ消去対象とする。削除途中の到着・生成を新しいExperienceとして救済する例外は設けない。具体的なtransaction、lock、snapshot方式は固定しない。

各受入・保存先は、既知sourceへの依存追跡に加え、進行中の対象情報についての消去条件を適用する。指定文字列は機械的な検索・除去・残存検証へ参加し、意味的な同一情報の完全検出までは保証しない。局所除去後も旧context・遅延結果・再接続Clientから対象情報を戻さない。

### 6.2 旧由来と新規提供の区別

完了後にOwnerが改めて提供した情報は新しいExperienceになり得る。同じ文字列への永久禁止を新設しない。旧由来の遅延結果・古い根拠からの再形成と、新規提供とを、文字列の一致ではなく由来・対応で区別する。

- 削除前の入力・出来事・管理操作との関係、Task・委任・推論要求との対応、Client依存なら取得Client・入出力roundや観測候補との関係、停止前とResume後・再起動前後・restore前後の活動の継続関係を、Context Assembly第3節の対応として保持する。
- 削除前の情報を利用した推論・Tool結果・Task Agent結果・cache・provider session・Client一時copy・restart前の処理・restore前後のlive処理から戻る対象情報は、完了後に到着しても旧由来として消去条件に従う。新着結果だから新しいExperienceとしない。
- 完了後にOwnerが改めて提供した情報は、削除前の根拠・revision・indexだけに依存しない新しいExperienceの根拠として扱える。到着が遅いことだけで出来事自体を新しくしないことと矛盾しない。必要な対応を失った結果は、到着先の現在活動へ付け替えず、その用途では受理できないものとして利用元が扱う。

古いHistory・Summary・revision・indexからのconsolidationでも、削除前の根拠だけを使って同じ情報をMemory、RelationshipまたはCompanion Stateとして自動再形成しない。background consolidation、過去revision、Summary全文、embedding送信からprivacyを迂回しない。

旧backupの明示restoreで情報が戻り得ることは、自動再形成禁止の迂回ではなく、要件に定めた別操作である（第7.4節）。復元成立と実行再有効化は別々に確認する。

### 6.3 cache・session・Client経路の再利用禁止

ene管理下のcache・embedding・検索結果・圧縮contextを再利用する場合も、内容だけでなく元の範囲・用途・現在性・消去状況を確認できる必要がある。hitしたという理由でsource参照や制約確認を省かない。元のHistoryが通常保持で失われた場合と、targeted deletionで利用を除去すべき場合を区別する。前者で形成済みLearningを自動削除せず、後者でcacheを代替根拠にしない。

Provider sessionに過去の情報が残る場合、その情報も後続生成へ寄与し得る入力として扱う。現在使えない情報を含むsessionへの新規依頼は、現在のcontextを短く渡すだけでは成立しない。利用対象から除外できる経路へ切り替える等、現在条件を満たせなければそのsessionを再利用しない。Provider保有copyの外部保持までene内部消去の保証へ含めないことと、そのcopyをeneが再利用してよいことは別である。

Clientからの直接送信やprotocol Pluginにも同じ成立条件を適用する。Hostの現在条件を確認できないClientは該当活動を継続せず、一時copyを第二の正本にしない。再接続しても古い表示copy・入力・Tool UI dataをHostへ戻して対象を再形成しない。

### 6.4 共有根拠の分離

一つのExperience Summaryやsourceが削除対象と無関係な情報の根拠にもなっている場合は、可能な範囲で対象情報だけを除去し、無関係な情報を不必要に削除しない。分離できない場合は削除の影響範囲をOwnerへ示す。

Global本文は使えてもprivate根拠は漏らさないこと、共有Summaryの保持が全内容の共通利用許可ではないことを維持する。共有されたcurrent内容から私的な旧revision・元History・Summary全文へaccessが広がらないようにし、参照・検索・処理中copyも新しい範囲に従わせる。分離不能な重要影響は保全・消去の影響説明へ返し、黙って対象を残さず、黙って無関係情報を消さない。

## 7. 再起動・再接続・restoreを跨ぐ保持

### 7.1 Hostで保全すべきpersistent property

具体的なjournal、transaction、WAL、lock、distributed protocolは選ばない。後続設計は、次の性質を満たす保持を選ぶ。

- 消去要求の目的・対象記述・影響・除外・必要な確認との対応。
- 各参加先の処理・検証結果と、未完了・失敗・未確認範囲。
- 対象範囲の利用・再保存を制限するための消去条件と、その有効区間・完了境界。
- 局所完了と全域完了の区別、pending／unreachable／failed verificationの区別。
- 再起動・再接続・restore後も、未完了の認識と必要な保留・再保存防止を維持すること。操作途中の再起動でも完了と誤認したり保留を黙って解除したりしない。
- 記録に削除対象の秘密・private本文を残すことは完了根拠の代わりにならない。

全域操作の未完了・再保存防止等、継続して守る必要のある状況はClientや一回の処理の寿命だけに置かず、Hostで保全する。一時bufferの消失は成功や完了の根拠にしない。継続して必要なTask状態・未伝達・作用不明・全域操作未完了等を本来のownerが保全する。

再構築可能であることは、全文contextや内部推論を永続保存する要求ではない。通常保存しないRaw Observation・Raw Voice・詳細Tool payload・内部推論を恒久保存する理由にしない。

### 7.2 Client切断・再接続

Client切断・再接続・Host再起動・restore等で未完了状態や再保存防止条件が失われないようにする。到達不能・確認不能を成功へ読み替えない。局所完了を全域完了にしない。

- 消去中にClientが切断した場合、接続・存在が確認不能を参加先へ結び付け、入出力・提示等が一時dataの消去状況を報告する。到達不能を消去成功に読み替えない。
- 切断したClientも古い一時dataを再接続時にHostへ戻して再形成しない。Clientに永続private cacheを置かない原則を維持する。
- どの到達性確認・無効化方法で完了根拠を得るかは後続設計へ残すが、必要な確認を省いて完了としない。
- Device失効・全データReset後に旧材料だけでHostの信頼を復活させないこと、復元されたdevice参照・許可を現在の接続・認証成立と照合することを維持する。

確認不能なClientや外部処理を成功へ読み替えず、局所処理の報告を全域完了待ちにして循環させることも避ける。参加ownerは局所の処理・検証結果を全体完了を待たずに返せる。保留・再保存防止は必要な期間維持し、保留解除と局所完了を同じ意味にしない。

### 7.3 Host再起動

Host再起動後は、保持された正本から現在用途に必要なcontextを再構成する。保存した派生物を材料にできても、旧要求の実利用許可や旧実行をそのまま再開しない。途中TaskはOwnerの明示再開、Scheduleは将来回の通常判定、Running個体のpresenceは元Clientへの復旧という、それぞれの既存条件に従う。

- 一部ownerの検証失敗・Host再起動では、保全・消去が未完了範囲と必要な保留をHostに保持する。参加ownerは全体完了前に局所結果を返せる一方、局所結果を返したことだけで再保存防止を解除しない。
- 再起動で未完了消去と必要な保留を失わない。完了後も削除前の根拠だけによる再形成・遅延再保存を防ぐ。
- Host shutdownでも必要な進捗・作用不明・未伝達・全域操作の未完了を保全し、外部作用がHostと同時に消えると推定しない。

通常再起動は、restoreのように全自動処理を一律の復元内容確認へ戻す操作ではない。未完了消去・復旧の保留があればそれを維持する。

### 7.4 backup・restoreとの交差

未完了消去・復旧とbackupが重なる場合、その制約を無視した正常・即実行可能なcopyを作らない。作成を待たせるか未完了を復旧可能に含めるかは自由度である。backupの運用設定・時機は保全・消去に残す。

- Full backupは各部のcopy出力だけで成功にせず、対象時点・参照・必要な履歴と未完了状況を復旧可能な対応で含める。単に各部のcopyが作れたことだけをfull backup成功にしない。
- Restoreは開始前からHostにある現在のCredential storeを維持し、それ以外の対象内部状態を対応backupから全置換して、成立後のHost正本を一つにする。旧live処理・Client copyを新正本へ混ぜず、用途別受入の契約を適用する。
- Restore前には、削除済み情報や旧Rule・同意・Scheduleが戻り得ることを説明する。Ownerが説明を受けて旧backupを明示restoreすると情報が戻り得ることは、自動再形成禁止の迂回ではなく別操作である。
- 切替前に開始した推論・Tool結果が切替後に届いても、旧live状態を復元後の正本へ混入させない。復元成立後もTask・Schedule・外部接続による自動処理は保留し、Ownerが内容確認後まとめて有効化できる。
- 復元されたassignment／consentだけで自動利用を開始しない。現在のCredential、現在の制約、既存のRestore後保留条件を満たす必要がある。

外部fileの現在内容・存在・access、外部作用、認証成功はbackup時点へ巻き戻らない。復元されたProvider／MCP等の参照を現在のCredential storeと照合し、利用可能なら現在のCredentialを利用、不足・無効なら再認証を要求する。

## 8. 完了の成立

### 8.1 局所と全域の区別

Targeted deletionの完了を、単一のstoreや一つのcoordinatorの成功だけで成立させない。一方で、すべてのSubsystemを新しい中央Persistence ownerへ従属させる設計にもしない。具体的なstate machineやenumは固定しないが、後続設計は少なくとも次の論理的な区別を保つ。

- **局所完了。** ある参加先が、自分の保持・利用範囲について、対象の除去または復元不能化、必要な保留・再保存防止の適用、範囲内の検証を終えたこと。局所結果の返却だけで必要な保留を解除しない。
- **pending／unreachable。** 消去中の接続変化・切断・再起動等により、ある範囲の処理・検証・確認が未確定であること。到達不能・確認不能を成功に読み替えない。
- **failed verification。** 機械的残存検証で対象文字列が残る、依存関係が解消できない、意味的対象範囲が確定できない等により、ある範囲の完了を確定できないこと。その不足を示す。
- **全域完了。** 保全・消去が各参加先の局所完了・検証・未完了を対応付け、内部全域の成立を確定したこと。局所完了の集合以上の条件（第8.2節）を必要とする。

参加ownerは局所の処理・検証結果を全体完了前に返せる。coordinatorはこの責任に依存し、全内部構造への無制限なaccessを要求しない。循環した承認・成功待ちをarchitecturalな前提にしない。

### 8.2 全域完了の条件

全域完了には、次の全体が必要である。意味的な探索の完全性と文字列検証を混同しない。

1. 対象範囲・重要な影響を説明し、必要な確認を経ている。無関係な共有情報は可能な範囲で分離し、分離不能な影響を説明している。
2. 対象情報を復元できる内部History、非会話活動記録・historical log／evidence、未伝達・処理中報告を含むSummary、Memoryと過去revision、Relationship、Companion Stateと保持済み根拠、Skill、Task・source copy、観測候補・routing用派生表現、index・embedding・cache、推論context、Audit／Debug等の該当情報、接続中Client・ene管理下の拡張一時dataを、第4節の参加原則に従って除去または復元不能にしている。Companion削除後の残存記録も除外しない。以下の列挙は例示であり、参加原則に属する範囲を列挙漏れで除外しない。
3. 開始から完了までに対象情報が再び内部へ到着・生成した場合も同じ消去対象として扱い、新しいExperienceとして除外しない。削除前の情報を使う処理、処理中context、遅延した推論・Tool結果からの再保存を防いでいる。古い根拠・revision・indexだけによる自動再形成も防いでいる。
4. 指定文字列は内部dataを機械的に検索・削除し、残存を検証している。LLMの要約や想起抑制で代用しない。言い換え・意味的同一情報の探索補助と、その完全検出を保証しない範囲を区別している。
5. 各参加先の未完了・失敗を集約しており、未確認の局所結果を全域完了にしていない。途中再起動でも未完了の認識と必要な保留を維持する。完了記録自体に削除内容を再保存していない。

完了の説明は参加先の根拠に基づき、LLMが納得したという要約で代用しない。各ownerは、自身の対象stateだけでなく、保持copy、revision、根拠・共有参照、派生物、処理中利用・遅延結果への関係を全域操作へ参加させる。認識・学習だけへの要求では、個体調整のHistory・非会話記録・未伝達、作業のTask context、推論のcontext・cache、Clientや拡張の一時dataを覆えない。

### 8.3 完了扱いにしてはいけない場合

- 局所削除だけが済み、別の保存先・context・Clientから戻る可能性が未処理の場合。
- 切断・再起動等によるpending／unreachableが残り、必要な確認を飛ばす場合。
- 機械的残存検証が失敗・未実施で、対象文字列の残存を否定できない場合。
- 消去区間の再到着・再生成の取込み、遅延結果からの再保存防止、古い根拠だけからの再形成防止のいずれかが未成立の場合。
- 意味的探索の検出限界を、既知依存の追跡省略や未確認範囲の完了扱いに読み替える場合。
- 外部Workspace・Owner保管backup・Provider保有copy等の外部copyの消去を内部完了の条件に含める場合。逆に、ene管理下の内部copyを外部扱いして除外する場合。
- 完了記録・監査・説明へ削除本文を戻すことで、完了根拠自体が復元源になる場合。

完了記録・Audit・Owner説明自体へ対象private本文を再保存しない。Auditの追記順は永久不変・削除不能を意味せず、通常保持管理とtargeted deletionへ参加する。

Targeted deletion、保持期間の短縮、手動削除は、対象をene内部から削除するが、すでに外部へ送信、export、backupされたcopyまで削除したと表示しない。内部copyの消去と外部で有効なCredentialの更新・失効は別操作として説明する。

## 9. 消去後も保持すべき事実と保持してはいけない対象本文の区別

由来・失敗・停止不能・未保存・次の安全な選択肢は、内部思考や詳細Promptを公開せず説明する。各発生元は、主要Action・Permission判断・外部作用・Provider割当・Credential参照・重要設定変更・消去・Reset・restore等について必要事実を供給する。保全・消去はAuditの追記順と保持を管理し、その順序を外部世界での発生順や現在の許可の正本へ昇格させない。

| 保持すべき事実 | 保持してはいけない対象本文 |
|---|---|
| 消去操作が行われたこと、目的、対象範囲の説明（本文を含まない記述）、影響・除外、必要な確認を経たこと。 | 削除したprivate本文、復元可能な言い換え、対象文字列そのもの。完了記録・Auditを復元源にしない。 |
| 各参加先の処理・検証・未完了・失敗の結果と、pending／unreachableの有無。全域完了か未完了かの別。 | 検証のために集めた対象本文の通常contextへの集約。強制・検証のために参照できることから、対象本文を通常model context・他個体・外部送信先へ渡す権限は生じない。 |
| 作用の確定度と根拠。確認済み成功・確認済み失敗・不明の別、既知の外部作用、停止不能・未保存。 | 作用記録・Task記録・Auditの中の対象本文。必要な事実の記録を対象本文保持の例外にしない。 |
| Taskの進捗・達成・未完了・次の判断。Task記録の存在と参照対応。 | Task context・source copy・結果の中の対象本文。 |
| 未伝達管理の報告状況。何をまだ伝える必要があるかという対応。 | 報告用要約・メモの中の対象本文。 |
| Permission判断・割当同意・費用等の制御条件の現在有効性。 | 判断記録・Audit文の中の対象本文、推論context内の許可文の悪用。 |
| 削除完了後の新規提供が新しいExperienceであることの対応。 | 削除前の根拠・revision・indexだけからの再形成。 |

説明に必要な事実を残し、本文の別保管庫を作らない。各供給元が不要な本文・秘密を出さず、記録側も別保管庫を作らない。Auditには通常、会話・file本文、秘密値、削除済みprivate内容を含めない。遅延・訂正された報告も元対象との対応を保つ。

容量管理目的の保持期間短縮や通常のHistory／log削除はtargeted deletionとは区別し、それだけを理由に形成済みMemory、Skill、Relationship、Companion StateやExperience Summaryへ削除をcascadeさせない。通常History／log整理の場合は、形成済みLearning・Summaryを残してsource参照不能を扱う。この目的差を、同じ削除mechanismの採用有無で変えない。

Companion削除は個体固有の現在状態・学習状態等の削除であり、過去に存在し会話・活動した記録を消す操作ではない。Targeted deletionが重なる対象本文は、Companion削除後の残存記録からも除去する。個体削除では必要なhistorical recordを残せるが、targeted deletionが重なる対象本文は残せない。

| 契約 | 詳細化によって維持する性質 |
|---|---|
| CC-01 | 消去の目的・対象と通常の意味変更・承認を区別する。生成contentから消去解除・権限新設をしない。既存依頼で足りる場合の再確認を増やさない。 |
| CC-02 | 参照・変換・共有・送信・保存・派生物・Client経路へ消去条件を適用する。Credentialは別経路で非露出を維持する。通常Learningのscope形成責任は維持する。 |
| CC-03 | 削除前の根拠と完了後の新規提供、過去の正しさと現在有効性を分離する。遅延結果の用途別受入により単一valid判定へownerを集めない。 |

State Ownership、Dependency Rulesとの照合では、semantic owner、Host／Client配置、trust／failure boundary、lifecycle、permission／consent semanticsを変更する必要は見つかっていない。新しい第二の正本・無所属の意味状態・LLMによる強制・失敗時専用の迂回・中央Persistence owner・万能Deletion Managerを導入していない。通常History保持、Companion削除、targeted deletion、backup／restoreはSO・DRの異なるlifecycleを維持する。

## 11. 後続設計への引渡しと残す自由度

後続のstate representation／persistence／concurrency／interface設計は、次を固定された契約として利用できる。

- 消去要求は目的・対象記述・消去区間・完了境界の対応であり、保存場所の指定ではない。機械的条件は必須・LLM非依存、意味的条件は補助・完全性なし、既知依存の追跡は免除されない。
- 各ownerは自分の保持・利用範囲について参加し、coordinatorは成立を調整する。対象を復元できる内部state・過去根拠・派生物・一時data・処理中利用は列挙の有無にかかわらず参加する。ene管理下の内部copyは除外せず、外部copyは成功条件に含めない。
- 新規利用は対象範囲で禁じ、進行中はbest-effortで扱い、遅延結果は用途別受入で消去条件へ照合する。確定度を消去理由で書き換えない。
- 消去区間の再到着・再生成は同じ対象とし、旧由来の遅延結果と完了後の新規提供は由来・対応で区別する。cache・session・Client copyの再利用・復帰で対象を戻さない。古い根拠だけからの自動再形成をしない。
- 未完了・保留・再保存防止はHostで保全し、再起動・再接続・restoreを跨ぐ。確認不能を成功にせず、局所完了を全域完了にしない。
- 全域完了は、内部全域の除去または復元不能化、機械的残存検証、区間内再到着の取込み、再保存・再形成防止、未完了集約の全体である。未確認・検証失敗を完了にしない。
- 保持すべき事実と保持してはいけない対象本文を区別し、完了記録・Auditを復元源にしない。

今回絞り込んだ禁止選択肢は、canonical削除だけでの完了、遅延結果の新Experience扱い、Client copyでのHost上書き・自動replay、古い根拠からの自動再形成、cache hitでの制約省略、Provider sessionの無条件再利用、確認不能の成功扱い、LLMの納得での完了、外部copy消去の内部完了条件化、内部copyの外部扱い除外、作用記録を理由とする本文保持、不明の成功・失敗・未実行への変換と自動replay、要約・復旧での確定度強化である。いずれも上位契約を成立させないため採れない。

以下は意図的に残すDesign Freedomである。

| 設計対象 | 固定済みのarchitecture property | 残すDesign Freedom |
|---|---|---|
| 対象記述・対応・追跡の表現 | 由来の偽装ができず、対象変更・失効・消去条件を各利用先で扱える。確認不能を許可・完了へ変換しない。 | 対象記述・由来・依存・区間・完了境界の具体表現、確認のまとめ方、対象探索・機械的検証の配置、識別・鮮度確認・競合制御。 |
| 除去・無効化・検証の実現 | 各ownerの意味責任を維持し、通常意味変更権をcoordinatorへ移さない。 | 除去・復元不能化の具体的方法、source・派生物・処理中利用の追跡方式、検証方法の実装、Client一時dataの無効化方式、到達性確認方式。 |
| 競合・受入の伝達 | 新規開始禁止、best-effort停止、遅延帰属、replay禁止。受付と完了を分ける。確定度を強めない。 | 停止伝達・切断検知・帰属調停・round区切り・queue／actor／event bus・lock／transaction・IPC・process配置・retry／timeout値。 |
| 再保存防止・再形成防止の保持 | 区間内取込み、旧由来と新規提供の区別、再利用禁止。文字列一致だけで完全検出を主張しない。 | 識別子・対応の保存単位・DB schema・repository・保持期間・永続化を必要とする未完了状態の範囲、consolidationの実装。 |
| 再起動・restoreの整合 | 未完了・保留の維持、旧live非混入、復元後保留、外部世界非巻戻しを守る。 | journal／WAL／transaction等の永続化機構、整合時点の作り方、backup形式・暗号化・復旧手順・対応version、部分失敗からの復旧。 |
| 記録・報告・監査 | 元事実の確定度・privacy・順序の意味と管理到達性を維持する。本文の別保管庫を作らない。 | audit format・保持期間・提示確認・要約粒度・UI layout・診断stack。 |
| 意味探索・費用 | 機械的条件をLLM待ちにせず、並列・処理中・不明を同じ上限へ反映する。 | 探索補助のalgorithm・Prompt・embedding・scoring・検索方式、費用予約・集計期間・推定、資源配分。 |

crate／module、Rust trait／type、concrete API・error型、middleware・interceptor・hook、event bus／queue／actor、IPC format、DB schema、transaction／lock、具体的Credential保護・sandbox・Plugin隔離、特定library・SDK・OS API、concrete deletion query、index implementation、queue／event bus、exact retry／timeout、specific storage engine、exact audit formatも固定しない。上表の対応関係から統一Context layer、Policy Engine、Manager、Service、Coordinatorの追加を導かない。既存の12責務、semantic owner、Host／Client配置とtrust boundaryの下で実現方法を選ぶ。

**新しいRequirement Ambiguity／Gapおよび上位architectureの変更を要するIssueは、今回の対象範囲では発見していない。** 対象探索・検証・到達性確認・backupとの交差等の具体mechanismが未決定であることはIssueにしない。必要な確認・Owner判断の省略、現在同意の拡張、未完了・不明の成功扱い、外部作用rollback・exactly-once実行の新保証はいずれも自由度に含めない。後続でこれらの性質を成立させられないことが判明した場合は、黙って例外を設けずArchitecture Issueとして戻す。

次は**Client帰属切替と活動の区切り**を詳細化するのが適切である。本書の消去条件・再保存防止・未完了保全を前提に、排他帰属と安全な区切り・再接続・復旧の全設計を独立して詰めることができる。

**Step 11は続行可能である。** 本書の範囲は後続設計への入力として利用できるが、Step 11全体の完了やStep 12への移行を宣言するものではない。
