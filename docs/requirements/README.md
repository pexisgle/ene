# Ene 要件定義

状態: **Baseline / 対話による初版確定**
最終確認: 2026-09-02

このディレクトリは、Ene が **どうあるべきか** を定義する正本です。Ene の現在の実装、crate 名、テスト、既存プロトコルは参考情報であり、実装されていることだけを理由に要件へ昇格させません。

## 文書の役割

- [製品定義](product.md) — 製品の目的、対象、価値、目標、非目標、対応範囲
- [ユースケース](use-cases.md) — ユーザーから観測できる代表的な利用シナリオ
- [機能要件](functional.md) — Ene が提供すべき能力と挙動
- [非機能要件](non-functional.md) — 性能、軽量性、信頼性、プライバシー、拡張性、対応環境など
- [不変条件](invariants.md) — 実装方法やProviderに関係なく破ってはならない条件
- [用語集](glossary.md) — この要件定義で使う用語の意味
- [決定記録](decisions.md) — 対話で確認した製品上・設計上の判断とその理由

## 読み方

本文の「なければならない」「できなければならない」は現行要件を表します。「目標とする」「望ましい」は、現時点で定量化していない品質目標または設計方針です。「将来」は現行版の必須範囲ではありません。「未確定」は、この文書だけでは実装判断を確定してはいけない項目です。

要件と設計判断は次のように分離します。

- 要件: ユーザー価値、外部から観測できる能力、守るべき制約
- 設計判断: 要件を満たすために現時点で採用する構成や優先順位
- 未確定事項: 今後の検証・対話・実測で決める項目

## 判断の優先順位

1. このディレクトリの明示的に `confirmed` された要件・決定を、あるべき挙動の正とする。
2. `invariants.md` の不変条件は、通常の機能・実装上の都合より優先する。
3. ソースコード、テスト、Cargo manifest、rustdoc は現在の挙動の証拠であり、要件の根拠ではない。
4. 過去の設計・計画資料やGit履歴は参考情報であり、現行要件ではない。採用する場合は、現行文書で改めて確認・記録する。
5. 未確定事項を、既存実装や旧資料から推測して埋めない。

## 現時点の大原則

- Ene の主役は、AITuber / AI companion としての人格的な体験である。
- 1人のユーザーが所有する1つの Host 上に、複数の独立した Companion が存在できる。
- 日常の主UIは、DesktopMate のような常駐デスクトップマスコットと音声中心の対話である。
- Agent Harness、Computer Use、Sub-agent、内部推論は Companion の能力として扱い、通常UIでは主役にしない。
- Memory、Skill、Emotion、Mood、Relationship、Interest は混同せず、それぞれの責務を保つ。
- LLM が意味を判断する一方、権限・Sandbox・発話排他・物理的制約などのHard Boundaryはシステムが強制する。
- 永続状態の正本は Host PC に置き、LLM等のProviderはローカル、クラウド、または混在で選択できる。
- 常駐するCoreは軽量性を最優先し、Main LLMはイベント駆動で起動する。

この文書群にない細部は、未確定である。実装を開始する際は、必要な追加判断を `decisions.md` に記録してから要件との整合を確認する。
