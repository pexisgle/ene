# 耐久性と回復(後継設計)

> **段階: 後継設計。v1.0 では実装しない**(D-4)。
> 実現する要件: **P-525**(重複効果なしのクラッシュ回復)、
> P-510 の耐久面、P-103(アボートの正しさ)。
> 参照: pi の「effect sandwich」「crash position table」「close = a controlled crash」。

v1.0 のクラッシュ耐性は、[agent-loop.md §12](agent-loop.md#12-中断の検出と報告p-515--d-5)
に閉じる——中断されたターン/ジョブを検出し、後始末をして、ユーザーに報告する
までで、**重複効果なしの再開は保証しない**(P-515、D-5)。

この文書が定義するのはその先である。v1.0 のスコープを維持したまま
ここまで作り込むと初版が出ない。一方 effect sandwich は後付けが難しく、
ログ形式とツール実行の境界に影響するので、設計としては捨てずに残す。
**v1.0 の実装は、ここに書かれた構造への移行を妨げない形を選ぶこと。**

以下は [storage-model.md](storage-model.md) の3ストアと
[operations.md](operations.md) の状態機械を前提とする。
どちらも同じく後継設計に属する。

## 1. 効果の境界(effects boundary)

効果(effect)とは、純粋計算でないすべて: コミット・プロバイダ要求・
ツール実行・フック・タイマー。うち**繰り返しに敏感な効果**
(繰り返すと外部から観測できるもの: ツール実行・送信・外部変更)は
特別扱いする。

アトミックトランザクションには内部の中間状態が無いので、
繰り返しに敏感な効果について、耐久位置は常に次の4つのいずれか。

## 2. effect sandwich

プロバイダ要求と実際のツール呼び出しは、**2つのコミットで挟む**:

```text
commit:  「X をこれから行う。出力は id R と U を使う」   ← 意図(intent)
         X を行う                                         ← 不確実な部分
commit:  出力 + usage + 次の状態                          ← セットルメント(settlement)
```

- **システム全体で唯一の不確実区間は「意図が耐久済みで、
  セットルメントが無い」区間**である。
- 意図コミットは、応答 entry と usage 行の id を**事前に発行**して書く
  ([storage-model.md §5](storage-model.md#5-恒等性uuidv7))。
  何も送出していない時点で id だけ確定する。
- セットルメントは、予約済みの id に出力・usage・次状態を1トランザクションで書く。
- フックは別のリプレイ規約に従う: 結果は**それを消費するトランザクション**で
  耐久化され、そのトランザクション前のクラッシュはフックを再実行し得る。
  冪等なフックはこの再実行を非目標として受け入れる。
  プロバイダ/ツールの意図は、リプレイポリシーが依存する場所で
  その不確実性を明示する。

## 3. 回復ポリシー

回復はジャーナルの再生ではなく、**`op.state` レジスタを読んで switch** する。
不確実区間(意図あり・セットルメントなし)に対する3つのポリシー:

| 復元された状態 | ポリシー |
|---|---|
| `assistant{effect_pending}` | **捕獲された**再試行ポリシーが許す場合のみ、番号を増やした試行を開始。許さない場合は、予約済みの応答 id に**合成エラー**を耐久化する。キャンセルが耐久済みなら、その id に合成 `aborted` を書き、再試行しない |
| `tools{effect_pending}` | 永続化された `op.tool_args` の引数は、**保存時の宣言と現在の宣言の両方**が `replay: safe` と言う場合のみ再実行。それ以外は予約済みの結果 id に合成 `interrupted` エラーを追記 |
| `deferred` | 待ち種別は `ask_user` / `approval` / `sidecar_health`([operations.md §2](operations.md#2-opstate--プログラムカウンタ))。`running` なら回答の `wake`(ask-user)または承認応答を待つ。新しい操作は起こさない。`cancel_requested` なら既存の予約 id に合成 `aborted` をセットルメント。上限なし |

### クラッシュ位置の全表

| クラッシュ位置 | 耐久されているもの | 回復 |
|---|---|---|
| 意図コミットの前 | 前の状態 | 何も起きなかったように効果を計画 |
| 意図の後、送出の前 | `effect_pending`。効果は未実行か判別不能 | 上のポリシー |
| 効果の途中/後、セットルメントの前 | `effect_pending`。結果は不明 | 同上 |
| セットルメントの後 | 出力 + usage + 次の状態 | 継続。**再セットルメントしない** |
| キュー適用コミットの前/後 | 項目は完全に pending / entry 存在でレジスタ消滅 | 後で適用 / 二度と適用しない |
| 構造変更の最終コミットの前 | 元の leaf は無傷、生成物は未コミット | 現在の状態とポリシーで再計算 |
| 構造変更の最終コミットの後 | 移動 + 要約 entry + usage + 終端掃除 | 完了 |
| 最初のアボートコミットの後 | キャンセルと drained id が耐久。drained ペイロードはレジスタに残る | 新しい通常効果を開始しない。整合のみ |
| 終端コミットの後 | op レジスタは削除済み、`lane.last_result` 書き込み済み | レーンはアイドル |

- **予約 id の排他性**(レジスタに居るか entry に居るか、
  [storage-model.md §3.3](storage-model.md#33-レジスタと-entry-の排他性))が
  「二度と適用しない」を保証する。
- 合成セットルメント(合成エラー・合成 `aborted`・合成 `interrupted`)は
  常に**予約済み id** に書く。特別ケースは作らない。

## 4. 復元(restore)

起動時の復元は、**分岐の走査も設定の逆参照もせずに**完了する。

1. 全レーンの `lane.state` を読む。`current_op_id` が null ならアイドル。
2. 操作があるレーンは `op.state` を読み、
   [operations.md §3](operations.md#3-状態の有効性ロード時検証) の検証を通す。
3. 状態に応じた次の動作を決める(§3 の表)。
4. `generation.context` は inline スナップショットなので、
   設定解決なしで「何が足りないか」を報告できる。

- 復元結果は**ライフサイクルイベント**で報告(「前回の作業を再開します」)。
  対話レーンは次のユーザー発話で、job レーンは自動再開。
- 復元を初期接頭辞から2回呼ぶテストは**不十分**。
  すべての回復接頭辞ごとに「close → reopen → resume → 中断なし回復との比較」
  を行う([invariants.md §3](invariants.md#3-テスト階層))。

## 5. 外部終端

終端トランザクションは、生きている駆動の**外側**からコミットされ得る
(別プロセスでの修復・管理ツール)。その場合:

- 駆動は、条件付きコミットまたは再ロードで自分の操作レジスタが
  **消えている**のを検出する。
- 検出したら**何も書かずに停止**し、`lane.last_result` から結果を解決する。
- 操作ごとに終端トランザクションは最大1回なので
  ([operations.md §6](operations.md#6-終端トランザクション))、
  二重終端は起きない。

## 6. アボート

アボートはフェーズではなく **control**([operations.md §2](operations.md#2-opstate--プログラムカウンタ))。

- **最初の `abort()`**: 1コミットで `control = cancel_requested` を書き、
  `requested_at` を記録し、drain した wake/inject の id を
  `control.drained` に移す。`phase` は触らない。drained 項目の
  `pending.entry` レジスタは**削除しない**(報告と再開が使う)。
  コミット後にシグナルを引き、未解放のゲート付き効果をキャンセル。
  呼び出しは**マーカーが耐久化した時点**で解決する。整合はバックグラウンド。
- **2回目以降**: 何も追記せずシグナルも出さず、同じ drained ペイロードを返す。
  終端後は `NoActiveOperation`。
- **キャンセル後も許可**: 既に意図された効果のセットルメント・
  usage 書き込み・受理済み遅延書き込みの適用・設定変更のコミット・
  キャンセルの完遂。
- **禁止**: 新しいプロバイダ要求・ツール・判断フック・再試行の開始。
- **アボートの正規化**: プロバイダ実装は、与えられたシグナルが
  引かれたときに限って `stop_reason: aborted` を出す。シグナルの所有は
  ハーネスが独占する。`abort()` はシグナルを引く**前**に control を
  コミットするので、確定した `aborted` 応答には必ずキャンセルが
  先に耐久化されている。
- タイムアウト・輸送失敗・不正ストリーム・プロバイダ側の拒否は
  すべて `error` でセットルメントし、通常の再試行経路を辿る。
  **ユーザーのアボートは再試行すべきでなく、一時的失敗は再試行すべき**
  なので、これが正しい。
- `aborted` 応答なのに `control.status == running` は到達不能であり、
  存在すればセッションは破損([invariants.md §1](invariants.md#1-不変条件カタログ) の I-19)。
- **アボート固有のアシスタントクロージャは存在しない**。ハーネスは
  「区切りを作るためだけ」に要求を始めたり応答を追記したりしない。
  ステップ間・ツール中・保留中のアボートは、アボート固有の
  アシスタントイベントを一切生まなくてよい。
- **出力ごとの整合**: planned のツール呼び出しは aborted エラー結果。
  復元された開始済み呼び出しは `interrupted`。ライブの開始済み呼び出しは
  最終化済みか生の結果を保持。アシスタントのセットルメントは
  キャンセル後、予約済みの応答 id に `aborted` で保存され、
  キャンセル済み checkpoint に移る。
- **音声割り込み(バグイン)** はこのアボート機構を使う:
  `interrupt` → `abort()` → control コミット → シグナル(TTS 停止・
  要求破棄)→ 新発話の受理([agent-loop.md §10](agent-loop.md#10-キャンセルと音声割り込みp-103))。

## 7. close — 制御されたクラッシュ

アプリの正常終了は、**クラッシュと同じ回復経路が使える形**で閉じる。

1. 新規の受理を止める(`LaneBusy` を返す)。
2. 実行中の効果にアボートではなく **drain** を要求
   ([plugins/ipc.md §3.1](../plugins/ipc.md#31-制御)): 進行中を片付けて
   セットルメントさせる。
3. drain の猶予([platform/process-model.md §8](../platform/process-model.md) の
   `plugins.shutdown_grace_ms`)を超えたら、状態を `effect_pending` のまま
   残して閉じる(**次回起動の回復に委ねる**)。
4. 保留中の手動操作(承認待ち等)は、実行せず拒否して閉じる。
   耐久状態はコミット済み接頭辞のまま。
- close は「制御されたクラッシュ」なので、close の前後で
  回復の正しさが変わらないことが受入条件
  ([invariants.md §3](invariants.md#3-テスト階層) の close 系の競合)。

## 8. 故障の分類(faults)

| fault | 意味 | ハーネスの応答 |
|---|---|---|
| `torn_transaction` | ストレージ層が all-or-none を破った | 即座に致命的エラー。ロード拒否 |
| `register_entry_overlap` | 予約 id がレジスタと entry の両方に居る | ロード拒否(排他性違反) |
| `orphaned_compaction_lock` | `compaction/start` に対応する `end` がない | 孤立ロックとして検出し、そのロックを無効化してから再開 |
| `missing_parent` | 親 entry が無い子 entry | ロード拒否(破損) |
| `aborted_with_running_control` | §6 の到達不能状態 | ロード拒否(破損) |
| `stale_effect_pending` | 意図が古く、再試行上限を超過 | 合成エラーで確定し、ターンを `failed` で終える |

- 破損系の fault は**決して自動修復しない**。ユーザーに
  バックアップからの復元を提案する([platform/process-model.md §5](../platform/process-model.md#5-バックアップと復元p-709))。
  自動修復は破損を隠蔽する。

## 9. 具体例 — ツール実行中のクラッシュ

抽象規則の運用を1つの筋で示す。ユーザーが job レーンに
「古いマイグレーションファイルを消して、テストを走らせて」と頼む。
モデルはツール呼び出し2件(`fs.delete` + `exec`)を返す。

ハーネスはバッチ計画をコミットし、続いて
「呼び出し0を実行する。引数はこれで、このツールは再実行不能(`replay: never`)」
とコミットする。ツールがファイルを削除し始めた瞬間、プロセスが死ぬ。

```text
TX[ entry n2 (assistant, 2 calls), usage u1, lane.leaf = n2,
    op.state/O = tools{ 結果 id n3, n4 を予約済み } ]
TX[ op.tool_args/O:s1:0, op.state/O = call 0 { effect_pending, replay: never } ]
… ツールがファイルを削除中 … ← クラッシュ
```

再起動時、ハーネスはレジスタを**1つ**読み、
`calls[0] = { effect_pending, replay: never }` を見る。
削除を再実行**しない**。効果の開始前に予約しておいた結果 id に
**合成エラー結果**を追記し、呼び出しを完了扱いにして、
呼び出し1(`exec`)へ進む:

```text
TX[ entry n3 (合成 "interrupted" 結果), lane.leaf = n3,
    op.state/O = call 0 completed ]
```

会話は整合を保つ——すべてのツール呼び出しに結果があり——
しかも**何も2回実行されていない**。

対照: ツールが `replay: safe`(読み取り・クエリ)を宣言していれば、
ハーネスは永続化された引数で**再実行**する(§3 の `tools{effect_pending}`
ポリシー)。どちらの分岐もレジスタの読み取りだけで決まり、
分岐走査も設定逆参照もない(§4)。
