# プロダクトビジョン

> 実装する前に、このアプリが「何であるか」を定義する文書。
> 機能目録は [features.md](features.md)、完成の定義は [done.md](done.md)。
> 用語の厳密な定義は [用語集](#用語集)にあり、以降の全設計文書はこの用語に従う。

## 1. 位置づけ

Ene は**ローカルファーストのパーソナル AI コンパニオン**である。

「エージェントハーネス」(LLM を道具として使って仕事をさせる枠組み)と
「コンパニオン」(人格・感情・記憶・身体を持ち、ユーザーと一緒に時間を過ごす存在)
の両立を設計の中核に置く。既存の参照実装は片方しか持たない:

| 系譜 | 代表 | 持つもの | 持たないもの |
|---|---|---|---|
| エージェントハーネス | [opencode](https://github.com/anomalyco/opencode)、[DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) | セッションランタイム、ツール実行、コンテキスト管理、サンドボックス | 感情、身体、能動発話、関係性 |
| 耐久ハーネス | [pi](https://github.com/earendil-works/pi) | 3ストア、effect sandwich、操作状態機械、レーンコマンド面、クラッシュ回復 | コンパニオン、承認/サンドボックス(既定ではユーザー権限で走る) |
| AI コンパニオン | [AIRI](https://github.com/moeru-ai/airi)、[Open-LLM-VTuber](https://github.com/Open-LLM-VTuber/Open-LLM-VTuber) | アバター、音声対話、感情表現、能動発話 | 仕事の遂行能力、セッションランタイム、安全なツール実行 |

Ene の設計上の立場は次の通り。

1. **コーディング特化ではない。** コーディング(fs/exec/git)はツールの1種に過ぎない。
   主眼は**非コーディングタスク**(調べ物、文書・表の作成、スケジュール調整、
   リマインド、生活支援)と**「一緒に過ごす」存在感**にある。
   これは Claude Cowork や ChatGPT Work のような「裏で動くエージェント」の能力を、
   コーディングだけでなく日常全般に広げたものに相当する。
2. **コンパニオンが主体であり、2層で1体である。**
   ユーザー入力(desktop/web の**音声もテキストチャットも**)は、必ず表層の
   **soul**(AIRI / Open-LLM-VTuber に似た実装)が受ける。soul は、計画立案を
   要さない簡単な作業なら自分で片付け、**複雑な作業のときだけ**裏層の
   **ハーネス**(opencode v2 / DeepSeek Harness に似た実装)へ託す(D-1)。
   両層は [Codex](https://github.com/openai/codex) の multi-agent v2 のように
   相互にメッセージを送り、進捗を確認し合う。
   ユーザーが見るのは機構ではなく、**1体のコンパニオン**である。
3. **複数体。** コンパニオンは多数存在し、同時に表示・会話できる(D-6)。
   各自が独立した人格を持つ。記憶も既定ではコンパニオンごとに分かれるが、
   ユーザーに関する事実と、抽出器が重要と判断した事項は**共有プール**に入り、
   全コンパニオンが自分の知識として参照する(D-7)。
   「あなたの名前」を人格ごとに覚え直させるのは不自然であり、
   一方で体験や関係性まで共有すると別人格である意味が消えるための線引きである。

## 2. 利用者像

- **主利用者**: 1人の個人ユーザー。自分の PC にインストールして使う(ローカルファースト)。
  マルチユーザー・チーム利用は非目標([done.md の非目標](done.md#非目標))。
- **使い方**:
  - デスクトップの stage にコンパニオンを表示し、音声とテキストで会話する。
  - 「旅行のしおりを作って」「この PDF を要約して」「明日の午後3時に会議の準備を
    思い出させて」のような非コーディングの仕事を依頼し、裏で進めてもらう。
  - 何も依頼しなくても、コンパニオンは能動的に話しかけたり、静かに寄り添ったりする。
- **スキルレベルを問わない。** CLI は開発・デバッグ用途であり、一般ユーザーは
  desktop(stage)と Web のみを使う想定で設計する。

## 3. 設計原則

以降の全設計文書で判断が割れたとき、この順で優先する。

1. **軽量であること。** 純 Rust カーネル。デスクトップはネイティブ描画のみで、
   WebView を含む Web 技術を使わない(D-21)。ツールはアウトプロセスで走るが、
   IPC はバルク転送をフレーム外へ出す設計で、軽量ツールも常用に耐える速度を出す。
   ハーネス機能(記憶想起・委譲など)はホスト内で走り、プロセス境界を越えない(D-10)。
2. **ローカルファースト。** 会話ログ・メモリ・設定はユーザーのデバイスに置く。
   クラウド LLM は「推奨される既定」だが、すべての LLM 呼び出しで
   ローカルモデルに切り替え可能であり、ローカル構成ではネットなしで全機能が動く。
   逆にすべての構成をクラウドLLMで動作させることも可能。
3. **内部複雑さは表層に出さない。ただし検証は可能にする。** 表層/裏層・層間
   メッセージ・サブエージェント・コンパクション・メモリ抽出などの機構は、
   stage とチャットの視界には出さない(作業中の1行表示までは可)。
   一方、詳細画面ではこれらを表示できる(D-11)。前者は既定値の問題であって、
   「決して見せない」という不変条件ではない。
   参照: AIRI / Open-LLM-VTuber は「魂」だけが表に出て、機構は舞台裏にある。
4. **構成可能性。** プロファイル/バンドル/パッチの積み重ねで、起動する機能集合を
   構成できる(DeepSeek Harness の Cordis 構成に倣う)。行の足し引きはホスト文脈の
   時空間合成で回収・再評価され、デーモンごと再起動しない(D-32)。
   ただしユーザーが触るのは粗いプリセットであり、詳細なパッチは
   開発者・高度ユーザー向けの機構である。
5. **安全の既定。** ツールプラグインは原則としてファイル・ネットワーク・資格情報に
   直接アクセスできず、Broker 仲介と承認ポリシーを通る。自動承認は「確認の手間」を
   省くだけで、検証(ハッシュ・サンドボックス)を無効化しない。
6. **会話ログの追記性による信頼性。** セッションで起きたことはすべて
   追記専用のログに記録され、UI・履歴・fork・リプレイはログから投影される
   ([core/session-log.md](../core/session-log.md))。「モデルに見えるものは必ず
   ログから再構成できる」は最上位の不変条件である。
   イベントソーシングの適用範囲は**会話ログに限る**。記憶・スケジュール・
   成果物・設定は通常のテーブル構造で持つ(D-9)。
7. **後方互換性の不在。** このアプリは未リリースであり、外部消費者はいない。
   設定・IPC・永続形式・CLI 面について互換性維持のための妥協はしない。
   きれいな設計を優先する。
8. **将来の配布可能性を塞がない。** プラグインとキャラクターのコミュニティ形成を
   目標に置く。ただし時期は将来であり、署名の厳格さもマーケットプレイスも
   v1.0 の要件ではない。v1.0 に課すのは「大規模な改修なしにそこへ到達できる
   設計にしておくこと」だけである(D-26)。

## 4. 参照系譜からの採用方針

「何を借り、何を借りないか」を固定する。各採用点は対応設計文書で具体化する。

### opencode v2 から

- **採用**: System Context と Session History の分離、Context Epoch(プロバイダ
  キャッシュ基準点)の概念、巨大ツール出力の spill、HTTP API+生成 SDK+
  Embedded/Remote 二重モード → [core/context-assembly.md](../core/context-assembly.md)、
  [platform/server-api.md](../platform/server-api.md)。
  **裏層ハーネス**の実装性格(セッションランタイム・ツール実行・コンテキスト管理)。
- **不採用**: コーディング特化の前提(worktree・patch・git 中心のツール面)。
  ツールは非コーディングを含めた対等な capability として設計する。
  ユーザー入力がハーネスに直接入る構成も採用しない(入口は表層 soul)。

### DeepSeek Harness から

- **採用**: セッションログのイベントソーシングと `model-visible = logged` 不変条件
  (適用は会話ログに限る — D-9)、
  turn/step ループ、ToolDefinition(正規出力宣言+モデル非公開フィールドの分離)、
  waterfall/emit の2モードイベント、capability seam の3役割、guard・plan・goal・
  interaction plane、プロファイル/バンドル/パッチ構成 →
  [core/](../core/README.md)、[tools/](../tools/README.md)、[plugins/](../plugins/README.md)
- **不採用**: Cordis(TypeScript 前提の in-process ローダ)そのもの。
  Web GUI を唯一のホストとする構成も採用しない(Ene のホストはコアデーモン)。
- **採用する抽象**: 時空間合成(D-32)。ホスト文脈への登録は巻き戻し可能な
  effect、行間の依存は `provides`/`requires` の反応的解決、設定変更は
  ファイバー単位の reconcile。実現は
  [plugins/composition.md](../plugins/composition.md)。
  アウトプロセス隔離(D-10)は保ち、プラグイン同士の直接呼び出しはしない。

### Codex multi-agent v2 から

- **採用**: 親と子が同期 await せず、型付きエンベロープで相互にメッセージを
  送る通信。`NEW_TASK`(ターンを起こす委託/追加指示)、`MESSAGE`(ターンを
  起こさずキューする共有)、`FINAL_ANSWER`(終端報告)の3種を層間プロトコルの
  骨格にする → [core/delegation.md](../core/delegation.md)。
  両層が互いの進捗を確認でき、あわせて**1つのエージェント経験**になる点。
- **不採用**: ユーザーがサブエージェントを直接観察・操作する IDE 向け UX。
  暗号化ペイロードやオペレータ監査 UI。Ene では層間メッセージはセッション
  ログに通常の事実として残る。表層UIには出ない。詳細画面では出せる(D-11)。
  Codex の `question` 面は層間の `question`/`answer` として拡張する
  (Codex 本体の第一級エンベロープではない)。

### pi から

- **v1.0 で採用**: レーンコマンド面と結果/エラーモデル(`resume` と
  `lane.last_result` 照合は後継)、不変条件と競合カタログと
  テスト階層、スパンにコンテンツを載せない → [core/lane-api.md](../core/lane-api.md)、
  [core/invariants.md](../core/invariants.md)、
  [core/observability.md](../core/observability.md)。
- **後継設計として保存(v1.0 では実装しない)**: 「three stores, one invariant」
  (entries / registers / usage)、OperationState をレーンのプログラムカウンタに
  する、effect sandwich、close = 制御されたクラッシュ
  → [core/storage-model.md](../core/storage-model.md)、
  [core/operations.md](../core/operations.md)、
  [core/durability.md](../core/durability.md)。
  v1.0 のスコープを維持したままここまで作り込むと初版が出ない。一方
  effect sandwich は後付けが難しいので、設計としては捨てずに残す(D-4)。
  v1.0 の最低ラインは「中断されたターン/ジョブを検出し、後始末をして、
  ユーザーに中断を報告する」であり、未消化の inbox はログから見せて
  実行は再開しない。重複効果なしの再開は保証しない(D-5)。
- **不採用**: コーディングエージェント CLI としての製品形。
  権限システムを持たない既定(ユーザー権限でツールが走る)。
  Ene は Broker・承認 plane・OS サンドボックスを必須にする。
  JSONL セッション木も採用しない(SQLite イベントログ)。

### AIRI から

- **採用**: soul(魂・エージェント)と body(体・アバター)の分離、
  内面(思考・感情・行動)の可視化、stage 中心の UX、複数 body の舞台、
  イベント駆動のサーバーランタイム → [body/](../body/README.md)、
  [companion/inner-channel.md](../companion/inner-channel.md)、
  [platform/clients.md](../platform/clients.md)。
  **表層 soul** の実装性格(存在感・感情・会話が主、仕事の遂行は裏に置く)。
- **不採用**: ブラウザ(Electron/Tauri 上の Web 描画)専有の前提。
  Ene はネイティブ描画(VRM/wgpu)を維持するが、描画は body レイヤーに閉じ込める。
  AIRI の soul がゲーム操作など作業そのものを持つ点も採用しない。
  Ene の表層に公開するのは副作用のない読み取り専用ツールだけで、
  複雑な作業と副作用は裏層へ託す(D-1/D-2)。

### Open-LLM-VTuber から

- **採用**: 全二重音声(割り込み・自声回避)、デスクトップペットの発想(後継)、
  エージェント実装の差し替え可能性、内面描写の表示 → [body/voice.md](../body/voice.md)、
  [core/agent-loop.md](../core/agent-loop.md)
- **不採用**: 単一コンパニオン前提、テキスト内感情キーワード埋め込みの表現方式。
  感情は構造化イベントとして扱い、テキストは発話に専念させる。

## 5. プロダクトの全体像

### 5.1 コアデーモン内の2層

コアデーモンは**唯一のホスト**である。ホストを表層と裏層に割らない。
各コンパニオンは、そのホストの中で次の2層として走る。

| 層 | 実装の性格 | ユーザー入力 | 責務 | 駆動するレーン |
|---|---|---|---|---|
| **表層 soul** | AIRI / Open-LLM-VTuber に似たコンパニオン実装 | **唯一の入口**(音声・テキスト・能動発話・スケジュール発火) | 会話、人格、感情、記憶、内面、能動発話、簡単な作業の実行、複雑さの判断、ユーザーへの伝え方 | 対話レーン(1本・単一フライト) |
| **裏層ハーネス** | opencode v2 / DeepSeek Harness に似た作業実装 | 直接は受けない。表層からの層間メッセージのみ | 複雑な調べ物・文書作成・副作用のあるツール実行・job・サンドボックス。進捗と成果を表層へ返す | job レーン(複数・並行) |

両層は**同一のハーネスカーネル**の上に乗る。カーネルが共有するのは
セッションログ、turn/step の駆動面、Tool Calling 規約、MCP 供給、skill 形式、
統一ツールレジストリである。**フィルタだけの2プロファイルではない。**
表層と裏層はそれぞれ専用のエージェント実装を持つ:

| | 表層実装 | 裏層実装 |
|---|---|---|
| 性格 | AIRI / Open-LLM-VTuber 寄り | opencode / dsh 寄り |
| 公開ツール | **副作用のない読み取り専用ツール**(記憶想起・時刻・計算・軽い参照)+ `delegate.*` | 作業ツール全般 + `delegation.send` + 再帰 `delegate.*` |
| ターン | 短く、発話と内面が主 | 長く、ツールステップが主 |
| Context Source | 人格・感情・記憶・内面。作業 Source は載せない | 委譲ブリーフ・job workspace・skill・MCP。親の対話履歴は既定で載せない |
| waterfall | 感情・quiet hours・能動発話ゲート | guard・plan・sandbox 前段 |

実装の登録表は [core/agent-loop.md](../core/agent-loop.md) と
[core/context-assembly.md](../core/context-assembly.md)。
後継の「実装差し替え」(P-514)は、この専用実装そのものを別アーキテクチャに
入れ替える余地であり、v1.0 の2実装分割とは別物である。

接合規則:

1. **入口は表層のみ。** desktop / web / CLI からの発話は、モダリティ
   (音声・テキスト)を問わず対話レーンに入り、裏層へは届かない。
2. **境界は「副作用の有無」であって「簡単さ」ではない。** 表層に公開するのは
   副作用のない読み取り専用ツールだけで、書き込み・実行・送信・外部状態を
   変えるツールは裏層のみが持つ(D-2)。表層はその範囲で、計画立案を要さない
   簡単な作業を自分で片付けてよい(D-1)。
   「簡単さ」をモデルの自己申告で判定して副作用の許可条件にすると事故が
   防げないが、副作用の有無は静的に決まるので境界として信頼できる。
3. **見誤りは機構で回収する。** 表層のターンが所定のステップ数を超える、
   または副作用のあるツールを必要とした時点で、ハーネスが自動的に裏層への
   委譲へ切り替える(D-3)。モデルが正しく判断することに依存しない。
4. **声は表層のみ。** ユーザーに向けた発話は対話レーンだけが発生させる
   ([core/invariants.md](../core/invariants.md) I-31)。裏層の出力が発話
   チャネルに直接出る経路はない。
5. **1体として成立する。** 裏層は表層と同じ soul の identity・記憶方針・
   skill を継承する。ユーザーから見れば「Ene(そのコンパニオン)がやってくれている」
   であり、内部の2エージェントではない。
6. **ハーネスは常駐の第二人格ではない。** 裏層実装はデーモンに常駐するが、
   実行は作業のたびに job レーンへ **spawn** する。常時もう1つの心が
   ユーザーと並行会話することはない。spawn ごとに独立した
   **job workspace** を持つ([tasks/jobs-and-schedules.md](../tasks/jobs-and-schedules.md))。

```text
                    │   ├─ ハーネス機能ツール(記憶想起・委譲・質問)    │
                    │   ├─ ハーネス内部処理(コンパクション・記憶抽出)  │
                    │   └─ 補助LLM(画面要約・抽出・能動発話の一次判定) │
                    │  実行系                                         │
                    │   ├─ プラグイン監督(ツールはアウトプロセス)      │
                    │   ├─ Broker(資源仲介)・承認 plane               │
                    │   └─ サンドボックス                             │
                    └──────────────────┬──────────────────────────────┘
                                       │ IPC(副プロトコル分割・バルクは枠外)
                    ┌──────────────────▼──────────────────────────────┐
                    │ プラグイン群                                     │
                    │  ツール(fs/exec/web/app/utility)                 │
                    │  プロバイダ(LLM/TTS/ASR/埋め込み)                 │
                    │  MCP クライアント経由の外部ツール                  │
                    │   (git/browser/calendar/homeassistant/geo)       │
                    └─────────────────────────────────────────────────┘
```

クライアントはコアデーモンに接続するが、会話の宛先は常に表層 soul である。
裏層は図の右側にあり、ユーザー入力の矢印は届かない。

### 5.3 層間メッセージ(Codex multi-agent v2 に倣う)

表層と裏層は、同期のツール結果待ちではなく、型付きエンベロープの送受信で
協調する。詳細なツール名と耐久化は [core/delegation.md](../core/delegation.md)。

| 種別 | Codex v2 の対応 | 方向 | 相手の扱い | 用途 |
|---|---|---|---|---|
| `task` | `NEW_TASK`(spawn / followup) | 表層 → 裏層 | **wake**(ターンを起こす) | 作業の委託、追加指示 |
| `message` | `MESSAGE` | **双方向** | **inject**(ターンを起こさない) | 進捗・補足・状況共有 |
| `question` | (v2 の質問面) | 裏層 → 表層 | **wake** | 表層(ひいてはユーザー)の判断が要る質問 |
| `answer` | `MESSAGE` / 応答 | 表層 → 裏層 | **wake** | 質問への回答 |
| `final` | `FINAL_ANSWER` | 裏層 → 表層 | **wake**(終端) | 完了・失敗。要約と成果物参照 |
| `cancel` | — | 表層 → 裏層 | **wake** | 協調的キャンセル |

「互いに進捗を確認する」の意味:

- 表層は裏層の状態を読める(`status`)。裏層は `message`(progress)で
  表層の次ターン境界に進捗を届ける。
- 裏層は、新しい `task` / `answer` / `cancel` が自分の inbox に来たかで
  表層側の方針を知る。**対話履歴そのものは既定で見ない**(表層が `excerpt`
  で選んだ文脈だけを見る)。
- どちらの層も、相手を同期 await しない。会話は裏層の作業で止まらない。

### 5.4 パッケージとの関係

キャラクターパッケージ([character/](../character/README.md))が配るのは
soul 定義と body であり、裏層ハーネスはパッケージに含めない。
ハーネスはコアデーモンがすべてのコンパニオンに付ける実行層である。
実行時の1体は「パッケージ由来の soul/body + デーモン由来の裏層」で、
ユーザー向けの名は**コンパニオン**である。

## 用語集

以降の全設計文書で使う用語の厳密な定義。opencode の CONTEXT.md に倣い、
「使わない言い換え」も指定する。

| 用語 | 定義 | 使わない言い換え |
|---|---|---|
| **コアデーモン** | 唯一のホスト。セッション・メモリ・ツール・プラグイン・音声と、各コンパニオンの表層/裏層を所有する常駐プロセス。desktop が起動する(開発中は CLI が起動する)。 | サーバー、バックエンド |
| **コンパニオン** | ユーザーから見える1体の存在。表層 soul・裏層ハーネス・結び付いた body の組。内部は2層だが、ユーザーには1つの Character として見える。 | キャラクター(パッケージ形式の文脈では使う)、エージェント |
| **表層(soul ランタイム)** | ユーザー入力の唯一の入口。AIRI / Open-LLM-VTuber 系の**専用実装**。人格・感情・記憶・能動発話・内面を駆動し、作業の要否を判断して裏層へ託す。対話レーンを持つ。 | フロント、チャットボット |
| **裏層(ハーネス)** | 表層が託した作業の実行体。opencode v2 / DeepSeek Harness 系の**専用実装**。ツール・job・サンドボックスを駆動し、層間メッセージで表層と進捗を共有する。ユーザー入力の入口ではない。spawn ごとに独立 workspace。 | サブエージェント(ユーザー向けに使わない)、ワーカー、内層 |
| **ハーネスカーネル** | 両層が共有するインフラ。セッションログ、turn/step 駆動面、コンテキスト組立機構、耐久性、Tool Calling / MCP / skill の形式、統一ツールレジストリ。ホストそのものでも裏層実装でもない。 | ハーネス(層を指すときは使わない)、プロファイル(プラグインツリーと混同しない) |
| **エージェント実装** | カーネル上の層専用コード。表層実装と裏層実装の2つ。公開ツール面・Context Source 集合・ターン予算・waterfall リスナーが違う。 | プロファイル(プラグインツリー)、エージェントプロファイル |
| **層間メッセージ** | 表層と裏層が送り合う型付きエンベロープ(`task` / `message` / `question` / `answer` / `final` / `cancel`)。Codex multi-agent v2 に倣う。表層UIには出ない。詳細画面では出せる(D-11)。 | RPC、コールバック |
| **soul** | 人格・感情・記憶方針・声・スキルを定義する永続エンティティであり、その表層ランタイム。body とは独立に存在し、交換可能。 | 魂、エージェント |
| **body** | アバター資産・表情/モーションカタログを定義する永続エンティティ。soul とは独立に存在し、交換可能。 | 体、アバター(表示装置の意味では使う) |
| **セッション** | 1体のコンパニオンに属する連続した会話。ログ・履歴・要約の単位。必ず単一の soul に属する。 | チャット、スレッド |
| **ターン** | 1回の発話の単位。ユーザー発話(または能動発話・スケジュール発火)+ 応答全体。`TurnId` を持つ。 | — |
| **ステップ** | ターン内の1回のモデル要求+それが呼ぶツール実行。ターンは0以上のステップから成る。 | イテレーション、ループ1周 |
| **レーン** | コンパニオン内の実行レーン。対話レーン(表層・1本・単一フライト)と job レーン(裏層・複数・並行)がある。 | スレッド、チャネル |
| **job** | 対話レーンの外で動くバックグラウンド作業。実体は委譲の public モード。進捗・成果物・ライフサイクルを持つ。ユーザー向けの呼称は「**タスク**」(D-12)。 | おつかい、依頼 |
| **ワークスペース** | 内部概念。**spawn(委譲)ごと**の作業ディレクトリ。fs/exec の既定スコープ。ユーザーには見えない。soul 根の下に `jobs/<id>/` として置く。 | プロジェクト(opencode の意味では使わない) |
| **System Context** | モデルに「指示・状況」として提示される構造化コンテキスト。セッション履歴とは別の状態。 | システムプロンプト |
| **Session History** | セッションログから投影される、時系列の会話メッセージ列。 | セッションコンテキスト |
| **Context Source** | System Context を構成する1つの独立した型付き値。安定キー・codec・loader・レンダラを持つ。 | プロンプト断片 |
| **Context Epoch** | 1回レンダリングされた System Context が不変の基準点として有効な期間。コンパクション完了・セッション移動・非互換遷移で終わる。 | — |
| **compaction** | 履歴が窓を溢れる前に、古いメッセージを要約へ畳む処理。 | 圧縮(曖昧なので避ける) |
| **spill** | 巨大なツール出力をセッション履歴の外(ファイル)へ逃がし、履歴には要約と参照だけを残す処置。 | — |
| **seam** | 差し替え可能な能力の接合面。Service Definition(宣言)・Service Provider(実装)・Consumer(消費者)の3役割から成る。 | インターフェース(曖昧なので避ける) |
| **ツール** | モデルが Tool Calling で呼び出す能力のうち、**アウトプロセスで実行される**もの。統一ツールレジストリに登録される。ビルトインもサードパーティも同じ API に載る(D-10)。層ごとに公開面が違う。 | ビルトイン関数、プラグイン(配布単位を指すときのみ使う) |
| **ハーネス機能ツール** | モデルが Tool Calling で呼び出せるが、**ホスト内で実行される**もの。ハーネス状態と密結合するため、プロセス境界の向こうに置けない(記憶想起・委譲・内面・ユーザーへの質問)。 | ビルトインツール(アウトプロセスのものと混同しない) |
| **ハーネス内部処理** | ホスト内で走り、モデルからは呼べない処理(コンパクション・記憶抽出・感情更新・能動発話の観測)。ツールレジストリに現れない。 | 内部ツール |
| **補助LLM** | ハーネス内部処理が呼ぶ LLM(D-15)。呼び出し元で分ける3カテゴリ(会話LLM / ツール内部の LLM / 補助LLM)の第3。画面要約・記憶抽出とスコープ判定・能動発話の一次判定・コンパクションの要約・感情更新に使う。ツールレジストリには載らないが、設定では `ai.tasks.<task>` でモデルを指定できる。 | サブモデル、小型モデル(役割ではなくサイズを指す語なので避ける) |
| **Tool Calling** | モデルとハーネスカーネル間の呼び出し規約(モデルがツールスキーマを見て呼び出す機能)。LLM API レイヤー。 | ツール実行(実行はハーネスの責務) |
| **MCP** | 外部のツール/リソース/プロンプト供給元への接続規約(輸送・発見の標準)。供給元レイヤー。 | ツール(レイヤーが違う) |
| **内面チャネル** | soul の思考・感情表出・行動意図を、発話と分離して記録する永続イベント列。表層UIには出さない。見るのは設定画面(またはそれに類する詳細画面)のセッションログだけ(D-20)。 | 独り言(曖昧) |
| **能動発話** | ユーザー発話なしにコンパニオンが起こすターン。`TurnOrigin::Proactive`。 | — |
| **共有記憶プール** | 全コンパニオンが参照する記憶領域。ユーザーに関する事実と、記憶抽出の補助LLM が重要と判断した事項がここに入る(D-7)。書いたコンパニオンを出所として保持するが、想起の際に出所は意識させない。 | 共有スペース、共通メモリ |
| **ボールト** | soul 専用のメモリ領域。他 soul から読めない。体験・関係性・感情はここに入る。 | — |
| **Broker** | プラグインがファイル・ネットワーク・資格情報へアクセスする際の仲介 RPC。 | — |
| **承認 plane** | ツール実行の可否を決めるポリシー層(事前ポリシー・AI 自動承認・ポップアップ)。 | — |
| **プロファイル** | 起動する**プラグインツリー**のバンドル積層リスト。`desktop`・`minimal` 等。エージェント実装(表層/裏層)とは別物。 | エージェントプロファイル |
| **バンドル** | プラグインツリーに挿入される構成行+コードの配布形式。 | — |
| **ファイバー** | プロファイル**行**の実行実体。子プロセス+ホスト文脈への登録+巻き戻しの蓄積。パッケージではなく行が単位(同じプラグインを設定違いで2行置ける)。 | プラグインインスタンス(曖昧)、コンポーネント(Cordis の用語。Ene では使わない) |
| **巻き戻し可能な effect** | ホスト文脈への変更とその逆の対。登録は必ずこの対で行い、ファイバー停止時に逆を LIFO で適用する(D-32)。 | dispose フック、deactivate(作者が書く破棄手続き) |
| **provides / requires** | ファイバーがホスト文脈へ入れる鍵と、ACTIVE になるために必要な鍵。解決はホストの seam が行う。プラグイン同士は直接呼び出さない。 | inject(層間メッセージの inject と衝突する)、依存注入 |
| **stage** | desktop クライアントの、コンパニオンを表示する場(UX 名)。 | ウィンドウ(曖昧) |
| **artifact(成果物)** | job やターンが生成した、ユーザーに交付する物(文書・表・画像等)。 | — |
| **skill** | 手順+参照文書+任意のスクリプトを1パッケージにした、非コーディングタスクの手順知識。業界標準準拠。 | レシピ(口語では使う) |
| **レーンコマンド面** | レーンを駆動するコマンドの集合(prompt/steer/abort 等)と受理/拒否・結果/エラーの契約。HTTP/WS はこの面の射影。`resume` と結果照合は後継。ユーザー発話の `prompt` は対話レーン(表層)にだけ届く。 | API(曖昧) |
| **storage version** | セッション DB の永続形式のバージョン番号。オープン時の連鎖マイグレーションの基準。 | スキーマバージョン(曖昧) |
| **委譲(delegation)** | 表層が裏層へ実作業を移す非同期の機構。層間メッセージの実行面。internal モード=秘匿サブエージェント、public モード=job。表層は待たない。 | タスク(曖昧)、サブタスク |
| **報告ターン** | 裏層の完了・失敗・質問が、表層の対話レーンに届くターン(`origin: subagent`)。表層がユーザーへの伝え方を決める。 | コールバック(機構名は使わない) |
| **thinking** | プロバイダの reasoning 出力。ログには記録し、表層UIには出さないが、詳細画面には出せる。内面派生の素材になる(既定)。 | 思考(内面の thought aspect と混同しない) |
| **出力秘匿** | LLM の生出力(thinking・ツール引数・生出し・子セッション)を**表層UIに**出さない既定。表示面ごとに「深さ」が違い、詳細画面ではこれらを表示できる(D-11)。「決して表示しない」という不変条件ではない。 | — |
| **表示の深さ** | 表示面ごとに、どこまで内部を出すかの段階。`surface` と `detail` の2段階だけ(D-11)。表層UI(stage・チャット)は発話と成果物のみ(作業中の1行表示までは可)、詳細画面は内面・ツール呼び出し・層間メッセージ・thinking まで。 | 可視性レベル(曖昧) |
| **詳細画面** | 内部状態を検証するための表示面。表層UIとは表示の深さが異なる。desktop は別ウィンドウで設定・記憶編集も含む。Web も同じ深さの表示面を持つが、閲覧とデバッグに限り、変更は desktop のみ(D-31)。CLI は `--verbose` / `ene debug`。 | デバッグ画面(開発者専用ではないので避ける) |
