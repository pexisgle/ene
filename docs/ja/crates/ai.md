# `ene-ai`（プロバイダ抽象化）と local-llm プラグイン

> **クレート**: `ene-ai` (プロバイダトレイト、メッセージ/ストリーミング型、レジストリ) | `plugins/provider/local-llm` (`ene-plugin-llama-cpp`、`llama-cpp-4` による GGUF ローカル推論)

`ene-ai` は Ene 向けに LLM チャット補完およびテキスト埋め込みの抽象化を提供します: 汎用のメッセージ/ストリーミング型・プロバイダトレイト・グローバルなプロバイダレジストリを定義します。具体的なクラウドプロバイダはプラグインバイナリ (`plugins/provider/*`) として提供され、`ene-plugin-host` が同じトレイトへブリッジします。ローカル推論 (GGUF/llama.cpp) は `ene-plugin-llama-cpp` プロバイダプラグインに、ローカル音声 (STT/TTS/VAD) は別クレートの `ene-voice` にあります。

---

## アーキテクチャ境界

- `ene-ai` はプロバイダ抽象化層を所有します: メッセージ/ストリーミング型、プロバイダトレイト、ヘルスモニタリング/フェイルオーバールーティング、リトライポリシー。永続化や認知ロジックへの依存はありません。
- プロセス外の LLM プロバイダ (Anthropic、OpenAI、local-llm プラグイン) は `ene-ai` 自身ではなく `ene-plugin-host` が所有する IPC アダプタを介して同じ `LlmProvider` トレイトへブリッジされます。`ene-ai` はアダプタが実装するトレイトを定義するだけです。ローカル GGUF 推論 (kind `"local"`) もそのプラグインバックエンドの 1 つで、ランタイムはクラウド種別とまったく同じようにレジストリ経由でプロアクティブ決定・画面ビジョン・埋め込みをルーティングするため、llama.cpp のクラッシュはプラグインプロセス内に封じ込められ、ホストが再起動を監視します。
- `ene-ai` は安全なモデルファイルダウンローダ (`ModelFetcher`、`model_fetch` モジュール) を共有ホストしています: 同一 URL への同時リクエストの合流、`.part` ファイル + アトミックリネーム、部分ダウンロードの RAII クリーンアップ、HTTPS 限定の強制、進捗レポート、そして `ModelValidator` トレイトによるダウンロード後検証のプラグイン化です。local-llm プラグイン (GGUF 重み) と `ene-voice` (Kokoro ONNX モデルおよび `voices.bin`) はどちらもこれを利用しているため、各ローカル推論エンジンが個別にダウンロード処理を自前実装するのではなく、ここが安全な実装を一箇所に集約する場所になっています。

## 設計思想

- **なぜ具象クライアント型ではなくプロバイダトレイトか**: `LlmProvider`/`EmbeddingProvider` により、クラウドプロバイダ（OpenAI 互換プラグイン、Anthropic プラグイン）、ローカル GGUF 推論、IPC 経由のプロセス外プラグインプロバイダのすべてが同一インターフェースを満たせます。これにより `ene-mind`/`ene-runtime` 側の補完ストリーミングや埋め込みコードは、どのバックエンドが応答しているかを知る必要がありません。
- **なぜローカル推論がプラグインバイナリか**: `llama-cpp-4` は GPU バックエンドのビルド複雑性 (`vulkan`/`cuda` Cargo feature) を持ち込みますが、クラウドのみのデプロイにはこれは不要です。プラグインに隔離することで、リモートプロバイダのみを使用する利用者向けに `ene-ai` を軽量に保てるうえ、プロセス境界がネイティブクラッシュを封じ込めます（クラッシュ隔離契約テストを参照）。

## API リファレンス

構造体・メソッドのシグネチャはここには転記しません — 転記すると必ず陳腐化します。最新かつ正確な API は rustdoc を生成して参照してください:

```sh
cargo doc -p ene-ai --open
```

`ene-ai` の `LlmProvider` / `EmbeddingProvider` トレイトから始めてください。
