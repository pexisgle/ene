# `ene-mind`

> **クレート**: `ene-mind` | **役割**: 純粋な認知ターンエンジン — セッション、想起、プロンプト構築、感情、演出

`ene-mind` は Ene の純粋な認知コアです。セッション状態、記憶抽出、想起プランニング、感情エンジン、コンテキスト予算管理、プロアクティブ発話評価、出力/演出調停、プロンプトパケット構築のすべてがここに存在します。`ene-runtime` は `CognitionEngine` を*呼び出す*だけで、自身のストリーミングパス内で mind ロジックを再実装することはありません。

---

## アーキテクチャ境界

- `ene-mind` は `ene-runtime` や `ene-plugin-host` に**一切依存しません** — これによりホストファサードとそれが駆動する認知層との間の循環依存を防いでいます。
- `ene-mind` の認知ロジックモジュール (想起、記憶調停者、忘却、キャラクター同期、ジャーナル、自己内省) は永続化層を `ene_core::MemoryPort` トレイト経由でのみ呼び出します — 具象型の `ene_store::MemoryStore` を直接呼び出すことはありません。これにより SQLite なしのインメモリテストダブルに対してユニットテストできます。
- `ene-mind` は `ene-store` を公開 API 経由でのみ呼び出し、生の SQL や `sea-orm` クエリを発行することはありません。`ene-store` が唯一の SQLite 所有者であり続けます。
- 旧・独立セッションクレートから吸収されたセッション状態は `session` モジュール配下にあります。

## 設計思想

- **なぜ具象ストア型ではなく `MemoryPort` か**: 認知ロジック (想起プランニング、記憶調停者、忘却ライフサイクル) を特定の永続化バックエンドから切り離すことで、これらのコードパスは SQLite セットアップのコストなしにテスト内のインメモリダブルに対して実行できます。また `ene-store` はすべての mind 側呼び出し箇所を変更することなくスキーマを進化させられます。
- **なぜ感情/情動状態が単純な3軸 PAD モデルより豊かか**: `ene-core::AffectState` は Pleasure/Arousal/Dominance (`valence`/`arousal`/`dominance` として実装) に trust・affinity・irritation・curiosity・fatigue の各次元を加えて拡張しています。これらはプレゼンテーション層だけでなく、プロアクティブ発話のゲーティングや演出キューの選択にも供給されます。
- **なぜターン開始時の決定的キーワード評価がないか**: チャットモデルは応答生成時にすでに今回のユーザー発話を読んでいるため、同一ターンの感情反応は応答本文に委ねます。`EmotionEngine` はターンを跨いだ連続性（減衰・会話疲労・ターン後分類器→次ターン）を担います。`CharacterState` プロンプトは感情が今回の発話前であることを明記し、ターン終了時の表情は `resolve_expression`（LLM 提案が正典）で応答に追従します。感情分類器が無効または失敗している場合、感情は減衰と長い会話による疲労でのみ変化するため、モデル自身が明示的な `<|perf:expr=…|>` マーカーを出力しない限り、表情は事実上中立のままです。
- **なぜプロンプト構築がフラットなメッセージ配列ではなく独立したウィンドウ対応ステップか**: アイデンティティ・感情・想起記憶・ツール仕様・対話履歴の各セクションはモデルのコンテキストウィンドウを奪い合い、圧迫下でアイデンティティ/安全ルールを維持するにはパッキングの順序が重要です — パッキングはウィンドウを優先度順に充填し、必須セクションを常に保持しつつ、最も優先度の低いドロップ可能セクションから順に落としていきます (#370)。セクション構成については `docs/concepts/turn-and-session.md` §3 を参照してください。
- **なぜプロアクティブ判定の文脈を手組みの `key: value` テキストではなく JSON で直列化するか** (#380): 判定モデルの出力は制御フィールド (`should_speak`, `confidence` など) を持つ JSON オブジェクトですが、文脈はかつて同じ `key: value` 形式のフリーテキストでした。そのため `screen_summary` や会話履歴に取り込まれた第三者コンテンツ（Web ページ・ドキュメント・チャット）が、これらの制御フィールドを模倣する行を運び、判定モデルを誘導する恐れがありました。文脈を `serde_json` で直列化することで、そうしたコンテンツはエスケープされた JSON の*値*として埋め込まれ、構造的に兄弟フィールドである制御フィールドとして現れることがなくなります。さらに判定システムプロンプトは `screen_summary`・`recent_conversation`・活動ラベルを観測データとして明示し、指示として解釈してはならないと定めています。
- **なぜ話題境界の検出に連続発話の類似度ではなく重心 + 複合スコアを使うか** (#367): ペアワイズの類似度は、相槌・埋め込みが不安定な短い発話・単一の低類似ペアが現れない緩やかなずれに対して機能しません。移動平均の話題重心はずれを累積し、重心距離・沈黙・話題ターン数の複合（短い相槌は評価からも重心更新からも除外）により、ハードコードされた語リストを使わずに言語をまたいで頑健に境界を検出します。検出はシグナル/スコアの生成のみを行い、それに基づく動作は圧縮 (#368) とセッション分割 (#369) へ委ねられます — `docs/concepts/turn-and-session.md` §2 を参照してください。
- **なぜツール由来記憶に安定キーによる上書きと妥当性ゲートを設けるのか (#349)**: ツール失敗の `Reflection` レコードは失敗した呼び出しのたびに揮発的なエラーテキストと共に書き込まれるため、コンテンツベースの重複排除とセマンティック一致の防波堤は決して発火せず、レコードは無制限に積み上がります。アービターはツール由来候補を安定した `(kind, title)` の組をキーとして扱うようになり、一致時に既存のアクティブレコードを上書きします。また、タイトルに記されたツールが一度も呼び出されていない候補や、コンテンツが純粋な定型文のみの候補は棄却します — 詳細は `docs/concepts/memory-system.md` §5 を参照してください。
- **なぜ話題圧縮が遡後的で、ウィンドウ逼迫トリガーがトークン基準か** (#368): 話題の切り替わりを即時に判断するのは難しく、応答を待たせる価値もありません。そのため境界判定と要約は遅延ポストタースロット（`Terminal` の後、記憶書き込みや感情分類と並行）で実行され、応答をブロックすることはなく、アシスタント自身の応答も追加の判定材料として利用できます。検出された境界はその*前*の区間を1つの scene span へ圧縮し（1話題 = 1要約）、次のターンへ「前の話題の要約 + 直近ターン」を残します。従のウィンドウ逼迫トリガーは、保持履歴のトークン推定値を設定可能な上限 (`ContextConfig::context_pressure_tokens`) と比較し、従来のメッセージ数比率とハードコードされた `1.25` を置き換えることで、境界が現れないほど長い話題に対するトークン認知の保険として機能します。
- **なぜ Identity Kernel の予算がモデルウィンドウに比例し、CJK を高密度に数えるのか (#386)**: 固定 400 トークン上限と英語前提の `chars / 4` 切り詰めは、日本語キャラクターカードを 3〜4 倍過小評価し、プロンプトの他セクションより Identity Kernel が過度に削られていました。予算は `available_window / 8`（400〜4 000 トークンにクランプ）とし、切り詰めは言語対応の文字重み（CJK ≈ 1.5 文字/トークン、ラテン ≈ 4 文字/トークン）で行い、日本語のアイデンティティ文を現実的なサイズで予算化します。

## API リファレンス

構造体・メソッドのシグネチャはここには転記しません — 転記すると必ず陳腐化します。最新かつ正確な API は rustdoc を生成して参照してください:

```sh
cargo doc -p ene-mind --open
```

ターン処理のエントリポイントは `CognitionEngine` (`engine` モジュール)、感情については `AffectState` / `EmotionEngine` (`ene-core` / `emotion` からの re-export) を参照してください。
