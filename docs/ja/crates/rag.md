# `ene-rag`

> **クレート**: `ene-rag` | **役割**: RAG ポリシー層 — 記憶想起のスコアリング/減衰、および検索拡張生成によるツール選択

`ene-rag` は、かつて永続化クレート (`ene-store` の純粋なスコアリング/減衰関数) と独立したツール選択クレート (旧 `ene-tool-rag`) に分散していた、検索拡張生成 (RAG) の*ポリシー*を集約します。スコアリングとランキング、半減期減衰、埋め込みキャッシュ管理、後処理 (再ランク、カテゴリごとの上限) を所有します。クレートマップ上では `ene-voice` と同格です。

---

## アーキテクチャ境界

- スコアリング/減衰のコアは `ene-core` **のみ** (と汎用依存) に依存します。`ene-rag → ene-store` の辺が存在しないため、store↔rag の循環依存はコンパイル時に不可能です — これは偶発的な性質ではなく設計上の目標です。
- 永続化には `ene_core::EmbeddingStorePort` および `ene_core::MemoryPort` トレイト経由でのみ到達し、具象の `ene_store::MemoryStore` は使いません。これらのポートを実装するのは `ene-store` であり、`ene-rag` は抽象に対してプログラムします。
- ツール選択パイプライン (`tool` モジュール) は、埋め込み/LLM の機構 (`ene-ai`) を必要とするため `tool` Cargo feature の背後に置かれています。永続化 (`ene-store`) と認知 (`ene-mind`) の呼び出し側はデフォルトの feature セット — 純粋なスコアリング/減衰のみ — を使うため、埋め込みのスタックが永続化層に漏れ出すことはありません (AGENTS.md: `ene-store` ↛ `ene-ai`)。`tool` を有効にするのは `ene-runtime` のみです。
- 純粋な状態機械のライフサイクルバリデータ (`validate_transition` / `validate_user_restore`) はここには**ありません** — これらはライフサイクルポリシーであり `ene-store` に留まります。移設されたのはスコアリング/減衰ポリシーのみです。

## 設計思想

- **なぜポリシー専用のクレートなのか**: `ene-store` の責務は永続化 (SQLite/SeaORM、スキーマ、ベクトルプリミティブ、候補収集) です。純粋なスコアリング/減衰関数はデータベースに一切触れないため、そこに置くことは「ストアは永続化のみ」という原則に反し、ストアが本来所有すべきでないポリシーに依存する状態を生んでいました。
- **なぜ `MemoryPort::search` がスコアリング済み結果ではなく収集済み候補を返すのか**: ストアの仕事はインデックスからの候補収集で終わり、スコアリングはポリシーです。ランク付けされていない `GatheredCandidate` を返すことで、呼び出し側は `store.search(...)` と `ene_rag::score_and_rank` を組み合わせることができ、収集/スコアリングの分離がトレイト境界で明示的になります。
- **なぜ半減期減衰プリミティブが1つなのか**: 想起の新近性 (`recency_score`) とライフサイクルの保持 (`decay_score`) は、同じ `exp(-λ·age)` 式を異なるアンカーで独立に実装していました。単一の `half_life_decay` カーネルに統一することで、各呼び出し側のアンカーと後処理を正確に保ったまま重複を排除します。
- **なぜ動的レジストリではなく `Scorer` トレイトなのか**: メモリ側は収集済み候補をスコア内訳へスコアリングし、ツール側はフィールド埋め込みをスカラーへスコアリングします — 候補型もスコア型も異なります。文字列キーのレジストリではこれらの型が失われますが、トレイトなら各 RAG システムが自身の候補/コンテキスト/スコア型を保ったまま、周囲のパイプラインを共有できます。これは計画中のドキュメント/ワークスペースインデックス (#185) の拡張点にもなります。
- **スコープに関する注記**: 本クレートは*構造的*な分離です。スコアリングの計算式は以前のまま正確に保たれています。ハイブリッドスコアの加算構造の再設計は別途管理されています (#346 / #436)。

## API リファレンス

構造体・メソッドのシグネチャはここには転記しません — 転記すると必ず陳腐化します。最新かつ正確な API は rustdoc を生成して参照してください:

```sh
cargo doc -p ene-rag --open
```

メモリポリシーには `scoring` と `decay` モジュールから、拡張点には `Scorer` トレイトから、ツール選択パイプラインには (feature でゲートされた) `tool` モジュールから始めてください。
