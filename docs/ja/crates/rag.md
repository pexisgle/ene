# `ene-rag`

> **クレート**: `ene-rag` | **役割**: RAG ポリシー層 — 記憶想起のスコアリング/減衰、および検索拡張生成によるツール選択

`ene-rag` は、かつて永続化クレート (`ene-store` の純粋なスコアリング/減衰関数) と独立したツール選択クレート (旧 `ene-tool-rag`) に分散していた、検索拡張生成 (RAG) の*ポリシー*を集約します。スコアリングとランキング、半減期減衰、埋め込みキャッシュ管理、後処理 (再ランク、カテゴリごとの上限) を所有します。クレートマップ上では `ene-voice` と同格です。

---

## アーキテクチャ境界

- スコアリング/減衰のコアは `ene-core` **のみ** (と汎用依存) に依存します。`ene-rag → ene-store` の辺が存在しないため、store↔rag の循環依存はコンパイル時に不可能です — これは偶発的な性質ではなく設計上の目標です。
- 永続化には `ene_core::EmbeddingStorePort` および `ene_core::MemoryPort` トレイト経由でのみ到達し、具象の `ene_store::MemoryStore` は使いません。これらのポートを実装するのは `ene-store` であり、`ene-rag` は抽象に対してプログラムします。
- `workspace` モジュール（デフォルト feature）は、ドキュメント/ワークスペース RAG のポリシー — 見出しと行範囲のメタデータ付きチャンキング、無視ルールの glob マッチ、ハイブリッドチャンクスコアリング、`rag.workspace` 設定 — を所有します。これはメモリ想起・ツール選択に続く3つ目の RAG 利用者であり、I/O のオーケストレーションはランタイムのインデクサー、インデックスの永続化は `ene_core::WorkspaceDocumentPort` 経由の `ene-store` が担当します。
- ツール選択パイプライン (`tool` モジュール) は、埋め込み/LLM の機構 (`ene-ai`) を必要とするため `tool` Cargo feature の背後に置かれています。永続化 (`ene-store`) と認知 (`ene-mind`) の呼び出し側はデフォルトの feature セット — 純粋なスコアリング/減衰のみ — を使うため、埋め込みのスタックが永続化層に漏れ出すことはありません (AGENTS.md: `ene-store` ↛ `ene-ai`)。`tool` を有効にするのは `ene-runtime` のみです。
- 純粋な状態機械のライフサイクルバリデータ (`validate_transition` / `validate_user_restore`) はここには**ありません** — これらはライフサイクルポリシーであり `ene-store` に留まります。移設されたのはスコアリング/減衰ポリシーのみです。

## 設計思想

- **なぜポリシー専用のクレートなのか**: `ene-store` の責務は永続化 (SQLite/SeaORM、スキーマ、ベクトルプリミティブ、候補収集) です。純粋なスコアリング/減衰関数はデータベースに一切触れないため、そこに置くことは「ストアは永続化のみ」という原則に反し、ストアが本来所有すべきでないポリシーに依存する状態を生んでいました。
- **なぜ `MemoryPort::search` がスコアリング済み結果ではなく収集済み候補を返すのか**: ストアの仕事はインデックスからの候補収集で終わり、スコアリングはポリシーです。ランク付けされていない `GatheredCandidate` を返すことで、呼び出し側は `store.search(...)` と `ene_rag::score_and_rank` を組み合わせることができ、収集/スコアリングの分離がトレイト境界で明示的になります。
- **なぜ半減期減衰プリミティブが1つなのか**: 想起の新近性 (`recency_score`) とライフサイクルの保持 (`decay_score`) は、同じ `exp(-λ·age)` 式を異なるアンカーで独立に実装していました。単一の `half_life_decay` カーネルに統一することで、各呼び出し側のアンカーと後処理を正確に保ったまま重複を排除します。
- **なぜ想起と忘却で異なるアンカーを使うのか** (#345): かつては単一の `last_accessed_at` フィールドが想起の新近性と忘却の減衰起点の*両方*を駆動しており、想起は無条件でこれを更新していました。その結果、頻繁に想起される記憶は自身の経過時間をゼロにリセットしてしまい、決してフェードしませんでした (自己強化ループ)。忘却は今や `active_decay_anchor` 経由で最後の*内容更新* (`updated_at`) を基準にし、想起の新近性は `last_accessed_at` を維持します。「最後に想起された」と「最後に編集された」は別の概念であり、もはや混同されません。アクセスブーストも同様に時間減衰し (`access_boost_score` は最終アクセスからの経過時間で減衰)、蓄積されたアクセスがスコアを永久に嵩上げできないようになっています。さらに想起の bump は、検索で上位に来たかどうかではなく、実際のプロンプトへの載入 (記憶システムのドキュメントを参照) でゲートされます。
- **なぜ `Scorer` トレイトが (まだ) 存在しないのか**: 以前の改訂では、メモリシステムとツールシステムにまたがる「1つの候補をコンテキストに対してスコアリングする」という処理を抽象化するために `Scorer` トレイトを導入していました。これはレビュー (#302) の過程で削除されました。自身のユニットテスト以外から呼び出される箇所が一切なく、ツール側の実装は選択パイプライン内のインラインロジックと重複していたためです。2回実装されるためだけに存在するトレイト — しかもその1つは feature flag の背後にある — は、拡張点ではなく負債です。ドキュメント/ワークスペースインデックス (#185) がその3つ目の利用者となりましたが、そのスコアリングは共有トレイトを無理に作らず、焦点を絞った純関数 (`workspace::score_chunk`) として実装しています。
- **スコープに関する注記**: 本クレートは*構造的*な分離です。その構造の上に、ハイブリッドスコアの合成は加算的な重み付き和から関連性駆動の乗算形式へ再設計され (#346)、ツール選択スコアは非正規化のフィールド合計から、フィールド数に依存しない正規化済み重み付き平均と負例ゲートへ再設計されました (#436)。両ポリシーをここに置くことで、メモリ側とツール側が再び分岐しないようにしています。
- **なぜツール失敗フィードバックがポート経由で流れるのか (#349)**: ツール選択パイプラインは、アクティブなキャラクターに対して最近失敗したツールの重みを下げることができますが、そのために永続化への依存を得てはなりません。最近の失敗は `ene_core::ToolFailureSignalPort` 抽象（`Reflection` の失敗レコードを既に所有する `ene-store` が実装）経由で読み取られ、`ene-rag → ene-store` の辺が存在しない状態を保ったまま、繰り返し失敗するツールをランキング内で沈ませることができます。

## API リファレンス

構造体・メソッドのシグネチャはここには転記しません — 転記すると必ず陳腐化します。最新かつ正確な API は rustdoc を生成して参照してください:

```sh
cargo doc -p ene-rag --open
```

メモリポリシーには `scoring` と `decay` モジュールから、ドキュメント/ワークスペースのポリシーには `workspace` モジュールから、ツール選択パイプラインには (feature でゲートされた) `tool` モジュールから始めてください。
