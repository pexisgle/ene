# 長期記憶システムとハイブリッド想起

Ene の長期記憶アーキテクチャは、セッションを越えた永続的な想起、型付きメモリの分類、ハイブリッド検索スコアリング、およびバックグラウンド記憶整理を提供します。

---

## 1. 型付きメモリの分類

`ene-store` 内の記憶は `MemoryKind`（`Episodic`, `Semantic`, `UserProfile`, `Relationship`, `Affective`, `Commitment`, `Preference`, `Procedure`, `WorldState`, `Reflection` の全 10 種）により型付けされます。対話コンテキストで利用される主な分類は以下の通りです：

| メモリ型 | スコープ | 具体例 |
|---|---|---|
| **エピソード (Episodic)** | 出来事の記録・対話サマリー | *"ユーザーは金曜日に Rust のゲームエンジン構築について話した。"* |
| **セマンティック (Semantic)** | 一般的ファクト・知識 | *"ユーザーは VSCode より Neovim を好む。"* |
| **プレファレンス (Preference)** | 嗜好・嫌悪・習慣 | *"深煎りコーヒーが苦手。"* |
| **コミットメント (Commitment)** | タスク・約束・合意事項 | *"明日の午前10時にデプロイログを確認すると約束した。"* |

---

## 2. ハイブリッド想起アルゴリズム

`before_turn` の実行時、 `ene-mind` は `ene-store` に候補の*収集* (ベクトル・字句・新近・コミットメントの検索) を依頼し、その候補を `ene-rag` に渡して多要因 **ハイブリッド検索スコア** で*スコアリング*します：

$$S = w_v \cdot S_{\text{vector}} + w_l \cdot S_{\text{lexical}} + w_r \cdot S_{\text{recency}} + w_s \cdot S_{\text{salience}}$$

各シグナルの定義：
- **$S_{\text{vector}}$**: `sqlite-vec` を使用した埋め込みベクトルのコサイン類似度。
- **$S_{\text{lexical}}$**: 全文検索 BM25 マッチスコア。
- **$S_{\text{recency}}$**: 作成時からの経過時間に基づく指数減衰スコア。
- **$S_{\text{salience}}$**: 記憶抽出時に割り当てられた重要度ランク。

### MMR (Maximal Marginal Relevance) 多様化
プロンプトパケットに重複したファクトが注入されるのを防ぐため、候補記憶は MMR リランクを通されて多様性が最大化されます。

### アクセス bump ポリシー
記憶が想起されると、その `access_count` と `last_accessed_at` が bump されます — ただし、**実際にプロンプトへ載った場合に限ります**。予算マネージャは、プロンプトがコンテキストウィンドウを超過した際に、想起された記憶のセクション全体を削除することがあります。そのような記憶は検索では想起されたもののモデルからは一切見えないため、bump *されません*。パッキングを生き残った記憶の集合は追跡され (`PromptPacketMeta::injected_memory_ids`)、合成後にそれらのみが bump されます。これにより「検索では上位だったが削除された」ことが記憶を強化するのを防ぎます (#345)。

bump がランキングに与える効果も制限されています。アクセスブーストは最終アクセスからの経過時間で減衰する (半減期減衰) ため、ずっと前のアクセスはカウントされなくなり、記憶が永続的なランキング上の優位を固定することはできません。

### 矛盾解決（メモリー調停器）
候補記憶を永続化する前に、メモリー調停器（arbiter）はそれが同じ種別（`Preference`, `UserProfile`, `Semantic`, `Relationship`, `Commitment`）の既存記憶と矛盾しないかを検査します。どの種別を検査するか（そして主題をどのようにキー付けするか）は、`MemoryKind` の種別別ポリシーテーブルという一箇所で定義されています。2 つの記憶は、その **タイトル埋め込み** のコサイン類似度が `mind.memory.contradiction_title_similarity_threshold`（デフォルト `0.82`）に達したときに同じ主題として扱われます。これにより、同義のタイトル（「職業」と「仕事」）は矛盾する重複として蓄積されるのではなく、1 つの主題にまとめられます。埋め込みプロバイダーが未設定の場合、調停器は正規化タイトルの完全一致にフォールバックします。

矛盾が見つかった場合、調停器は候補の confidence を既存記憶のものと比較します。候補が既存を `mind.memory.supersede_confidence_delta`（デフォルト `0.05`）以上上回れば、新しい記憶が古い記憶を *上書き（supersede）* します。差が `mind.memory.dispute_confidence_gap`（デフォルト `0.15`）の範囲内であれば、既存記憶は *係争中（disputed）* とマークされます。それ以外の場合、判定はユーザー確認へ回されます。重複排除時の意味的重複検出には `mind.memory.semantic_similarity_threshold`（デフォルト `0.85`）を使用します。`min_confidence_to_persist` を含むこれら 4 つの閾値はすべて `mind.memory.*` で設定でき、読み込み時に `0.0..=1.0` へ clamp されます (#352)。

ユーザー確認へ回された候補は `pending_candidates` キュー（`AskConfirmationLater`）に保持されます。これらはデスクトップの設定画面で手動レビューできますが、**通常のハイブリッド想起にも参加**します。保留候補は埋め込みを持たないため、想起はライブのキューを読み込み、クエリと語彙が重なる（lexical overlap）行だけを通常のスコア競争に参加させます。表面化した候補はプロンプト内で `[unconfirmed]` マーカー付きで描画され、キャラクターはそれを確定事項として断言するのではなく、会話内で確認すべき情報として扱います。`recall_pending_candidate_limit`（デフォルト `3`）はターンごとに競争へ参加する数を上限し、`0` にすると設定画面のレビュー一覧に影響を与えずに想起経路を完全に無効化できます。この上限は `MindMemoryConfig` でコード調整でき、設定としてはまだ公開されていません。

### 承認モード（`mind.memory_approval.require_approval`）
`require_approval` を有効にすると、パイプラインは**保存前レビュー**になります。通常は
永続化される（または既存記憶を上書きする）候補はすべて、typed memory に書き込む代わりに
同じ `pending_candidates` キューに留め置かれます。各候補は出典ターンと出典引用、抽出理由、
confidence、上書き対象（`existing_memory_id`）を保持します。承認モードの候補は
**想起から完全に除外**されます。プロンプトには現れず、レビューキューでのみ表示されるため、
未承認の情報が通常の想起に漏れることはありません。既定の自動保存モードは変更されません。

このキューは単なる一覧ではなく、完全なワークフローです。

- **一覧・確認** — CLI の `/memory approval`（および `approval inspect <id>`）と
  デスクトップ Memory Journal の承認タブで、出典・理由・confidence・競合対象を表示します。
- **承認・却下** — 承認すると候補が typed memory として永続化され
  （`existing_memory_id` は `supersedes_id` として引き継がれ、自動保存の上書き
  パスと同様に古い記憶は無効化されます）、却下すると破棄されます。
- **編集・編集して承認** — ユーザー編集可能な項目（タイトル・内容・種別・confidence）を
  保存前に修正できます。編集は書き込み前に検証され、
  `WHERE status = 'pending'` の条件付き更新で適用されるため、不正な編集や競合が
  発生しても元の候補が失われることはありません。
- **履歴** — 解決済みの候補はキューに残り（`pending_candidate_retention`、コード既定
  14 日 / 200 件で上限）、`/memory approval history` とデスクトップの履歴ビューで
  解決日時とともに確認できます。

すべての解決・編集操作は実行中のターン ID を保持したままランタイムの actor を経由し、
`CandidateChanged` ライフサイクルイベントとして発行されるため、決定の経緯は
actor のイベントバスから監査可能です。コミットメント候補（専用の台帳パス）と
明示的なユーザー忘却・係争（dispute）判定は、どちらのモードでも即時に適用されます。

### 自己反省フィードバックループ
`mind.memory.reflection.enabled` を設定すると、ターン後パイプラインは定期的に永続化された記憶の成果をレビューし、成功した・失敗した対話戦略を要約する `Reflection` 記憶を書き込みます。これらの反省は**想起時にループを閉じます**。読み込まれてスコアリング信号として適用され、成功戦略に一致する記憶をブーストし、回避すべき戦略に一致する記憶をペナルティします。反省記憶は意図的に**想起候補セットから除外されます**（検索クエリの種別フィルタによる）。これにより、スコアを調整しつつ、通常の想起結果として表示されたり LLM のコンテキストに漏れたりすることはありません。適用された各補正はスコア内訳の `reflection_multiplier` に記録され、説明可能なスコアが表示される total と一致し続けます。

記憶を永続化する調停判定にはすべて、`outcome_rating`（-1.0 のネガティブ〜1.0 のポジティブ）がアクションと適用結果（`AppliedDecision`）の両方に刻まれ、ターンの感情価（`PostTurnInput.affect.valence`）から導出されます。リフレクションが有効な場合、評価された各判定は永続的な `memory_outcomes` テーブル（`rating`、`source`、`source_ref`、`created_at`）に書き込まれます。`source` 判別子（`affect` | `user_feedback`）は、将来の明示的なユーザーフィードバック経路に備えたストレージ契約を予約します。評価の書き込みは L1 リコールキャッシュを無効化するため、次の想起は最新の評価を反映します。リフレクションパスは、パイプライン生成後に記録された行を新しい順・パスごとの上限付きで集計します。呼び出しごとのメモリバッファではなく永続化されたテーブルを読み出すため、評価は再起動後も残り、リフレクション信号の唯一の情報源となります。古い成果行の保持・削除は将来の課題です。

## 3. コミットメント台帳

コミットメント（Ene が行った約束やユーザーからの依頼）には特別なアトミック性が与えられます：

- **単一の真実のソース**: コミットメントエンティティは厳格な状態 (`Active`, `Fulfilled`, `Cancelled`, `Expired`) で管理されます。
- **台帳の保護**: 約束したタスクの失念を防ぐため、アクティブなコミットメントはプロンプト構築時に最優先で挿入されます。
- **曖昧なタイトル一致**: 埋め込みプロバイダーが利用可能な場合、台帳は着信したコミットメントを、タイトルの完全一致ではなく *タイトル埋め込みの類似度* でアクティブなコミットメントと照合します。これにより、言い回しの異なる約束（「資料をまとめる」と「資料作成」）は矛盾する二重登録ではなく、既存のコミットメントの更新（supersede）として扱われます。類似度の閾値は `mind.memory.commitment_title_similarity_threshold` で設定でき、埋め込みプロバイダーがない場合は正規化タイトルの完全一致にフォールバックします。照合は適用バッチごとにアクティブな台帳行をメモリへ読み込み、`mind.memory_limits.commitment_active_match_limit`（デフォルト `4096`）が件数上限です。切り捨て警告には上限の上げ方が含まれます。

## 4. バックグラウンド整理と忘却サイクル

ターンレイテンシを低く保つため、記憶の書き込みは非同期に処理されます：

1. **同期的なターン完了**: ターンが終了すると、即座に `EneEvent::Terminal` が発行されます。
2. **遅延記憶抽出**: バックグラウンドタスクがターンのトランスクリプトを検査し、候補ファクトを抽出し、ベクトル埋め込みを生成して SQLite に保存します。
3. **忘却と減衰**: 低重要度の記憶はスコアが自然減衰し、保持ルールに従ってアーカイブまたは削除されます。

### 忘却のアンカー
忘却の減衰は、記憶が最後に想起された時 (`last_accessed_at`) ではなく、最後の**内容更新** (`updated_at`) を基準に測定されます。想起の新近性 (候補のランキングに使う) は引き続き `last_accessed_at` を使いますが、この2つは意図的に分離されています。記憶が想起されたことで、自身の忘却の時計をリセットできてはならないためです。もしリセットできれば、頻繁に想起される記憶はフェード閾値に決して到達せず、想起が記憶のスコアを*上げると同時に*忘却からも守るという自己強化ループが生じます (#345)。記憶の内容を編集すれば `updated_at` が更新されて正当に生き延びますが、単に想起するだけでは生き延びません。

## 5. ツール由来記憶のガードレール

ツール実行結果から抽出される記憶 — とりわけツール呼び出しの失敗時に書き込まれる
`Reflection` レコード（`persist_failure_reflection`、既定で有効）— は本質的にノイズが
多く、同じツールが毎ターン*異なる*エラーメッセージで失敗し得るため、コンテンツベースの
重複排除だけでは決して一致しません。放置するとこれらのレコードは無制限に積み上がります。
以下の 2 つのガードレールが、他の記憶種別の挙動を変えずにこれを抑止します：

- **安定キーによる上書き重複排除。** ツール由来の候補は、揮発的なコンテンツではなく、
  安定した `(kind, title)` の組（例：`Reflection` + `tool failure:{tool_name}`）をキーと
  します。新しい候補がそのキーで既存のアクティブなレコードと一致した場合、アービターは
  重複を挿入する代わりに既存レコードを*上書き (supersede)* するため、同じツールの繰り返しの
  失敗は単一の・常に最新の記憶行に集約されます。
- **軽量な妥当性検査。** ツール由来の候補は永続化前に妥当性ゲートを通過する必要があります：
  タイトルに記されたツールが実際にそのターンで呼び出されていること、そしてコンテンツが
  定型の失敗テキスト以上を含んでいることです。ゲートを通過できない候補は即座に棄却されます。

### ツール選択における失敗フィードバック

想起側がこのループを閉じます：`ene-rag` のツール選択パイプラインは、アクティブなキャラクターに
対して最近失敗したツールの重みを下げることができます。最近の失敗は
`ene_core::ToolFailureSignalPort` 抽象（`ene-store` が実装）経由で読み取られ、設定可能な
ペナルティ（`tools.rag.use_failure_feedback` / `tools.rag.failure_penalty`）がランキング前に
そのスコアへ適用されます。これにより `ene-rag` は永続化への依存を持たないまま、繰り返し失敗する
ツールをランキング内で沈ませることができます。
