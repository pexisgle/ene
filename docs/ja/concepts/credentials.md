# 資格情報

Ene は、プラグインが外部サービスと通信するために必要な資格情報をホスト側で
管理します。プラグインは `x-ene-credentials` で必要なものを宣言し
（[プラグインと MCP](plugins-and-mcp.md) 参照）、ホストが値の解決・スコープ
判定・監査・保管・自動更新・失効を担います。プラグイン自身が生のシークレット
を扱うことはありません。

## 種別

- **API キー** — 設定（`plugins.list.<id>.config.api_key`、
  `ai.providers.<alias>.api_key`、または `{ID}_API_KEY` 環境変数）から
  ホストが解決する静的シークレット。プラグインが宣言したヘッダーに注入します。
- **OAuth2** — 下記の認可フローで取得するトークン一式。公開
  `client_id` が必要です（クライアントシークレットは同梱しません。デスクトップ
  アプリでは秘密にできないためです）。

## 認可フロー（Authorization Code + PKCE）

OAuth2 資格情報は [Authorization Code + PKCE](https://datatracker.ietf.org/doc/html/rfc7636)
フローで取得します。フローはすべてホストが駆動します。

1. プラグインが `request_authorization("google.calendar")` を呼ぶか、
   デスクトップの設定画面で **認可** ボタンを押します。
2. ホストは 256 ビットの PKCE verifier と S256 challenge を生成し、
   `127.0.0.1`（ランダムポート）に一時リスナーを bind して、認可 URL を
   システムブラウザで開きます。
3. ユーザーが同意すると、認可サーバーは `code` とフローの `state` を添えて
   ループバックコールバックへリダイレクトします。
4. ホストは `state`（128 ビット CSPRNG、使い捨て）を検証し、PKCE verifier
   付きで `code` をアクセストークン（発行されればリフレッシュトークンも）と
   交換します。
5. トークン一式を vault と永続化ファイルに保存し、リクエスト元プラグインへ
   無効化通知を送って再解決させます。

フローは帯域外（out-of-band）で進みます。ワイヤプロトコルは不変で、プラグインは
`request_authorization` に対して `AuthorizationPending` を受け取り、その後に
無効化通知、そして解決済みの資格情報を受け取ります。失敗・タイムアウト
（ブラウザ起動不可、state 不一致、サーバー拒否）でも無効化されるため、次の
resolve は資格情報を「存在しない」と報告します。

## 自動更新

resolve 時にアクセストークンが期限切れ（または期限 60 秒前）の場合、ホストは
宣言された `token_url` でリフレッシュします（`grant_type=refresh_token`）。
同じ資格情報への同時 resolve は 1 本の HTTP リフレッシュに束ねられます。
サーバーが新しいリフレッシュトークンを発行した場合は保存され（ローテーション）、
無ければ現行のものを維持します。`expires_in` を返さないサーバーのトークンは
期限不明となり、自動更新されません。

リフレッシュに失敗すると `RefreshRequired` が返り、資格情報サービスはそれを
`PluginError::authorization_required` に変換して UI に再認可を促します。また
その資格情報への再試行は 60 秒間拒否されるため、失効したリフレッシュトークンで
トークンエンドポイントを連打しません。

## 保管

トークンは **決して `settings.json` に書き込まれません**。
`<app_data_dir>/credentials.json` — ストレージキーから生の資格情報への JSON
マップ — に保存され、Unix では一時ファイル＋ rename による原子的書き込みと
所有者のみの権限（`0600`）が適用されます。永続化バックエンドはトレイトの背後に
あるため、将来 OS キーチェーンへ差し替えられます。

注意点:

- **Windows** ではファイルモードによる所有者限定は効きません。ファイルは
  ユーザーアカウント自体によってのみ保護されます。将来のキーチェーン
  バックエンドで解消されます。
- 破損したファイルは `credentials.json.bak` に退避され、ストアは空から始まり
  ます。読めないエントリ 1 件はスキップされ、致命的にはなりません。
- desktop と CLI が同じプロファイルを共有する場合、ファイルは
  last-write-wins です。
- アンインストールされたプラグインの資格情報は失効されるまでファイルに残り
  ますが、スコープ判定で到達不能（未宣言 ID は拒否）なので実害はありません。

## 管理

- **デスクトップ**: 設定の「資格情報」ページに、保存済みの全資格情報と宣言済み
  OAuth2 資格情報（ID・種別・期限・状態）が一覧表示され、**認可** / **取り消し**
  操作ができます。スキーマ駆動の汎用設定 UI に吸収されるまでの暫定ページです。
- **CLI**: 認可フローは CLI では実行できません（ブラウザが必要）。
  `/auth list`・`/auth status <id>`・`/auth revoke <id>` で端末から管理できます。

失効操作は、vault エントリの削除・永続化ファイルからの削除・クライアントへの
無効化通知をまとめて行います。

## 制限と将来課題

- **動的ポートのリダイレクト URI** には RFC 8252 §8.3 準拠の認可サーバー
  （Google・GitHub・Microsoft など大半が該当）が必要です。事前登録された固定
  リダイレクト URI しか受け付けないサーバーは非対応です。将来、宣言に
  `redirect_uri` フィールドを追加すれば対応できます。
- **デバイスコードフロー**は未実装です（現行の宣言に grant 種別の概念が
  ないため）。したがって CLI でのヘッドレス認可はできません。
- **OS キーチェーン**保管は平文ファイルの将来の置き換え先です。
- これらの優先度は、親の資格情報エピックの完了時に整理されます。
