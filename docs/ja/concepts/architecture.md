# アーキテクチャ

このページでは Ene の全体像を説明します: どんなプロセスがあり、各クレートが
何を担当し、チャットの 1 ターンがシステム内をどう流れるかです。

## 全体図

Ene は Cargo ワークスペースで、2 つのアプリケーション、ライブラリクレート群、
そして**プロセス外プラグイン**群から構成されます。

```text
┌────────────────────────────────────────────────────────────┐
│ ホストプロセス（ene-desktop または ene-cli）                │
│                                                            │
│  ene-runtime  ── アクターファサード（EneHandle）、イベント、ツール │
│    ├─ ene-mind      認知エンジン（プロンプト・メモリ・感情・   │
│    │                想起・プロアクティブ）                    │
│    ├─ ene-store     SQLite 永続化（唯一の DB 所有者）         │
│    ├─ ene-ai        プロバイダートレイト・ルーティング・リトライ │
│    ├─ ene-rag       スコアリング/減衰/ツール選択のポリシー層   │
│    ├─ ene-plugin-host  プラグインプロセス管理                │
│    └─ ene-connector 外部サービス資格情報・ゲート              │
└───────────────┬────────────────────────────────────────────┘
                │ IPC（長さプレフィックス付きフレーム、プロトコル v7）
┌───────────────▼────────────────────────────────────────────┐
│ プラグイン子プロセス                                        │
│  plugins/tool/*     ファイルシステム・web・ブラウザ・git・…   │
│  plugins/provider/* anthropic・openai・local-llm・kokoro・  │
│                      whisper・voicevox・…                   │
└────────────────────────────────────────────────────────────┘

ene-vrm（crates/ene-vrm）は ene-desktop だけが使う独立した
wgpu レンダラーです。
```

この設計を支える 2 つの原則:

1. **LLM は発話の生成器である。** 性格・記憶・感情・行動は Ene 自身の状態
   （`ene-mind` + `ene-store`）にあり、モデルの中にはありません。モデルを
   交換してもキャラクターの人格は変わりません。
2. **便利さより隔離。** プラグインは別プロセスで動き、データベースは
   1 クレートだけが所有し、パニック隔離により 1 つの障害がアプリ全体を
   落としません。

## クレートと役割

| クレート | 役割 | 依存してはいけないもの |
|---|---|---|
| `ene-core` | 永続化非依存のドメイン語彙（メモリ型・感情状態・約束・スケジュール）と `MemoryPort` トレイト | 内部クレートすべて |
| `ene-config` | 設定の読み書き・スキーマ・キャラクターカード・パス・プロンプトパック | — |
| `ene-mind` | 認知エンジン: プロンプト構成・想起計画・メモリ書き込み・感情・プロアクティブ・セッション | `ene-runtime`・`ene-plugin-host`・`ene-store`（本番コード） |
| `ene-store` | SQLite/SeaORM の**唯一の**所有者: スキーマ・マイグレーション・ベクトル検索・バックアップ | `ene-ai`・`ene-mind`・`ene-runtime` |
| `ene-ai` | LLM/埋め込み/STT/TTS/VAD プロバイダートレイト・タスクルーティング・リトライ・コンテキスト窓計算 | — |
| `ene-rag` | RAG ポリシー: ハイブリッドスコアリング・減衰・ツール選択（`tool` フィーチャー）・ワークスペースチャンク化 | `ene-store`・`ene-mind` |
| `ene-runtime` | アクターベースのホストファサード（`EneHandle`）・ターン制御・イベントバス・ツール・スケジュール・undo | — |
| `ene-connector` | 外部サービス接続フレームワーク: 資格情報・権限ゲート・webhook | `ene-config`・`ene-plugin-proto` |
| `ene-plugin-proto` | ワイヤ ABI: IPC プロトコル v7・ツール型・capability | ビジネスロジック |
| `ene-plugin` | プラグイン作成ファサード（`run_plugin_server`・トレイト・prelude） | `ene-runtime`/`ene-mind`/`ene-store` |
| `ene-plugin-macros` | プロシージャルマクロ: `ToolAction`・`ToolSpec`・プロバイダー derive | — |
| `ene-plugin-host` | プラグインプロセス管理・capability ルーティング・IPC プロバイダーブリッジ・MCP クライアント | — |
| `ene-plugin-db` | プラグイン用の型付き CRUD クライアント（ホストの DB へ IPC 経由） | — |
| `ene-infer` | シングルスレッドローカルモデルフレームワーク（ワーカースレッド・有界キュー・キャンセル） | — |
| `ene-voice` | ローカル音声エンジン（Whisper・Kokoro・Silero） | — |
| `ene-vrm` | VRM 1.0 ローダー + wgpu レンダラー | `ene-mind`/`ene-runtime`/`ene-store` |
| `ene-util` | 純粋ヘルパー（truncate・HTML→Markdown） | — |

フィーチャーフラグや依存エッジを含む完全な一覧は
[クレートリファレンス](../reference/crates.md) にあります。

## 重要なアーキテクチャ境界

- データベース接続を開くのは `ene-store` だけです。他のすべては
  `ene_core::MemoryPort`（mind・runtime）か、IPC ベースの `ene-plugin-db`
  クライアント（プラグインバイナリ）を経由します。
- `ene-mind` は `MemoryPort` に対してプログラミングし、`ene-store` を直接
  使いません（結合テストだけが両者を結びます）。
- `ene-rag` は両者の間に位置し、スコアリングと減衰は永続化・認知のどちらも
  再実装してはいけない純粋ポリシーです。
- ワイヤ ABI クレート（`ene-plugin-proto`）にビジネスロジックは置かず、
  ビジネスロジックがスキーマだけを宣言するプラグインバイナリに移ることも
  ありません。

## チャット 1 ターンの流れ

```text
1. ユーザーメッセージ → EneHandle::run（TurnId を返す。別ターン実行中は Busy）
2. ene-mind::before_turn
   - 感情状態を読み込み、現在時刻まで減衰
   - 想起計画（新メッセージからの意図）とハイブリッドメモリ検索
   - キャラクターアイデンティティ・lorebook・シーン要約・約束を読み込み
3. プロンプトパケットを構成
   - セクション化されたシステムプロンプト（アイデンティティカーネル・
     メモリ・ワークスペースチャンク・約束・文体例・出力契約）
   - モデルのコンテキスト窓に収まる履歴
4. LLM プロバイダーからトークンをストリーミング
   - 途中でツール呼び出しが実行されることがある（ファイル・web・…。
     権限ゲート付き）
   - アバター向けのパフォーマンスキューを発行
5. ene-mind がターンを確定
   - 感情提案（決定的 + 任意の LLM 分類器）
   - セッション履歴を ene-store にコミット
6. EneEvent::Terminal を発行。以降はバックグラウンドで遅延処理
   - メモリ抽出と仲裁（候補 → ストア or 承認キュー）
   - 忘却・減衰パス
```

詳細パイプラインは[認知ランタイム](../reference/architecture/cognitive-runtime.md)、
ホスト向け契約は [API v1](../reference/architecture/api-v1.md) を参照してください。

## プロセスモデルとフォールトトレランス

ホストはターン状態を Tokio アクターで管理します。すべてのコマンドと
バックグラウンドタスクは `catch_unwind` で包まれるため、1 つのコマンドの
パニックはログ記録（`DiagnosticEvent::ActorPanic`）にとどまり、アクターは
動き続けます。このためリリースプロファイルで `panic = "abort"` を指定しては
**いけません** — アンワインドこそが隔離を可能にします。

プラグインは管理される子プロセスです。ホストが起動 → IPC プロトコルを
ネゴシエーション → capability を登録 → ヘルスを監視 → 連続失敗時は
サーキットブレーカー付きで再起動します。

## 状態の置き場所

- `memory.db` — SQLite データベース（会話ログ・型付きメモリ+埋め込み・
  感情状態・約束・スケジュール・監査ログ）。`ene store backup` /
  `/store backup` でバックアップ。
- `undo.db*` — アクターの undo スタック。
- `assets/characters/<name>/` — キャラクターカードとそのアセット。
- `assets/models/` — ダウンロードしたローカルモデル（gitignore 済み）。

パスの詳細（デバッグ/リリース）は[設定](../configuration.md)を参照してください。
