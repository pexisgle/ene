# ローカル音声パイプラインと VRM 3D アバター描画

本ドキュメントでは、Ene のローカル音声処理エンジン (`ene-voice`) および 3D アバター描画システム (`ene-vrm`) について解説します。

---

## 1. ローカル音声パイプライン (`ene-voice`)

Ene はオプションで完全ローカルな音声対話パイプラインを提供します：

```text
マイク入力
  │
  ├─> 1. オーディオ録音 (cpal ストリームキャプチャ)
  ├─> 2. 発話区間検出 (Silero VAD、ONNX Runtime / ort)
  ├─> 3. 音声認識 STT (Whisper モデル、whisper-rs)
  │
  └─> LLM ターン処理
        │
        ├─> 4. 音声合成 TTS (TTS エンジン)
        └─> 5. オーディオ再生 & 口パク連動 (rodio)
```

### 構成要素
- **STT (音声認識)**: `whisper-rs` を用いたローカル Whisper モデルによる高速認識。
- **VAD (発話区間検出)**: ONNX Runtime (`ort`) 上で動作する Silero VAD によるリアルタイム発話判定。
- **TTS (音声合成)**: ローカル音声合成エンジンにより再生用 PCM バッファを生成。
- **オーディオデバイス**: `cpal` および `rodio` を介した低レイテンシ PCM キャプチャ・出力。

---

## 2. VRM 3D アバター描画 (`ene-vrm`)

`ene-vrm` は `ene-desktop` 内で VRM 1.0 3D モデルを表示するための独立した wgpu レンダラーです。

### アーキテクチャ上の完全な独立性
`ene-vrm` は `ene-mind`, `ene-runtime`, `ene-store` に**一切依存しません**。純粋なメッシュ、テクスチャ、ボーン変換行列、ブレンドシェイプウェイトのみを受け取ってレンダリングします。

### Performance キューのマッピング

会話ターン中、`ene-runtime` はチャットバス上で `EneEvent::Performance { turn, origin, cues, source }` をブロードキャストします。`cues: Vec<ene_mind::PerformanceCue>` は `ene-mind` の出力調停から得られます。各 `PerformanceCue` は種別 (`kind`: 表情 / 動作 / 視線 / キャンセル)、キューを識別する `name`、および種別ごとのフィールド (表情の場合は目標ウェイトと保持時間、動作の場合は `MotionLayer`) を持ちます。正確なフィールドは `cargo doc -p ene-mind --open` (`output::performance::PerformanceCue`) を参照してください。

`ene-desktop` はこれらの Performance イベントを受信し、VRM のブレンドシェイプおよびボーンアニメーションにマッピングして再生します。

### 表情の解決

ターン最終の表情は `ene-mind` の表情アービターが、優先度順に以下の3つのソースから決定します。

1. **LLM 提案** — チャットモデルの `<|perf:expr=…|>` マーカー（PHI モード）、または感情分類器の `recommended_expression`（感情モード）。どちらもプロンプトでカードの表情一覧を受け取り、その中の名前を正確に選ぶ必要があります（大文字小文字は区別しません）。一覧にない名前は受け入れられません（曖昧な文字列マッチングは適用されません）。拒否された提案は、affect 写像で得られる表情があればそれに、無ければ neutral（カードに neutral が無い場合は先頭の名前）にフォールバックします。
2. **感情写像** — LLM 提案がない場合、アービターは現在の感情状態を感情空間で*最も近い注釈付き表情*に写像します。注釈はカードの `extensions.ene.expressions[].affect` で表情ごとに定義します:

   ```json
   {
     "name": "にっこり",
     "vrm": { "happy": 1.0 },
     "affect": { "valence": 0.6, "arousal": 0.3 }
   }
   ```

   距離は `valence`, `arousal`, `irritation`, `fatigue` の4次元で計算します（欠損次元は `0.0` 扱い）。`affect` 注釈のない表情はこの経路では選択されません。組み込みのデフォルト表情には従来の閾値写像に近似する注釈が付与されているため、`extensions.expressions` を持たないカードは典型的な状態では従来どおり動作します（完全な等価は不可能です — 優先順位連鎖と最近傍は境界領域で食い違います。例: 中程度の irritation を伴う高い valence は、旧実装では angry、新実装では happy になります）。中性状態（全次元が `0.0` 付近）では原点付近の注釈 — カードの休息表情 — だけがマッチし、存在しない場合は感情的な表情を休憩時にまとう代わりに neutral へフォールバックします。
3. **neutral フォールバック** — 注釈付きの表情が存在しない場合（または表情一覧が空の場合）。

### 発話中の表情タイミング同期（TTS 同期）

TTS が有効な場合、表情マーカーは発話の**途中で**音声再生に同期してアバターの表情を切り替えます。

1. 各 `<|perf:expr=…|>` マーカーには、発話テキスト（マーカー除去後）上の文字位置がタグ付けされます（`PerformanceCue::text_offset`）。
2. TTS の文分割が、各マーカーをその文字範囲を含む文に対応づけます。文と文の間にあるマーカーは後続の文に適用され、自分の文が送信済みの後に届いたマーカーは次の文に適用されます。最後のテキストの後ろに残ったマーカーは、代わりにターン終了イベントで処理されます。
3. 文のキューは、その文の最初の PCM チャンク（`AudioChunk::cues`、専用オーディオチャンネル）に載せて送られます。デスクトップの再生経路は、その文の音声が再生を開始した時点で表情を切り替え、キューを感情パイプラインに予約します。パイプラインは `hold=秒数`（デフォルト 4 秒）を守り、その後フェードアウトします。次のマーカーが現在の表情を置き換えます。マーカーのない文は現在の表情を維持します（ホールドとフェードは継続）。表情マーカーを 1 つも含まない返答は、従来どおりターン終了時の解決に委ねられます。
4. マーカー由来の発話中切替はターン終了時のヒステリシスの対象外です（マーカー言語由来であり、affect アービター由来ではないため）。ターン終了時の解決は従来どおりです。
5. `cancel:expr` はタイミング付き経路を停止します。まだ TTS の文に紐づけられていないキューは破棄され、以降の表情マーカーは無視されるため、その発話の残りは現在の表情が維持されます。すでに音声チャンクに紐づけられたキューは再生時に発火し、表示中の表情は発話途中ではクリアされません。キャンセルはターン終了時の `EneEvent::Performance` に載って届き、その後デスクトップ側で予約済み・適用中の表情状態がクリアされます。

モーションと視線キューは従来どおりターン単位です。ターン終了時に `EneEvent::Performance` を通じて一度だけ適用されます。

**TTS が無効な場合**、同期すべき音声タイムラインが存在しないため、マーカーは従来どおりのターン終了時動作を維持します — ランタイムが蓄積し、表情アービターが単一の `EneEvent::Performance` に解決します。TTS 有効時と無効時で挙動が異なるのは設計上の意図です。

## 3. ビート同期: システム音声のリズム・スペクトラム連動アバターモーション

ビート同期 (Beat Sync) は、システムで再生中の音楽や動画に合わせてアバターを動かします。デスクトップが音声**出力**のループバックをキャプチャし、リアルタイムにビートを検出して、リズムに合わせてアバターの体を揺らします。

### 信号の流れ

```text
システム音声出力 (モニターループバック)
  │
  ├─> 1. ループバックキャプチャ (cpal、`desktop.beat_sync` 有効時)
  ├─> 2. FFT + 低域エネルギー onset 検出 (rustfft)
  ├─> 3. { bpm, intensity } パルス → ene-runtime チャットバス
  │      (EneEvent::BeatPulse、EneHandle::report_beat_pulse 経由)
  └─> 4. ene-vrm BeatSway: 手続き的な体の揺れ + VRMA 速度同期
```

### 検出アルゴリズム

低域（キック帯域）に対するエネルギー onset 検出を使います。

1. キャプチャストリームは ~250 Hz の 2 次 Butterworth ローパスフィルタを通し、帯域外成分が解析帯域に漏れないようにします。
2. 約 21 ms ごとに Blackman-Harris 窓の 4096 点 FFT を計算し、≈20–150 Hz 帯域（DC 除く）の平均振幅をフレームエネルギーとします。
3. エネルギーが緩やかな指数平均を一定のマージンで上回り、キック帯域が 500 Hz 以下のエネルギーの 40% 以上を占め（ハイハットや過渡音を抑制）、約 250 ms の不感期間を経過し、絶対フロアを超えたとき（無音では発火しない）に onset と判定します。
4. onset 強度は正規化されたエネルギー超過 `1 - 平均/エネルギー`（`[0, 1]` にクランプ）、BPM は直近の onset 間隔の中央値から `60 / 間隔` として求め、60–180 にクランプします。

このエネルギー onset 方式は、自己相関やコームフィルタによるテンポ追跡よりも頑健で実装が単純なため採用しました。キック主体の音楽ではよく追従し、音声や静かな音声では onset なし（静止）に自然に劣化します。

### プラットフォーム対応

`cpal` にはループバック API がありません。Linux では `ALSA`/`PipeWire` のキャプチャデバイスを列挙するため、モニターソースが入力デバイスとして公開されている環境で動作します（`PipeWire` のモニターポート、`pipewire-alsa` から見える `PulseAudio` モニターソースなど）。デバイス選択順は次のとおりです。

1. `desktop.beat_sync.device` — 明示的なデバイス名の上書き。
2. デフォルト**出力**デバイス名を含む入力デバイス（`<出力>.monitor` 命名規則）。
3. 名前に "monitor" を含む任意の入力デバイス。

モニターデバイスが存在しない場合は警告をログして無効のままになります — デフォルトのマイクにフォールバックすることはありません。Windows はクロスコンパイルのみの対象です。WASAPI にはモニター型の入力列挙がないため、この機能は無効に劣化します。

### アバターの反応

- **手続き的な揺れ**（`ene-vrm::beat_sync::BeatSway`、追加アセット不要）: 腰・背骨・胸・頭にビート同期した回転（最大約 4°）を合成。各パルスで位相をリセットし、ビート間は強度エンベロープが減衰します。
- **ロコモーション速度同期**: ビートがアクティブな間、再生中の VRMA クリップの `VrmaPlayer.speed` を `BPM / 120`（0.85–1.2 にクランプ）でスケーリングし、歩行・ダンスクリップをテンポに追従させます。
- パフォーマンスキュー（`EneEvent::Performance`）には影響しません。揺れは VRMA リターゲット**後**・スキンパレット生成**前**に加算合成されるため、LLM / affect パイプラインが選んだモーションの上に常に重なります。

### 設定

`desktop.beat_sync.enabled`（既定値 `false` — 既定でシステム音声をキャプチャするのはプライバシー上好ましくないため）と `desktop.beat_sync.device`（任意の上書き）があります。機能ページのトグルで有効/無効を切り替えると、アプリ再起動なしでキャプチャスレッドが開始・停止されます。ビート同期にはデスクトップの `voice` ビルド機能（マイクキャプチャや TTS 再生と同じ cpal/ALSA ツールチェーン）が必要です。
