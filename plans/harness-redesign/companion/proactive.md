# 能動発話

> 実現する要件: **P-105**(能動発話)、**P-106**(静寂の同居)、
> **P-112**(画面の視覚認知のうち観測経路)、**P-524**(補助LLM)、
> P-306(疲労・quiet hours のゲート入力)。参照: D-14、D-16。
> スケジュール発火は **P-606 の所有者**
> ([../tasks/jobs-and-schedules.md](../tasks/jobs-and-schedules.md) §3)であり、
> このパイプラインの入力ではない。

ユーザー発話なしにコンパニオンが起こすターン。

**この設計は現行実装(`ene-mind/src/proactive/`)を正とする**(D-28)。
当初の下書きは「一定間隔ごとに話しかけるか判断する」時間駆動モデルだったが、
実装は既にイベント駆動で、決定的ゲート・世界状態の傾向分析・
二段のモデル確認を持っていた。設計書の側が後退していたので、実装に合わせる。

## 1. 設計の要点

**ほとんどの観測では発話しない。** 重要なことが起きたときだけ話す。
これは頻度の調整ではなく、パイプラインの各段が独立に沈黙を選べる構造から来る。
どの段も**失敗時は沈黙**に倒れる(fail-closed)。「判断できなかったから話す」は
起きない。

段の数が多いのは、**高い段ほど高価だから**である。安いゲートで大半を落とし、
残りだけを小さなモデルに見せ、さらに残ったものだけがメインモデルに届く。

```text
観測(数十秒〜数分間隔)
  ├─ 活動シグナル(アイドル秒数・フォーカス中のウィンドウ・直近の切り替え)
  ├─ 画面要約(補助LLM。D-16 の観測経路)
  ├─ 約束の期限接近・記憶の再浮上
  └─ ユーザーからの明示指示(「これ終わったら教えて」)
        ↓
世界状態メモリ(有界リング・非永続)
  └─ 傾向要約(アイドル傾向・ウィンドウ切替回数・没入しているか)
        ↓
決定的ゲート(§3)
  └─ 不通過ならここで終わり。モデルを一切呼ばない
        ↓
決定(ローカル小モデル、§4)
  └─ should_speak / confidence / topic_hint / urgency
        ↓
統合確認(メインモデル、§5)
  └─ 拒否トークンなら可視テキストが出る前にストリームを中止
        ↓
発話(TurnOrigin::Proactive のターン)
```

スケジュール/リマインドの発火は `TurnOrigin::Scheduled` であり、
このパイプラインを通らない。発火と quiet hours の繰り下げは
[../tasks/jobs-and-schedules.md §3](../tasks/jobs-and-schedules.md#3-スケジュールp-606)
が所有する。二重ゲートしない。

## 2. 観測と世界状態

### 2.1 観測(observation)

ホストが観測間隔ごとに1件作る。中身は次のとおり。

| 要素 | 内容 |
|---|---|
| 活動シグナル | アイドル秒数、フォーカス中のウィンドウのラベル、直近の切り替え内容 |
| 画面要約 | 補助LLM が画面から作るテキスト要約。利用可否は状態として持つ(有効/無効/取得失敗) |
| セッション沈黙 | 最後のユーザー発話からの経過秒数 |

ウィンドウのラベルは**プライバシー安全な形**に落とす(アプリ名と、
必要なら伏字化したタイトル)。生のタイトルをそのまま持たない。

### 2.2 画面要約はツールではない(D-16)

画面を「見る」経路は2つあり、これは**観測側**である。

| | モデルが呼ぶ「見る」 | ハーネスが「観ている」(ここ) |
|---|---|---|
| 実装 | 通常のツール(アウトプロセス) | 補助LLM(ホスト内) |
| 起動 | モデルの tool call | ハーネスの定期観測 |
| 出力 | 画像。会話履歴に入る | 要約テキスト。履歴に積まない |

観測側をツールで実装できない理由は3つある。第一に、ツール呼び出しは
ターンの中でしか起きないが、この観測はターンの外——ユーザーが何も
していないとき——に走る。第二に、観測結果を毎回画像として履歴に積むと
コンテキスト窓が数分で溢れる。第三に、生画像を毎分クラウドへ送るのは
コストとプライバシーの両面で持続しない。

ただし「生画像をクラウドに出さない」は不変条件ではなく、頻度に応じた既定である
(D-17)。観測経路の既定はローカル要約だが、設定でクラウドを選べる。

### 2.3 世界状態メモリ

観測は有界リングに積まれ、**永続化しない**。1点の観測では
「ずっと同じ作業をしている」と「たまたま今この画面」を区別できないので、
傾向を見るために数点を保持する。

リングから作る傾向要約は次を含む。

| 項目 | 内容 |
|---|---|
| アイドル傾向 | 上昇 / 下降 / 横ばい / 不明 |
| ウィンドウ切替回数 | 直近区間での切り替え数 |
| 没入しているか | 切り替えが少なく操作が続いている状態 |
| 最新のウィンドウ | プライバシー安全なラベル |

**画面要約はリングに保存しない。** 判断ごとに取り直して捨てる。
ウィンドウラベルより機微度が高く、蓄積する価値に見合わないため。

## 3. 決定的ゲート

ここを通らなければ**モデルを1回も呼ばない**。コストのかかる判断は
必ずゲートの後に置く。

| ゲート | 説明 |
|---|---|
| 有効性 | 能動発話そのものが無効化されていないか |
| クールダウン | 前回の能動発話からの最小間隔 |
| 最小アイドル | ユーザーが無操作になってからの時間 |
| quiet hours | 曜日別の時間帯と抑制ポリシー(一切話さない / 重要なものだけ) |
| 疲労 | 感情モデルの fatigue が高いと話しかけ頻度を落とす |
| 一時停止 | 「静かにして」で明示解除まで停止 |
| ソースの有無 | 話す材料が1つもない場合 |

閾値の具体値は設定であり、実装しながら決める(D-29)。
**キャラクターごとに上書きできる**——よく話しかける人格と、
めったに口を開かない人格を、同じ機構で表現する。

## 4. 決定(ローカル小モデル)

ゲートを通った観測だけが、補助LLM(D-15、P-524)による判定にかかる。
安価で高速なモデルを使う。ここでの判定結果は次の形を取る。

| 項目 | 内容 |
|---|---|
| 話すべきか | 真偽 |
| 確信度 | 0.0〜1.0 |
| 話題のヒント | 何について話すか |
| 緊急度 | 低 / 通常 / 高 |
| 画面ダイジェスト | 診断用。**そのまま発話しない** |
| 理由 | 診断用。**そのまま発話しない** |

ダイジェストと理由を発話に流用しない理由は、これらが小型モデルの
生出力であり、キャラクターの声で書かれていないからである。
発話は §5 でメインモデルが改めて生成する。

確信度には閾値があるが、**閾値ちょうどで切り落とさない**。
設定閾値より少し低い「実効閾値」を別に持ち、その間の境界事例は
沈黙させずにメインモデルへ送る。小型モデルの確信度は粗く、
境界付近の判断を任せるには精度が足りないためである。
最終判断は §5 が行う。

失敗(モデルエラー・解析失敗・タイムアウト)はすべて沈黙。

## 5. 統合確認(メインモデル)

ここが二段目の確認で、**別の呼び出しを足すのではなく、発話生成そのものに
組み込む**。

メインモデル(会話用の高性能モデル。通常はクラウド)は、能動発話の
生成要求を受けたとき、2つの選択肢を持つ。

- **受理**: そのまま発話を生成する。ストリームが可視テキストを出し、
  ターンが成立する。
- **拒否**: 拒否トークンを返す。ハーネスは**可視テキストが1文字も出る前に**
  ストリームを中止し、ターンは発話なしで終わる。

この形にする利点は3つ。追加の往復が要らない。判断材料が生成時の
フルコンテキスト(人格・感情・記憶・直近の会話)であり、小型モデルが
見ていたものより豊かである。そして「話すと決めたが、書き出してみたら
言うことがなかった」を拒否として扱える。

可視テキストが出ないまま終わった場合(空応答・マーカーのみ)は、
受理でも拒否でもない第3の状態として区別して記録する。診断上、
モデルが明示的に断ったのか、単に何も出さなかったのかは別の問題だから。

## 6. ソースと優先度

| ソース | 内容 | 優先度 |
|---|---|---|
| 約束の期限 | 期限接近・確認待ちの再浮上 | 高 |
| ユーザーの明示指示 | 「これ終わったら教えて」等 | 高 |
| 画面・活動の変化 | 長時間の同一作業、離席からの復帰、注目すべき画面の変化 | 中 |
| 会話 | 途切れ・未完の話題 | 中 |
| 記憶 | 「そういえば」 | 低 |

複数のソースが同時に成立する場合は、優先度の高い1つを採用し、
残りはキューへ回す(保持期間は設定)。

ユーザーの明示指示は、モデルが自由に解釈するのではなく、
**信頼された入力**として決定コンテキストに載る。ユーザーが
「教えて」と言ったものを、モデルの裁量で握り潰さないため。

## 7. 静寂の同居(P-106)

- 能動発話が起きない時間は「不在」ではなく「同居」として扱う。
- body は静寂中でも最小限の生命感を持つ: 瞬き・呼吸・軽い視線移動、
  ユーザーの大きな入力への軽い反応(顔を向ける等)。
  これらはターンを起こさない **body の自律アニメーション**であり、
  感情状態を弱く反映する([../body/body-and-performance.md](../body/body-and-performance.md))。
- 静寂の長さ自体を内面チャネルに記録しない(ノイズの抑止)。

## 8. 設定キー

具体的な数値は実装しながら決める(D-29)。
`mind.proactive.*` の多くは**キャラクターごとに上書きできる**。

| キー | 説明 |
|---|---|
| `mind.proactive.enabled` | 全体の有効性 |
| `mind.proactive.observation_interval` | 観測間隔 |
| `mind.proactive.cooldown` | 前回発話からの最小間隔 |
| `mind.proactive.min_idle` | 最小アイドル時間 |
| `mind.proactive.quiet_hours` | 曜日別に上書き可能 |
| `mind.proactive.quiet_policy` | 一切話さない / 重要なものだけ |
| `mind.proactive.min_confidence` | 決定モデルの確信度閾値 |
| `mind.proactive.confirmation` | メインモデルによる統合確認を行うか |
| `mind.proactive.sources.*` | ソースごとの有効性(画面要約を含む) |
| `mind.proactive.world_state.capacity` | 世界状態リングの保持数 |
| `mind.proactive.max_screen_summary_chars` | 画面要約の切り詰め長 |

## 9. 障害モード

すべて**沈黙に倒す**。判断できないときに話すことはない。

| 障害 | 挙動 |
|---|---|
| 画面要約の取得失敗 | その要素なしで続行(状態として記録)。他のソースがあれば判断は続く |
| 決定モデルの失敗・解析失敗・タイムアウト | 沈黙。ライフサイクル警告 |
| メインモデルが拒否 | 可視テキストが出る前にストリーム中止。ユーザーには何も起きない |
| メインモデルが空応答 | 受理・拒否と区別して記録し、発話なしで終わる |
| quiet hours 中 | ポリシーに従って抑制。スケジュール発火の繰り下げは jobs-and-schedules 側 |
| クールダウン中のユーザー発話 | 能動発話を抑制(ユーザー発話が常に優先) |
| 対話レーン塞がり | 能動発話はキューへ。塞がりが長ければ破棄(古い判断材料で話さない) |
