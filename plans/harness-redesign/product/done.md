# 完成の定義

> 「何が揃えば完成と言えるか」を定義する唯一の文書。
> 機能 ID は [features.md](features.md) に従う。位置づけは [vision.md](vision.md)。

## 構造

- **ビジョン**: プロダクトの到達点(この文書の §2)。段階に依存しない。
- **v1.0 = 完成**: 観察可能な受入条件で定義する。これを満たせば「完成した」と
  宣言できる。
- **後継マイルストーン**: 完成定義の外だが、形式が支える機能群。
- **非目標**: やらないこと。

## ビジョン(到達点)

ユーザーのデバイスに、**複数の AI コンパニオン**が住んでいる。

コンパニオンはそれぞれ独立した人格と感情を持ち、音声とテキストで全二重に
会話できる。記憶も基本は独立だが、ユーザー自身についての知識は全員が共有する。
入力は表層の soul が受け、簡単なことはその場で片付け、複雑な作業だけ裏層の
ハーネスへ託す。両層はメッセージで進捗を共有し、ユーザーからは1体として
見える。何も頼まれなければ、たいていは静かに寄り添い、
重要なことが起きたときだけ自分から話しかける。

すべてはユーザーのデバイスで完結し(ローカルファースト)、ツール実行は
サンドボックスと承認ポリシーに守られている。キャラクターはパッケージとして
配布・交換でき、ユーザーは soul と body を自由に組み替えて自分だけの
コンパニオンを作れる。

## v1.0 = 完成

### 総括条件

次の状態が**同時に**成り立つとき、v1.0 は完成である。

1. desktop(stage)+ CLI + Web の3クライアントが、同一のコアデーモンに
   接続して使える。
2. 1体以上のコンパニオンが、以下の受入条件をすべて満たす。
3. ローカルモデル構成でネットワークなしに §受入条件 の会話が成立する
   (オフライン可)。
4. Linux 開発機で `nix develop` からビルド・起動でき、
   [platform/process-model.md](../platform/process-model.md) が定める
   性能の観点(常駐時のメモリ・起動時間・軽量ツールの往復)で許容できる。
   具体的な数値は実装しながら決める(D-29)。
5. 監査ログ・バックアップ・エクスポートのデータ保全系が動作する。

### P-1xx 会話と存在感の受入条件

- [ ] 話しかけると、**発話を遮って**割り込める。遮られた応答は中断として
      記録され、続きを話せる(または自然に新しい話題に移る)。
- [ ] コンパニオンの声に自分の声が混ざらない(自声回避)。
- [ ] テキスト入力でも同じセッションに会話でき、音声とテキストの履歴が
      1つのセッションログに統合される。
- [ ] 内面(思考・感情表出)が**表層UIには出ず**、設定画面(またはそれに
      類する詳細画面)のセッションログでのみ読める(D-20)。
      表層に出す設定は無い。ライブの内面演出は無い。
- [ ] 放置しても、ほとんどの場合は何も起きない。重要なイベントが起きたときだけ
      能動発話がある(D-14)。完全に無効化でき、発話しやすさを設定で変えられる。
- [ ] 2体のコンパニオンが stage に**同時に表示**され、それぞれと別々の会話が
      できる(D-6)。
- [ ] セッションはアイドルタイムアウトと明示分割でのみ区切れる。話題が変わっても
      勝手に分割されない(D-8)。一覧・検索・再開・エクスポートができる。

### P-2xx/P-3xx 記憶と感情の受入条件

- [ ] アプリを再起動しても、前回の会話内容・学んだユーザー情報・約束を覚えている。
- [ ] 「〇〇は覚えていないで」と言うと該当記憶が消え、削除が監査に残る。
- [ ] 数日の使用で、関係メトリクス(信頼・親密度)が応答トーンに反映される
      (感情の一貫性が観察できる)。
- [ ] 感情表出が表情・モーション・声のトーンに反映され、ちらつきがない。
      感情の内部状態(PAD 等)は詳細画面でのみ見える(D-19)。
- [ ] 片方のコンパニオンにユーザーの呼び名や好みを伝えると、もう片方も
      それを自分の知識として使う(共有記憶プール)。一方で、片方との
      個別の出来事や関係性はもう片方に漏れない(D-7)。
- [ ] 「これはみんなに覚えておいて」と言うと、抽出を待たず共有プールへ
      書き込まれ(`memory.write_shared`、P-212)、他のコンパニオンが
      自分の知識として使える。書き込みは監査に残る。
- [ ] 画面を「見て」もらう依頼が通り(ツール経路)、それとは独立に、
      何も頼まなくても画面の変化が能動発話の材料になっている(補助LLM 経路)。
      後者の観測結果が会話履歴を圧迫しない(D-16)。

### P-4xx 身体と表示の受入条件

- [ ] stage に VRM コンパニオンが表示され、発話にリップシンクし、
      感情で表情が変わり、視線と軽い仕草がある。
- [ ] soul と body を設定で組み替えられる(互換性警告が出る場合はその旨表示)。
- [ ] テキスト専用モードで、描画なしでも全会話機能が動く。

### P-5xx ハーネスの受入条件

- [ ] 音声でもテキストでも、入力は表層 soul だけが受け、裏層ハーネスへ
      直接届かない(P-522)。複雑な作業は表層が裏層へ託し、対話は止まらない。
- [ ] 「今何時?」「さっき何て言ったっけ?」のような簡単な依頼が、委譲を
      起こさずその場で返る(D-1)。応答に委譲の往復ぶんの遅延が乗らない。
- [ ] 表層に副作用のあるツールが1つも公開されていない(D-2)。
- [ ] 表層が簡単だと判断して始めた作業が実は複雑だったとき、ステップ数超過
      または副作用ツールの要求を機構が検出し、自動的に委譲へ切り替わる
      (D-3)。モデルの判断に依存していないことがテストで確認できる。
- [ ] 会話をしながら job を依頼すると、対話が途切れずに job が裏で進む。
      job の進捗が見え、完了時に**報告ターン**が届き、表層が成果物と
      報告の伝え方を判断する(発話/内面/静黙)。報告が対話を遮らない。
- [ ] job 実行中のキャンセルが効く。進行中の job に対して表層から
      追加指示・キューする補足(`message`)・質問回答ができ、裏層がそれを
      受けて挙動を変える。裏層の progress `message` は表層の会話を起こさない。
- [ ] ユーザーが話しかけ続けている間、委譲の完了報告は割込まず、
      会話の切れ目で届く(ユーザー発話が常に優先)。
- [ ] 表示の深さの検証テストに通る(D-11): 表層UI(stage・チャット)と
      エクスポート既定に、thinking・ツール引数原文・ツール生出し・
      子セッションのコンテンツが1件も出ない。internal 委譲の存在を示すものが
      表層UIに出ない(承認ポップアップの匿名化を含む)。
      同じ情報が**詳細画面では見える**ことも、同じテストで確認する。
- [ ] 子の質問が24時間未回答のとき、子は仮定を置いて進み、
      その仮定を報告する(停止して腐らない)。
- [ ] 1つの委譲から複数の質問が同時に来たとき、親は1ターンに
      結合して尋ね、回答をそれぞれ届けられる。
- [ ] 委譲が孫委譲を起こせる(再帰)。深さガードが資源を守る。
      internal の子孫はユーザーから見え続け、internal の子から
      public の孫は作れない(秘匿の連鎖)。
- [ ] 長時間の会話がコンテキスト窓を溢れても、compaction で会話が継続し、
      「さっき言ったこと」の要点が残っている。
- [ ] セッションログが `model-visible = logged` 不変条件の検証テストに通る。
- [ ] セッションの任意時点から fork でき、元のセッションが無傷で残る。
- [ ] job 実行中にコアデーモンを強制終了(`kill -9`)し、再起動すると、
      中断された job が検出され、後始末された上で、コンパニオンが中断を
      ユーザーに報告する。**沈黙のまま消えない**(D-5)。
      未消化のユーザー発話・委譲報告・ask-user 質問はログから見え、
      中断報告の材料になる。それらを入力にモデルを回して作業を
      続けることはない。
      重複効果なしの再開は v1.0 では保証しない(P-525 は後継)。
- [ ] 単なるツール呼び出しの失敗は、中断とは区別して失敗として報告される。
- [ ] LLM の使用量(トークン数・コスト)を soul/セッション/期間単位で
      集計して見られる。応答があるのに台帳に行がない、または台帳に
      行があるのに確定した試行がない、が起きない(台帳完全性)。
- [ ] CLI の `ene debug spans` で、直近のターン/ツール/コミットの
      計測を閲覧できる。スパン属性にプロンプト等のコンテンツが
      一切載らないことが CI で検証されている。
- [ ] アプリを更新してストレージ形式が変わったとき、既存セッションが
      起動時の連鎖マイグレーションで開ける。開いている job が途中で
      あっても、更新後に中断として確定し、ログから「途中だった」ことが
      見える。実行は再開しない(D-5)。古いバイナリが
      新しい形式のデータを開こうとすると拒否される。

### P-6xx ツールと仕事面の受入条件

- [ ] 「明日の午後3時に〇〇を思い出させて」がスケジュールされ、時刻に
      リマインドが来る(quiet hours をまたぐ場合は次可能な時刻に繰り下げ)。
      `important` のスケジュールは quiet hours 中でも発火する。
- [ ] 「このテーマで調べてしおりにまとめて」が workflow として走り、
      Markdown/テキスト成果物が交付される。
- [ ] MCP サーバーを1つ、プロファイル行への手書き設定で接続し、
      そのツールを対話から実行できる。内製ツールと MCP ツールが
      同じパイプラインを通る。設定画面からの導線 UI は後継(P-616 / D-23)。
- [ ] skill を1つ導入し、該当する依頼で使われる。
- [ ] `fs` / `exec` と MCP の git サーバーで簡易なコーディング作業が完遂できる。
      `exec` が `fs` とは別の承認ポリシーで扱われる(D-24)。
- [ ] 巨大なツール出力(例: 長いファイル)が spill され、会話が壊れない。
- [ ] job の進捗と完了が、進捗バーやシステム通知ではなく**コンパニオンの発話**
      として届く(D-13)。ユーザー向けの呼称が一貫して「タスク」である(D-12)。

### P-7xx プラットフォームの受入条件

- [ ] desktop を起動するとコアデーモンが自動起動し、stage が使える。
- [ ] CLI からコアデーモンを直接起動し、テキスト対話・ツール一覧・
      セッション操作ができる。desktop 専用の機能が CLI 経由で
      できないことはない(API 面の対等性)。
- [ ] Web から(同一 LAN の)コアに接続し、テキスト対話ができる。
      Web からも詳細画面を開け、内面・thinking・タスク一覧・記憶の閲覧が
      できる(D-31)。設定変更と記憶の削除は Web からはできない。
- [ ] 詳細画面から、セッションログ上の内面・ツール呼び出し・層間メッセージ・
      thinking・感情の内部状態を確認できる(P-712)。内面のライブ演出はしない。
      desktop は別ウィンドウ。
- [ ] desktop が WebView を一切使っていない(D-21)。
- [ ] 2つのクライアントが同一セッションに同時接続でき、排他資源
      (音声入力・承認応答)が調停される。
- [ ] 設定変更(JSON/環境変数)が反映され、スキーマが自動生成される。
- [ ] バックアップ取得と復元がデータ欠損なくできる。

### P-8xx キャラパッケージの受入条件

- [ ] Ene 正規形式のパッケージをインストールし、キャラを表示・会話できる。
- [ ] V3(PNG)カードをインポートし、正規形式へ変換して使える。
- [ ] キャラをエクスポートし、別環境でインポートして再現できる。
- [ ] soul 単独・body 単独のファイルを組み合わせて1キャラを作れる。

### P-9xx 安全とプライバシーの受入条件

- [ ] プラグインがサンドボックス外へ出ていけない(Landlock/bwrap 下で検証)。
- [ ] ファイル書き込みツールが、承認ポリシーに従って自動実行/確認される。
- [ ] 「次から確認しないで」でポリシーが追加され、次回から自動実行される
      (変更はユーザー確認+監査ログ付き)。
- [ ] AI 自動承認モードで、承認判断の理由が監査ログに残る。
- [ ] 資格情報がボールトに暗号保管され、プラグインプロセスの環境変数に
      平文キーが漏れない。
- [ ] ローカルモデル構成で、外部通信ゼロで会話・記憶・スケジュール・
      ローカルツールが動作する。

### P-10xx 拡張性の受入条件

- [ ] プロファイル切り替えで起動プラグイン集合が変わる。
- [ ] Rust 以外の実装言語で書いたダミーツールプラグイン(IPC 規約準拠)が
      登録・実行できる。
- [ ] ビルトインツールとサードパーティツールが**同じ API** に載っている
      (D-10)。`fs` と同等の機能を持つツールを、コアに手を入れずに
      サードパーティとして書けることが確認できる。
- [ ] ツールプラグインが provider 副プロトコル(音声・埋め込み等)を
      知らなくてもビルドでき、provider 側にモダリティを1つ足しても
      既存のツールプラグインが失効しない(D-22)。
- [ ] プラグインがクラッシュしてもカーネルは生き残り、サーキットブレーカーが
      作動する。

## 後継マイルストーン

v1.0 の完了定義には含めないが、**形式が支える**(既存形式の破壊を強制しない)。

| マイルストーン | 内容 | 支える形式 |
|---|---|---|
| M1 モバイル | スマホアプリ。ホスト型かクライアント型かは未定。 | server-api・SDK・音声ストリーミング |
| M2 コミュニティ配信基盤 | キャラ・プラグインの一覧/ダウンロード/評価/更新と、署名による検証(D-26)。 | パッケージ配布仕様(署名を後から足せる形) |
| M3 高度な複数体 | 同室会話(P-114)、複数体の協調表示。 | セッションログの room 拡張、body 契約 |
| M4 デスクトップペット | 透過・最前面・クリックスルー常駐。 | stage の表示抽象 |
| M5 カメラ認知・Live2D | カメラからの認知(P-115)、Live2D body(P-408)。画面の認知は v1.0(P-112)。 | capability seam、body 形式の拡張性 |
| M6 メモリ暗号化 | 保存時暗号化(P-214)。 | ストア抽象 |
| M7 重複効果なしのクラッシュ回復 | 3ストア・effect sandwich・OperationState による、任意のクラッシュ位置からの再開(P-525、D-4)。 | v1.0 のログ形式(後付けを妨げない構造) |
| M8 MCP 接続導線 | 設定画面から代表的な MCP サーバーを選んで追加(P-616 / D-23)。 | プロファイル行の形式 |

## 非目標

設計に含めないもの。将来の方針転換にはビジョンの改訂を要する。

- **マルチユーザー共有サーバー**: 1デバイス=1ユーザー。アカウント・チーム・
  権限管理は作らない。
- **VTuber 配信連携**: OBS 連携・コメント読み上げ・同接機能は対象外
  (個人のコンパニオンであり、配信ツールではない)。
- **モバイル/クラウド同期のホスティング事業**: ローカルファーストであり、
  同期サービス自体の提供は非目標(形式上の余地は残す)。
- **コーディング特化 UX**: IDE 統合・diff レビュー UI・worktree 管理など、
  コーディングエージェント専用 UI は作らない(ツールとしてのコーディングは持つ)。
- **独自 LLM の開発・配布**: モデルはプロバイダ経由で利用する。
