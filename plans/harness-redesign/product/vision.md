# プロダクトビジョン

> 実装する前に、このアプリが「何であるか」を定義する文書。
> 機能目録は [features.md](features.md)、完成の定義は [done.md](done.md)。
> 用語の厳密な定義は [用語集](#用語集)にあり、以降の全設計文書はこの用語に従う。

## 1. 位置づけ

Ene は**ローカルファーストのパーソナル AI コンパニオン**である。

「エージェントハーネス」(LLM を道具として使って仕事をさせる枠組み)と
「コンパニオン」(人格・感情・記憶・身体を持ち、ユーザーと一緒に時間を過ごす存在)
の両立を設計の中核に置く。既存の参照実装は片方しか持たない:

| 系譜 | 代表 | 持つもの | 持たないもの |
|---|---|---|---|
| エージェントハーネス | [opencode](https://github.com/anomalyco/opencode)、[DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) | セッションランタイム、ツール実行、コンテキスト管理、サンドボックス | 感情、身体、能動発話、関係性 |
| AI コンパニオン | [AIRI](https://github.com/moeru-ai/airi)、[Open-LLM-VTuber](https://github.com/Open-LLM-VTuber/Open-LLM-VTuber) | アバター、音声対話、感情表現、能動発話 | 仕事の遂行能力、セッションランタイム、安全なツール実行 |

Ene の設計上の立場は次の通り。

1. **コーディング特化ではない。** コーディング(fs/exec/git)はツールの1種に過ぎない。
   主眼は**非コーディングタスク**(調べ物、文書・表の作成、スケジュール調整、
   リマインド、生活支援)と**「一緒に過ごす」存在感**にある。
   これは Claude Cowork や ChatGPT Work のような「裏で動くエージェント」の能力を、
   コーディングだけでなく日常全般に広げたものに相当する。
2. **コンパニオンが主体であり、2層で1体である。**
   ユーザー入力(desktop/web の**音声もテキストチャットも**)は、必ず表層の
   **soul**(AIRI / Open-LLM-VTuber に似た実装)が受ける。soul が「作業が必要」
   と判断したときだけ、裏層の**ハーネス**(opencode v2 / DeepSeek Harness に
   似た実装)へ託す。両層は [Codex](https://github.com/openai/codex) の
   multi-agent v2 のように相互にメッセージを送り、進捗を確認し合う。
   ユーザーが見るのは機構ではなく、**1体のコンパニオン**である。
3. **複数体。** コンパニオンは多数存在でき、各自が独立したメモリと人格を持つ。
   既定ではメモリを共有しない。共有は「共有スペース」による明示的なオプトインのみ。

## 2. 利用者像

- **主利用者**: 1人の個人ユーザー。自分の PC にインストールして使う(ローカルファースト)。
  マルチユーザー・チーム利用は非目標([done.md の非目標](done.md#非目標))。
- **使い方**:
  - デスクトップの stage にコンパニオンを表示し、音声とテキストで会話する。
  - 「旅行のしおりを作って」「この PDF を要約して」「明日の午後3時に会議の準備を
    思い出させて」のような非コーディングの仕事を依頼し、裏で進めてもらう。
  - 何も依頼しなくても、コンパニオンは能動的に話しかけたり、静かに寄り添ったりする。
- **スキルレベルを問わない。** CLI は開発・デバッグ用途であり、一般ユーザーは
  desktop(stage)と Web のみを使う想定で設計する。

## 3. 設計原則

以降の全設計文書で判断が割れたとき、この順で優先する。

1. **軽量であること。** メモリ・ストレージ・起動時間の予算を明示し
   ([core/ 系文書と platform/process-model.md](../platform/process-model.md#6-性能予算))、
   純 Rust カーネルで守る。プラグインはすべてアウトプロセスだが、
   IPC は MessagePack+FD 渡しのゼロコピー寄り設計で、軽量ツールも
   常用に耐える速度を出す。
2. **ローカルファースト。** 会話ログ・メモリ・設定はユーザーのデバイスに置く。
   クラウド LLM は「推奨される既定」だが、すべての LLM 呼び出しで
   ローカルモデルに切り替え可能であり、ローカル構成ではネットなしで全機能が動く。
   逆にすべての構成をクラウドLLMで動作させることも可能。
3. **内部複雑さのユーザー非表示。** 表層/裏層・層間メッセージ・サブエージェント・
   コンパクション・メモリ抽出などの機構は、ユーザーの視界から完全に隠す。
   参照: AIRI / Open-LLM-VTuber は「魂」だけが表に出て、機構は舞台裏にある。
4. **構成可能性。** プロファイル/バンドル/パッチの積み重ねで、起動する機能集合を
   構成できる(DeepSeek Harness の Cordis 構成に倣う)。ただしユーザーが触るのは
   粗いプリセットであり、詳細なパッチは開発者・高度ユーザー向けの機構である。
5. **安全の既定。** プラグインは原則としてファイル・ネットワーク・資格情報に直接
   アクセスできず、Broker 仲介と承認ポリシーを通る。自動承認は「確認の手間」を
   省くだけで、検証(署名・ハッシュ・サンドボックス)を無効化しない。
6. **イベントソーシングによる信頼性。** セッションで起きたことはすべて
   追記専用のログに記録され、UI・履歴・fork・リプレイはログから投影される
   ([core/session-log.md](../core/session-log.md))。「モデルに見えるものは必ず
   ログから再構成できる」は最上位の不変条件である。
7. **後方互換性の不在。** このアプリは未リリースであり、外部消費者はいない。
   設定・IPC・永続形式・CLI 面について互換性維持のための妥協はしない。
   きれいな設計を優先する。

## 4. 参照系譜からの採用方針

「何を借り、何を借りないか」を固定する。各採用点は対応設計文書で具体化する。

### opencode v2 から

- **採用**: System Context と Session History の分離、Context Epoch(プロバイダ
  キャッシュ基準点)の概念、巨大ツール出力の spill、HTTP API+生成 SDK+
  Embedded/Remote 二重モード → [core/context-assembly.md](../core/context-assembly.md)、
  [platform/server-api.md](../platform/server-api.md)。
  **裏層ハーネス**の実装性格(セッションランタイム・ツール実行・コンテキスト管理)。
- **不採用**: コーディング特化の前提(worktree・patch・git 中心のツール面)。
  ツールは非コーディングを含めた対等な capability として設計する。
  ユーザー入力がハーネスに直接入る構成も採用しない(入口は表層 soul)。

### DeepSeek Harness から

- **採用**: イベントソーシング・セッションログと `model-visible = logged` 不変条件、
  turn/step ループ、ToolDefinition(正規出力宣言+モデル非公開フィールドの分離)、
  waterfall/emit の2モードイベント、capability seam の3役割、guard・plan・goal・
  interaction plane、プロファイル/バンドル/パッチ構成 →
  [core/](../core/README.md)、[tools/](../tools/README.md)、[plugins/](../plugins/README.md)
- **不採用**: Cordis(TypeScript 前提のプラグインフレームワーク)そのもの。
  Rust で同等の「登録=巻き戻し可能な effect」という構成可能性を実現する。
  Web GUI を唯一のホストとする構成も採用しない(Ene のホストはコアデーモン)。

### Codex multi-agent v2 から

- **採用**: 親と子が同期 await せず、型付きエンベロープで相互にメッセージを
  送る通信。`NEW_TASK`(ターンを起こす委託/追加指示)、`MESSAGE`(ターンを
  起こさずキューする共有)、`FINAL_ANSWER`(終端報告)の3種を層間プロトコルの
  骨格にする → [core/delegation.md](../core/delegation.md)。
  両層が互いの進捗を確認でき、あわせて**1つのエージェント経験**になる点。
- **不採用**: ユーザーがサブエージェントを直接観察・操作する IDE 向け UX。
  暗号化ペイロードやオペレータ監査 UI。Ene では層間メッセージはセッション
  ログに通常の事実として残り、ユーザー可視チャネルには出ない。

### AIRI から

- **採用**: soul(魂・エージェント)と body(体・アバター)の分離、
  内面(思考・感情・行動)の可視化、stage 中心の UX、複数 body の舞台、
  イベント駆動のサーバーランタイム → [body/](../body/README.md)、
  [companion/inner-channel.md](../companion/inner-channel.md)、
  [platform/clients.md](../platform/clients.md)。
  **表層 soul** の実装性格(存在感・感情・会話が主、仕事の遂行は裏に置く)。
- **不採用**: ブラウザ(Electron/Tauri 上の Web 描画)専有の前提。
  Ene はネイティブ描画(VRM/wgpu)を維持するが、描画は body レイヤーに閉じ込める。

### Open-LLM-VTuber から

- **採用**: 全二重音声(割り込み・自声回避)、デスクトップペットの発想(後継)、
  エージェント実装の差し替え可能性、内面描写の表示 → [body/voice.md](../body/voice.md)、
  [core/agent-loop.md](../core/agent-loop.md)
- **不採用**: 単一コンパニオン前提、テキスト内感情キーワード埋め込みの表現方式。
  感情は構造化イベントとして扱い、テキストは発話に専念させる。

## 5. プロダクトの全体像

### 5.1 コアデーモン内の2層

コアデーモンは**唯一のホスト**である。ホストを表層と裏層に割らない。
各コンパニオンは、そのホストの中で次の2層として走る。

| 層 | 実装の性格 | ユーザー入力 | 責務 | 駆動するレーン |
|---|---|---|---|---|
| **表層 soul** | AIRI / Open-LLM-VTuber に似たコンパニオン実装 | **唯一の入口**(音声・テキスト・能動発話・スケジュール発火) | 会話、人格、感情、記憶、内面、能動発話、作業が要るかの判断、ユーザーへの伝え方 | 対話レーン(1本・単一フライト) |
| **裏層ハーネス** | opencode v2 / DeepSeek Harness に似た作業実装 | 直接は受けない。表層からの層間メッセージのみ | 調べ物・文書・ツール実行・job・サンドボックス。進捗と成果を表層へ返す | job レーン(複数・並行) |

両層は**同一のハーネスカーネル**(セッションログ・turn/step ループ・耐久性・
ツールレジストリ)の上に乗る。コードベースを二つに割る必要はない。違うのは
エージェントプロファイル(公開ツール面・コンテキスト・ターンの長さ)である。

接合規則:

1. **入口は表層のみ。** desktop / web / CLI からの発話は、モダリティ
   (音声・テキスト)を問わず対話レーンに入り、裏層へは届かない。
2. **作業は裏層へ託す。** 表層は副作用のある作業ツール(fs / exec / web /
   browser / 送信系)を持たない。会話を成立させる局所能力(記憶想起、時刻、
   内面、層間メッセージ)だけを持つ。作業が必要だと判断したら層間の
   `task` で裏層へ渡す。
3. **声は表層のみ。** ユーザーに向けた発話は対話レーンだけが発生させる
   ([core/invariants.md](../core/invariants.md) I-31)。裏層の出力が発話
   チャネルに直接出る経路はない。
4. **1体として成立する。** 裏層は表層と同じ soul の identity・記憶方針・
   skill を継承する。ユーザーから見れば「Ene(そのコンパニオン)がやってくれている」
   であり、内部の2エージェントではない。
5. **ハーネスは常駐の第二人格ではない。** 裏層はコンパニオンに属する能力の層
   であり、作業のたびに job レーン上の委譲として起きる。常時もう1つの心が
   ユーザーと並行会話することはない。

  │  web     │◄────►│    │ AIRI / OLV 系         │   Codex v2 風     │
  ├──────────┤  WS  │    │ 人格・感情・記憶・内面 │◄──────────────►┐  │
  │  cli     │◄────►│    │ 対話レーン(1本)        │  task/message/  │  │
  └──────────┘      │    └───────────────────────┘  final          │  │
                    │                                               ▼  │
                    │                            ┌─ 裏層ハーネス ───┐  │
                    │                            │ opencode / dsh 系│  │
                    │                            │ ツール・job・sandbox│ │

                    │   └─ ツールレジストリ(層ごとに公開面が違う)      │
                    │  実行系                                         │
                    │   ├─ プラグイン監督(全アウトプロセス)            │
                    │   ├─ Broker(資源仲介)・承認 plane               │
                    │   └─ サンドボックス                             │

                    ┌──────────────────▼──────────────────────────────┐

裏層は図の右側にあり、ユーザー入力の矢印は届かない。

### 5.3 層間メッセージ(Codex multi-agent v2 に倣う)

表層と裏層は、同期のツール結果待ちではなく、型付きエンベロープの送受信で
協調する。詳細なツール名と耐久化は [core/delegation.md](../core/delegation.md)。

| 種別 | Codex v2 の対応 | 方向 | 相手の扱い | 用途 |
|---|---|---|---|---|
| `task` | `NEW_TASK`(spawn / followup) | 表層 → 裏層 | **wake**(ターンを起こす) | 作業の委託、追加指示 |
| `message` | `MESSAGE` | **双方向** | **inject**(ターンを起こさない) | 進捗・補足・状況共有 |
| `question` | (v2 の質問面) | 裏層 → 表層 | **wake** | 表層(ひいてはユーザー)の判断が要る質問 |
| `answer` | `MESSAGE` / 応答 | 表層 → 裏層 | **wake** | 質問への回答 |
| `final` | `FINAL_ANSWER` | 裏層 → 表層 | **wake**(終端) | 完了・失敗。要約と成果物参照 |
| `cancel` | — | 表層 → 裏層 | **wake** | 協調的キャンセル |

「互いに進捗を確認する」の意味:

- 表層は裏層の状態を読める(`status`)。裏層は `message`(progress)で
  表層の次ターン境界に進捗を届ける。
- 裏層は、新しい `task` / `answer` / `cancel` が自分の inbox に来たかで
  表層側の方針を知る。**対話履歴そのものは既定で見ない**(表層が `excerpt`
  で選んだ文脈だけを見る)。
- どちらの層も、相手を同期 await しない。会話は裏層の作業で止まらない。

### 5.4 パッケージとの関係

キャラクターパッケージ([character/](../character/README.md))が配るのは
soul 定義と body であり、裏層ハーネスはパッケージに含めない。
ハーネスはコアデーモンがすべてのコンパニオンに付ける実行層である。
実行時の1体は「パッケージ由来の soul/body + デーモン由来の裏層」で、
ユーザー向けの名は**コンパニオン**である。

## 用語集

以降の全設計文書で使う用語の厳密な定義。opencode の CONTEXT.md に倣い、
「使わない言い換え」も指定する。

| 用語 | 定義 | 使わない言い換え |
|---|---|---|
| **コアデーモン** | 唯一のホスト。セッション・メモリ・ツール・プラグイン・音声と、各コンパニオンの表層/裏層を所有する常駐プロセス。desktop が起動する(開発中は CLI が起動する)。 | サーバー、バックエンド |
| **コンパニオン** | ユーザーから見える1体の存在。表層 soul・裏層ハーネス・結び付いた body の組。内部は2層だが、ユーザーには1つの Character として見える。 | キャラクター(パッケージ形式の文脈では使う)、エージェント |
| **表層(soul ランタイム)** | ユーザー入力の唯一の入口。AIRI / Open-LLM-VTuber 系のコンパニオン実装。人格・感情・記憶・能動発話・内面を駆動し、作業の要否を判断して裏層へ託す。対話レーンを持つ。 | フロント、チャットボット |
| **裏層(ハーネス)** | 表層が託した作業の実行体。opencode v2 / DeepSeek Harness 系の実装。ツール・job・サンドボックスを駆動し、層間メッセージで表層と進捗を共有する。ユーザー入力の入口ではない。 | サブエージェント(ユーザー向けに使わない)、ワーカー |
| **ハーネスカーネル** | 両層が共有するインフラ。セッションログ、turn/step ループ、コンテキスト組立、耐久性、ツールレジストリ。ホストそのものではなく、裏層ハーネスとも区別する。 | ハーネス(層を指すときは使わない) |
| **層間メッセージ** | 表層と裏層が送り合う型付きエンベロープ(`task` / `message` / `question` / `answer` / `final` / `cancel`)。Codex multi-agent v2 に倣う。ユーザー可視チャネルには出ない。 | RPC、コールバック |
| **soul** | 人格・感情・記憶方針・声・スキルを定義する永続エンティティであり、その表層ランタイム。body とは独立に存在し、交換可能。 | 魂、エージェント |
| **body** | アバター資産・表情/モーションカタログを定義する永続エンティティ。soul とは独立に存在し、交換可能。 | 体、アバター(表示装置の意味では使う) |
| **セッション** | 1体のコンパニオンに属する連続した会話。ログ・履歴・要約の単位。必ず単一の soul に属する。 | チャット、スレッド |
| **ターン** | 1回の発話の単位。ユーザー発話(または能動発話・スケジュール発火)+ 応答全体。`TurnId` を持つ。 | — |
| **ステップ** | ターン内の1回のモデル要求+それが呼ぶツール実行。ターンは0以上のステップから成る。 | イテレーション、ループ1周 |
| **レーン** | コンパニオン内の実行レーン。対話レーン(表層・1本・単一フライト)と job レーン(裏層・複数・並行)がある。 | スレッド、チャネル |
| **job** | 対話レーンの外で動くバックグラウンド作業。実体は委譲の public モード。進捗・成果物・ライフサイクルを持つ。 | タスク(ユーザー向け UI では「おつかい」と呼ぶ) |
| **ワークスペース** | 内部概念。ジョブ・成果物・ファイルツールが根を置くディレクトリと設定の組。ユーザーには見えない。 | プロジェクト(opencode の意味では使わない) |
| **System Context** | モデルに「指示・状況」として提示される構造化コンテキスト。セッション履歴とは別の状態。 | システムプロンプト |
| **Session History** | セッションログから投影される、時系列の会話メッセージ列。 | セッションコンテキスト |
| **Context Source** | System Context を構成する1つの独立した型付き値。安定キー・codec・loader・レンダラを持つ。 | プロンプト断片 |
| **Context Epoch** | 1回レンダリングされた System Context が不変の基準点として有効な期間。コンパクション完了・セッション移動・非互換遷移で終わる。 | — |
| **compaction** | 履歴が窓を溢れる前に、古いメッセージを要約へ畳む処理。 | 圧縮(曖昧なので避ける) |
| **spill** | 巨大なツール出力をセッション履歴の外(ファイル)へ逃がし、履歴には要約と参照だけを残す処置。 | — |
| **seam** | 差し替え可能な能力の接合面。Service Definition(宣言)・Service Provider(実装)・Consumer(消費者)の3役割から成る。 | インターフェース(曖昧なので避ける) |
| **ツール** | モデルが Tool Calling で呼び出す能力。統一ツールレジストリに登録される。供給元(ビルトイン/プラグイン/MCP/委譲)は問わない。層ごとに公開面が違う。 | — |
| **Tool Calling** | モデルとハーネスカーネル間の呼び出し規約(モデルがツールスキーマを見て呼び出す機能)。LLM API レイヤー。 | ツール実行(実行はハーネスの責務) |
| **MCP** | 外部のツール/リソース/プロンプト供給元への接続規約(輸送・発見の標準)。供給元レイヤー。 | ツール(レイヤーが違う) |
| **内面チャネル** | soul の思考・感情表出・行動意図を、発話と分離して記録・表示する永続イベント列。 | 独り言(曖昧) |
| **能動発話** | ユーザー発話なしにコンパニオンが起こすターン。`TurnOrigin::Proactive`。 | — |
| **共有スペース** | 複数の soul がオプトインで読み書きできる命名メモリ領域。既定のメモリ非共有を崩す唯一の手段。 | 共通メモリ(曖昧) |
| **ボールト** | soul 専用のメモリ領域。他 soul から読めない。 | — |
| **Broker** | プラグインがファイル・ネットワーク・資格情報へアクセスする際の仲介 RPC。 | — |
| **承認 plane** | ツール実行の可否を決めるポリシー層(事前ポリシー・AI 自動承認・ポップアップ)。 | — |
| **プロファイル** | 起動するバンドルの積層リスト。`desktop`・`minimal` 等。 | — |
| **バンドル** | プラグインツリーに挿入される構成行+コードの配布形式。 | — |
| **stage** | desktop クライアントの、コンパニオンを表示する場(UX 名)。 | ウィンドウ(曖昧) |
| **artifact(成果物)** | job やターンが生成した、ユーザーに交付する物(文書・表・画像等)。 | — |
| **skill** | 手順+参照文書+任意のスクリプトを1パッケージにした、非コーディングタスクの手順知識。業界標準準拠。 | レシピ(口語では使う) |
| **レーンコマンド面** | レーンを駆動するコマンドの集合(prompt/steer/abort/resume 等)と受理/拒否・結果/エラーの契約。HTTP/WS はこの面の射影。ユーザー発話の `prompt` は対話レーン(表層)にだけ届く。 | API(曖昧) |
| **storage version** | セッション DB の永続形式のバージョン番号。オープン時の連鎖マイグレーションの基準。 | スキーマバージョン(曖昧) |
| **委譲(delegation)** | 表層が裏層へ実作業を移す非同期の機構。層間メッセージの実行面。internal モード=秘匿サブエージェント、public モード=job。表層は待たない。 | タスク(曖昧)、サブタスク |
| **報告ターン** | 裏層の完了・失敗・質問が、表層の対話レーンに届くターン(`origin: subagent`)。表層がユーザーへの伝え方を決める。 | コールバック(機構名は使わない) |
| **thinking** | プロバイダの reasoning 出力。ログには記録するが、ユーザー向け表示には出さない。内面派生の素材になる(既定)。 | 思考(内面の thought aspect と混同しない) |
| **出力秘匿** | LLM の生出力(thinking・ツール引数・生出し・子セッション)をユーザーに見せない既定。発話・内面・要約・成果物のみ可視。 | — |
