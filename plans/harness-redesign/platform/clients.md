# クライアント

> 実現する要件: **P-704**(desktop/stage)、**P-705**(CLI)、**P-706**(Web)、
> **P-707**(複数クライアント同時接続)、P-405(複数体表示の表示側)。

## 1. クライアントの役割分担

すべてのクライアントは [server-api.md](server-api.md) の同一 API を使う。
役割は「表示と入力の様式」の違いのみ。音声もテキストも、宛先は
**表層 soul の対話レーン**である。裏層ハーネスへクライアントから
直接入力する経路はない([../product/vision.md](../product/vision.md#51-コアデーモン内の2層))。

| クライアント | 役割 | 特徴 |
|---|---|---|
| **desktop(stage)** | 主クライアント。コアを起動し、コンパニオンを表示する場 | VRM 描画・ローカル音声デバイス・詳細画面・承認ポップアップの主表示先 |
| **CLI** | 開発・デバッグ・動作確認 | テキスト対話・セッション/ツール/プラグインの操作。desktop 専用機能がないことの検証手段(P-705) |
| **Web** | 外部からの接続クライアント | ブラウザでテキスト対話・音声(ブラウザのマイク)・詳細画面。描画は後継(テキスト+簡易表示) |
| **モバイル** | 後継(M1) | ホスト型かクライアント型か未定。API が同一なのでどちらにも対応可能 |

- **desktop 専用 API は存在しない**(確定済み)。desktop が持つのは
  「コアの起動・ローカルデバイス入出力・ネイティブ描画」であり、
  それらはクライアント側の責務として API の外にある。
- CLI はコアを起動できる(開発用)。desktop が起動したコアにも
  接続できる。

## 2. desktop(stage)の詳細

### 2.1 実装スタック(D-21)

**ネイティブ描画のみ。WebView は使わない。**

- UI は egui、描画は wgpu。VRM も同じ wgpu 上で描く
  (現行 `ene-vrm` を再利用、D-27)。
- WebView を使わない理由は、常駐アプリとしての起動時間・メモリ・
  配布サイズがこのアプリの価値に直結するため。デスクトップに
  ずっと居るものが数百 MB を占めるのは、軽量原則
  ([../product/vision.md §3](../product/vision.md#3-設計原則))と両立しない。
- この判断は egui で必要な UI(設定・記憶編集・詳細画面)が組めることを
  前提にしている。組めないと判明した場合は再検討するが、
  **その場合も WebView ではなく別のネイティブ GUI を検討する**。

### 2.2 責務

- **コアの起動**: desktop はコアデーモンを子プロセスとして起動し、
  ready イベントで API アドレス+トークンを受ける
  ([process-model.md §1](process-model.md))。desktop 終了時の
  コアの生存方針: 既定はコアも終了(`desktop.core_lifetime = app`)。
  常駐を望む場合は `detached` に設定可能。
- **描画**: VRM を wgpu で描画。
  body のキュー購読([../body/body-and-performance.md](../body/body-and-performance.md))。
- **音声デバイス**: ローカルのマイク/スピーカーをコアへ中継
  ([../body/voice.md §1](../body/voice.md#1-所有と配置))。
- **承認ポップアップの主表示先**(ただし応答は任意のクライアント可能、§3)。

### 2.3 表層UIと詳細画面(P-712 / D-11)

desktop は**2つの表示面**を持つ。

| 面 | 内容 |
|---|---|
| **表層UI**(主画面) | コンパニオンの姿と会話。作業中は1行の要約のみ |
| **詳細画面**(別ウィンドウ) | 設定・記憶編集・キャラ管理・タスク一覧、セッションログ(内面を含む)、thinking・ツール引数・生出し・感情の内部状態。内面のライブ演出はしない |

- 詳細画面を**別ウィンドウ**にするのは、主画面が「そこに居る」ための
  場所だからである。デバッグ情報をタブやパネルとして同じ窓に置くと、
  存在感の場が情報表示の場に変わる。
- 表示の深さの規則は [../core/visibility.md](../core/visibility.md)。
  何を出すかの判断はサーバ側で行い、クライアントのフィルタに依存しない。

## 3. 複数クライアントの同時接続と排他資源(P-707)

確定済み決定: **対等+排他資源のみ調停**。

- すべてのクライアントは対等に操作できる(送信・承認・キャンセル)。
- **排他資源**は調停する:

| 資源 | 調停規則 |
|---|---|
| 音声入力(マイク) | **アクティブデバイス 1 台**のみが VAD に入力する。他は送信できない(音声入力の競合・VAD 破損の防止)。アクティブはユーザーが切替、または「今このクライアントで話す」の明示で移動 |
| 音声出力(再生) | 主再生クライアント 1 台(通常 desktop)。他は購読のみで再生しない(エコー・二重再生の防止) |
| 承認応答 | 承認要求は**全クライアントに配信**され、最も早く応答したものが採用される。他には「解決済み」が同期される。応答の競合は先着+冪等キーで排除 |
| ask-user 応答 | 承認と同じ(先着採用) |
| OS 通知 | **出し手は1クライアント**(既定は desktop)。出し方はクライアントが決める(D-25)。コアは OS 通知 API を呼ばない |

- 排他資源の所有はコアが管理し、`client_id` で追跡。
  所有クライアントの切断時は資源を解放し、他クライアントが
  取得可能になる。
- 同一セッションの履歴・内面・ツール表示は全クライアントで同期
  (WS のイベント購読による)。

### 3.1 OS 通知(D-25)

現行 `utility.notify` の後継。モデルから呼ぶツールは持たない。

- コアは `notify.hint`(surface)を出すだけ。タイトルと短い本文、きっかけ
  (発話・承認・能動発話)。本文の本編は会話側(D-13)。
- desktop が既定の出し手。ウィンドウが非フォーカスのとき OS 通知にしてよい。
- Web はブラウザ通知(許可時)。CLI は出さない。
- 進捗バーやタスク完了のシステム通知には使わない。

## 4. Web の詳細(P-706)

- desktop がホストするコアに、同一 LAN・トンネル経由で接続。
- テキスト対話・タスク/成果物の閲覧・承認応答を提供。
- 音声: ブラウザのマイクを WS でコアへ送る(§3 の音声入力調停に従う)。
  再生は `audio.chunk` をブラウザで再生(Web が主再生になる場合がある)。
- **VRM 描画は後継**。v1.0 の Web はテキスト+簡易状態表示。
  body を持たないので、感情は body の emotion をそのまま簡易な
  テキスト表示にする(専用の表現体系は設計しない、D-19)。
- 内面・thinking 等は表層のチャットには出さない。**詳細の表示面は持つ**
  (D-31)。深さの規則は desktop と同じ
  ([../core/visibility.md](../core/visibility.md))。
  詳細面ではタスク一覧と記憶の**閲覧**、および内面・thinking・ツール引数・
  層間メッセージを見られる。設定変更・記憶の削除/編集・キャラ管理の変更は
  **desktop のみ**。
  v1.0 の Web に VRM は無いので、desktop のような別ウィンドウは必須ではない。
  UI の置き方(別ページ / 別パネル)はクライアントが決める。
  接続は面ごとに2本張る([server-api.md](server-api.md))。
- 認証はトークン+QR(接続の簡易化)。

## 5. CLI の詳細(P-705)

- コマンド群(現行の `/command` 系を発展):
  - `ene chat <soul>` — テキスト対話(REPL)
  - `ene session list/show/fork/export` — セッション操作
  - `ene session compact` — 手動 compaction([../core/lane-api.md](../core/lane-api.md))。`ene session resume` は後継(P-525)
  - `ene usage` — LLM 使用量の集計([../core/storage-model.md](../core/storage-model.md) §4)
  - `ene tool list/call` — ツール一覧・実行
  - `ene plugin list/restart` — プラグイン
  - `ene task list/cancel` — タスク(内部の呼称は job)
  - `ene memory list/edit/delete <soul>` — 記憶(scope の確認・変更を含む)
  - `ene schedule list/add` — スケジュール
  - `ene core start/status/stop` — コアの制御
  - `ene debug log/delegation/spans` — デバッグ。CLI は**詳細画面と同じ深さ**を
    扱える([../core/visibility.md](../core/visibility.md))。
    内面・thinking・ツール引数・生出しをここから見る
- CLI は「API でできること」の全操作を目標とし、
  desktop 専用機能が混入していないかの検証に使う。
- CLI の通常の対話出力は表層UIと同じ深さ(要約のみ)。
  深い情報は `--verbose` や `ene debug` の明示で出す。
  開発者向けだからといって既定を変えると、
  「表層に出ない」ことの検証手段にならなくなる。

## 6. 将来モバイルの接点(M1)

- API・SDK・音声ストリーミングが揃っているため、モバイルは
  「クライアント」として接続可能。ホスト型(スマホでコアを動かす)は
  プラットフォーム依存が大きいので、M1 で判断する。
- 接点の維持: モバイルの画面サイズを想定したイベントの
  粒度調整(通知相当のイベント種別)を後継で追加できるよう、
  `lifecycle.*` の拡張余地を残す。

## 7. 障害モード

| 障害 | 挙動 |
|---|---|
| desktop とコアの接続断 | 自動再接続(指数バックオフ)。不能なら「コアが応答しない」表示+再起動提案 |
| 2台が同時に音声入力しようとする | アクティブでない側は「音声入力は他クライアントが使用中」と通知 |
| 承認の同時応答 | 先着を採用。後着は「既に解決済み」を返す |
| Web の音声再生と desktop 再生の競合 | 主再生クライアントの指定で解決。指定なしは desktop 優先 |
| CLI のコア未起動 | `ene core start` を提案。接続先は設定/環境変数で指定可能 |

## 8. 設定キー

| キー | 説明 |
|---|---|
| `desktop.core_lifetime` | `app`(desktop と共に終了。既定)/ `detached`(常駐) |
| `clients.audio.active_policy` | 音声入力のアクティブ切替(`explicit`/`last_used`) |
| `clients.approval.broadcast` | 承認の全クライアント配信(既定 `true`) |
