# capability seam 群と MCP

> 実現する要件: **P-602**(内製ツール)、**P-603**(MCP)、
> **P-604**(MCP に委ねる外部連携)、**P-611**(コード実行)、
> **P-612**(コーディング)、**P-112**(画面の視覚認知)、
> **P-524**(補助LLM)、**P-1003**(プロバイダ seam)。参照: D-23、D-24、D-25。

## 0. 何を内製し、何を MCP に委ねるか(D-23)

内製を増やすほど保守対象が増える。判断基準は「成熟した MCP サーバーが
存在するか」と「ハーネス固有の要求があるか」の2点。

| 扱い | 対象 | 理由 |
|---|---|---|
| 内製 | `app`(GUI自動化・画面取得、§4) | MCP に等価物がなく、承認とサンドボックスが OS 依存。vision(§9)の素材でもある |
| 内製 | `fs`(§1) | `undo` が独自機構。承認モデルの中心 |
| 内製 | `exec`(§2。`fs` から分離) | D-24 |
| 内製 | `web`(§3) | 使用頻度が最も高く、鍵管理・レート制限・キャッシュをホスト側で持ちたい |
| 内製 | `utility`(§7) | モデルが自力では確実にできない決定的な計算(D-25) |
| MCP に委ねる | git・ブラウザ操作・カレンダー・Home Assistant・気象/位置 | 成熟した MCP サーバーが存在する。内製しても劣化版になる |
| 持たない | 状態付きのサンプルツール | 実用の需要がない |

MCP に委ねたものも、ユーザーから見れば同じツールである。承認・ガード・
spill は同一パイプラインを通る(§5)。

## capability seam の3役割(dsh に倣う)

差し替え可能な能力は必ず3役割で設計する。

1. **Service Definition**: インターフェース宣言(Rust トレイト相当の契約)。
2. **Service Provider**: 実装(ローカル実装 / プラグイン / リモート)。
3. **Consumer**: 使用者。大半はモデル向けのツール。

プロバイダを入れ替えると、消費者を分岐させずに製品全体が切り替わる。
例: fs の provider をリモートサンドボックスに向けると、
fs 系ツール・コード実行・成果物保管がすべて一緒に移動する。

## 1. fs seam

| 役割 | 内容 |
|---|---|
| Definition | `open_read/open_write/list/stat/watch/move/remove`。パスは正規化済みで受ける |
| Provider(既定) | ローカル FS。Broker 経由でプラグインに委譲([../plugins/broker.md](../plugins/broker.md)) |
| Consumer | `fs.read` / `fs.write` / `fs.edit` / `fs.patch` / `fs.search` / `fs.list` / `fs.undo` ツール、成果物保管、spill |

- ルート概念: ツールは必ず**当該 spawn の job ディレクトリ**を基準に動く
  (`<data>/workspaces/<soul_id>/jobs/<job_id>/`、
  [../tasks/jobs-and-schedules.md](../tasks/jobs-and-schedules.md))。
  soul 根や他 job への横断はスコープ外。絶対パス指定はスコープ検査後に解決。
- `fs.search` は大規模リポジトリに耐える実装(rg 呼び出し)を既定とする。
- **`fs.undo`**: 書き込み系の操作を巻き戻す。MCP の filesystem サーバーには
  ない機構であり、`fs` を内製する主な理由の1つ。
  書き込み前の状態を記録し、直近の操作から順に戻せる。
  **範囲は当該 spawn の job ディレクトリ内で、その job が行った
  書き込み系操作だけ**(D-30)。他 job・soul 根・セッション跨ぎの成果は
  対象外。表層は書き込みツールを持たないので、undo も裏層のみ。
- `side_effects`: 読み取り系は空(表層に公開される)。
  書き込み系は `["fs.write"]`(裏層のみ)。

## 2. exec seam(シェル/プロセス実行)(D-24)

**`fs` とは別のプラグインにする。** 現行実装では `fs` プラグインに
`shell` アクションが同居しているが、任意コマンド実行はファイル操作とは
危険度もサンドボックス要件も別物で、承認ポリシーも別系統になる。
同じプラグインに置くと、片方の許可がもう片方に漏れる。

| 役割 | 内容 |
|---|---|
| Definition | `run(command, cwd, env, timeout) → { stdout, stderr, exit_code }` と持続 PTY の2面 |
| Provider(既定) | サンドボックス内ローカル実行([../security/sandbox.md](../security/sandbox.md)) |
| Consumer | `exec.run` / `exec.pty` ツール、サイドカー起動 |

- コーディング(P-612)と日常スクリプト(P-611)の両方がこの seam を使う。
- `cwd` の既定は当該 spawn の job ディレクトリ(fs と同じ根)。
- `side_effects: ["exec"]`。表層には公開されない。承認ポリシーの対象。
- 持続 PTY は `exec.pty` で扱い、セッション跨ぎのシェルを1つだけ許可
  (複数 PTY は後継)。

## 3. web seam

| 役割 | 内容 |
|---|---|
| Definition | `search(query) → 結果列`、`fetch(url) → 正規化コンテンツ` |
| Provider(既定) | ホスト側 HTTP クライアント(Broker 代行)+ HTML→Markdown 変換 |
| Consumer | `web.search` / `web.fetch` ツール |

- SSRF 防護は Broker 層で強制(私的アドレス帯の既定拒否)。
- `fetch` は巨大ページを spill 候補として扱う(本文上限+要約)。
- `side_effects` は空。表層からも呼べる。ネットワークアクセスは
  ユーザーの環境を変えないため、副作用として扱わない。
  ただし承認ポリシーは別で、ドメイン単位の許可はここでも効く。

## 4. app seam(GUI 自動化・画面取得)

デスクトップの窓・画面・入力デバイスへの接点。MCP に等価物がなく、
承認と OS サンドボックスの要求が大きいので内製する。

| 役割 | 内容 |
|---|---|
| Definition | `screenshot(target) → 画像`、`window_list()`、`window_focus()`、`click/type/key`、`clipboard_get/set` |
| Provider(既定) | OS ネイティブのプラグイン(アウトプロセス) |
| Consumer | `app.*` ツール群、および vision seam(§9)の観測経路 |

- **同じ capability を2つの経路が使う**(D-16)。モデルが呼ぶ `app.screenshot`
  と、ホスト側の継続観測が呼ぶ内部取得は、この seam の同じ面を通る。
  違いは結果の行き先で、前者は会話履歴に画像として入り、後者は補助LLMで
  テキスト化されて会話履歴には入らない(§9)。
- `screenshot` の出力は画像ブロック(spill 対象)。
- 入力系(`click`/`type`/`key`)は `side_effects: ["input"]`。
  画面外の世界を動かすので裏層のみ、かつ承認必須。
- `screenshot` / `window_list` は `side_effects` が空(読み取り)だが、
  **プライバシー上の承認は別途必要**。副作用の有無と機微さは別の軸であり、
  承認ポリシーは両方を見る([../security/approval.md](../security/approval.md))。

## 4.1 MCP に委ねる領域(P-604 / D-23)

以下は内製せず、MCP サーバーに接続して使う。

| 領域 | 委ねる先の例 |
|---|---|
| git 操作 | git の MCP サーバー |
| ブラウザ操作 | Playwright 系 MCP サーバー。ログイン済みセッションの扱いもサーバー側の責務 |
| カレンダー・メール | 各サービスの MCP サーバー。資格情報もサーバー側 |
| スマートホーム | Home Assistant の MCP サーバー |
| 気象・位置 | 該当 MCP サーバー |

委ねることで、ホスト側は資格情報ボールト・OAuth フロー・API 変更追随を
持たなくてよくなる。代わりに、ユーザーが MCP サーバーを設定する手間が
増える。この交換は、内製した場合の保守コストとサービス API の変更頻度を
考えると妥当と判断した。

**v1.0 の接続はプロファイル行への手書きで足りる**(D-23)。
設定画面から代表的なサーバーを選んで追加する導線(P-616)は後継。
v1.0 の受入は「手書きした1サーバーが同一パイプラインで動く」まで。

## 5. MCP seam(P-603)

MCP サーバーは**供給元**として接続する([registry.md](registry.md) 前提参照)。

- **接続**: stdio / Streamable HTTP をホスト側 MCP クライアント
  (プラグインプロセス)が扱う。接続設定は manifest/profile の行。
- **tools**: MCP ツールをレジストリに登録。`execute` は MCP 呼び出しへの
  ブリッジ。承認・ガード・spill はネイティブと**同一パイプライン**。
  ツール名は `mcp:<server>.<tool>` の名前空間。
- **resources → Context Source**: MCP resource を
  [context-assembly](../core/context-assembly.md) の `mcp.resources` Source に
  変換。購読型 resource の変更は途中システムメッセージになる。
- **prompts → skill 素材**: MCP prompt を skill 素材として取り込める
  ([../tasks/skills.md](../tasks/skills.md))。
- 障害: MCP サーバー死亡は `mcp_unavailable` として、その供給元の
  ツールだけを一時的に無効化。他は影響しない。

## 6. 資格情報の扱い

MCP に外部サービスを委ねても、ホスト側が鍵を持つ場面は残る
(`web` の検索 API、プロバイダの API キー、MCP サーバー自身に渡す鍵)。

- ボールトから Broker の `cred.inject` 経由で注入
  ([../plugins/broker.md §2](../plugins/broker.md))。プラグインに平文を渡さない。
- MCP サーバーへ渡す鍵も同じ経路を通す。設定ファイルに平文で置かせない。
- 受信イベント(カレンダー変更等、MCP サーバーが通知するもの)は
  `inject` 入力として inbox に入り、能動発話やリマインドの材料になる。

## 7. utility seam(決定的な計算)(D-25)

**モデルが自力では確実にできないことだけ**を置く。
モデルの能力向上で不要になったものは削る。

| ツール | 残す理由 |
|---|---|
| `utility.calc` | 桁数の多い算術・単位換算はモデルの生成では誤る |
| `utility.random` | 生成モデルの「ランダム」は一様でも検証可能でもない。くじ引きやサイコロで結果の公平さが問われる場面がある |
| `utility.time` | 現在時刻はモデルが知り得ない。タイムゾーン変換も含む |
| `utility.text` | ハッシュ・エンコード・正規表現の適用など、桁単位の正確さが要るもの |

置かないもの:

- **カウンタ**: 状態を持つだけのツールで、実用の需要がない。必要なら
  `fs` か記憶で足りる。
- **整形・要約・翻訳**: モデルが直接できる。ツールにすると往復が増えるだけ。

`side_effects` は全て空。表層から呼べる。時刻や計算のために委譲が
起きないことが、この seam を置く目的の半分を占める。

## 7.1 code seam(コード実行)(P-611)

- **v1.0(最小)**: exec seam 上の隔離ディレクトリでスクリプト
  (Python 等)を実行。成果物は fs seam に書く。
- **後継**: 専用のコード実行ランタイム(依存のキャッシュ・複数言語)。
  seam は同じなので差し替えのみ。
- `side_effects: ["exec", "fs.write"]`。

## 8. プロバイダ seam(P-1003)

LLM/埋め込み/STT/TTS/VAD はすべてプロバイダ seam。

| seam | 面 |
|---|---|
| `llm` | chat/generate。ツールスキーマ渡し・ストリーミング・内面チャネル対応 |
| `embed` | テキスト→ベクトル |
| `stt` | 音声→テキスト(部分結果の逐次) |
| `tts` | テキスト→音声(ストリーミング、感情/スタイル指定) |
| `vad` | 音声フレーム→発話区間 |

- クラウド/ローカルを問わない同一経路(P-909)。プロバイダはプラグイン
  として実装され、[ipc.md](../plugins/ipc.md) のプロバイダ副プロトコルを使う。
- タスク別モデル選択(`ai.tasks.<task>`)は
  [manifest-and-profile.md §3](../plugins/manifest-and-profile.md#3-プロバイダの選択p-909)。

### 8.1 補助LLM(P-524 / D-15)

`llm` seam の呼び出し元には、会話モデルでもツールでもない**第三の分類**が
ある。ハーネス内部処理がモデルを使う場合である。

| 分類 | 呼び出し元 | 出力の行き先 |
|---|---|---|
| 会話LLM | 表層/裏層のエージェントループ | ユーザーへの発話、ツール呼び出し |
| ツールのLLM | プラグインが内部で使う | そのツールの結果 |
| **補助LLM** | ハーネス内部処理(記憶抽出、画面要約、能動発話の判定、compaction) | ハーネスの内部状態。会話履歴には入らない |

補助LLMを別分類にする理由:

- **モデル選択が独立している。** 記憶抽出や画面要約は、会話と同じ高性能
  モデルを使う必要がない。安価なローカルモデルで足りる場面が多く、
  頻度も高い。`ai.tasks.<task>` で個別に指定できる必要がある。
- **失敗時の扱いが違う。** 会話LLMの失敗はユーザーに見えるエラーだが、
  補助LLMの失敗は「その回の処理を諦める」で済むことが多い
  (能動発話なら沈黙、記憶抽出なら次回に回す)。
  ただし承認判断だけは例外で、諦めた先が「勝手に実行」になってはならないため
  ポップアップへ落とす。
- **課金計上を分けたい。** 使用量台帳(P-516)は補助LLMの消費も含めるが、
  内訳を区別できないと「何もしていないのに課金が増える」と見える。

補助LLMの出力はモデル呼び出し可能なツールではないので、
レジストリには載らない([registry.md §0.1](registry.md))。

## 9. vision seam(P-112 / D-16)

画面とカメラの視覚認知。**v1.0 で画面は実装する**(カメラは後継)。

現行実装では vision は `app` プラグインの1ツールになっている。
これは**モデルが見たいときに見る**経路としては十分だが、
それだけでは能動発話が成り立たない。モデルを呼ばないと画面を見られず、
画面を見ないと呼ぶべきか判断できないという循環になる。

そこで**2つの経路**を定義する。両方とも取得は app seam(§4)を使う。

| | ツール経路 | 継続観測経路 |
|---|---|---|
| 起動 | モデルが `app.screenshot` を呼ぶ | ホスト側が一定間隔で取得 |
| 結果の形 | 画像ブロック | 補助LLM(§8.1)によるテキスト要約 |
| 会話履歴 | **入る**(モデルが見た事実として残る) | **入らない**(世界状態メモリに入る) |
| 用途 | 「この画面見て」への応答 | 能動発話の判定材料([../companion/proactive.md](../companion/proactive.md)) |

継続観測を会話履歴に入れない理由は、数十秒ごとの要約が履歴を埋め尽くし、
compaction を無意味にするため。世界状態メモリは揮発性のリングバッファで、
永続化もしない。

クラウドモデルへの画像の扱い: **モデルが画像入力に対応しているなら、
そのまま渡す。** ローカルに限定すると、視覚認知の質がローカルモデルの
性能で頭打ちになる。画面をクラウドに送ることの是非はユーザーの設定で
決める問題で、設計側で一律に禁じることではない。

- `app.screenshot` の承認は §4 の通り(副作用は空だが承認は必要)。
- 継続観測の間隔・有効/無効はユーザー設定。既定は無効寄り
  (画面の常時監視は明示的に選ばせる)。
