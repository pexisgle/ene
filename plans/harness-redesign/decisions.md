# 設計決定の記録

この文書群は当初 AI が下書きしたもので、作者の意図と食い違う箇所が多数あった。
レビューを通じて確定した決定を、**根拠つきで**ここに記録する。

各設計文書はこの決定に従う。**設計文書とこの記録が矛盾したら、この記録が勝つ**
(`product/` との関係は README の規則どおり、product/ がさらに上位)。

決定を覆すときは、この文書の該当行を書き換えてから設計文書を直す。逆順は禁止。

## D-1 層の境界 — 表層は「簡単な作業」をしてよい

**決定**: 表層は、計画立案を要さず単一(またはごく少数)のツール呼び出しで
終わる作業を、自分で実行してよい。裏層へ渡すのは複雑な作業に限る。

**却下した当初案**: 表層は一切の作業ツールを持たず、短い検索すら裏層へ出す。

**根拠**: 「今何時?」「さっきのファイル名は?」のために委譲を起こすのは、
遅延と機構の重さに見合わない。会話の即応性は存在感の中核であり、
一律委譲はそれを壊す。

**実施方法**: 表層の公開ツール面は副作用のない読み取り専用に限る(D-2)。
複雑さの判定を誤って表層が抱え込む事故は、安全網(D-3)で回収する。

## D-2 表層の公開ツール面 — 読み取り専用のみ

**決定**: 表層に公開するのは副作用のないツールだけ。書き込み・実行・送信・
外部状態を変えるツールは裏層のみ。

**根拠**: 「簡単さ」はモデルの自己申告で決まるため、それを副作用の許可条件に
すると事故が防げない。副作用の有無は静的に決まるので、境界として信頼できる。

## D-3 安全網 — 表層が抱え込んだ複雑な作業の自動委譲

**決定**: 表層のターンが所定のステップ数を超える、または副作用のあるツールを
必要とした時点で、ハーネスが自動的に裏層へ委譲へ切り替える。モデルの判断に
依存しない。

**根拠**: D-1 が成り立つには「簡単だと思ったが実は複雑だった」場合の回収が要る。
モデルに正しく判断させるのではなく、機構で検出して切り替える。

## D-4 耐久性 — v1.0 は簡易、3ストア/effect sandwich は後継設計

**決定**: pi 由来の3ストア(entries/registers/usage)・effect sandwich・
OperationState プログラムカウンタは**後継設計**として保存し、v1.0 では実装しない。
v1.0 の最低ラインは D-5。

**根拠**: v1.0 のスコープを維持したまま耐久性まで作り込むと初版が出ない。
ただし effect sandwich は後付けが難しいので、設計としては捨てずに残す。

**波及**: `core/durability.md`・`core/operations.md`・`core/storage-model.md` の
3文書は「後継設計」と明示する。v1.0 が満たす範囲を各文書の冒頭で切り分ける。
compaction の `start`/`end` ロック括弧も後継。v1.0 は成功時の
`compaction/applied` のみ書く。

## D-5 クラッシュ回復の最低ライン — 後始末と報告

**決定**: v1.0 は「重複効果なしの再開」を保証しない。再起動時に、中断された
ターン/ジョブを検出し、後始末をして、ユーザーに中断を報告する。
未消化の inbox(ユーザー発話の wake、委譲の報告・質問、ask-user の保留)は
**セッションログから復元して「途中だった」と見せる**。モデルを回して
作業の続きは実行しない。レジスタ(`pending.entry`)は使わない。

**根拠**: ツール呼び出しが単に失敗した場合は、失敗として表示すれば足りる。
これと区別すべきなのはプロセスが落ちた場合で、そこは「途中だったことを
なかったことにせず、正直に伝える」で v1.0 は成立する。続きを走らせるかは
ユーザーが新しいターン/job として指示する。

**実施方法**: inbox 項目は `inbox/enqueued` 等のログイベントとして書く
([core/session-log.md §3.7](core/session-log.md))。起動時は未 claim 項目を
放棄して中断報告の材料にする([core/agent-loop.md §12](core/agent-loop.md))。
同一プロセス内の通常動作では、ask-user の回答は従来どおり同一ターンを続ける。

## D-6 複数コンパニオン — v1.0 で同時並存

**決定**: 複数のコンパニオンが同時に存在し、同時に表示・会話できる。

## D-7 記憶の共有 — 共有プール + 抽出時のスコープ判定

**決定**: 記憶は既定でコンパニオンごとに分かれる。ただしユーザーに関する事実と、
抽出器が重要と判断した事項は**共有プール**に入り、全コンパニオンが参照する。

**判定者**: 記憶抽出の補助LLM(D-15)が、抽出時に `scope: shared | private` を
付与する。種別による機械的な振り分けではない。

**読み取り側**: 共有記憶は出所(どのコンパニオンが書いたか)を保持するが、
通常の想起では出所を意識させない。参照するコンパニオンは自分の知識として扱う。

**根拠**: ユーザーの名前や生活リズムを人格ごとに覚え直させるのは不自然。
一方で体験や関係性まで共有すると、別人格である意味が消える。

## D-8 セッションの区切り — アイドルタイムアウトと明示分割のみ

**決定**: セッションはアイドルタイムアウトと明示的な分割で区切る。
**話題境界による自動分割はしない。**

**根拠**: コンパニオンとの会話は本来連続的なもので、話題が変わるたびに
セッションが割れると、会話が分断された感覚を生む。

## D-9 イベントソーシングの適用範囲 — 会話ログのみ

**決定**: イベントソーシングは `sessions` に限定する。記憶・スケジュール・
成果物・設定は通常のテーブル構造(`companions.db`)。

**根拠**: fork(P-109)と `model-visible = logged`(P-502)はイベントソーシング
前提の要件であり、これらを v1.0 に残す以上、会話ログは追記ログにする。
一方で記憶やスケジュールに広げると実装量が跳ね上がり、得るものが少ない。

**注意**: 読み取りが必ず投影を通るので、素朴に書くと履歴取得が
O(イベント数) になる。v1.0 は compaction(P-506) で投影結果を有界にする。
`compaction/applied` の範囲は走査しない。スナップショットや投影キャッシュは
持たない。必要になったら後継。

## D-10 ツールとハーネス機能の2軸整理

**決定**: 次の2軸で分類し、設計文書はこの語彙で書く。

| | ホスト内実行 | アウトプロセス実行 |
|---|---|---|
| **モデルから呼べる** | ハーネス機能ツール(記憶想起・委譲・内面など、ハーネス状態と密結合) | 通常のツール(fs / exec / web / app …)。**ビルトインもサードパーティも同じ API** |
| **モデルから呼べない** | ハーネス内部処理(コンパクション・記憶抽出・感情更新) | — |

**却下した当初案**: 「プラグインは全アウトプロセス」という一律の宣言。
記憶想起や委譲までアウトプロセスにする読み方ができてしまい、実態と矛盾していた。

**根拠**: ビルトインツールもサードパーティと同じ API に載せることで、
実装量が減り、かつ「fs のようなサードパーティツールを後から作れる」が保証される。
一方、ハーネス状態に直接触る機能をプロセス境界の向こうに置くのは、
往復のコストにも整合性にも見合わない。

## D-11 出力秘匿 — 「深さ」の切り替え

**決定**: 秘匿は「見せない」の一律規則ではなく、**表示面ごとの深さ**で決める。
深さは `surface` と `detail` の**2段階だけ**。中間段
(「ツール引数までは見せるが thinking は見せない」など)も、
カテゴリ別の ON/OFF も持たない。

| 表示面 | 深さ |
|---|---|
| 表層UI(stage・チャット) | 発話・成果物のみ。作業中は1行の状況表示までは可 |
| 詳細画面 | ツール呼び出し・層間メッセージ・thinking まで表示可。内面はセッションログとして読める(D-20)。ライブ演出はしない |

詳細画面の置き方はクライアントが決める。desktop は**別ウィンドウ**が適切
(主画面を存在感の場として保つため)。Web も詳細の表示面を持つ(D-31)。
CLI は `--verbose` / `ene debug` が同じ深さ。

**却下した当初案**: thinking やツール引数を「決して表示しない」とする不変条件。
中間段やカテゴリ別トグルも、面の性格を曖昧にするため却下。

**根拠**: 表層の体験を機構で汚さないことと、作者・上級ユーザーが内部を
検証できることは両立する。前者は既定値の問題であって、不変条件ではない。

## D-12 用語 — job のユーザー向け呼称は「タスク」

**決定**: ユーザー向けの呼称は「タスク」。「おつかい」は使わない。

## D-13 ジョブ進捗の伝え方 — コンパニオンが話す

**決定**: 裏層のジョブの進捗・完了は、進捗バーやシステム通知ではなく、
コンパニオンの発話としてユーザーに届く。

## D-14 能動発話 — イベント駆動 + ローカル/クラウドの二段確認

**決定**: 数十秒〜数分間隔で環境を観測し、決定的なゲートを通ったものだけを
**ローカル小モデル**で判定、さらに**クラウド高性能モデル**で二重確認してから発話する。
ほとんどの観測では発話しない。重要なイベントでのみ発話する。
発話しやすさはキャラクターと設定で変えられる。

**却下した当初案**: 時間駆動で「一定間隔ごとに話しかけるか判断する」モデル。

**根拠**: 現行実装(`crates/ene-companion/src/proactive/`)が既にイベント駆動で、
決定的ゲート → 軽量LLM の二段構成を持つ。当初案はこれより後退していた。

## D-15 補助LLM — 呼び出し元で分ける3カテゴリの第3

**決定**: LLM の使われ方を**呼び出し元**で3つに分ける。

| 分類 | 呼び出し元 | 出力の行き先 |
|---|---|---|
| 会話LLM | 表層/裏層のエージェントループ | ユーザーへの発話、ツール呼び出し |
| ツール内部の LLM | プラグインが自分の処理のために使う | そのツールの結果 |
| **補助LLM** | ハーネス内部処理 | ハーネスの内部状態。会話履歴には入らない |

分類の軸は**誰が呼ぶか**であって、誰が供給するかではない。
供給は3つとも同じプロバイダ seam を通る(クラウドでもローカルでも
プラグインが提供する)。供給側の話と混ぜない。

**補助LLM の用途**: 画面要約、記憶抽出とスコープ判定、能動発話の一次判定、
コンパクションの要約、感情更新。

**根拠**: これらはモデルの意思とは無関係にハーネスが起こす呼び出しなので、
**ツールレジストリには載らない**(モデルからは選べない)。一方、
**設定では `ai.tasks.<task>` に並び、ユーザーがモデルを指定できる**。
記憶抽出や画面要約は会話ほどの品質を要さず頻度が高いので、
会話と別のモデルを当てられなければ意味がない。
失敗時の扱いも会話とは違い、多くは「その回を諦める」で済む
(能動発話なら沈黙、記憶抽出なら次回に回す)。
ただし承認判断だけは例外で、諦めた先が「勝手に実行」になってはならないため
ポップアップへ落とす。

## D-16 vision — 2経路を別物として設計する

**決定**: 画面を「見る」経路は2つあり、統合しない。

| 経路 | 実装 | 起動主体 | 出力 |
|---|---|---|---|
| モデルが呼ぶ「見る」 | 通常のツール(`app.screenshot` 等、アウトプロセス) | モデルの tool call | 画像。会話履歴に入りマルチモーダルモデルが直接読む |
| ハーネスが「観ている」 | 補助LLM(D-15、ホスト内) | ハーネスの定期観測 | 要約テキスト。能動発話の材料。履歴には積まない |

**根拠**: ツール呼び出しはターンの中でしか起きないが、能動発話の観測は
ターンの外で走る。加えて、常時観測の結果を画像として履歴に積むと
コンテキスト窓が数分で溢れ、毎分クラウドへ送るのはコスト的に持続しない。

## D-17 画像のクラウド送信 — 不変条件ではなく頻度依存の既定

**決定**: クラウドモデルが画像を読めるなら、適切に渡してよい。
ツール経路(D-16 上段)は生画像を渡す。常時観測経路(下段)はローカル要約が
既定だが、設定でクラウドを選べる。

**却下した当初案**: 「生画像はクラウドに出さない」という不変条件。

## D-18 記憶の想起 — 自動想起とツール想起の併用

**決定**: ターン開始時の自動想起と、モデルが明示的に呼ぶ想起ツールの両方を持つ。

## D-19 感情の表示

**決定**: 感情は常に body の emotion と連携して表示する。body の扱い方は
クライアントごとに異なり、**コアは指定しない**。body のない desktop / web では、
body の emotion をそのまま簡単なテキストUIに出せば足りる(専用の表現を設計しない)。
感情の内部保持状態(PAD 等)は詳細画面にのみ出す。

## D-20 内面は表層に出さない — 見るのは設定のログだけ

**決定**: 内面は表層UI(stage・チャット)に出さない。出す設定も持たない。
ユーザーが内面を見るのは、設定画面(またはそれに類する詳細画面)の
セッションログだけである。生成・記録・自己参照は続ける。

**根拠**: 内面はコンパニオンの一貫性を支える内部状態であり、
対話の演出ではない。常時流れていると、相手と話している感覚が薄れる。

## D-21 デスクトップの実装 — ネイティブのみ

**決定**: WebView を含む Web 技術は使わない。egui + wgpu を基本とする。
不十分だと判明した場合のみ再検討する。

**根拠**: 高速軽量なネイティブアプリを目標に置いている。

## D-22 プラグイン IPC — 副プロトコルへの分割を伴う書き直し

**決定**: 現行 `ene-plugin-proto`(v8)を書き直す。方向は3点すべて。

1. **副プロトコルへの分割**。core(ライフサイクル)/ tool / provider / capability を
   独立バージョンにする。
2. **境界の型付け**。`arguments: String`(中身は JSON)、`provider_config: Value`、
   `messages: Vec<Value>` のような非型付けの穴を塞ぐ。
3. **バルク転送をフレーム外へ**。FD 渡しまたは共有メモリ。

**根拠**: 現行は単一の巨大 enum にライフサイクル・ツール・権限・プロバイダ6種・
ケイパビリティが同居している。このため (a) ツールプラグインが VAD や TTS の
変種まで知る必要があり、(b) 新しいモダリティを足すたびに共有バージョンが上がって
N-1 ポリシーで無関係な全プラグインが失効し、(c) 音声が `audio_base64: String` で
フレームに乗る。さらに `request_id` が `#[serde(default)]` なので相関IDが
省略可能になっており、全ハンドラが空文字を許容する作りになっている。

## D-23 コネクタの範囲

**決定**: 内製として残すもの、MCP に委ねるもの、削除するものを次のとおり分ける。

| 扱い | 対象 | 理由 |
|---|---|---|
| 内製 | `app`(GUI自動化・画面取得) | MCP に等価物がなく、承認とサンドボックスが OS 依存。vision(D-16)の素材でもある |
| 内製 | `fs`(read/write/edit/patch/search/undo) | `undo` は独自機構。承認モデルの中心 |
| 内製 | `exec`(`fs` から分離) | D-24 |
| 内製 | `web`(fetch / search) | 使用頻度が最も高く、鍵管理・レート制限・キャッシュをホスト側で持ちたい |
| 内製 | `utility`(time / system_info / calc / random) | D-25 |
| MCP に委ねる | `git`・`browser`・`homeassistant`・`calendar`・`geo` | 成熟した MCP サーバーが存在する |
| 削除 | `counter` | 状態付きのサンプル。実用の需要がない |

**MCP サーバーの接続導線は v1.0 の要件ではない**(P-616 は後継)。v1.0 はプロファイル行への
手書き設定で足りる。設定画面から代表的なサーバーを選んで追加できる UI は後継。
委ねた領域の使い勝手は導線に依存するが、それを v1.0 の受入条件に入れると
「どのサーバーを推奨するか」の選定まで初版に持ち込むことになる。

## D-24 `exec` を `fs` から分離

**決定**: 現行 `fs` プラグインに含まれる `shell` アクションを別プラグインへ出す。

**根拠**: 任意コマンド実行はファイル操作と危険度もサンドボックス要件も別物で、
承認ポリシーも別系統になる。同じプラグインに置くと、片方の許可がもう片方に漏れる。

## D-25 `utility` の再分類

**決定**: 現行 `utility` プラグインの中身を次のとおり振り分ける。

| 現行アクション | 移動先 | 理由 |
|---|---|---|
| `question` | ハーネス機能(表層への差し戻し) | ユーザーへの質問は層をまたぐ制御であって、ツールではない |
| `notify` | クライアント機能 | 通知の出し方はクライアントが決める。契約は [platform/clients.md §3.1](platform/clients.md) |
| `timer` | `tasks/` のスケジュール | スケジュール機構と重複している |
| `todo` | `tasks/` のジョブ | ジョブ機構と重複している |
| `time` / `system_info` | 新 `utility` に残る | — |

さらに `calc`(evaluate / unit / currency / color)と
`random`(number / pick / uuid / color)を新 `utility` に統合する。
加えて `text`(ハッシュ・エンコード・正規表現の適用)を新設する。

**根拠**: 統合後の `utility` は「**モデルが自力では確実にできない決定的な計算**」
という一貫した括りになる。正確な四則演算・単位換算・為替の生レート・
真の乱数・UUID・ハッシュ値・エンコード結果は、いずれも LLM 単独では信用できない。
逆に、整形・要約・翻訳はモデルが直接できるので置かない(往復が増えるだけ)。

## D-26 配布とコミュニティ

**決定**: プラグインとキャラクターのコミュニティ形成を目標に置く。ただし時期は将来。
署名レベルの厳格さは v1.0 では不要。マーケットプレイスも将来。
**大規模な改修なしにそこへ到達できる設計**にしておくことだけが v1.0 の要件。

## D-27 再利用するコード

**決定**: 基本はフルリライト。ただし `ene-vrm` とプラグインシステムの一部は再利用する。

## D-28 現行実装との関係 — 主要領域は現行が上位

**決定**: 当初の下書きは、能動発話・vision・記憶スキーマにおいて**現行実装より
後退**していた。これらの領域では現行実装を正とし、設計文書を現行に合わせて書き直す。

## D-29 文書の粒度 — 方針は厳密に、数値は控えめに

**決定**: 方針と不変条件は実装が一意に定まる粒度で書く。一方、具体的な数値
(閾値・既定値・予算)は減らす。数値は実装しながら調整するものだから。

## D-30 `fs.undo` の範囲 — 当該 job が書いたものだけ

**決定**: `fs.undo` が巻き戻せるのは、当該 spawn の job ディレクトリ内で、
その job が行った書き込み系操作だけ。セッション跨ぎや他 job の成果は対象外。

**根拠**: 内製する理由は「今の作業を取り消せる」ことであって、
コンパニオン単位のグローバル履歴ではない。他 job まで戻すと、
並行した別作業の成果を消す。

## D-31 Web にも詳細画面を置く

**決定**: Web クライアントも `depth: detail` の詳細画面を持つ。
desktop と CLI だけに限らない。

Web の詳細画面で**できること**(閲覧):
- 内面・thinking・ツール引数・層間メッセージ・感情の内部状態
- タスク一覧、記憶の閲覧

Web の詳細画面で**できないこと**(変更は desktop のみ):
- 設定変更、記憶の削除・編集、キャラ管理の変更

**根拠**: 外出先から内部を検証したい。深さの規則(D-11)はクライアントを問わない。
一方、破壊的な変更を外出先の薄いクライアントに置く必要はない。
制限は **Web クライアントが表示・提供しないこと**であり、
API をクライアント種別で分岐しない(P-707 の対等)。
Web の v1.0 は VRM を持たないので、desktop のような「別ウィンドウ」は必須ではない。
UI の置き方(別ページ / 別パネル)はクライアントが決める。
不変条件は、表層のチャットに深い情報が混ざらないことと、詳細の表示面から
同じ深さで到達できること。

## D-32 プラグイン合成 — ホスト文脈の時空間合成

**決定**: アウトプロセス隔離(D-10)を保ったまま、ホスト側の合成に
時空間の2次元を入れる。参照は Cordis の形式化
(Shi, Zhang, Cui, *A Programming Paradigm for Spatiotemporal Composability*)。
Cordis そのもの(TypeScript の in-process ローダ)は採用しない(vision §4)。

1. **時間(巻き戻し可能な effect)**。プロファイル行はホスト上の**ファイバー**。
   ツール登録・seam 束縛・Context Source・Broker 委譲・子プロセス spawn は、
   すべて「変更 + 逆」の対としてホストが追跡する。行の無効化・死亡・
   差し替えは、蓄積した逆を LIFO で適用してホスト文脈を回収する。
   プラグイン作者に `deactivate` フックを書かせない。
2. **空間(反応的な依存)**。ファイバーは `provides` / `requires` を宣言する。
   満たされた行だけが ACTIVE になり、失われたら UNLOADING に入る。
   プラグイン同士は直接呼び出さない。解決と配送はホストの seam が行う
   (論文の service broker。既存の capability seam 3役割がそれ)。
3. **差分適用**。プロファイル/パッチの変更はファイバー単位で reconcile する。
   無関係な行とコアデーモンは再起動しない。ネイティブバイナリの HMR は
   後継。v1.0 の代替は「そのファイバーだけ process を建て直す」で、
   ホスト文脈の回収が(1)で保証されているからデーモンごと落とさなくてよい。

**却下した案**:

- **子プロセスの kill を時間合成とみなす。** プロセス境界はプラグイン側の
  メモリを捨てるが、ホストに残る登録(レジストリ・seam・委譲 FD)は回収しない。
  回収漏れを避けるためにデーモンごと再起動すると、会話・音声・進行中 job の
  プロセス内状態まで捨てる。論文 §1.2.3 の coarse-grained workaround そのもの。
- **プラグイン同士の直接 IPC。** サンドボックス(P-901)と Broker 原則(P-902)を
  破る。空間合成はホスト経由に限る。
- **VSCode 型の activate/deactivate フック。** 生成と破棄が分離し、
  完全な回収を作者の勤勉さに頼る。ホストが追跡する対に一本化する。

**根拠**: vision はすでに「登録=巻き戻し可能な effect」を採用している。
現行のプラグイン3文書は輸送・宣言・Broker だけで、ホスト文脈の回収と
依存の再評価が無かった。エージェントハーネスは実行中に行を足し引きする
(プロファイル切替、プロバイダ死亡、コミュニティプラグインの導入)ので、
この2次元が無いと「死んだプラグインのツールが残る」「LLM を差し替えると
無関係なツールまで再起動する」が構造的に起きる。

**波及**: [plugins/composition.md](plugins/composition.md) が本体。
manifest の `provides`/`requires`、監督のファイバー状態機械、
レジストリ登録の逆、seam のブローカー役、プロファイル差分の reconcile。

実施規則(実装が一意に定まるまで、ここが勝つ):

1. **`target` は充足の真偽であって提供者 uid ではない。** `requires.seams`
   の各鍵は「そのブローカーに ACTIVE な backing が1つ以上あるか」だけを
   見る。backing の差し替え・追加は neutral。最後の1つが落ちたときだけ
   deactivating。
2. **プロファイル行は安定 `id` を持つ。** 省略時は `plugin` と同一。
   同じ `plugin` を2行置くときは `id` 必須。パッチの `target` /
   `insert_after` は行 `id`。ファイバー `uid` は行 `id` ではなく、
   起動のたびに払い再利用しない。disable→enable も新しい `uid`。
3. **失敗の行き先。** 宣言/ポリシーで起動できない行は `inactive` のまま
   自動再試行しない。spawn/hello/apply の実行時失敗は死亡と同じ
   (backoff → 規定回数で `failed`)。
4. **`reconfigure` は応答を持つ。** プラグインは
   `applied` / `need_rebuild` / `error` を返す。無応答は `need_rebuild`。
5. **逆を積むのはホスト。** 子プロセスの SDK は apply 側だけ書く。
   非 Rust プラグインでもホストが `spec`/grant/spawn を見て対を積む。
6. **進行中呼び出しは cancel。** ステップ開始時にモデルへ渡したスキーマは
   そのステップの間固定。unload は提供を直ちに止め、進行中の
   `tool.call` / `generate` を `cancel` し、新規は `plugin_unloading`。
   次ステップのスキーマから消える。

コード上の名前はホストの `dispose` 蓄積とする。耐久性の effect sandwich
(D-4、v1.0 では実装しない)と混ぜない。
