# Ene ハーネス再設計 — 設計文書群

Ene を「コーディング特化ではない AI コンパニオン型エージェントハーネス」へ
再設計する文書群。2層構造: **プロダクト定義(完成形)が先、設計は後**。

1. **[product/](product/README.md)** が「完成形」を定義する。
2. 領域別フォルダが、`product/features.md` の要件 ID(`P-xxx`)を
   実現する設計を記述する。各文書は冒頭に「実現する P-xxx」を置く。

レビューで確定した決定は [decisions.md](decisions.md) にあり、
**設計文書とそこが矛盾したら decisions.md が勝つ**。

## 確定済みの骨格決定(全文書の前提)

各項目の末尾の `D-xx` は [decisions.md](decisions.md) の決定番号。
そこに決定の根拠と、却下した当初案が記録されている。

1. 純 Rust 軽量カーネル。**ツールはアウトプロセス**(ビルトインもサード
   パーティも同じ API)、**ハーネス機能はホスト内**(D-10)。
2. コアデーモン+マルチクライアント(desktop 主・CLI デバッグ・Web 外部接続)。
   desktop はネイティブ描画のみで WebView を使わない(D-21)。
3. **会話ログだけ**イベントソーシング(`model-visible = logged` 不変条件)。
   記憶・スケジュール・成果物・設定は通常のテーブル(D-9)。
4. コンパニオンごとに**表層 soul + 裏層ハーネス**の2層。表層がユーザー
   入力の唯一の入口(対話レーン1本)、裏層が複雑な作業(独立 job レーン)。
   両層は Codex multi-agent v2 風の層間メッセージで進捗を共有し、
   ユーザーからは1体に見える(P-522)。
5. **表層は簡単な作業を自分でしてよい**(D-1)。公開されるのは副作用のない
   読み取り専用ツールのみ(D-2)。複雑さを見誤った場合は、機構が検出して
   自動的に裏層へ切り替える(D-3)。
6. 複数コンパニオンが同時並存(D-6)。記憶は既定でコンパニオンごとだが、
   ユーザーに関する事実と抽出器が重要と判断した事項は**共有プール**に入る(D-7)。
   サブエージェントはユーザーから秘匿。
7. 構成可能プラグインツリー(プロファイル/バンドル/パッチ)。
8. 統一ツールレジストリ。Tool Calling(モデル規約)と MCP(供給元規約)は
   別レイヤーとして統合。成熟した MCP サーバーがある領域(git・browser・
   calendar・homeassistant・geo)は内製せず MCP に委ねる。v1.0 の接続は
   プロファイル行への手書きで足り、設定画面の導線 UI は後継(D-23)。
   `fs.undo` は当該 job が書いたものだけを戻す(D-30)。
9. 承認は事前ポリシー+AI 自動承認+ポップアップ。対話からのポリシー追加可。
10. soul/body は分離。既定は「セット=1キャラ」、自由な結合を公式サポート。
11. 感情はハイブリッド(離散ボキャブラリの対外層+PAD の内部状態層)。
    表示は常に body の emotion と連携。body の扱い方はクライアントが決め、
    **コアは指定しない**(D-19)。
12. 内面チャネルは永続+自己参照窓。**表示は既定 OFF**、詳細画面でのみ ON(D-20)。
13. 音声は全二重・サーバー所有。
14. workspace は内部概念のみ。**spawn(委譲)ごと**に独立し、fs/exec の既定
    スコープになる。成果物は広範+段階化。skill は業界標準準拠。
15. LLM の使われ方は**呼び出し元**で3つに分ける(D-15)。会話LLM
    (表層/裏層のループ)、ツール内部の LLM、**補助LLM**(ハーネス内部処理。
    画面要約・記憶抽出・能動発話の一次判定・要約・感情更新)。供給は3つとも
    同じプロバイダ seam を通る。補助LLM はツールレジストリに載らないが、
    設定では `ai.tasks.<task>` でモデルを指定できる。
16. Broker 仲介原則(manifest 同梱アセットは素通り)。
17. **v1.0 の耐久性は簡易**。3ストア(entries/registers/usage)・effect sandwich・
    OperationState は**後継設計**として保存する(D-4)。v1.0 の最低ラインは
    「中断されたターン/ジョブを検出し、後始末し、ユーザーに報告する」(D-5)。
18. **出力秘匿は「深さ」の切り替え**(D-11)。深さは `surface` / `detail` の
    2段階だけ。表層UIは発話と成果物のみ(作業中の1行表示までは可)、
    詳細画面では内面・ツール呼び出し・層間メッセージ・thinking まで出せる。
    desktop も Web も詳細画面を持つ。Web は閲覧とデバッグまでで、
    設定変更・記憶削除は desktop のみ(D-31)。「決して表示しない」不変条件ではない。
19. 複雑な作業は**非同期委譲**に移す。表層は待たず会話を続け、完了報告は
    対話レーンにターンとして届く(P-519/P-521)。job と秘匿サブエージェントは
    同機構の public/internal モード。進捗はコンパニオンの発話として伝わり、
    進捗バーやシステム通知にはしない(D-13)。
20. ホストはコアデーモンただ1つ。表層と裏層はホストを割らず、同一
    ハーネスカーネル(ログ・Tool Calling / MCP / skill)の上の**専用実装**として
    走る。公開ツール面のフィルタだけではない。
21. **能動発話はイベント駆動**。定期観測 → 決定的ゲート → ローカル小モデル →
    クラウド高性能モデルの二重確認。ほとんどの観測では発話しない(D-14)。
22. **画面を見る経路は2つ**あり統合しない。モデルが呼ぶ「見る」は通常のツール、
    ハーネスが定期的に「観ている」のは補助LLM(D-16)。
23. プラグイン IPC は**副プロトコルへ分割**して書き直す。core / tool /
    provider / capability を独立バージョンにし、境界を型付けし、バルク転送を
    フレーム外へ出す(D-22)。
24. プラグインとキャラクターの**コミュニティ形成が目標**。ただし時期は将来で、
    署名の厳格さもマーケットも v1.0 の要件ではない。v1.0 に課すのは
    「大規模な改修なしにそこへ到達できる設計」だけ(D-26)。

## この文書群の使い方

- 実装は [migration.md](migration.md) のウェーブ順で進める。
- 矛盾したときの優先順位は **decisions.md > product/ > 領域別文書**。
- P-xxx にない機能を設計に足さない。足すならまず
  [product/features.md](product/features.md) に ID を追加する(要レビュー)。
- 粒度の方針(D-29): **方針と不変条件は実装が一意に定まるまで書く**
  (イベント語彙・スキーマフィールド・状態遷移・境界条件)。一方、
  **具体的な数値は書かない**。閾値・タイムアウト・予算・既定値は実装しながら
  調整するもので、文書に固定すると嘘になる。数値が要る箇所は
  「何に基づいて決めるか」を書き、値そのものは設定キーに委ねる。
- コードそのものは書かない(実装者の言語選択の余地は残さないが、
  コード表現は実装に委ねる)。
