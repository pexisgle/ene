# 移行計画(現行コード → 新構成)

> 実装ウェーブの順序・完了条件・リスクを定義する。
> 各文書が「何を」作るか、この文書が「どの順で」作るかを決める。

## 1. 現行クレート → 新構成のマッピング

**基本はフルリライト**(D-27)。ただし `ene-vrm` とプラグインシステムの
一部は再利用する。判定は **流用**(ほぼそのまま)/
**書き直し**(概念は活かし再実装)/ **破棄**(新設計で不要)の3種。

ただし、能動発話・vision・記憶スキーマの3領域では**現行実装が
設計文書より進んでいる**(D-28)。これらは「書き直し」の判定であっても、
現行の挙動を出発点にする。当初の下書きに合わせて実装すると機能が後退する。

持たなくてよくなる。代わりにユーザーが MCP サーバーを設定する手間が増える。
v1.0 はその手間を手書き設定として受け入れる。導線 UI は後継(P-616)であり、
移行の完了条件には入れない。

## 2. 実装ウェーブ

各ウェーブは「完了条件」を満たして次へ進む。並行できるものは並行する。

### W0: 基盤(カーネルの骨)

- session-log のイベント語彙+SQLite 永続化+投影(L-1..L-5)。
  **イベントソーシングは会話ログのみ**(D-9)。
- storage-model の v1.0 範囲(usage 台帳・スキーマ進化)。
  3ストア/レジスタは後継設計なので作らない。
- agent-loop の最小(対話レーンのみ)+ **中断の検出と報告**(D-5)。
  effect sandwich と操作状態機械は作らない。
- lane-api の v1.0 コマンド面(prompt/steer/follow_up/abort/compact の
  受理/拒否・結果)。`resume` と `lane.last_result` 照合は後継なので作らない。
- **表示の深さ**(D-11): `depth: surface|detail` の購読分離と、
  サーバ側で深さを判定する経路。投影走査テストの骨格。
- observability の最小(スパン語彙・ローカルリング・コンテンツ禁止)。
- context-assembly の最小(Context Source・epoch なしの組立)。
- コアデーモンの起動・設定・アクター配置・起動時の中断検出。
- **完了条件**: テキストのターンが回り、ログに記録され、投影から
  履歴が再現できる。`model-visible = logged` の検証テストが通る。
  プロセスを強制終了した後の起動で、中断が検出・片付け・報告される
  (自動再開はしない)。`depth: surface` の購読に内面が届かない。

### W1: 実行系(ツールとプラグイン)

- plugins/ipc.md の**副プロトコル分割**(D-22)。core / tool を先に作り、
  provider は W3 以降で足す。manifest とプロファイル。
- **時空間合成**(D-32): ファイバー状態機械、登録の逆、`provides`/`requires`、
  プロファイル差分の reconcile。unload 後にホスト文脈が空であること
  (I-46)を W1 の完了条件に含める。後から足すと半登録が残る経路が固まる。
- ツールレジストリ+パイプライン+**2軸の分類**(D-10)。
  ハーネス機能ツールの実行経路(ホスト内)も**同じパイプライン**を通す。
- ビルトインの最小(`fs` / `exec` / `web` / `utility`)。
  `exec` は `fs` と別プラグインとして最初から分ける(D-24)。
- **表層の公開面**(D-2): `side_effects` が空かどうかでフィルタする実装。
  ツール名のホワイトリストは作らない。
- Broker の最小(fs/net)。サンドボックス(Landlock)の適用。
  grant はファイバーの effect として追跡する。
- **承認 plane 完成前の既定**: 副作用のあるツールは **deny-by-default**。
  開発中の暗黙 allow は禁止する。
- **完了条件**: アウトプロセスのツールが登録・実行され、
  サンドボックス内で動く。IPC オーバーヘッドの基準線を計測して記録する
  ([platform/process-model.md §6](platform/process-model.md#6-性能予算))。
  表層のスキーマ面に `fs.write` が現れないことがテストで確認できる。
  副作用ツールの暗黙実行がテストで拒否される。
  行の disable / 強制 kill のあと、その供給元のツールと grant が残らない。
  プロファイルから1行外しても他行とコアデーモンは再起動しない。

### W2: セキュリティ面

- 承認 plane(ポリシーDSL+ポップアップ+監査ログ)。
- 資格情報ボールト。AI 自動承認。対話からのポリシー追加。
- **副作用と機微さの2軸**を plane が扱う。`app.screenshot` のように
  副作用が空でも承認が要るものが正しく止まること。
- W1 の deny-by-default を plane が引き継ぐ。`approval.mode` が実行時の正。
- **完了条件**: approval.md の受入条件(P-903..P-906)が観察できる。
  監査ログの hash chain が検証できる。W1 の暗黙実行拒否テストが
  plane 経由でも成立する。

### W3: コンパニオン層

- soul-and-affect(ハイブリッド感情)。inner-channel(表層に出さない、D-20)。
- memory 全体。**`scope`(private/shared)と共有記憶プール**(D-7)、
  抽出時の補助LLM による scope 判定。
- **補助LLM の分類**(D-15)をプロバイダ seam に入れる。
- proactive: **現行実装を出発点にする**(D-28)。世界状態メモリ・
  決定的ゲート・ローカル小モデルの判定・主モデルによる二重確認。
- character/package-format の実装(+V3 インポート)。**署名は作らない**(D-26)。
- **完了条件**: 再起動跨ぎの記憶・感情の一貫性・能動発話・
  キャラパッケージのインストールが動く(P-2xx/P-3xx/P-8xx)。
  内面が表層UIに出ず、設定・詳細のセッションログで読める。共有プールに回った記憶を
  別のコンパニオンが自分の知識として使える。

### W4: 身体と音声

- body-and-performance(VRM 描画+キュー、`ene-vrm` を流用)。voice(全二重)。
- 感情は**常に body に連動**する(D-19)。内部状態(PAD)は詳細画面のみ。
- **完了条件**: 全二重音声のバグイン・自声回避・リップシンクが動く
  (P-102/P-103/P-4xx)。

### W5: 仕事面と視覚

- delegation.md の非同期委譲(public/internal 両モード)・親↔子
  メールボックス・報告ターン・**自動昇格**(D-3)。
- job レーン・スケジュール・ワークフロー・artifact。skills。
- MCP seam。接続はプロファイル行への手書き(D-23)。導線 UI(P-616)は作らない。
- **vision の2経路**(D-16): `app.screenshot`(モデルが呼ぶ、会話履歴に入る)と
  継続観測(補助LLM が要約、世界状態メモリへ、会話履歴に入らない)。
- **完了条件**: 対話と並行してタスクが走り、成果物が交付される。
  リマインダーが鳴る。MCP ツールが動く(P-6xx)。
  進捗が**コンパニオンの発話として**届く(D-13)。
  表層が副作用ツールを求めたとき委譲へ自動昇格し、実行はされない。
  画面の内容を根拠にした能動発話が起き、その要約が会話履歴を埋めない。

### 内部プレビュー線(W5 の後、任意)

W5 の完了条件を満たしたら、W6 に進む前に**開発者向け内部プレビュー**を
置くことを推奨する。v1.0 = [product/done.md](product/done.md) の全受入は
まだ求めない。目的は衝突と性能負債を W7 に溜めないこと。

- 対象: `minimal` と `headless` プロファイル。desktop 全機能は任意。
- 見るもの: 対話+委譲+タスク+MCP の通し、W1 の deny-by-default が
  W2 承認と衝突していないこと、`minimal` の性能の基準線。
- プレビューで見つかった性能/衝突は W6 に入る前に潰す。

### W6: プラットフォーム完成

- server-api の全体(HTTP/WS/SDK 生成)。clients の desktop/CLI/Web。
- server-api は lane-api の射影として構築(エンドポイント=コマンド対応表、
  [../core/lane-api.md](core/lane-api.md) §5)。
- **詳細画面**(D-11 / D-31): desktop の別ウィンドウと Web の詳細表示面。
  `depth: detail` の接続を張り、内面・thinking・ツール引数・感情の内部状態・
  タスク一覧・記憶の閲覧を出す。Web から設定変更・記憶削除は出さない。
- 複数クライアントの排他資源調停。バックアップ。
- **完了条件**: 3クライアントが同一コアに接続し、同時接続・
  排他調停が動く(P-7xx)。desktop の主画面と詳細画面が別ウィンドウで、
  Web からも詳細画面が開ける。主画面/表層チャットには深い情報が一切出ない。

### W7: 統合と v1.0 判定

- product/done.md の全受入条件の検証。性能ベンチ(`minimal` を正、
  `desktop` は別予算)。オフライン検証。
- 性能の**目標値をここで確定**する(D-29)。W1 以降で計測した値を
  基準線として置き、以後の回帰監視に使う。先に決めた数字に実装を
  合わせるのではない。
- **完了条件**: done.md の総括条件が同時に成立する。

## 3. リスク一覧

| リスク | 影響 | 緩和 |
|---|---|---|
| アウトプロセス化による軽量化の困難 | 性能の悪化 | 測定は `minimal` プロファイルで行う(W1 で早期に基準線を取る)。ハーネス機能はホスト内なので、そもそも IPC を通らない(D-10) |
| **現行より後退した実装になる** | 機能の劣化 | 能動発話・vision・記憶スキーマは現行を出発点にする(D-28)。W3/W5 の完了条件に現行相当の挙動を含める |
| 副プロトコル分割によるプラグイン作者の負担増 | 拡張性 | SDK が「実装した面だけ名乗る」を自動生成する。作者のコードは分割前と同じ量に保つ。登録の逆も SDK が組み立て、`deactivate` を書かせない(D-32) |
| プロファイル切替でホスト文脈が残る | 幽霊ツール・幽霊 grant | W1 で I-46 を完了条件にする。kill を回収とみなさない |
| MCP へ委ねた領域の使い勝手低下 | 体験品質 | v1.0 は手書き設定で受け入れる(D-23)。導線 UI は後継(P-616)。CLI で接続確認できることだけを v1.0 の緩和とする |
| 感情ハイブリッドの不自然さ | コンパニオン品質 | 裁定器のヒステリシス調整。離散ボキャブラリの centroid をパッケージ側で調整可能に |
| V3 インポートの情報欠落 | インポート品質 | 汎用 emotion_map を既定で付与。欠落は警告のみ(拒否しない) |
| イベントソーシングの性能 | セッション長大化 | 会話ログのみに限る(D-9)。索引の最小化+PK 順走査。compaction で履歴を有界に |
| 中断時に副作用が二重に及ぶ | データ破損 | v1.0 は**自動再開しない**(D-5)。検出・片付け・報告までで止め、再開の判断はユーザーに委ねる。安全な再開は後継設計(D-4) |
| 継続観測が会話履歴を埋める | 対話品質 | 観測の要約は世界状態メモリ(揮発)に入れ、会話履歴には入れない(D-16) |
| 委譲のデバッグ困難 | 開発効率 | 詳細画面と CLI が `depth: detail` で同じ情報を見られる(D-11)。表層に出さないことと、見られないことは別 |
| 非同期委譲の報告が遅れる感覚 | 体験品質 | 報告は `inbox/enqueued` でプロセス生存中は失われない。プロセスが死んだあとはログから見せ、報告ターンは起こさない(D-5)。進捗はコンパニオンが語る(D-13)ので、遅延も会話で説明できる |
| thinking 秘匿による「考えている様子」の喪失 | コンパニオン品質 | 内面派生(visibility.md)。発話+仕草で思考の存在感を補う |
| 移行中の並行開発の衝突 | 作業効率 | ウェーブ単位で完了条件を固定し、並行は別フォルダ/別クレートに限定 |

## 4. やらないこと(移行期)

- 現行の `docs/` と AGENTS.md は、新構成が確定するまで書き換えない。
- 現行の機能停止を伴う「ビッグバン置換」はしない。ウェーブごとに
  新構成を増やし、最後に切替える。
- データ移行ツールは v1.0 の範囲外(未リリースのため、
  既存データの互換性は保証しない)。
- **後継設計の先取り実装をしない**。effect sandwich・3ストア・
  操作状態機械・署名検証・マーケットは v1.0 では作らない(D-4、D-26)。
  形式上の接点だけを残し、実装は後回しにする。
