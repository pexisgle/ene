# 承認 plane

> 実現する要件: **P-903..P-906**(承認)、**P-907**(資格情報ボールト)、
> **P-908**(監査ログ)、P-211(記憶の承認キュー)。

## 1. 設計の立場(確定済み決定)

- 承認は「事前ポリシー + AI による自動承認 + ポップアップ」の3層。
- 粗粒度のモード(すべて確認 / AI 自動承認 / すべて承認)を
  事前設定でき、ポリシーは対話からも追加できる。
- 自動承認は「確認の手間」を省くだけで、検証(ハッシュ・
  サンドボックス)を無効化しない(vision.md 設計原則5)。
- plane は Broker([../plugins/broker.md](../plugins/broker.md))の
  決定を**適用**する。Broker が窓口、plane が判断。

### 副作用の有無と承認の要否は別の軸

`side_effects` が空であることは**表層への公開可否**を決める
([../tools/registry.md §2.1](../tools/registry.md#21-層ごとの公開面p-522--d-2))が、
承認の要否を決めるわけではない。

典型は `app.screenshot`。画面を読むだけなので副作用はないが、
画面には他人には見せたくないものが映る。逆に workspace 内への
一時ファイル書き込みは副作用があるが、いちいち確認する価値はない。

plane は**副作用と機微さの両方**を見る。この2つを1つのフラグに
まとめないことが、承認モデルの前提になる。

## 2. ポリシー(P-903)

### 粗粒度モード

soul ごと(またはグローバル)に1つのモードを持つ。
**実行時の正は `approval.mode`**。プロファイルの
`plugins.policy.approval_mode` は起動時にこれを初期化するだけ
([../plugins/manifest-and-profile.md](../plugins/manifest-and-profile.md))。
対話や設定 UI で変えた値は `approval.mode` に書き、プロファイル既定は
上書きしない限り再適用しない。

| モード | 挙動 |
|---|---|
| `ask_all` | 副作用を持つ操作と機微な読み取りを全て確認 |
| `policy`(既定) | ポリシーに合致すれば自動、しなければポップアップ |
| `ai_auto` | ポリシー合致→自動、不合致→AI 判断(§3) |
| `auto` | すべて自動(上級者向け) |

### ポリシー規則(DSL)

ポリシーは「ツール名+対象」の規則列。YAML/TOML で記述。

```yaml
rules:
  # fs 系: workspace 内の読み書きは自動
  - tool: "fs.*"
    scope: "workspace"
    decision: allow
  # exec: 承認必須(対象を限定しても)。fs とは別プラグインなので
  # fs の許可がここに漏れない(D-24)
  - tool: "exec.*"
    decision: ask
  # web: 取得は自動
  - tool: "web.fetch"
    decision: allow
  # 画面取得: 副作用はないが機微
  - tool: "app.screenshot"
    decision: ask
  # MCP サーバー単位の許可
  - tool: "mcp:calendar.*"
    decision: allow
  - tool: "mcp:git.push"
    decision: ask
```

- 評価は**先頭一致**。合致しなければモードに従う。
- `decision` は `allow`(自動実行)/ `ask`(ポップアップ)/
  `ai`(AI 判断)/ `deny`(禁止)。
- `scope` は対象のスコープ(workspace/home 等)、`scope_prefix` は
  対象文字列のプレフィックス(URL・パス・宛先)。
- 規則の変更は監査ログに残る。

## 3. AI 自動承認(P-904)

- モード `ai_auto`、または規則の `decision: ai` のとき、
  承認判断をモデルに委ねる。
- 判断は**補助LLM**(`ai.tasks.approve`、
  [../tools/capabilities.md §8.1](../tools/capabilities.md#81-補助llmp-524--d-15))が、
  「操作の内容・対象・副作用・文脈(直近の対話)」を見て
  allow/deny+理由を返す。会話モデルとは別に指定できる。
- **判断の理由**は必ず監査ログに残す(P-904 の受入条件)。
- deny はポップアップに繰り上げ(ユーザーが上書き可能)。
- 補助LLM が応答不能なときは**ポップアップに落とす**。
  他の補助LLM は失敗時に諦めてよい(能動発話なら沈黙)が、
  承認だけは諦めた先が「勝手に実行」になってはならない。
- AI 判断は**高リスク操作には使わない**(§4)。

## 4. リスク分類とポップアップ(P-905)

リスクは `side_effects`([../tools/registry.md §2](../tools/registry.md#2-tooldefinition))と
**対象の機微さ**の両方から導く(§1)。

| リスク | 例 | 既定の扱い |
|---|---|---|
| なし | fs.read(workspace 内), web.fetch, utility.* | ポリシー次第で自動 |
| 低 | workspace 内の fs.write | ポリシー次第 |
| 中 | workspace 外の読み書き、`app.screenshot`、スケジュール作成 | ポリシー or ポップアップ |
| 高 | exec の破壊的コマンド、資格情報 export、`app` の入力系、外部への送信(MCP 経由を含む) | 常にポップアップ(AI 判断なし) |

- ポップアップは**全クライアントに配信**され、最も早い応答を採用
  ([../platform/clients.md §3](../platform/clients.md))。
- ポップアップには「この種は今後自動にする」の選択肢を付け、
  選択するとポリシー規則の追加提案になる(§5)。
- タイムアウト(`approval.popup.timeout`)で deny。
- **委譲由来のポップアップは表層UIでは匿名化する**
  ([../core/visibility.md](../core/visibility.md)): 操作の内容・対象・
  リスクは表示するが、「どのサブエージェントが」を示す文言は載せない。
  承認の判断自体は通常通り行える。
  詳細画面では委譲元まで表示する(D-11)。表層の匿名化は
  存在感を守るためであって、情報を消すためではない。

## 5. 対話からのポリシー追加(P-906)

- ユーザーが対話で「次から確認しないで」「これは勝手にやっていい」と
  言ったとき、soul は `approval.policy_add`(ハーネス機能ツール)を呼ぶ。
- plane は提案された規則を**ポップアップで確認**してから追加する
  (対話だけで勝手にポリシーを変えない)。
- 追加された規則は監査ログに「対話由来」として記録。
- ポップアップの「今後自動」選択も同じ経路(提案→確認→追加)。
- ユーザーは設定 UI でポリシーを一覧・編集・削除できる。

## 6. 監査ログ(P-908)

`<data>/audit.db`(専用 DB、append-only)。

| 記録対象 | フィールド |
|---|---|
| ツール実行 | ts, soul_id, tool, args の要約, decision, mode, policy_ref?, reason?, duration |
| 承認判断 | 上記+応答クライアント、AI の理由 |
| ポリシー変更 | 変更内容、由来(対話/ポップアップ/手動)、確認の有無 |
| 設定変更 | キー、新旧値、由来 |
| キャラ/プラグインのインストール | digest、確認の有無(署名は将来、D-26) |
| 記憶の削除/秘匿 | 対象、由来 |
| 共有記憶プールへの書き込み | 対象、書き手 soul、由来(補助LLM の判定か明示か)([../companion/memory.md §4](../companion/memory.md)) |
| 詳細画面への接続 | いつ、どのクライアントが深い情報を購読したか |

- 監査ログは改ざん検知のため hash chain(前行ハッシュを保持)。
- 閲覧は設定 UI と `GET /audit` API([../platform/server-api.md](../platform/server-api.md))。

## 7. 資格情報ボールト(P-907)

- API キー等を `<data>/vault`(OS キーリング優先、フォールバックは
  パスフレーズ派生キーの暗号化ファイル)に保管。
- プラグインには平文を渡さない。Broker の `cred.inject` で
  ホスト側が注入して代行([../plugins/broker.md §2](../plugins/broker.md))。
- プロバイダと MCP ブリッジの `cred.export` は例外で、
  承認必須+有効期限付き。外部サービス連携を MCP に委ねた(D-23)分、
  この経路を通る鍵が増える。**MCP サーバーの設定ファイルに平文で
  書かせない**ことがボールトを持つ理由なので、例外にはしない。
- ボールトのロック解除は起動時の1回(キーリング)または
  パスフレーズ入力。

## 8. 記憶の承認キュー(P-211)

- 記憶抽出の低信頼/機密候補は承認キューへ
  ([../companion/memory.md §7](../companion/memory.md#7-裁定p-205))。
- plane のポップアップと同じ UI 面で「覚えていい?」を確認。
- **共有記憶プールへの書き込みは別扱い**(D-7)。補助LLM が
  `scope: shared` と判定したものは、他のコンパニオンにも読まれる。
  機微な内容が共有側に回った場合の影響が大きいので、
  private よりも承認に回す閾値を低くする。
- 承認/拒否は監査ログに記録。

## 9. プライバシー(P-910)

- テレメトリなし。ローカルファースト。
- エクスポートには秘匿処理([../core/session-log.md §8](../core/session-log.md#8-エクスポートp-110))。
- クラウド LLM を使う場合、送信内容に資格情報が混入しないよう
  送信前に既知パターンをスキャン(漏洩防止)。
- **画面の内容をクラウドへ送ることは禁じない**(D-16)。
  モデルが画像入力に対応していれば渡す。ローカルに限ると視覚認知の質が
  ローカルモデルの性能で頭打ちになるためで、送るかどうかは
  ユーザーの設定で決める。ただし継続観測の有効化は明示的な操作を要し、
  既定では無効寄りにする。

## 10. 障害モード

| 障害 | 挙動 |
|---|---|
| ポップアップの応答なし | タイムアウトで deny。対話で「さっきの確認、どうする?」と再提示はしない(ユーザーの意思を尊重) |
| AI 判断の補助LLM が不能 | ポップアップに繰り上げ+警告。自動実行には**倒さない** |
| ポリシーの矛盾(複数規則合致) | 先頭一致。矛盾は設定の検証で警告 |
| 監査ログの書き込み失敗 | 操作自体を**拒否**(監査が残らない操作は実行しない、データ保全優先) |
| キーリング不可環境 | パスフレーズフォールバック。それもなければ資格情報を使う機能を無効化+通知 |
| `side_effects` 未宣言のツールが承認を要求 | レジストリ登録時に弾く([../tools/registry.md §6](../tools/registry.md)) |

## 11. 設定キー

数値は実装しながら決める(D-29)。

| キー | 説明 |
|---|---|
| `approval.mode` | 実行時の正。粗粒度モード(既定 `policy`) |
| `approval.popup.timeout` | ポップアップタイムアウト |
| `ai.tasks.approve` | AI 判断に使う補助LLM |
| `approval.policy_file` | ポリシー規則(既定は `<data>/policy.yaml`) |
| `approval.audit.db` | 監査 DB(既定は `<data>/audit.db`) |
| `vault.backend` | `auto`(キーリング優先)/ `file` |
