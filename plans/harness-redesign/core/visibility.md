# 出力秘匿モデル

> 実現する要件: **P-520**(出力秘匿モデル)、P-508(秘匿の実体)、
> P-613(要約のみ可視化)、P-104(内面表示のオプトイン)、P-910(プライバシー既定)。
> 参照: 多くのコーディングハーネスは thinking・ツール入出力を
> そのまま UI に流す。このアプリは**逆**——ユーザーは対話相手と
> 話しているのであって、パイプラインのデバッグ出力を見ていない。

## 1. 原則

**LLM の生出力は、ユーザーに見せないのが既定。**
ユーザーが見えるのは、コンパニオンが「話したこと」「思っていること
(内面、オプトイン)」「やったことの要約」「作ったもの」だけ。

根拠は3つ:

1. **コンパニオン体験**: 生の thinking・ツール JSON は「機械の臓物」であり、
   存在感(P-104..P-106)を壊す。
2. **秘匿の完全性**(P-508): サブエージェントの存在自体を秘匿するには、
   その経路に出るあらゆる派生出力(ツール引数・進捗文言)も秘匿が必要。
3. **機微情報の漏洩面削減**(P-910): 生出力は資格情報・個人情報・
   ファイル内容を原文で運び得る。既定秘匿が漏洩面を最小化する。

## 2. チャネル分類(全体表)

| チャネル | 内容 | ログ | ユーザー可視 | モデル可視 |
|---|---|---|---|---|
| 発話(assistant/message) | ユーザーへの応答 | あり | **あり** | あり |
| 内面(inner/message) | 思考・感情表出・行動意図 | あり | **オプトイン**(既定: UI に表示、設定で off) | `model_visible` のもののみ自己参照窓 |
| thinking ブロック | プロバイダの reasoning 出力 | **あり**(`assistant/thinking`、§3) | なし(派生内面として再表現、§4) | プロバイダ規約に従う(履歴返送) |
| ツール呼び出し(引数) | モデルが決定した引数 | あり(要約は投影) | **要約のみ**(`present_call` の要約形。引数原文は UI に出さない) | あり(履歴として) |
| ツール生出し | ツールの返した生データ | あり(spill 可) | **なし**。要約+成果物参照のみ | あり(ただし spill/圧縮後の形) |
| 委譲の内部 | 子セッションの全イベント | 子セッションに永続 | **なし**(internal/public 問わず。public は job カードの要約のみ) | 親は終端要約のみ |
| 承認ポップアップ | 操作の確認文 | 監査ログ | あり(確認のため)。internal 由来は匿名化 | なし |
| 診断(リング/スパン) | デバッグ情報 | リングのみ | なし。開発 CLI 限定 | なし |

- 「ユーザー可視」の列は **UI 投影の唯一の根拠**。
  この表にない経路でユーザーに生コンテンツを出してはならない。
- ツール引数・生出しがログに残るのは、`model-visible = logged`
  (P-502)のためである。**ログにあることと見せることは別の軸**。

## 3. thinking の扱い

プロバイダの thinking/reasoning ブロックは、**記録はするが表示しない**。

- **記録する**: thinking は `assistant/thinking` イベントとして
  セッションログに永続化する([session-log.md §3.3](session-log.md#33-メッセージ))。
  「何が起きたか」の事実であり、`model-visible = logged`(L-1)の
  精神を強化する——モデルが思考したものも logged になる。
- **履歴返送はプロバイダ規約に従う**: 多ターン要求で thinking を
  返送するかはプロバイダごとに決める(投影の
  `ThinkingVisibility: provider|off`、[session-log.md §9](session-log.md#9-設定キーと既定値))。
  返送する場合も投影経由で行い、logged と一致させる。
- **表示しない(絶対)**: thinking はユーザー向けチャネル
  (UI 表示・ライブバス・発話・内面表示・エクスポート既定)に
  **1件も出ない**。見せるのは派生内面(§4)のみ。
- **容量対策**: thinking はログ容量の主因になり得る。
  compaction は `assistant/thinking` を要約対象に含め、
  shadowed 範囲の thinking は投影で要約に置き換わる
  (元行は消えない、L-3)。管理目的では精密書き換え
  ([storage-model.md §6](storage-model.md#6-精密書き換え唯一の削除経路))の対象にもできる。
- **実装上の義務**: プロバイダ適応はストリームから thinking を検出し、
  **発話チャンクに混ぜない**(混ぜると発話が汚染される)。
  検出した thinking は(1)ログへ記録、(2)内面派生の素材
  ([§4](#4-thinking--内面の派生任意))にのみ使う。

## 4. thinking → 内面の派生(任意)

thinking は記録されるが、ユーザーには決して見せない(§3)。
「考えている様子」の表現は内面チャネルへの派生で行う。

- **派生**: ターン終了後(バックグラウンド)、`assistant/thinking`
  について、感情エンジンが思考の要点を
  `inner/message{aspect: thought}` として**再生成**する
  (原文のコピーではなく、キャラの語り直し)。
- 派生はオプトイン(`mind.inner.derive_from_thinking`: 既定 `true`)。
  プロバイダが thinking を出さない構成では何も起きない。
- 派生内面は通常の `model_visible` 規則に従い、自己参照窓に載り得る
  ([../companion/inner-channel.md §3](../companion/inner-channel.md#3-自己参照p-502-両立))。
- 派生処理は軽量ローカルモデル(`ai.tasks.inner`)で走る。
  対話レーンを塞がない。

## 5. UI 投影規則(P-613 の実体)

- ツール呼び出しの表示は `present_call`/`present_result` が作る
  **要約形**のみ。引数原文・生出しは投影しない。
- 委譲由来の呼び出しは投影自体に出ない(P-508)。
  public job は「おつかいカード」(job 定義の title/progress)のみ。
- 「詳細を見る」系の UI は**作らない**(内部機構への入口になるため)。
  デバッグ情報は CLI 限定([../platform/clients.md](../platform/clients.md))。
- ライブバスのイベントもこの規則に従う: `tool.call`/`tool.result` の
  ペイロードは要約形であり、チャンク系イベントは発話と内面のみ。

## 6. 検証(受入条件)

- **投影走査テスト**: UI 投影とライブバスの全経路を走査し、
  生の thinking・ツール引数・ツール生出し・子セッションの
  コンテンツが出ていないことを CI でアサートする。
- **internal 秘匿テスト**: internal 委譲の存在を示すイベントが
  ユーザー可視チャネルに1件も出ないことを検証
  (承認ポップアップの匿名化を含む)。
- **エクスポート秘匿**(P-110): 上記チャネルの秘匿は
  エクスポートの既定([session-log.md §8](session-log.md#8-エクスポートp-110))にも適用される。

## 7. 設定キーと既定値

| キー | 既定 | 説明 |
|---|---|---|
| `mind.inner.derive_from_thinking` | `true` | thinking → 内面派生 |
| `mind.inner.ui_visible` | `true` | 内面の UI 表示(オプトインの既定) |
| `harness.tool_output.ui_summary_chars` | `200` | UI 投影のツール要約上限(文字) |

## 8. 障害モード

| 障害 | 挙動 |
|---|---|
| プロバイダが thinking を発話チャンクに混ぜて返す | 適応層で分離する(§3 の義務)。分離不能なプロバイダは「thinking 非対応」として扱い、発話のみ採用 |
| 内面派生モデルの失敗 | 派生を諦める(thinking はログに残る)。対話に影響なし |
| ツール生出しをモデル履歴に載せると窓が溢れる | spill([context-assembly.md §5](context-assembly.md#5-spill))。これは「モデル可視」の軸の話であり、ユーザー可視とは独立 |
| ユーザーが「全部見せて」と要求 | 対話で断るか、CLI/診断経路(開発者)を案内する。UI の秘匿既定は対話では変えない(P-520 の既定は崩さない) |
