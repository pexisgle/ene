# 不変条件と検証

> 実現する要件: **P-502**(model-visible = logged の検証)、P-510 の検証面。
> 参照: pi Part 9(invariants・race catalog・test tiers)を Ene 向けに再構成。

この文書は、設計が主張する性質を**検証可能な形**で一覧化する。
設計の正しさはここにある。実装はこれらのテストを通すこと。

## 0. v1.0 と後継設計の切り分け(D-4 / D-5)

耐久性の高度な機構(effect sandwich・操作状態機械・レジスタ)は
**後継設計**であり、v1.0 では実装しない
([durability.md](durability.md)、[operations.md](operations.md)、
[storage-model.md](storage-model.md) の各冒頭)。

そのため不変条件も2つに分かれる。

| 区分 | 意味 |
|---|---|
| **v1.0** | 実装と同時にテストを書く。CI の門になる |
| **後継** | 後継設計を実装するときに有効になる。v1.0 では検証しない |

後継の不変条件を消さずに残すのは、v1.0 の実装がそれらを**将来
成立させられない形**にしていないかを、設計時に照らすためである。

## 2. 競合カタログ

各競合には**ちょうど2つの耐久履歴**がある。両方を、手動駆動で、
両方の順序でテストする。

### v1.0 で検証するもの

| 競合 | 2つの順序 |
|---|---|
| 同一レーンへの `prompt` vs `prompt` | 一方が受理、もう一方は `LaneBusy` |
| `abort` vs 応答のセットルメント | マーカー先 → 正規化 `aborted` / 応答先 → stop reason を保持 |
| `abort` vs ツール結果のコミット | 計画結果を合成 / 実際の結果がそのまま成立 |
| `cancelQueued` vs checkpoint 消費 | `cancelled` / `already_consumed` |
| `next_run` vs 受理 | 今回の run が捕獲 / 次回のために残留(承認の遅延応答。ask-user 回答は同一操作の `wake`) |
| `close` vs 保留中の手動操作 | 操作は実行せず拒否。耐久状態はコミット済み接頭辞 |
| 音声割り込み vs TTS 再生完了 | 割り込み先 → `interrupted` で確定 / 再生先 → 通常完了 |
| `delegate.cancel` vs 子の完了コミット | cancel 先 → `cancelled` / 完了先 → cancel は `already_completed` |
| 子の `question` vs 親の `delegate.answer` | 質問先 → 回答が届く / 取下げ先 → 回答は `not_found`(再試行安全) |
| 報告 wake の滞留 vs ユーザー発話 | ユーザー wake が常に先。報告は次ターン境界で結合して届く |
| 質問のタイムアウト仮定 vs 遅着した回答 | 仮定成立後 → 回答は棄却されログに残る(子は仮定を維持)/ タイムアウト前 → 回答を採用 |
| **自動昇格 vs ユーザーの次の発話** | 昇格先 → 委譲が始まり、発話は次ターンへ / 発話先 → 昇格は次ターンで判断し直す |
| **異常終了 vs job の完了コミット** | 終了先 → `interrupted` として検出 / 完了先 → 通常の `completed` |
| **ファイバー unload vs 進行中の tool.call** | unload 先 → 呼び出しは `cancelled`/`plugin_unloading`、登録は回収済み / 完了先 → 正規の result のあと unload。半登録は残らない(I-46) |

### 後継設計で検証するもの

| 競合 | 2つの順序 |
|---|---|
| `abort` vs pre-step のフォローアップ | フォローアップは破棄 / コミットされて run が継続 |
| `set_model` vs 生成ステップの開始 | 旧スナップショットを使用 / 新スナップショットを使用 |
| `abort` vs 構造変更のコミット | マーカー先 → エントリなしで `aborted` / 構造コミット先 → `completed` |
| 手動コンパクションの予約 vs アイドルツリーの書き込み | 予約先 → 書き込みは待機 / 書き込み先 → 準備は新 leaf を使用 |
| 遅延書き込み vs abort | 書き込みはどちらでも abort を生き延びる |
| `close` vs セットルメント | セットルメントは放棄され `effect_pending` のまま / フラグ設定前にコミット済み |

## 3. テスト階層

### 階層 A — 状態と再開(v1.0 は縮小版)

**v1.0 の範囲**: 異常終了からの起動で、中断が検出・片付け・報告される
こと。未消化の inbox はログから見え、実行は再開されない(D-5)。
中断なし実行との一致は**求めない**。求めるのは、
「壊れた状態のまま起動しない」ことと「同じ副作用を繰り返さない」こと。

- プロセスを各段階で強制終了し、次回起動で `interrupted` が確定すること。
- 片付け対象(workspace の一時ファイル)が消え、成果物は残ること。
- 未 claim の inbox(発話・委譲報告・ask-user)はログから復元され、
  `abandoned_interrupt` で閉じ、次ターンの入力として claim されないこと。
- `queued` の job は起動後も `queued` のままで、自動実行されないこと。
- 中断の報告が次のターンでコンパニオンの発話として届くこと。

**後継の範囲**: [operations.md](operations.md) のすべての状態について、
耐久化 → close → reopen → 次の動作の検証。各回復接頭辞ごとに
close → reopen → resume → 中断なし回復との比較。

### 階層 B — 書き込み適合性

公開ハーネスを**計測ストレージデコレータ**に対して走らせる:
`commit()` を包み、すべてのトランザクションの書き込みを順に記録するスパイ。
比較用の耐久ログは存在しない。デコレータがオラクルである。

v1.0 でこの階層が捕捉する回帰:

- コミット**前**に通知が発火する(I-26)。
- ある stop reason で応答が欠落する。
- usage が耐久化される前に次の処理が始まる。
- 補助LLM の消費が台帳に載らない(I-35)。

### 階層 C — 決定的インターリーブ

§2 の全競合を、両方の順序で、手動駆動で。v1.0 は v1.0 の表のみ。

### 横断要件

- **バックエンド適合性**: 1スイート・全バックエンド・同一結果。
- **駆動の等価性**: 同一シナリオの自動駆動と手動駆動が、
  バイト同一の耐久状態を産む。
- **シグナルの所有**: 公開面はシグナルを受け取らない。
  シグナルを運ぶ要求は剥奪される。型とテストでアサート。
- **台帳完全性**(I-8、I-35)。
- **クエリ計画のガード**: 分岐走査の `EXPLAIN QUERY PLAN` が
  インデックス走査であることを確認(全 entries スキャンの禁止)。
- **トランザクション規律**: すべてのトランザクションが
  `BEGIN IMMEDIATE` で開くことをアサート。「読み → 他接続コミット →
  書き込み」が成功する回帰テスト。
- **計測の秘匿性**: スパン属性にコンテンツ(プロンプト・補完・
  ツール引数/結果・ファイル内容・資格情報)が含まれないことを、
  属性スキーマの宣言性と CI 走査で検証
  ([observability.md §3](observability.md#3-プライバシー規則絶対))。
  これは表示の深さとは**別の話**で、詳細画面に出る情報でも
  計測スパンには載せない。スパンは外部に出ていく可能性があるため。
