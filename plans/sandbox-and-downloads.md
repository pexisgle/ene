# Ene プラグインサンドボックス・統一ダウンロード・許可システム 実装プラン

## 1. 目的

Ene のプラグイン・サイドカー・モデルの取得と実行を、統一 Artifact システムと OS 強制サンドボックスで安全に管理する。

- ダウンロードを「任意サイトへの動的アクセス」と「実行可能 Artifact のインストール」の 2 系統に分離する
- プラグインには直接の OS アクセスを与えず、ホストが仲介する Broker 経由のみで操作させる
- 許可を「要求できる機能」と「実際の承認」の 2 層に分け、全体ポリシーとプラグイン別ポリシーで自動許可を実現する
- 公式 Artifact は署名付き Catalog で、Catalog 外 Artifact はローカルファイル + SHA-256 の手動インポートのみ許可する

## 2. 全体方針

### 2.1 対象プラットフォーム

- 開発・CI 対象: Linux のみ
- 配布対象: Linux、Windows(クロスコンパイル)
- macOS は非対応。サンドボックス初期化に失敗する環境ではプラグインを起動しない

### 2.2 原則

- プラグイン・サイドカー・stdio MCP・ブラウザは、すべて同じ Artifact・Broker・リソース管理下に置く
- プラグイン自身に socket・DNS・HTTP クライアント・Cookie 保存領域・API キーを直接渡さない
- ユーザーファイルの読み書きは `FileBroker` 経由にし、プラグインへ直接のファイルパス権限を与えない
- 自動許可は確認ダイアログを省略するだけであり、署名・hash・サイズ・接続先・サンドボックス・リソース制限の検証を無効化しない
- 後方互換性は維持しない。新しい manifest・IPC・Broker へ一括移行する

## 3. サンドボックス設計

### 3.1 必要最小権限

プラグイン・サイドカー・stdio MCP のプロセスには次のみを見せる:

- 読み取り専用のコード・Artifact ディレクトリ
- 容量制限付きの専用 temp ディレクトリ
- Broker IPC チャネル

実際の `HOME`、`PATH`、作業ディレクトリ、資格情報領域、ユーザーファイル領域は渡さない。環境変数もホストが厳密に制御する。

### 3.2 Linux サンドボックス

以下を必須とし、いずれかが初期化できない場合はプラグインを起動しない:

- Landlock: ファイルシステムへのアクセスをホスト指定のパスに制限
- `no_new_privs` + seccomp: 権限昇格と不要なシステムコールを禁止
- cgroup v2: メモリ・CPU・プロセス数・デバイスアクセスを制限
- rlimit と FD 数上限: リソース枯渇攻撃を防止
- ネットワーク名前空間: プラグインに直接のネットワークアクセスを与えない

### 3.3 Windows サンドボックス

以下を必須とする:

- AppContainer + Low Integrity: 低権限の分離されたセキュリティコンテキストで実行
- 明示的な ACL: ユーザーファイル・資格情報領域へのアクセスを禁止
- ネットワーク Capability なし: 直接のネットワークアクセスを禁止
- Job Object: 子プロセス生成の禁止、CPU・メモリ・プロセス数制限
- 制限付き token: 管理者権限・SeDebug など特権の除去

### 3.4 Broker 設計

- IPC に単一の認証済み Broker チャネルを導入する(プロトコル v8 へのバージョンアップを想定)
- プラグイン識別情報はホストがチャネルに固定し、プラグインが偽装できないようにする
- Broker 種別:
  - `Artifact`: 実行可能 Artifact の取得・検証・切替
  - `File`: ユーザーファイルの読み書き・保存
  - `Network`: ダウンロード・Web アクセスの仲介
  - `Process`: 子プロセス起動の仲介
  - `Credential`: 資格情報の通信時注入
  - `Platform` / `Db`: プラットフォーム機能と DB アクセス
- プラグインには Broker 経由以外の手段で OS へ触れる経路を残さない

## 4. 許可モデル

### 4.1 2 層構造

1. **Manifest 層(要求できる機能の上限)**
   - 署名付き `PluginManifest` に以下を宣言する
     - 論理 FS スロット: `workspace`、`media` など(実パスは記録しない)
     - 固定接続先: HTTPS の正確な origin リスト
     - `dynamic_web`: 未知の公開 Web サイトへのアクセスを要求できるか
     - 必要な Artifact、サイドカー、ホストサービス、リソース上限、side effect
   - metadata にない権限は、自動許可設定があっても要求できない

2. **承認層(実際の許可)**
   - インストール時に「要求可能な権限」を事前承認する(通信自体の一括許可ではない)
   - FS は初期許可ゼロとし、ユーザーがフォルダを選択する
   - FS 許可は `plugin_id + manifest_digest + slot + canonical_path + access` に結び付け、更新後は再確認する

### 4.2 承認モードとカテゴリ

ホスト側に以下を追加する:

- `ApprovalMode::{Inherit, Ask, Allow, Deny}`
- `ApprovalCategory`(カテゴリ列挙)
- `ApprovalPolicy`(全体ポリシー)
- `ApprovalRequest`(要求オブジェクト)
- `ResolvedApproval`(解決結果)

カテゴリ:

- FS 読取・作成・変更・削除
- 固定 origin 通信・動的 HTTPS・HTTP・LAN・loopback
- Web ファイル保存
- Plugin・Sidecar・Model のインストールと更新
- プロセス・shell・ブラウザ・プラットフォーム機能
- 資格情報の利用

### 4.3 判定順序と優先度

判定順序:

1. 強制セキュリティ制約(署名・hash・サイズ・SSRF ブロックなど)に違反していないか
2. プラグイン別設定
3. 全体設定
4. `Ask`(確認ダイアログ)

プラグイン別設定は全体設定より優先する。プラグイン別設定は署名済み `plugin_id` と publisher に結び付け、publisher が変わった場合は無効化する。

### 4.4 自動許可(全体・プラグイン別)

- 全カテゴリの初期値は `Ask`
- 全体ポリシーを既定値とし、プラグインごとに「継承・確認・自動許可・拒否」を上書きできる
- 「すべて自動許可」は各カテゴリを一括設定するプリセットとして提供する
- 高危険度カテゴリ(実行 Artifact 更新、新規フォルダ権限、HTTP、LAN、資格情報追加)も、二段階の強い警告を確認した後に全体またはプラグイン別で自動許可できる
- 高危険度の全体自動許可が有効な間は、設定画面へ常時警告を表示する
- 自動許可された操作も、プラグイン・カテゴリ・対象・適用ルール・結果を監査ログへ記録する。秘密・本文・ユーザーファイル内容は記録しない
- 設定画面には全体ポリシー表、プラグイン別上書き、適用理由、許可対象、緊急停止、`Ask` への一括リセットを追加する

## 5. FS・Web アクセス・ダウンロード

### 5.1 FS アクセス

- FS の自動許可には、ユーザーが事前設定した実フォルダと読取・書込範囲が必要
- プラグインが任意の絶対パスを指定して権限を得ることはできない
- ユーザーファイルの操作は `FileBroker` 経由に限定する

### 5.2 動的 Web アクセス

- `dynamic_web` を宣言したプラグインは、`NetworkBroker` 経由で任意の公開サイトへアクセスできる
- 未許可の origin には、正確な origin(scheme・host・port)を表示して初回承認する
- 許可は現在の manifest にだけ保持し、更新またはユーザーによる取消で失効する
- リダイレクト・API・iframe・サブリソースも、別 origin なら追加承認する
- 同時発生した承認要求は 1 つの画面にまとめる
- HTTPS を標準とする。HTTP は盗聴・改ざん警告付きで別承認とし、資格情報を注入しない
- loopback、プライベート IP、link-local、クラウド metadata、DNS rebinding は常に拒否する。LAN アクセスは v1 では許可しない
- `DynamicHttps=Allow` なら、動的 HTTPS の初回承認を省略できる

### 5.3 Web ファイル保存(閲覧系ダウンロード)

- 通常の Web ファイルはホストの一時領域へ取得する
- 取得完了時に、最終 URL・種類・サイズ・SHA-256・保存先を表示して毎回承認する
- 承認後に `FileBroker` が保存する。プラグインが直接書き込まない
- 保存ファイルは名前を無害化し、SHA-256 と取得元を記録する
- 自動実行・自動展開・既存ファイルの自動上書きは禁止する
- 中止・失敗時は一時ファイルを削除する
- 自動保存には、保存先・最大サイズ・競合時の名前変更規則を事前設定する。未設定の場合は `Allow` でも確認画面を表示する

### 5.4 ダウンロードしたファイルの実行禁止

- Web ダウンロードしたファイルを Plugin・Sidecar・Model として直接インストールすることはできない
- 実行可能なものは必ず「6. Artifact 管理」の経路を通す

## 6. Artifact 管理(実行可能なダウンロード)

### 6.1 構成

新しい `ene-artifact` 層に以下を集約する:

- TUF ベースの署名付き Catalog
- CAS(SHA-256 ベースの Content-Addressable Storage)
- 再開可能ダウンロード(Range・ETag)
- 検証・インストール状態管理
- GC・ロールバック

### 6.2 metadata と Catalog

- プラグイン metadata には URL 群ではなく Artifact ID とバージョン条件を書く
- 実際の URL・許可 origin・リダイレクト先・SHA-256・サイズは署名付き Catalog 側で管理する
- Catalog metadata は起動時、6 時間ごと、手動更新時、設定画面表示時に更新する。この段階では本体を取得しない
- インストール済みバージョンと署名付き Catalog を比較し、更新内容・サイズ・digest・依存関係・権限差分を表示する

### 6.3 更新

- Plugin・Sidecar の更新は毎回ユーザー承認を必要とする(`ArtifactUpdate=Allow` なら自動取得・検証・切替)
- Model は固定バージョンを基本とし、更新候補だけを通知する
- 同一バージョンで digest が変わった更新、期限切れ Catalog、署名不正、rollback、サイズ超過は自動許可に関係なく拒否する
- 更新失敗時は旧版を維持し、一世代のロールバックを可能にする
- 許可単位は `artifact_id + version + digest + max_bytes` とし、許可済みホストから別ファイルを取得することを防ぐ

### 6.4 CAS 実装要件

- ダウンロードは `.part` ファイルへ行い、排他ロックで多重取得を防ぐ
- サイズ・digest を検証してから fsync、atomic activation を行う
- 公式 Artifact も同じ Catalog・CAS・許可ポリシーを使用する
- Catalog 外 Artifact はローカルファイルと SHA-256 による手動インポートだけを許可する

## 7. セキュリティ境界(常に有効)

自動許可・動的 Web・更新に関係なく、以下は常に拒否する:

- 署名・hash 不一致、期限切れ Catalog、rollback 攻撃
- サンドボックス初期化失敗時のプラグイン起動
- プラグインによる直接の socket・DNS・プロセス・資格情報アクセス
- SSRF(loopback・プライベート IP・link-local・クラウド metadata・DNS rebinding)
- 実行時 `npx -y` や `uvx` による暗黙ダウンロード
- archive traversal(展開時のパス逸脱)
- ディスク枯渇(サイズ上限を超えた取得)
- 承認トークンの別プラグイン・別リクエストへの再利用

## 8. 実装ステップ

### Phase 1: 基盤

1. `ene-artifact` crate の新設(CAS・Catalog・検証・再開ダウンロード)
2. IPC の Broker チャネル化とプロトコル v8 移行
3. Manifest スキーマの拡張(論理 FS スロット・固定 origin・`dynamic_web`・Artifact 要件・side effect)

### Phase 2: サンドボックス

4. Linux: Landlock + seccomp + `no_new_privs` + cgroup v2 の実装と必須化
5. Windows: AppContainer + Job Object の実装と必須化
6. プラグイン起動時の環境・リソース制御(env・FD・rlimit・temp)

### Phase 3: 許可システム

7. `ApprovalMode`・`ApprovalCategory`・ポリシー解決の実装
8. 全体ポリシー・プラグイン別上書き・高危険度二段階警告
9. 設定画面(ポリシー表・監査ログ・緊急停止・一括リセット)
10. 監査ログ記録

### Phase 4: 動的 Web とダウンロード

11. `NetworkBroker` の実装(origin 承認・リダイレクト追跡・SSRF ブロック)
12. Web ファイル保存フロー(一時領域 → 承認 → `FileBroker` 保存)
13. Artifact 更新検知と自動更新フロー

### Phase 5: 移行と検証

14. 既存プラグイン(utility・fs・anthropic・local-llm など)の新 manifest・Broker への移行
15. ドキュメント整備(`docs/concepts/plugins-and-mcp.md` と `docs/ja/` 対応版、設定画面の i18n)
16. テスト拡充と CI 追加

## 9. テスト計画

### 単体・統合

- ポリシーの継承、プラグイン別優先、明示的上書きの解決をテスト
- metadata 外権限・publisher 変更・署名不正・hash 不一致が自動許可されないことを検証
- FS 範囲逸脱、symlink 交換、SSRF、DNS rebinding、LAN 区分、承認トークン再利用を検証
- Artifact 自動更新の成功、失敗時ロールバック、同一バージョン digest 変更を検証
- TUF の署名・期限・rollback、ダウンロード再開、archive traversal、ディスク枯渇、atomic rollback を検証

### サンドボックス脱出試験

- 悪意あるテストプラグインから、未許可 FS、直接通信、localhost、任意プロセス、秘密情報、承認トークン再利用がすべて拒否されることを検証
- Linux CI と Windows ネイティブ CI(またはクロスビルド + 起動テスト)で実行

## 10. 前提と既定値

- 対象 OS は Linux と Windows。macOS と弱いサンドボックスへのフォールバックは対象外
- `dynamic_web` は任意の公開サイトへアクセスできるが、無条件・無表示のアクセスを意味しない
- Web 閲覧用ダウンロードと実行可能 Artifact のインストールは完全に分離する
- 公式プラグインも同じ Catalog・検証・権限承認経路へ登録する
- 後方互換性は維持しない。新しい manifest・IPC・Broker へ一括移行する
- 初期値は全カテゴリ `Ask`
- プラグイン別設定が全体設定より優先される
- 高危険度の全体自動許可は可能だが、初回の二段階警告が必須
